# Implementation Plan

## M119 — Mode-None Milestone Identity Enforcement {#M119}

**Goal:** Close the `mode: none` milestone-identity gap on all three surfaces. `/spec-write` can currently skip the mint because the allocation guard is one long paragraph whose sequential branch reads first and whose tracker-less branch reads last, and because the plan template independently scaffolds a sequential milestone key. Probe #73 cannot catch the result because its grandfathering is keyed on filename shape alone, making a freshly mis-named plan byte-identical to a legitimately legacy one. Repositories already in the bad state have no repair path, and their window closes at first release.

**Prerequisites:** None external. STE-440 and STE-441 are independent and may land in either order. STE-442 depends on nothing in STE-441 but shares the exemption vocabulary STE-441 introduces, so landing STE-441 first avoids a temporary state where the migration offers to repair plans the operator has no way to exempt.

**Release target:** v2.59.0

**Migration:** `mode-none-sequential-milestone` — STE-442 introduces the registry entry this milestone is bound to. Its `introduced_in` is `2.59.0`, matching the shipping version as the coverage rule enforces, not `2.56.0` as the registry's prose definition would suggest.

**Provenance:** field report captured via `/dev-process-toolkit:report-issue` on 2026-08-04 against v2.58.0 — two sibling repositories under identical `mode: none` configuration diverged, one minting correctly and one producing sequential plans with no identity key, with `/gate-check` reporting clean in both. Design session and claim-by-claim verification: `/dev-process-toolkit:brainstorm`, same date.
