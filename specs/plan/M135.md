# Implementation Plan

## M135 — Epic Binding Convergence {#M135}

**Goal:** Make the Jira Epic-keyed milestone binding converge, and stop the gate at the archival boundary from certifying that it did when it did not. The canonical milestone name embeds the key that Epic creation allocates, so the name can never be the join key between the writer and the reader — every bind mints a second Epic under a fresh key, reports success, and leaves the ticket parented to something the reader will never accept. The token already carries the Epic's identity, so binding resolves by key instead and the name stops being load-bearing. Two riders on the same subject travel with it: a remedy ordering a flag that does not exist, and prose telling a reader to supply a value the code will reject.

**Prerequisites:** M134 merged (v2.73.0). Serial invariant only — no FR here depends on anything M134 introduced.

**Release target:** v2.73.1 (provisional; PATCH — all six FRs are `Fixed`, no new user-facing capability). **This is the first PURE-FIX milestone of the program, so the bump trap produces a materially wrong answer here for the first time.** Every previous milestone mixed `Added`/`Changed`/`Fixed`, so the two readings agreed and the defect stayed invisible; a pure-fix set is the only shape that separates them. The helper reads a camel-cased `changelogCategory` while the frontmatter writes the snake-cased `changelog_category`, and the two disagree here by a whole release line:

| Key read | Inferred bump | Version |
|---|---|---|
| `changelogCategory` (what the helper actually reads) | PATCH | v2.73.1 — CORRECT |
| `changelog_category` (what the frontmatter writes) | MINOR | v2.74.0 — WRONG |

At `/ship-milestone`: run BOTH controls, report BOTH numbers, and state which key was actually fed. A report reading "v2.73.1, falsified" is NOT sufficient — it is indistinguishable from having fed the wrong key and gotten lucky, which is the whole failure mode. Report the pair. Codename decided at `/ship-milestone`.

**Migration:** `none` — every change is toolkit-internal. No consumer-authored file changes shape and no consumer artifact gains or loses a key. The Epic-creation contract change is an instruction to the toolkit's own minting step, not to anything a consuming project writes.

**Scope boundary:** three findings from the same triage are deliberately excluded and are NOT to be folded in. Phantom milestone ids listed off an Epic's key rather than its summary token; the mixed numeric/Epic archive sort order; and the absence of the Epic-degrade token from the capability-gap token set. All three are low severity and batched elsewhere. The `gh gist create -s` publish defect belongs to a different report and a different milestone. Excluding the token-set finding constrains STE-523 in particular: the numeric-under-Epic path keeps its current capability result rather than gaining an informational row, because adding a token would drag the closing-summary contract and its probe into a milestone about binding convergence.
