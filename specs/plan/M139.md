# Implementation Plan

## M139 — Tracker-First Linear Milestones {#M139}

**Goal:** A Linear milestone identity is derived from the milestone the tracker created, the way a Jira one is derived from its Epic.

**Prerequisites:** M138 (both milestones edit `resolve_milestone_identity.ts`; serial execution keeps them off each other).

**Release target:** v2.76.0 (provisional, minor — all three FRs are Changed).

STE-377 made Jira claim-on-create: create the Epic, read the key back, derive `M_<epic-key>`, collision-free with no scan. Its AC.4 pinned "Linear and mode:none unchanged" as a regression block, and STE-417 AC.5 later re-scoped that block to Linear alone. STE-417's own scope boundary names the rest explicitly as deferred: extending key-derived identity to Linear by deriving from the native milestone object's server-assigned id. This milestone lands that deferral. The pin is retired here by name.

Existing projects adopt with no action and nothing already written is rewritten — the union grammar carries `M<N>` and `M_<key>` side by side, and `milestoneBranchToken` already renders the second as `m_<key>`. No migration entry ships: with nothing repairable, a registry detector would report itself forever, which is the residue STE-442 was faulted for. The notice fires once, at the first mint.

The sequential allocator is retargeted rather than deleted, following STE-417 and STE-522: it keeps the collision refusal that still guards a hand-typed identity.
