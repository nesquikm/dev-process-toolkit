# Implementation Plan

## M_2306b6 — Proven Live {#M_2306b6}

**Goal:** Prove the shared-tracker programme end to end. The scenario set that passes offline, against tracker doubles that honour their own queries, must also pass against a real Jira space and a real Linear project with two real repositories. A program grades the live run from recorded evidence, and the programme's release cannot ship without that proof at the current code.

**Prerequisites:** Ships FOURTH and last, after M_947c79, M_685ff6 and M_85e846 are merged and released. Its scenarios drive their front doors and hooks, so nothing here can be written against a moving target. The milestones ship serially because parallel milestones collide on pinned counts and the release files. Operator preconditions before the live run: workspace trust for `../dpt-shared-jira-a`, `../dpt-shared-jira-b`, `../dpt-shared-linear-a` and `../dpt-shared-linear-b`; a second throwaway Jira space (for example DST2), passed as `--jira-repoint-from`, without which the Jira repoint is a named skip and the release gate refuses the Jira proof; Linear headroom for the seven expected issues plus the worst-case allowance Phase 0 prints; DST visible with create permission.

**Release target:** v2.90.0, one minor above M_85e846's v2.89.0 (or above whatever release lands between), because all three FRs are Added. Verify with `inferBump` against the FR frontmatter and the CHANGELOG rather than trusting this line. This release is the programme's, and STE-618 blocks it until both live verdicts pass at the current behaviour digest, the Jira one with its repoint scenario passed. After release, sharing repositories raise `min_dpt_version` to this version, the readiness precondition M_947c79 documents. The release notes must name the known duplicate-container race D-4 (STE-616 § What ships as a known defect) in the release's own prose, not only in the FR: this is the version that declares the programme ready, and a passing live run proves only the paths it took.

**Migration:** none. No consumer-artifact convention changes. The new skill, grader and gate are maintainer tooling, and the `### Live proof` table is a convention of this repository's own plans.

### Risks

| Risk | One side | The other side |
|------|----------|----------------|
| The live run finds defects in the earlier milestones | Every fix changes the behaviour digest and needs a fresh live run | That is the gate working; plan for a second run per tracker |
| Linear's free-plan issue cap | A run that reaches it aborts with issues spent that no tool can archive | At most seven issues per run, stated at Phase 0; the operator archives by hand; a cap abort is never a pass |
| DST collects items it cannot delete | About a dozen Jira items per run, each moved to Done | The run nonce scopes teardown and stops old items from matching new titles |
| Doubles drift from the real trackers | The offline suite passes against behaviour the real tracker lacks | The live smoke runs the same registry against the real ones, and an unknown conjunct fails loudly |
| Operator-only steps stall the milestone | The last FR cannot close without keystrokes | The task list names them in order; no agent is asked to type them |
| Old clients sit outside every code guard | A teammate below the floor writes anyway | The detector flags what such a client writes, and the smoke measures its recall |
| The mutation matrix slows the suite | Each row re-runs scenarios against a copied tree | Rows re-run only the scenarios they name, in unique temporary directories |
| A receipt is a file any process can write | A hand-written receipt could look like a decision | The hook of STE-607 trusts only receipts announced by a command in its `RECEIPT_ANNOUNCING_MODULES`; the live grader re-checks that on real transcripts and fails any receipt no front-door run announced |
| Live evidence ships to every installing user | A bundle could leak account ids, site hosts or home paths | Bundles are field projections, and the grader refuses any that still matches a leak pattern |
| The committed bundles are re-graded by the current grader on every later test run | A later grader change that reads a new field reds the programme's shipped proof and blocks unrelated work | Post-release mode grades the recorded scenario set; a grader change that breaks an old bundle must be named in its own FR, never silenced by editing the bundle, whose hash the plan pins |
