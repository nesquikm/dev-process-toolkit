# Implementation Plan

## M121 — Tracker-less Conformance Coverage {#M121}

**Goal:** Make `mode: none` — the default tracker configuration for every project this toolkit bootstraps — an always-on third leg of the project-local `/conformance-loop` and `/smoke-test` skills, and make the leg set one-way-derived data so it cannot silently drift again. The toolkit's most common downstream configuration is currently its least-tested path: the loop hardcodes exactly two legs, and `/setup` never writes a `mode: none` line because absence of `## Task Tracking` *is* none.

**Prerequisites:** None external. Internal sequencing is strict — see the dependency graph below.

**Release target:** v2.61.0

**Migration:** `none` — no consumer-artifact **convention** changes. No file layout, no frontmatter schema, no identity format, no tracker-binding shape: nothing an existing downstream project would need `/upgrade` to repair. The verdict rests on that and only that.

It does **not** rest on the work being confined to this repository, which would be false. **Seven of this milestone's thirteen FRs** modify surfaces that ship to every plugin consumer, and a future reader changing this milestone's scope should audit the verdict against this list rather than take it on faith. (The count is restated rather than softened: it read "four of the nine" until STE-457, when both numbers had gone stale. Replacing a wrong number with a vague word would make the claim unfalsifiable instead of wrong, which is worse.)

**`migration: none` RE-ARGUED against the widened set (STE-457), not inherited from the four-surface form.** The verdict was reached when this table had four rows, and the fifth — `plugins/dev-process-toolkit/skills/implement/SKILL.md` — is the most-run skill the toolkit ships, so re-deriving it is cheaper than trusting that the reasoning generalised. It does. Every consumer receives the same file with two rewritten bullets and nothing else: no file layout moves, no frontmatter key is added or renamed, no identity format changes, no tracker-binding shape changes, and `LocalProvider`'s implementation is byte-unchanged. The `.dpt/locks/<id>` artifact the new instruction names is the artifact `LocalProvider.claimLock` has always written — a consumer that already ran `/implement` under `mode: none` and *did* claim has exactly the disk the new step 0.d asserts, and a consumer that did not has nothing to repair, only a next run that now refuses instead of proceeding. There is no existing artifact for an `/upgrade` migration to rewrite, because the change is entirely in what the skill *instructs*, never in what it leaves behind.

**The one honest consequence, named rather than buried:** a consumer whose next `mode: none` `/implement` still fails to claim will now be **hard-refused at Phase 1 exit** where it previously proceeded silently. That is the intended behaviour and it is a behaviour change on a shipped skill — but it is not a *convention* change, it needs no scripted repair, and its remedy is one step the refusal itself names. It earns a changelog line, not a migration.

**Provenance:** design session `/dev-process-toolkit:brainstorm`, 2026-08-07, against main at v2.60.0 (gate 6605 pass / 15 skip / 0 fail). The design rests on a measured falsifiability result rather than an inference — see § Falsifiability baseline below.

### Falsifiability baseline (measured 2026-08-07)

Widening `SMOKE_LEGS` in `adapters/_shared/src/smoke_fixture_groups.ts` from `["linear","jira"]` to a three-member array containing a synthetic leg, then running the full gate, returned **6605 pass / 15 skip / 0 fail — byte-identical to the clean baseline. Zero tests went red.**

`grep -rln "SMOKE_LEGS\|SmokeLeg" tests/ adapters/` returns **only the defining module**. The exported "authority" for the leg set is imported by nothing; at the time of measurement its only consumers were two call sites inside its own file — `appliesToLeg`'s unknown-leg fallback and the CLI's `--leg` membership guard. (Deliberately named rather than line-numbered: STE-445 has since inserted `groupsCoveringLeg` and a second CLI guard, so any line number recorded here would already be stale, and nothing enforces one.)

Exactly one assertion in the suite was reachable by that mutation and it tolerated it: in `tests/m117-ste-425-falsifiable-coverage.test.ts`, the test "an unrecognized or missing `--leg` is a usage error, not a verdict" asserted `toMatch(/--leg must be one of linear \| jira/)` against a string built by `SMOKE_LEGS.join(" | ")`. Unanchored, so `linear | jira | zzprobe` still matched. (Named by test rather than line, for the same reason as above — STE-445 has since rewritten it.) Every other two-leg pin stayed green legitimately — it asserts against skill prose or its own literals and was never bound to the enum.

**Consequence for this milestone:** the derivation binding is *greenfield, not an extension*. Nothing can be tightened; everything must be built. STE-445 exists to build it and to prove it can fail.

**The STE-456 ──▶ STE-457 arrow is LOAD-BEARING, not a preference about ordering.** No offline test can prove a headless child *follows* prose, so STE-457's compliance is observable only on a live conformance run — and only if that run can report. STE-456 is what makes it reportable, which makes the detection STE-457's **only falsifier**. Reordering the pair does not merely delay the detection; it ships a fix nothing can check. STE-455 is independent of both and lands first because it is the cheapest and unblocks nothing — the order is F2, then detection, then fix, and it is to be held literally.

**The parallelism above is LOGICAL, not OPERATIONAL.** It describes which FRs are free of each other's dependencies, not an invitation to run two `/implement` invocations at once. Concurrent runs commit to the same working tree on the same branch and would race — the same reason `/conformance-loop` dispatches its own per-finding fixers sequentially rather than in parallel. Drive one FR at a time; the graph tells you which one is eligible next, not how many to start.

### The archival blind spot — found by performing the archive, not by testing for it

**Recorded at milestone level because it is evidence about this milestone's own process, and because the FR that fixes it will be archived by the very operation it describes.**

Thirteen FRs of falsifiability work — mutation batteries, executed fences, two-directional proofs, six AUDIT stages — and none of them asked whether the suite survives the archival that every milestone ends with. The reason is structural rather than careless: **the gate is always run against a live tree.** Every measurement in this milestone, including every mutation, was taken with `specs/frs/STE-4*.md` and `specs/plan/M121.md` present. The archive is the one state transition that no gate run precedes, which puts it in the same family as § 0l's history-asserting tests — a property that cannot be verified at the moment you rely on it, because the act of verifying changes the input.

**The two halves fail differently and the quiet half is the worse one.** Fourteen assertions read the artifact and assert on its content, so a missing file is `null` and they fail loudly — they stop the release, someone reads them, they get fixed. Three assertions sit behind guards written to tolerate a plugin-only checkout that ships no specs; archival is byte-indistinguishable from that case, so those guards fire, the tests skip, and the suite reports GREEN with three fewer things checked. That is Pattern 31's rider restated by a new mechanism: a spurious RED announces itself and a spurious GREEN never does.

**There is an asymmetry inside the quiet half too, and it is worth carrying.** `m121-ste-458`'s two skips are LABELLED — the test name gains `[SKIPPED — FR absent from specs/frs/ or history unreachable]`, so a reader who scrolls past sees why. `m121-ste-455`'s is a bare `describe.skip` with no label, indistinguishable from a test somebody disabled deliberately. Both are fixed to read the archived artifact instead of skipping; the rule that survives is that a guard which can fire on a routine operation must say so in the test name.

**The idiom was already there.** `existsSync(active) ? active : archived` ships at `tests/m108-ste-393-docs-pins.test.ts:99` and `tests/m114-ste-416-linear-checkbox-doc-accuracy.test.ts:203` — thirteen and seven milestones ahead of this one respectively. Six new files did not adopt it, and no assertion anywhere required them to. **A convention discoverable only by reading unrelated test files is not a convention, it is a coincidence that has held so far**, which is why STE-459 ships a meta-test rather than only six edits.

Only the field's spelling and arity move, and the old spelling is **structurally incapable of expressing a tracker-less-leg finding at all**, so retaining it would be an active correctness defect rather than fidelity to history. The three enforcing assertions were **replaced, never deleted** — deleting them would relax the shipped AC, which is the move this milestone forbids.

**AC-STE-224.5** is recorded here too, as the cautionary precedent rather than as new work. It requires Phase A's children to "run to completion **via `wait`**"; STE-355 replaced the foreground `wait` with a detached spawn plus a bounded `kill -0` poll, because a same-call wait is guaranteed to hit the harness's 600 s ceiling and truncate both legs. **That supersession was never recorded, and the assertion enforcing it went silently vacuous for two milestones:** measured by STE-453, the only satisfier of `/wait\s+"\$\{PID_LINEAR\}"/` in the whole document is the paragraph *explaining that the shape is forbidden*. The pin was broken in both directions — reinstating the truncating `wait` at the spawn site would not have reddened it, while deleting a paragraph of pure history would. Repaired by STE-453 and proven with the distinguishing mutation (M18 RED at the spawn site; M19, deleting the historical paragraph, correctly stays GREEN).

**Why this section exists at all.** An unrecorded supersession is indistinguishable from an oversight one milestone later, and AC-STE-224.5 is the proof: nobody noticed, and the test kept reporting coverage of a mechanism that had been deliberately removed.

### Recorded conflict — AC-STE-423.4 vs AC-STE-446.4

**A second pair of shipped ACs in this repository cannot both be satisfied once a third leg exists. Recorded here rather than resolved by amending either, on the same principle as the pair below.** Measured by STE-448 while keying its artifacts on the tracker-less leg.

- **AC-STE-423.4** (M116, shipped) requires that **every** `dpt-smoke-` literal in `.claude/skills/smoke-test/SKILL.md` carry a tracker segment, and its test spells the permitted set as a hardcoded alternation — `(?:<tracker>|${TRACKER}|$TRACKER|linear|jira)`. That alternation predates the third leg and knows nothing of it.
- **AC-STE-446.4** (M121, shipped) requires that `tests/m116-ste-423-tracker-scoped-artifacts.test.ts` "remain green **without modification**", and its test enforces the second half literally: the file is diffed against `merge-base HEAD main` and must be byte-unchanged.

Those cannot both hold for a driver that names a third leg's scratch paths. Writing `dpt-smoke-none-…` into the smoke driver turns AC-STE-423.4 red; the only repair is widening that alternation, which AC-STE-446.4 forbids.

**Resolution: neither AC is amended, and STE-448 complied with both by not needing the literals.** The tracker-less leg's artifact classes are stated in the smoke driver through the `<tracker>` template, and the per-leg ENUMERATION lives in `/conformance-loop`, which STE-423 explicitly declares out of scope and where every per-leg path is asserted against `SMOKE_LEGS`. That is the route STE-446's own AC.4 hazard note prescribes, so this is the designed path rather than a workaround discovered late.

**What a future reader needs to know, because the shape reads as an oversight.** In § Operator-driven parallelism the smoke driver spells out `linear` and `jira` per-leg paths and does **not** spell out the third leg's. That asymmetry is the conflict above showing through, not a gap in the third leg's coverage — the paths exist, they are covered, and they are covered in the other driver. **The fix, when a milestone is willing to take it, is to derive `TRACKER_SEGMENT` from `SMOKE_LEGS`** rather than restate it; STE-446's own audit already recorded that alternation being hand-copied a third time. Doing so requires touching the file AC-STE-446.4 pins, so it needs a milestone that does not inherit that arm — which is a scheduling fact, not a technical obstacle.

Full measurement in `specs/notes/follow-ups.md` § 0e(a).

### Resolved conflict — AC-STE-445.4 vs AC-STE-446.5

**Two ACs in this milestone are mutually unsatisfiable as written. The conflict is recorded here rather than resolved by amending either FR.**

- **AC-STE-445.4** forbids any derivation test from reading a skill file to compute its own expected value, enforced by a meta-test that textually bans skill-path reads inside an expectation-defining module.
- **AC-STE-446.5** requires the STE-445 mutation harness to turn at least one of the five prose-derivation tests RED.

Those cannot both hold. The five surfaces assert against skill *prose*, so evaluating them requires reading the two driver skills — which the harness module is barred from doing. Registering them into `DERIVATION_SPECS` would break AC-STE-445.4.

**Resolution: AC-STE-445.4 wins; AC-STE-446.5 is Partial by construction.** STE-445 is shipped and its contract is correct; relaxing a predecessor's constraint to flatter a successor's phrasing is how spec history stops being trustworthy. `leg_prose_surfaces.ts` therefore takes document *text* (`proseLegs(docs)`) and the caller supplies it.

**What a maintainer needs to know, because the reasonable inference is false.** `runLegDerivationMutation()` reports exactly ONE target — `leg-error-exact-set`. It does **not** enumerate every derivation target in the milestone. The five prose surfaces are bound to `SMOKE_LEGS` and that binding IS falsifiable, but enforcement lives in the AC-STE-446.5 test block, not the harness registry. An auditor searching `failuresUnderMutation` for the five will not find them — **by construction, not by omission**.

Neither FR's ACs were amended. The conflict is the durable record.

### Scope facts

- **Two new fixture groups is the largest change this phase of the smoke skill has taken in its history.** Stated as a fact about the work, not treated as a reason to shrink it. Registering a group moves a roster count pinned across several test files; that cost is known and mechanical.
- **`--legs` reopens a decision STE-159 already made.** That FR explicitly rejected a combined-mode fan-out flag as over-engineering. The ground shifted: the driver-side fan-out already exists in `/conformance-loop`, so the selector chooses *within* an existing fan-out rather than creating one.
- **A third leg costs approximately zero additional wall-clock.** The legs are detached concurrent brace groups sharing one bounded poll. It costs tokens, not minutes — which is why the leg is default-on rather than opt-in.

### Milestone finding — a heavy adversarial review is NOT a substitute for the AUDIT stage

**Recorded at milestone level rather than in an FR, because it is evidence about this milestone's own process and it would be lost the moment that FR is archived.** Measured during STE-452, and it is the sixth consecutive FR in which a post-completion stage found real vacuity the implementer had missed.

STE-452 ran a **24-agent adversarial review across four independent lenses** (vacuity, shell semantics, collateral damage, AC compliance) with a per-finding skeptic pass, *before* the AUDIT stage. That review was productive: it confirmed twelve findings, including a genuinely vacuous prose pin and a vacuous-green the FR's own edit had introduced.

**AUDIT then found something all four lenses had missed.** The FR's prose pins bound the *summary* of the two model-executed surfaces — the five bullets in the loop driver's pre-flight (0) paragraph — while the instructions a model actually executes for leg-completeness and aggregation sit roughly **480 lines further down** in the document. Measured: reverting either operative paragraph to the pre-STE-452 wording turned **nothing** red, while the summary bullet went on asserting the opposite. The document would have contradicted itself with the gate green.

**The generalisable conclusion, and the reason this is here:**

- **Review and AUDIT are not substitutes.** They failed differently on the same artifact. The lenses were aimed at the diff; the audit was aimed at the ACs, and it was the AC-shaped question — *does every surface AC.7 names actually predicate the selection?* — that walked the reader from the summary to the operative text.
- **A heavy adversarial pass is not a reason to expect AUDIT to return empty.** STE-452 ran the largest pre-audit review in the milestone and AUDIT still returned two Partials and a code-changing advisory. Any FR that skips AUDIT on the grounds that it was reviewed thoroughly is reasoning from the wrong precedent.
- **Pinning the SUMMARY of a mechanism is not pinning the mechanism.** This is structurally the same error as pinning prose that describes a guard the adjacent snippet does not implement — the error the milestone exists to remove — displaced from code into documentation. Where a surface has no executable form, pin the text a reader will *act on*, not the text that describes it, and confirm the two are the same passage.

Cross-refs: `docs/patterns.md` Pattern 31 (the pin-collision family this belongs to), `specs/frs/STE-452.md` § AUDIT findings for the measurement.
