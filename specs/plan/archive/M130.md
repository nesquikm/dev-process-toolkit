# Implementation Plan

## M130 — FR-Scoped Delivery {#M130}

**Goal:** Give `/deliver` the FR-scoped entry shape it advertises but does not have. An FR identity is currently used only to look up its milestone and is then discarded, so naming one task builds, version-bumps and releases every task in its milestone with no signal that the scope widened.

**Prerequisites:** M129 merged (v2.68.0). `resolveDeliverArgument` and `classifyResume` both ship there and are the two surfaces this milestone extends.

**Release target:** v2.69.0 "Pinpoint" (provisional; minor — two `Added` FRs alongside two `Fixed`)

**Migration:** `none` — every change is additive and a milestone-identity run is byte-identical to today. No consumer artifact changes shape.

### FRs

   verify: an FR classifies alone; milestone-scoped classification is byte-identical to its shipped output.

   verify: the boundary is asserted in both directions, last-active and one-sibling-remaining.

### Dependency graph

```
STE-499 ──► STE-500 ──► STE-501   (scope must be carried before it can be classified,
                                    and classified before a chain can branch on it)

STE-502   independent of the three, but must land LAST
          (it states the rules the other three establish)
```

Suggested order: STE-499, STE-500, STE-501 strictly in sequence — each consumes the previous one's output. STE-502 last, because it documents the finished behaviour rather than a planned one.

### Risks

| Category | Risk | Severity | Mitigation |
|---|---|---|---|
| Unclear acceptance criteria | **The last-active-FR predicate (AC-STE-500.2) is off-by-one sensitive in both directions, and both directions are expensive.** One direction ships a milestone whose FRs are not all done; the other strands a finished milestone at an open PR the operator must notice by hand. | high | AC-STE-500.2's boundary is asserted in both directions rather than once, and AC-STE-501.4 puts the remaining-FR count in front of the operator at the confirm gate so a miscount is visible before anything runs. Two independent defences, one in code and one in the gate. |
| Breaking changes | STE-499 changes a code path every shipped `/deliver` invocation uses. A regression there breaks milestone delivery, which is the only shape anyone uses today. | medium | AC-STE-499.5 asserts the milestone path against its shipped output rather than a restatement, and AC-STE-499.4 re-asserts every refusal. |
| Unclear acceptance criteria | The extended chain includes `/spec-archive`, which is easy to read as redundant with `/implement`'s own archival and therefore easy to drop in review. | medium | AC-STE-501.3 states the reason inline — single-FR `/implement` runs deliberately leave `status: active` — so the step cannot be removed without contradicting a written criterion. |

No high-severity risk is left unmitigated.

### Notes

- **The defect is live, not missing.** `/deliver STE-500` today would build four FRs and open a release PR. This is a wrong shape accepted, not an unsupported path refused, which is why STE-499 is worth shipping even if the chain work slipped.
- **STE-502 is a guard, not documentation.** M129 recorded, as a first-class process finding, that it repaired this exact defect class in its first FR and reproduced it in its fifth — routing rules landing only in `docs/deliver-reference.md`, a file the skill marks "not required reading". This milestone writes to the same two surfaces. Line-cap pressure is not a defence: when M129 reproduced the defect the skill was 119 lines of a 358-line cap.
- **Reuse over re-derivation is a stated constraint, not a preference.** M129 found three separate predicate/routing splits in one milestone, every one of them producing a grader that would fail a healthy run. STE-499's scope field exists so STE-500 and STE-501 branch on one answer rather than each re-deriving intent from `kind`.
