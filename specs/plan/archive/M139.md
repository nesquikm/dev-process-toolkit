# Implementation Plan

## M139 — Tracker-First Linear Milestones {#M139}

**Goal:** A Linear milestone identity is derived from the milestone the tracker created, the way a Jira one is derived from its Epic.

**Prerequisites:** M138 (both milestones edit `resolve_milestone_identity.ts`; serial execution keeps them off each other).

**Release target:** v2.77.0 (minor — all three FRs are Changed).

> **Corrected mid-flight.** This plan was drafted naming v2.76.0. M141 was inserted ahead of M139 partway through the program and took that number — v2.76.0 shipped 2026-09-03 as "Answerable" (PR #78), and `plugin.json` on main reads 2.76.0. The replacement was not hand-picked: `inferBump` was fed this milestone's three FRs exactly as `parseFrontmatter` returns them and answered `2.77.0` ("minor bump: milestone shipped 3 additive FRs"). That reader is the one M141 repaired, and it was re-verified as live here rather than assumed: `categoryOf` now falls back to the snake_case frontmatter key as written, and a discriminating probe (two `Fixed` FRs fed as-read) returns the patch bump `2.76.1`, which the pre-fix camelCase-only reader could not have produced. No workaround is needed at this plan's call site, and none is recorded here.

STE-377 made Jira claim-on-create: create the Epic, read the key back, derive `M_<epic-key>`, collision-free with no scan. Its `AC-STE-377.4` pinned "Linear and mode:none unchanged" as a regression block, and `AC-STE-417.5` later re-scoped that block to Linear alone. STE-417's own scope boundary names the rest explicitly as deferred: extending key-derived identity to Linear by deriving from the native milestone object's server-assigned id. This milestone lands that deferral. Both pins are retired here by name: `AC-STE-377.4` ("Linear milestone allocation is byte-unchanged", `adapters/_shared/src/epic_first_allocation.test.ts`) and `AC-STE-417.5`'s narrowed "Linear keeps the sequential five-way scan unchanged" clause (`tests/m115-ste-417-docs-pins.test.ts`) are retired, and every test asserting Linear stays on the sequential scan is retargeted onto the mint — never merely deleted — with its replacement named at the site.

Existing projects adopt with no action and nothing already written is rewritten — the union grammar carries `M<N>` and `M_<key>` side by side, and `milestoneBranchToken` already renders the second as `m_<key>`. No migration entry ships: with nothing repairable, a registry detector would report itself forever, which is the residue STE-442 was faulted for. The notice fires once, at the first mint.

The sequential allocator is retargeted rather than deleted, following STE-417 and STE-522: it keeps the collision refusal that still guards a hand-typed identity.

### AC-STE-539.6 ships PARTIAL

The AC requires the zero-call claim be "asserted as a call count on a double". That instrument cannot observe this subject: the mint reaches `nextFreeMilestoneNumber` by module IMPORT, never through the provider, so a counter on the provider double is blind and its zero is guaranteed by construction. Demonstrated, not argued — a mint edited to genuinely call the allocator left all five legs green. The positive control proves the counter increments when the TEST calls it by hand; it certifies the instrument, not the observation. What guards the claim is the source-absence leg the AC does not name. The honest repair is rewording AC.6 to name that leg; a second double would add a second thing that cannot fail.

### A defaulted-empty input is a WRITE, not a bad read

Found in review, owned by no AC. The dispatcher's linear branch defaulted a missing `project`/`title` to `""` and handed them to the mint, on the stated grounds that this matched the jira branch's one-refusal shape. It did not: `milestoneIdFromEpicKey("")` throws before anything happens, while the mint CREATES then derives — so the defaulting silently allocated a real tracker milestone named `""` in a project named `""` and returned a well-formed id from it. Guarded before the mint now, the absence asserted as a count on a recording provider. The shape generalizes: on any claim-on-create path, a defaulted-empty input is an outward side effect.

### Consequences of tracker-first minting, recorded

- **`mode: linear` no longer resolves an identity offline.** The sequential scan needed no tracker; `mintMilestoneLinear` requires a provider carrying the milestone-create op, so `resolveMilestoneIdentity({ mode: "linear" })` without one now throws rather than returning a number. That is the intended shape of claim-on-create — an identity derived from a tracker object cannot be computed without the tracker — but it is a real change for any caller that previously resolved a Linear identity with no provider, and the tests written against that assumption are retargeted here rather than deleted.
