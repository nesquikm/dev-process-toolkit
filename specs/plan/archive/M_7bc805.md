# Implementation Plan

## M_7bc805 — Capture what a run actually did {#M_7bc805}

**Goal:** Record what each run did, opt-in and privacy-safe. That covers when its tool calls ran and returned, and which review rounds changed the tree. It also covers whether each gate passed on a named input. A measurement spike comes first and decides what the later FRs may record. Gate receipts can gain an outcome and an input key, behind tracking.gate_outcomes. A capture hook adds tree state the transcript cannot hold, registered only by an approved opt-in. A timeline reader derives the rest from the transcript. With every switch off, which is the default, the toolkit behaves as in v3.0.0, the M_94e6f7 merge commit. That commit is the defaults baseline for this milestone and the two after it, never v2.101.4 (supervisor ruling 2026-11-04, for operator review).

**Prerequisites:** M_94e6f7 (v3.0.0) is merged (main 6c62b32c, PR #128). It ships `specs/settings.yaml`, `loadProjectSettings`, `loadProjectSection`, `writeProjectSettings`, `settingsKeyOrder`, `NEW_KEYS` and `upgradeOfferSwitchOn` in `project_settings.ts`, and `docs/settings-reference.md`. M_94e6f7's closing dogfood task is done (PR #129 moved this repo's settings into `specs/settings.yaml`). This repo runs v3.0.0 from a refreshed plugin cache and has been migrated by /upgrade. Its tree holds no moved setting in two places, and probe #69 reports no pending migration. STE-714 is merged before any other FR of this milestone starts. Its decision table fixes branches in STE-716 and STE-717, and its D6 row decides whether STE-716 proceeds at all.

**Release target:** v3.1.0, a minor release after v3.0.0, with four Added FRs. Verify against CHANGELOG.md before shipping.

**Rebase onto v3.0.0.** These specs were rebased onto 6c62b32c and reconciled with what v3.0.0 shipped. Every new key enters the loader's closed key sets (`settingsKeyOrder`, `NEW_KEYS`), defaults off, and gains its AC-STE-706.12 `new` row with the planted-knob control still green. No FR writes a CLAUDE.md settings section. Skills keep reading the tracker mode from the CLAUDE.md binding stub with no tool call (STE-708, operator ruling for 3.x), so no modelled tool-call list here holds a mode call. STE-716 and STE-717 name their interaction with per-section validation and the migrated-tree rule.

**Operator rulings.** 2026-11-04: the four-milestone programme is approved, with this milestone second. No setting may lower generated-code quality or disable a deterministic gate. The toggle lives in the `tracking` section of `specs/settings.yaml`. Timestamps and error flags are derived from the transcript. The live hook is used only for tree state at call time, the diff size at a commit, and durability. Error state is `is_error`, not an exit code, unless the spike proves one exists. Duration comes from Pre/Post rows paired by `tool_use_id`, with orphans handled. Tree hashes are taken only on commit-class Bash and Skill calls. The hook has a p95 bound and a short timeout, in seconds. With the flag off, the hook exits before any heavy import. Gate receipts are extended, not duplicated. Rows live under `.dpt/ledger/` and hold no raw commands, cwd or branch names. Hook-count pins move; superseded by the capture-registration ruling below, so `hooks/hooks.json` and its pins stay unchanged. The repository is public, so only synthetic ids appear. Gate-check freeze (R5) is pre-granted once for this milestone. Re-base the AC-STE-618.8 KICKOFF once at this milestone's gate-check edit commit, listing the new permitted lines. The re-base lands as its own reviewed commit with the freeze test green (STE-715). Dogfooding (R2): M_94e6f7 ends with this repo refreshed, upgraded and checked for leftovers, so this milestone starts on a migrated tree.

Defaults unchanged (operator rule, 2026-11-04): no behaviour change by default; every optimization is a settings change the user approves. So gate outcome receipts sit behind `tracking.gate_outcomes`, off by default (amendment 2).

Capture registration (supervisor ruling 2026-11-04, for operator review): the capture hook is not registered in `hooks/hooks.json`, which stays byte-identical. Only an approved opt-in registers it, in the project-local `.claude/settings.local.json`, and the `capture-registration` migration removes it on approval once the setting is gone. A default install starts no new hook process.

**Decisions.** These are self-decided defaults, recorded 2026-11-04. The capture key is `tracking.tool_calls`, beside `tracking.token_stats`, and the outcome key is `tracking.gate_outcomes`. Writers write to the home the loader reports. Neither key has a legacy home, and the CLAUDE.md binding stub (M_94e6f7 ruling R1) carries no tracking key. `/setup` writes neither key. This milestone, not M_d1b4b7, supersedes the requirements.md Out of Scope line "No hooks/bin/.lsp.json in the plugin" (STE-716). M_d1b4b7 keeps the other lines it rewrites. Outcome receipts cover all three gates: gate-check, tdd and spec-review. The STE-716 latency bounds stay as drafted until a task re-reads them against the spike's no-op baseline. The spike runs interactively with the operator at the keyboard. Its recorder is registered in the measurement checkout's project-local settings and removed afterwards. STE-717 records why zero-yield rounds come from result blocks and tree digests, not the advisory notes file. Tracker ids are lowercased inside file paths when placeholders are filled.

**Migration:** capture-registration. It is a follower, not a move: it applies only when `tracking.tool_calls` and the project-local registration disagree, so a default tree never sees it. Apply registers or unregisters the capture entry in `.claude/settings.local.json`. Explicit approval required. `tracking.tool_calls` and `tracking.gate_outcomes` are new optional keys that default to false, and receipts gain fields only with the outcome switch on.
