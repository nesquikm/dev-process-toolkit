# Implementation Plan

## M_8f07e0 — One Milestone, Two Homes {#M_8f07e0}

**Goal:** A milestone that deliberately spans two repositories becomes declarable, readable and visible, so the repo that finishes first is told it is waiting rather than told to ship, and a second repo joining the shared container cannot mint a rival.

**Prerequisites:** Ships after M_840a06 (v2.81.0), and after the GB→GF repoint. Until it merges, the first shared milestone across glacy-app-fe and glacy-app-be must not be declared. The next milestone reads the reader this one ships.

**Release target:** v2.82.0 — a minor bump, because four of the six FRs are not fix-class. Verify with `inferBump` against the FR frontmatter rather than trusting this line.

### Risks

| Risk | One side | The other side |
|------|----------|----------------|
| A stray bare target repo key that routed silently now throws | Loud beats silent; that is the intended trade | It is a behaviour change, so it ships under Changed, not Fixed |
| The spanning declaration is something nothing forces | This milestone makes the honest state representable and visible | A repo that omits the key is ship-ready again and can release the shared milestone alone — the dishonest state stays possible |
| Probe 75 is warning-only, so nothing hard-grades a malformed map until the next milestone | A new probe costs about a hundred pinned rows and is refused by the programme | The next milestone's ship-coherence violation kind is the correct home, so the soft window is accepted |
| The close offer goes quiet with no reason for a waiting milestone | Widening the CLI stream would break a contract the implement skill parses | The reason is visible at the gate's awaiting-sibling note and nowhere else |
| A malformed declaration on an otherwise ship-ready plan makes probe 75, the close-offer CLI and resume all raise the refusal | One predicate, one loud answer | A stamped, parked or still-busy plan is never read, so the refusal fires only at ship-readiness |
| Normalizing loosens a match on a write path: two genuinely different titles differing by case now join | The ambiguity refusal turns the loosening into a question | The genuine-miss control pins that a real miss still mints |
| The Epic label carries no repo tag | The previous milestone ruled containers shared by design, carrying no owning repo | Its tag-mismatch arm therefore governs tickets only; a container arm would be a dead branch and is not shipped |
| A failed label write is reported on the mint result only | It is a second route to a fact the parent leg already carries, never worth failing a mint | No capability row fires, so a caller that ignores the result never sees it |
| Join mode matches by name | The allocation guard orders join-by-key, and this mode is only the safety net beneath it | A rename in the tracker still defeats a name join |
| The executing copy of the join and label rules lives on a line this milestone may not edit | skills/spec-write/SKILL.md:177 belongs to the previous milestone, sits at 358 of 358 lines and one STE token of headroom, and the programme contract forbids an edit here — both gaps were raised to the supervisor instead | That line still describes the Epic mint as returning a key and an id with no label step, and describes a no-enumerator refusal that the call it documents never triggers; the adapter docs now carry the join mode and the live label call, but a live /spec-write follows the skill, not the adapter doc |
| The shared normalizer loosens further than the three drift classes the FR names | It reuses the idempotency probe's rules unchanged, so title comparison keeps one home | Those rules also strip a trailing `{#anchor}` and fold dashes, so a single existing "Foo {#x}" silently joins a mint of "Foo"; the ambiguity refusal only bounds two or more candidates |
| The object binding's auto-create still finds by exact name | Out of scope: this milestone owned the two mint modules only | attach_project_milestone.ts keeps an exact-name find before its saveMilestone auto-create — the same duplicate-on-drift class, carried forward as a follow-up |
| The resume runner does not refuse a milestone that is waiting on a sibling | The chain it builds is empty, so no stage is ordered | It still claims the tracker milestone and spawns a worker with nothing to run; latent only because the runner has no production consumer yet |

### Handed forward to the next milestone
