# Implementation Plan

## M143 — Chains That Continue {#M143}

**Goal:** An orchestrated run reaches its end without the operator having to restart it at every step.

**Prerequisites:** None. Sequenced after M139, M140 and M142; check shipped versions before naming a release target, since three plans currently contend for the same number.

**Release target:** the next minor after M142 ships.

An operator reported the delivery pipeline stopping twice, at two different boundaries. Auditing every flow found twenty-seven stop points, nine of them defects across five skills, and nothing anywhere that observes whether a chain continued.

The mechanism is one instruction whose consequence depends entirely on composition. Every user-facing stage closes with a report block mandated as the last thing in that report. Under a fork, ending the turn returns control to the orchestrator, which is why the test-driven flow is the one part of the toolkit that gets this right — not because its prose differs, but because the boundary does. Inline, the identical instruction ends the whole run. Two blocks in one report is separately refused, so a turn cannot legitimately span two phases at all.

The second half is offers. Four skills end by asking whether to run the step that comes next, in runs where the orchestrator named that step before the skill started. One of them does not merely re-ask: it leads to the close ceremony running twice.

None of these can be delegated away today. The gate registry holds nine entries, three of them delegable, and no continuation prompt is among them — so by the toolkit's own taxonomy each is a decision the operator must answer personally, however many times the same answer has already been given.

Why it shipped is worth recording: the only automated observer defines a healthy skill as one that terminated with its closing block. A skill that correctly continued scores identical or worse.

### Follow-ups carried out of M143

Measured during delivery, none blocking, none in scope for this milestone:

- **The three new modules have no gate consumer.** `inline_terminal_block.ts`'s and `continuation_offer.ts`'s scanners are registered as no `/gate-check` probe and reached from no CLI, so a dropped clause reddens one suite rather than the gate. Registering a probe costs a registration probe #81 counts and ripples through many pinned counts, so it is an FR of its own rather than a quiet addition here.
- **`performanceDirectiveIn` recognises a closed verb list.** It was widened after an audit measured 12 of 13 rewordings escaping it, and every measured escape is now caught — but the recogniser is still a literal one, and `drivenClauseParagraph` bounds its scan at the first blank line, so an order relocated one paragraph down inside the same offer span is invisible.
- **Two archived specs assert the retired halt wording verbatim** — `specs/frs/archive/HG95TM.md:19` and `specs/plan/archive/M10.md:22`. Both are audit-trail only with no live reader, and archives are frozen history here, so they are recorded rather than rewritten.
- **Nine shipped scanners fail silent if the authoring root moves** (`existsSync` → `continue` → zero violations). Named by the STE-550 refactor pass; it is the house idiom across the adapter layer, so changing it is a sweep, not a cleanup.

### Follow-ups carried into M143

- Nothing observes that a chain continued. The harness drives each skill as its own child, so the driver is the continuation, and its completion check rewards terminating. The pipeline additionally refuses to run non-interactively, and a fixture group asserts that refusal — so the existing harness cannot observe this class by construction. Closing that needs a new mechanism, not a new assertion, and is deliberately out of scope here.
- One stage's report contract is already unsatisfiable on its own terms: four shipped instructions require content after the block its own contract mandates as last. Resolving that is adjacent to STE-550 and should be revisited once the inline path is settled.
- Three offers were classified ambiguous rather than defective, each turning on whether a watched run is also a driven one. STE-549's signal is what would settle them.
