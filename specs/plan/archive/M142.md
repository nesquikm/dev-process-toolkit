# Implementation Plan

## M142 — Stack-Aware TDD Hook {#M142}

**Goal:** The commit guard that requires a test-driven run recognises every stack the toolkit bootstraps, and says so when it recognises none.

**Prerequisites:** None. Ships after M139 and M140.

**Release target:** the next minor after M140 ships. M139 and M140 both currently name v2.77.0, so one of them must move before this milestone can name a number; check the shipped versions rather than the plans.

Reported externally against v2.74.0 and reproduced on this tree at v2.76.0 by executing the shipped classifier. A Dart commit carrying a source and its test classifies as carrying nothing to guard, and so do Python, Go, Kotlin, and TypeScript whose tests use an extension outside a three-item list. The toolkit ships example configurations for six stacks; the guard covers one.

The documented trigger and the implemented trigger disagree: the reference names a test directory the code does not match. Neither the documented name nor any non-TypeScript layout can fire.

The second half is what let the first survive. An unrecognised layout resolves to the same outcome as a commit with nothing to guard, so a guard that never looked reads exactly like a guard that passed. The reporter found it only because a spec-only carve-out working as designed made the asymmetry visible.

A longer list of extensions is the same defect spelled differently. The stack is already detected from marker files elsewhere in the toolkit, and the predicates should follow that detection rather than keep a private copy.

### Measured before implementation

Each row was measured on this tree before any code changed, and each contradicts something the FRs' Technical Design sections assume.

| Measured | Consequence for the design |
|---|---|
| `STACK_MARKERS` is a module-level `const` with no `export`; STE-547 calls it "already exported". | It moves to its own shared module, imported by `capture_skip_baseline.ts` and by the hook. One table still — but a commit hook has no business importing the skip ratchet's runner, capture and gate identity. `detectGate` stays DEFINED in `capture_skip_baseline.ts` (a shipped test pins the token `detectGate(` there) and keeps returning exactly `{ stack, command }` (another pins that shape with `toEqual`). |
| The table is ordered most-specific-first, and Kotlin and Go carry no runner this repo can parse a count out of. | A new entry placed by specificity would change `detectGate`'s answer for a project carrying both a new marker and `package.json`, from the bun command to `null` — a silent regression in the skip ratchet. So an entry declares a gate or declares none, and `detectGate` scans past the gate-less ones. Layout takes the first matching entry; the gate takes the first that also runs something. |
| `classifyStagedPaths(paths)` is a pure function of a path list; the layout question needs a project root. | It gains an OPTIONAL second parameter, leaving every call site and every existing expectation untouched. The default walks up from the process working directory to the first directory holding a stack marker or a `.git` — which is what keeps this repo's own unit expectations green, since the gate runs from `plugins/dev-process-toolkit`, which carries no marker, inside a checkout whose root does. |
| The shipped integration fixtures are markerless temp `git init` repos, not TypeScript projects. | Under stack-derived predicates they resolve to no stack rather than to the TypeScript layout they were written to exercise. Their assertions stay byte-identical; each fixture that MEANS "a recognised TypeScript project" gains the marker that makes it one. AC-STE-547.4 excludes rewriting an expectation to conceal a regression, and an unchanged `toBe(2)` against a project that now says which stack it is conceals nothing. |

### Dependency graph

STE-547 lands first — it decides what "recognised" means, which is the thing STE-548 reports the absence of. Sequencing them the other way would pin a signal against a definition still in motion.

### Measured behaviour change on the TypeScript layout

AC-STE-547.4 pins that the shipped expectations are byte-unmodified, and they are — but "unchanged" is a property of the predicates, and those pins only cover paths already chosen to pass. Differencing the retired predicates against the new ones over a shared corpus, now a leg in the M142 suite, found movement in both directions.

| Direction | Paths | Disposition |
|---|---|---|
| Narrowed | `__tests__/fixtures/data.json`, `__tests__/README.md`, `docs/__tests__/notes.txt` | CLOSED. The first implementation asked for a known source extension even inside a test directory, so these stopped requiring the run. A fixture in a test directory is test material, and a refusing hook that quietly stops refusing is the defect this milestone is about. A path inside a stack's test directory is now a test whatever its extension. |
| Narrowed | `weird__tests__dir/x.ts` | KEPT, and it is the corpus leg's single sanctioned exception. The retired trigger matched the substring `__tests__` while the retired carve-out matched the path segment, so the old code called this path a test and not-a-test at once. The two halves now agree; any OTHER narrowing fails the leg. |
| Widened | `src/foo.test.mjs` and siblings outside the three shipped extensions; anything under `tests/` | DELIBERATE. AC-STE-547.5 asks for the stack's convention rather than an extension list, and `tests/` is the directory the reference has documented all along and no code ever matched. |

### Follow-ups carried OUT of M142

- The reference now quotes the advisory `Reminder:` block's exact text, and nothing pins that quote against what the hook emits. Not hypothetical: the first draft of that doc paraphrased it and was corrected only by reading the source. AC-STE-547.3 established the two-sided pattern for directory names; the same for the emitted reason is unspecced, so it was recorded rather than added.
- `classifyStagedPaths(paths, projectRoot)` has no production consumer — the entrypoint calls `classifyStagedPathsForEntry`. A two-line delegation, and the suite pins both front doors equal, so a note rather than a gap.
- `resolveStackLayout` walks up from the working directory while `git diff --cached` returns checkout-root-relative paths. The directory predicates are segment-anywhere rather than start-anchored, so common monorepo shapes still match; the mismatch is latent. Pre-existing to STE-547.

### Follow-ups carried into M142

- The shared marker table had no Kotlin entry on entry to this milestone, though a gate probe enforces Kotlin lint configuration. STE-547 added one for the layout question; the gate detector still resolves no runner for Kotlin or Go, and its own coverage remains a separate question.
- The external report is at the gist referenced in STE-547's notes. Its second scenario is correct but for a reason worth preserving: a TypeScript project using the documented test directory does fire, via the suffix rule rather than the directory rule, so the documented directory rule has never once been load-bearing.
