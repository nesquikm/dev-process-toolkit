# The skip ratchet compares named skips and says which comparison it made

## Summary

The ratchet subtracts one number from another. That arithmetic cannot answer the question it is asked. A run that removes one skipped test and adds a different one has a difference of zero and passes, though a skip was introduced. A run where somebody deleted a local fixture that twelve tests guard on reads plus one and fails, though no code changed.

Both failures have the same root. The count is an aggregate over a set, and the set is what carries the information. The runner already knows the names — measured on this checkout, the junit reporter names all fifteen skipped tests, at no extra run beyond the one already being made.

So when both sides can be named the comparison is over sets and the newly skipping tests are listed by name. When neither side can, the count stands as it does today, and the row says out loud that it is only a count. When the baseline is named and the current run is not, that is not a weaker comparison but no comparison at all, and it refuses. A weak comparison that looks like a strong one is the same defect wearing different clothes.

## Requirement

The ratchet compares the identities of skipped tests when both sides can be named, degrades to the count when neither can and labels the degrade, and refuses when the baseline is named and the current run is not.

## Acceptance Criteria

- AC-STE-529.1: A baseline record MAY carry `names`, the identities of the skipped tests at capture, extracted from the runner's own machine-readable report. For the bun stack the source is `bun test --reporter=junit --reporter-outfile=<path>`, measured this session to name all fifteen of this checkout's skips while the same run still emits the stdout summary the count is parsed from — one run, both signals.
- AC-STE-529.2: When both the baseline and the current run carry names, the verdict is computed from the SET: the newly skipping tests are those present now and absent at baseline. The outcome is `fail` if and only if that set is non-empty, and the rendered line NAMES its members (capped, with the total stated when capped).
- AC-STE-529.3: When NEITHER side carries names, today's scalar arithmetic stands unchanged, and the rendered row labels itself as a count-only comparison. A comparison that silently got weaker is indistinguishable from one that did not, and the reader has no other way to tell.
- AC-STE-529.4: When the baseline carries names and the current run yields only a count, the outcome is `incomparable`. It is never `pass`, and it never renders a delta — including a delta of zero. Mixing a named baseline with an unnamed present is the "cannot compare collapsing into measured zero" failure, and it is refused rather than approximated.
- AC-STE-529.5: When the baseline carries only a count and the current run is named, the comparison degrades to the scalar and says so. This direction IS a comparison — the baseline number is still a number measured on the same checkout — just a weak one, and it is deliberately not treated the same as AC.4.
- AC-STE-529.6: The discriminating case is asserted directly: a run that removes one skipped test and adds a different one, so the counts are equal. The scalar comparison returns `pass` with delta zero — asserted, as the behaviour being replaced — and the set comparison returns `fail` naming the added identity. Both halves in one test, because the pin that matters is the disagreement, not either verdict alone.
- AC-STE-529.7: Identity extraction is non-vacuous in both directions, and the two absences are distinguishable. A report parsed successfully with zero skipped tests yields an EMPTY set, meaning "named, and none". An absent, unreadable, or unparseable report yields `unavailable`, meaning "not named". A parse failure read as an empty set is the fail-open shape AC-STE-508.4 already closed once for counts.
- AC-STE-529.8: A stack with no identity source records `namesSource` naming that stack, so the degrade is a fact written into the record rather than inferred from a missing key. An absent `names` field could mean the runner cannot name skips or that the writer forgot; those must not read the same.
- AC-STE-529.9: The set comparison is mutation-verified and each mutation is asserted to have applied. Inverting the set difference so it computes the removed rather than the added tests turns AC.2's assertion red; deleting the count-only label turns AC.3's red. The test names the clause each mutation changed.
- AC-STE-529.10: The extraction reads the runner's report from a path the caller supplies, and holds no knowledge of where a gate command writes its artifacts. A second composer of that path would agree with the caller until the caller moved it.

## Technical Design

Identity extraction lives in its own module rather than inside the existing count parser, because the two take different inputs. The count parser reads stdout; identities come from a structured report file the runner writes on request. Folding a file read into a pure string parser would make the pure one impure for every existing caller.

The junit format is the source for the bun stack because bun already emits it and because pytest emits the same format on request, so one reader covers two of the three shipped stacks. Flutter's machine format is different and is deliberately left to the degrade path in this FR rather than guessed at.

The verdict function keeps its current signature for the scalar path and gains a set-aware sibling, with the outcome selection made in one place. Two independent selectors would be free to disagree about the same pair of records, which is the two-renderers defect this repository has already recorded.

The cap on named skips in the rendered line exists because a project can legitimately introduce many at once, and a report that scrolls is a report nobody reads. The total is always stated, so the cap never hides the magnitude.

## Testing

The discriminating case in AC.6 is built from two explicit sets rather than by mutating a real suite, so the test states exactly the condition being distinguished: equal cardinality, different membership.

The extraction tests use a real report file written by a real run of the bun runner over a tiny fixture suite, not a hand-authored xml document. A hand-authored fixture tests the parser against the author's belief about the format rather than against the format.

The two absences in AC.7 are asserted with distinct expected values in the same test, since the whole point is that they must not compare equal.

## Notes

The scalar path is retained as a DEGRADE, not as a default. It is the only signal available on a runner that cannot name its skips, and refusing outright there would make the ratchet unusable on those stacks rather than merely weaker.
