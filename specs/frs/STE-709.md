# The settings file marks a tree as toolkit-managed, and the gate probes grade it

## Summary

Several checks decide whether the toolkit owns a project by looking for CLAUDE.md headings.
Other checks then grade those headings directly.
After settings move, an owned project would read as unowned, and some checks would fail.
This change counts the settings file as proof of ownership.
Each affected check now grades the settings file, and still grades CLAUDE.md on projects that have not moved.

## Requirement

### Managed-tree signal

`toolkit_managed.ts` gains a fourth `ManagedSignal`, `settings_file`, present when `specs/settings.yaml` exists as a regular file. `DETECTORS` order becomes `setup_marker`, `task_tracking_section`, `docs_section`, `settings_file`. The predicate stays synchronous, pure and never-throwing; a malformed settings file still counts as the signal, because presence is the evidence and the loader's refusal is reported by the probes below. Today each `DETECTORS` entry tests only the CLAUDE.md body; the new entry tests the project root, so the entry shape widens to take both. The heading detectors move behind the loader's legacy module (STE-707). Every caller of `isToolkitManaged` follows, `spans_repos.ts` judging a sibling among them.

`skills/upgrade/SKILL.md` Step 0 names the settings file among the managed signals.

The gate-check probe entries must state both arms. That file is frozen by AC-STE-618.8, with one pre-granted `KICKOFF` re-base per milestone. So this FR leaves it byte-identical, and the entries land in the single gate-check edit commit of STE-713.

The stub leg on a settings-file tree: in a tracker mode, CLAUDE.md must carry exactly one stub slot, byte-equal to `renderTrackingStub` over the settings. Missing, duplicated or drifted is red, with a remedy naming `/dev-process-toolkit:upgrade`. In `mode: none`, any stub slot holding a recognised key is red.

## Technical Design

The managed predicate gains one detector, a file existence check. Every probe that asks the shared question learns the new home at once.

Each probe then asks the loader for its value instead of scanning headings. Its assertion side keeps one arm per source.

On a settings-file tree, probe #18 grades the pointer paragraph, the CLAUDE.md surface the move creates. Probe #25 grades the binding stub the same way. Both are byte-compared against their renders, like the stop paragraph.

## Testing

Paired settings and legacy fixtures per probe, the two regression cases, the stub leg rows, and the existing probe suites unchanged.
