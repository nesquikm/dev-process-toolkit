# Make the tracker-less lock evidence two-sided and capture it before the phases that get forfeited

## Summary

Both halves of the tracker-less lock assertion live after the canonical chain. A run killed post chain forfeits both at once, which is exactly what happened on the first live exercise of this leg: three chains completed, all three legs died before the fixture and verify phases, and neither half of the assertion ever rendered a verdict.

The evidence itself survived. The sampler fires inside the chain and the claim witness is a commit in the test project, so both were still on disk after the kill. What was lost was only the rendering, and the recovery window closes at the next run of the same leg.

Separately the sampler appends only on a hit, so a sampler that never ran and a sampler that ran and found nothing leave byte identical disk. That is a one sided latch inside the fixture built to catch one sided evidence.

The outcome rules are correct and are not touched. What changes is that the evidence becomes two sided and is captured before the phases that get forfeited.

## Requirement

Make the lock evidence two sided and durable at the point of observation, and make the end of run release proof require the durable claim witness rather than absence alone, without altering any outcome rule or the sampling gap carve out.

## Technical Design

Phase order is explicit in the driver: canonical chain, then the fixture phase, then chain integrity, then capture, then verify on disk, then teardown. Both halves of the lock assertion sit after the chain, which is the single point of failure. The repair is not to move the verdicts, which belong where they are, but to move the moment of CAPTURE earlier, into the chain where the sampler already runs.

The sampler becomes two sided by writing a line unconditionally rather than only on a hit. The outcome rule keys on the presence of at least one hit line, so it is unaffected, and an absent file now carries information it could not carry before.

The tripwire narrowing gains inflected verb forms and excludes the commit token from both gap spans. Measured on a labelled corpus it scores correctly on every case with one residual hole, which is named rather than hidden. The verb set currently misses its own inflections, so a witness written in the third person walks past it today.

The window budget is a real constraint rather than a caution: the last guarded pin sits well inside the slice today and the new row consumes part of the remaining headroom. An over long witness pushes guarded pins out of the window, and that failure reads GREEN.

## Testing

Every fence is extracted from the driver and executed under bash rather than grepped, on the discipline the milestone's termination harness established.

The two sidedness test is the one that cannot be faked: a run where the sampler never fires and a run where it fires and finds nothing must produce DIFFERENT files. Today they do not.

Each narrowing is measured in both directions — green under the form being replaced, red under the form shipped — because narrowing a pin and blinding it are the same edit and only the mutation tells them apart.

Full gate green from the plugin root.

## Notes

The sampling gap carve out is CORRECT and is deliberately preserved. A short chain step can legitimately produce zero samples, and rendering that as a failure would be a false red on a healthy run.

The two cases are distinguishable and the shipped rule already distinguishes them: a short window leaves no samples but a claim commit, a claim that never fired leaves no samples and no claim commit. The claim witness is the discriminator and it cannot miss. If implementation finds these genuinely indistinguishable from the available artifacts, that is a legitimate finding and must be stated plainly rather than resolved with a heuristic that will cry wolf.

This FR is STE-457's ONLY falsifier. No offline test can prove that a headless child follows prose, so the fix's compliance is observable only on a live run — and only if that run can report. The dependency is load bearing, not a preference about ordering.

Build order: this FR lands SECOND, after STE-455 and BEFORE STE-457.

### What this FR does NOT prove

**No test here proves a real `/implement` run under `mode: none` writes the lock, and none can.** That is STE-457's subject and it is observable only on a live conformance run — which is the whole reason this FR lands first. What is proved is narrower and is the thing that was missing: **if** the claim does not fire, the evidence now says so durably, inside the chain, and the end-of-run row goes RED instead of green.

The Phase 4 row's decision rule is PROSE a model executes at runtime; `releaseProofRow` is a labelled TypeScript analogue of it. Its *inputs* come from the extracted fences, so what is modelled is the decision and never the evidence — but a model that ignores the row's instruction is not caught by anything offline, and that ceiling is stated in the test file's header rather than left for a reader to infer.
