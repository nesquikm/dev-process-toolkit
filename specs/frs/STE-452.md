# Build the N-leg termination harness with executed bash fences

## Summary

The termination check decides whether a conformance run is finished and whether it succeeded. It is written as a shell snippet in the driver skill that counts high-severity lines across the per-leg findings files, and it currently assumes exactly two of them.

Generalizing that to a variable number of legs is the kind of change that needs real coverage rather than a prose assertion, because a prose grep passes happily against text describing a guard the adjacent snippet does not implement. This repository has shipped that defect more than once, and the flag this harness attaches to is itself an example of claimed-but-absent machinery.

The snippet is genuinely executable, so it can be extracted from the skill and run against synthetic inputs. That precedent already exists here for a different guard and is the model to copy exactly.

One case needs a decision rather than a test. A leg whose findings file is missing entirely currently fails closed only by accident, through a shell usage error rather than by design. A leg that produced no findings file did not run, and no findings must never reconcile with no evidence.

## Requirement

Build a fixture-backed harness for the termination probes, generalized to N legs, that EXECUTES the extracted shell fences rather than inspecting the prose around them.

Scope is the termination probes only. Extracting the aggregation pass and the cross-leg dedup into callable code is a genuine architectural change that would dominate this milestone and displace the tracker-less coverage work; it is explicitly out of scope and recorded as a follow-up.

## Acceptance Criteria

- AC-STE-452.2: A slice-sanity test asserts the extracted fence still resolves and still carries its anchors, so a prose edit cannot silently reduce the extraction to an empty string and leave the executed assertions vacuous. {#AC-STE-452.2}
- AC-STE-452.3: The harness covers and asserts N=1, N=2 and N=3; all-green; all-red; and asymmetric, meaning at least one green leg alongside at least one red leg. {#AC-STE-452.3}
- AC-STE-452.4: A missing per-leg findings file aborts the iteration and is asserted NOT to report green. {#AC-STE-452.4}
- AC-STE-452.5: The absent-file semantic is written into the fence explicitly rather than inherited from shell behavior. {#AC-STE-452.5}
- AC-STE-452.6: The `no-progress` probe is covered by the same executed-fence discipline as the `green` probe. {#AC-STE-452.6}
- AC-STE-452.7: **A reduced `--legs` run reaches a verdict, and the question of which leg set the termination surfaces count is answered rather than inherited.** Every leg-counting surface downstream of pre-flight (0) MUST count the SELECTED leg set, not the registered one. This FR MUST record its outcome in its `## Implementation notes` as exactly one of two literal tokens: `reduced_run_reaches_verdict` or `reduced_run_still_aborts`. The second form MUST be followed on the same line by the surface that still aborts and the reason it was not adapted. A probe asserts exactly one of the two tokens is present. Either decision is acceptable; completing this FR without the question having been put is not. {#AC-STE-452.7}
- AC-STE-452.8: **The AC.7 outcome is proven by execution, not by inspection.** A test EXECUTES the adapted surfaces against a synthetic proper subset of `SMOKE_LEGS` — at minimum a single-leg selection — with per-leg artifacts present for the selected legs and ABSENT for the unselected ones, and asserts the run reaches a reported verdict rather than aborting. **This test must FAIL if a reduced run aborts, and must FAIL if a reduced run reports `green` while a selected leg's findings file is missing.** Both halves are required: an implementation that reaches a verdict by ignoring absent files would satisfy the first and violate AC.4. {#AC-STE-452.8}

## Technical Design

The model is `plugins/dev-process-toolkit/tests/driver-gate-fail-open-guards.test.ts`, which pulls every shell fence body from a skill, selects the one it wants by an anchor string, and runs it under bash against synthetic files. Its slice-sanity test is the guard against the extraction silently matching nothing, and is why AC.2 is a separate criterion rather than an implementation detail.

AC.5 is the substantive behavioral change. Today, a missing findings file makes the counting command fail with an empty result, so the comparison that follows is a shell usage error whose non-zero status happens to skip the success branch. The run therefore does not report green, but only by accident — nothing in the snippet expresses the intent, and any refactor could silently invert it. The fence must test for the file's existence and treat absence as an abort with its own message.

The asymmetric case in AC.3 is the one most likely to expose a generalization bug, because a naive N-leg rewrite that folds the per-leg counts with the wrong operator passes both the all-green and all-red cases.

### AC.7 and AC.8 — the defect STE-447 introduced and this FR is obliged to close

**This is not speculative scope. It is a measured defect, shipped knowingly on this branch because STE-452 lands in the same release.** STE-447 added the `--legs` selector; it did not adapt any surface that counts legs. Evidence, executed during STE-447's implementation and again by its AUDIT stage — see that FR's `## Implementation notes` § Audit findings and `specs/notes/follow-ups.md` § 0a:

- With only `linear.rc` present, the rc-collection fence exits 1 with
  `/conformance-loop: Phase A subprocess failed (linear=0, jira=1, none=1). Aborting.`
- That gate fires **before** aggregation and **before** the capture-only short-circuit, so a reduced run yields no report and no verdict in either mode. It never reaches the `green` probe at all.
- The diagnostic additionally misleads: it names a subprocess failure when no subprocess was ever spawned for the unselected legs.

**So `--legs` currently parses correctly, guards emptiness correctly, and then dies at the first gate that counts legs.** It fails closed, which is the right direction — no vacuous green is reachable through it — but it is not a working reduced run, and shipping the milestone with the selector unusable for any proper subset would leave M121 having built an opt-out nobody can use.

**Four surfaces count legs off the registered set** and each needs the selection. Ordered by which fires first:

1. **rc collection** — start here; it is what actually aborts.
2. The **`green`** termination probe — the surface AC.1–AC.5 already address.
3. The **leg-completeness check**, which verifies each leg's grandchild log set.
4. **Aggregation**, which reads one per-leg findings file per registered leg.

The common requirement is that `SELECTED_LEGS`, resolved by pre-flight (0) in `.claude/skills/conformance-loop/SKILL.md`, must be visible to all four. For each surface the rule is the same and is what makes AC.8's two halves non-negotiable: an absent artifact for a **selected** leg stays an abort (AC.4); an absent artifact for an **unselected** leg is a no-op. Those two cases are indistinguishable today precisely because none of the four surfaces can see the selection.

**Why AC.7 is shaped as a forced two-token decision.** It is modelled on AC-STE-446.6, which used the same construction for the roster-guard scope question and worked: it made an inherited question impossible to complete the FR without answering. Adapting all four surfaces may prove larger than this FR should carry, and `reduced_run_still_aborts` is a legitimate outcome — but only if it is chosen, named and justified in the implementation notes, rather than arrived at by not looking. A note in a predecessor's follow-ups file is not a forcing function; an AC whose audit cannot return `missing_acs: []` while the defect is live, is.

## Implementation notes

### AC.7 outcome

`reduced_run_reaches_verdict`

A reduced `--legs` run now reaches a reported verdict. All four surfaces named in the Technical Design — rc collection, the `green` probe, the leg-completeness check and aggregation — count `SELECTED_LEGS` rather than `SMOKE_LEGS`. The two executable ones (rc collection, `green`) are adapted in shell and proven by execution; the two prose ones (leg-completeness, aggregation) are LLM-executed instructions with no runnable form and are adapted in prose with positive pins, which is a ceiling rather than an omission and is stated as such below.

### The "before" measurement, executed rather than recalled

Both fences were extracted from the shipped SKILL and run under `bash -c` against synthetic artifacts **before** anything was changed. Verbatim:

```
# rc-collection fence, SELECTED_LEGS unaware, only linear.rc present
/conformance-loop: Phase A subprocess failed (linear=0, jira=1, none=1). Aborting.
rc=1

# green fence, only linear findings file present, ZERO high lines
grep: /tmp/dpt-smoke-findings-<date>-jira.md: No such file or directory
grep: /tmp/dpt-smoke-findings-<date>-none.md: No such file or directory
bash: line 6: [: : integer expression expected
POST-FENCE STATUS is UNSET
rc=0
```

Two details worth keeping. Only **one** `integer expression expected` diagnostic appears despite two empty variables, because `&&` short-circuits at the `jira` test and the `none` test is never evaluated. And the rc gate reported `linear=0` — the one leg that actually ran passed; the abort was caused entirely by the two legs that were never spawned.

Full-selection controls behaved correctly in both cases (`rc=0` with no output; `STATUS=[green]`), which is what isolates the defect to the reduced selection rather than to the fences generally.

### The "after" measurement

Same extraction, same synthetic inputs, against the fences as shipped by this FR:

- `--legs linear` with `jira`/`none` rc-files absent → the rc gate falls through, rc 0. Asserted per leg, so it is not a linear-only result.
- `--legs linear` with only that leg's findings file present and zero high lines → `STATUS=[green]`. **A reduced converged run now reports green instead of running to `--max-iterations` and terminating as `exhausted`.**
- `--legs linear,none` with `none`'s findings file missing → `no findings file for selected leg(s): none — a leg that produced no findings file did not run…`, rc 1. A selected leg's absence is still an abort.
- `--legs ""` reaching either gate → refusal, rc 1. Never a clean pass.

### The missing-file semantic is written, not inherited — and the witness proves the difference

AC.5's claim is not observable from outcomes alone: the guarded fence and the pre-STE-452 fence **both** decline to report green on a missing file. The difference is that one of them says so. The standing witness strips the explicit `[ ! -f … ]` check out of the extracted fence and measures what comes back: no abort, rc 0, no message — the accidental fail-closed behaviour, reproduced. The guarded fence aborts with a named leg and a reason. That is the assertion AC.5 needs, and no not-green assertion could have made it, because both sides satisfy that.

The strip function throws if its regex fails to match. A mutation that silently no-ops would leave the guard in place and the witness would then "pass" by asserting that a guard it never removed still works (`specs/notes/follow-ups.md` § 0b).

### The asymmetric case has its own witness, for the same reason

All-green and all-red cannot separate `&&` from `||`; only the asymmetric case can. The witness swaps the fold's operator in the extracted fence and asserts the asymmetric case then reports green — and, for contrast, that all-green and all-red are unchanged under the same swap. Without it, the three asymmetric assertions would be indistinguishable from three assertions that pass because nothing ever reports green.

### A vacuity this FR's own edit CREATED, found before it shipped

Giving each leg an explicit `[ ! -f … ]` check meant each findings path appeared in the fence **twice** — once mentioned, once counted. The `green-probe-findings-files` derivation surface (STE-446) scanned the whole fence body, so after the edit it could no longer distinguish the two: deleting a leg's `grep -c` line while leaving its existence check would have kept the surface green while the probe stopped weighing that leg's findings entirely.

My first fix was to scope the surface itself to `grep -c` lines. **Review refuted the reasoning and the fix was reverted.** It was not "strictly stronger": narrowing it also stopped it seeing a phantom or stale leg named only in an existence-check line, which is exactly the drift `AC-STE-446.5` direction (i) exists to catch. I had closed one hole and opened another on a predecessor's surface while describing the trade as a pure win.

The surface keeps its whole-fence scan. The counted-set property is asserted **additively** instead, in this FR's own test file: the `grep -c` lines' leg set must equal `SMOKE_LEGS`. Two assertions, two properties, neither weakened. Deleting a leg's `grep -c` while leaving its existence check turns the new one RED (measured — mutation M1 in the table below).

### `driver-gate-fail-open-guards.test.ts` needed the selection threaded through

That harness built its script as `DATE=… / ITER=1 / <fence>` and set no `SELECTED_LEGS`. Under the new fence that is not a neutral omission: the variable expands empty, every membership arm misses, no rc-file is read, and the gate exits 0. Five tests would have gone red — and the one whose job is to prove the gate is *not stuck closed* would have stayed **green while the gate was stuck open**, which is the milestone's central failure mode landing in the file written to prevent it. The harness now takes the selection as a parameter defaulting to every registered leg, and three tests were added: an unselected leg's absent rc is a no-op, a selected leg's absent rc still aborts, and an empty selection refuses.

### The prose pin was VACUOUS on first write, and three reviewers proved it

The worst finding against this FR, and it landed in the assertion written to enforce the milestone's own thesis. The first version of the prose pin sliced 3000 characters from an anchor sentence and checked that four nouns appeared **somewhere inside**. Demonstrated, not argued: rewriting all four bullets to say the surfaces still count the REGISTERED set left the test green, the sibling ban green, and the full gate at 6890/0. Two of the four nouns were not even supplied by the bullets — the SUPERSEDED history paragraph sits inside the same window and contains "could never reach `green`" and "**before** aggregation", so deleting those two bullets outright also passed. Only two bullets were load-bearing, and only for the presence of a hyphenated noun, never for what the sentence predicated.

A test titled "the four adapted surfaces are each named as counting the SELECTION" that passes against prose saying the opposite is the exact defect M121 exists to remove. It is now bound per surface: each surface's own bullet must match `/selected/i` and must not match `/registered/i`, the pin is restricted to bullet LINES so the explanatory prose cannot donate the words being checked for, and the bullet count is asserted first so the per-surface loop cannot iterate nothing. A companion test pins the poll loop as the one bullet that legitimately still says "registered" — a blanket ban would have driven a correct exemption into hiding.

Two further repairs to the same block. The ban on the retired claim exempted any line naming `STE-452`, so the retired operative statement could be reinstated verbatim as long as the sentence also named the FR that retired it; the exemption is now the superseded blockquote marker itself. And a ban is satisfied by deleting the corrective paragraph entirely, so it is now paired with a positive assertion that the correction is present — Pattern 31's rider, applied after failing to apply it.

### Known ceiling, stated rather than implied

The leg-completeness check and aggregation are **prose instructions executed by a model**, not shell. Adapting them to the selection is a prose edit, and their pins are prose pins. That is weaker than the executed coverage the two shell fences carry, and weaker in a way no test in this FR can repair — a model can read a correctly-worded instruction and still do something else, which no assertion over the text can detect. The survey behind this FR found both sections' leg-set language pinned by nothing at all beforehand, so the pins are an improvement on the baseline; after the vacuity above, though, "strict improvement" is a claim I have already been wrong about once in this FR and it is not restated. **Two surfaces are executed; two are asserted.**

### A FIFTH leg-counting surface, found by review

AC.7 says *every* leg-counting surface downstream of pre-flight (0). The four in the Technical Design were not all of them: the **closing-summary table** carries one `high (<leg>)` column per registered leg. It may not be narrowed to the selection — `closing-summary-columns` is a shipped STE-446 derivation surface asserting those headers enumerate `SMOKE_LEGS` exactly, and relaxing a predecessor's AC to fit a successor is what this milestone forbids. Resolved in the same shape as the recorded AC-STE-423.4 conflict: the columns stay, and the **content** carries the distinction — an unselected leg's cells render `—` (not run), never `0`, because a zero would assert the leg was examined and clean. That is the no-evidence-as-no-findings confusion the whole FR removes, and it would have been reintroduced one layer up in the operator's own summary.

Aggregation's report **shape** — the `**Tracker coverage:** linear + jira` header and its two-entry source list, already stale before this FR — is STE-453's scope and is deliberately untouched here.

### The AC.1 / AC.7 tension, recorded rather than resolved by amendment

**AC.1 forbids any assertion in this FR from being a prose grep. AC.7 mandates a probe over this FR's own markdown text.** They cannot both hold. The implementation satisfies AC.7.

This is recorded here rather than fixed by editing either AC, on the same principle the milestone applies to `AC-STE-423.4 vs AC-STE-446.4` and `AC-STE-445.4 vs AC-STE-446.5`: an FR that quietly rewrites its own acceptance criteria to match what it built has stopped being a specification. The tension is mild and the resolution is obvious — AC.1's real target is the *termination-fence* assertions, and every one of those executes — but "obvious" is exactly the reasoning that should be written down rather than acted on silently.

A future editor amending AC.1 should scope it to the fence assertions rather than delete it; the constraint it expresses is the reason this FR exists.
