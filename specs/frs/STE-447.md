# Add the --legs selector with a fail-closed zero-legs guard

## Summary

Running all three legs by default is the right choice, but a token-tight run needs a way to drop one. That selector is the operator-facing half of the leg-set work, and it brings a hazard the internal binding does not.

The moment an operator-supplied selector exists, the resolved leg set can be empty. An empty selection, or one naming only unrecognized values, would spawn nothing at all — and a run that spawns nothing produces no findings files, which means no high-severity lines, which the termination probe reads as success. The loop would report green having tested nothing.

That is the same vacuous-pass shape this entire milestone exists to hunt, so shipping it here would be incoherent. Today the hazard cannot occur because the leg count is fixed at two and no input can drive it to zero. The selector is what changes that, so the selector is what must guard it.

The guard is a consequence of a rule already settled for this milestone rather than a new decision: no findings and no evidence must never reconcile to the same verdict. A zero-leg run is the degenerate case of exactly that, one level up from a missing findings file.

## Requirement

Add a `--legs` selector to `/conformance-loop`, defaulting to every registered leg, as the documented opt-out for a reduced run. Guard the emptiness it introduces, fail-closed, before any subprocess is spawned.

Also correct two statements that are already false and would become more so under a third leg:

- The Phase 0 contract estimates wall-clock as `max-iterations × ~10 min × 2 trackers`. The legs are detached concurrent brace groups sharing one bounded poll, so leg count does not multiply wall-clock. The line is wrong today and must not be propagated to a factor of three.
- `adapters/_shared/src/smoke_verdict.ts:365` prints `usage: bun smoke_verdict.ts emit --tracker <linear|jira>` while the guard it documents validates by shape, not membership.

## Technical Design

AC.4 is the load-bearing one. AC.2 and AC.3 are the mechanism; AC.4 is the proof the mechanism cannot be bypassed into a green verdict. It must assert the refusal outcome specifically, not merely that a non-zero status was returned — a run that crashes for an unrelated reason also exits non-zero and would satisfy a weaker assertion.

The zero-leg guard belongs with the other pre-flight refusals, ordered before pre-flight (a) or immediately after argument parsing, so that it fires before the cwd probe rather than after. The ordering matters because a refusal that fires late has already had the opportunity to touch the filesystem.

AC.9's regex is benign in its present effect — it whitelists fixed-loop shapes, and a widened fixed loop is still a fixed loop, so nothing is currently mis-flagged. It is in scope because it is the same unanchored-prefix pattern found during the design measurement and it sits directly in this milestone's blast radius.

## Implementation notes

**Baseline re-measured before anything changed:** 6671 pass / 15 skip / 0 fail across 6686 tests. **After the AUDIT-stage fixes:** 6721 / 15 / 0 across 6736 — 50 new tests, zero regressions. (The pre-audit figure was 6713 / 15 / 0 across 6728.)

### The guard is an EXECUTED fence, not prose

Every claim about refusal, selection and side effects is a claim about what the shipped fence actually did. `tests/m121-ste-447-legs-selector.test.ts` extracts pre-flight (0)'s bash fence from `.claude/skills/conformance-loop/SKILL.md` and runs it under `bash -c` with a test-only continuation appended — a continuation that materializes the per-leg pidfiles and logs a spawn would create and prints the green status the termination probe would report. A prose grep could not have distinguished a guard that works from a paragraph describing one; this milestone's whole thesis is that the difference only shows up when you execute it.

The fence is located by the refusal token it emits (`legs_zero_selection`), never by a leg name. Locating it by a leg would reinstate exactly the slicing technique STE-446 retired and would stop finding the fence the day that leg is renamed.

### The RED-producing input, named and EXECUTED

**Delete the single line `exit 2` from the zero-leg guard block.** The refusal still prints — it just no longer stops. Measured against the real file on disk, not reasoned about:

```
(fail) --legs "" refuses with the SPECIFIC zero-selection refusal
(fail) --legs "" NEVER reaches STATUS=green
(fail) no status of any kind is reported on a refusal path
(fail) with the unknown-value refusal removed but the zero-leg guard intact, the zero-leg guard still catches it
39 pass / 4 fail
```

That input was chosen over the blunter "delete the whole guard block" because the blunt one also removes the fence's own location anchor, so 20 tests fail and most of them fail for a slicing reason rather than the reason under test. A mutation that takes down the extraction proves less than one that leaves it intact. (The blunt mutation was run too: 20 fail, restore checksum-verified.)

Both mutations were also **restored and verified by md5 comparison rather than by trusting the copy**, with absolute paths on both sides — the recorded probe hazard that bit STE-446 twice.

The same mutations exist as **standing tests**, applied in-memory to the extracted fence text rather than to the file on disk, so falsifiability is permanent coverage rather than a one-off session artifact. Each strip function throws if its regex fails to match, because a replacement that silently no-ops would leave the guard in place and the witness would then "pass" by asserting the guard works — the inversion that makes a witness worthless.

### Guard ordering — verified, and it lands after nothing that writes

Asserted rather than inspected. Pre-flight (0) is placed at the top of `## Pre-flight refusals`, ahead of (a). Four tests measure byte offsets in the document (document order IS execution order for a driver SKILL): no side-effecting shell construct appears in any earlier fence, no prose write-instruction precedes it, and it precedes pre-flight (a), the Phase 0 pre-approval gate and Phase A. A non-vacuity test requires every side-effect marker to demonstrably fire somewhere later, which caught two dead markers (`truncate`, `mkdir`) in the first draft that matched nothing at all.

**It is labelled `(0)` and NOT lettered, and that is a compatibility decision.** Re-lettering to insert it as a new `(a)` would silently re-point every by-letter cross-reference — `.claude/skills/smoke-test/SKILL.md`, three test files that name refusals (f)/(g) by letter, and the loop skill's own threat-model paragraph — at a different refusal than its author meant. A test pins that (a)–(h) all still exist.

### AC-by-AC

**All nine Done.** AC.1 was reported Partial at the commit gate and that was WRONG in a way worth recording rather than quietly corrected.

**AC.1 — reported Partial, then found to be a real behavioural defect, then fixed.** The Partial reasoning was: "the spawn fence structurally must keep one brace group per registered leg, so `restricts the spawned set` is prose." The first half is true; the conclusion was not. Challenged on which of two readings held — *the groups are guarded at runtime and only their expression is comment-shaped*, versus *the restriction is genuinely only a comment, so `--legs linear` still spawns all three* — the answer was the second. `grep SELECTED_LEGS` across the whole Phase A section returned nothing. **The selector was decorative: it parsed, it guarded emptiness, and then it spawned every registered leg regardless.**

**How that survived to a commit gate is the instructive part.** Two tests appeared to cover it — `"a subset restricts the selection"` and `"a single-leg selection spawns exactly one leg"` — and both passed. Neither touched the spawn fence. They ran pre-flight (0) plus a **test-only continuation** (`for SEL in ${SELECTED_LEGS}`) and counted artifacts that continuation wrote. They proved `SELECTED_LEGS` RESOLVES correctly, which is a different claim from anything spawning correctly. **One of them had "spawns" in its name while asserting nothing about spawning** — a test title carrying a claim its body never made, which is precisely how the whole class hides. It has been renamed to say `RESOLVES`.

**Fixed:** each brace group is now wrapped in `case " ${SELECTED_LEGS} " in *" <leg> "*)` — real shell, not an instruction. Each `{` and `} &` stays at column 0 so `leg_prose_surfaces.ts`'s spawn-fence parser still finds all three groups, which is what makes the fix compatible with the STE-446 derivation surface that forced the original shape.

**Now covered by execution.** A new block runs the ACTUAL spawn fence with `claude` and `bun` stubbed and asserts on the artifacts THE FENCE creates: a reachability anchor (full selection opens a log and pidfile per leg), `--legs linear` produces only linear's log and pidfile and none for the others, a two-leg case, and a falsifiability witness that strips the `case` wrappers and asserts all three legs spawn again under a single-leg selection — the shipped defect, reproduced as a standing test.

Building that test hit the no-op-mutation hazard immediately: the fence sets its own `ITER=<N>` and `DATE=$(date +%Y-%m-%d)`, overriding the caller's, and `ITER=<N>` is a stdin redirect rather than an assignment. Artifacts landed on a real-date path the assertions never looked at, and the reachability anchor failed alongside the restriction tests — which reads as "the fence spawns nothing" rather than "the harness is misconfigured". Both substitutions now throw if they fail to apply.

### One new dependency, and why it is not a fourth copy of the leg list

`smoke_fixture_groups.ts` gains a `legs` subcommand that prints `SMOKE_LEGS`, and pre-flight (0)'s fence calls it. The alternative was a literal leg list inside the guard, which would have been a fourth hand-maintained copy of the leg set inside the milestone that exists to delete such copies. A test asserts the fence contains no quoted leg literal.

**An unreadable registry is its own refusal (`legs_registry_unreadable`), never an empty set.** Reading it as empty would route a broken module straight into the vacuous-green path this gate exists to close.

### Known limitation — and it is a usability DEFECT, not just a scoping note

**A reduced run cannot report `green`, and under `--auto-fix` it reports a false verdict instead.** Measured by executing the extracted `green`-probe fence, not inferred:

- Full selection, zero high lines → `STATUS=green`. Correct.
- `--legs linear` → the probe greps every REGISTERED leg, so two `grep: … No such file or directory` lines and one `[: : integer expression expected` land on stderr, `STATUS` stays unset, and **the script continues**. It does not refuse and does not abort.

The consequence splits by mode. In capture-only (the default) the short-circuit still lands on `STATUS=capture-only`, so the operator gets a verdict — preceded by three unexplained shell diagnostics. Under `--auto-fix` the loop can never reach `green`, runs to `--max-iterations`, and terminates as `exhausted`, whose operator-facing prose asserts that high-severity findings remain and manual triage is needed. **For a reduced run that genuinely converged, that verdict is false**, and the loop spends its whole iteration budget producing it.

Failing closed was the right direction and is what STE-447 chose — a probe that cannot report success beats one that reports success dishonestly. But under `--auto-fix` it does not fail closed; it fails loudly wrong. That is named here as a defect rather than filed as a limitation, and it is recorded in `specs/notes/follow-ups.md` § 0a **and** inline against STE-452's absent-file task in `specs/plan/M121.md`, because the next implementer meets it there rather than in skill prose. Fixing it is out of this FR's ACs.

## Audit findings — what an independent reader caught that I did not

The `/tdd` AUDIT stage was run against the finished FR (RED/GREEN/REFACTOR are incoherent against already-green ACs and were not forced). It returned `missing_acs: []` with **one Partial and seven advisory findings, two of them demonstrated defects rather than inferences.** I re-verified every substantive claim by execution before accepting it, and one of them turned out to be understated.

**HIGH — the glob-metacharacter guard was UNREACHABLE. Fixed.** The `for CANDIDATE in $(printf … | tr ',' ' ')` list is an unquoted command substitution, so pathname expansion runs before the loop body. The metacharacter guard was therefore inspecting the FILENAMES a glob had already matched, never the glob. Measured in a directory containing a file named `linear`: `--legs 'li?ear'` resolved to `legs_selected=linear` — an unregistered value silently admitted by the one gate that may not fail open, with `*` selecting whatever the directory happened to hold. Compounded by pre-flight (0) running before (a)'s cwd probe, so that directory is unverified. **Fixed with `set -f` around the loop, verified in both directions** (directive stripped → `legs_selected=linear`; directive present → `unknown=[li?ear]`).

The audit called this "unreachable for `*`" and said `li?ear` "stays literal and is caught". **That understates it** — any glob matching anything bypassed the guard; only globs matching nothing stayed literal. My own test passed for the wrong reason: it ran from the toolkit repo root, which contains no file named after a leg, so the refusal fired on unrelated filenames rather than on the guard. The test now runs from a scratch directory containing one file per registered leg, with a non-vacuity check that a valid selection still resolves there.

**HIGH — my own § 0a handoff document was FACTUALLY WRONG. Corrected.** I claimed a reduced run reaches the `green` probe and that capture-only "DOES get the aggregated report and a verdict", explicitly flagged as read-not-executed. The audit executed it. A reduced run never reaches that probe: **the rc-collection gate aborts first**, in both modes, with `Phase A subprocess failed (linear=0, jira=1, none=1). Aborting.` — before aggregation and before the capture-only short-circuit. Re-measured myself and confirmed. The corrected entry names four surfaces STE-452 must adapt, not one, and notes that the diagnostic itself misleads: no subprocess was ever spawned for those legs.

**MED — a green test was pinning a documentation hole open. Fixed.** Pre-flight (0) emits three refusal tokens; only two had canonical templates. My slice-sanity test hard-asserted `toHaveLength(2)`, so documenting the third would have turned it RED — the test actively defended the gap it should have caught. Same shape as the archive hole at `ac_prefix.test.ts:174-204`. The third refusal now has a template, and the expectation is DERIVED from the tokens the fence emits, so a refusal added without documentation is red by construction.

**LOW — I introduced two new hand-maintained leg copies. Fixed.** The `argument-hint` frontmatter and the unknown-flag remedy both spell the leg set literally, unpinned, inside the milestone whose purpose is deleting such copies. Both now assert against `SMOKE_LEGS.join(",")`.

**LOW — `plainFences()` mis-sliced. Fixed.** `/```\n([\s\S]*?)```/g` treats a ```bash fence's closing delimiter as a plain-fence opening, returning ~26 regions for ~13 real fences, half of them prose. Benign for the original consumers but a trap, and the new derived refusal check depends on it. Replaced with a line-state scanner.

**INFO — accepted without change.** AC.5 and AC.6(c)/(d)/(e) are prose greps, which I had already disclosed. The audit confirms they are falsifiable against the pre-change baseline (the git diff shows none of those refusals carried the token before) but would accept an incidental mention. AC.6(h) is materially stronger — it pins the actual remedy loop that replaced a literal two-path list. These are LLM-executed prose with no executable form, so this is a ceiling rather than an omission.

**What the audit did NOT dispute:** AC.2/.3/.4/.8/.9. It independently verified that the AC.4 witnesses bite and that AC.9's derived regex rejects both a widened and a shortened leg list.

### Correction tally, carried forward — the milestone is now at EIGHT

STE-446 recorded four. This FR produced four more, all mine, every one surfaced by RUNNING rather than reading. Two I found; two the AUDIT stage found after I had already reported the work as complete:

5. **A textual pin fired on my own correction paragraph.** AC.7's first assertion was a whole-document ban on a leg multiplier near `~10 min`. It went RED — on the sentence explaining that `max-iterations × ~10 min × 2 trackers` was the *previous, wrong* form. The settled resolution in this codebase is to narrow the pin, never to delete the documentation, so it is now scoped to the surfaces that PRESENT an estimate (the When-to-use bullet, the Phase 0 contract fence) plus a strictly stronger check that the superseded form survives **only** on a line labelled as superseded. Section-level scoping was tried first and was still too coarse — it swallowed the same paragraph.
6. **The same trap again, from the opposite direction, on a predecessor's pin.** A comment I wrote in `smoke_fixture_groups.ts` explained the defect by naming the identifier STE-446 deleted. AC-STE-446.1 pins a zero-hit grep for that name across `adapters/` and `tests/`, so the full gate went red on two STE-446 tests. **The pin was not weakened.** Its wording is a shipped predecessor's acceptance criterion, and relaxing one of those to flatter a successor's prose is what the milestone plan explicitly forbids; the comment was reworded instead, which was also the cheaper fix.

Two more instances make this **six occurrences of the whole-file-textual-pin-versus-explanatory-prose collision in one milestone**. It is no longer a recurrence worth noting — it is a property of writing meta-tests in a codebase that documents its own mechanisms in the files those meta-tests scan. The lesson each time has been identical: pin the hazard (an import, a call expression, an operative surface), never an identifier everywhere.

7. **A green test that passed while the guard it named was unreachable — found by AUDIT, not by me.** `m121-ste-447:274`, "a glob metacharacter is an unknown value, not a wildcard match", passed only because the toolkit repo root happens to contain no file named after a leg. The guard it claimed to exercise was bypassed for every glob that matched anything. This is the milestone's central failure mode landing inside a test written specifically to hunt it — and I had reported the FR as complete with that test green. Worth stating plainly: my own falsifiability discipline did not catch this, an independent reader did.
8. **The textual-pin trap a SEVENTH time, inside my own verification script.** Checking that `set -f` was load-bearing, I asserted `'set -f' not in stripped` — which fired on the comment explaining what `set -f` does. Re-scoped to the directive (a line whose entire content is the command) rather than the identifier anywhere. Same lesson, third time in this FR alone.

**And one hazard that fired live rather than being reasoned about.** The first attempt at that same verification stripped `set -f` with `sed 's/^set -f$//'`, which silently matched nothing because the directive is indented. Both the "fixed" and "unfixed" runs then printed identical output — which I could easily have read as "the fix makes no difference" and reverted a correct fix. It was caught only because the two outputs were byte-identical, which is the tell. The rewrite asserts the strip removed exactly two directives before running anything. **A mutation that silently no-ops is indistinguishable from a fix that does nothing**, and this is the second time in M121 a mutate-observe probe has failed by no-opping rather than by erroring.

A third correction is worth recording even though it was caught before it shipped: the ordering check's first draft carried two markers (`truncate`, `mkdir`) that matched nothing in the driver at all. They would have made the ordering assertion pass for free on two of eight dimensions. Only the non-vacuity test found them — reading the marker list would not have, because every entry looks reasonable.
