# Route the Linear branch through the minter and retarget the sequential scan

## Summary

With Linear minting from the tracker, the sequential allocator loses the caller it was built for. Deleting it would also delete the collision refusal that still protects an author who types an identity by hand, so it is retargeted instead.

Existing projects adopt with no action of their own, and nothing already written is rewritten.

The change is visible the first time a milestone comes out shaped differently, so the notice belongs at that moment.

## Requirement

The identity dispatcher's Linear branch delegates to the tracker-first minter. The sequential allocator keeps a real caller in the hand-typed validation path, and every shipped instruction that tells a reader to run it for a new Linear milestone is retargeted or removed. The first mint under the new scheme in a project that still holds sequential plans surfaces exactly one notice.

## Acceptance Criteria

- AC-STE-541.1: The dispatcher's `linear` branch delegates to `mintMilestoneLinear` and returns a milestone id with no `id:` key, which probe #73 requires of every tracker-mode plan.
- AC-STE-541.2: `nextFreeMilestoneNumber` keeps a production caller in the explicitly-typed-identity validation path, and probe #81 reports zero references that are both ordered and unreachable for that module.
- AC-STE-541.3: Every shipped instruction directing a reader to run the five-way scan for a new Linear milestone is removed or retargeted; the grep asserting this runs a positive control in the same test so a zero-hit result is a claim about the search.
- AC-STE-541.4: No migration-registry entry ships. `/spec-write`'s Linear branch emits `linear_milestone_scheme_adopted` the first time it mints an identifier-derived milestone in a project that still holds sequential plans, and does not emit it once such a milestone exists.
- AC-STE-541.5: The M139 plan declares `migration: none`. Should a registry entry ever be added for this change, its `introduced_in` equals the version it ships in, which is what the coverage module enforces and what the registry's own documentation contradicts.
- AC-STE-541.6: STE-417 AC.5's "Linear unchanged" regression pin is retired by name in the M139 plan, and every test asserting that Linear stays on the sequential scan is updated or removed with its replacement named in the same change.

## Technical Design

**Superseded in part by STE-539/540 as shipped** — their ACs govern, and this section was drafted before them. The corrections: derive via `milestoneIdFromLinearMilestone` (`M_` plus the leading six hex), never `milestoneIdFromEpicKey`; no rename, and binding is by KEY; `saveMilestone` stays unwidened, since a second create call site breaks AC-STE-539.5 — an optional `createMilestone` was added and only `listMilestones` widened, with `id?`; the mint takes four arguments.

`resolve_milestone_identity.ts`'s `linear` branch awaits `mintMilestoneLinear` and returns `{milestoneId}` with no `id:`. That strips `next_free_milestone_number.ts`'s last importer, so both take `import.meta.main` front doors — the allocator's builds the explicit-`M<N>` refusal today living only in prose. Re-measure `ORDERED_UNREACHABLE_PIN` by diffing sets. Export `KEY_OWNER_SKILL`; register `linear_milestone_scheme_adopted`.
