# Add /upgrade repair migration for mis-named mode-none milestone plans

## Summary

Detection and prevention do nothing for repositories already carrying mis-named tracker-less milestone plans. The reported incident involves two such plans in one repository, and the window to repair them closes at the first release: once the ship ceremony stamps the milestone token into the changelog and into the plan's shipped marker, renaming the plan trips the ship-coherence probe.

Repair therefore has to reach these plans before they ship, and it has to rewrite every reference in one step. The milestone token is the key that archive lookup, ship stamping, and milestone resolution all read, so a rename that misses any binding leaves the project worse off than before.

This FR adds a scripted entry to the migration registry the upgrade skill walks. It mints a fresh identity, renames the plan, records the minted value, and rewrites the bindings on every feature-requirement file that pointed at the old token. Plans that have already shipped are reported rather than touched.

## Requirement

An operator running `/upgrade` on a tracker-less project holding mis-named milestone plans must be offered a scripted repair that leaves the project in the state the minting path would have produced. The repair must never rename a plan that has already shipped, and must be safe to run more than once.

This reverses the coexistence-without-migration stance taken when minting shipped. The reversal is deliberate and is recorded here rather than left implicit.

## Technical Design

The entry follows the shape the registry already establishes. A module-level detector function is shared by `detect` and by `apply`'s own guard, so "did this fire" and "is there anything left to do" can never disagree — the pattern the M104 entry uses and the reason its apply path is safe to re-enter.

The version rule in AC-STE-442.2 is the trap worth naming explicitly. The registry's own documentation describes `introduced_in` as the release that made the legacy state legacy, which here would be the release that shipped minting. But the coverage module enforces something different: the declared entry's `introduced_in` must equal the version being shipped, and for an archived plan it must equal that plan's shipped marker. Every existing entry satisfies both readings because its migration shipped in the same release that created the legacy state. This entry is the first where the two diverge, and the enforced rule wins — a value matching the documentation would pass every unit test and then refuse the release at ship time.

The rename is the delicate part. The milestone token appears in the plan filename, in the plan's own frontmatter, and in the `milestone:` binding of every FR that targets it. All three must move together, and the FR sweep must cover the archive as well as the active tree, because an archived FR still resolves its milestone through that key. Ordering within a single plan's repair is mint, then rewrite bindings, then rename the file last, so that a failure before the rename leaves a state the detector still recognises.

Shipped plans are excluded by reading the plan's ship marker rather than by inspecting the changelog. The marker is on the plan itself, which keeps the detector filesystem-local and avoids a second parser.

The asymmetry in AC-STE-442.9 is a consequence of the registry contract, not an oversight. The detector cannot use git, so it cannot tell a genuinely legacy plan from a mis-named fresh one — it will offer to repair both. That is acceptable because the entry requires explicit per-entry approval and the preview lists every affected plan, but it means the set this migration offers to fix is deliberately wider than the set the gate probe fails on.

## Testing

Fixtures are temporary project trees rather than mocks, because the repair spans filenames, frontmatter, and cross-file bindings. The core fixture holds one unshipped mis-named plan with two FRs bound to it, and asserts after apply that the plan is renamed, its identity key matches the new filename tail, and both FR bindings moved.

A second fixture holds a shipped mis-named plan and asserts nothing is renamed and the summary names the reason. A third holds one of each and asserts the unshipped plan is repaired while the shipped one is untouched in the same run.

Idempotency is asserted by running apply twice and comparing a full file-tree snapshot after each run. The exemption cases are covered by fixtures carrying each of the two exempt `kind` values, asserting the detector does not report them.

The partial-write property in AC-STE-442.7 is tested by injecting a failure at the rename step and asserting the FR bindings were not left rewritten against a plan that no longer matches them.

## Notes

The stance reversal is the part that deserves to be visible to anyone reading this later. When minting shipped, the explicit decision was coexistence with no migration: existing sequential plans would keep resolving, archiving, and shipping indefinitely. That decision was correct for its moment, because the only cost was cosmetic inconsistency. The reported incident changes the calculus — the same shape is now also what a mis-named fresh plan looks like, so leaving it in place indefinitely means leaving real defects indistinguishable from cosmetic ones.

The repair is offered, never imposed. Explicit per-entry approval is required, the preview lists every affected plan, and a project that prefers to keep its sequential plans can decline and instead declare the exemption key that STE-441 introduces.
