# Add the mode:none leg end-to-end to /smoke-test and /conformance-loop

## Summary

Tracker-less is the default configuration for every project this toolkit bootstraps. The setup skill never writes a mode line for it — the absence of the tracking section is what the default means. Yet the conformance loop has only ever driven two legs, both of them tracker-bound, so the most common downstream configuration is the least tested path in the toolkit.

This adds it as a real third leg rather than a degraded one. Tracker-less is not a weaker version of the tracker chain; it exercises a genuinely different set of code paths. Identity is minted locally instead of allocated remotely, the milestone is an opaque token rather than a sequential number, and release is proved by the deletion of a lock file rather than by a ticket transition.

The gate behaves differently too. Roughly eleven probes go vacuous while two others switch into their enforcing arms, so this leg's gate step is a different set of checks rather than a shorter one.

The leg costs essentially no additional wall-clock, because the legs are detached and run concurrently under a single shared poll. It costs tokens, not minutes.

## Requirement

Add `none` as a third conformance leg across both project-local driver skills, with its own artifacts, no tracker surface, and verify-on-disk assertions that only a tracker-less run can make.

The leg must not be a special case bolted beside the other two. Its admission to the basename allow-list and its spawn group derive from `SMOKE_LEGS` per STE-446, not from a third hardcoded literal.

## Technical Design

The leg's artifacts follow the existing tracker-segment convention exactly, which is why STE-423's scoping tests stay green unmodified — they assert templates, not literals.

The MCP-free path is the one genuine branch. Phase 1 step 5 constructs a wrapped MCP config per tracker; the `none` leg skips it entirely, and the spawn omits the corresponding flag rather than passing an empty file. Pre-flights (c) and (d) do not fire for this leg per AC-STE-447.6.

AC.9 is deliberately only half of the lock assertion. An end-state absence check is satisfied vacuously by a lock that was never created, so on its own it cannot distinguish a working release path from a claim that silently no-opped. The other half — proving the lock existed mid-run — is STE-451, and it needs mid-run observation that Phase 4 structurally cannot perform.

## Testing

Derivation tests from STE-446 already cover the allow-list and artifact-path surfaces once the enum gains its third member; this FR adds the leg-specific behavioral assertions.

The Phase 4 verify rows are prose contracts executed by the driver at run time, so their coverage here is the meta-test asserting the rows exist and name the right paths. Their live exercise is a conformance run.

### AC-by-AC

**All nine Done.** Seven are covered by executed assertions; two rows of AC.7/.8 and parts of AC.4/.5/.6 are prose contracts the driver runs at runtime, and every such check is labelled `PROSE` in the test file rather than dressed up as behavioural.

**AC.1 — the alternation is bound PER SITE, and that is strictly stronger than a union.** The smoke driver states its supported set in four places: the frontmatter `argument-hint`, the argument-parsing bullet, and two shell guards' `must resolve to` diagnostics. `smokeTrackerAlternationSites` returns them as a list of token lists, deliberately unflattened, because a union cannot see a site that has gone stale as a strict SUBSET of another. **Measured, not argued:** with `none` stripped from the frontmatter only, the union still equals the enum (`jira,linear,none`) and a union-only surface stays GREEN, while the per-site assertion goes RED. The context anchor on `--tracker` is load-bearing for a measured reason too — an unanchored lowercase-alternation scan matches ordinary prose (`<user-supplied|default applied>` yields the pair `supplied|default`), and a standing test pins that it does not.

**The surface is deliberately NOT registered in `LEG_PROSE_SURFACES`.** AC-STE-446.2 pins that registry at exactly five entries, "one per Requirement bullet" of STE-446, and a sixth is not one of those bullets. Relaxing a shipped predecessor's count to make room for a successor is the move this milestone forbids, so the function lives beside the registry and is asserted in this FR's own block. A test pins the decision, so a later change cannot quietly register it and push the repair onto STE-446's test.

**AC.3 was already satisfied by STE-446 and is re-verified through the same surface**, not by a fresh grep — so it cannot pass against an allow-list the authority does not agree with. A second arm pins the arm is still a CLOSED list: deriving an allow-list must not be confused with opening it, and a `*)` catch-all would satisfy every other assertion while admitting arbitrary basenames.

**AC.4's real content is the SCOPING, not a sentence saying the leg skips MCP.** The test slices the pre-flight list, splits it into numbered items, and requires any item mentioning an `mcp__` tool to declare `(Linear-only)` or `(Jira-only)`. **AC.9 is half an assertion and the test pins the disclaimer, not just the row.** An end-state absence check is satisfied *vacuously* by a lock that was never created, so a green row does not establish that the release path works. A later "strengthening" that added a mid-run existence claim would make the disclaimer false while Phase 4 still cannot make that observation; a test asserts the row does not grow one.

### A defect found, fixed, and covered — beyond the nine ACs

**The spawn fence aborted a reduced run under `set -u`, at its own last line.** The summary line read `linear=${PID_LINEAR} jira=${PID_JIRA} none=${PID_NONE}` — one variable per REGISTERED leg. An unselected leg's brace group never runs and never assigns its variable, so `set -u` killed the shell AFTER the selected legs were detached and BEFORE anything could `wait` on them (measured: `PID_JIRA: unbound variable`, rc 1, groups orphaned). It is a fifth reduced-run surface beyond the four in § 0a, and the only one inside Phase A's own fence.

It also explains a flake. The STE-447 spawn-fence harness leaked three `.rc` files per run, deterministically, because `wait` was never reached and the orphaned groups wrote their rc-files after cleanup. Those leftovers sit at a `process.pid`-keyed path, so a recycled PID lets a later run observe a previous run's artifacts — the likely mechanism behind the single `--legs linear spawns ONLY linear` failure seen in one of five full-suite runs, which passed in isolation. After the fix: zero leftovers, measured.

**And it was invisible.** Reverting the fix and running the whole suite returned 6764 pass / 0 fail — byte-identical to the clean gate. Nothing in the repository could tell the two apart. That is this milestone's central failure mode landing on my own fix, so it is now covered by an executed test that runs the extracted fence under `set -u` with a proper subset and asserts it reaches a sentinel, plus a shape pin so the defect cannot return in a form that survives the full selection (which assigns every variable and passes regardless). Both go RED against the reverted form.
