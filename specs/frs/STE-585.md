# The minted milestone Epic carries its milestone label

## Summary

A repository joining a shared Jira milestone lists milestones by two routes, Epics and labels.
An Epic minted under its human title is invisible to the Epic route until someone renames it, and nothing ever writes the label.
So the joining repository cannot see the milestone at all.
The mint now writes the milestone label on the Epic it created or found, after the identity is derived, and a label failure never fails the mint.

## Requirement

After deriving the milestone id, the Epic mint must write the milestone label onto the Epic through the provider's optional label op, refusal-free, report whether it landed, and the Jira adapter doc must stop saying the opposite.

## Acceptance Criteria

- AC-STE-585.1: With a recording provider whose `createEpic` returns `GF-78`, `mintMilestoneEpic(p, "GF", "Waiting States II")` records exactly one call `addLabel("GF-78", "milestone-M_GF_78")` and resolves to `{ epicKey: "GF-78", milestoneId: "M_GF_78", labelled: true }`.
- AC-STE-585.2: With `addLabel` rejecting, the mint resolves to `{ epicKey: "GF-78", milestoneId: "M_GF_78", labelled: false }`, does not reject, and records exactly one `addLabel` call and zero sleeps — the label write sits outside the retry.
- AC-STE-585.3: A provider carrying only `createEpic` still mints and resolves with `labelled: false`.
- AC-STE-585.4: With `createEpic` returning the key `""`, the mint rejects with the id derivation's own refusal, and the recorder shows zero `addLabel` calls.
- AC-STE-585.5: With `listEpics` returning an Epic named exactly the title, `createEpic` is called zero times and `addLabel` is called once with the found key.
- AC-STE-585.6: Round trip through the shipped reader. A `fetchPage` whose one issue carries `labels: ["milestone-M_GF_78"]`, fed into `listMilestones` in `adapters/jira/src/list_milestones.ts`, returns `[{ name: "M_GF_78" }]`; in the same test the labels `milestone-M_`, `milestone-M5-extra` and `xmilestone-M5` each return `[]`.
- AC-STE-585.7: Dedupe, not double-count. The same milestone fed through both legs — the label and an Epic `{ key: "GF-78", summary: "M_GF_78 — Waiting States II" }` — returns exactly `[{ name: "M_GF_78" }]`.
- AC-STE-585.8: `adapters/jira.md` stops contradicting the code. `grep -c 'It scatters no' adapters/jira.md` returns 0, where it returns 1 at v2.81.0, and the section headed `## Project Milestone` carries a sentence containing both `milestone-M_` and `mint`, stating that the label is written on the Epic at mint time only and that the per-FR attach still writes no label.
- AC-STE-585.9: In `adapters/jira.md`, step 2 of the section headed `## Milestone Listing` contains `labels IS NOT EMPTY` and a clause naming the absent issuetype filter as what makes the Epic's label visible to the label leg.
- AC-STE-585.10: No new capability key: `CANONICAL_CAPABILITY_KEYS.length` is still 45.
- AC-STE-585.11: The front door stays a preview. `bun run adapters/_shared/src/mint_milestone_epic.ts GF "Waiting States II" GF-78` exits 0, prints its four existing lines (`summary=`, `epicKey=`, `milestoneId=M_GF_78`, `plan=`) unchanged, and adds `label=milestone-M_GF_78`, read off the recorded label argument; it writes nothing.
- AC-STE-585.12: The full `bun test` from `plugins/dev-process-toolkit` reports zero failures with the skip count unchanged from the 15 measured at v2.81.0.

## Technical Design

Add a step after `milestoneIdFromEpicKey`, outside `retryTransient`: when `provider.addLabel` exists, call it once inside a try/catch and set `labelled`. Widen `MintMilestoneEpicProvider` to `Pick<MilestoneOps, "createEpic" | "listEpics" | "addLabel">`, all optional, and `MintedMilestoneEpic` with `readonly labelled: boolean`. The label derives from the id, never composed by hand. `addLabel` is a read-merge-write union, so a re-mint stays idempotent. Measured: the Epic listing leg counts an Epic only when its summary leads with a milestone token, so a title-only mint is invisible there. No repo tag goes on the Epic: the previous milestone ruled containers shared by design.

## Testing

Provider doubles record every call; assert call counts and arguments, never source text.

## Notes

A failed label write is reported on the result, not raised, and fires no capability row. That quiet half is named in the plan's risks.
