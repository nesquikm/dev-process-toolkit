# Minting a milestone Epic is a real step with a computable name

## Summary

The adapter documentation tells whoever is minting a milestone to create the Epic with a summary equal to the canonical milestone name. That name begins with the milestone id, and the milestone id is derived from the key the tracker assigns to that very Epic. The instruction asks for a value that will not exist until after the call it is an argument to has returned.

An instruction that cannot be followed does not stop anyone. It gets approximated. Whoever is minting types the human title, or a guess at the id, and the Epic ends up carrying something that is not the canonical name — which is the exact state the binding then fails on. The impossible instruction and the duplicate Epic are the same defect seen from two ends.

What is computable at creation time is the title. So the Epic is created with the title alone, the allocated key comes back, the milestone id is derived from that key, and only then is the plan file written with a heading that carries both. Order is the whole fix: derive after, never before.

Giving that sequence a module rather than a paragraph is the other half. This repository has been bitten repeatedly by steps that exist only as prose for a language model to approximate, and a step whose correctness depends on reading a value back before using it is exactly the kind that gets skipped when it is narrated. It also gives the creation op a legitimate home, now that binding no longer creates anything.

## Requirement

Creating a milestone Epic has a named module, a summary that is computable at creation time, and a documented derive-then-write order — replacing an instruction that names a value which does not exist at the moment it is ordered.

## Acceptance Criteria

- AC-STE-522.1: A helper `mintMilestoneEpic(provider, project, title)` creates the milestone Epic with `summary` set to the human title ALONE, and returns both the tracker-assigned key and the milestone id derived from it via `milestoneIdFromEpicKey`.
- AC-STE-522.2: The helper never passes a canonical `M_<key> — <Title>` name to the creation call. Asserted by reading the recorded create argument on the provider double, not by inspecting the helper's source.
- AC-STE-522.3: The returned pair satisfies the binding predicate by construction: for returned id `M_<key>` and returned key `<key>`, `milestoneBindingPresent({ parent: key }, "<id> — <title>", "epic")` is TRUE. This is the property the whole milestone exists to guarantee, so it is asserted rather than argued.
- AC-STE-522.4: When the tracker returns a key that does not sanitize to a well-formed union token, the helper surfaces the underlying refusal rather than returning a malformed id. A silently bad id would seed every downstream surface with a token no plan file can be named after.
- AC-STE-522.5: `adapters/jira.md` states the creation summary as the human title and states the order as create, read the key back, derive the id, then write the plan file. The prior instruction passing the canonical name to the creation call is REMOVED, not merely supplemented — leaving both readings in place preserves the one that cannot be followed.
- AC-STE-522.6: AC.5 is mutation-verified in both directions: an assertion fails if the canonical-name instruction returns, and fails if the title-only instruction is deleted. A one-directional pin would stay green on a surface that said both things at once.
- AC-STE-522.7: The Jira Epic-first branch in `skills/spec-write/SKILL.md` names this helper by module path, so the ordered step is executable rather than narrated. The surface currently orders Epic-first creation and names no module for it.
- AC-STE-522.8: The `createEpic` op has exactly ONE production call site across the adapters and skills trees, and it is this helper. Asserted as a call-site count with the searched roots named in the assertion, so a second home cannot appear and the op cannot become dead.
- AC-STE-522.9: The count in AC.8 is measured over a search that is proven to be looking at something: the same scan run for a token known to be present returns a non-zero count in the same test. A scan pointed at the wrong root reports zero exactly like a clean tree does.

## Technical Design

The helper is small and its value is entirely in the ORDER it enforces, so it lives beside the token derivation it depends on rather than inside the attach module it no longer belongs to. It calls the provider's creation op with the title, receives the key, and puts that key through `milestoneIdFromEpicKey` — whose existing contract already throws rather than returning a malformed id, so AC.4 is satisfied by propagation and not by a second guard.

There is a deliberate asymmetry with STE-521. That FR forbids creation on the binding path; this one requires it on the minting path. The rule that reconciles them is which value is unknown: at minting time the key does not exist and creation is the only way to obtain one, while at binding time the key is already encoded in the token and creating a new one destroys the correspondence.

The documentation change is the part most likely to be under-done, because two of the three surfaces read plausibly today. `adapters/jira.md` gives the impossible instruction outright. `skills/spec-write/SKILL.md` orders Epic-first without naming what performs it, which reads as an omission rather than an error until you try to follow it. Both need the same sequence stated, and the impossible one needs its old text gone rather than qualified.

The `resolve_milestone_identity` Jira branch already takes the Epic key as an INPUT and derives the id from it, so it needs no change — it is the consumer that has always assumed someone upstream did this correctly. Naming that upstream is what this FR adds.

## Testing

The provider double records creation arguments so AC.2 can assert on what was actually sent. Asserting the helper's source text instead would pass on a helper that composed the canonical name in a variable and sent it anyway.

AC.3's construction check is written so it cannot become circular. The predicate is called with the helper's real return values against a ticket view built from the returned key, exercising the same code path the archival gate uses; it does not re-implement the comparison inside the test.

The call-site count carries its own witness per AC.9, following this repository's rule that a zero-hit search is a claim about the search and not only about the tree. The searched roots are named in the assertion message so a future reader can tell whether a regression means a new call site or a moved directory.
