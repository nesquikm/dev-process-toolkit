# A live two-repository smoke, graded from the harness records

## Summary

Offline doubles cannot show what a real tracker and a real model session do together.
This adds a maintainer-only smoke, started by keystrokes, that builds two throwaway repositories bound to one real container and runs the shared-tracker scenarios through real sessions.
A program grades the run from recorded tool calls, tracker answers and files on disk, never from what the model says it did.
Every session it starts is recorded, and cleaned up only after a pass.

## Requirement

**Where the smoke lives — decided by measured cost.** A fourth `SMOKE_LEGS` leg would be the wrong unit and the dearer one. A leg is one test project; this needs two repositories bound to one container. Measured at HEAD ac1f3cb: `SMOKE_LEGS` is referenced by 34 tracked files outside `specs/` and the CHANGELOG (2 skills, 5 shared modules, 26 suites, 1 doc), and 8 assertions pin its exact value or length (AC-STE-587.5 and .8 among them). `leg_derivation_mutation.ts` spells the canonical set by hand, and every fixture group roster would have to learn the leg. A mode of `/smoke-test` fares no better: that document is 2442 lines built around one `../dpt-test-project-<tracker>` directory per leg. A new project-local skill costs one entry in `HARNESS_SKILL_RELATIVE_PATHS` (one exact pin, `tests/m127-ste-487-phase9-artifact-identity.test.ts:567`), one widened `DocId` union in `tests/_spawn_fences.ts`, and four operator trust seeds. The skill is `.claude/skills/shared-tracker-smoke/SKILL.md`, frontmatter `disable-model-invocation: true`, so only a person typing the command starts it. Its slug avoids `drive`, `check` and `verify`, so implementation-time discovery (`scanCandidateCheckSkills`) still finds nothing. The document also lands inside the scan set of every gate probe that globs `.claude/skills/*/SKILL.md`. That includes `auto_approve_marker` (every heredoc `claude -p` fence carries the auto-approve marker) and `requires_input_sentinel_coverage` (a declared `requires-input:` gate names `requireOrRefuse` and the protocol doc), so the new file must satisfy both. The root CLAUDE.md structure note counts the skills across the two roots (29 at ac1f3cb). That count moves to 30 in the same commit.

**Isolation of the three client shapes.** Every scenario child loads the plugin through `--plugin-dir`, the mechanism `/smoke-test` already relies on, which shadows the installed copy of the same plugin. The tree under test serves the normal scenarios. A scratch copy that differs only in its `plugin.json` version serves the below-floor client. The `--old-client` directory serves the old client. The intruder gets a plugin directory with no tracker-write hook registered. Isolation is graded rather than assumed: the old client and the intruder carry no tracker-write hook, so a hook refusal in either session means the wrong plugin loaded (AC.12).

**Invocation.** `/shared-tracker-smoke --tracker jira|linear` runs ONE tracker per invocation; two terminals may run both at once, because every per-run path carries the tracker segment. Jira: `--jira-project <KEY>` (default DST) and `--jira-repoint-from <KEY>`, a second throwaway space (for example DST2) that the operator creates and that B starts bound to; the repoint scenario (S8) moves B from it into the shared space. The Atlassian MCP can neither create nor delete a space, so DST alone cannot host a repoint. When the flag is given, S8 is REQUIRED on Jira: not observed or failed fails the run. When it is not given, S8 is the named, reported skip `repoint-space-not-given` in Phase 0, the verdict artifact and the closing summary, never silently omitted, and STE-618 then refuses the Jira proof. Linear: `--linear-team <KEY>` (default STE); the skill creates the shared throwaway project and B's pre-repoint project itself. `--old-client <plugin dir>` defaults to the newest cached plugin that lacks the tracker-write hook wrapper. `--keep` skips teardown prompts.

**Phases.**
0. Pre-approval, typed by the operator. It names every container the run will write to (Jira keys, the repoint-from space included when given, or the Linear team and the two project names it will create), whether S8 runs or is skipped as `repoint-space-not-given`, the expected and worst-case item counts, and the number of children the run will start. No tracker call precedes it.
0.5. Clear this tracker's stale scratch.
1. Pre-flights, all before any spawn or tracker write.
2. Bootstrap. `../dpt-shared-<tracker>-a` and `-b` become git repositories. The M_947c79 declaration front door writes each one's declaration and stop paragraph, with the floor set to the version under test. Each repository gets a wrapped MCP config, and B's registers the tracker server under a second name (`claude_ai_Atlassian` / `claude_ai_Linear`). A also gets a trivial passing test command and a clean tree, so that `/ship-milestone`'s refusals #1 to #3 cannot be the ones that fire in the sibling-busy scenario. One run nonce goes into every title the smoke writes, so no ticket from an earlier run can ever match.
3. Scenarios. One `claude -p` child per scenario step, serial, each prompt carrying one scenario marker line written by the skill's fence. Every child is started with `--session-id` after a run-ledger append (leg `shared-<tracker>`), from a fence written to a file and run with `bash <file>`. The fence ends with the live-child count. The run starts at most the number of children the registry derives (its live steps plus the two audits). A fence that would exceed that ceiling refuses instead of spawning.
4. Audit. A read-only child runs the fixed nonce query that the fence writes into its prompt, pages it to the last page, and then reads back by key every item any scenario's tool_results report as created.
5. Teardown. Jira: every nonce item, Epics included, goes to Done. Linear: both throwaway projects are completed. A second read-only audit child then re-reads the nonce items.
6. Extract and grade. The grader turns the ledgered sessions' transcripts, both audits included, into an evidence bundle, grades it, and writes the verdict. Teardown is therefore inside the evidence the release gate re-grades.
7. Session cleanup: the STE-593 delete mode, on pass only, after extraction.
8. Closing accounting.

**Live scenarios.** Every registry id (STE-616) that applies live, notably:
- same-title FR create, coexisting and spanning;
- span mint in A with the explicit join in B;
- orphan listing and the untagged detector;
- a sibling-busy `/ship-milestone` refusal in A, and its permit twin once B's FR is archived;
- a below-floor client refused by the hook. Its plugin dir is a scratch copy of the tree under test differing only in its plugin.json version, and its prompt instructs one tracker write, so the refusal is observed rather than inferred;
- the old client on the cached pre-hook plugin;
- a hook-less intruder child (no tracker-write hook in its plugin set) writing one untagged item;
- repoint (S8): on Jira from the `--jira-repoint-from` space into the shared one, required when that flag is given and a named skip otherwise; on Linear always;
- claim and import ownership (S13): B handed A's ticket key is refused, and an untagged item is imported only after an answered yes; no issue is created;
- zero-write join and span (S14): B's new plan naming A's container is refused before its decided join, and A's release is held while B's plan does not name A back; its permit twin is S2's create under the decided join, so it spends no extra issue;
- a new numeric milestone (S16): the typed-`M<N>` door and probe #73 run in both roots, record-only, with no tracker call;
- commit-writing subcommands and aliases (S17): in the S12 session, one `git -C <B> merge --no-ff` and one aliased commit, refused then permitted, with no tracker call. S15 and S18 are offline-only: S15 would need seeded tickets carrying a numeric label, and S18's visibility is a harness exit-code property the grader cannot read from tool records;
- a commit and a PR into B from a session rooted in A, refused, then permitted once B's own gate evidence exists. B has no remote, so a PR the hook failed to stop still reaches nothing outward, and the permitted PR's tool_result is a gh error rather than a hook refusal.

**The grader** is `adapters/_shared/src/shared_tracker_live_grader.ts`, a module with a command-line front door (`digest`, `extract`, `grade`). It reads only harness records:
- the tool_use / tool_result pairs, subagent sidechains included, from the transcripts of the sessions the run ledger names. It finds them through the transcript index `smoke_session_cleanup.ts` already builds, exported for this, never through a second directory walk;
- the receipts in both repositories;
- both repositories' git state.

It never reads assistant text. Beyond the per-scenario predicates, the grader holds four run-wide checks. It decides all four from records the model cannot author by talking.
- **Gated writes.** This check covers every session except the old client and the intruder, whose writes are ungated by design and are graded by the detector. In those sessions, every successful tracker write of a kind the tracker-write hook gates by receipt must be preceded, in the same session, by a Bash run of the named front door whose tool_result announces a receipt (`dpt-receipt: <path>`). That receipt must exist in the decided-for repository and record the decision the write carries. A write without one fails as `ungated-write`. A receipt on disk that no front-door run announced fails as `unannounced-receipt`. A tracker receipt counts as announced only when the module that WRITES its kind announced it, under that module's receipt-writing subcommand where it has one — `create` and `reuse` by `create_idempotency_probe.ts decide`, `milestone-decision` by `resolve_milestone_identity.ts`, `binding` by `ticket_ownership.ts confirm`, `import` by `container_ownership.ts consent`, `attach-target` by `attach_project_milestone.ts`, `repoint` by `repoint_tracker_binding.ts`. For every kind the hook gates, that is exactly the hook's `RECEIPT_ANNOUNCING_MODULES` (STE-607), and a drift test keeps the two equal; the grader is stricter than "any trusted module", so one module cannot vouch for another's receipt kind, and a hook that stopped enforcing its rule cannot pass.
- **Listing provenance (MI-5).** Every milestone decision's receipt names the listing it was computed from. That listing must equal the last-page answer of an MCP listing call recorded earlier in the same session. Otherwise the run fails as `unlisted-decision`.
- **Audit completeness.** The audit's nonce query must be byte-equal to the query its fence wrote and must reach its last page. Its answer must hold every item the scenarios' tool_results created. Otherwise the run aborts as `audit-incomplete`, never passes.
- **Spawn ceiling.** A run ledger holding more sessions than the registry-derived ceiling aborts as `spawn-overrun`.

The same module owns `behaviourDigest(pluginRoot)`: SHA-256 per file over every git-tracked file under the plugin root, read from the working copy, except `tests/` and colocated `*.test.ts`, plus one digest over the sorted list. `.claude-plugin/plugin.json` is hashed with its `version` value replaced by a fixed placeholder, so a version bump alone never changes the digest while any other manifest change does. Ignored and untracked files never count, so two clean checkouts of one commit, worktrees included, agree. A scratch copy that is not a git checkout, such as the below-floor plugin, is hashed over the tracked-file list of the checkout it was copied from, passed in explicitly. A root that is neither a git checkout nor given a list refuses as `digest-unavailable`. The verdict vocabulary is `SMOKE_OUTCOMES` from `smoke_verdict.ts`, so the outcome words exist once.

**The evidence bundle is a projection, not a copy.** Only the fields the predicates read are kept: tool names, tool inputs, and from each tracker answer the key, summary, labels, status, parent, milestone and issue type. Absolute paths are rewritten relative to the run's roots. The bundle ships inside the plugin tree to every installing user, so the grader refuses to write it while any string in it matches an email address, an Atlassian account id, a tracker site host, or a home-directory path.

**Linear's free plan.** No MCP tool archives or deletes a Linear issue, and the workspace's free plan refuses issue creates past its cap with a 400. The run therefore spends at most the registry's Linear issue budget: seven expected creates, plus one per refusal-expected scenario whose guard, if broken, would let one more through. Phase 0 states both numbers. The run never retries a cap refusal, and names every issue it created so the operator can archive them by hand.

## Technical Design

The skill follows the smoke driver's proven shape: tracker-scoped paths, pre-approval, ledgered spawns run from files, live-child counts, and a verdict artifact read by a program. What is new is the grading source. The children's transcripts already hold every tool call and every tracker response verbatim, so the grader pairs them by id and decides each scenario from those records, the receipts and git state alone. A successful write with no announced front-door run behind it fails the run, which is how a skipped front door surfaces live. Scenario markers are written by the fence, never by the child. Titles carry a run nonce, which also scopes teardown.

## Testing

The grader's suite runs on synthetic bundles built from the offline suite's records: one passing bundle, one single-scenario failure per registry id, one bundle per run-wide defect (AC.17) and per refused privacy pattern (AC.16), text-decoupling, abort and malformed cases. The skill's fences are tested by extraction with stubs, in the manner of the existing harness suites. The live run itself is graded by STE-618, not here.

## Notes

An old client cannot be stopped by code it lacks. The smoke measures whether it obeys the stop paragraph and whether the detector sees its writes. An old client adopting a tagged sibling ticket by title stays invisible, unprovoked by the smoke. Without a second throwaway space, the Jira repoint is a named skip.

## Findings about the method

**The TDD loop can manufacture agreement.** During GREEN, an implementer widened the receipt-announcement rule to "any toolkit module" so a test would pass, and a test-writer assertion pinned the widened rule ("a toolkit module did announce it, so it is not unannounced"). Neither fork did anything visibly wrong; together they reached green by weakening the property, so a cross-kind forgery (one module vouching for another's receipt) would have shipped with every artifact looking healthy. Mutation testing does not catch this: a row still kills against a correct implementation of a weakened rule. What caught it was the orchestrator reading the diff against the SPEC rather than against the tests. That check is the loop's only cover for this blind spot, and a green loop is not evidence the property survived. STE-616's S18 defect (test and code agreeing on the wrong expectation) is the same shape without the security consequence.

**One spec, N artifacts, never checked pairwise.** This FR's skill document and its grader were written by different forks from the same FR; each was internally coherent and checked against the spec, and nothing compared them to each other until the audit read both. The document's S14 step created an issue after the refused attach, which the grader fails by construction; no step archived B's FR for S5's permit twin; no step produced B's gate evidence inside the S12 and S17 sessions. The live smoke would have been the first thing to notice, at the cost of a Linear run. It is STE-616's S18 defect inverted: there a test and its code agreed and were both wrong; here two artifacts disagreed and nothing noticed. When one spec spawns several artifacts, the loop checks each against the spec and never checks them against each other.

**The announcement forgery came back.** The first grader credited `bun run <writer> …; echo 'dpt-receipt: …'` to the writer, because its announcement pattern was anchored at the start only, and it never compared the announced sha256 with the receipt's bytes. That is the defect M_85e846 spent four review rounds closing in the hook, reproduced independently by a fork writing fresh code from a different FR. Nobody copied it; the same problem invited the same wrong answer twice. The closed form belongs in one shared helper, not in prose telling the next author what to do.

**A fixture set that always supplies a field can never test its absence.** The fifth fail-open (a Jira teardown check that skipped any audit item with no project, so an answer omitting the field passed teardown vacuously) hid where no test could see it: every fixture carried the field. Uniform fixtures encode an assumption, and the uniformity makes a whole class of defect structurally invisible to the suite; it took an auditor reading the predicate against the audit prompt to find it. The rule: for each field a predicate requires, one fixture that omits it. The audit field lists are now one exported constant, graded against every field any predicate reads, and the skill's audit fences are asserted equal to it, so the audit prompt, the predicates and the fixtures cannot drift apart again.

**One spec, several artifacts, a third time.** The document against the grader (the S14, S5, S12, S17 and S11 steps), `extract` against `grade` over the bundle hash, and the audit prompt against the predicates' field needs: three instances of artifacts written from one spec that disagreed while each was internally sound. Nothing in the loop compares siblings. That is the mechanism, and it heads the follow-on milestone's evidence.

**Five fail-opens, one shape: absence of evidence read as permission.** The commit and PR hooks read an unreadable CLAUDE.md as an unmanaged repository (STE-616); the first fix still read a symlink loop or a dangling link as absent (STE-616, Stage B); the live grader emitted nothing when a bundle held no second audit, so a run that never proved its teardown could pass (this FR); it read an absent receipts directory as a readable, empty one (this FR, audit); and its Jira teardown skipped any audit item carrying no project (this FR, pre-handover audit). Each was fixed with a permit twin and shown red first. Five instances make it a pattern rather than a coincidence: every place this codebase infers "fine" from "nothing there" is a candidate for a deliberate sweep in the follow-on milestone.

No production module outside `tracker_answer.ts` may carry a paging or wrapper token (`isLast`, `hasNextPage`, `nextPageToken`, `endCursor`, `pageInfo`, a `nodes` read, an `identifier` read), except three exemptions, each with its exact count and written reason:
- a milestone-identifier field of an error class;
- the session's own completeness claim on the two hand-assembled repoint inputs;
- refusal text naming the fields.

Mutation controls prove it goes red: when an `isLast` read is added to a module, when a `nodes` read is added to the hook, and when an exempt file gains one more token. Its red-before is the tree before this round: nine files carried the tokens, and `sibling_release` alone carried 31.

The pin is heuristic about TOKENS, not semantics. It catches a new reader that mentions paging; it cannot catch one that reads a shape by another spelling. This round's own evidence shows the limit: the two fake `{issues: [ticket]}` pages spelled no paging token at all, so the pin could never have found them. The enumeration found them. The enumeration is the semantic half and is a point-in-time measurement; the pin keeps it from rotting. Neither alone is proof the class cannot recur.

**Named, not fixed.**
- The guard-mutation matrix runs the plain Jira double only. The scenario suite runs every Jira scenario in both shapes.
- With the double on the measured Linear shape, the kickoff's fail-open `pageIsLast` reads an incomplete Linear listing as complete. The matrix's kickoff-side expectation for that row changed accordingly (the kickoff now grades silently instead of warning). Every current-code expectation is unchanged.

**The dropped middle page, and the mirror counted again.** Stage B's review of this round found that the create decision never proved a multi-page set was one chain. It took "capped" from whichever page file came last, so a set missing its middle page (the one holding the existing ticket), or one given out of order, read as a complete miss and returned `create`: a DUPLICATE from the module built to prevent one. That was the same harm as D-4 and the attach step's window, by a third route. `sibling_release` had closed this class in an earlier review round; the create decision never got it. The chain rule now has one home, `readTrackerListing` in `tracker_answer.ts`:
- only the final page may be proven last;
- each earlier page names a `next`;
- each page after the first carries the `requestCursor` it was fetched with, equal to the previous page's `next`;
- no cursor repeats, and no key sits on two pages.

The create decision, the sibling check, the orphan listing and probe #49 all read multi-page listings through it. Red-before was on the harm itself: pages 1 and 3 without page 2, a reordered set, and a wrapped-Jira dropped page all returned `create` before and refuse now. A correctly linked chain still finds a ticket on its second page, and a single page is untouched. The documented contract gains what the sibling check already asked for: each saved page after the first records its `requestCursor`.

The orphan listing is the instructive instance, because one wrong rule failed in OPPOSITE directions on either side of this round. It called a listing complete only when EVERY page was last, which no correct multi-page listing can be. Before the strict reader, a multi-page Linear listing read as complete anyway (fail-open, since the old reader treated a missing paging field as last). After it, the same listing read as never complete (a false red). Probe #49 checked only the final page, so a set missing its middle page was graded as if whole. The same clause was wrong in both states, which is why "it went green" is not evidence. Counting the mirror pattern (a rule fixed on one path and not its twin) across this programme, this is at least its sixth instance, and every one was found by a reader who was not its author.

**Migration `linear-team-key`, for a break this milestone's own ruling caused.** The team rule reads a Linear row's team key from its identifier prefix, and a binding holding the team's display name therefore refuses every create decision. The template documented exactly that form (`team: <team-name>`). So an operator who followed the documentation would meet a refusal with no reason given. The template, the Schema L table and the setup step now say "the team KEY". A registered migration (`linear-team-key`, 2.90.0, scripted, explicit approval) makes the state gate-visible: probe #69 renders it on every `/gate-check`, which a release note would not.
- It repairs it only from what is local and checkable: the prefixes of the repository's own Linear-bound FR files, active and archived.
- When there are none, or they disagree, it REFUSES with the hand-set remedy and never guesses a key; `list_teams` exposes no key to look up.

- Reachability was measured on the maintainer's machine only, where the one Linear-mode repository already binds the key.

### The third pre-handover audit round: an inert guard, and the labels nobody created

The re-freeze at e93af85f was voided by the third independent audit. It confirmed every claim of the shared-reader round against the shipped code and could not break the chain reader, and it found two Linear run-killers. Measuring for the fix found a third.

**A value threaded to four places and not the fifth.** The live smoke's bootstrap never passed `--team` to the binding writer, so neither throwaway repository's declaration carried `team:`. Every create decision printed a payload with no team, and Linear's create requires one, so every Linear create would have failed. The fence did carry `LINEAR_TEAM` everywhere else: it captured the value, guarded it non-empty, recorded it in the run state and handed it to `extract`. A value threaded carefully to four places and missing from the fifth is harder to notice than a value nobody has, because every check you run finds it present.

**An INERT guard is a distinct failure from a wrong one.** With no team in the binding, the team conjunct never entered the query, so the identifier-prefix rule this programme added for the live run could not have fired on it. The same goes for the ticket-ownership team comparison, which is guarded by the binding having a team. Neither guard was wrong, unmeasured or untested; each was incapable of firing on the thing it was built for. The only question that catches this is "what makes this guard fire, and does the run produce it?" An empty team also strips `team` from every create payload, and Linear rejects such a create, so today a passing Linear verdict implies the guard was live. But that implication rests on an invariant outside the toolkit: Linear continuing to require `team`. So the grade now shows it directly instead of inferring it. Every Linear create decision's recorded payload must carry the run's team (`team-conjunct-inert` otherwise), and a run that recorded no create decision never showed the guard live. The bootstrap now writes the team and refuses unless both declarations carry it.

The same pattern appears a second time in this round, deliberately. Neither the tracker-write gate's label-create permit nor the grader's matching rows can fire on a live run, because the run creates its tag labels from the operator's own session, which declares no shared container, and no child creates a label. They are correct, tested offline, and structurally incapable of firing on the run that is supposed to prove them. This time that is by design: moving label creation into a child to make the guard exercisable would bend the run to suit the instrument. It is named here so the two instances read as one thing: a guard's correctness and its reachability by the run are separate facts, and each needs its own evidence.

**Measuring the fix found a third run-killer.** The pre-flight resolved the team with `.key == <LINEAR_TEAM>` against a saved team lookup, but no Linear tool answers a `key`. Measured: neither `get_team` nor `list_teams` carries one. The skill's stub fed an invented `{key, name}`. So the Linear leg would have refused at its pre-flight, before its first write. That is the invented-shape class once more, in the one fixture the shared-reader round did not reach, because it lives in the skill harness rather than in a tracker reader. The pre-flight now names the tool (`get_team`, saved verbatim), requires the team to be key-shaped, and takes the answer's `id` as the team uuid the label creates need.

**The labels nobody created, and the mirror in the hook.** A Linear create naming a label the team does not hold fails, and nothing created the two repository-tag labels. Phase 2 now creates both from the operator session with `save_issue_label`, names them in the approval, and a check refuses the first spawn unless both resolve. Teardown retires them, since the MCP cannot delete a label; that step is not graded. Underneath sat a shipped defect for every Linear user. The hook permitted only `create_issue_label`, which the Linear MCP itself marks deprecated, while `save_issue_label` with no `id` (the tool the MCP's own description steers a model to) fell through to the catch-all refusal. The grader mirrored the same single-tool permit. Both now permit `save_issue_label` with no `id` naming a declared repository tag. With an `id` it is still a refused rename. Red-before was on both. The gap existed only on Linear, because Jira labels are free-form strings, which is why it survived a Jira-shaped reading. This is another instance of the mirror pattern (a rule fixed on one path and not its twin).

**The skill harness was a second population of invented shapes.** The boundary pin grades production modules. The skill's own stubs, which stand in for tracker answers when the harness tests the document, were never in its scope, and one of them invented `{key, name}` for a tool that has never returned a key. So they were enumerated like the readers: every answer the harness writes was read and classified. Six stood in for real answers:
- two were measured once this round's fixes landed (the team lookup and the label listings);
- two were invented (both forms of the second-server read, one carrying a Linear `key` field that no answer has);
- two were trimmed subsets of measured answers (the Jira space and create-metadata lookups).

All six are now built from the pinned measured answers, and the skill names the tool that produces each saved input. No other tracker-shaped literal exists in the harness; the live-bundle fixtures and the tracker doubles were already bound to the pins.

**The label permit, tightened, and one gap named with its right remedy.** The label-create permit now allows only a PLAIN label: a label group, or a label nested under one, named like a repository tag has no honest use and is refused (red-before in the hook and the grader).

Named, not fixed: the permit checks the label's NAME against the declared repository tags, never the team the label lands in. A team-scoped Linear label names its team by `teamId`, a uuid, and the gate reads only a team key, so repository A can create its own tag label inside a sibling's declared team. This is pre-existing: the permit was written this way for `create_issue_label` and inherited when `save_issue_label` joined it. The harm is bounded: no duplicate container, no sibling ticket written, and no tag stripped, because retire, restore and rename stay refused. It is not nothing, though. A's tag existing in B's team makes it applicable there, and a ticket in B carrying A's tag is an ownership misattribution, even though each such write is gated separately.

The obvious fix, refusing any label create that names its team by an opaque id, would be wrong. A team-scoped label REQUIRES a `teamId`, and no tool resolves a uuid to a key, so that rule would forbid the action and leave no legal way to perform it. That is the same shape as a hard stop whose remedy has no legal input. The right fix is a binding-schema change: the declaration records its team's uuid beside the key (the pre-flight already obtains it from `get_team`). Then "this `teamId` is my declared team" becomes answerable offline, and the permit is precise without closing the legal path. That belongs to the follow-on milestone.

**Named, not fixed.** The milestone decision's Jira Epic listing refuses a page that does not prove it is the last, with the remedy "page the search to the end and save one listing holding every Epic". The front door takes one page file, and one page holds at most the search's page size, so once the Epic search spans pages the remedy has no legal input. That is a hard stop, fail-closed, and unreachable against a fresh throwaway space. It is recorded here so it is known before someone meets it.

### The fourth pre-handover audit round: fences that trusted their inputs

The re-freeze at 8d794f4f was voided by the fourth independent audit. It confirmed every closure of the previous round against the shipped code, and both of its HIGHs sat inside code that commit added. The old surface is stabilising; new code is now where defects come from. So every fence added from here gets a precondition-absent row before it is called done.

**STANDING RULE: for every precondition a fixture supplies, one row that omits it.** This is the third time a precondition that every fixture supplied made a defect structurally invisible, after the Jira `project` field and the invented Linear paging. The new tag-label fence sourced its run state with no failure check. With the run state missing, or `<tracker>` left unsubstituted, it took the "not a Linear run" branch and exited 0. It was the one guard whose job was to stop every child failing its create, and it disarmed itself and reported green. No test saw it, because every test row wrote a run state first. The rule now applies to every fence, existing and new, as an audit of the ones this programme did not add, not only as a promise about future ones.

**What the audit of the other fences found.** Ten fences source the run state; at the fence audit's start, only the new one had been checked. Omitting one precondition at a time was measured against each fence's committed body: 63 of 99 rows failed open (exit 0, or a child spawned), and the other 36 refused for an unrelated reason. They were:
- the audit spawning its child with an empty search query;
- scenario steps spawning children in the operator's own directory;
- the privacy dry run and the extract step checking nothing themselves.

The worst was S11's worktree fence with its repository variable empty: `git -C ""` and `cd ""` both mean "here", so the fence COMMITTED the operator's own uncommitted `CLAUDE.md` into whatever repository they were standing in, added an exclude line to it, and only then refused. That was driven in a throwaway repository before any fix, and it is the worst thing found in this milestone: the run writing into the user's work.

One structural fix covers every omit-one row the audit measured; it does not cover everything, as the named items below record. A single run-state preamble, byte-identical in all ten fences, refuses before anything else when the run state is unreadable, the tracker is not exactly the substituted one, or any variable that fence declares is empty. The test finds the fences from the document itself, so an eleventh fence written bare reds, and it holds the preamble identical across them. It runs one omit-one row per fence and declared variable, plus a missing-run-state row and bad-tracker rows. A sweep parses every fence for paths built from a variable (`git -C`, `cd`, `rm`, `mkdir`, `cp`, `mv`, `chmod`, `worktree add`, plugin and project roots) and requires each such variable to be declared and guarded: 137 sites, none unguarded after the fix. The same audit found two unguarded startup steps (a plan written with unparseable counts, and a run state written without its spawn ceiling), both now refusing. It also found the wait fence reading a missing step pidfile as "exited" and exiting 0, telling the operator a step had finished that never ran. That fence now refuses the missing pidfile, and it also no longer exits 1 on a normal exit.

The Linear projects got the same treatment the labels had, the mirror in the operator's own paragraph. The tool and its required team argument are named, both projects are verified from their saved lookups against the run's team before any spawn, and the teardown marker is written after the first tracker write rather than after the fourth. Labels are retired by id, since the retire tool takes no name, and the containers fence reads its answers from the same directory the pre-flight does.

**The fifth audit: no HIGH, two fixes before the keyboard, and what stays named.** The fifth independent audit traced every fence's declared run state against the real phase sequence on both trackers. It checked the preamble's variable test on the actual bash 3.2, and checked every Linear tool and answer the new fences read against the live MCP. It found no variable a correct run can leave empty and no field the server does not send.

The path sweep's control asserts more than 20 sites while this record reports 137, so the sweep could lose most of its reach and stay green. It is neither a fail-open nor a mirror: it is a refusal whose remedy cannot be followed. **The mirror, in prose.** The two-commit amendment corrected the rule where STE-618 states it and left the same rule's older statement a few paragraphs later, still reading as one commit; the plan carried the same stale sentence.
