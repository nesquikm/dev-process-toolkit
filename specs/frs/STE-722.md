# Close-out offers a retrospective only when a rule tripped

## Summary

Today nothing tells an operator that a retrospective would find something.
This adds one question at the end of an implement run and at the end of a delivery run.
The question appears only when the project turns the offer on and at least one rule tripped.
A delivery run asks it once, never once per milestone and again inside each worker.
Declining prints the command to run later.

## Requirement

### The offer front door

New module `adapters/_shared/src/retro_offer.ts`, front door `bun run retro_offer.ts <projectRoot> <scope>` with the `if (import.meta.main)` guard, in the `video_offer.ts` shape:

- Reads `retro.enabled` first, before any scope or ledger read; a loader refusal counts as off.
- Prints nothing and exits 0 when `retro.enabled` is off, the scope resolves to no session, or no rule trips. `retro.enabled` gates this offer and nothing else; `/retro` itself always runs (STE-719, operator ruling R4).
- Otherwise prints `scope=<scope>` and then one line per tripped rule: `rule=<id> <value> <unit> > <threshold>`.
- It calls `resolveRetroScope` and `evaluateRetroRules` (STE-719), never a second derivation. An FR or milestone scope needs `tracking.token_stats` on (STE-719); with it off the offer stays silent and `/retro` names that reason.
- It is read-only and writes no report file; only `/retro` writes one.

### /implement

Registry entry in `CONTINUATION_OFFERS` (`continuation_offer.ts`):

- `id: "implement_retro_offer"`, `skill: "implement"`, `runsWhenAccepted: ["/retro"]`, `runsWhenDriven: []`.
- Anchor `Run a retrospective for <scope>? [y/N]`.

It sits in the `/implement` close-out after the M_94e6f7 `implement_upgrade_offer` and before the `implement_ship_ready_close` offer, so it is asked while the run's record is complete. Scope is the milestone on a milestone-scope run and the FR otherwise. Accept runs `/dev-process-toolkit:retro <scope>`. Decline prints `Run: /dev-process-toolkit:retro <scope>` and exits 0. The span carries `DRIVEN_OMISSION_CLAUSE`. `skills/implement/SKILL.md` carries the anchor, the clause and a one-line pointer. The detail lives in `docs/implement-reference.md`, and the skill stays within the 358-line cap.

### /deliver

Registry entry:

- `id: "deliver_close_retro_offer"`, `skill: "deliver"`, `runsWhenAccepted: ["/retro"]`, `runsWhenDriven: []`.
- Anchor `Run a retrospective for the delivered milestones? [y/N]`.

It is the second offer in `## Close-out — offers after the last milestone`, the section M_94e6f7 builds after `## Post-PR — merge-policy routing`, following `deliver_close_upgrade_offer`. `/deliver` refuses non-interactive stdin at its first action, so the offer needs no headless branch. `/deliver` runs `retro_offer.ts` once per delivered milestone and asks one question covering every milestone that printed rows. Accept runs `/retro` per such milestone. Decline prints one `Run:` line per milestone. The span carries `DRIVEN_OMISSION_CLAUSE`. Spawned workers run `/implement` driven, so their offer is omitted and the operator sees one question per run.

### Counts

`CONTINUATION_OFFERS` grows by two over the count M_94e6f7 leaves. In `tests/m143-ste-551-continuation-offers.test.ts` the length pin, the `offersForSkill("implement")` id list and any `offersForSkill("deliver")` pin move with it; the distinct-skill pin does not, since M_94e6f7 already added `deliver`. The module header's offer count is corrected to the new total.

### Defaults unchanged

Operator rule, 2026-11-04: this milestone changes no toolkit behaviour by default. This FR owns the milestone's proof, `tests/m_d1b4b7-defaults-unchanged.test.ts`. On a tree with no settings file, and on one whose settings file holds only M_94e6f7 and M_7bc805 keys, it runs `retro_offer.ts`, the `/report-issue` payload front door without `--from-retro`, and a modelled standalone `/implement` and `/deliver` close-out. Each output and written file must equal its v2.101.4 literal, and no close-out records an operator turn for a retro offer. It also asserts that `retro_proposal.ts apply` is never reached without an explicit approval (STE-728).

## Technical Design

The offer reuses three shipped pieces. The `video_offer.ts` shape gives empty stdout for no prompt. The registry and probe #85 give driven omission. The M_94e6f7 close-out section gives `/deliver` a place to ask. Because workers run `/implement` driven, only the orchestrator asks, so one run yields one question. The threshold lives only in the rule engine, so the offer and the report can never disagree about what tripped.
