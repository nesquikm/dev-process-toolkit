# Close-out offers a retrospective only when a rule tripped

## Summary

Today nothing tells an operator that a retrospective would find something.
This adds one question at the end of an implement run and at the end of a delivery run.
The question appears only when the project turns the offer on and at least one rule tripped.
A delivery run asks it once, never once per milestone and again inside each worker.
Declining prints the command to run later.

## Requirement

### The offer front door

New module `adapters/_shared/src/retro_offer.ts`, front door `bun run retro_offer.ts <projectRoot> <scope>` with the `if (import.meta.main)` guard, in the `video_offer.ts` shape.

### The offer rides an existing call

Supervisor ruling 2026-11-04, for operator review: with every switch off, a default close-out issues no extra tool call. Both close-outs already run one command on v3.0.0, the STE-712 `upgrade_offer.ts <projectRoot>` call. So this FR folds the retro switch read into that call, the pattern STE-715 uses for `outcome: on`:

- `upgrade_offer.ts` also reads `retro.enabled`, through the same loader and the same refusal-means-off rule. When it is on, the CLI prints one extra last line, exactly `retro: on`. When it is off, its stdout is byte-identical to v3.0.0 on every input.
- The skills run `retro_offer.ts` only when that call printed `retro: on`. With the offer off no such line exists, so no retro call is made.
- The upgrade question is asked only when the upgrade CLI printed `UPGRADE_OFFER_QUESTION`. An output holding only `retro: on` counts as no upgrade offer, so the Phase 4 remedy line stays as STE-712 says. The STE-712 fixtures carry no `retro:` section, so its ACs hold unchanged.
- Every sentence of `skills/implement/SKILL.md`, `skills/deliver/SKILL.md` and their reference docs that names `retro_offer.ts` also names `retro: on`.

The front door itself:

- Reads `retro.enabled` first, before any scope or ledger read, as a second guard; a loader refusal counts as off.
- Prints nothing and exits 0 when `retro.enabled` is off, the scope resolves to no session, or no rule trips. `retro.enabled` gates this offer and nothing else; `/retro` itself always runs (STE-719, operator ruling R4).
- Otherwise prints `scope=<scope>` and then one line per tripped rule: `rule=<id> <value> <unit> > <threshold>`.
- It calls `resolveRetroScope` and `evaluateRetroRules` (STE-719), never a second derivation. An FR or milestone scope needs `tracking.token_stats` on (STE-719); with it off the offer stays silent and `/retro` names that reason.
- It is read-only and writes no report file; only `/retro` writes one.

### /implement

Registry entry in `CONTINUATION_OFFERS` (`continuation_offer.ts`):

- `id: "implement_retro_offer"`, `skill: "implement"`, `runsWhenAccepted: ["/retro"]`, `runsWhenDriven: []`.
- Anchor `Run a retrospective for <scope>? [y/N]`.

It sits in the `/implement` close-out after the M_94e6f7 `implement_upgrade_offer` and before the `implement_ship_ready_close` offer, so it is asked while the run's record is complete. It is offered only when the upgrade call printed `retro: on`. Scope is the milestone on a milestone-scope run and the FR otherwise. Accept runs `/dev-process-toolkit:retro <scope>`. Decline prints `Run: /dev-process-toolkit:retro <scope>` and exits 0. The span carries `DRIVEN_OMISSION_CLAUSE`. `skills/implement/SKILL.md` carries the anchor, the clause and a one-line pointer. The detail lives in `docs/implement-reference.md`, and the skill stays within the 358-line cap.

### /deliver

Registry entry:

- `id: "deliver_close_retro_offer"`, `skill: "deliver"`, `runsWhenAccepted: ["/retro"]`, `runsWhenDriven: []`.
- Anchor `Run a retrospective for the delivered milestones? [y/N]`.

It is the second offer in `## Close-out — offers after the last milestone`, the section M_94e6f7 builds after `## Post-PR — merge-policy routing`, following `deliver_close_upgrade_offer`. `/deliver` refuses non-interactive stdin at its first action, so the offer needs no headless branch. When the close-out's upgrade call printed `retro: on`, `/deliver` runs `retro_offer.ts` once per delivered milestone and asks one question covering every milestone that printed rows. Without that line it runs none. Accept runs `/retro` per such milestone. Decline prints one `Run:` line per milestone. The span carries `DRIVEN_OMISSION_CLAUSE`. Spawned workers run `/implement` driven, so their offer is omitted and the operator sees one question per run.

Operator rule, 2026-11-04: this milestone changes no toolkit behaviour by default. This FR owns the milestone's proof, `tests/m_d1b4b7-defaults-unchanged.test.ts`. The baseline is v3.0.0, the M_94e6f7 merge commit; every literal is pinned from its bytes (supervisor ruling 2026-11-04, for operator review). On a tree with no settings file, and on one whose settings file holds only M_94e6f7 and M_7bc805 keys, it runs `upgrade_offer.ts`, `retro_offer.ts` and the `/report-issue` payload front door without `--from-retro`. Each output and written file must equal its v3.0.0 literal; `retro_offer.ts`, being new, must print nothing. The modelled `/implement` and `/deliver` close-outs take their reached offers from those real outputs, never as a hand-written input. They must record no operator turn and no `retro_offer.ts` call. The one named difference is the `/report-issue` front-door call of STE-720, which prints nothing. It also asserts that `retro_proposal.ts apply` is never reached without an explicit approval (STE-728).

## Technical Design

The offer reuses three shipped pieces. The `video_offer.ts` shape gives empty stdout for no prompt. The registry and probe #85 give driven omission. The M_94e6f7 close-out section gives `/deliver` a place to ask. Because workers run `/implement` driven, only the orchestrator asks, so one run yields one question. The threshold lives only in the rule engine, so the offer and the report can never disagree about what tripped.
