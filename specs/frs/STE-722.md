# Close-out offers a retrospective only when a rule tripped

## Summary

Today nothing tells an operator that a retrospective would find something.
This adds one question at the end of an implement run and at the end of a delivery run.
The question appears only when the project turns the offer on and at least one rule tripped.
A delivery run asks it once, never once per milestone and again inside each worker.
Declining prints the command to run later.

## Requirement

### The offer front door

New module `adapters/_shared/src/retro_offer.ts`, front door `bun run retro_offer.ts <projectRoot> <scope>` with the `if (import.meta.main)` guard, in the `video_offer.ts` shape.

### The offer rides an existing call

Operator ruling at the v3.0.0 rebase: with every switch off, a default close-out issues no extra tool call. The retro switch is read inside the two calls v3.0.0 already makes for its own close-out switch, exactly as `upgrade_offer: on` is printed (STE-712, `upgradeOfferSwitchOn`):

- `gate_capture.ts` (the `/implement` step 14 run) and `deliver_decision.ts` (the `/deliver` decision command) each read `retroSwitchOn(projectRoot)` (STE-719) beside `upgradeOfferSwitchOn`. When it is on, each prints one extra line, exactly `retro: on`. A loader refusal reads off.
- The switch lines trail the record in a fixed order: `retro: on`, then `upgrade_offer: on`. With only the retro switch on, `retro: on` is the last line. With both on, `upgrade_offer: on` stays the last line, so the shipped STE-712 contract ("printed `upgrade_offer: on` as its last line"), its skill sentences and the AC-STE-712.14 pins hold byte for byte, and `retro: on` is the line before it. These one or two lines are the call's trailing switch lines.
- With the retro switch off, each call's stdout is byte-identical to v3.0.0 on every input, with the upgrade switch on or off.
- `upgrade_offer.ts` is not touched: it reads no retro key and its stdout stays byte-identical to v3.0.0.
- The skills run `retro_offer.ts` only when the call's trailing switch lines hold `retro: on`. With the offer off no such line exists, so no retro call is made.
- Every sentence of `skills/implement/SKILL.md`, `skills/deliver/SKILL.md` and `docs/implement-reference.md` that names `retro_offer.ts` also names `retro: on`.

The front door itself:

- Reads `retro.enabled` first, before any scope or ledger read, as a second guard; a loader refusal counts as off.
- Prints nothing and exits 0 when `retro.enabled` is off, the scope resolves to no session, or no rule trips. `retro.enabled` gates this offer and nothing else; `/retro` itself always runs (STE-719, operator ruling R4).
- Otherwise prints `scope=<scope>` and then one line per tripped rule: `rule=<id> <value> <unit> > <threshold>`.
- It calls `resolveRetroScope` and `evaluateRetroRules` (STE-719), never a second derivation. An FR or milestone scope needs `tracking.token_stats` on (STE-719); with it off the offer stays silent and `/retro` names that reason.
- It is read-only and writes no report file; only `/retro` writes one.

### /implement

Registry entry in `CONTINUATION_OFFERS` (`continuation_offer.ts`):

- `id: "implement_retro_offer"`, `skill: "implement"`, `runsWhenAccepted: ["/retro"]`, `runsWhenDriven: []`.
- Anchor `Run a retrospective for <scope>? [y/N]`.

It sits in the `/implement` close-out after the M_94e6f7 `implement_upgrade_offer` and before the `implement_ship_ready_close` offer, so it is asked while the run's record is complete. It is offered only when step 14's `gate_capture.ts` run printed `retro: on` among its trailing switch lines. Scope is the milestone on a milestone-scope run and the FR otherwise. Accept runs `/dev-process-toolkit:retro <scope>`. Decline prints `Run: /dev-process-toolkit:retro <scope>` and exits 0. The span carries `DRIVEN_OMISSION_CLAUSE`. `skills/implement/SKILL.md` is at the 358-line cap, which six tests pin exactly (`tests/ticket-ownership-shared.test.ts`, `tests/m_79b1f6-ste-590-offers-ask-the-gate.test.ts`, `tests/m_685ff6-ste-609-prose.test.ts`, `tests/m_8f07e0-ste-584-awaiting-siblings.test.ts`, `tests/m_79b1f6-ste-592-epic-mint-prose.test.ts` and the `tests/m143-ste-550-inline-no-terminal-block.test.ts` net-zero baseline). The cap is not raised (AC-STE-712.9 awaits the operator). So the offer adds no line: its sentences are appended in place to the Phase 4 Close paragraph that already carries the upgrade offer (line 297 at v3.0.0), after that offer's omission clause and before the `### Ship-ready close offer` heading. The anchor, the `retro: on` condition, the accept and decline paths, `DRIVEN_OMISSION_CLAUSE` and a pointer to `docs/implement-reference.md` § Retro offer all sit in those appended sentences. The file keeps 358 split-lines, every other line keeps its bytes and position, and none of the six pins moves. Probe #85's span for `implement_upgrade_offer` then ends at the retro anchor, so each offer's clause stays inside its own span. The detail lives in `docs/implement-reference.md` § Retro offer.

### /deliver

Registry entry:

- `id: "deliver_close_retro_offer"`, `skill: "deliver"`, `runsWhenAccepted: ["/retro"]`, `runsWhenDriven: []`.
- Anchor `Run a retrospective for the delivered milestones? [y/N]`.

It is the second offer in `## Close-out — offers after the last milestone`, the section M_94e6f7 builds after `## Post-PR — merge-policy routing`, following `deliver_close_upgrade_offer`. `/deliver` refuses non-interactive stdin at its first action, so the offer needs no headless branch. When the decision command `deliver_decision.ts` printed `retro: on` among its trailing switch lines, `/deliver` runs `retro_offer.ts` once per delivered milestone and asks one question covering every milestone that printed rows. Without that line it runs none. Accept runs `/retro` per such milestone. Decline prints one `Run:` line per milestone. The span carries `DRIVEN_OMISSION_CLAUSE`. Spawned workers run `/implement` driven, so their offer is omitted and the operator sees one question per run.

## Technical Design

The offer reuses four shipped pieces. The `video_offer.ts` shape gives empty stdout for no prompt. The registry and probe #85 give driven omission. The M_94e6f7 close-out section gives `/deliver` a place to ask, and the M_94e6f7 switch line gives both skills a zero-cost signal. Because workers run `/implement` driven, only the orchestrator asks, so one run yields one question. The threshold lives only in the rule engine, so the offer and the report can never disagree about what tripped.
