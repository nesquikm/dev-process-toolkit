# One runnable front door for every delivery decision

## Summary

The delivery orchestrator names eight shared modules and orders six of their decisions to be taken from code rather than by eye. Not one of those modules can actually be run. They carry no command-line entry point, so the order is prose, and a reader who cannot execute it does the next best thing and renders the classification in their own words. That happened on a real run and went unnoticed for twenty minutes.

This adds a single runnable command that prints the whole pre-spawn decision record for a delivery argument. It decides nothing itself. Every field it prints is asked of the module that already owns that question, so the command is an assembly and a printer, and a second answer cannot hide inside it.

One entry point, not seven. Seven would mean seven output formats and seven places for them to drift apart.

## Requirement

A single command prints the delivery pipeline's entire pre-spawn decision record, assembled from the modules that already own each answer.

## Acceptance Criteria

- AC-STE-513.1: A new module at `adapters/_shared/src/deliver_decision.ts` carries an `import.meta.main` command-line guard following the shipped idiom in `active_plan_ship_ready.ts`.
- AC-STE-513.2: Importing the module executes no side effect — the guarded block does not run under `import`, asserted by a test that imports it and observes no output.
- AC-STE-513.3: `bun run <plugin-root>/adapters/_shared/src/deliver_decision.ts <argument> [projectRoot]` runs, and `projectRoot` defaults to `process.cwd()` when the second positional is absent.
- AC-STE-513.4: The printed record carries all seven labelled fields in one fixed order: argument kind, target-repo route, resume state, the rendered chain, effective merge policy, the confirm gate's class, and whether that gate still relays. A record missing any field is a refusal, not a shorter record.
- AC-STE-513.5: Every chain step in the record carries its placement on the step's own line. A chain rendered without per-step placement is refused.
- AC-STE-513.6: The module delegates to `deliver_argument`, `target_repo`, `resume_classifier`, `orchestration_config`, `merge_policy_ratchet` and `gate_class`, and contains no branch of its own over argument kind, route, resume state, merge policy or gate class.
- AC-STE-513.7: AC.6 is mutation-verified per delegate: a test stubs each of the six in turn and asserts the printed record changes. A delegate whose stub leaves the output byte-identical is a second answer living in this module, and the test fails.
- AC-STE-513.8: The record is read-only — running the command mutates no file, writes to no tracker, and creates no commit, asserted by a byte-comparison of the tree before and after.
- AC-STE-513.9: A malformed or unresolvable argument surfaces the canonical refusal shape and exits non-zero; it never prints a partial record.

## Technical Design

The idiom is the shipped one. `active_plan_ship_ready.ts` guards its entry point with `import.meta.main` so the module stays free of side effects when imported and runs as a command when invoked, and this module copies that shape rather than inventing a second one.

Assembly-only is the load-bearing constraint and AC.7 is what makes it real. A module that re-derives even one of its six answers becomes a second home for a question that already has one, which is the defect the whole approach exists to prevent. Asserting the absence of a branch by reading the source is weak; asserting that stubbing each delegate visibly changes the output proves the delegate is actually consulted.

The resume state is itself assembled — the classifier reaches four further predicates for plan task counts, ship-readiness, stamp coherence and the review-flag enumeration. Those stay behind the classifier. This module asks the classifier one question and does not reach past it.

Field order is fixed because the confirm gate renders these bytes verbatim. A record whose field order varies between runs cannot be compared against what a gate displayed.

## Testing

Unit tests import the module and assert no output, proving the guard holds. Command-level tests invoke it as a subprocess for each argument kind and assert the seven fields in order, with per-step placement present.

The mutation suite is the centre of gravity. Six stubs, six assertions that the output moved. A stub that changes nothing is reported as a failure naming the delegate, because that is the shape a re-derivation takes.

Read-only is asserted by hashing the tree before and after a run rather than by inspecting the code for write calls.

## Notes

Corrects the approved design on one point. The design defined reachability as an entry point present AND at least one non-test consumer. This module is a pure front door and will have no importer, so that rule would classify it unreachable on the day it ships. See the triage FR in this milestone for the corrected rule and the nine shipped modules the original rule misclassified.
