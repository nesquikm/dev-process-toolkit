# The test capture runs the commands a project declares

## Summary

The gate capture and the skip-baseline capture always run a built-in test command.
A project that tests through a version manager or per-service make targets gets the wrong tool.
A project can now list its own test commands in its settings file.
The captures run each command and add up the counts.
A command that gives no count fails the whole capture.
A project that lists nothing runs exactly as before.

## Requirement

When a project declares its test commands in its settings file, the gate capture and the skip-baseline capture run exactly those commands and sum their counts, failing closed; when it declares none, both behave as in v3.3.0.

## Acceptance Criteria

- AC-STE-730.1: `specs/settings.yaml` accepts an optional `verification.test_commands`: a non-empty list of mappings, each with exactly `stack` (one of `bun`, `pytest`, `flutter`, which picks the count parser) and `command` (a non-empty list of non-empty strings). Any other shape throws `SettingsShapeError` naming the dotted path (e.g. `verification.test_commands[1].command`). The key is added to the closed key order, `NEW_KEYS` and `docs/settings-reference.md`.
- AC-STE-730.2: A legacy CLAUDE.md verification block never supplies the key; such projects keep today's table.
- AC-STE-730.3: With the key present, `gate_capture.ts` and `capture_skip_baseline.ts` run every entry's `command`, in list order, from `<projectRoot>`, each through the existing bounded supervisor, and never run the `stack_layout.ts` table command.
- AC-STE-730.4: Pass, fail and skip totals are the sums of every entry's parsed counts; `gate_capture.ts` prints one totals line for the sum; the baseline record names every declared command in order.
- AC-STE-730.5: An entry with no readable count, or killed on its bound, makes both front doors refuse in the NFR-10 shape naming that entry; no baseline is written and `gate_capture.ts` exits non-zero. A partial sum never stands.
- AC-STE-730.6: A declared entry is count-only: no report flag is added to its argv, and the record's `namesSource` says it was a declared command with no report.
- AC-STE-730.7: With the key absent, both front doors' argv, output and record are byte-identical to v3.3.0.
- AC-STE-730.8: Fixtures prove it: a fake `fvm` wrapper on `PATH` shows the wrapper ran and bare `flutter` did not; a two-entry fixture shows summing; a red entry shows the refusal.
- AC-STE-730.9: Removing the declared-list read, the summation or the fail-closed rule turns at least one named test red.
- AC-STE-730.10: `bun test` from `plugins/dev-process-toolkit` reports 0 failures, and its skip identities equal the trunk baseline by name.

## Technical Design

### Root cause

Both front doors take the runner from the `stack_layout.ts` marker table, which maps a marker file to one hard-coded argv. Nothing a project writes can change it, so a wrapper or per-service target is never run.

### Fix

One resolver returns the declared entries when the settings key is present and the table's single entry otherwise. Both front doors loop over its result through the shipped supervisor and parser, summing counts. A declared command still comes from a tracked file and never from argv, so the "a caller handed a command" guard holds.

## Testing

Temporary project roots with a settings file, fake runner scripts on a private `PATH` that print recorded runner output, and the shipped front doors run as subprocesses; mutation controls for each rule.

## Notes

Origin: field reports from a Flutter project pinned through a version manager and a Python monorepo with per-service make targets. No setup prompt writes the key; it is documented only.
