# Ticket provenance checks which server and site answered

## Summary

The write gate trusts a ticket it saw fetched in the session.
It did not check which Jira site answered that fetch.
A project can now name its Jira site in its settings.
When it does, reads, writes and ticket links must point at that site.
A project that names no site keeps the old behaviour.

## Requirement

A Jira binding may declare its site, and then the tracker-write gate and its live grader count only evidence from that site and permit only writes to it.

## Acceptance Criteria

- AC-STE-871.1: `task_tracking.jira` in `specs/settings.yaml`, and the legacy `### Jira` sub-section, accept the optional keys `site` (a host, stored lower case with no scheme, port or path) and `cloud_id` (a UUID). `readWorkspaceBinding` returns them. A `site` that is no host, a `cloud_id` that is no UUID, or either key under Linear refuses in the NFR-10 shape naming the key. A blank value reads as absent.
- AC-STE-871.2: A call's `cloudId` matches when it is the declared `cloud_id` in any case, or the declared `site` as a bare host or an `https` URL of that host in any case. Every other value is a mismatch, and so is a missing, blank or non-string `cloudId`. Host comparison is exact: a host with the declared one as prefix or suffix is a mismatch.
- AC-STE-871.3: With a site declared, a gated Jira write in scope of that binding with a mismatched `cloudId` is refused through the `.sh` wrapper, direct and wrapped, on v1 and v2. The refusal names the value and the declared site, and when the value is a UUID and no `cloud_id` is declared, or a host and no `site` is, it says which key to add. Permit twins pass.
- AC-STE-871.4: With a site declared, a `getJiraIssue` answer, a create answer, a search page and a container re-list whose call has a mismatched `cloudId` is no evidence, in the hook and in every deciding command that reads calls from the transcript. Newer evidence from another site neither proves ownership nor hides an older matching answer.
- AC-STE-871.5: With a `site` declared, a `/browse/<KEY>` URL resolves only on that host, in issue links, graph links and every other subject the gate reads a URL from. Another host is an unresolvable side. With only `cloud_id` declared, browse URLs resolve as today.
- AC-STE-871.6: Any MCP server spelling that reaches the declared site counts. The server name is not evidence.
- AC-STE-871.7: With neither key declared, every verdict, stdout and stderr equals v3.10.0 over the existing gate and grader suites, which pass unmodified, and undeclared repositories keep exit 0 with no output.
- AC-STE-871.8: The live grader gives the hook's verdict for each payload above. One shared function compares sites.
- AC-STE-871.9: `/setup`, `adapters/jira.md`, the settings reference and `docs/setup-tracker-mode.md` document both keys as optional, say where to read the values, and say that an older client refuses a settings file with an unknown key, so `min_dpt_version` must be raised with them.
- AC-STE-871.10: Removing the write check, the evidence check, the browse-host check or the exact host comparison each turns at least one named test red.
- AC-STE-871.11: `bun test` from `plugins/dev-process-toolkit` reports 0 failures, and its skip identities equal the trunk baseline by name.

## Technical Design

A new module `atlassian_site.ts` holds `siteMatches(binding, cloudId)` and `browseHostMatches(binding, url)`. The binding readers gain two fields. The hook's transcript walk and the grader filter calls through the shared function per target, because one session may bind several roots with different sites. A call in scope of two bindings must match each target that it writes for. The translator already unwraps `cloudId` and refuses two values, so both readers take the canonical input.

## Testing

Settings reader tests for both homes, hook tests through the `.sh` wrapper for each evidence kind, grader twins, and an unmodified run of the existing suites.
