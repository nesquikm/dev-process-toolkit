# A retrospective shows the trend across runs

## Summary

A single retro grades one run, so a slow drift across many runs stays invisible.
A trend mode now reads the ledgers across the last twenty runs of each kind of work.
It groups runs by skill, change type and size.
It shows waste, tokens and time next to four quality signals.
A number with no recorded data says so and is never shown as zero.
It writes one report and changes nothing else.

## Requirement

`/retro --trend [--last N]` reports waste, tokens, time and four quality signals per skill, category and size group over the last N runs, ordered by `retro.priority`, and writes one report file and nothing else.

## Acceptance Criteria

- AC-STE-776.1: `retro.ts <root> --trend [--last N]` defaults N to 20, a constant. N must be a positive integer, given at most once, and `--trend` takes no other argument; otherwise, or when the loader refuses `retro.priority`, the command refuses in the NFR-10 shape. `skills/retro/SKILL.md` documents the flag.
- AC-STE-776.2: A run is one archived FR's delivery: the sessions its token-ledger rows claim. Its group is the skill, the FR's `changelog_category` and a size bucket. Size is the added plus deleted lines of the commits whose footer carries `Refs: <FR id>`: S under 100, M 100 to 500, L over 500, all constants. An archived FR whose ledger rows claim no session is no run; a run's skill is the skill on its first claimed row, and an FR with no `changelog_category` groups under `unknown`. When git cannot be read, every run's size reads `unknown`. An FR with no `Refs:` commit has 0 changed lines, sizes as S, and reads skipped for every value that needs its commits.
- AC-STE-776.3: Per group, over the window, waste is reruns on an unchanged key plus rounds that changed no file, per run; tokens is parent-visible output tokens per changed line; time is the run's median gate wall time. Each metric shows its window median and the difference between the newer and the older half of the window; when either half has no observable value, the cell reads skipped.
- AC-STE-776.4: Per group, the four quality signals are the gate failure rate (failed over all gate outcomes), spec-review missing plus partial ACs per FR, code-review concerns per 100 changed lines (both from `review-findings` receipts), and post-merge fixes: `fix` commits within 14 days of the FR's last commit that touch a file the FR changed and do not reference the FR.
- AC-STE-776.5: A value whose input is not recorded reads `skipped: not observable` and names the tracking key that is off. A group with fewer than 5 runs reads `insufficient: <n> runs`. Neither ever reads 0.
- AC-STE-776.6: Metric columns follow `retro.priority`. Groups are sorted worst first by the newer-half change of the first-ranked metric.
- AC-STE-776.7: The command writes exactly one file, `.dpt/ledger/retro/trend-<stamp>.json` with schema `dpt-retro-trend/1`. Sessions appear only as aliases, each with the 16-hex digest the single-run report also carries, and the file holds no path, command or branch name. It writes no receipt, settings or proposal, and `retro_proposal.ts` refuses a trend report.
- AC-STE-776.8: A pinned fixture project prints known numbers for every metric and signal. Removing the grouping, the skipped rule or the insufficient rule turns at least one named test red.
- AC-STE-776.9: `bun test` from `plugins/dev-process-toolkit` reports 0 failures, and its skip identities equal the trunk baseline by name.

## Technical Design

A new `retro_trend.ts` beside `retro.ts`. It reuses the timeline, the token-ledger claims and the gate receipt readers that the single-run rules already use, adds a git reader for `Refs:` commits and post-merge fixes, and reads `retro.priority`. Constants live in one table. The report reuses `session_aliases.ts`. `retro.ts` routes `--trend` to the new module and keeps its single-run path unchanged.

## Testing

A fixture project built in a temporary root: a git history with `Refs:` footers and later fix commits, a token ledger, gate receipts, timeline captures and `review-findings` receipts, with known expected numbers; groups with 4 and 5 runs; each tracking key off in turn.
