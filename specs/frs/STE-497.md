# /deliver refuses a milestone identity it cannot deliver, instead of brainstorming it

## Summary

The orchestrator's argument is documented as a feature request or idea. A milestone identity is a well-formed value for that, so naming one is accepted and enters the design phase — brainstorming a feature whose design and specs already exist and, often, are already merged.

The operator's intent and the skill's behaviour diverge with no signal at all. The first visible symptom is a Socratic question about work that shipped last week. This is a wrong shape accepted rather than merely an unsupported path, and it is worth fixing on its own even if the surrounding resume capability were declined.

## Requirement

An argument that names a milestone or FR identity is recognized as one, and the orchestrator never treats such an identity as a fresh feature idea.

## Acceptance Criteria

- AC-STE-497.1: `/deliver`'s argument grammar admits a milestone identity and an FR identity alongside a feature request.
- AC-STE-497.2: Milestone-identity recognition uses the shared milestone-token grammar from `adapters/_shared/src/milestone_token.ts` rather than a hand-rolled pattern.
- AC-STE-497.3: An identity that names no plan file on disk refuses in the NFR-10 canonical shape and never falls through to the design phase.
- AC-STE-497.4: That refusal names both plausible intents, so an operator who meant to start new work is told how to do so.
- AC-STE-497.5: An FR identity resolves to its `milestone:` frontmatter and then follows the same routing.
- AC-STE-497.6: A non-identity argument behaves exactly as it does today.
- AC-STE-497.7: Under non-tty stdin every form above still refuses with the canonical `<dpt:requires-input-refused>v1</dpt:requires-input-refused>` marker; identity recognition earns no carve-out.

## Technical Design

`skills/deliver/SKILL.md` line 4 declares `argument-hint: '[feature request or idea]'`, and a sweep of the skill and its reference for "resume", "already exists", "skip Phase", and "existing milestone" returns zero hits. Nothing rejects a milestone identity, so it is accepted as an idea.

AC.2 matters because the milestone grammar is not simply `M\d+`: the tracker-less and Jira routes mint `M_<short-ULID>` and `M_<epic-key>` forms respectively. Hand-rolling the pattern here would recognize only the Linear-style numeric form and silently misroute the other two.

AC.3 is the actual defect fix and is deliberately separable from the classifier FR in this milestone: even with no resume capability at all, refusing beats silently brainstorming a shipped milestone. AC.4 exists because the refusal must not strand an operator who genuinely meant to start new work whose name resembles an identity.

AC.7 restates the existing unconditional non-tty refusal so that widening the argument grammar cannot be read as widening the headless surface.

## Testing

Grammar coverage for milestone identities in all three minted forms, for FR identities, and for ordinary prose arguments. NFR-10 refusal coverage for an identity with no plan file, asserting both that it refuses and that it does not enter the design phase — the second half mutation-verified, since a refusal that still fell through would pass a naive assertion. Non-tty refusal asserted for every argument form. `bun test` full root.

## Notes

Origin: 2026-08-17 feature request filed from a downstream repo after merging a spec-only pull request, reporting that the natural invocation would have brainstormed an already-merged milestone.

The reporter explicitly separated this refusal from the resume capability and argued it is worth shipping alone. That separation is preserved here as its own FR so the defect can land even if the classifier work slips.
