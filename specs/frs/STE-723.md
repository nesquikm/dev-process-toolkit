# The settings file names a closed set of reuse knobs and a probe refuses any other

## Summary

A project can ask its gate to reuse a result already proved on identical input.
One settings section accepts only knobs from a fixed list, each set to reuse or run.
Every knob is off unless the project turns it on, and an off knob changes nothing.
Reuse also requires gate outcome recording, which it never turns on itself.
A new gate probe fails on any other knob, any other value, or a knob aimed at the review.

## Requirement

### Schema

`specs/settings.yaml` (the M_94e6f7 consolidated settings file) gains an optional top-level `optimizations:` mapping. It is read through the M_94e6f7 settings loader and never re-parsed privately. `docs/settings-reference.md` documents `optimizations.gate_commands`, and the M_94e6f7 key-mapping table (AC-STE-706.12) gains a `new` row naming this FR. `/setup` writes no `optimizations:` section.

Loader wiring (rebase onto v3.0.0: every new key lives in the loader's closed key sets). `TOP_KEYS` gains `optimizations` as its last entry, and `settingsKeyOrder("optimizations")` returns `["gate_commands"]` (that is, `OPTIMIZATION_KNOBS`), so the section is a closed set like every v3.0.0 section. Its validator requires a map and closes it with that list, so an unknown or refused knob name throws `SettingsShapeError` naming `optimizations.<key>`. The knob's value is not checked by the loader: any scalar passes, and `validateOptimizations` grades it. `ProjectSettings` and `defaults()` gain `optimizations: { gate_commands: "run" }`, the legacy load returns that default, and `NEW_KEYS` gains `"optimizations.gate_commands"`. The AC-STE-706.12 test's `MAPPING` gains `"optimizations.gate_commands": { kind: "new", fr: "STE-723", note: "no legacy home" }`, and its "every new key is off when absent" row learns that an enum knob's off value is `run`, the moved assertion carrying an `Amended by AC-STE-723.8: an enum knob is off at run.` comment. The planted-knob control still reports only `orchestration.skip_gates`.

What the closed set changes, and why it is safe. The draft passed the section through so that a bad knob would not refuse every settings read. On v3.0.0 a section read validates only its own section, so a bad knob name refuses only `optimizations` reads, which `readOptimizations` maps to `run`. Whole-file readers (`loadProjectSettings`: the binding probes, the settings writer and the setup audit) refuse a bad knob name loudly, exactly as they refuse `orchestration.skip_gates` today, and the probe names the reason. A bad value never refuses anything. Only a user who wrote the section can reach either state, so no default tree changes.

```yaml
optimizations:
  gate_commands: reuse   # reuse | run   (absent = run)
```

- **Closed knob set** `OPTIMIZATION_KNOBS = ["gate_commands"] as const`. `gate_commands` covers the project's deterministic gate commands (typecheck, lint, test, build) run by `/gate-check` and nothing else.
- **Closed value set** `OPTIMIZATION_VALUES = ["reuse", "run"] as const`. `run` is the default and equals an absent key or an absent section.
- **Refused names** `NEVER_REUSABLE_STEPS`: `code_review`, `review`, `spec_review`, `tdd`, `probes`, `conformance_probes`, `tracker_probes`, `upgrade_staleness`. Each names a step that is an LLM judgement or reads outside the tree (the `/gate-check` `## Code Review` section, the tracker probes, probe #69, the date-epoch probes). A knob with one of these names is refused with its own reason, distinct from an unknown name.
- **One effect only.** The sole effect any knob may have is reuse of a stored deterministic pass, as decided by STE-724. No knob skips a command, lowers a severity, or changes what a run checks. With `gate_commands` anything but `reuse`, `/gate-check` runs exactly as today: no front door, no step receipts (operator ruling R6).
- **One dependency, never implied.** Reuse needs the stored outcome records of STE-715, so `gate_commands: reuse` takes effect only when `tracking.gate_outcomes.enabled` is `true`. Nothing turns that key on implicitly: not this knob, not the loader, not the probe. Without it, `readOptimizations` reads every knob as `run`, and the probe reports `requires-gate-outcomes`. The loader checks the knob name only, as decided above, so the dependency is graded by the reader and the probe, never by a loader refusal.
- **No environment override.** No `DPT_*` variable and no `userConfig` field changes a knob's value. The existing `DPT_*` knobs (`DPT_GATE_TIMEOUT_MS`, `DPT_SKIP_FETCH` and the rest) stay where they are and stay out of the settings file. `milestone_scan_fetch`'s precedence chain is untouched.

### Module

A new module `adapters/_shared/src/optimizations_config.ts` exports `OPTIMIZATION_KNOBS`, `OPTIMIZATION_VALUES`, `NEVER_REUSABLE_STEPS`, `readOptimizations(projectRoot)` (reads `loadProjectSection(projectRoot, "optimizations")` and `gateOutcomesSwitchOn` from STE-715, and returns the effective knob map, every knob `run` when the section is absent, refused or invalid, or when `tracking.gate_outcomes` is off) and `validateOptimizations(raw, gateOutcomesEnabled)` (returns violations). The probe and the STE-724 front door both call `validateOptimizations`; there is no second validator.

The module carries an `import.meta.main` entry with one verb: `bun run optimizations_config.ts knob <root> <knob>` prints the effective value from `readOptimizations`, `reuse` or `run`, and exits 0. A knob name outside `OPTIMIZATION_KNOBS` exits 1 in NFR-10 shape with nothing on stdout. The verb is for hand runs and tests. No skill calls it, so an off knob costs no tool call: `/gate-check` keys on the `reuse: on` line its receipt call prints (STE-724), and `/simplify` on that line in the gate-check run it already consults (STE-725).

### Probe

A new `/gate-check` probe `optimizations_reuse_only` at the next free probe number, registered in `skills/gate-check/SKILL.md` by a probe line that says: call `runOptimizationsReuseOnlyProbe(projectRoot)` from `adapters/_shared/src/optimizations_config.ts`. **Severity: error.** Vacuous when the tree is not toolkit-managed (routed through `isToolkitManaged` in `toolkit_managed.ts`), when the settings file is absent or foreign (`isForeignSettingsFile`), or when it has no `optimizations:` section. It decides the shape from the parsed value, never from the raw lines. A new export in `project_settings.ts`, `settingsSectionValue(projectRoot, section)`, parses the file with the loader's own `Bun.YAML.parse` and returns `{ value }` for the section, or `null` when the file is absent, unreadable or not valid YAML; it never throws and validates nothing. A plain-object value is a mapping, whatever its YAML style: block style, flow style such as `optimizations: { gate_commands: reuse }` (the style STE-716 itself writes, and that the STE-710 writer keeps), and the empty `optimizations: {}`, which holds no knob and passes with zero violations. Any other value, `null` from a bare `optimizations:` line included, is `not-a-mapping`. Knob names are the parsed object's own keys, so `unknown-knob` and `never-reusable` are named even when the loader refuses the section. Lines come from `settingsSectionKeys` when it lists the key (block style); a key it does not list, as every flow-style key, cites the section's own line from `settingsKeyLine(projectRoot, "optimizations")`. A file that `settingsSectionValue` cannot parse leaves this probe vacuous, since every loader read of it already refuses in NFR-10 shape. It grades values through the loader's `optimizations` read when that read succeeds. Violation rows use the NFR-10 shape with `specs/settings.yaml:<line> — <reason>`. Reasons: `unknown-knob`, `unknown-value`, `never-reusable`, `not-a-mapping`, `requires-gate-outcomes`. A vacuous run returns zero violations and zero notes.

## Technical Design

One small module owns the vocabulary, the reader and the validator. The probe and the reuse front door call the same validator, so their verdicts cannot drift.

The reader fails toward `run`: an absent, malformed or refused section means no reuse anywhere. The refused-name list exists so that an author who writes `code_review: reuse` gets a reason naming why, not a bare unknown key.

The section is read through the M_94e6f7 settings loader. No environment variable takes part, which keeps the knob out of reach of a model-written env block.

## Testing

Unit cases for the reader and validator; a probe test with one positive and one negative fixture per reason; a source grep with a control; mutation controls.

## Notes

Depends on M_94e6f7 for the settings loader and on the STE-715 outcome switch. Only one knob ships, on purpose. A second knob needs its own FR proving its step is deterministic and in-tree. The key name gate_commands is a recorded milestone decision.
