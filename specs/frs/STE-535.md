# Plan narrative is capped by section kind, not by section name

## Summary

Milestone plans carry most of their length in prose under headings that vary between plans, so no fixed section name can find it. One recent plan spent 939 words on tasks and over 2000 on narrative under headings no other plan uses. This classifies each subsection by what its body is rather than what it is called, and caps the ones that are prose.

## Requirement

Any level-three subsection of an active plan whose body is prose is capped at a hundred and fifty words. A subsection is structural, and so exempt, when its checkbox items, markdown table rows and fenced code lines counted together make up more than sixty percent of its content lines; the three kinds form one combined structural share rather than three independent exemptions.

## Acceptance Criteria

- AC-STE-535.1: A classifier returns narrative or structural for a subsection from its BODY alone, never from its heading text. The function takes the body and does not receive the heading, so name-based classification is not merely discouraged but unavailable.
- AC-STE-535.2: A body more than sixty percent checkbox ITEMS classifies structural, where an item spans its checkbox line plus any indented continuation lines beneath it. Counting bare checkbox lines instead misclassifies the plan template's own mandated two-line task entry — an action line plus an indented verify line — which sits at exactly fifty percent and so can never clear a sixty percent threshold. The threshold is a named constant and the test asserts both sides of it.
- AC-STE-535.2a: The discriminating case is asserted directly against the mandated two-line task format: a Tasks body written to the template's own shape classifies structural. Measured on this milestone's own plan, the line-counting variant classified that body narrative at 346 words, so the two definitions disagree on the single most common subsection in every plan this toolkit writes.
- AC-STE-535.3: A body that is a markdown table classifies structural, recognised by a header row followed by a delimiter row rather than by counting pipe characters, so a prose line mentioning a pipe does not read as a table.
- AC-STE-535.4: A body that is a fenced code block classifies structural, and an unterminated fence does not swallow the rest of the file into one section.
- AC-STE-535.5: A narrative subsection over a hundred and fifty words yields a violation naming the file, the line, the rule and the heading it was measured under. The cap is a named constant.
- AC-STE-535.6: Only active plans are scanned. `specs/plan/archive/` is frozen history and yields no violations, asserted directly against this repository's archive tree, which held every plan it has before M137.
- AC-STE-535.7: Renaming a section does not change its classification. The test takes one body, classifies it under two different headings, and asserts the two verdicts are equal — the rule cannot be evaded by renaming, which is the whole reason classification is by kind.
- AC-STE-535.8: The scanner is run over this repository's own active plans in the same commit, and the result is asserted non-vacuous — at least one subsection actually classified. This repository had no active plan before M137 wrote one.
- AC-STE-535.9: Mutation-verified, each mutation asserted to have applied. Inverting the classifier turns AC-STE-535.2's assertion red; passing the heading into the classifier and branching on it turns AC-STE-535.7's red.

## Technical Design

Classification is a pure function from body to kind, which is what makes AC-STE-535.7 assertable rather than merely intended. The scanner walks level-three headings the same way the FR scanner walks level-two ones, so the two share a section-walk helper rather than each owning a copy.

The mixed-body case is decided by the checkbox majority in AC-STE-535.2, counted over items rather than lines. A subsection that is half prose and half checklist is narrative, because the prose half is the part that grows.

The plan and FR scanners report through one violation type so probe #67 renders both without a second code path.

## Testing

AC-STE-535.2's threshold is tested on both sides rather than at one point, because a threshold asserted once is satisfied by a constant function.

AC-STE-535.7 uses the same body twice under different headings; the assertion is equality of verdicts, not the value of either.

Fixtures come from the measured plans in this repository's archive, so a classifier that happens to work only on hand-written examples fails.

## Notes

The hundred and fifty word cap would flag M136's 634-word header and its 1161-word follow-ups section, and several subsections of M129. That was the point.
