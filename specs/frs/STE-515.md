# The resume confirm gate is registered, not merely defaulted

## Summary

The gate taxonomy sorts approval points into three classes and decides from that class whether a standing authorization can reach one. The resume confirm gate is not in the registry at all. It gets the right answer today by falling through to the fallback for unknown gates, which happens to be the class that no standing authorization reaches.

Right answer, no pin. A fallback that produces the correct verdict by accident is indistinguishable from one that produces it on purpose, and the day someone changes the fallback, this gate changes class with it and nobody finds out. Registering it makes the non-delegability explicit and testable.

Registration changes no verdict today, which is exactly why it needs a test that can tell the difference. The evidence is not that the class is right — it already is — but that it is now declared rather than inherited from a branch meant for gates nobody has thought about.

## Requirement

The resume confirm gate is a registered entry in the gate taxonomy, classified so that no standing authorization can reach it.

## Acceptance Criteria

- AC-STE-515.1: The resume confirm gate is a registered entry in the shipped gate registry, carrying the class that no standing authorization reaches and a summary naming the action it gates.
- AC-STE-515.2: Looking the gate up by id returns a registered descriptor rather than nothing, asserted directly rather than inferred from its classification.
- AC-STE-515.3: Classifying the gate returns the same class it returned before registration, so the shipped verdict is unchanged and the change is a pin rather than a behaviour change.
- AC-STE-515.4: AC.3 is asserted against the fallback rather than assumed: a test changes the unknown-gate fallback to a different class and asserts this gate's classification does NOT move. Before registration that same mutation moves it.
- AC-STE-515.5: The gate still relays with no delegation on the record, and continues to relay under a standing authorization covering the delegable class.
- AC-STE-515.6: The registry's other entries are untouched — their ids, classes and summaries are byte-identical, asserted rather than assumed.

## Technical Design

The registry is a flat list of descriptors and classification is ordered and fail-closed: a guard hit wins outright, a registered gate gets its declared class, and anything else falls back. This gate reaches its class through the third branch, which is the branch meant for gates nobody has thought about.

AC.4 is what makes this FR falsifiable rather than cosmetic. Registering a gate whose classification does not change is easy to assert vacuously — the verdict is the same before and after, so a test comparing verdicts passes either way. Mutating the fallback discriminates: an unregistered gate follows the fallback and moves, a registered one does not. That mutation is the entire evidence that registration took effect.

AC.6 guards the sweep hazard. Editing a flat exported list is exactly where an unrelated entry loses a character.

## Testing

Registration is asserted by lookup, not by classification, because classification passes for the wrong reason. The fallback mutation runs both ways: with the gate registered the classification holds, and a control asserting an unregistered id does move under the same mutation, so the test is shown to be capable of failing.

Delegation behaviour is asserted with no delegation on the record and with a standing authorization present, covering both sides of the reachability question.

## Notes

Follows the shipped principle that a shared module plus a gate check beats prose. The prose already said this gate was non-delegable; nothing enforced it.
