# Fixture group 7's tdd-result count must read forked-child tool_result content

## Summary

The check that counts the test-driven-development orchestrator's hand-off blocks looks for them at the start of a line. Since captures became a streaming JSON format, there are no line starts to find — newlines are encoded as characters inside a string — so the count is zero on every run, healthy or broken. The recommended repair routes through a helper that also returns zero, because these particular blocks arrive as tool results rather than assistant messages. Correctly scoped, the subject is healthy on all three runs.

## Requirement

The group-7 count reads the fenced blocks where they actually arrive — inside forked-child `tool_result` content — and is proven by STE-483's harness to fail when the blocks are absent. The two retired forms and the reason each was wrong are recorded so the repair is not attempted a third time.

## Acceptance Criteria

- AC-STE-484.1: The group-7 assertion counts fences inside forked-child `tool_result` content and returns a non-zero count on each of the three archived healthy captures (linear 8, jira 6+1 and 5+1, none 12).
- AC-STE-484.2: Both the line-anchored form and the bare unanchored form are retired; Notes record that the unanchored form was also vacuous, matching the injected SKILL body rather than the run.
- AC-STE-484.3: The assertion's counts exclude the injected synthetic-`user` SKILL body, so the number reflects the run and not the prompt.
- AC-STE-484.4: STE-483's harness proves the assertion fails when the blocks are absent from the capture.
- AC-STE-484.5: The SKILL prose naming `extractAssistantText` as the repair for this assertion is corrected — it is the wrong projection for fork-emitted blocks, and saying so prevents a third round of the same mistake.

## Technical Design

Three independent measurements agree. The assertion is a line-anchored `grep -c` for the fence tag against `/tmp/dpt-smoke-<tracker>-implement.log`, requiring ≥ 3. STE-352 made `--output-format stream-json --verbose` mandatory, so that capture is NDJSON with newlines JSON-escaped as two characters — a line-anchored pattern has no line to anchor to and returns 0 unconditionally.

The documented repair is also wrong, and that is the part worth pinning. `extractAssistantText` (STE-421) excludes `user` and `tool_result` events by design, and the orchestrator's children run `context: fork`, so their blocks arrive precisely in the excluded events. Routing through it returns 0 as well. The correct projection reads fork-emitted `tool_result` content.

The unanchored fallback is vacuous in the other direction: on the jira leg 2 of its 14 matches came from the injected synthetic-`user` SKILL body and are run-independent, so it would pass on a run where the orchestrator emitted nothing.

## Testing

Assertion run against all three archived captures (expect non-zero) and against a capture with the fork blocks stripped (expect fail) via STE-483's harness. Unit test on the projection helper. `bun test` full root.
