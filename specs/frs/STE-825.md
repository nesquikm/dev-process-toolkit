# Probe #14 passes a ticket that is not started, and the commit gate refuses a failed gate

## Summary

A new tracker ticket waits in the backlog until implementation claims it.
Probe 14 calls that state drift, so every tracker spec run fails the gate.
The model then commits through the failure, which teaches it to ignore a failed gate.
The probe now passes a ticket that is provably not started.
All three signs must hold together.
The commit gate also refuses a commit when the recorded gate verdict was a failure.

## Requirement

Probe #14 passes an active FR whose ticket is provably not started, and `pre-commit-gate-check` refuses a commit whose vouching gate run recorded a `fail` outcome.

## Acceptance Criteria

- AC-STE-825.1: `activeTicketDriftPasses` gains a not-started carve-out. It passes only when all three hold: the ticket's status maps to the `initial` role (the backlog or todo lane), no checked task line in the FR's milestone plan names the FR's tracker id, and no lock entry names the FR.
- AC-STE-825.2: Three tests each make exactly one of the three conditions false, and each one still fails the probe with the existing drift row.
- AC-STE-825.3: Probe #14's truth table in `skills/gate-check/SKILL.md` gains the not-started row, and a pass through it is logged as `carve_out: not_started`.
- AC-STE-825.4: When the gate run that vouches for a commit has a recorded `gate-outcome` of `fail` for that checkout, `pre-commit-gate-check` refuses the commit with exit 2. The refusal names the failed run and says to fix the gate or re-run it. With no outcome recorded, behaviour is unchanged.
- AC-STE-825.5: A later `pass` outcome for the same checkout clears the refusal, and a `fail` recorded for another checkout does not refuse this one.
- AC-STE-825.6: `docs/hooks-reference.md` describes the failed-outcome refusal.
- AC-STE-825.7: `bun test` from `plugins/dev-process-toolkit` reports 0 failures, and its skip identities equal the baseline by name.

## Technical Design

The carve-out reads the plan's task lines (via `plan_task_state.ts`) and the lock store (`lock.ts`). In tracker mode no lock file is ever written, so the third condition holds there by construction, but it is still read. The hook reads the newest `gate-outcome` receipt for the vouched checkout through `gate_receipt.ts`, beside the existing receipt leg.

## Testing

Predicate unit tests for the carve-out and each single-condition failure. Hook tests with fail, pass-after-fail and foreign-checkout outcomes.
