# Probe #14 passes a ticket that is not started, and the commit gate refuses a failed gate

## Summary

A new tracker ticket waits in the backlog until implementation claims it.
Probe 14 calls that state drift, so every tracker spec run fails the gate.
The model then commits through the failure, which teaches it to ignore a failed gate.
The probe now passes a ticket that is provably not started.
All three signs must hold together.
The commit gate also refuses a commit when the recorded gate verdict was a failure.

## Requirement

Probe #14 passes an active FR whose ticket is provably not started, and `pre-commit-gate-check` refuses a commit whose vouching gate run recorded a `fail` outcome.

## Acceptance Criteria

- AC-STE-825.1: `activeTicketDriftPasses` gains a not-started carve-out. It passes only when all four hold: the ticket's status maps to the `initial` role (the backlog or todo lane); no checked task line (`[x]` or `[X]`) in the FR's milestone plan names the FR's tracker id; no lock entry names the FR; and nothing shows the work has begun, meaning no run-start ledger row of `/implement` or `/tdd` names the FR and no commit on HEAD or a local branch whose message names the tracker id (in any letter case) touches a path outside `specs/`. A caller that does not supply the started evidence gets no carve-out, and a history that cannot be read (git missing, failing or timing out) counts as evidence that the work began; only a repository with no commits yet reads as not started.
- AC-STE-825.2: Four tests each make exactly one of the four conditions false, and each one still fails the probe with the existing drift row. A ticket whose work began without a claim fails, and a freshly written FR with only its own spec commit still passes.
- AC-STE-825.3: Probe #14's truth table in `skills/gate-check/SKILL.md` gains the not-started row, and a pass through it is logged as `carve_out: not_started`.
- AC-STE-825.4: `pre-commit-gate-check` reads every gate run announced for the checkout, in any window, in transcript order, once a window vouches for the checkout. An outcome counts only when its own `dpt-gate-outcome` announcement is in the transcript after its run and the file still hashes to the announced digest; outcomes are ordered by that announcement. The newest counted outcome decides: `fail` refuses the commit with exit 2, naming the failed run and saying to fix the gate or re-run it; `pass` admits. A receipt call with no outcome never changes the verdict. A call that runs the outcome verb and has no result in the transcript yet is waited for like a receipt run; still missing after the wait, the commit is refused as a pending gate outcome. A call that runs the outcome verb but is not counted (a compound command, an error result, a missing or extra announcement line) is an unreadable outcome and refuses until a later counted outcome decides. Both are scoped to the gate the call names; a call that names no gate it can place counts for every gate. An older verdict never decides past a pending or unreadable one. When no run has an outcome, behaviour is unchanged.
- AC-STE-825.5: A later run's `pass` outcome for the same checkout clears the refusal, in the same window or a later one, including a window another checkout opened; an outcome file nothing announced never clears it; a later `fail` refuses after an earlier `pass`; and a `fail` recorded for another checkout does not refuse this one.
- AC-STE-825.6: `docs/hooks-reference.md` describes the failed-outcome refusal.
- AC-STE-825.7: `bun test` from `plugins/dev-process-toolkit` reports 0 failures, and its skip identities equal the baseline by name.

## Technical Design

The carve-out reads the plan's task lines (via `plan_task_state.ts`) and the lock store (`lock.ts`). In tracker mode no lock file is ever written, so the started leg reads the run-start ledger and the commit history instead. The run-start ledger is opt-in, so before the first commit with tracking off the carve-out still admits; that residual is named in the SKILL. The hook grades only outcomes the transcript announced after their run, with the file still intact, and the newest such outcome decides.

## Testing

Predicate unit tests for the carve-out and each single-condition failure. Hook tests with fail, pass-after-fail and foreign-checkout outcomes.
