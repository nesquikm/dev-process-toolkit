# What a consumer copies works for the consumer, not for this repo

## Summary

The stack examples and the project template are copied wholesale, so a defect here ships into every project that adopts the toolkit. This repo's gate exercises none of it.

One example names this repository's own directory, so any other consumer gets a path not in their tree. Every example hardcodes a dash the grader tolerates three spellings of. The starter workflows are strict subsets of the gate they claim parity with. The template omits a key the first gate requires.

## Requirement

No shipped example hardcodes this repository's own paths or refuses in a consumer's tree, and a project configured from the template alone passes the probes the template's own keys govern.

## Acceptance Criteria

- AC-STE-569.1: No shipped example hardcodes this repository's own paths. `examples/plugin/release.yml` carries a `plugins/<your-plugin>/` placeholder, its marketplace entry is `optional: true` (a plugin repo that is not also a marketplace has no such file), and the header says in one line which paths the consumer must edit — repeated at the two places that hand the file to a consumer, `skills/setup/SKILL.md` step 7e and `docs/ship-milestone-reference.md`.
- AC-STE-569.2: That is asserted by SWEEP over every shipped example, not by fixing the one instance found: a test reds on any `examples/**` file containing this repository's own plugin path. The audit that produced these findings first searched a directory that does not exist and returned confidently empty, so the enumeration is derived from the tree rather than from a list.
- AC-STE-569.3: `examples/plugin/release.yml` carries the `specs/requirements.md` entry the root block gained in STE-554, marked `optional: true` so a consumer whose overview line has no quoted codename skips rather than refuses. Its header describes the entries it actually has. The dogfood claim is either made true or dropped — a fixture that calls itself the dogfood case and diverges from the block it mirrors is worse than one that claims nothing.
- AC-STE-569.4: Every shipped example's README `pattern` accepts the same dash class `README_LATEST_RE` accepts, while `replace` keeps the em-dash so a bump canonicalizes it. MEASURED: for each of em-dash, en-dash and hyphen, the shipped pattern run through the real `bumpRegex` bumps a banner carrying that dash, and the retired em-dash-only pattern is measured to throw on the other two in the same leg.
- AC-STE-569.5: The two grammars are asserted to AGREE rather than each being asserted separately — the dash class the writer accepts is compared against the class the grader accepts, so widening one and not the other reds. This is the whole defect: two correct-looking grammars that disagree.
- AC-STE-569.6: `kotlin` joins step 7e's stack roster in `skills/setup/SKILL.md` and the per-stack defaults in `docs/ship-milestone-reference.md`, so the mapping the skill already declares at two earlier steps is one `/setup` can act on. The roster is asserted against the set of `examples/*/release.yml` on disk, so a sixth stack cannot be added without appearing in it.
- AC-STE-569.7: Each starter CI workflow runs everything its sibling `gate-commands.md` runs, satisfying the parity rule `docs/adaptation-guide.md` states and points at these files to demonstrate. A `kotlin` starter workflow joins them, and the guide's list of starter configs names every one that ships. Asserted by comparing the two files per stack rather than by pinning a command list.
- AC-STE-569.8: `templates/permissions.json` uses the `:*` prefix form for every argument-carrying entry, as the file's own `_doc` prescribes. A bare rule for a command that is never invoked bare is inert, which this repo has measured before; the consumer currently gets an allowlist that looks configured and permits nothing. Asserted: no entry names a command that the shipped gate-command examples invoke with arguments, without the `:*` suffix.
- AC-STE-569.9: `examples/flutter-dart/gate-commands.md` and `docs/adaptation-guide.md` stop advertising a `/bump-version` skill that would be a second writer for the `pubspec.yaml` version `/ship-milestone` owns. Fixing only the example would leave the guide stale, which is how this class propagates.
- AC-STE-569.10: A project configured from the template alone passes the probes the template's own keys govern. `templates/CLAUDE.md.template` states that tracker mode also requires a populated `### Linear` (team + project) or `### Jira` (project) sub-section under `## Task Tracking`, naming probe #25 as what hard-fails without it. Asserted END-TO-END: a fixture project whose `CLAUDE.md` is built from the template's own documented keys is run through probe #25 and passes — the statement is about the outcome, not about the sentence.
- AC-STE-569.11: The template's `field:` legend states the three per-kind capabilities the parser enforces rather than one capability for three kinds. MEASURED by execution against the real `parseReleaseFiles` and `bumpFile`: each documented example is legal for the kind it is offered under, and at least one previously-offered combination is measured to be refused, so the assertion names the defect it fixes.
- AC-STE-569.12: The template's specs tree carries `deps.yaml` and `best-practices.yaml`, both real toolkit-read surfaces, and its skill inventory names `/deliver` — described as the orchestrator that consumes the `## Orchestration` block the template itself documents — alongside `/spec-archive` and `/best-practices`. Asserted: every user-invocable skill the template's `## Orchestration` keys are read by is named somewhere in the template.
- AC-STE-569.13: `milestone_scan_fetch` gains the deterministic reader every other documented key has. `adapters/_shared/src/milestone_scan_fetch_config.ts` exports `readMilestoneScanFetch(claudeMdPath)` (standalone top-level line; absent or malformed ⇒ `false`) and `resolveFetchPolicy({ noFetch, fetch, configValue })` encoding the documented four-way precedence, both unit-tested including the absent-line leg and the `--no-fetch`-beats-`--fetch` leg, and `skills/spec-write/SKILL.md` names the reader rather than describing the parse in prose.
- AC-STE-569.14: The remediation text a consumer reads when the release-surface codename drift fires states the condition rather than a universal. Since STE-554 the toolkit writes that field, so "this field goes stale unless it is written by hand" is false for exactly the project reading it in this repo and true for one on the shipped examples; the wording names which case the reader is in.
- AC-STE-569.15: Falsifiability. AC.2, AC.4, AC.5, AC.8 and AC.10 are mutation-tested — reintroducing this repo's plugin path into an example reds AC.2, narrowing either dash class reds AC.5, stripping a `:*` suffix reds AC.8, and removing the workspace binding from the fixture reds AC.10 — each routed through the throwing `mutate` helper.

## Technical Design

Two of these are grammar-agreement defects and they get an agreement check, not two corrected literals. A writer and a grader that each look right alone and disagree in the middle is the shape of both the dash finding and its sibling FR's Kotlin finding.

Optionality is used where the surface is genuinely optional and refused where it is not. That distinction is load-bearing: an optional miss is silent, so a wrong pattern on a required field reports success.

The template AC is written as an outcome, not a sentence — a template that mentions the binding and a project that still fails the probe would satisfy a prose assertion.

The permissions change is upstream, not in the byte-identical copies.

## Testing

Every measurement in this FR runs the real module. The dash finding, the `field:` finding and the Kotlin finding were all found by execution and none of them is visible to a string assertion, so the tests execute `bumpRegex`, `parseReleaseFiles` and `bumpFile` rather than describing them.

The example sweep enumerates the directory rather than iterating a list, because the audit that produced these findings demonstrated the failure mode: a reader handed a path that does not exist returns a confident empty result, which is indistinguishable from a clean surface.

## Notes

The examples surface is not assumed exhaustive. The audit's first pass over it searched a non-existent directory, and the findings here came from a corrected second look; the sweeps in AC.2 and AC.6 are written to enumerate rather than to check a list precisely so a finding the audit missed still reds.
