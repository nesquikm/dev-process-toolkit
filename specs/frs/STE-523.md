# A numeric milestone under the Epic binding writes where the reader looks

## Summary

A project that adopts Epic-keyed milestones still has its old numeric ones. The reader already knows this and carries a grandfather clause: for a numeric token under the Epic binding it stops looking at the parent and looks at the label instead, because those milestones predate Epics and were bound with labels. The writer has no such clause. It routes on the declared binding alone, so it sets a parent for a milestone whose binding will only ever be read off a label.

Nothing throws. The parent is set, the read-back confirms the parent, and the attach reports success. The predicate then reads labels, finds nothing, and says the binding is absent — so the next sweep attaches again, sets the same parent again, reports the same success, and the count of work done never falls. The reported symptom is a backfill that says it fixed two tickets on every pass, forever.

The fix is to give the writer the clause the reader already has. Route on the token's kind as well as on the declared binding, and send a numeric token to the label surface. The two sides then read and write the same field for the same milestone, which is the only arrangement in which a second pass can find nothing left to do.

## Requirement

Under the `epic` binding the attach routes on the milestone token's KIND as well as the declared binding, so a grandfathered numeric milestone writes to the label surface the reader's own grandfather clause reads.

## Acceptance Criteria

- AC-STE-523.1: In `attachProjectMilestone`, the `epic` branch routes on the milestone token's kind: an epic-kind token binds via the parent Epic, and a numeric-kind token takes the label path, writing `milestone-M<N>` through the existing read-merge-write attach.
- AC-STE-523.2: The non-convergence is reproduced and asserted closed: with `milestoneBinding: "epic"` and milestone `M15`, `milestoneBindingPresent(freshIssue, canonicalName, "epic")` is TRUE immediately after the attach returns, asserted in the same test. This criterion FAILS on the current implementation, where the attach sets a parent and the predicate reads labels.
- AC-STE-523.3: A second attach over the same ticket is a no-op: the predicate stays true, and the label is not duplicated in the label set. Two passes are asserted rather than one, because the reported symptom is a sweep that reports the same work done on every pass.
- AC-STE-523.4: On AC.2's numeric fixture, `setParent` is called ZERO times, asserted as a call count. A numeric milestone under this binding must not acquire a parent Epic at all; leaving one behind re-creates the divergence the criterion is meant to close.
- AC-STE-523.5: The epic-kind path is asserted UNCHANGED in the same test file: an epic token still binds by parent and its label set is untouched. Without this pin the numeric routing could silently capture both kinds and every epic case would fail elsewhere.
- AC-STE-523.6: An unparseable leading token under the `epic` binding is not silently routed to either surface — it refuses, naming the token. Malformed tokens reaching a binding decision are how a bad milestone id becomes a wrong write rather than an error.
- AC-STE-523.7: The declared `label` binding is byte-unchanged: a numeric token under `milestoneBinding: "label"` behaves exactly as it does today. The two paths converge on the same write, and this criterion pins that as intentional reuse rather than accidental duplication.

## Technical Design

The routing decision moves from `provider.milestoneBinding === "epic"` alone to that condition plus the parsed kind of the canonical name's leading token. The token extraction is the same expression `milestoneBindingPresent` and `milestoneLabel` already use, so all three surfaces recover the token identically.

Reusing `attachViaMilestoneLabel` for the numeric case is deliberate and is what makes AC.2 true by construction rather than by coincidence. The reader's grandfather clause calls `milestoneLabel(canonical)` and checks membership; the label attach writes `milestoneLabel(canonical)` and read-back-verifies membership. One function decides the string on both sides.

The capability result for this path stays as it is. Surfacing an informational row for a numeric milestone bound by label under an Epic-declared adapter is a real gap, but the token set that would have to carry it is a separate, lower-severity finding batched elsewhere, and widening this FR to add a token would drag the closing-summary contract and its probe into a milestone about binding convergence.

The malformed-token refusal in AC.6 is not new behaviour invented here so much as behaviour that currently has nowhere to happen: today an unparseable token falls through to the epic path, sets a parent, and the predicate's own `try` swallows the derivation failure into a `false`. Once the writer routes on kind, the third case has to be named.

## Testing

Both passes in AC.3 are driven through the real attach, not simulated by calling the predicate twice. The failure being pinned is a write that does not land where the read looks, so a test that never writes twice cannot see it.

The call-count assertion in AC.4 is the one that distinguishes a real routing change from a fix that writes the label in addition to setting the parent. That weaker implementation would satisfy AC.2 and AC.3 and still leave a numeric milestone parented to an Epic, which is the state that makes the phantom-id finding worse.

AC.5 is placed in the same file rather than trusted to the existing epic suite, so a single run shows both kinds behaving differently under one binding. Kind-routing bugs are symmetric by nature and a suite split across files tends to catch only one direction.
