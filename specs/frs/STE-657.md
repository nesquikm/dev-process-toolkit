# Plans carry a validated codename composed at spec time

## Summary

A milestone plan now records its own release codename, so nobody is asked what to call a release.
When the spec-writing skill writes a plan, it composes the heading title and a short codename from the approved design.
The codename is checked against the same rules the release has always enforced, before the plan is written.
One shared validator and one plan reader serve every consumer, so the rules live in exactly one place.

## Requirement

- **Shared validator.** One function decides whether a codename is valid: trimmed, non-empty, at most 32 characters, no backtick, no line break. It returns the value or names the rule broken.
- **Plan reader.** One function reads a plan's optional `codename:` key: the value, or nothing when the key is absent or `null`; an invalid value refuses.
- **Front door.** The reader has a command form that prints one line, so prose skills never re-derive the rules.
- **Template.** The plan template carries the key.
- **Composed, never asked.** `/spec-write` composes the plan title and the codename from the approved design and never asks the operator for either.

## Acceptance Criteria

- AC-STE-657.1: `validateCodename(value)` in `adapters/_shared/src/milestone_codename.ts` accepts every codename read from the `## [X.Y.Z] — date — "Codename"` headers of this repo's `CHANGELOG.md`, and rejects `""`, a whitespace-only value, a 33-character value, a value containing a backtick, and values containing `\n` or `\r`, each with a reason naming the broken rule.
- AC-STE-657.2: `readPlanCodename(planPath)` returns the `codename:` value, returns `null` when the key is absent or the literal `null`, and throws an NFR-10 canonical error naming the plan path and the broken rule when the value fails `validateCodename`.
- AC-STE-657.3: `bun run adapters/_shared/src/milestone_codename.ts <planPath>` prints exactly one stdout line, `codename=<value>` or `codename=absent`, and exits 0; on an invalid value it prints the NFR-10 envelope on stderr, nothing on stdout, and exits 1.
- AC-STE-657.4: `templates/spec-templates/plan.md.template` carries a `codename:` frontmatter line directly after `migration:`, with a comment naming the four rules and the front door.
- AC-STE-657.5: The plan.md section of `skills/spec-write/SKILL.md` states that the milestone title and the codename are composed from the approved design and never asked, and that the composed codename passes the front door before the plan file is written.
- AC-STE-657.6: A prose test asserts that the plan.md section of `skills/spec-write/SKILL.md` contains no prompt or `AskUserQuestion` instruction asking for the milestone title or codename, and goes red when such a line is planted.

## Technical Design

New module `adapters/_shared/src/milestone_codename.ts` exporting `CODENAME_MAX = 32`, `validateCodename` and `readPlanCodename`, with an `import.meta.main` front door. Frontmatter is read through the shared `frontmatter.ts` parser, never a private regex. Refusals use the NFR-10 helper the other front doors use. The template gains one line; `/spec-write`'s plan section gains one paragraph after the em-dash heading rule, reusing the existing title rule for the heading.

## Testing

`adapters/_shared/src/milestone_codename.test.ts` covers the validator (CHANGELOG-derived accept set plus the six rejects), the reader (value, absent, null, invalid) and the front door (spawned, stdout/stderr/exit). A prose test under `tests/` pins the template line and the spec-write paragraph, with a planted-line control.
