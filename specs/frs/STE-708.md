# Skills keep reading the tracker mode from CLAUDE.md, which the binding stub now carries

## Summary

Seven skills decide the tracker mode by reading CLAUDE.md themselves, following written steps.
After settings move, a migrated tree still carries the mode in CLAUDE.md, inside a generated block.
So the skills keep their written steps and make no extra call.
Code reads the mode through the settings loader instead.
A command that runs the loader exists for code, and becomes the skills' path in 4.0.

## Requirement

The Schema L probe in `docs/patterns.md` § Tracker Mode Probe is a prose procedure: read CLAUDE.md, `grep -c '^## Task Tracking$'`, and treat zero as `mode: none`. Seven skills run it by reference: `/setup`, `/spec-write`, `/implement`, `/gate-check`, `/pr`, `/spec-review` and `/spec-archive`. The model answers it from the CLAUDE.md that Claude Code auto-loads, with no tool call.

Operator ruling, 2026-11-04: through 3.x the skills keep that prose read, exactly as today, so they make zero extra calls. On a legacy tree it reads the real `## Task Tracking` section. On a settings-file tree in a tracker mode it reads the generated binding stub of STE-706, which carries the `## Task Tracking` heading, the `mode:` line and the adapter's binding keys. A settings-file tree in `mode: none` has no stub, and the absent heading still means `mode: none`. So the prose read answers correctly on every tree, provided the stub exists exactly when the mode is a tracker mode. Every settings writer keeps it in step (STE-710), the migration writes it (STE-711), and probe #25 grades it byte-equal to its render (STE-709).

Measured on 2026-11-04 over 405 recorded runs of six of the seven skills (`/setup` had none): the first 12 tool calls after entry never Read CLAUDE.md, and no Bash call ran the Schema L grep. A front-door call at entry would therefore have added one call per skill run, not replaced one. That is why the skills do not call it in 3.x.

The loader's front door from STE-706 stays, for code and for 4.0:

```
bun run "${CLAUDE_PLUGIN_ROOT}/adapters/_shared/src/project_settings.ts" mode "<projectRoot>"
```

It prints `mode: <value>` and `source: <settings|legacy|none>`. No SKILL.md runs it in 3.x. When 4.0 removes the stub, the skills move to it. On a legacy or `none` tree it reads only the `mode:` value of `## Task Tracking`, with the line parse of the v2.101.4 readers. It never parses the adapter sub-section or `specs/tracker-config.yaml`, and it does not strip HTML comments, so its answer equals the prose procedure's answer.

`skills/gate-check/SKILL.md` is frozen by AC-STE-618.8, and the operator pre-granted one `KICKOFF` re-base per milestone. This FR leaves that file byte-identical; its gate-check rows land in the single gate-check edit commit of STE-713.

`docs/patterns.md` § Tracker Mode Probe states that on a settings-file tree the heading the procedure reads is the generated stub, and names the front door as the code-side read and the 4.0 skill path. The key-table paragraph (line 428 at drafting) no longer recommends keeping workspace URLs or other metadata in a sub-section. The settings schema is closed, and the move of STE-711 refuses any line under `## Task Tracking` that is not a key line or structural. So the paragraph names the binding keys as the only sub-section content, and sends any other tracker metadata to a prose section outside `## Task Tracking`. Its "emitting additional top-level keys" sentence names the legacy home as legacy.

The remedy that probe #21 names sends metadata to the same refused place. `scripts/migrate-task-tracking-canonical.ts` moves non-canonical top-level `## Task Tracking` keys under a `### <Tracker>` sub-section, which the STE-711 move then refuses. This FR rewrites the helper so its diff moves those key lines, verbatim and each prefixed `- `, into a `## Tracker Notes` prose section inserted directly after the `## Task Tracking` span, appending to an existing `## Tracker Notes` without a second heading. It stays dry-run only and prints a unified diff. `tests/migrate_task_tracking_canonical.test.ts` asserts the same properties against the new destination. The probe #21 sentence in `skills/gate-check/SKILL.md` is rewritten in STE-713's single gate-check edit commit (review 4, R4-4).

The adapter docs read binding values in prose too: `adapters/linear.md`, `adapters/jira.md` and `adapters/_template.md` source `team`, `project`, `default_labels` and `jira_issue_type` from the `### Linear` / `### Jira` sub-section in CLAUDE.md. Those reads stay, since the stub carries every binding key. Each such line gains a clause that on a settings-file tree the sub-section is the generated stub, rendered from `task_tracking.<adapter>` in `specs/settings.yaml`, and is never edited by hand.

## Technical Design

The skills' prose read stays, because the binding stub keeps the heading it reads on every tracker-mode tree. The change here is documentation plus tests that pin the read and the call lists.

The front door already exists from the loader FR. It serves code now and the skills in 4.0.

The probe #21 helper moves stray keys to a prose section, so following its remedy never produces a tree the migration refuses.

## Testing

Per-skill pins of the probe step, stub-read rows, front-door spawns for the settings case and each refusal, a timing bound, and the call-list pins with a planted control.

## Notes

Origin: the consolidation-blast finding that a code-side fallback cannot reach a probe written as prose. Operator ruling 2026-11-04: zero extra calls in 3.x; the stub carries the prose read until 4.0. The gate-check rows wait for the docs FR's single edit commit.
