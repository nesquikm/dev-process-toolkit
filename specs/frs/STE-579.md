# The idempotency probe stops always-missing, stops mis-binding, and grades its stop

## Summary

Before creating a ticket the toolkit searches for one that already matches, so a retry cannot duplicate. On Jira that search asks for an exact summary match, which the query language accepts and then answers with nothing, every time. A duplicate lands on a board with no delete button. The search now narrows first and compares afterwards, stops rather than creates when the match belongs to another repo, and that stop becomes a graded outcome.

## Requirement

The create-idempotency probe must be capable of matching an existing ticket, must scope its search to a container and an owning repo, must never widen an uncertain result into a create, and must surface its stop through a registered capability key rather than an ungraded phrase.

## Technical Design

Measured live, read-only, against cloudId `96bffaef-cf5d-4dbf-a170-3d700df9bc83`:

```
project = GF AND summary = "The reward banner, repainted light"      -> {"issues": [], "isLast": true}
project = GF AND summary ~ "\"The reward banner, repainted light\""   -> GF-83, exactly one
project = GF AND summary ~ "\"reward banner\""                       -> GF-84, GF-83, GF-81 (~ narrows, never joins)
project = GF AND labels = "milestone-M46"                            -> totalCount 5   (control: labels = works)
Linear list_issues(query="Reward banner", team=STE)                  -> 9 issues, none carrying the string
```

GF-83 provably carries that exact summary, fetched by key. So `=` on a summary is accepted and answers zero: a silent always-miss, not a syntax error. Four sites order that comparison — `adapters/jira.md:291-294`, its retry table at `:296-319`, `adapters/linear.md:248-259`, and the executing copy at `skills/spec-write/SKILL.md:109`. The new shape narrows by container (`parent = <EpicKey>`, or `labels = "milestone-<M-token>"` for a grandfathered numeric milestone) and by `labels = "<repo_tag>"` when declared, then a client-side normalized compare decides. The registry in `adapters/_shared/src/closing_summary_capability_keys.ts` is bidirectional, so the key and its directive ship together.

## Testing

Isolation is half a test: each drift-trigger case must also fail on its siblings' fix, or the suite proves only that six cases pass. Assert the create call count is exactly zero on both the refusal and the success path. Pair every absence assertion with a presence one — an absence assertion is the easiest kind to satisfy by deleting the subject. Count the sites pinning the capability-key length as a bare literal before editing rather than discovering them mid-edit; one of them re-parses the literal out of a sibling test file. Re-run the module-reachability probe with `await` before and after.
