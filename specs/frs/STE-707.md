# Every settings read goes through the settings loader

## Summary

Many modules read their own setting straight from a CLAUDE.md heading today.
Each one keeps its own small parser, so they can disagree.
This change sends every one of those reads through the new settings loader.
A value now reads the same whether it lives in the settings file or in CLAUDE.md.
Messages that name a setting point at the place the value actually came from.

## Requirement

Every reader below keeps its exported signature and derives its value from `loadProjectSettings` (STE-706). A reader that takes a `claudeMdPath` resolves the project root as its directory. The private CLAUDE.md parse inside each reader is deleted; the parse logic lives only in the loader's legacy module.

A `file:line` citation or a remedy names `specs/settings.yaml` and the dotted key path when the value came from the settings file, and the CLAUDE.md heading when it came from the legacy home.

## Technical Design

Each reader becomes a thin view over the loader's typed result. The reader keeps its public signature, so its callers and its existing tests stay put.

The private parsers move into the loader's legacy module unchanged, which is what keeps the legacy fixtures green.

Citations carry a source tag from the loader, so a message can name the right file and line. The one-reader scan is the fuse: a new module that parses a heading on its own fails the suite.

## Testing

Per-reader twin rows, the defect case, the one-reader scan with its control, hook wrapper spawns on settings-file trees, and the pre-existing legacy suites unchanged.

## Notes

The probe modules that grade headings, rather than read a value, are handled by the managed-tree FR. The writers are handled by the setup FR.
