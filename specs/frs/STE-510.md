# A stage cannot report ok without machine-read evidence

## Summary

The hand-off block a stage reports back with has a gate section described as carrying pass and skip counts, and nothing anywhere checks that it does. A stage can report success in prose and be believed. The counts have to come from reading the captured output of the commands that ran, because a number the reporting agent typed is not evidence of anything.

## Requirement

The hand-off carries gate, drive and end-to-end evidence derived from captured output, and success cannot be claimed without it.

## Acceptance Criteria

- AC-STE-510.1: The `deliver-stage-result` fence gains `drive:` and `e2e:` sections in fixed order after `gate:`.
- AC-STE-510.2: The `gate:` section carries pass, fail AND skip counts plus the baseline delta.
- AC-STE-510.3: Every count in those sections is derived by code from captured command output; no count is authored by the reporting worker.
- AC-STE-510.4: A fence whose counts disagree with the captured output is a contract violation and takes the existing bounded-retry-then-halt path.
- AC-STE-510.5: `status: ok` is refused when a required count is absent, and when any count indicates failure.
- AC-STE-510.6: The fence line cap is raised to fit the new sections; they stay inside the fence rather than moving to a companion artifact, because a second artifact would split one source of truth in two.
- AC-STE-510.7: Guards are mutation-verified — a worker-authored count and an absent capture each go RED.

## Technical Design

The shipped fence specifies six sections and describes `gate:` as carrying "final gate numbers, pass AND skip counts". Nothing validates that. `deliver_stage_capture.ts` exists and the shape validator checks section presence, order and the line cap — but not whether the numbers inside correspond to anything that ran.

AC.3 is the whole FR and the rest are its consequences. The counts must come from `parseTestOutput` over captured stdout, joined to STE-509's baseline, and rendered by code into the fence. A worker that composes the fence from memory produces a block that is byte-valid and evidentially worthless. This is the highest-risk criterion in the milestone precisely because the wrong implementation passes every shape check.

AC.4 reuses the shipped bounded-retry-then-halt path rather than adding a second failure mode: one scoped re-prompt restating the contract, then a deterministic halt naming the stage. AC.5 makes `status: ok` a derived value rather than a worker assertion.

AC.6 records a decision. A companion artifact under `.dpt/scratch/` would keep the fence small, and it would also mean the orchestrator reads success from one place and evidence from another — the split-source-of-truth pattern M129 recorded three separate times in a single milestone, every instance producing a grader that failed healthy runs. Raising the cap keeps one block, one read, one truth.

AC.7's two mutations are named because they are the two that ship a green guard over nothing: a count the worker typed, and a capture that was never taken.

## Testing

Fence coverage for the new sections in fixed order, and for the raised cap. Round-trip coverage from real captured output through the parser to a rendered fence, asserting the numbers match the capture. AC.5 coverage: a fence missing a required count and a fence carrying a failing count are each refused. AC.4 coverage through the existing retry-then-halt path. AC.7's two mutations each run and each asserted RED — a worker-authored count that disagrees with the capture, and a fence rendered with no capture present. `bun test` full root.

## Notes

M129's own record is the warning: all eighteen shipped ACs of the FR that introduced this fence were greps of the skill's own prose, "which is precisely why a fence with no producer passed every one of them". This FR must not be verified the way that defect was introduced — the subject of every assertion here is a capture, not a document.

The two fail-open Tier-1 guards M129 shipped are the second warning. AC.7 exists because a guard that cannot fail is indistinguishable, in a green run, from a guard that works.
