# An Epic-keyed milestone binds by key, and the attach never mints

## Summary

An Epic-keyed milestone id is not a label someone chose. It is derived from the key the tracker allocated when the Epic was created, which means the id already carries the Epic's identity inside it. The reader knows this: it takes the ticket's parent, sanitizes that key, and asks whether the result equals the milestone token. The writer does not. The writer looks for an Epic whose summary matches a name, and the name it matches on embeds the very key it is trying to find.

That is not a comparison that can succeed. The Epic that gave the milestone its id was created before the id existed, so it carries whatever human title someone typed. The attach looks for the canonical name, does not find it, and creates a second Epic that does carry it — under a fresh key, which is precisely the key that will not match. Every bind mints another one, reports success, and leaves the ticket parented to an Epic the reader will never accept.

The fix removes the name from the join entirely. For an Epic-keyed token the Epic is found by key, the same identity the reader already uses, so writer and reader agree by construction rather than by matching strings. Once the name is not load-bearing, every drift trigger that mints a duplicate today stops mattering: an en-dash, a stray space, a copied anchor, an ordinary mid-milestone retitle. None of them can move a key.

A token whose Epic is absent is then a genuine error rather than an invitation to create one. Minting an Epic to satisfy a token derived from a different Epic guarantees a key that can never match, which is the defect wearing a recovery costume.

## Requirement

For an Epic-keyed milestone token, `attachProjectMilestone` resolves the milestone Epic by KEY — the identity the token already encodes and the reader already checks — never by summary equality, and never creates an Epic.

## Acceptance Criteria

- AC-STE-521.1: On the `epic` binding, when the milestone token parses to `kind: "epic"`, `attachProjectMilestone` selects the milestone Epic as the one whose key sanitizes to that token under `milestoneIdFromEpicKey`. Summary/name equality is not consulted on this path.
- AC-STE-521.2: The reported state is reproduced and asserted to bind correctly: a project holding Epic `GF-78` whose summary is the human title `Waiting States II`, a plan heading `## M_GF_78 — Waiting States II {#M_GF_78}`, and ticket `GF-79`. After the attach, the ticket's parent is `GF-78`. This criterion FAILS on the current implementation, which parents the ticket to a freshly minted second Epic.
- AC-STE-521.3: On AC.2's fixture the `createEpic` op is called exactly ZERO times, asserted as a call count on the provider double. A criterion that only checked the resulting parent would pass on an implementation that minted a stray Epic and then ignored it — and the stray Epic, consuming a real tracker key, is half the defect.
- AC-STE-521.4: On AC.2's fixture, `milestoneBindingPresent(freshIssue, canonicalName, "epic")` returns TRUE immediately after the attach returns, asserted in the same test as AC.2. Writer and reader are shown to converge on one state rather than each being checked against its own.
- AC-STE-521.5: The name-drift triggers are inert, asserted as SEPARATE cases: the plan heading's title differing from the Epic's summary by (i) an en-dash where the Epic has a hyphen, (ii) a double space, (iii) a trailing space, (iv) a non-breaking space, (v) a retained `{#anchor}`, and (vi) an ordinary title edit. Each binds to `GF-78` with `createEpic` called zero times. One combined case would pass on an implementation that handled a single trigger.
- AC-STE-521.6: When no Epic in the project sanitizes to the milestone token, the attach REFUSES in the NFR-10 canonical shape, naming the milestone token, the Epic key it looked for, and the project. It does not create an Epic.
- AC-STE-521.7: AC.6's refusal is asserted together with a `createEpic` call count of zero, so "never mints" is pinned on the failure path as well as the success path. A guard that refuses after minting has not fixed anything.
- AC-STE-521.8: The already-bound pre-check survives unchanged: when the ticket's parent already equals the resolved Epic's key, `setParent` is called zero times and the result is `{ capability: null, epicKey }`. Asserted, because the idempotency property is what keeps a re-run from rewriting a parent.
- AC-STE-521.9: The transient-retry contract survives: the find leg still re-runs inside the retry wrapper on a transient failure, and a `MilestoneAttachmentError` still short-circuits without retry. Asserted directly, because the retry's original justification was re-finding an Epic a timed-out create had already made — a justification this FR removes, and a removal that silently took the retry with it would be invisible.
- AC-STE-521.10: The `object` and `label` bindings are byte-unchanged by this FR, asserted by exercising both on their existing fixtures in the same run. The routing change must not leak past the epic branch.

## Technical Design

The change is one line of intent in `adapters/_shared/src/attach_project_milestone.ts`: inside the `epic` branch, replace `epics.find((e) => e.name === milestoneName)` with a key-sanitizing match against the milestone token, and delete the `createEpic` fallback in favour of a refusal.

The milestone token is recovered from the canonical name the same way `milestoneBindingPresent` recovers it — the leading whitespace-delimited token — and parsed through `parseMilestoneToken`. Only `kind: "epic"` takes this path; a numeric token under the same declared binding is STE-523's subject and must not be captured here. Matching is `milestoneIdFromEpicKey(epic.key) === token`, which is exactly the reader's expression with the parent key swapped for the candidate Epic's key. That symmetry is the point: the two surfaces cannot disagree about which Epic is the milestone's, because they compute the same function of the same field.

The lossiness of the sanitizer is what makes matching on the sanitized form correct rather than merely convenient. A raw key `GF-78` and a mirror `GF_78` both sanitize to `M_GF_78`, so de-sanitizing the token back into a key would be a guess. Sanitizing every candidate key forward and comparing is total and exact.

Removing the mint from the Epic-keyed leg does NOT leave `createEpic` without a call site in this module, and an earlier draft of this paragraph claimed it did. The grandfathered numeric branch still calls it, correctly: this FR's own scope boundary forbids capturing a numeric token, which is STE-523's subject. Only after STE-523 routes numeric tokens to the label surface does the last call site here disappear. That sequencing is load-bearing rather than cosmetic — STE-522 pins `createEpic` to exactly one production call site, and that pin is unsatisfiable until STE-523 has landed. The build order is therefore STE-521 → STE-523 → STE-522, not the FR-number order. The op never becomes dead: STE-522 gives it a real home at milestone-minting time, where the key does not yet exist and creation is the correct act.

The refusal carries the Epic key rather than only the token, because an operator reading it needs to know what to look for in the tracker. A token whose Epic is absent means either the Epic was deleted, or it lives in another project, or the plan file was hand-authored with a token nobody derived from a key — three different fixes, all of which start by looking up that key.

## Testing

The reproduction fixture is the one the triage used: an in-memory provider double exposing `listEpics`, `createEpic`, `setParent`, and `getIssue`, seeded so that the milestone Epic carries a human title and the canonical name is unmatchable by name. It is driven through the real shipped module, so a green result is a statement about production code and not about a mock.

Every criterion that asserts an absence asserts it as a COUNT on the double, never as an absence of an observable side effect. The distinction matters here more than usual: the duplicate Epic is invisible from the ticket's point of view — the ticket ends up parented to something, and the attach's own read-back agrees with itself.

The drift-trigger cases are enumerated rather than parameterized over a single assertion, so a partial implementation cannot ride one passing case. The frontmatter shape used in every fixture is the block form; the triage's first attempt used an inline `tracker: {jira: GF-79}` map, which the frontmatter parser ignores, and the resulting vacuous run read as a pass.
