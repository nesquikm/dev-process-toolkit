# Base-relative tests read the shipped grammar and imports

## Summary

Two tests compare the working tree against the main branch while they run.
They passed on the release branch and failed once that branch was merged.
One test still expects the old shape of the shipped version stamp on main.
The other copies a fixed list of files and misses a file the new code imports.
This fix teaches both tests the new shape and the full import list.
Then they pass both before and after a merge.

## Requirement

### Steps to reproduce

1. Check out main at 42dd416a, the merge of PR #119 (v2.100.0).
2. From `plugins/dev-process-toolkit`, run `bun test tests/m_79b1f6-ste-589-sibling-ship-gate.test.ts tests/m_685ff6-ste-608-numeric-door.test.ts`.

### Expected

Both files pass on merged main, as they did on the branch head 908db01f.

### Actual

Three tests fail. The STE-589 guard's non-vacuity check finds 0 stamp literals of the old `/^v\d` shape on main where it requires 1 in each of the three stamp files. Both STE-608 controls fail with "Cannot find module './active_plan_ship_ready'". The STE-590 nested run of the STE-589 file fails with them, so the full gate reads pass 19366, fail 4, skip 16.

- AC-STE-692.2: Regression: `tests/m_685ff6-ste-608-numeric-door.test.ts › (control) mode: jira — archive_fr.ts + plan_ship_stamp.ts are byte-identical to HEAD on M8; label and filename unchanged` and its `linear` twin fail before the fix and pass after it on merged main.
- AC-STE-692.3: The STE-589 guard's main-side count and live count both recognise a stamp literal in either shipped form: the `v<X.Y.Z>` form alone and the shared grammar that also admits `unreleased`. Its non-vacuity check still requires exactly one stamp literal in each of `plan_ship_coherence.ts`, `resume_classifier.ts` and `active_plan_ship_ready.ts` on main.
- AC-STE-692.4: The guard still reports a shared module that gains a second stamp-shaped literal over main, in either form. A control plants a second literal of each form and is reddened by it.
- AC-STE-692.5: `baseModules()` in the STE-608 suite reads its base from a named commit constant, the last pre-STE-608 commit the control was written against, never from `merge-base HEAD main`, which equals HEAD after a merge and turns the control into HEAD-versus-HEAD (the STE-672 precedent). It copies the requested modules plus every module they import by relative path, transitively, from that commit. No module outside that closure is copied, and the copied set is named in the test's own assertion message.
- AC-STE-692.6: A merged-tree simulation runs both checks against a fixture repository whose `main` already contains the branch's change, so the merge-base equals HEAD. Both pass there and in the branch shape, where main lacks the change.
- AC-STE-692.7: Removing the shared-grammar arm from the counter, or replacing the closure walk with the fixed three-file list, each reddens at least one test.
- AC-STE-692.8: `bun test` from `plugins/dev-process-toolkit` reports 0 failures on the branch, and its skip identities equal the trunk baseline by name.

## Technical Design

### Root cause

Both suites read `main` or `merge-base HEAD main` at run time. While M_7a948e sat on its branch, those resolved to the pre-release tree. After the merge they resolve to the release itself. STE-690 changed the three `STAMP_RE` definitions to the shared grammar, and it made `plan_ship_stamp.ts` import `active_plan_ship_ready.ts`. The STE-589 grep pattern and the STE-608 fixed file list each encoded the old tree.

The counter's pattern becomes one regex that matches both literal forms. The closure walk parses relative `import ... from "./x"` specifiers and follows them to a fixed point.

## Testing

Unit tests run the counter over both literal forms, with planted second literals as controls. The closure walk is tested over a small fixture module graph. The merged-tree simulation uses a temporary git repository with a branch and a merged main.
