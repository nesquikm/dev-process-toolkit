# An unreleased ship stamp counts as shipped

## Summary

When a milestone closes without a version, its plan still needs a mark that says it shipped.
The new mark is the word unreleased in the place where a version number normally goes.
Every check that reads that mark must accept it in projects that opted in.
In every other project the same mark is an error, so a typing slip cannot pass as a release.

## Requirement

Five readers grade a plan's `shipped_in:` stamp against the grammar `v<X.Y.Z>`: plan/ship coherence (probe #63, including its sibling leg), the resume classifier, active-plan ship-readiness, release-surface agreement and the live-proof gate. Under `changelog_unversioned: true` the release writes `shipped_in: unreleased`, which every one of them would read as corrupt or unshipped today. The sentinel joins the one stamp grammar (STE-589.8) and is accepted only in a project that declares the flag.

## Acceptance Criteria

- AC-STE-690.1: The stamp grammar shared by `plan_ship_coherence`, `resume_classifier` and `active_plan_ship_ready` admits exactly `v<X.Y.Z>` and the literal `unreleased`; the STE-589 pin over those definitions is updated so the three still agree, and no fourth stamp-shaped regex is added.
- AC-STE-690.2: `stampShippedIn(planPath, "unreleased")` writes `shipped_in: unreleased`, and any other non-`v<X.Y.Z>` value is still refused.
- AC-STE-690.3: In a project declaring `changelog_unversioned: true`, plan/ship coherence reports no violation for an archived plan stamped `unreleased` and does not look for a CHANGELOG heading for it; in a project without the flag the same plan reports `corrupt_stamp`, naming the stamp and the flag as the remedy.
- AC-STE-690.4: Coherence's sibling leg accepts a sibling plan stamped `unreleased` only when the sibling repository's own CLAUDE.md declares the flag.
- AC-STE-690.5: With the flag, `classifyResume` classifies a milestone whose plan is stamped `unreleased` as `shipped`, and its refusal names `shipped_in: unreleased`; without the flag the stamp is not read as shipped.
- AC-STE-690.6: With the flag, an archived plan stamped `unreleased` is neither ship debt for `active_plan_ship_ready` nor a candidate for `/ship-milestone`'s ship-debt offer.
- AC-STE-690.7: `release_surface_agreement.ts` exits 0 and reports the check as vacuous in a project declaring the flag, as it does for `changelog_ci_owned: true`.
- AC-STE-690.8: The live-proof gate treats `shipped_in: unreleased` as a release with no CHANGELOG heading to check under the flag, and as an unmatched stamp without it.
- AC-STE-690.9: Every stamp reader leaves a `v<X.Y.Z>` stamp graded exactly as before; the existing probe #63, resume and ship-readiness suites pass unmodified.
- AC-STE-690.10: Removing the flag condition from any one reader reddens at least one test.
- AC-STE-690.11: `bun test` from `plugins/dev-process-toolkit` reports 0 failures, and its skip identities equal the trunk baseline by name.

## Technical Design

Each reader already knows its project root; it reads the flag through `readDocsConfig` once per call. The sentinel is a constant exported from `plan_ship_stamp.ts` so readers compare one value. `shipStampVersion` keeps returning a version or null, so callers that need a number never receive the sentinel.

## Testing

Each reader gets a flag-on and a flag-off fixture with an `unreleased` stamp, plus the unchanged versioned case.

## Notes

Operator choice 2026-10-21: approach 1, one shared grammar, flag-gated in every reader.
