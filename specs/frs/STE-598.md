# A fix with no feature request can still prove its tests were red

## Summary

The same guard demands proof that one specific orchestrator ran, and that orchestrator only works when a feature request is in play. A fix that came from an audit has no feature request, so there is no honest way to produce the proof, and the only workaround is the very thing the guard exists to stop. Give that work a second, legitimate door.

## Requirement

The pre-commit TDD guard grades any commit staging a test file as requiring evidence, and the only evidence it accepts is a tool use of the per-FR orchestrator. M71 fixed that evidence formally as one orchestrator entry per feature request in milestone scope. An audit-driven fix has no such count, so the requirement is unsatisfiable rather than merely strict, and invoking the orchestrator with no feature request purely to plant the token is precisely the workaround the guard exists to prevent.

Measured on 2026-09-16: a green gate and a correct, audit-driven change was refused twice. The evidence the guard wanted existed — several test legs were red on the old bytes — but the mechanism had no way to see it. The committer stopped rather than working around it, which was right, and the absence was recorded rather than papered over.

Add a second accepted proof for exactly that shape of work, without weakening what the guard already catches.

## Acceptance Criteria

- AC-STE-598.1: The requirement is satisfied by either the existing orchestrator evidence or a recorded red-before proof. With neither present the commit is refused exactly as it is today, and the existing trigger is unchanged.
- AC-STE-598.2: The proof names the staged test paths it covers. A proof naming none of the staged paths that raised the requirement does not satisfy it.
- AC-STE-598.3: The proof is found through the same transcript reader the existing evidence uses. No second discovery mechanism ships, and the guard family stays on one mechanism.
- AC-STE-598.4: The refusal message names both satisfying paths, so an operator who hits it learns the second door exists rather than rediscovering it.
- AC-STE-598.5: The rejected alternative — a content-keyed artifact keyed to staged blob hashes — is recorded in this FR with the threat-model reasoning that rejected it.

## Technical Design

Keep the existing trigger and the existing reader. Add one accepted alternative: a canonical marker in the committing session's transcript recording that the covered tests were run and were red on the pre-change bytes, naming those paths. The guard is satisfied when either that marker or the orchestrator entry is present, and refuses naming both when neither is. Nothing subtracts from the required set, so the STE-360 precedent — subtract only via a dual key, never waive for the rest — is untouched.

## Testing

Assert the disjunction in all four combinations: orchestrator only, proof only, both, neither. Assert the path-scoping clause with a proof that names an unrelated test file, which must not satisfy the guard — that is the clause a permissive implementation would quietly drop. Assert the refusal text names both doors. Every clause must also fail on its sibling.

## Rejected Alternatives

- **A content-keyed artifact keyed to staged blob hashes.** The proof would be a
  file written by the test run, naming each covered path together with the git
  blob hash of the bytes that were red, and the guard would recompute those
  hashes over the staged index and demand a match. Rejected.
- **Why.** The threat model here is self-discipline, not an adversary: the owner
  of the guard is the person it guards. Binding the proof to a staged blob hash
  buys tamper-resistance against someone who is not in the picture, and charges
  for it in a new artifact lifecycle — where it is written, when it is
  invalidated, what a stale one means, how a rebase or an amend re-keys it —
  every part of which is a thing to get wrong in the direction of a false green.
  A transcript marker has no lifecycle of its own: the session either recorded
  the claim or it did not.
- **What is given up, stated plainly.** Nothing stops an operator from typing the
  marker without having run anything. That is the same trust the existing door
  already extends to whoever invokes the orchestrator, and the FR does not
  pretend otherwise. Nor does anything detect an honestly-recorded marker that
  has gone stale — tests run red, then further edits staged on top — which the
  blob-hash key would have caught without any adversary in the picture. That
  detection is the concrete capability traded away. The mitigation is
  visibility, not cryptography — the marker is in the transcript, named, and the
  Notes below ask whether the second door becomes habit.

## Notes

- Threat model: this guards self-discipline, not an adversary. The owner is the person guarded.
- The content-keyed artifact was rejected on that basis, and it buys a new lifecycle to get wrong.
- Watch whether the second door becomes habit rather than exception.
