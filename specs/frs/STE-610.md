# Joining a milestone declares the span in both plans, and a one-sided span is held

## Summary

When a second repository joins a milestone another repository created, nothing records that the milestone now spans both, so every cross-repository release guard stays switched off.
Joining now writes the span into both plans, naming each repository by its tag and by a relative path that has been verified.
A plan whose sibling does not name it back is held before release.
So is a milestone whose shared container holds another repository's work that the plan never declared.

## Requirement

Measured at HEAD ac1f3cb (findings SF-4, RS-4, and the skeptics' template finding):

- `spans_repos` is only ever hand-written. `/spec-write`, `/brainstorm` and `/setup` never mention it, including `/spec-write`'s shared-project join branch. The plan template keeps it in a comment marked never scaffolded. So the default state of a joined milestone is undeclared on both sides, and every sibling surface (refusal #4, probes #63 and #75, the resume waits, `/pr` footers) behaves as if the milestone lived in one repository.
- With a one-sided declaration, the undeclared repository ships while the other is busy, and its `--partial` refuses with "no second half". The mismatch surfaces only in the declaring repository's post-ship probe #63.
- The template's literal example (`glacy-app-fe: .`, `glacy-app-be: ../glacy-app-be`) resolves both entries to self when pasted into the sibling's plan. The gate then passes with an empty footer while the other side is busy, and the first verification fixture fell into exactly that trap.

Required behaviour:

1. One executed writer declares the span in both plans. Each entry is named by the repository's `repo_tag`, read through STE-602, so a name is never typed. Each path is relative and computed from the repositories' main worktree roots (the root STE-609 resolves against). The sibling is verified before anything is written.
2. The join decision of STE-608 names the sibling in a shared container, so a join cannot be approved without saying who owns the other half.
3. Pre-ship, a located sibling whose plan does not name this repository back is a held state, `one-sided`. Until now this was a post-ship finding only.
4. Pre-ship, in a repository whose binding is shared, the release reads the container's child tickets. Work that carries neither this repository's tag nor a declared sibling's tag holds the release.
5. The template example can no longer resolve to self when pasted.

Old clients never write the span and never read children. A sibling on an older client therefore leaves its own side undeclared, which this repository reads as `one-sided` and holds; the older client's own release is unguarded until it reaches the floor.

## Acceptance Criteria

- AC-STE-610.1: `declareSpan({ invokingRepo, planFile, milestone, siblingPath })` is exported from `adapters/_shared/src/spans_repos.ts`, with the front door `bun run adapters/_shared/src/spans_repos.ts <planFile> <milestone> --declare <siblingPath>`. Before writing, it verifies each of the following and refuses in NFR-10 shape naming the failed check, writing nothing in either repository: the sibling is a git repository and not `sameRepository` with the invoking one; it is toolkit-managed; both CLAUDE.md files bind the same tracker mode and project; both declare a `repo_tag`, and the two differ; the sibling holds a plan for the milestone, live or archived, read through the git-state reader of STE-609 (any worktree, local branch or remote-tracking ref). The dry run of AC.4 stops there; the write additionally requires that plan in the sibling's main worktree and otherwise refuses naming the ref that holds it, since the back-reference cannot be written into a branch that is not checked out. An unreadable plan file, a missing sibling path, a malformed existing `spans_repos` in either plan, or a CLAUDE.md declaration that STE-602 refuses on either side, refuses with that reader's own text.
- AC-STE-610.2: On success both plans gain `spans_repos:` with exactly two entries. The invoking plan gets its own `repo_tag` mapped to `.` and the sibling's `repo_tag` mapped to the path from its main worktree root to the sibling's main worktree root. The sibling's plan gets the mirror image. Round trip: `resolveSpansRepos` run from each root, from its primary checkout and from a sibling-directory worktree, resolves self to that repository and the other entry to the other repository. Only the frontmatter lines added differ: a byte diff of each plan against its pre-write copy shows exactly the inserted `spans_repos:` block.
- AC-STE-610.3: Idempotence and conflict. When both plans already carry the same two entries, zero bytes are written in either repository (modification times unchanged). A plan that maps either tag to a different path refuses and names both paths, rather than overwriting. Under `mode: none`, or without a `repo_tag`, the writer refuses and says to hand-write the declaration; it never invents a name.
- AC-STE-610.4: The join names its sibling. In a repository whose binding is shared, the STE-608 front door decides a join only when `--sibling <path>` is given. It runs AC.1's checks as a dry run, writes nothing, and puts the sibling's tag and path into the `gate=` sentence. A join decided without `--sibling` exits 1: the refusal names the key it would have joined and the two ways forward, `--sibling <path>` or a distinct title. `skills/spec-write/SKILL.md` line 177 orders the `--declare` step right after the plan file is written. The edit stays within STE-608's line-177 budgets (358 split-lines, no module path to a module without a front door, zero new STE tokens). In an unshared repository the decision is byte-identical to STE-608 without this clause.
- AC-STE-610.5: One-sided is held before release. Refusal #4 adds the state `one-sided` to the set STE-609 defines: a located sibling whose plan for the milestone, read through that FR's git-state reader, does not resolve an entry to this repository (by `sameRepository`); a sibling plan with no `spans_repos:` at all is `one-sided` too. Refusal #4 refuses on it without `--partial`, probe #75 renders it as `awaiting-sibling milestones: <token> (<sibling>: one-sided)`, and both resume scopes treat it as awaiting. Red on HEAD, which ships with exit 0 and flags the mismatch only after the release. Control: a sibling that names this repository back and is otherwise idle passes.
- AC-STE-610.6: The undeclared side is graded. In a repository whose binding is shared, the refusal #4 front door run for a release requires `--children <listingFile>`: for Jira, the milestone Epic's child issues as the tracker returns them; for Linear, the project's issues, which the front door filters to the milestone by identifier because the tracker offers no milestone filter. A missing, unreadable, malformed or not-last-page listing refuses. So does a listing that omits any of this repository's own FR tickets bound to the milestone (the tracker keys of its active and archived FR files): those tickets are children by construction, so their absence proves the listing was filtered or stubbed. Because a release needs at least one archived FR, an empty child list can never pass a release; `children=0` is printed and refused as incomplete. Each child carrying neither this repository's tag nor the tag of a declared `spans_repos` entry refuses the release without `--partial`, naming those child keys and their labels. A complete listing whose every child carries an accounted tag passes and prints `children=<n>` (permit leg). The offer surfaces that run the same front door (the release candidate list in `skills/ship-milestone/SKILL.md`, `/pr` step 3, the `/spec-archive` exit hint and the implement milestone-close prompt) pass `--offer` instead: every other state is still graded, and one stderr line `children=not checked (offer)` says what was skipped. Without either flag, a shared repository refuses and names both. In a repository without `repo_tag`, neither flag is required or read, and refusal #4 is byte-identical to STE-609. The case of FE undeclared while BE's tagged child sits under FE's Epic is red on HEAD.
- AC-STE-610.7: The template cannot resolve to self. The `spans_repos` comment in `templates/spec-templates/plan.md.template` uses the placeholders `<this-repo-tag>: .` and `<sibling-repo-tag>: ../<sibling-directory>` and names the `--declare` command as the way to write the key. Pasting the example verbatim into both roots of a fixture is refused by refusal #4 from both roots, as unlocatable. Pasting the HEAD example verbatim into the sibling is refused by STE-609's one-self rule, and on HEAD it passes (red on HEAD). The template-literal pin at `tests/m_79b1f6-ste-591-sibling-by-tracker-id.test.ts:571` is amended to the placeholder form in the same commit. `tests/m_8f07e0-ste-583-spans-repos.test.ts` (the key stays documented, never scaffolded, and the gate skill still numbers 85 probes), `tests/plan-template-shape.test.ts` and `tests/template-tracker-id-convention.test.ts` stay green unedited.

## Technical Design

The writer sits beside the reader in `spans_repos.ts` and reuses its parser. The frontmatter edit inserts one block and never rewrites a line. Entry names come from `readWorkspaceBinding`, so the names match the tags the tracker carries, and that is what lets the child-ticket check attribute foreign work to a declared sibling. The `one-sided` state reuses the post-ship names-back resolution, moved before the release. The children listing is MCP output passed in by the session, the same pattern as the other decision front doors.

Declare from the primary checkout and from a worktree; assert both plans with byte diffs and the round trip. Cover each refusing check, idempotence and the path conflict. Drive refusal #4 over one-sided and undeclared-with-foreign-children fixtures, plus a children listing that is missing, malformed and not the last page. Paste both template versions.

## Notes

- Writing the back-reference edits the sibling's working tree and leaves it uncommitted there. The output names the file to commit in that repository.
- Children filed by hand without a tag hold a shared release until someone tags them, which is deliberate.
