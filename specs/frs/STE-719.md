# A retrospective command grades a run's trace against fixed rules

## Summary

A new retrospective command reads what a finished run left behind and reports where it was slow or wasteful.
Each rule names its data, a fixed number and one of three outcomes.
A rule whose data the session cannot see says so instead of reporting a clean result.
It writes one ignored report file, and changes a setting only on explicit approval.
Running it by hand always works; a project setting only decides whether close-out offers it.

## Requirement

### Audience and switch

Consumer-facing: the skill ships in the plugin. `specs/settings.yaml` gains a top-level `retro:` section with the closed key set `{enabled}`, read through `loadProjectSection(projectRoot, "retro")` from `project_settings.ts` (M_94e6f7). `docs/settings-reference.md` documents `retro.enabled` (type boolean, default false, no legacy home) as the switch for the close-out offer only. An absent section or `enabled: false` is off. An unknown key under `retro:` throws `SettingsShapeError` naming the dotted key path, as every M_94e6f7 closed set does.

Loader wiring, in the v3.0.0 `close_out.upgrade_offer` shape. `TOP_KEYS` gains `retro` (after `close_out`), and `settingsKeyOrder("retro")` returns `["enabled"]`. `ProjectSettings` and `defaults()` gain `retro: { enabled: false }`, which the legacy load returns as its default, since no legacy home carries the key. The section validator requires a map, closes it with `settingsKeyOrder("retro")` and requires a boolean `enabled`. `NEW_KEYS` gains `"retro"`, the block whose `enabled` is the switch, so the AC-STE-706.12 "every new key is off when absent" row reads `settings.retro.enabled` rather than a bare boolean. The test's `MAPPING` gains `retro: { kind: "new", fr: "STE-719", note: "no legacy home" }` and `LEAF_BLOCKS` gains `retro`. The archived AC-STE-706.12 prose names this key as `retro.enabled`; that is the key inside this block. A `retroSwitchOn(projectRoot)` export, in the `upgradeOfferSwitchOn` shape, is the one reader: true only for an explicit `true`, and any loader refusal reads off. The per-section rule of v3.0.0 holds: a malformed `retro:` section breaks only the offer's switch read, never another section's readers, and `/retro` itself never reads it.

Off by default means offers only (operator ruling R4, 2026-11-04). `retro.enabled` decides only whether the STE-722 close-out offer runs. Invoking `/retro` by hand always runs, whatever `retro.enabled` says, and grades whatever data exists. A rule whose input is missing reports `skipped: input not observable`. No path of `/retro` refuses on `retro.enabled`, and it writes its one report file either way.

### Hard invariant

`/retro` never changes a gate, a threshold, a receipt, a ledger row, a tracked file or a tracker. The one exception is the settings change of STE-728, which the skill applies only on an explicit operator approval; `retro.ts` itself never writes a setting. The front door writes exactly one file, `.dpt/ledger/retro/<scope-slug>-<UTC yyyymmddThhmmssZ>.json`, which the existing `ledger/` rule in `.dpt/.gitignore` already ignores. Thresholds are constants in code, never settings knobs.

### Surfaces

- `skills/retro/SKILL.md`: user-invocable, `argument-hint: '[<milestone> | <fr-id>]'`, within the NFR-1 cap. Overflow lives in `docs/retro-reference.md`.
- `adapters/_shared/src/retro_rules.ts` (new): exports `RETRO_RULES`, `PARENT_VISIBLE_SOURCES`, `RETRO_DISPOSITIONS` and `evaluateRetroRules(inputs)`.
- `adapters/_shared/src/retro_report.ts` (new): exports `buildRetroReport(...)` and `parseRetroReport(text)` (schema validator).
- `adapters/_shared/src/session_aliases.ts` (new): exports `createAliasMap()`, `aliasFor(map, sessionId)`, `sessionDigest(sessionId)` and `seedAliasMap(map, sessions)`. It is the one session aliaser: this report and the STE-720 payload pass both number sessions through it.
- `adapters/_shared/src/retro_scope.ts` (new): exports `resolveRetroScope(projectRoot, arg)`, the one scope resolver `/retro` and STE-722 share.
- `adapters/_shared/src/retro.ts`: front door `bun run retro.ts <projectRoot> [scope]` with the `if (import.meta.main)` guard probe #81 requires.

### Scope

- No argument: the current session, located with `findCurrentSession(cwd)`.
- An FR id or milestone, classified with `classifyDeliverArgument(...)` from `deliver_argument.ts` (`fr_identity` or `milestone_identity`): the sessions whose token-ledger rows (`readLedgerRows`, `token_usage.ts`) are `claimed_by` that FR, or by any FR whose frontmatter `milestone` names the milestone (specs/frs and specs/frs/archive). FR and milestone scopes need the token ledger, so with `tracking.token_stats` off they resolve to no session and the reason says `tracking.token_stats off`.
- A `feature_request` classification (free text) is refused in the NFR-10 shape.
- A scope that resolves to no session evaluates every rule as `skipped: input not observable` with reason `scope resolves to no session`.

### Data sources

Closed set `PARENT_VISIBLE_SOURCES`, each read from a session's own files:

- `timeline`: the M_7bc805 `tool-call-timeline/v1` file at `toolCallTimelinePath(root, sessionId)`, which already joins the transcript, the capture rows and the gate receipts. Its `gate_runs[]` and `rounds[]` are the only gate and round data a v1 rule reads.
- `capture_ledger`: the M_7bc805 `tool-call/v1` rows at `toolCallLedgerPath(root, sessionId)`, read for the `diff` of `commit` rows only. Rows with `scope: "fork"` are ignored.
- `token_ledger`: `.dpt/ledger/token-ledger.jsonl` through `readLedgerRows`.

Every v1 rule reads only these. A fork-internal rule needs its own FR, whatever the M_7bc805 spike found. No v1 rule times a `gate-check`, `tdd` or `spec-review` Skill call, because M_7bc805 records that an inline skill's call returns when its body loads; gate wall time comes only from `gate_runs[].wall_ms`.

### Rule shape and dispositions

Each rule declares `id`, `source` (one or more of the closed set), `threshold` (`value`, `unit`, comparator), and an evaluator returning `{ observable, value }`. The engine maps it to exactly one disposition: `tripped`, `clear`, or `skipped: input not observable` with a reason naming the missing input. A rule never reports `clear` from absent data.

### v1 rules

| id | source | measure | threshold | trips when |
|---|---|---|---|---|
| `slow_gate_run` | timeline | `wall_ms` of a `gate_runs[]` entry whose `outcome` is `pass` or `fail` | by `subject` (`gateSubject(...)`): gate-check 900000 ms, spec-review 1200000 ms, tdd 3600000 ms | any one run's `wall_ms` > its subject's bound |
| `gate_rerun_unchanged_key` | timeline | over `gate_runs[]` with `outcome: "pass"` and `key_stable: true`, grouped by (`subject`, `key_digest`) across the scope's sessions: the sum of (group size − 1) | 1 | the sum ≥ 1 |
| `zero_yield_round` | timeline | `rounds[]` of `dev-process-toolkit:tdd-implement` or `dev-process-toolkit:tdd-refactor` with `tree_changed: false` | 2 | the count ≥ 2 |
| `cost_per_changed_line` | token_ledger, capture_ledger | `output_tokens` summed over the scope sessions' token-ledger rows, divided by `insertions + deletions` summed over their `commit` rows' `diff` | 500 tokens per line | the ratio > 500 |

Skip conditions, each with its own reason: every timeline rule skips when no scope session has a timeline file, and the reason names `tracking.tool_calls off` when that key is off, since M_7bc805 writes no timeline then. `slow_gate_run` skips when no gate run has a non-null `wall_ms`. `gate_rerun_unchanged_key` skips when no gate run has a non-null `key_digest`. Each of those two reasons names `tracking.gate_outcomes off` when that key is off, since M_7bc805 then writes no outcome or key. `zero_yield_round` skips when the scope has no such round, or every such round carries `tree_disposition: "not-observable"` (the M_7bc805 D5-no branch). `cost_per_changed_line` skips when `tracking.token_stats` is off, no token row exists, no `commit` row carries a `diff`, or the line sum is 0. Its report line always labels the numerator `parent-visible tokens`, because the token ledger reads only the main transcript.

### Report schema v1

`{ schema: "dpt-retro/1", plugin_version, generated_at, scope: { kind, id }, sessions: [{ alias: "s1", digest }, ...], rules: [{ id, source, threshold, unit, value, disposition, reason }], tripped_count, suggested_severity }`. Session ids are stored only as aliases `s1`, `s2`, ... in first-appearance order, each from `aliasFor`. Each alias carries `digest`, the first 16 hex of the sha256 of the raw id, from `sessionDigest`. The digest lets the payload pass seed its map, so one session keeps one alias in every report file. The report holds no absolute path, raw command, cwd or branch name. `suggested_severity` is `low` for one tripped rule and `medium` for two or more; it is never `high`.

## Technical Design

The engine is pure: inputs are parsed rows, outputs are dispositions. The front door loads settings, resolves scope, reads the three sources through `readLedgerRows` and the M_7bc805 path composers, calls the engine, aliases sessions through the shared aliaser, and writes the report. It never reads `retro.enabled`. Thresholds live beside the rules as constants, so changing one is a reviewed code change with a moved fixture. The skill is thin: it runs the front door, prints the rule table, and closes with the status block.

## Testing

Fixture triples per rule, boundary pairs for each comparator, front-door subprocess runs for each setting value and the single write, scope cases, a privacy scan of fixtures, and count pins.
