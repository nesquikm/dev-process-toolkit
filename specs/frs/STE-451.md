# Add fixture group 10 — mode:none lock lifecycle

## Summary

Under tracker-less mode there is no ticket to move, so the proof that work was claimed and released is a lock file written when the work starts and deleted when it is archived. That deletion is the tracker-less analogue of a ticket reaching Done.

The end-of-run check can only observe the end state, and the end state of a correct run is that the lock is gone. An assertion that a file is absent at the end is satisfied just as well by a lock that was never created at all. So absence alone cannot tell a working release path apart from a claim step that silently did nothing.

That is the same vacuous-pass shape this milestone keeps finding, and it is the exact equivalent of asserting a ticket is Done without ever checking it left the backlog. Closing it requires observing the lock while the run is still in flight.

Mid-run observation is what a runtime fixture group is for and what the end-of-run verification structurally cannot do. That is what makes this group load-bearing rather than additional coverage.

## Requirement

Add fixture group 10 to the canonical roster, scoped to the `none` leg only, observing mid-run that the lock file EXISTS after the implement skill's claim step.

The group must ship with a named input that turns it red, and that input must be executed rather than described.

## Acceptance Criteria

- AC-STE-451.1: Fixture group 10 exists in `CANONICAL_FIXTURE_GROUPS` with `legs: ["none"]`, as a group separate from group 9, and a corresponding `#### Fixture group 10` block exists in the smoke-test skill's runtime-check phase. {#AC-STE-451.1}
- AC-STE-451.2: The group observes, mid-run and after the implement skill's claim step, that `.dpt/locks/<id>` EXISTS for the FR under construction. {#AC-STE-451.2}
- AC-STE-451.3: Suppressing the claim-time lock write turns fixture group 10 RED. The suppression is executed as part of this FR's verification and its red result is recorded in the implementation notes. If no such input can be constructed, the group is not a test and does not ship. {#AC-STE-451.3}
- AC-STE-451.4: Fixture groups 9 and 10 produce independent outcomes — either failing does not mask, skip, or short-circuit the other. {#AC-STE-451.4}

## Technical Design

The observation has to happen between the claim and the archive, which means the fixture reads the test project's lock directory while the chain is still running rather than after it completes. The natural attachment point is the same phase that already inspects grandchild captures mid-chain.

The identity in the lock filename is the full minted identity, not the shortened tail used for the FR filename, so the assertion must resolve the identity from the FR's recorded identity rather than from its filename stem.

AC.3 is the acceptance bar this FR is really written around. The suppression input is concrete: run the claim path with the lock write disabled and confirm the group reports red. A group that stays green under that input is observing something other than what it claims to observe.

## Testing

The group's falsifiability check is AC.3 and is not optional.

AC.4 is checkable from the reconciliation model directly — the per-group record already resolves each group independently against the roster, so the assertion is that neither new group's outcome is derived from the other's.

Full gate green from the plugin root.

### The headline result — this FR's own Technical Design named an attachment point that cannot work

`## Technical Design` says the fixture "reads the test project's lock directory while the chain is still running" and that "the natural attachment point is the same phase that already inspects grandchild captures mid-chain" — Phase 2.X. **By the time Phase 2.X runs, the lock is gone on a correct run**, so a sub-fixture that listed `.dpt/locks/` there would be RED on every healthy leg. Measured from the artifacts, not inferred:

- `docs/implement-reference.md` § Phase 4 Close (b): *"`mode: none`: deletes `.dpt/locks/<id>` (runbook does not apply)"* and *"**No exit path through Phase 4 skips this step.**"* Step (c) adds that *"the deterministic `.dpt/locks/<id>` deletion in step (b) is the proof-of-release for `mode: none`"*.
- So the claim at § 0.c and the release at Phase 4 Close both happen **inside Phase 2 step 3**. Phase 2.X fires after step 6.
- **And there is no archive commit at all.** The smoke chain uses the single-FR form, which `skills/implement/SKILL.md` § Milestone Archival says *"intentionally leave[s] `status: active`"*. The absence row's own wording — "after the archive commit" — describes an event that never occurs on this leg. The row still passes, for a different reason than it states.

**Consequence, and it is the whole shape of the group.** The observation window is *inside a single grandchild's lifetime*, which is why the group splits:

- **10a** samples during step 3's bounded poll — the literal in-flight read AC.2 asks for. Prose at runtime, like every fixture group in this phase.
- **10b** reads the **claim commit**. `claimLock` does not merely write the lock, it `git add`s and commits it, so the mid-run state is **durable** and readable after the release deleted the file. This is the race-proof half: a sampler that never happened to fire inside the window reports the same empty log as a claim that never wrote anything, and those are opposite findings.
- **10c** pins the identity resolution — the lock is keyed on the whole 29-character minted id, the FR's filename on six of it.
