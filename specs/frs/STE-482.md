# Allow-list: make the /setup merge loud, and grant compound git-commit forms

## Summary

Setup adds entries to the permission allow-list beyond what the caller wrote — behaviour that is intended, documented, and now confirmed three separate times. What is missing is any signal that it happened, so the list a reviewer reads in a pull request is the opening posture rather than the effective policy. Separately, commit commands written as a chain or with an inline document body are refused even though the plain form is permitted, forcing every run to find another route.

## Requirement

The merge stays — it is correct and load-bearing, and reverting it would break the toolkit's own skills. `/setup` reports how many entries it added beyond the caller's list, as a capability row, so the effective policy is visible at review time. Independently, the shipped permission templates grant the chained and heredoc commit invocation forms the prefix rule already intends to cover.

## Acceptance Criteria

- AC-STE-482.1: `/setup` emits a capability row naming the count of allow-list entries it added beyond a caller-supplied list; the row is a literal registered token with rendered prose in the closing-summary static map.
- AC-STE-482.2: The merge behaviour itself is byte-unchanged — a caller-supplied list is still merged rather than replaced, and the resulting entry set is identical to today's.
- AC-STE-482.3: When the caller supplied no list, the row reports the scaffolded count rather than being silently skipped — the quiet half is reported too.
- AC-STE-482.4: `templates/permissions.json` grants the chained (`&&`) and heredoc commit invocation forms; a fixture exercising both records zero permission denials.
- AC-STE-482.5: Notes record that the merge is intended behaviour with three independent confirmations, so it stops being re-filed as a defect on every run.

## Technical Design

F13 measured: the driver heredoc wrote 22 `permissions.allow` entries; the post-`/setup` committed `.claude/settings.json` carried 43. Third confirmation after 2026-07-20 and 2026-07-27, and the two legs disposed of it oppositely — linear filed it as a finding, jira filed the identical measurement under *What worked*. The operator decision is to keep the behaviour and make it loud: the row addresses the real complaint (a reviewable single-file diff bounds the opening posture, not the effective policy) without reverting something three runs confirmed as intended.

F5 measured: one denial in `/setup` on linear (`git commit -F - <<'EOF' … && echo … && git log …`), one in `/setup` and one in `/spec-write` on jira. The tracked allow-list grants `Bash(git:*)` and the prefix rule is correct; the auto-mode classifier does not credit it for heredoc or `&&`-chained forms. Every child recovered by another route, so no chain impact — recorded so a future run that does not recover has a precedent. Neither denial is `claude`-headed, so `checkChildSpawnCapture` stays clean and STE-350 is unaffected.

## Testing

Unit test on the added-entry count including the caller-supplied-nothing path. Permission fixture exercising both commit invocation forms and asserting zero denials. Round-trip test that the merged entry set is byte-identical to today's. `bun test` full root.
