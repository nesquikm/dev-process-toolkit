# Reviews record their finding counts

## Summary

Spec reviews, the TDD audit and the code review end with a result block, but no ledger keeps their counts.
So a later trend cannot tell whether quality dropped.
With a new opt-in switch on, each review writes one small receipt that holds only its counts.
The receipt never holds a finding's text, a path or a branch name.
With the switch off, every skill makes exactly the calls it makes today.

## Requirement

With `tracking.review_findings` on, every spec review, TDD audit and code-review pass records one receipt of its finding counts; with it off, nothing changes.

## Acceptance Criteria

- AC-STE-774.1: `specs/settings.yaml` accepts `tracking.review_findings: { enabled: boolean }`, default off. Any other shape throws `SettingsShapeError` naming the dotted path. The key joins the closed key order, `NEW_KEYS` and `docs/settings-reference.md`.
- AC-STE-774.2: `review_findings_receipt.ts record <root> <reviewer> <result-file>` takes `reviewer` in {`spec-review`, `tdd-audit`, `code-review`} and writes one `review-findings` receipt holding the session id, the HEAD commit, the FR ids and the counts. The spec reviewers record `done`, `partial` and `missing` per FR from their `spec-review-result` or `tdd-spec-review-result` block. The code review records the `N` of `OVERALL: CONCERNS (N)` per pass, and 0 only for an `OVERALL: OK` line.
- AC-STE-774.3: A result block that does not parse writes no receipt and prints one NFR-10 refusal line. It never records a zero.
- AC-STE-774.4: `/spec-review`, the `/tdd` audit stage and `/implement` Phase 3 run the record call only when their existing receipt call printed `review_findings: on`. With the switch off, their tool calls are exactly those of v3.5.0.
- AC-STE-774.5: No commit, pull-request or tracker gate reads a `review-findings` receipt.
- AC-STE-774.6: Removing the parse, the switch check or the refusal turns at least one named test red.
- AC-STE-774.7: `bun test` from `plugins/dev-process-toolkit` reports 0 failures, and its skip identities equal the trunk baseline by name.

## Technical Design

A new `tracking` leaf read through `loadProjectSection`, like `gate_outcomes`. The receipt writer reuses the shipped receipt store under `.dpt/ledger/receipts/<session>/` and the existing block parsers for the two spec-review result shapes; the code-review count comes from the one `OVERALL:` line. The switch line rides the existing gate receipt call's trailing switch lines, so a skill learns the switch without an extra call.

## Testing

Temporary project roots with a settings file, captured result blocks as fixtures (valid, malformed, OK and CONCERNS shapes), and the front door run as a subprocess; a tool-call parity test with the switch off; mutation controls for each rule.

## Notes

Milestone A of the self-tuning settings design. The trend in the third FR of this milestone is the first reader.
