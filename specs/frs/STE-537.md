# /setup mints the mode:none bootstrap scaffold identity

## Summary

A tracker-less project bootstrapped with no arguments gets a plan named with a sequential number — the one shape that mode does not use.

Nothing reds on it. The bootstrap plan is exempt from the probe that would object, so the mismatch simply waits for the author's first spec.

Setup mints the identity when it writes the plan, so the name is right from the start. Both tracker modes are untouched.

## Requirement

When the resolved tracking mode is the tracker-less one, `/setup` step 8 mints a milestone identity and writes the bootstrap plan under that identity, recording the minted value in the plan's own frontmatter. Under either tracker mode the scaffold is byte-identical to what ships today.

## Acceptance Criteria

- AC-STE-537.1: In `mode: none`, `/setup` step 8 writes the bootstrap plan at `specs/plan/M_<tail>.md` and never at `specs/plan/M1.md`.
- AC-STE-537.2: That plan's frontmatter carries the full minted `id:` verbatim and `kind: scaffolding`.
- AC-STE-537.3: In `mode: linear` and `mode: jira` the scaffold is byte-identical to today — written at `specs/plan/M1.md`, carrying no `id:` key.
- AC-STE-537.4: The STE-189 class-(5) scaffold-inventory sentence in `skills/setup/SKILL.md` names both filename shapes and no longer claims `specs/plan/M1.md` unconditionally, and the file's line count does not increase: it sits at 358 lines against a 358-line cap, so the edit is net-zero or shorter, measured the way the enforcing test measures rather than by `wc -l`.
- AC-STE-537.5: The minted scaffold does not depend on probe #73's `scaffolding` exemption, and the assertion says why rather than mutating an unreachable branch: because the scaffold's filename is already a minted id, the probe short-circuits before provenance and the exemption are consulted at all. The probe reports zero violations against it, and a control on the old sequential name shows the same probe does reach the exemption there — so the claim is about an exercised code path.
- AC-STE-537.6: The step-8 producing instruction — the line telling the reader which filename to write — is pinned line-scoped in its own right, not only the downstream inventory sentence. A file-wide substring check cannot tell the two surfaces apart and would leave the producer unpinned.

## Technical Design

New module `adapters/_shared/src/setup_scaffold_plan_identity.ts` exporting `scaffoldPlanIdentity(specsDir: string, mode: MilestoneIdentityMode): { fileName: string; id?: string }`. On `"none"` it delegates to `mintMilestoneId(specsDir)` (`mint_milestone_id.ts:52`) — `fileName` = `${milestoneId}.md`, `id` verbatim; every other mode returns `{ fileName: "M1.md" }` with the key structurally absent. Sync, and deliberately NOT `resolveMilestoneIdentity` (`resolve_milestone_identity.ts:108`): its linear branch runs the five-way scan rather than a literal `M1`, and its jira branch throws on the absent bootstrap Epic key.

Edits: `skills/setup/SKILL.md:271` (step-8 routing) and `:273` (class-(5) sentence). Also `plan_identity_mode_conditional.ts:713-715` — test `planKind(content) === SCAFFOLD_PLAN_KIND` BEFORE `isMintedPlanId`, or a minted-named scaffold accumulates as an active minted plan and STE-481's unconsumed-scaffold pass goes permanently blind.
