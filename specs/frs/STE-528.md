# The skip-baseline capture has a caller that always fires

## Summary

The skip ratchet shipped with a read side that runs on every implementation report and a write side that has never run once in this repository. Two independent gates stand in front of it. The order that names the capture opens by asking whether an optional tracking key is present and closes by saying that its absence means skip entirely. This project does not set that key. Even where it is set, the capture is placed after a branch creation, so a branch that is already acceptable creates nothing and captures nothing.

The result is not a guard that fails open. It is a guard whose absent number the read side treats as grounds to refuse, so a clean run becomes uncertifiable and whoever is standing there supplies a number by hand. That is exactly what happened once already, and the number supplied was wrong.

Closing this means the order fires unconditionally, before any branch decision, and it means the thing being ordered is runnable rather than named. An order that only a language model can carry out is how this died the first time.

## Requirement

Nothing conditions the skip-baseline capture on an optional key or on a branch creation succeeding; the capture carries a command-line entry point; and the surfaces that order it order a runnable command.

## Acceptance Criteria

- AC-STE-528.1: No production surface conditions the skip-baseline capture on the presence of a `branch_template:` key. Measured today at `skills/implement/SKILL.md:45`, whose ordering paragraph opens "if Schema L carries `branch_template:`" and closes with the literal sentence "Absent `branch_template:` ⇒ skip entirely". The assertion scans for a capture order standing inside a `branch_template:`-conditioned scope, and is red before the change.
- AC-STE-528.2: No production surface conditions the capture on a successful `git checkout -b`. Measured today at `docs/implement-reference.md:77`, which opens "On a successful `git checkout -b`, and only there". This is a SECOND and independent gate: closing AC.1 alone leaves it standing, and closing this one alone leaves AC.1 standing.
- AC-STE-528.3: The two surfaces in AC.1 and AC.2 are corrected TOGETHER and their parity is asserted — deleting the change from either one turns the assertion red. Named because this repository has shipped the one-surface-not-its-neighbour defect repeatedly, most recently three times inside a single milestone, and it has no general guard.
- AC-STE-528.4: The capture carries a command-line entry point (`import.meta.main`), and both ordering surfaces order it as a runnable command fence rather than as prose naming a function to call. A prose order is what the previous attempt shipped, and it produced zero calls.
- AC-STE-528.5: No argv position of that entry point carries a skip count. The entry point runs the gate command itself and derives the number from the output it captured, through the shipped `parseTestOutput`. This is the direct cause of the wrong number already on disk: a capture that accepts a hand-typed count will eventually be handed one, and the tree cannot tell the two apart afterwards.
- AC-STE-528.6: `/implement` Phase 1 step 0 orders the capture unconditionally, before any branch decision is made. Asserted by locating the order in the shipped skill and showing it stands outside every conditional scope, not merely that the text appears somewhere in the file.
- AC-STE-528.7: `/gate-check` orders the capture when the checkout is clean and standing on a protected trunk, and when it does not, reports the reason by name. There is no silent branch: a skip that says nothing and a capture that never ran leave identical output, which is the shape this whole milestone is repairing.
- AC-STE-528.8: The order fires in a project that sets no `branch_template:`. Asserted by driving the shipped ordering path against a CLAUDE.md fixture whose `## Task Tracking` block matches this repository's byte for byte — `mode`, `mcp_server`, `jira_ac_field`, `team`, `project`, and no sixth key — and observing that a baseline record results. Red today, for the reason AC.1 states.
- AC-STE-528.9: The order fires when the current branch is already acceptable and no checkout occurs. Asserted separately from AC.8 with `isCurrentBranchAcceptable` returning true, because the two gates are independent and a fix aimed at one leaves the other in place.
- AC-STE-528.10: AC.8 and AC.9 are non-vacuous: each asserts the record was read back off disk after the run, not that the entry point returned successfully. A capture path that reports success while writing nothing is the failure mode this FR exists to detect, and it must not be able to satisfy its own test.

## Technical Design

The entry point is the load-bearing part, not the deconditioning. Removing the `branch_template:` clause makes the order unconditional in prose; giving the module a command-line front door makes the order executable, and the shipped reachability check already treats a front door as what distinguishes an order that can be carried out from one that cannot.

Deriving the count inside the entry point rather than accepting it is a deliberate narrowing of the function's interface. The low-level `captureSkipBaseline` keeps its numeric parameter — the tests need it, and a store writer that cannot be handed a number is untestable — but nothing a skill can invoke exposes that parameter. The number and the tree it was measured on are produced by the same call or not at all.

Placement in `/implement` moves from step 0.b″ to step 0. The old placement was inside the branch-proposal block for a reason that was true of the old contract and is false of the new one: the baseline used to belong to the branch, so it was captured where the branch was born. It now belongs to the trunk commit, which is known before any branch question is asked.

`/gate-check` is ordered too, not instead. It is the surface most often run on a clean trunk, so it is where the capture usually costs nothing extra beyond its own run; but it cannot be the only caller, because a project that never runs it would then never capture.

## Testing

The two deconditioning assertions are scoped to the ordering line and its enclosing conditional, not to the file. A file-scoped test would pass the moment the words appear anywhere, which is how a paragraph and its neighbour drift apart.

The CLAUDE.md fixture in AC.8 is copied from this repository's own file rather than hand-written, because the defect is precisely that the real block lacks a key, and a hand-written fixture is free to lack it for the wrong reason.

Both firing assertions read the store back off disk. Asserting on the entry point's return value would let a writer that silently no-ops satisfy the test — the exact class this milestone was opened to close.

## Notes

The reachability check shipped in M133 already classifies both of these ordering surfaces as ordered and reachable. That is not a contradiction of this FR: reachability asks whether the module can be run, and the module can. What it does not ask is whether the order will ever fire, and both of these could not. That gap is STE-531's subject.
