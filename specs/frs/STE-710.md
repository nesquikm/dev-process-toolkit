# Setup writes the settings file and a slim CLAUDE.md

## Summary

A fresh setup today writes every project setting into CLAUDE.md as headed sections.
This change makes setup write the settings file instead.
CLAUDE.md keeps the guidance the model must always see, plus a short pointer to the settings file.
Every other command that writes a setting writes it to the place the loader reads it from.
A project that has not moved keeps receiving its writes in CLAUDE.md.

## Requirement

### The writer

`project_settings.ts` gains `writeProjectSettings(projectRoot, update)`: read the current settings, apply `update`, validate against the closed sets of STE-706, and serialize with a fixed key order. A write that leaves the settings unchanged leaves the file byte-identical. Every writer below calls it, or the loader's legacy-module renderer on a legacy tree, chosen by `loadProjectSettings(projectRoot).source`. `settings` writes the settings file, and `legacy` writes the legacy home exactly as today. On `none`, only `/setup` creates the settings file, before its first writer runs; it alone passes `{ create: true }`. Every other writer on a `none` source writes its legacy home exactly as v2.101.4 does. So `/video init` on an unmanaged tree still writes `.dpt/video/`, and never makes the tree look toolkit-managed through the `settings_file` signal of STE-709.

Every write to the settings file also keeps the binding stub of STE-706 in step. It inserts, replaces or removes the CLAUDE.md stub slot so the slot is byte-equal to `renderTrackingStub` over the written settings. No other CLAUDE.md byte changes, and a write that leaves the render unchanged leaves CLAUDE.md byte-identical.

### The slim CLAUDE.md

`templates/CLAUDE.md.template` drops `## Docs`, `## Token Stats`, `## Release Files`, the `Layout:` line of `## Testing Conventions`, and the commented optional blocks for Task Tracking, `milestone_scan_fetch`, Verification and Orchestration. It gains a `## Project Settings` section holding `renderSettingsPointer`'s paragraph: the settings live in `specs/settings.yaml`, they need toolkit 3.0.0 or newer, and an older or unknown plugin version must stop and ask the operator to upgrade. It keeps the `/setup` marker, `## Key Commands` with the gating-rule prose, the rest of `## Testing Conventions`, and every other prose section. `## /setup audit` is not in the template; `setup/audit_log.ts` still appends it to CLAUDE.md. The template carries no stub; `/setup` in a tracker mode gets it from `writeProjectSettings`, through all of 3.x.

### Setup from a template

`skills/setup-template/SKILL.md` copies config files, and in whole-project mode the template's whole tree. A copied `specs/settings.yaml` passes through one filter before the Step 5 diff: every key listed in `NEW_KEYS` (STE-706) is dropped. Today that is `close_out.upgrade_offer`; later milestones add `tracking.gate_outcomes`, `tracking.tool_calls`, `retro.enabled`, `report_issue.identifier_redaction` and `optimizations.gate_commands`. STE-716 adds the same filter for capture hook entries in a copied `.claude/settings.local.json`. The Step 5 preview and the closing report name each dropped key. Every other copied byte is unchanged. A template therefore never turns on a recording, an offer or a knob; the target project turns each one on through its own approval.

`examples/*/release.yml` header comments name `release.files` in the settings file. `skills/setup/SKILL.md` stays within the NFR-1 cap; displaced prose moves to `docs/setup-reference.md`.

## Technical Design

One serializer owns the file, so key order and spacing never depend on which writer ran last. Writers pick their home from the loader's source and never decide it themselves. A legacy tree therefore keeps today's bytes until the upgrade runs.

The template loses the moved sections and gains the pointer section. The pointer is rendered by the loader module, so the template, the upgrade and probe #18 share one string. The stub is re-rendered by the same writer, so it cannot drift from the file.

This FR is marked breaking: a fresh setup no longer writes CLAUDE.md headings that NFR-2 protects.

## Testing

Round-trip and refusal rows for the writer, per-writer rows over three tree kinds, stub re-render rows, the template scans, and the existing legacy writer suites unchanged.

## Notes

The comments in a settings file are not preserved by a rewrite; the reference doc says so. Decided: this FR keeps the breaking flag, which the release bump reads, so the milestone ships as 3.0.0. Writers write to the home the loader reports.
