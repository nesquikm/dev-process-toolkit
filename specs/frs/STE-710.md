# Setup writes the settings file and a slim CLAUDE.md

## Summary

A fresh setup today writes every project setting into CLAUDE.md as headed sections.
This change makes setup write the settings file instead.
CLAUDE.md keeps the guidance the model must always see, plus a short pointer to the settings file.
Every other command that writes a setting writes it to the place the loader reads it from.
A project that has not moved keeps receiving its writes in CLAUDE.md.

## Requirement

### The writer

`project_settings.ts` gains `writeProjectSettings(projectRoot, update)`: read the current settings, apply `update`, validate against the closed sets of STE-706, then edit the file in place. A changed key rewrites only the line or lines that hold it. A trailing comment on the changed key's own line is kept, byte-identical after the new value. A key inside a flow collection, such as `token_stats: { enabled: false }`, rewrites that one flow line in flow style and keeps its trailing comment. A new key is inserted at its place in the fixed key order among its existing siblings. A removed key loses only its own lines. Every comment, blank line and other key keeps its bytes and its order. Only a create, by `/setup` or by the migration of STE-711, serializes a whole new file, in the fixed key order and in block style: one scalar per line, every non-empty map and list as a block. An empty map or list is written `{}` or `[]`. A write that leaves the settings unchanged leaves the file byte-identical. A create never overwrites a foreign `specs/settings.yaml` (STE-706): it refuses in NFR-10 shape, naming the file, and writes nothing. Every writer below calls it, or the loader's legacy-module renderer on a legacy tree, chosen by `loadProjectSettings(projectRoot).source`. `settings` writes the settings file, and `legacy` writes the legacy home exactly as today. On `none`, only `/setup` creates the settings file, before its first writer runs; it alone passes `{ create: true }`. When the path holds a foreign file, `/setup` writes every legacy home exactly as v2.101.4 does, leaves the foreign file byte-identical, and names it in its closing report. Every other writer on a `none` source writes its legacy home exactly as v2.101.4 does. So `/video init` on an unmanaged tree still writes `.dpt/video/`, and never makes the tree look toolkit-managed through the `settings_file` signal of STE-709.

Every write to the settings file also keeps the binding stub of STE-706 in step. It inserts, replaces or removes the CLAUDE.md stub slot so the slot is byte-equal to `renderTrackingStub` over the written settings. No other CLAUDE.md byte changes, and a write that leaves the render unchanged leaves CLAUDE.md byte-identical.

### The set verb

Today `/implement` writes `verify_skill` by model prose; no code does it, and `scaffold_check_skill.ts` writes only the skill stub. A model-run edit of a moved heading on a settings-file tree would make the source `both`, and every skill would then stop at entry. So the front door of AC-STE-706.10 gains one verb:

```
bun run "${CLAUDE_PLUGIN_ROOT}/adapters/_shared/src/project_settings.ts" set <dotted key> <value> "<projectRoot>"
```

Its key list is closed, `SETTABLE_KEYS = ["verification.verify_skill"]`. Any other key refuses in NFR-10 shape and writes nothing, so a model can never set a `NEW_KEYS` key or a gate through it. On a `settings` source it calls `writeProjectSettings` and prints `source: settings`. On a `legacy` or `none` source it writes nothing and prints `source: legacy` or `source: none`; the skill then writes the legacy home exactly as v2.101.4's prose says. On `both`, or any loader refusal, it exits non-zero with the NFR-10 message on stderr and nothing on stdout. `skills/implement/SKILL.md` lines 230, 231, 232 and 244 and `docs/verification-skills.md` lines 119-122 and 211-212 name the verb and its legacy branch, edited in place with the line count unchanged. Line 231 and lines 121-122 are path 3, the ambiguous adopt, which writes `verify_skill` for the picked candidate exactly as path 2 does (review 4, R4-5).

The skill runs the verb only when the auto-loaded CLAUDE.md carries the `## Project Settings` section, which only a settings-file tree has and probe #18 grades (STE-709). Otherwise it writes the legacy home exactly as v2.101.4's prose says. So the adopt paths add no tool call on any tree: the condition is read from context the model already holds (operator ruling 2026-11-04, zero extra calls). The verb's own `legacy` and `none` branches stay as a guard, for a run that reaches it anyway.

### The writer scan

`tests/m_94e6f7-ste-710-settings-writers.test.ts` scans `skills/*/SKILL.md` and `docs/*.md`. Its unit is a paragraph or a list item, joined across wrapped lines, so a phrase split over two lines is still one unit. A unit fails when it tells the reader to write, emit, add, splice, paste, insert or append into a moved heading, unless the same unit names `writeProjectSettings`, the `set` verb or the word legacy. This FR rewrites every hit, so the scan is green on its own commit. At drafting the hits sit in `implement`, `setup`, `docs/setup-reference.md`, `setup-docs-mode.md`, `setup-tracker-mode.md`, `layout-reference.md`, `verification-skills.md` and `patterns.md`. A hit that describes a read, not a write, gains the legacy clause.

`repoint_tracker_binding.ts --verify` and its `repoint` receipt hash the serialized `task_tracking.status_vocabulary` on a settings-file tree, and `specs/tracker-config.yaml` on a legacy tree.

### The slim CLAUDE.md

`templates/CLAUDE.md.template` drops `## Docs`, `## Token Stats`, `## Release Files`, and the commented optional blocks for Task Tracking, `milestone_scan_fetch`, Verification and Orchestration. It gains a `## Project Settings` section holding `renderSettingsPointer`'s paragraph: the settings live in `specs/settings.yaml`, they need toolkit 3.0.0 or newer, and an older or unknown plugin version must stop and ask the operator to upgrade. It keeps the `/setup` marker, `## Key Commands` with the gating-rule prose, the whole of `## Testing Conventions` with its `Layout:` bullet byte-identical (STE-706), and every other prose section. `## /setup audit` is not in the template; `setup/audit_log.ts` still appends it to CLAUDE.md. The template carries no stub; `/setup` in a tracker mode gets it from `writeProjectSettings`, through all of 3.x.

### Setup from a template

`skills/setup-template/SKILL.md` copies config files, and in whole-project mode the template's whole tree. In per-category mode it copies only what `template_source_analyzer.ts` inventories. Its `PROCESS_CONFIG_FILES` gains `specs/settings.yaml`, so a 3.x template's settings file is offered with the other process config files, and `tests/m125-ste-469-setup-template.test.ts` pins the entry. A 2.x template has no settings file, so its inventory and copy are unchanged.

A 3.x template's CLAUDE.md holds only the pointer and, in a tracker mode, the stub. So when the template carries `specs/settings.yaml` and a per-category selection copies CLAUDE.md without it, setup-template refuses in NFR-10 shape before the Step 5 diff. The refusal names both files, asks the operator to select the settings file too or deselect CLAUDE.md, and copies nothing. The other direction refuses the same way: a selection that copies `specs/settings.yaml` without CLAUDE.md would leave the target without the pointer and stub, or beside a legacy CLAUDE.md as a `both` tree. So the pair is copied together or not at all. A copied `specs/settings.yaml` passes through one filter before the Step 5 diff: every key listed in `NEW_KEYS` (STE-706) is dropped. Today that is `close_out.upgrade_offer`; later milestones add `tracking.gate_outcomes`, `tracking.tool_calls`, `retro.enabled`, `report_issue.identifier_redaction` and `optimizations.gate_commands`. STE-716 adds the same filter for capture hook entries in a copied `.claude/settings.local.json`. The Step 5 preview and the closing report name each dropped key. Every other copied byte is unchanged. A template therefore never turns on a recording, an offer or a knob; the target project turns each one on through its own approval.

`examples/*/release.yml` header comments name `release.files` in the settings file. `skills/setup/SKILL.md` stays within the NFR-1 cap; displaced prose moves to `docs/setup-reference.md`.

## Technical Design

One writer owns the file. It creates a file in a fixed key order and edits an existing one line by line, so comments survive every write. Writers pick their home from the loader's source and never decide it themselves. A legacy tree therefore keeps today's bytes until the upgrade runs.

The template loses the moved sections and gains the pointer section. The pointer is rendered by the loader module, so the template, the upgrade and probe #18 share one string. The stub is re-rendered by the same writer, so it cannot drift from the file.

This FR is marked breaking: a fresh setup no longer writes CLAUDE.md headings that NFR-2 protects.

## Testing

Round-trip and refusal rows for the writer, per-writer rows over three tree kinds, stub re-render rows, the template scans, and the existing legacy writer suites unchanged.

## Notes

Comments in a settings file survive every write. Decided: this FR keeps the breaking flag, which the release bump reads, so the milestone ships as 3.0.0. Writers write to the home the loader reports.
