# One settings file and one loader that still reads the old CLAUDE.md homes

## Summary

Project settings are spread across CLAUDE.md headings and three separate files today.
This change adds one settings file under the specs folder, with a fixed schema.
A single loader reads it and returns every setting in one typed shape.
A project that has not moved yet is read from its CLAUDE.md headings as before.
A project with settings in both places is refused, so no value is silently picked.

## Requirement

### The file

`specs/settings.yaml`, committed, one per project. It is the only new home; nothing else in this milestone adds a settings file.

```yaml
schema_version: 1
min_dpt_version: 3.0.0          # strict X.Y.Z; the loader refuses a lower running toolkit
task_tracking:                  # absent section ≡ mode none
  mode: linear                  # none | linear | jira | <custom adapter>
  mcp_server: linear
  jira_ac_field: ""
  branch_template: "{type}/m{N}-{slug}"
  secondary_tracker: none       # optional; buildResolverConfig reads it; probe #21 reds it, as on v2.101.4
  milestone_scan_fetch: false   # was the standalone top-level CLAUDE.md line
  linear:                       # was ### Linear (or jira: for ### Jira)
    team: STE
    project: Example Project
    default_labels: []
    repo_tag: example-fe        # shared container only
    min_dpt_version: 3.0.0      # shared container only
    linear_bug_label: Bug
  status_vocabulary:            # was specs/tracker-config.yaml, same document
    tracker_key: linear
    statuses: [Todo, In Progress, In Review, Done]
    roles: { initial: Todo, in_progress: In Progress, in_review: In Review, done: Done }
verification: { verify_skill: smoke-test, verify_mode: manual, run_cmd: none, e2e_cmd: none }
docs: { user_facing_mode: false, packages_mode: false, changelog_ci_owned: false, changelog_unversioned: false }
orchestration: { default_effort: ultracode, merge_policy: offer }
tracking:
  token_stats: { enabled: false }   # M2 adds its capture toggle beside it
close_out:
  upgrade_offer: { enabled: false } # STE-712; absent means off, no legacy home
release:
  files: []                     # the ## Release Files entries, same entry shape
video:
  config: {}                    # was .dpt/video/config.yaml, parsed by parseVideoConfig
  style: {}                     # was .dpt/video/style.yaml, parsed by parseVideoStyle
```

The example values are synthetic. Every section's key set is closed and equals what today's reader accepts, by the same spelling: `CANONICAL_KEYS` in `task_tracking_canonical_keys.ts` plus `milestone_scan_fetch`, `secondary_tracker` (read by `buildResolverConfig`), the `linear` and `jira` adapter sub-maps (either or both, since v2.101.4 tolerates an inactive adapter's sub-section) and `status_vocabulary`; the binding keys `readWorkspaceBinding` parses (`team`, `project`, `default_labels`, `repo_tag`, `min_dpt_version`, `linear_bug_label`, `jira_bug_issue_type`) plus `jira_issue_type`, which `writeTrackerSubsection` writes and `adapters/jira.md` reads; `CLOSED_KEYS` in `verification_config.ts`; the four `DocsConfig` keys; the two `OrchestrationConfig` keys; `{enabled}` for token stats; `{enabled}` for `close_out.upgrade_offer`, the one key this milestone adds (STE-712); the `ReleaseFile` shape; `TrackerConfig`; `VideoConfig` and `VideoStyle`. The loader accepts `secondary_tracker` because a v2.101.4 reader reads it. Probe #21 still reds it on both arms, exactly as trunk's `CANONICAL_KEYS` does (STE-709), so no gate is relaxed.

### Never moved

`.dpt/.env` (secrets), the per-user `userConfig.tracker_write_gate` (project copies are refused as forged by `tracker_write_gate_setting.ts`), `.claude/settings.json` (owned by Claude Code), and the `DPT_*` environment knobs stay where they are. The loader never reads them.

### Stays in CLAUDE.md

The `/setup` generation marker, `## /setup audit`, `## Key Commands` and its gating-rule prose, the whole of `## Testing Conventions`, and every other prose section. Its `Layout:` bullet is model-facing guidance that Claude Code auto-loads, so it is not moved in 3.0. `detectLayout` in `bun_zero_match_placeholder.ts` keeps reading it from CLAUDE.md exactly as v2.101.4 does. The settings file has no `testing` section, and the bullet is never a legacy home (supervisor ruling 2026-11-04, deferral recorded in the M_94e6f7 plan, for operator review). The shared-container stop paragraph also stays in CLAUDE.md, because Claude Code auto-loads that file and not the settings file.

### Sources

`detectSettingsSource(projectRoot)` decides the source without parsing values and never throws. It returns `settings`, `legacy`, `none` or `both`. `loadProjectSettings(projectRoot)` returns `{ source, settings }`:

- `settings` — `specs/settings.yaml` exists and no legacy home exists.
- `legacy` — no settings file, and at least one legacy home exists: a moved CLAUDE.md heading, the standalone `milestone_scan_fetch:` line, `specs/tracker-config.yaml`, or `.dpt/video/config.yaml` / `style.yaml`. Values come from the same parse today's readers perform.
- `none` — neither. Every section takes today's documented default.
- Both a settings file and a legacy home: refusal. The loader never merges two homes.

A foreign file is not a settings file. Repositories that keep OpenAPI or test specs under `specs/` may already carry a `specs/settings.yaml`. A file with no line starting `schema_version:` or `min_dpt_version:` at column 0 is foreign. The test is a raw-line scan, so it never parses the file and never throws. Every reader treats a foreign file as absent: the source is decided as if the path were empty, the `settings_file` signal of STE-709 is not raised, and no writer overwrites it (STE-710, STE-711). The `mode` and `get` verbs of the front door then print one warn note on stderr, `note: specs/settings.yaml ignored: not a toolkit settings file`, keep stdout unchanged and exit 0. A file with either key and a bad shape is a settings file and refuses as usual.

Comments, per reader. Each legacy home is matched the way its own v2.101.4 reader matches it. The heading readers of `## Task Tracking` and its `### Linear` / `### Jira` sub-sections, `## Verification`, `## Docs`, `## Orchestration`, `## Token Stats` and `## Release Files` match raw lines and do not strip HTML comments, so a heading inside `<!-- -->` counts exactly as it does on v2.101.4. `readMilestoneScanFetch` also matches raw lines without stripping. Its home is any line starting `milestone_scan_fetch:` at column 0, whatever the value; the value reads `true` only for the literal `true` its pattern accepts, and `false` otherwise. `detectLayout` is the one trunk reader that strips HTML comments, and it reads no legacy home of this loader.

Section isolation. On a `legacy` or `none` source, `loadProjectSection(projectRoot, section)` parses only the legacy home of the named section. Today a malformed `## Verification` breaks only the verification reader, and the move keeps that: a malformed legacy section refuses reads of that section and of no other. Every reader of STE-707 calls `loadProjectSection`. On a `settings` source the file is validated whole, as the closed sets require.

Inside `task_tracking` on a `legacy` source, `status_vocabulary` is a lazy accessor. `loadProjectSection(projectRoot, "task_tracking")` parses `specs/tracker-config.yaml` only when that accessor is read, and a malformed file throws `SettingsShapeError` at that read and nowhere else. `readWorkspaceBinding`, `buildResolverConfig` and the bundled hooks never read it. So a malformed tracker config file blocks no tracker write and no ledger row, as on v2.101.4, where `readWorkspaceBinding` never opens that file.

Beside a settings file, a moved CLAUDE.md heading counts as a legacy home only when its body carries at least one key its section's closed set recognises. A consumer heading of the same name holding only prose, such as a hand-written `## Verification` checklist, is never a second home.

### The binding stub

Through all of 3.x, a settings-file tree in a tracker mode also carries a generated legacy stub in CLAUDE.md. It exists so a pre-3.0 cached hook, `pre-tracker-write-gate` above all, keeps guarding. `renderTrackingStub(settings)` renders it: first one marker comment line, `<!-- Generated from specs/settings.yaml for older plugins. Edit that file, not this block. -->`, which sits just before the slot and outside it, then a `## Task Tracking` heading with the `mode:` line, then the adapter's `### Linear` or `### Jira` sub-section with the binding keys of `task_tracking.<adapter>`, in the v2.101.4 line shape `readWorkspaceBinding` parses. A custom adapter gets the `mode:` line only. `mode: none` renders the empty string. The renderer lives in the legacy module; `project_settings.ts` re-exports it.

The marker names no heading and holds no key line, so no reader takes it for a home. On a settings-file tree the stub's slot is the `## Task Tracking` heading with its sub-sections. The 3.x loader never reads that slot and never counts it as a second home, whatever it holds. Drift is graded by probe #25 (STE-709) and repaired by `/upgrade` (STE-711). The stub is removed in 4.0.

## Technical Design

The loader reads the settings file with Bun.YAML, then validates each section against its closed set. It delegates video and status checks to their existing validators.

The legacy half is a separate module holding today's CLAUDE.md, tracker config and video parsers, moved without behaviour change. Only the loader imports it. Legacy sections parse one per read, as today. It also holds the stub renderer, so the old line shape has one owner.

Source detection runs first and is cheap: existence checks plus the readers' raw-line heading scan. It skips the stub slot and needs a recognised key before calling a heading a second home.

The pointer and stub renders are pure string functions, so probes can byte-compare them.

## Testing

Table tests over the closed sets, legacy parity over the existing reader fixtures, both-homes rows per legacy kind, same-name heading rows, stub-slot and stub-render rows, floor rows, a source purity scan and a front-door spawn.
