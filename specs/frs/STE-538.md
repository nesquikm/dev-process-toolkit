# Adopt the scaffold's minted id instead of minting a second one

## Summary

Once setup mints an identity for the bootstrap plan, spec-writing must not mint another. A second mint would rename the plan from one opaque name to another for no reason, and the identity recorded inside would disagree with the one that named it.

Adoption makes the first mint the only mint.

A second mint leaves no trace in the resulting filename, so the guard has to be a call count rather than an inspection of the outcome.

## Requirement

Resolving a tracker-less milestone identity adopts the identity already recorded on an eligible bootstrap plan when one is present, and mints a fresh identity only when none is. On the adoption path the plan is not renamed, its body is unchanged, and the recorded identity is left exactly as it was found.

## Acceptance Criteria

- AC-STE-538.1: `adoptOrMintMilestoneId(specsDir)` returns the recorded `id:` of the active plan declaring `kind: scaffolding` when exactly one such plan carries a well-formed minted id; with no such plan it mints a fresh identity.
- AC-STE-538.2: On the adoption path no rename occurs and the file's body below the frontmatter is byte-identical before and after. Adoption resolves before `consumeScaffoldPlan`'s destination guard, which throws when the target path already exists: after STE-537 the scaffold already carries its final name, so routing an adopted identity into that guard would refuse the very file it exists to keep.
- AC-STE-538.3: On the adoption path the `kind:` line is dropped and `milestone:` is rewritten, and the `id:` line is left untouched.
- AC-STE-538.4: A tracker-mode scaffold is never adopted, and a plan declaring `kind: scaffolding` that carries no `id:` mints fresh rather than adopting.
- AC-STE-538.5: Across a `mode: none` `/setup` followed by `/spec-write`, exactly one active plan exists, named `M_<tail>.md`, and `mintMilestoneId` is invoked exactly once — asserted as a call count on a double, not inferred from the filename.
- AC-STE-538.6: STE-481's two recorded-but-untested refusals are covered: the more-than-one-scaffolding-plan refusal and the missing-frontmatter path each assert their own message.
- AC-STE-538.7: The asymmetry between `findScaffoldPlan` walking every `*.md` and probe #73 filtering by canonical filename is closed, or recorded in this FR's notes with the shape that remains unguarded.

## Technical Design

New `adapters/_shared/src/adopt_or_mint_milestone_id.ts`:

`export type MilestoneMinter = (specsDir: string) => MintedMilestoneId;`
`export function adoptOrMintMilestoneId(specsDir: string, mint: MilestoneMinter = mintMilestoneId): MintedMilestoneId`

It calls `findScaffoldPlan` (`consume_scaffold_plan.ts:101`), reads `id:` through `parseFrontmatter(raw, { lenient: true })`, adopts when `ULID_REGEX` (`ulid.ts:19`) matches — token via `milestoneIdFromUlid` — else delegates to `mint`. `resolve_milestone_identity.ts:127`'s `none` branch routes through it; add `minter?` to `ResolveMilestoneIdentityInput` beside the `provider`/`branchScanner` seams.

The trap: an adopted identity makes `to` (`consume_scaffold_plan.ts:215`) the scaffold itself, firing the `:228` clobber refusal. Branch on `from === to` first — rewrite in place, preserving the `id:` line `:175` drops — and extend the four-outcome docstring at `:194`. Off-canonical scaffolds keep the rename. `skills/spec-write/SKILL.md:177` gains the new name and loses its now-false "renames"/"mints the identity locally" claims.

## Testing

Both build real temp projects with `specs/plan/{,archive/}` and a `CLAUDE.md` carrying `## Task Tracking\n\nmode: <mode>`, as the STE-481 fixtures do. `runPlanIdentityModeConditionalProbe` is `async` (`plan_identity_mode_conditional.ts:664`) — every leg that calls it `await`s it, or `.violations` is `undefined` and the assertion is meaningless.

**Shared double.** `countingMinter()` returns a real function wrapping `mintMilestoneId` and carrying a `calls` counter. Every absence assertion below is a count on this double, never a grep and never an inference from the returned value.

**AC.1 — `adoptOrMintMilestoneId` (co-located file).** Four fixtures, each asserting the returned pair, not just one half:
- one active `kind: scaffolding` plan carrying `id: fr_<26-char Crockford>` → the returned `id` is `toBe`-equal to the fixture's literal id and `milestoneId` is `toBe(milestoneIdFromUlid(thatId))`; the double records `calls === 0`. The zero here has its positive control in the next bullet, which uses the same double on the same harness and records 1.
- no plan file at all → the returned `id` matches `ULID_REGEX` and is not the fixture id; `calls === 1`.
- one plan carrying `kind: legacy` plus a well-formed `id:` → mints (`calls === 1`), proving adoption keys on `SCAFFOLD_PLAN_KIND` and not on the mere presence of an `id:`.
- **Isolation control**: take the adopting fixture and delete only its `id:` line; the same call now mints. One byte separates the two legs, so the adoption clause is what fired.

**AC.2 — no rename, body byte-identical (milestone file).** Fixture is the STE-537 shape: `specs/plan/M_<tail>.md`, frontmatter `milestone:` / `status: active` / `id: fr_…` / `kind: scaffolding`, body carrying the `<scaffolding>` FR row and a `verify:` line. Read `raw` AND assert `readdirSync(activeDir)` is `toEqual([basename])` BEFORE the call, so the post-state listing is a comparison and not a lone snapshot. Then run `resolveMilestoneIdentity({ specsDir, mode: "none" })` and `consumeScaffoldPlan`. Assertions: `outcome.consumed === true`; `outcome.from` is `toBe(outcome.to)`; `readdirSync` of the active dir is again `toEqual([basename])` — the same one name; and `splitFrontmatter(after)!.rest` is `toBe(splitFrontmatter(raw)!.rest)`, a byte comparison of the whole remainder rather than a `toContain` on a marker (a `toContain` passes on a delete-and-rewrite that reproduces the marker). Falsification control: the same body assertion on the `M1.md`-named fixture, which takes the rename leg, must also pass — so the body pin is not accidentally satisfied by the no-rename branch alone — while `from === to` is red on that fixture, which is what shows the no-rename pin carries its own weight.

**AC.3 — `kind:` dropped, `milestone:` rewritten, `id:` untouched.** The fixture carries a deliberately STALE `milestone: M_STALE1`, puts `id:` LAST in the frontmatter, and writes it with two spaces after the colon (`id:  fr_…`). The stale value is what makes the `milestone:` half falsifiable: `to` derives from the adopted `id:`, never from this line, so a fixture whose `milestone:` already read `M_<tail>` would satisfy the assertion whether or not the rewrite ran. **Pre-call controls, asserted before the call on `splitFrontmatter(raw)!.lines`**: some element matches `/^kind:/` (without this the absence assertion below is vacuous), and the last element is exactly `id:  fr_…`. Post-call, on `splitFrontmatter(after)!.lines`: no element matches `/^kind:/`; the `milestone:` element is `toBe("milestone: M_<tail>")`; and the LAST element is `toBe` the pre-call `id:` string, spacing included. Note the index is NOT asserted as unchanged — dropping the `kind:` line shifts every later element up one, so an absolute-index pin could never pass. Last-position-plus-byte-equality is the mutation-sensitive form: today's `rewriteConsumedFrontmatter` drops the line at `consume_scaffold_plan.ts:175` and re-inserts a normalised `id: <id>` immediately after `milestone:` (`:185`), which both moves it off the end and eats the double space. Verify by mutation: route the adoption fixture through the unmodified rewrite and confirm this exact assertion goes red.

**AC.4 — two legs, both absence-shaped, both with positive controls.**
- *Tracker mode is never adopted.* The identical adoptable scaffold, under `mode: linear` and under `mode: jira` (the jira leg MUST pass `epicKey: "DST-49"` — `resolveMilestoneIdentity` routes jira through `milestoneIdFromEpicKey(input.epicKey ?? Assert `expect("id" in identity).toBe(false)` (the key absent, not merely undefined — probe #73 fails a tracker plan carrying an `id:` line); `identity.milestoneId` matches `/^M\d+$/` for linear and is `toBe("M_DST_49")` for jira; `consumeScaffoldPlan` returns `{ consumed: false, from: null }`; `readFileSync(scaffold)` is `toBe` its pre-call bytes. The absence assertion is `double.calls === 0` for both tracker legs, and its positive control is the third leg in the same test: the same fixture and the same double under `mode: "none"` with the scaffold's `id:` removed records `calls === 1`. Without that third leg a zero count proves only that nothing ran.
- *A `kind: scaffolding` plan with no `id:` mints fresh.* Scaffold present, `id:` line absent; assert `calls === 1`, the returned `id` matches `ULID_REGEX`, and it equals no id present anywhere under `specs/plan/**`.

**AC.5 — exactly one active plan, exactly one mint.** One harness, one shared counting double, two legs run in order. Setup leg: call the double to obtain an id, write the scaffold at `specs/plan/<milestoneIdFromUlid(id)>.md` with `kind: scaffolding` — the bytes STE-537 produces. Spec-write leg: `resolveMilestoneIdentity({ specsDir, mode: "none", minter: double })` then `consumeScaffoldPlan`, writing a fresh plan at `outcome.to` only when `consumed === false`. Assertions: the active-dir listing is `toHaveLength(1)` and its single entry matches `/^M_[0-9A-HJKMNP-TV-Z]{6}\.md$/`; `double.calls` is `toBe(1)`; the survivor's `splitFrontmatter(...)!.lines` carries no `/^kind:/` element, with the setup leg's own frontmatter asserted to carry one as the control; and `(await runPlanIdentityModeConditionalProbe(root))` reports `mode === "none"` with `violations` `toEqual([])`. The `kind:` check is asserted DIRECTLY and not inferred from that zero, because the probe cannot see it: `runPlanIdentityModeConditionalProbe` sorts a minted-named file into `activeMintedPlans` on `isMintedPlanId(basename(file))` before ever reading `kind:` (`plan_identity_mode_conditional.ts:713-716`), and the unconsumed-scaffold pass fires only when `activeScaffolds` is non-empty — so a survivor that still declared `kind: scaffolding` would report zero violations too. The probe leg stands only for what it can prove: the survivor is a well-formed minted plan. **Positive control, in the same describe**: re-run the identical harness with the spec-write leg calling `mintMilestoneId` through the double directly (the pre-STE-538 behaviour) and assert it records `calls === 2` and leaves two active plans. Both AC.5 count assertions are therefore proven able to fail on this exact fixture.

**AC.6 — STE-481's two untested refusals.** Both are genuinely untested today: the M126 file carries only a bare `.toThrow()` at `:466` for the clobber path and one message-matched throw at `:835` for `assertExactlyOneActivePlan`.
- *Multi-scaffold.* Two active plans both declaring `kind: scaffolding`. `expect(() => findScaffoldPlan(specsDir)).toThrow(/2 active plans declare kind: scaffolding/)`, the same through `consumeScaffoldPlan` and through `adoptOrMintMilestoneId` (the new caller inherits the refusal, so it needs its own leg). Then assert both files are still on disk with their original bytes — a refusal that half-consumed would still satisfy a bare `toThrow()`.
- *No frontmatter block.* This path is reachable only because of a regex asymmetry that the fixture must be built from: `parseFrontmatter` matches through `FRONTMATTER_RE` (`frontmatter.ts:22`), which carries the `/m` flag and so finds a block starting at any line, while `splitFrontmatter`'s `FM_SPLIT_RE` (`frontmatter.ts:78`) is anchored at offset 0. So the fixture is a plan whose frontmatter is preceded by one blank line. Assert first that `findScaffoldPlan` returns that path (without this the throw test would pass vacuously on a file that was never a candidate), then `expect(() => consumeScaffoldPlan(specsDir, identity)).toThrow(/has no YAML frontmatter block to record the minted id/)`, then that the file's bytes are unchanged.

**AC.7 — the `findScaffoldPlan` / probe #73 filename asymmetry.** Fixture: `specs/plan/bootstrap-plan.md` — a name `PLAN_FILENAME_RE` (`milestone_token.ts:51`) rejects — carrying `kind: scaffolding` and a well-formed `id:`.
