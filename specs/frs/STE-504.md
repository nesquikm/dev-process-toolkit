# A project that documents how to run itself must declare it

## Summary

The rule the operator asked for is that the app should be run whenever it is possible to run it, and that possibility is knowable — a project that documents how to start itself has already answered the question. Turning that into a gate means deciding what counts as documentation, and deciding it narrowly, because a probe that fires on every library teaches people to silence it rather than answer it.

## Requirement

A repo carrying discoverable run instructions must declare a run command; a repo carrying none is never asked.

## Acceptance Criteria

- AC-STE-504.1: `detectRunnability(projectRoot)` reports whether the repo carries discoverable run instructions, from a closed and named source set.
- AC-STE-504.2: The sources are exactly: a `dev` or `start` script in `package.json`, a `run` target in a Makefile, a README heading matching Running / Getting Started / Development, and a run block in CLAUDE.md.
- AC-STE-504.3: A gate probe fails when detection fires and no `run_cmd` is declared.
- AC-STE-504.4: The probe is silent when detection does not fire, and silent when `run_cmd` is declared — `none` included.
- AC-STE-504.5: Each source is mutation-verified in both directions: it fires on a real positive AND does not fire on a near-miss.
- AC-STE-504.6: The probe message names which source fired, so declaring `none` is a considered answer rather than a reflex.

## Technical Design

The operator's rule was stated as "the app SHOULD be run if it's possible for the project — for example, if there is information on how to run it". `detectRunnability` is that inference made explicit and auditable. The source set is closed (AC.2) rather than heuristic because an open-ended "does this look runnable" predicate is the thing that would make the probe untrustworthy.

AC.5 is the criterion that keeps the probe honest, and the near-miss half is the one that matters. A `build` script is not a `dev` script. A Makefile `run-tests` target is not a `run` target. A README heading "Running the test suite" is not "Running". Every source needs its negative case pinned, because a detector that fires on everything makes `run_cmd: none` the path of least resistance and the whole contract collapses into a config line nobody read.

AC.6 exists for the same reason from the other direction. A probe that says "declare run_cmd" teaches nothing; a probe that says "package.json declares a `dev` script — declare run_cmd, or `none` if it is not the app entry point" lets the author answer correctly in one step.

This repository is its own first test case: it carries no `dev` or `start` script and no Makefile `run` target, and its README documents installation rather than running. Detection should not fire here, and that non-firing is worth asserting.

## Testing

Per-source fixtures, each asserted in both directions per AC.5 — a real positive fires, a near-miss does not. Probe coverage for the four combinations of detection fired or not against `run_cmd` declared, absent, or `none`. Probe-message coverage asserting the fired source is named. A fixture for this repository's own shape asserting detection does not fire. `bun test` full root.

## Notes

The failure mode this FR is designed against is not a missed detection but an over-eager one. A probe that reds a library repo trains the author to write `run_cmd: none` without reading the question, and a contract everyone silences is worse than no contract, because it looks like coverage.

Registering a new probe has historically moved pinned counts across many test files; land the registration in one sweep.
