# A resumed FR is classified at FR scope, including whether it closes its milestone

## Summary

The resume classifier answers one question: what state is this milestone in. An FR-scoped run needs a different question answered — what state is this one FR in, and would building it leave its milestone with nothing active left. Without that second answer the chain builder cannot know whether the ship ceremony belongs at the end.

## Requirement

Classification accepts an FR and reports that FR's own state plus whether it is the last active FR bound to its milestone.

## Acceptance Criteria

- AC-STE-500.1: `classifyResume` accepts an FR-scoped input and returns a classification for that FR alone.
- AC-STE-500.2: The classification states whether the FR is the last active FR bound to its milestone.
- AC-STE-500.3: The FR's own `needs_technical_review` flag is read and surfaced, so a `--no-tech` FR routes to a spec-write pass scoped to that FR.
- AC-STE-500.4: An already-archived FR refuses in the NFR-10 canonical shape, naming its archived state.
- AC-STE-500.5: Classification is read-only on every FR-scoped path — no spec write, no tracker write, no commit — mutation-verified.
- AC-STE-500.6: Milestone-scoped classification is unchanged.

## Technical Design

`classifyResume` in `adapters/_shared/src/resume_classifier.ts` assembles four shipped helpers rather than re-deriving their predicates — `plan_task_state`, `active_plan_ship_ready`, `plan_ship_coherence`, and `needs_technical_review_consistency`. The FR-scoped branch keeps that discipline: `milestoneFrBinding` from `active_plan_ship_ready` already enumerates the FRs bound to a milestone, so AC.2's last-active-FR question is a count over that existing enumeration minus the FR under work, not a new scan.

AC.3 narrows an existing capability rather than adding one. The milestone-scoped `needs_technical_review` state flags every bound FR awaiting review; the FR-scoped equivalent reads one FR's frontmatter flag. `needs_technical_review_consistency` is still the source — its violations are carried rather than swallowed, matching the shipped contract.

AC.4 has no milestone-scoped counterpart. A milestone is refused when `shipped` or `parked`; an FR is refused when its own `status:` is `archived`, which the six milestone states cannot express. The refusal names the archived state so an operator who meant a different FR is not left guessing.

AC.5 is the invariant the whole classifier rests on, and it is asserted by mutation rather than by reading the code: classifying an FR and walking away must leave the tree byte-identical and the tracker untouched. The FR-scoped branch reads more files than the milestone branch does, which is precisely why the read-only claim needs re-proving rather than inheriting.

## Testing

On-disk fixtures per FR state: an FR with siblings still active, an FR that is the last active one, an FR flagged `needs_technical_review`, an archived FR. Each classified from the fixture tree with the result asserted field by field. AC.2's boundary asserted in both directions — the last-active case and the one-sibling-remaining case, since an off-by-one here silently ships or silently fails to ship a milestone. AC.5 mutation-verified by asserting zero tree mutation and zero tracker calls across every FR-scoped path. AC.6 asserted against the shipped milestone-scoped output. `bun test` full root.

## Notes

The last-active-FR predicate is the load-bearing one: it decides whether STE-501's chain extends into a release. An off-by-one in either direction is expensive — one direction releases an unfinished milestone, the other strands a finished one.

Deliberately not in scope: any notion of "this FR is partly implemented". The milestone-scoped classifier has `partly_implemented` because plan task ticks give it evidence; a single FR has no equivalent signal that is not a guess.
