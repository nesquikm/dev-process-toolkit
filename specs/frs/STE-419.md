# STE-419: Enforce the first-turn Socratic contract in /setup {#STE-419}

## Summary

Given exactly the same stimulus, three skills that are supposed to share one contract behave three different ways. Two of them refuse and touch nothing. The setup skill asks nothing at all, then edits the project's configuration file twice and commits the result onto a fresh branch.

The assertion helper flags this as a genuine violation whether or not it is told where the project root is, so it is not an artifact of how the check was scoped. It is a real scaffold-before-ask, which is precisely the bypass shape the first-turn contract was written to prevent.

The inconsistency is the real defect. The toolkit currently has no single answer to what a skill should do when it cannot ask a question, and the skill that resolves it most permissively is the one that runs first in every chain.

## Requirement

`/setup` MUST honor the same first-turn Socratic contract as `/spec-write` and `/brainstorm`: under non-tty stdin its first tool call MUST be an `AskUserQuestion` `tool_use` OR a `RequiresInputRefusedError` raise, and `Write` / `Edit` / `NotebookEdit` before that point MUST be forbidden.

Observed 2026-07-27 on the Linear leg's Phase 8 fixture. Stimulus: the harness autonomous-mode reminder verbatim, verbose pre-baked args covering every question the skill might ask, and **no** auto-approve marker. Result: zero `AskUserQuestion` calls, then two `Edit` calls against the test project's `CLAUDE.md`, then a commit onto a second bootstrap branch. `assertFirstTurnShape` reported `violation tool=Edit index=19` both with and without `projectRoot`.

By contrast `/brainstorm` and `/spec-write` both refused on the identical stimulus and left the tree clean. `/spec-write`'s own closing narration flagged the asymmetry unprompted.

This FR does not change what `/setup` does once it is legitimately allowed to proceed — only what it may do before its first ask or refusal.

## Acceptance Criteria

- AC-STE-419.1: Under non-tty stdin with no auto-approve marker, `/setup`'s first tool call is an `AskUserQuestion` `tool_use` or a `RequiresInputRefusedError` raise; `assertFirstTurnShape` over the captured transcript returns `ok-asked` or `ok-refused`, never `violation`.
- AC-STE-419.2: Under the same conditions, `/setup` performs zero `Write` / `Edit` / `NotebookEdit` calls inside the project root before that first ask or refusal, and the working tree is byte-unchanged if it refuses.
- AC-STE-419.3: A pre-baked-args prompt body that appears to answer every question does NOT by itself authorize `/setup` to skip the ask — a fixture supplies one and asserts the ask-or-refuse outcome still holds.
- AC-STE-419.4: With the sanctioned marker present, `/setup` completes its bootstrap non-interactively via the same mechanism STE-418 establishes, so the two skills agree on what an absent ask tool means.
- AC-STE-419.5: An interactive (tty) `/setup` run is behaviorally unchanged.

## Technical Design

`/setup` needs the same three-branch marker/refusal routing the other two skills already run: byte-grep the prompt body via `check_marker_runtime.ts`, then route through `requireOrRefuse(...)`. The work is to identify every gate site in `/setup` that currently resolves from pre-baked prose and move each onto that routing, plus a first-turn guard that forbids scaffold writes before the first ask or refusal.

Sequencing note: AC-STE-419.4 depends on the mechanism chosen in STE-418. Implement STE-418 first, then adopt it here rather than inventing a second answer-source shape.

The `chore/setup-bootstrap-2` branch observed in the capture is a symptom worth checking during implementation — a second bootstrap branch implies the skill re-ran its branch gate on an already-bootstrapped project.

## Testing

- A Phase-8-shaped stream-json fixture per AC-STE-419.1 / .2 / .3, each asserting the first-turn outcome and the clean tree.
- A marker-present fixture asserting non-interactive completion (AC-STE-419.4).
- Existing interactive `/setup` tests unchanged and green.

## Notes

This is the finding that let the 2026-07-27 run's Phase 1 succeed at all — had `/setup` refused like its siblings, the run would have had no scaffolded project to test against. Fixing it therefore has a hard dependency on STE-418 landing first, or the chain regresses further rather than improving.
