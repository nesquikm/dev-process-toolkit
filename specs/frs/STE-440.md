# Route /spec-write milestone allocation through a single identity dispatcher

## Summary

The milestone-allocation guard in the spec-write skill is one paragraph of roughly nine hundred words. Its opening sentence commands the sequential allocation path, and the tracker-less mint branch is the final clause of that same paragraph. A reader following the paragraph in order reaches the sequential instruction first and can act on it before ever seeing the branch that actually applies.

The plan template compounds this independently. Its scaffolded frontmatter carries a literal sequential milestone key, while the requirement to mint a tracker-less identity lives in an HTML comment below it. Two separate surfaces therefore nudge toward the wrong outcome, and the reported incident shows both nudges landing.

This FR replaces prose routing with code routing. One dispatcher decides the milestone identity for every mode, so skipping the mint stops being a reachable state rather than merely a discouraged one. The skill prose collapses to a single call, which relieves the line budget instead of consuming it.

## Requirement

`/spec-write` must obtain a milestone identity by calling one dispatcher that routes internally by mode, rather than by following per-mode prose branches. In `mode: none` the dispatcher must be structurally incapable of returning a sequential `M<N>` token.

The five existing meta-tests that pin the mode-none branch prose are load-bearing on the current wording. Moving that logic into code makes them assert the absence of what they were written to guarantee, so they must be retired as part of this change rather than added to.

## Technical Design

The dispatcher is a thin router, not a reimplementation. Each branch delegates to the helper that owns that mode today, so the sequential five-way scan, the Epic-key derivation, and the collision-guarded minter all keep their current semantics and their current tests. What changes is that the choice between them becomes a `switch` rather than a paragraph.

The return type is a discriminated result rather than three shapes. `mode: none` is the only branch producing an `id`, and it is the only branch whose caller must write that value into plan frontmatter. Modelling `id` as optional on a single interface keeps the call site to one destructure.

Ordering matters at the call site. The dispatcher must be invoked before any plan or FR file is written, because the tracker-less branch determines the plan filename. This is the current contract for all three branches and is preserved verbatim.

The gate-site invariant in AC-STE-440.4 is the reason this FR does not simply inline three calls at the call site. The prior design routed all three branches through one `requireOrRefuse` call precisely so that no branch could bypass the gate; an off-gate branch is the silent no-op the gate exists to prevent. The dispatcher must sit inside that call's `defaultValue` computation, not around it.

The template change in AC-STE-440.7 is deliberately scoped to removing the misleading default rather than adding a new key. The plan-frontmatter identity key that `mode: none` requires is written by the producer at plan-creation time, and STE-441 owns the probe that enforces it. Scaffolding a placeholder value here would create a third surface to keep in sync.

## Testing

Unit tests cover the dispatcher directly: one per mode asserting the returned shape, plus the equivalence tests in AC-STE-440.3 that pin each branch against the helper it delegates to. The `mode: none` branch is exercised with a seeded ULID so the derived token is deterministic.

The negative case in AC-STE-440.2 is the one worth stating as its own test: no input produces a sequential token under `mode: none`. Asserting the positive shape alone would pass a dispatcher that fell through to the sequential branch on an unexpected input.

AC-STE-440.6 is verified by running the suite. The retired pins fail loudly if the prose change lands without them, which is the intended signal rather than a problem to work around.

Meta-tests over `skills/spec-write/SKILL.md` cover the line cap and the token ceiling. These are existing test shapes in this repo and are extended, not newly written.

## Notes

The line budget is the constraint that shapes this FR. `skills/spec-write/SKILL.md` currently sits at 357 lines against a 358-line cap, and the skills-tree `STE-<N>` token ceiling is at 246 of 246. Any change that adds prose to this file fails the gate. The dispatcher is what makes the change fit: it removes substantially more prose than it adds.

This FR does not change what any mode produces. Linear still allocates sequentially, Jira still derives from the Epic key, and tracker-less still mints. The defect is that the tracker-less branch is skippable, not that it is wrong.
