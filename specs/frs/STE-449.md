# Audit every fixture group's leg roster and resolve the setup 7c contradiction

## Summary

Seven of the eight runtime fixture groups are tracker-agnostic, and only one carries an explicit exemption. If the tracker-less leg simply inherits that default, its runtime-check phase re-proves what the linear leg already proves and adds coverage of nothing.

So before any new group is written, every group's leg roster gets re-derived from what that group actually asserts. The exercise is expected to produce findings rather than merely confirm the status quo.

One case is already known to be live. The setup skill contains two statements about branch templates under tracker-less mode that cannot both hold, and they contradict each other independently of anything the smoke driver does. The contradiction sharpens under this milestone because a tracker-less milestone identity is an opaque minted token with no sequential number for the template to substitute.

Resolving it decides whether one group is legitimately not applicable on the tracker-less leg or is a genuine gap. Those are different verdicts with different meanings, and the vocabulary to express both already exists.

## Requirement

Re-derive the leg roster of all eight canonical fixture groups from what each group actually asserts, and record a rationale per group. Resolve the setup step 7c contradiction, since one group's roster depends on the answer.

The contradiction, verified in-session:

- `plugins/dev-process-toolkit/skills/setup/SKILL.md:190` calls `{type}/m{N}-{slug}` "the single seeded default in both tracker mode and `mode: none`".
- `plugins/dev-process-toolkit/skills/setup/SKILL.md:194` says `mode: none` projects that elected option 1 in step 7b "skip writing; branch automation stays disabled."

Those two lines contradict each other before the smoke driver's pre-baked answers block is considered. Separately, the driver bakes a branch-template answer unconditionally, and under a minted milestone identity the `{N}` placeholder has no referent.

## Acceptance Criteria

- AC-STE-449.1: Each of the eight canonical fixture groups in `CANONICAL_FIXTURE_GROUPS` carries an explicit `legs` roster re-derived from what that group actually asserts, with a one-line recorded rationale per group. {#AC-STE-449.1}
- AC-STE-449.2: The setup step 7c contradiction between lines 190 and 194 is resolved with a stated winner, and the losing statement is corrected rather than left standing. {#AC-STE-449.2}
- AC-STE-449.3: Fixture group 5's outcome on the `none` leg is assigned per AC-STE-449.2's resolution using only the existing `FIXTURE_GROUP_OUTCOMES` vocabulary — `not-applicable` when branch automation is off under tracker-less mode, `not-reached` only if it genuinely did not run. No new outcome token is introduced. {#AC-STE-449.3}
- AC-STE-449.4: Audit findings that fall outside this milestone's scope are recorded in `specs/notes/follow-ups.md` rather than silently absorbed or dropped. {#AC-STE-449.4}

## Technical Design

The audit is per-group and mechanical: read what the group's runtime-check line asserts, determine whether that assertion has meaning under each registered leg, and record the answer. Group 2 is the existing precedent — it is linear-only because the probe it tests is vacuous elsewhere.

Group 5 is the group in question. Its subject is the branch-gate marker contract, so its applicability under tracker-less mode turns entirely on AC.2's resolution. If branch automation is disabled there, the group is not applicable on that leg and saying so is accurate. If the seeded default does apply, the group runs and the template's missing placeholder becomes its own finding.

The distinction between the two outcome tokens is load-bearing and already modeled in the code: collapsing them would either report a phantom gap on every tracker-less run or hide a real gap behind a by-design exemption.

## Testing

Roster assertions live in the existing fixture-group module tests. The audit's own output is the recorded rationale per group, which a meta-test can assert is present and non-empty for all eight.

Any correction made under AC.2 needs its own assertion so the resolved statement cannot silently revert.

Full gate green from the plugin root.

So there is nowhere for the key to be written under tracker-less mode, line 194 is the only reachable behavior, and line 190's "in both tracker mode and `mode: none`" is the false clause. What `/setup` writes does not change for any project in any mode. See `specs/plan/M121.md` § Blast radius.

If implementation finds this analysis wrong — that some path does write the key under tracker-less mode — that is a behavior change to a shipped skill. Stop and surface it rather than absorbing it into a prose fix.

This FR modifies a SHIPPED plugin skill, not a project-local one. That does not change the milestone's `migration: none` verdict, which rests on the absence of convention changes rather than on the work being repo-local.
