# STE-427: Correct the falsified containment and settings-write invariants {#STE-427}

## Summary

Two invariants the threat model states without qualification were measured false during this run. Neither caused damage, but both are load-bearing for how the smoke test reasons about its own safety, so leaving them overstated is worse than the underlying behavior.

The containment claim says the working-directory guard bounds where the children operate and that the operator's other projects are unaffected. Two children wrote files into a directory entirely outside the test project. The cause is benign — children inherit the operator's configuration directory and with it a global instruction that mandates a write at the start of every response — but the claim as written is simply not true, and this is also what makes an unrelated assertion produce false alarms.

The second invariant asserts the child layer denies every write to the project settings file, full-file and append-only alike, and that no child-side merge path exists. That is the stated reason the parent must pre-create the file carrying the complete final allow-list. In this run the child extended it from twenty-nine entries to fifty and said so in its own commit message.

## Requirement

Both documented invariants MUST be restated to match measured behavior, and any safety argument resting on them MUST be re-derived from what actually holds.

Verified 2026-07-27:

- **Containment.** Both the Phase 8 `/setup` and `/brainstorm` children issued writes to `/Users/ns/english/mistakes/inbox/`. Confirmed independently at aggregation time by numeric epoch-mtime comparison against the run-start timestamp: 3 files created inside the run window (14:29:57Z, 14:58:12Z, 15:07:23Z). The cause is inheritance of `CLAUDE_CONFIG_DIR` and the operator's global instructions, not a defect in the guard's own logic — the guard bounds the spawn cwd, which is a narrower claim than the one the prose makes.
- **Settings writes.** Phase 0 and Phase 1 step 6 assert the child model layer "denies ALL `.claude/settings.json` writes — full-file Write AND append-only Edit alike (iter-2 confirmed **no child-side merge path** exists)". The driver wrote 29 entries; the post-setup committed file carries 50. The bootstrap commit body reads: "merged canonical bun allow-list into the pre-existing file (29 entries preserved, 21 added)". Recurrence of a 2026-07-20 observation.

## Acceptance Criteria

- AC-STE-427.1: The containment claim states what the guard actually bounds — the spawn working directory — and no longer asserts unconditionally that the operator's other projects are unaffected.
- AC-STE-427.2: The documentation records that children inherit the operator's configuration directory and may therefore perform writes outside the test project driven by global instructions, naming this as the reason first-turn assertions must be scoped to the project root.
- AC-STE-427.3: The settings-write invariant is restated to match measured behavior, and every argument that cited "no child-side merge path" as its justification is re-derived or withdrawn.
- AC-STE-427.4: The parent-pre-creation rationale is restated on grounds that survive AC-STE-427.3 — or, if it no longer holds, the step is re-justified on its actual merits.

## Technical Design

Documentation-only in the narrow sense, but the second invariant has downstream consequences worth thinking through rather than editing around. If children can extend their own allow-list, then the "reviewable single-file diff" property the threat model claims for the tracked allow-list is weaker than stated: the reviewed artifact is the starting point, not the effective policy.

Implementation should determine whether the child-side merge is intended behavior that the docs never caught up with, or an enforcement gap worth closing. The finding establishes that it happens, not which of those it is — that determination belongs in this FR's implementation, and the outcome may spawn a follow-up.

## Testing

- Byte assertions over the corrected threat-model prose for both invariants.
- A regression case asserting a child's settings-file merge is either observed and documented, or blocked — whichever the implementation determines is correct.

## Notes
