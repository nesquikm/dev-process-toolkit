# The release content approval stops authorising the pull request

## Summary

A release skill asks one question and takes three actions on the answer, the last of which opens a pull request. Its own later step insists that the pull request is a separate decision, and its own rules say the two must never be folded together. The skill already knows the right shape; its wording does not follow it.

## Requirement

The content approval bundles applying the rewrite, committing it, and pushing plus opening a pull request behind a single yes, leaving the middle act with no gate of its own. A later step then states outright that the pull request is not the diff just shown, and asks for a second, separate approval. The skill's own first rule says one approval for the content and a second for what follows, never one for both.

Measured consequence: a release worker had to treat a supervisor's hard stop as authoritative over the skill's own wording, and asked for that reading to be confirmed before acting. A worker following the skill literally pushes and opens a pull request on a yes that was meant for the diff.

That same rule also names the later step by the wrong act — it calls the push-and-open step the merge, when the merge is the step after it. Fixing the prompt alone would leave the rule still wrong.

## Acceptance Criteria

- AC-STE-599.1: The content approval asks only about applying and committing. Its prompt text names no push and no pull request.
- AC-STE-599.2: Opening the pull request is authorised solely by the later step's own approval, which is the only approval that reaches that act.
- AC-STE-599.3: The rule that fixes the two-approval split names the push-and-open step and the merge step correctly, rather than calling one by the other's name.
- AC-STE-599.4: No remaining step's prose implies the content approval authorises a push or a pull request.

## Technical Design

A prose change to one skill file in a sibling repository, touching the content-approval prompt, the rule that states the approval split, and any step text that restates the old bundling. No code, no tests, no toolkit ceremony exists in that tree.

## Testing

Verified by reading: the approval prompt, the rule, and every step that mentions an approval are checked against each other for agreement, and the change is reviewed in the pull request it opens. The target repository carries no gate, drive, or end-to-end command to report counts from.
