# Gate receipts record whether the gate passed and the exact input it graded

## Summary

A gate run leaves a receipt that only says it ran, written before the checks start.
This adds an opt-in outcome record with a key naming the exact input graded.
The key covers the commit, uncommitted changes, toolchain and toolkit versions, gate commands and settings.
With the setting off, the default, gates write exactly what they write today.
No commit or pull request gate reads the outcome record.

## Requirement

Today `recordGateRun` in `adapters/_shared/src/gate_receipt.ts` writes one receipt of `kind: "gate"`, `decision: "ran"` (`GATE_RECEIPT_DECISION`), `evidence: { head }`, before the gate's commands run. The stored `head` is never read back. Later work needs a record that a gate **passed** on a named input. This FR extends the same receipt store (`tracker_receipts.ts` `writeReceipt` / `readSessionReceipts`); it adds no second store, directory or ignore rule.

### The switch

Operator rule and amendment 2, 2026-11-04: nothing here runs by default. `specs/settings.yaml` gains `tracking.gate_outcomes`, closed key set `{enabled}`, the shape of `tracking.token_stats`. It is read through `loadProjectSection(projectRoot, "tracking")`. An absent key or section, `enabled: false`, a legacy tree, a tree with no settings file and any loader refusal all mean off. No legacy home carries the key; `/setup` and every migration leave it unwritten. It enters the AC-STE-706.12 table as a `new` row naming this FR, and `docs/settings-reference.md` documents it. `gate_receipt.ts` loads the settings module by dynamic `import()` only, so a hook importing its evidence readers loads nothing new. That makes `recordGateRun` async: it returns `Promise<string>` where trunk returns `string`. Its one caller, the `gate_receipt.ts` CLI entry, awaits it. This is a declared signature change, not drift; no other caller exists today.

With the switch off:

- `recordGateRun` writes the v2.101.4 receipt, `evidence: { head }`, and never calls `gateReuseKey`.
- The receipt call `gate_receipt.ts <skill> <path>` prints exactly its v2.101.4 stdout, the one `dpt-receipt: ` announcement line, and nothing else.
- No skill issues an outcome call, so `/gate-check`, `/tdd` and `/spec-review` make exactly the tool calls they make on v2.101.4.
- The outcome front door reads the switch first. It exits 0 with empty stdout and stderr and writes nothing, whatever its other arguments.

Everything below describes the switch on.

### The reuse key — new module `adapters/_shared/src/gate_reuse_key.ts`

`gateReuseKey(root, options?)` returns, computed on the spot:

| Field | Value |
|---|---|
| `v` | `1` |
| `head` | `git rev-parse HEAD`, or `null` on an unborn branch |
| `clean` | `true` iff `offendingPaths(root)` in `skip_baseline.ts` returns no path (`git status --porcelain --untracked-files=normal`, the `assertCapturable` rule); this FR exports `offendingPaths` with its body unchanged |
| `worktree` | `worktreeDigest(root)`: `sha256:` over `git diff HEAD --binary --no-ext-diff` (staged plus unstaged; `git diff --cached --binary` on an unborn branch), then, for each path of `git ls-files --others --exclude-standard -z` in byte order, the path, a NUL, and the sha256 of its content. Ignored files are outside the key. |
| `bun` | `Bun.version` (overridable through `options.bunVersion` for tests) |
| `plugin` | `runningDptVersion(options.pluginRoot)` from `dpt_version.ts` |
| `commands` | `sha256:` of the `## Key Commands` section of `<root>/CLAUDE.md` (heading line through the line before the next `## ` heading), or `"absent"` |
| `settings` | `sha256:` of `<root>/specs/settings.yaml` bytes, or `"absent"` |

`reuseKeyDigest(key)` is `sha256:` over the key serialised as JSON with sorted keys. `worktreeDigest` is exported for STE-716. `gateReuseKey` is the toolkit's only reuse-key function: M_fd9a03 composes its per-command key from it and adds no second one.

### The ran receipt

With the switch on, `recordGateRun` evidence becomes `{ head, key, key_digest }`. `head` keeps its value and meaning. The receipt call then prints a second stdout line, exactly `outcome: on`, after the announcement and only once the receipt is written. A refusal still prints nothing on stdout. The hooks read announcements line by line (`announcementsIn` in `templates/hooks/_lib/session.ts`), so the extra line changes no evidence verdict.

### The outcome front door

```
bun run gate_receipt.ts outcome <skill> <path> <pass|fail> [--step <name>=<pass|fail>[:<summary>]]...
```

- Pairs with the latest `kind: "gate"` receipt of this session (`CLAUDE_CODE_SESSION_ID`) for the same subject and checkout root that no `gate-outcome` receipt already references.
- Writes one receipt: `kind: "gate-outcome"`, `subject: gateSubject(skill)`, `decision: "pass" | "fail"`, `evidence: { run, key, key_digest, key_stable, steps }`, where `run` is the paired receipt's `receiptDigest`, `key` is recomputed now, `key_stable` is `key_digest === <paired>.evidence.key_digest`, and `steps` is the `--step` list (`summary` passed through `oneLine`, capped at 200 characters).
- Prints exactly `dpt-gate-outcome: <absolute path> sha256:<digest>` on stdout. It never prints the `dpt-receipt: ` prefix (`RECEIPT_ANNOUNCEMENT_PREFIX`).
- New export `runsGateOutcome(command): boolean`: true only for one plain `bun [run] <absolute path> outcome ...` whose path realpaths to this front door, read by the same `bunInvocation` grammar `announcesGateReceipt` uses. STE-716 classifies with it.
- New `GATE_RECEIPT_REASONS`: `no-run` (no unpaired run receipt), `unknown-outcome` (verdict not `pass`/`fail`, or a malformed `--step`). Every refusal: NFR-10 on stderr, exit 1, empty stdout, nothing written.

### Skill wiring

Each skill runs the outcome call only when its receipt call printed `outcome: on`. With the switch off no such line exists, so the skill issues no outcome call, and its tool calls and output stay as in v2.101.4. The outcome front door's own off-check stays as a second guard.

- `skills/gate-check/SKILL.md` line 9 keeps its trunk text verbatim, including the `gate_receipt.ts gate-check` call and "Invoking this skill is itself the token the commit gate reads." It gains one appended sentence (line count unchanged): only if that call also printed `outcome: on`, after the verdict run the outcome front door with `pass` for GATE PASSED or GATE PASSED WITH NOTES and `fail` for GATE FAILED, one `--step` per deterministic command with its actual result summary. The edit lands in its own commit. The AC-STE-618.8 freeze in `tests/m_2306b6-ste-618-live-proof-gate.test.ts` is then re-based once, under the operator's pre-granted ruling for this milestone: a separate reviewed commit moves `KICKOFF` to the edit commit and adds a `RE-BASED` comment that names the ruling and lists line 9 as the new permitted line. `PERMITTED_LINES` and its pin are unchanged, and the freeze test is green at the re-base commit.
- `skills/tdd/SKILL.md` names the outcome call, under the same `outcome: on` condition on its line 36 receipt call, after § 5 AUDIT (`pass` when the audit returns `status: ok`) and on the Halt path (`fail`).
- `skills/spec-review/SKILL.md` names the outcome call, under the same condition on its line 28 receipt call, after the audit result is parsed (`pass` when `drift_count` is 0 and every traceability row is `done`, else `fail`).

### What does not change

The three blocking hooks keep taking evidence only from the transcript Skill call plus an announced `kind: "gate"` receipt (STE-614, STE-641). An outcome record permits nothing.

## Technical Design

The outcome is a second receipt in the same session store, not an edit of the first: hooks bind a receipt to its announced digest, so rewriting the run receipt would read as tampering. A distinct kind and a distinct announcement prefix keep it out of every evidence reader, which filter on the gate kind and the receipt prefix. Pairing by "latest unpaired run" makes a stray outcome call refuse instead of minting a record no run stands behind. The key is recomputed at the outcome too, so a tree that moved during the gate is recorded as unstable.
