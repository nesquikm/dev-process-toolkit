# The gate reuses a deterministic command's pass only when it recomputes the same key itself

## Summary

With the reuse knob off, its default, the gate runs exactly as it does today.
With it on, the gate still runs, writes its receipt and runs its review.
Inside that run, a command may be skipped when it already passed on identical input.
The gate proves this itself, from a key it computes at that moment.
A reused command reports the stored run's real numbers.
The commit and pull request hooks never read any of this.

## Requirement

### The live key

`adapters/_shared/src/gate_reuse.ts` exports `computeReuseKey(projectRoot, commandText, options?)`. It passes `options` (`bunVersion`, `pluginRoot`) through to `gateReuseKey` unchanged, so tests can stub those two parts; the front door passes none. It returns `null` (no reuse possible) unless every part is readable, and otherwise an object of exactly these keys:

| key | source |
|---|---|
| `gate` | `gateReuseKey(root)` from `gate_reuse_key.ts` (M_7bc805, STE-715): `v`, `head`, `clean`, `worktree`, `bun`, `plugin`, `commands`, `settings` |
| `command_sha256` | `sha256:` of the exact command text |

It returns `null` when `gateReuseKey` throws, when `gate.head` is `null`, or when `gate.clean` is `false` (`offendingPaths` in `skip_baseline.ts` reports a modified, staged or untracked path). A dirty tree never yields a key. `git write-tree` is not used: it hashes the index only.

**One key function.** `gateReuseKey` is the function the M_7bc805 run receipt records. This module composes it and adds only the per-command hash; it reads no `Bun.version`, plugin version or settings bytes of its own. The gate commands come from `CLAUDE.md` `## Key Commands` or `specs/settings.yaml`, both covered by the M_7bc805 key.

**Residual, named.** Git-ignored paths (a local `.env`, dependency directories such as `node_modules`, generated and build output) and runtimes other than Bun are outside the key. A change there can make a reused pass one a fresh run would not produce. The same-session limit below bounds that residual; it is not closed here. `docs/settings-reference.md`, beside `optimizations.gate_commands`, states it in those words.

### The stored pass

A stored pass joins two records: the M_7bc805 `gate-outcome` receipt (pass or fail plus the gate-wide key) and a per-command step receipt this FR adds, because the outcome holds no per-command key or exit status. Step receipts exist only while the knob is on:

- Each command the front door runs with `gate_commands: reuse` writes one receipt through `writeReceipt` in `tracker_receipts.ts` with `kind: "gate-step"`, `adapter: null`, `container: null`, `subject: "dev-process-toolkit:gate-check"`, `decision` `pass` or `fail` from the real exit status, and `evidence: { key, label, exit, summary, duration_ms, run }`, where `run` is the `receiptDigest` of the enclosing `kind: "gate"` run receipt, the same reference the M_7bc805 `gate-outcome` receipt carries. It is announced with `announceReceipt`. `key` is the live key computed before the command ran, or `null` when none was computable; a step with a `null` key is never reused.
- `summary` is `renderTotalsLine` from `gate_capture.ts` when the stack from `detectGate` (`capture_skip_baseline.ts`) parses the output, else the last non-empty output line cut to 200 characters, with every absolute-path token replaced by `<path>`.
- **One account of each step.** With the knob on, which needs `tracking.gate_outcomes` on, the `--step` entries `/gate-check` passes to the M_7bc805 outcome front door are taken from these step results, so the outcome and the step receipts never disagree. With the knob off and the outcome key on, those entries are built as M_7bc805 builds them.
- **No session id.** When `CLAUDE_CODE_SESSION_ID` is unset or empty (a hand run), the front door runs the command, writes no receipt, never reuses, names the missing variable on stderr, and exits with the command's status.

### The knob rides the receipt call

Supervisor ruling 2026-11-04, for operator review: with the knob off, a default `/gate-check` issues no extra tool call. So no skill calls the STE-723 `knob` verb. The knob is read inside the receipt call `/gate-check` already makes, the pattern of STE-715's `outcome: on`:

- When the receipt call for `gate-check` prints `outcome: on`, `gate_receipt.ts` then loads `optimizations_config.ts` by dynamic `import()` and calls `readOptimizations(root)`. When `gate_commands` reads `reuse`, it prints one more stdout line, exactly `reuse: on`.
- With the outcome switch off, the receipt call never loads the module, so its stdout stays the v3.0.0 announcement line alone. A `tdd` or `spec-review` receipt call never prints `reuse: on`.
- A load or read error prints no `reuse: on` line and changes nothing else, as STE-715 degrades key errors.
- This amends AC-STE-715.13, whose two-line form becomes three lines when the knob is effective.

### The decision

`bun run gate_reuse.ts run <root> <label> -- <command text>`:

1. If `readOptimizations(root).gate_commands` is not `reuse` (which includes `tracking.gate_outcomes` being off, per STE-723), or `validateOptimizations` reports any violation, run the command, write no receipt, print no `dpt-reuse:` line, name the off knob on stderr, and exit with the command's status. `/gate-check` never calls the front door in this state; the branch exists for a hand run.
2. Compute the key on the spot. `null` means run.
3. Look for a `gate-step` receipt in this session (`readSessionReceipts` with `CLAUDE_CODE_SESSION_ID`) whose `decision` is `pass`, whose `evidence.key` deep-equals the live key, and whose `run` is referenced by an M_7bc805 `gate-outcome` receipt with `decision: pass` and `key_stable: true`. Both receipts must be announced in this session's transcript with a matching digest, parsed with `parseReceiptAnnouncement` and checked with `receiptDigest` from `tracker_receipts.ts`, never a second parser. The transcript is `<config-dir>/projects/<cwdToSlug(cwd)>/<session id>.jsonl`, via `defaultConfigDir` and `cwdToSlug` from `find_current_session.ts`, read through `firstCopies`.
   - Provenance, mirroring `announcesGateReceipt` (STE-614). An announcement counts only inside the `tool_result` of the Bash `tool_use` that printed it. For the step receipt, that call must pass the new export `announcesGateStep(command)`: one plain `bun [run] <absolute path> run ...` whose path realpaths to this module, read by the same `bunInvocation` grammar. For the outcome receipt, the call must pass `runsGateOutcome` (STE-715). So an `echo`-printed line, a `cd ... &&` chain and a same-named file outside the plugin vouch for nothing, and a hand-written receipt behind one is never reused.
   - A missing transcript, a missing or unvouched announcement, or a digest mismatch means run.
4. On a match, print `dpt-reuse: <label> — <stored summary> (stored run <createdAt>, exit 0, <receipt path>)` and exit 0. Otherwise run the command through `sh -c` under `gateRunTimeoutMs()` from `gate_identity_run.ts`, stream its output, write the `gate-step` receipt, and exit with the command's exit code.

### What is never reused

- The `## Code Review` step of `/gate-check` and every `/gate-check` probe always run, the tracker probes, probe #69 and the date-epoch probes among them. The front door accepts only a command text and refuses a label naming a `NEVER_REUSABLE_STEPS` entry from STE-723.
- `/tdd` and `/spec-review` do not call the front door.

### Hooks and evidence (STE-641 stands)

No hook reads a `gate-step` receipt or a `dpt-reuse:` line. `gateReceiptEvidence` in `gate_receipt.ts` grades only `GATE_RECEIPT_KIND` (`"gate"`), so a `gate-step` receipt never satisfies `pre-commit-gate-check`, `pre-commit-tdd-orchestrator` or `pre-pr-spec-review`. The commit gate still needs the real `Skill` call plus its announced `gate` receipt. `docs/hooks-reference.md`'s sentence naming two evidence-free legs stays true and unchanged.

### Skill wiring

`skills/gate-check/SKILL.md` `## Commands` keeps its trunk lines byte for byte and gains one paragraph after them. Only when the receipt call at line 9 also printed `reuse: on` is each gate command run as `bun run "${CLAUDE_PLUGIN_ROOT}/adapters/_shared/src/gate_reuse.ts" run "<root>" <label> -- <command>`. Otherwise each command runs exactly as the trunk lines say, and no step receipt is written (operator ruling R6). Every sentence of the file that names `gate_reuse.ts` also names `reuse: on`. With the knob on, the `## Reporting` `commands: <P> of <N> pass` row names each reused command with `(reused)` and its stored numbers.

## Technical Design

With the knob off, the gate never reaches the front door, so today's behaviour is kept byte for byte.

With it on, the front door is the only writer of step records and the only reader that may skip a command. It recomputes every key part itself, so nothing stored can claim a key the tree lacks.

A stored pass counts only when this session announced it and its bytes still hash to the announced digest. That is the STE-614 vouching rule, reused rather than copied.

Step records are a separate receipt kind. The hook readers filter on the gate kind, so commit and pull request evidence is untouched.

## Notes
