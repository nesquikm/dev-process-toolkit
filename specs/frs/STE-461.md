# STE-461: Make LocalProvider lock commits conform to the toolkit's own commit-msg hook, and fail safe when a commit is rejected

## Summary

The hook this toolkit installs rejects any commit subject longer than seventy-two characters, and the toolkit also builds its own lock claim subject from a fixed prefix, a minted identifier and the current branch name. The fixed part alone costs sixty-two characters, so the branch may be at most ten, while the toolkit's own branch convention routinely produces names three times that.

The collision stayed invisible because the tracker-less claim step was skipped entirely and a failed claim merely left a dirty tree the run ignored. Making that step a hard entry gate turned a latent defect into one that stops the most-run skill this toolkit ships, on the default configuration of every project it bootstraps.

No test could have caught it. Nothing in the suite ever installs the hook into a lock-provider fixture, and nothing asserts the subject's shape, so the full gate was green over a shipped defect.

This removes the branch from the subject, records it in the message body, and repairs the failure itself rather than only this one trigger. Branch length stops being a variable rather than becoming a larger one.

## Requirement

`LocalProvider.claimLock` builds its commit subject as `chore(locks): claim lock for ${id} on ${branch}`. Fixed overhead is 62 characters — a 29-character prefix, a 29-character `fr_`-prefixed minted id, and 4 characters of ` on `. The shipped `commit-msg` hook rejects any subject over 72, so the branch may be at most **ten** characters. Measured: `main` (4) → 66 PASS; `fix/m1-x` (8) → 70 PASS; `feat/m122-thing` (15) → 77 FAIL; the current branch (35) → 97 FAIL.

Two things must change, and fixing only the first would be fixing the instance rather than the class.

**The subject must stop scaling with the branch.** Not "scale less" — the defect is precisely that a bounded-looking string was assumed bounded. Keying the subject on the 6-character id tail while retaining the branch was measured at **74 characters on this very branch**, so it is still over the cap; that option is rejected on measurement, not on taste.

**The failure mode must stop corrupting the tree.** `claimLock` writes the lock, stages it, then commits. A rejected commit therefore leaves the lock present-and-staged with no witness commit, splitting the two conjuncts step 0.d asserts, and `/implement` refuses at Phase 1 exit. Subject length is only one of many ways to reach that state: a downstream project's own hook, a signing failure, a rejecting pre-commit hook, a full disk. Repairing only the subject leaves the mechanism intact.

**Out of scope, and rejected explicitly:** exempting these commits from the hook with `--no-verify`. It contradicts the deterministic-gates-override principle, it teaches downstream users that bypassing their own gate is normal, and it would leave non-conforming subjects in downstream history where other machinery reads commit subjects. If a toolkit-generated commit cannot satisfy the toolkit's own hook, the repair is to make the commit conform.

## Acceptance Criteria

Conformance is asserted against **both** shipped hooks — `templates/git-hooks/commit-msg.sh` and the `--commitlint` variant, whose config overrides only `header-max-length` and delegates every other rule upstream. RED-producing input: re-introduce the branch — the 35- and 68-character repos fail.
- AC-STE-461.3: Before `writeFileSync`, `claimLock` asserts the subject length is within the cap and throws when it would exceed, naming the subject, its length and the cap. ## Technical Design

**Subject.** `chore(locks): claim lock for ${id}`. Fixed overhead 29; subject length `29 + len(id)` = 58 for a minted id, **constant in the branch name**. Maximum branch length: **unbounded — the branch does not appear**. Headroom at 58 is 14 characters. The residual dimension is `len(id)`, bounded at 29 by the minting contract and 7 for a tracker id; AC.3's pre-write assertion converts that residual from an inherited assumption into a named, enforced bound.

Executed against the real shipped hook with a 68-character branch: proposed subject 58, exit 0, accepted; current template on the same branch, 130, rejected `subject-too-long`.

**Branch preservation.** The branch moves to a body line. The hook validates only the first non-blank non-comment line (`commit-msg.sh:26-53`), so the body is unconstrained. The branch was **already** recoverable independently — the lock file content records `branch: ${branch}`, and smoke sub-fixture 10b already reads it out of the committed blob via `git show`.

**Ownership re-homing, and why not the stricter form.** Removing the branch from the subject removes the ownership conjunct 0.d asserts, which was a deliberate, measured decision recorded in the plan: truncating before ` on <branch>` "dropped the ownership conjunct the tracker arm has as `assignee == currentUser`". Ownership is therefore re-homed to the lock file's own `branch:` line rather than deleted.

The stricter alternative — resolving the claim commit's sha and reading ownership from the committed blob — was considered and rejected on two grounds. Tracker-less locking is documented as **best-effort** (`specs/requirements.md:260`) with cross-tree collision detected, never prevented, so blob-strictness buys rigor for a guarantee the toolkit declines to make. And step 0.d is **prose executed by a model**: resolving the commit that touched a path (not necessarily HEAD by the time 0.d runs) and reading a blob out of it is real git plumbing expressed in prose. This defect came from prose that was too vague; prose that is too intricate is the same failure from the other side. A simple check that is actually performed beats a rigorous one that is approximated.

The residual is narrow and named: a hand-written lock file alone cannot pass, because the witness conjunct still requires a real claim commit for that id. AC.11 state (c) exists precisely because the failure-tolerant rollback can itself fail, and that is the one path that splits the conjuncts.

**Fail-safe ordering.**

1. Build the subject; assert length within cap; throw **before** any write (AC.3) — nothing to roll back.
2. Write lock, stage, commit.
3. On commit failure: capture the original error and git stderr, unstage and unlink the lock, then **rethrow** with the diagnostic (AC.4–AC.6).
4. If cleanup fails, **append** its failure to the original message; never substitute (AC.7).

Unstaging must not assume a reachable `HEAD` — `git reset -- <path>` fails on an unborn HEAD. The index-removal form is chosen and verified by execution rather than by reading.

## Testing

Gate: `bun test` from `plugins/dev-process-toolkit`.

Two executed experiments in throwaway repos carrying the real shipped hook, mirroring the disproof recorded in the milestone's follow-ups:

- **E1 — the instance.** Realistically long branch, real `LocalProvider.claimLock`, hook installed. Assert: subject length, hook exit 0, the commit **lands**, the witness is greppable by the new fence, and the ownership conjunct resolves.
- **E2 — the class.** Legal subject, but a `pre-commit` hook that exits 1. Assert: the exception **propagates**, `git status --porcelain` is **empty**, the lock is absent, and the message names the rejection.

**E2 is what proves the class rather than the instance**, and it is the reason the scope covers the failure mode rather than the subject alone.

**Mutation-siting.** Per the trap recorded in the milestone's follow-ups, every mutation slices its region first, mutates inside it, and aborts when the anchor is absent **from that region** — a first-occurrence anchor in a document whose guards share one house shape lands on the wrong instance and reports a false GREEN.

**A trap specific to this FR.** Fixture group 10's mutation 3 failed by **throwing out of `claimLock`**, and therefore proved nothing about the downstream predicate. Every rollback mutation here must be verified to redden **because the tree was dirty**, not because `claimLock` threw earlier; a mutation that merely relocates the throw is rejected as evidence.

Restores use absolute paths on both sides and are checksum-verified. A mutation that silently no-ops prints identical output on both sides, so byte-change is asserted, not assumed.

## Notes

**This is a shipped-plugin defect, not an M121 defect.** It predates the milestone. What STE-457 changed is its reachability: before it, step 0.d skipped `mode: none` entirely, so a thrown claim left a dirty tree and the run continued. After it, 0.d is a hard entry gate, so the split state refuses at Phase 1 exit. Shipping STE-457 without this repair converts "the tracker-less claim silently never fires" into "the tracker-less claim fires and blocks the run" — which is why the two must ship in the same release.

**Correction to the follow-ups note that filed this.** Its headline says `claimLock` "cannot commit in any project carrying the toolkit's own `commit-msg` hook". Measured, that is conditional on branch-name length: a branch of 10 characters or fewer commits fine; 11 or more is rejected. The defect is real and the arithmetic in the body is exact; the headline overstates the precondition.

**Why the autonomous legs could not catch it.** `/setup` step 6b's hook install is explicitly best-effort, and the model-layer block on `.git/hooks/` writes is expected under `bypassPermissions` — which is how every `claude -p` smoke and conformance leg runs. The legs carry no hook, so the collision never fires there. It bites interactive downstream users only.

**A bypass exists in the hook and is deliberately not used.** A subject whose first byte is `#` is skipped outright by the hook's comment branch, and `git commit -m` defaults to `--cleanup=whitespace`, which does not strip `#` lines. Recorded so a future reader knows the hook is less airtight than it reads, not as a route this FR takes.
