# A skill can tell whether an orchestrator is driving it

## Summary

Nothing readable at runtime tells a skill whether a human typed it or a pipeline invoked it as a step.

The toolkit has two channels and they are disjoint. The marker signalling a non-interactive run is forbidden in orchestrator kickoffs, and the answer block it gates reaches two skills.

Every other repair here needs the distinction. Without it a skill chooses between always stopping, which is the defect, and never stopping, which removes gates a standalone run needs.

## Requirement

A skill invoked as a step of an orchestrated run can determine that fact at runtime, from a signal the orchestrator supplies rather than by inference. The signal is distinct from the existing non-interactive marker, because a driven run may be fully interactive with an operator present throughout. A skill receiving no such signal behaves exactly as it does today.

## Acceptance Criteria

- AC-STE-549.1: A driven invocation and a standalone invocation of the same skill differ in exactly one readable fact, and a skill can branch on it without inspecting its arguments for orchestrator-shaped prose.
- AC-STE-549.2: The signal is distinct from `<dpt:auto-approve>v1</dpt:auto-approve>`. A driven run carries no implication of being headless, and a headless run carries no implication of being driven; the four combinations are each expressible and each asserted.
- AC-STE-549.3: An invocation carrying no signal behaves exactly as today. The existing expectations run unmodified, asserted as an unchanged count rather than by review.
- AC-STE-549.4: `/deliver` supplies the signal on both surfaces it drives: the inline Phase 1 and Phase 2 invocations, and the kickoff text of every Phase 3 worker. A surface that drives a stage without supplying it is a violation of this criterion, not an omission.
- AC-STE-549.5: The signal cannot be forged by prose in a user's own argument. Whatever carries it is checked the way the shipped marker is checked — by a deterministic read, not by the model judging whether it looks orchestrated.
- AC-STE-549.6: Falsifiability — removing the signal from one driven surface makes a stage that reads it behave as standalone there, asserted by a mutation on that surface alone.

## Technical Design

The precedent is `<dpt:auto-approve>v1</dpt:auto-approve>`, read by `check_marker_runtime.ts` as a byte-grep, deliberately not an inference. The driven signal follows that shape: a distinct literal, a distinct reader, no shared truthiness.

`/deliver` supplies it at three sites: the two inline invocations at `skills/deliver/SKILL.md:129` and the Phase 3 kickoff at `:160-176`. The prohibition at `:176` and `:198` is on the auto-approve marker specifically and is not weakened — a driven worker's gates stay live, which is the whole point of keeping the two signals separate.

Consumers read it through one exported predicate rather than each grepping for themselves, so the literal has one owner and a second reader cannot drift from the first.

## Testing

New `tests/m143-ste-549-driven-signal.test.ts`, plus edits where the reader lands.

- AC.1 / AC.2 — a four-case matrix over the two markers: neither, driven only, headless only, both. Assert the predicate's answer for each. The matrix is the assertion: a predicate that returns true whenever any marker is present passes a one-case test and fails here.
- AC.3 — assert the count of pre-existing expectations in every touched suite is unchanged. A rewritten assertion would conceal the regression this criterion excludes.
- AC.4 — read `skills/deliver/SKILL.md` and assert the signal appears at each of the three driving sites, matched line-scoped. A file-wide substring check cannot tell three surfaces apart and would pass with two of them empty.
- AC.5 — feed a prompt body containing the literal inside quoted user prose and assert the reader still resolves it the same way the shipped marker reader would, so the two treat forgery identically rather than differently.
- AC.6 — mutation per driving site: remove the signal from one, assert a stage reading it behaves as standalone there while the other two sites are unaffected.

## Notes

The two signals must stay separate because they answer different questions. Headless asks whether anyone is there to type; driven asks whether the answer is already on the record. A worker spawned by the pipeline is driven and fully interactive at once, and collapsing the two would either silence gates that must stay live or leave this defect unfixed.
