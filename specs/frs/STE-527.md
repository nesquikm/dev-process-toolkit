# The skip baseline belongs to a trunk commit, measured in this checkout

## Summary

The skip baseline is stored under the branch it was captured on, and captured whenever someone calls the capture function with a number. Neither half survives contact with how the number actually behaves.

The count is not a property of the source tree alone. Measured on one commit, in this repository, on the same day: the primary working tree reports fifteen skipped tests and a detached worktree at that identical commit reports twenty-seven. Twelve tests guard on capture fixtures that git deliberately ignores, so they run in a checkout that has them and skip in one that does not. Eight more turn on whether a python documentation tool is installed, and one on an environment variable. The number encodes the machine as much as the code.

A baseline is therefore only meaningful against the commit it was taken at, in the checkout that took it. So the record is keyed by the trunk commit a branch forked from, writable only from a checkout standing on that commit with nothing modified, and stamped with an identity that no clone inherits. A read that cannot prove it is looking at its own checkout refuses instead of subtracting.

## Requirement

The skip baseline is keyed by the trunk commit the branch forked from, is writable only from a checkout standing on that commit with a clean working tree, records which checkout produced it, and refuses comparison across checkouts.

## Acceptance Criteria

- AC-STE-527.1: The store is a versioned envelope — a top-level `version` key, a `checkoutId`, and a `baselines` map keyed by trunk commit sha. A file carrying no `version` key is recognised as the shipped v1 branch-keyed shape and its entries are NEVER read as sha-keyed records. Today `readStore` returns the raw map and the reader indexes it by branch name, so a v1 key and a v2 key are indistinguishable to it; that is what makes silent reinterpretation possible.
- AC-STE-527.2: Capture refuses unless BOTH preconditions hold: `git rev-parse HEAD` equals the sha being captured, and `git status --porcelain` is empty (untracked files included). The refusal carries the NFR-10 canonical shape and names the observed HEAD, the requested sha, and the first three offending paths. Today `captureSkipBaseline(projectRoot, branch, skipped)` accepts any number, at any time, from any tree state.
- AC-STE-527.3: Every record carries a `checkoutId`, and a read whose store id differs from the current checkout's id yields `incomparable` — never `pass`, and never a computed delta. The id is minted once into a git-ignored file under the toolkit-owned tree, so a clone or a fresh worktree has none of its own and mints a different one by construction. Asserted by minting an id, copying the store into a second root, and observing the refusal.
- AC-STE-527.4: Reads resolve the branch's trunk commit through `git merge-base HEAD <trunk>`, where `<trunk>` is the first existing local ref among the shipped `PROTECTED_TRUNKS` constant from `adapters/_shared/src/branch_proposal.ts`. This module composes no trunk literal of its own — the same single-composer rule that already keeps the store path in `dpt_paths.ts`.
- AC-STE-527.5: Write-once per trunk sha is preserved unchanged: a second capture for the same sha returns the standing record with `written: false` and does not move `capturedAt`. Asserted as a REGRESSION guard carried over verbatim from AC-STE-509.4 — the identity this record is keyed by changed, the write-once rule did not, and a rekey is the obvious place to lose it.
- AC-STE-527.6: The v1 records now on disk are DROPPED and named, never migrated. Measured on `.dpt/skip-baseline.json` at 9b420ec: `feat/m133-executable-delivery-decisions: 15`, `feat/m134-reachable-workers: 27`, `fix/m135-epic-binding-convergence: 15`. Two of the three are post-spec counts recorded by hand at step 14, and none of the three can prove which checkout produced it. Re-keying them to their merge-base shas would install known-wrong numbers behind keys that look measured. The migration reports each dropped key by name.
- AC-STE-527.7: The `.dpt/.gitignore` entry that keeps the store untracked is asserted still in force, in the same test that asserts AC.3. A store that starts travelling between clones re-opens exactly the cross-checkout comparison AC.3 exists to refuse, and the two facts are one fact.
- AC-STE-527.8: Both new preconditions are mutation-verified, and each mutation is asserted to have APPLIED before its effect is read. Stubbing the clean-tree check to always-true turns AC.2's assertion red; inverting the `checkoutId` comparison turns AC.3's red. The test names the clause each mutation changed, so a mutation that silently failed to apply is distinguishable from a pin that works.
- AC-STE-527.9: The envelope's own read path is non-vacuous in both directions: an absent file yields no baselines and no crash (today's behaviour, preserved), and a file present but holding a `version` this build does not know is `incomparable` rather than empty. An unknown future version read as "no baseline" would silently downgrade a stricter store.

## Technical Design

The store gains an envelope because the alternative — sniffing whether a key looks like a sha — is a heuristic, and this milestone exists because a heuristic about reachability certified two orders that could not fire. An explicit `version` key makes the v1 shape a fact the reader observes rather than infers.

The `checkoutId` is deliberately the cheapest thing that works: a random id minted once into the git-ignored toolkit tree. It cannot travel through git, which is the whole property required of it. It does not attempt to fingerprint installed tooling — a machine that installs the python documentation tool between capture and read changes eight skip identities, and that case is answered by the named-skip comparison rather than by refusing the whole store.

Trunk resolution reuses `PROTECTED_TRUNKS` rather than hard-coding `main`. The constant already exists and already has two members; a second spelling of it here would agree until a project uses `master`.

The capture preconditions are checked by shelling out to git rather than by a library, because the question is about the real working tree and the toolkit already shells out for every other git fact it needs.

## Testing

The cross-checkout refusal is exercised by copying a written store into a second project root and observing that the read refuses rather than compares — the failure this prevents is a number from one machine grading another, and only a two-root fixture reproduces it.

The clean-tree precondition is exercised with a genuinely dirty tree rather than a stubbed status, in both directions: a modified tracked file and an untracked file each refuse, and a clean tree captures. The untracked case is the one that matters here, because the branch this repository's own flow cuts carries untracked FR files at exactly the moment the old contract said to capture.

The v1 drop is asserted against a fixture holding the three real records above, byte-for-byte, so the test states what was actually on disk rather than a synthetic stand-in.

## Notes

The 15-versus-27 measurement is recorded in the M132 follow-ups memory, which previously carried a different and incorrect mechanism for it. The cause is `.gitignore:13` ignoring `plugins/dev-process-toolkit/tests/fixtures/socratic-first-turn/*.json`, not the presence or absence of FR files; that correction was made before this FR was written and this FR depends on it.
