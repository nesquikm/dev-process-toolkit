# /implement's self-review stops before it edits the FR

## Summary

A self-review finding disagreed with what the FR said about tests.
The run edited the FR to match the code and carried on.
The tracker ticket kept the old text, because implementation never writes descriptions.
Specs are the source of truth, so the code must not rewrite them.
Now a conflict with the FR ends the review round as an escalation.
The report names the FR section, and the spec skill makes the change.

## Requirement

During `/implement` Phase 3, a self-review finding that conflicts with the FR's text escalates instead of editing the FR file.

## Acceptance Criteria

- AC-STE-835.1: `skills/implement/SKILL.md` Phase 3 says that a finding which conflicts with the FR's Acceptance Criteria, Technical Design or Testing section never edits the FR file. The round ends as an escalation that names the FR section and the finding.
- AC-STE-835.2: The escalation emits the capability token `implement_spec_conflict_escalated`, registered in `CANONICAL_CAPABILITY_KEYS` with `spec-write` as its owner, the convention for every token `/implement` emits, and carries a remedy row: run `/spec-write <FR-id>`, which syncs the tracker. The `MUST emit` directive sits in both `/implement` Phase 3 and the `/spec-write` § 7 row, and a test pins the `/implement` one by an anchor, with a mutation control that deleting it turns the test red.
- AC-STE-835.3: `docs/implement-reference.md` § Phase 3 carries the same rule and the reason: an FR edited mid-run leaves the tracker description stale.
- AC-STE-835.4: `bun test` from `plugins/dev-process-toolkit` reports 0 failures, and its skip identities equal the baseline by name.

## Technical Design

Prose plus one registered token. The existing rule that spec changes need approval is cited, not restated.

## Testing

Contract tests read the SKILL and reference text and the key registry.

## Notes
