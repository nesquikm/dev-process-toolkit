# Summary sentences stay short and plain

## Summary

Summaries that people read are often long and dense.
This change adds a plain-language rule to four summary surfaces.
Each sentence states one idea in twenty words or fewer.
The gate now rejects a long sentence in an FR summary.
Report lead-ins get the same check when a report is graded.
Acceptance criteria and design sections keep their full detail.

## Requirement

- **One rule, stated once.** A "plain sentences" rule, adapted from ASD-STE100 at roughly 80% strictness, lives in the prose-altitude doc: one idea per sentence; at most 20 words per sentence; active voice; one term for one thing; no idioms; no claim absent from the body being summarized.
- **Four surfaces, human-facing only.** The rule binds the FR `## Summary`, the prose lead-in above a `stage-status-block`, the PR body `## Summary`, and the one-sentence explanation of a code-reviewer `CONCERN` line. Each surface points at the rule; none restates it.
- **Out of scope, explicitly.** `## Requirement`, `## Acceptance Criteria`, `## Technical Design`, `## Testing`, `## Notes`, plan prose, and skill/agent instruction prose are untouched. Precision there is load-bearing and must not be traded for readability.
- **Deterministic where the text lives in a file.** The FR `## Summary` gets a `sentence_cap` rule inside the existing `fr_summary_altitude` probe — no new probe id. The rendered-report verifier gets the matching lead-in check. The PR body and review headlines are guidance only (no file to grade).
- **No retroactive red.** FRs introduced before the cap ships are spared visibly, the same way word caps were.

## Acceptance Criteria

- AC-STE-661.1: `docs/prose-altitude.md` carries a `## Plain sentences` section listing exactly the six rules named in the Requirement and naming the four surfaces it binds; a test asserts each rule and each surface by text.
- AC-STE-661.2: Each of the four writer surfaces carries one line pointing at `docs/prose-altitude.md` § Plain sentences — `skills/spec-write/SKILL.md` § 0b Summary guidance, `docs/stage-status-block.md` (lead-in rule), `skills/pr/SKILL.md` (body `## Summary`), `agents/code-reviewer.md` (`CONCERN` explanation); a test asserts all four pointers.
- AC-STE-661.3: A new pure module `adapters/_shared/src/plain_sentences.ts` exports `PLAIN_SENTENCE_WORD_CAP = 20` and `longSentences(lines)`, which ends a sentence at `.`, `!`, `?` or `;` followed by whitespace or end of text, and at a blank line; tokens such as `v2.46.0`, `e.g.x` and `and/or` do not end a sentence; it returns one row `{ line, words }` per sentence over the cap, anchored at the line holding the cap-crossing word.
- AC-STE-661.4: `RuleName` in `scan_fr_summary_altitude.ts` gains `sentence_cap`; the `Summary` row of `SECTION_RULES` lists it and the `Technical Design` and `Notes` rows do not.
- AC-STE-661.5: On an active FR fixture, a `## Summary` with one 21-word sentence yields exactly one `sentence_cap` row at the crossing line; a 20-word sentence yields zero; a 30-word sentence wrapped over two lines anchors on the line holding word 21; fenced content is not counted.
- AC-STE-661.6: `FR_SENTENCE_CAP_EPOCH` is a new exported constant set to midnight UTC of the release date; `runFrSummaryAltitudeProbe` classifies `sentence_cap` rows against it through `classifyFrProvenance` — `legacy` is dropped and named in `grandfathered`, `undecidable` is `warning`, `fresh` is `error` — while `word_cap` keeps `FR_WORD_CAP_EPOCH` and the four per-line rules stay ungrandfathered.
- AC-STE-661.7: `verifyStageReportAdoption` refuses a report whose narration lead-in (cap-exempt sections excluded) holds a sentence over `PLAIN_SENTENCE_WORD_CAP`, the reason naming the line and the word count; the same report with that sentence at 20 words grades clean on this rule.
- AC-STE-661.8: `skills/gate-check/SKILL.md` probe #67 names `sentence_cap` in the closed rule union and its rule count, and `docs/stage-status-block.md` lists the lead-in sentence rule with its adoption-rule count updated; every existing test pin on those sentences is updated in the same commit, and `bun test` finds no stale count.
- AC-STE-661.9: Mutation-verified: removing `sentence_cap` from the `Summary` row turns the AC-STE-661.5 test red, and removing `;` from the terminator set turns a dedicated semicolon test red; each mutation is asserted to have applied before its test runs.
- AC-STE-661.10: Dogfood: `longSentences` over this FR's own `## Summary` returns zero rows, and the measured longest sentence word count is recorded in `## Notes`.
- AC-STE-661.11: `bun test` from `plugins/dev-process-toolkit` reports 0 failures, and its skip identities are identical to main's by name.

## Technical Design

One pure splitter module serves both graders, so the FR scanner and the report verifier cannot disagree on what a sentence is. The scanner gains one rule id and one table entry, following the word-cap precedent; it accumulates non-fenced Summary text per file and asks the splitter for long sentences. Grandfathering reuses the provenance classifier with a new epoch, because a cap shipping now must not red FRs written since September. The report verifier calls the same splitter over narration lines only.

## Testing
