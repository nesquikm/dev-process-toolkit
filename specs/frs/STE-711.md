# An upgrade step moves every setting into the settings file

## Summary

Existing projects keep their settings in CLAUDE.md and three separate files.
This change adds an upgrade step that moves every one of them into the settings file.
It then removes each old copy, so no setting lives in two places.
It previews the full change and applies it only after an explicit yes.
A second run changes nothing, and a leftover old copy shows up as pending.
Older plugins keep their guards through a small generated block in CLAUDE.md.

## Requirement

A migration registry entry `settings-file` in `adapters/_shared/src/migrations/entries/settings_file.ts`, `introduced_in: "3.0.0"`, `kind: "script"`, `requires_explicit_approval: true`, registered last in `MIGRATIONS`. The entry file is new. Its retired path literals, and the closed list of shipped template comment blocks below, are added to the existing `migrations/legacy_paths.ts` (STE-391), which this FR extends.

**Detect** reads `detectSettingsSource` (STE-706) and never throws. It applies in three cases, with one `file:line` evidence line per finding:

- Move: no settings file, and the source is `legacy`.
- Cleanup: a settings file exists beside a leftover legacy home, that is source `both`. A leftover is a moved CLAUDE.md section carrying a recognised key, the standalone `milestone_scan_fetch:` line, or one of the three retired files. The `## Testing Conventions` `Layout:` bullet is not moved in 3.0 and is never a leftover (STE-706).
- Stub repair: a settings file in a tracker mode whose CLAUDE.md stub slot is missing, duplicated or not byte-equal to `renderTrackingStub`, or a stub slot left under `mode: none`.

A key line is a line the section's own v2.101.4 reader parses as a key, by that reader's line pattern; under `## Release Files` it is the fenced YAML block. For the standalone `milestone_scan_fetch:` home it is any line starting `milestone_scan_fetch:` at column 0, whatever the value. Its value is parsed as `readMilestoneScanFetch` parses it: `true` only for the literal `true`, `false` for anything else. A recognised key line holds a key in its section's closed set (STE-706). A key line outside the closed set is unrecognised.

Structural lines of the `## Task Tracking` span are never refused: blank lines, the `### Linear` and `### Jira` heading lines, and the shared stop paragraph. Both adapter headings count, active or not, because v2.101.4 tolerates an inactive adapter's sub-section (`docs/patterns.md` § Workspace binding sub-sections). Recognised key lines of an inactive sub-section move into `task_tracking.<that adapter>`, as the active one's do, so `readWorkspaceBinding` for that adapter returns the same value before and after. The stub renders only the active adapter.

Detect lists each unrecognised key line, and each other line of the `## Task Tracking` span that is neither a key line nor structural, as its own `file:line` evidence line. A `workspace_url:` line under `### Linear` is an unrecognised key line, and a prose line there is neither. The move refuses while any such line exists (step 0). So does a `###` heading other than `### Linear` or `### Jira`, such as `### Notes`, with every line under it. Trunk probe #21 skips everything after the first `###` line, and `docs/patterns.md` told users to keep workspace metadata in a sub-section, so such trees are green on v2.101.4. The refusal therefore names a destination: move the line to a prose section outside `## Task Tracking`, whose bytes the move keeps.

Shipped template comment blocks. Every v2.x `templates/CLAUDE.md.template` carried HTML comment blocks that tell the user or the model to edit a moved section: the Task Tracking, `milestone_scan_fetch`, Verification, Orchestration, Docs, Token Stats and Release Files blocks. Left in place after a move, their advice recreates a second home. `legacy_paths.ts` gains `LEGACY_TEMPLATE_COMMENT_BLOCKS`, a closed list of every distinct text of those blocks shipped in a v2.x template, from `<!--` to `-->`. Each entry names the first and last release that shipped it, and the commit of that last release. A block in CLAUDE.md matches only when byte-equal to an entry. Detect lists every other HTML comment block that names a moved heading or a moved key, as informational `file:line` evidence. That evidence never refuses, and never by itself makes detect apply.

**Apply (move)**, in one pass, on the bytes the detector read:

0. Refuse in NFR-10 shape, writing nothing, when detect listed an unrecognised key line, or a line in the `## Task Tracking` span that is neither a key line nor structural. The refusal names each line and its destination, a prose section outside `## Task Tracking`, so the preview shows what must be moved by hand first. Refuse the same way when `specs/settings.yaml` is a foreign file (STE-706), naming it and asking the operator to rename it; the move never overwrites it. No line is ever dropped silently. The `## Task Tracking` span is the stub slot after the move, and a kept line there would drift from the render.
1. Build the settings from the loader's legacy reading and write `specs/settings.yaml` through the settings serializer of STE-710, with `schema_version: 1` and `min_dpt_version: 3.0.0`.
2. Remove from CLAUDE.md only the recognised key lines it moved, from `## Task Tracking` with its `### Linear` / `### Jira` sub-sections, `## Verification`, `## Docs`, `## Orchestration`, `## Token Stats` and `## Release Files`, plus the standalone `milestone_scan_fetch:` line. Replace the first block matching `LEGACY_TEMPLATE_COMMENT_BLOCKS` with one pointer comment, `SETTINGS_COMMENT_POINTER` in `legacy_paths.ts`: `<!-- Project settings live in specs/settings.yaml. Edit them there. -->`. Remove every later matching block. A comment block that matches no entry stays in place, byte-identical, and the preview names it. When such a kept block names a moved heading or a moved key, the move puts one `SETTINGS_COMMENT_POINTER` line directly after it, unless that line is already the pointer (review 4, R4-7). This is additive and deletes no user text, and it holds where the block's heading was emptied too, so a later "turn on token stats" is not sent back to a moved heading. A second run therefore inserts nothing. Every other line stays under its heading, byte-identical and in order. A moved heading whose remaining body holds only blank lines and HTML comment blocks, matched or not, loses its heading line and its blank lines. A pointer comment there goes with it, since `## Project Settings` already names the file. An unmatched block there stays in place, byte-identical, and the preview names it. CLAUDE.md is model-written from the template, so a block one byte off its entry still empties its heading. On the v2.101.4 template the first matched block sits in `## Commit Convention`, which keeps prose, so exactly one pointer survives there; a tree whose matched blocks all sit in emptied headings ends with none, which is harmless. A heading that keeps any other line stays, holds no recognised key, and so is no legacy home (STE-706).
3. Insert `## Project Settings` with the pointer paragraph where the first removed section stood, else after the first top-level section. In a tracker mode the binding stub, rendered from the new settings file, follows it directly.
4. Shared container: move the stop paragraph into `## Project Settings`, raise `min_dpt_version` to at least `3.0.0` in the settings file and so in the stub, and re-render the paragraph through `renderSharedTrackerSentinel` for that floor.
5. Delete `specs/tracker-config.yaml`, `.dpt/video/config.yaml` and `.dpt/video/style.yaml` when present.

What stays in CLAUDE.md, byte-identical and in order: the `/setup` generation marker, `## /setup audit`, `## Key Commands` with its gating-rule prose, the whole of `## Testing Conventions` with its `Layout:` bullet, every comment block that matches no listed template block, every other prose section, the new `## Project Settings` section and the stub.

**Apply (cleanup)**: a leftover whose values deep-equal the settings file's is removed: its CLAUDE.md key lines by step 2's rule, or its file. A leftover whose values differ refuses in NFR-10 shape, naming both homes and each differing key path, and writes nothing. **Apply (stub repair)**: the stub slot is re-rendered, or removed under `mode: none`.

Never read or written: `.dpt/.env`, `.claude/settings.json`, the user's `userConfig`. Older registry entries that read CLAUDE.md run first by registry order, so a 2.x tree is brought current on its legacy home before this entry moves it.

**Stale plugin caches.** A pre-3.0 client reads only CLAUDE.md, and three things reach it there. The pointer paragraph tells its model to stop. The binding stub keeps its hooks guarding: a 2.x `pre-tracker-write-gate` reads the stub's `### Linear` / `### Jira` declaration exactly as before. On a shared container the stub carries the raised `3.0.0` floor, so that hook's own floor check refuses a tracker write from a pre-3.0 client. Every 3.x loader enforces the settings file's `min_dpt_version` as well. The stub is removed in 4.0, when NFR-2 allows it.

## Technical Design

The entry is a thin composition. Detection reuses the loader's non-throwing source decision, and the write reuses the settings serializer. The CLAUDE.md edit removes only key lines, located by the legacy module's own line parse, so detection and removal cannot disagree. Prose stays, and an unknown key refuses. Shipped template comments are matched byte for byte and removed, so no stale advice recreates a second home.

Cleanup compares values, not bytes, and refuses rather than choose between two different answers. Stub repair re-renders from the settings file, which the stub never outranks.

Older CLAUDE.md fixes apply first, by registry order.

The explicit-approval flag keeps the move out of auto-approve runs, because it rewrites a file a person edits.
