# A retrospective can propose a settings change the operator must approve

## Summary

A retrospective often skips a rule because the project has not turned on the data it needs.
Today the operator must work out which setting to change by hand.
This lets the retrospective propose that one change, with the evidence that motivated it.
The change is applied only after an explicit yes from the operator.
It can only turn on a setting from a fixed list, so it never weakens a gate.

## Requirement

Operator rule, 2026-11-04: the toolkit's default behaviour does not change, and every optimization is a settings change the user approves after `/retro`. This FR is that approval path. It is the only path by which `/retro` changes a file other than its report.

### The proposable set

A new module `adapters/_shared/src/retro_proposal.ts` exports `PROPOSABLE_SETTINGS`, a closed table. Each row names one key, the one value it may propose, and the rule outcome that justifies it:

| Key | Proposed value | Proposed when |
|---|---|---|
| `tracking.token_stats.enabled` | `true` | `cost_per_changed_line` skipped, or the scope resolved to no session, with a reason naming `tracking.token_stats off` |
| `tracking.tool_calls.enabled` | `true` | a timeline rule skipped with a reason naming `tracking.tool_calls off` |
| `tracking.gate_outcomes.enabled` | `true` | `slow_gate_run` or `gate_rerun_unchanged_key` skipped with a reason naming `tracking.gate_outcomes off` |

Every proposed value turns a recording on. The table holds no gate, threshold, review or approval key, and no `false` value. The row shape is closed: a `tracking.<name>.enabled` key with the value `true`, or, once M_fd9a03 ships, an `optimizations` knob from `OPTIMIZATION_KNOBS` with the value `reuse`. A row outside that shape is refused when the module loads. STE-723 adds the one reuse row; any other row needs its own FR.

### propose

`bun run retro_proposal.ts propose <projectRoot> <report-file>` is read-only. It reads the report through `parseRetroReport` (STE-719) and the settings through `loadProjectSettings`. It prints nothing and exits 0 when no row applies, when every applicable key is already on, or when the settings source is not `settings`. Otherwise it prints one `set <key>: <value>` line per row, one `because <rule id> <disposition>: <reason>` line per row, then `digest=sha256:<hex>`. The digest covers the settings file bytes and the printed rows.

### apply

`bun run retro_proposal.ts apply <projectRoot> <report-file> <digest>` recomputes the proposal. A digest that no longer matches refuses in NFR-10 shape and writes nothing. On a match it writes each row's key through `writeProjectSettings` (STE-710) and nothing else. For the `tracking.tool_calls.enabled` row it then calls `register` in `capture_registration.ts` (STE-716), in the same act. Preconditions of both writes are checked before either write: a registration that would refuse leaves the settings file unchanged too. `apply` never commits.

### The gate

`skills/retro/SKILL.md` runs `propose` after printing the rule table. When it prints, the skill asks its own `AskUserQuestion`: apply the shown change, or leave settings unchanged. Leaving settings unchanged is the default. The question follows the `requires_explicit_approval` rail of `docs/upgrade-reference.md`: the auto-approve marker never answers it. A driven run, or a run without an interactive operator, prints `settings proposal not applied — run /dev-process-toolkit:retro to review it` and never calls `apply`. Only an explicit approval calls `apply`.

`retro.ts` never imports this module, and the report schema is unchanged.

## Technical Design

The proposal is derived from the saved report, never from a second evaluation, so it can only cite what the report already says.

The table is closed and holds only turn-on values for recording keys, plus the one reuse knob. A proposal therefore cannot reach a gate.

The digest binds the approval to the bytes the operator saw. A settings change in between makes the apply refuse rather than write something unseen.

Capture registration rides the same approval, because the key alone records nothing.
