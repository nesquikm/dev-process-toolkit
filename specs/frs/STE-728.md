# A retrospective can propose a settings change the operator must approve

## Summary

A retrospective often skips a rule because the project has not turned on the data it needs.
Today the operator must work out which setting to change by hand.
This lets the retrospective propose that one change, with the evidence that motivated it.
The change is applied only after an explicit yes from the operator.
It can only turn on a setting from a fixed list, so it never weakens a gate.

## Requirement

Operator rule, 2026-11-04: the toolkit's default behaviour does not change, and every optimization is a settings change the user approves after `/retro`. This FR is that approval path. It is the only path by which `/retro` changes a file other than its report.

### The proposable set

A new module `adapters/_shared/src/retro_proposal.ts` exports `PROPOSABLE_SETTINGS`, a closed table. Each row names one key, the one value it may propose, and the rule outcome that justifies it:

| Key | Proposed value | Proposed when |
|---|---|---|
| `tracking.token_stats.enabled` | `true` | `cost_per_changed_line` skipped, or the scope resolved to no session, with a reason naming `tracking.token_stats off` |
| `tracking.tool_calls.enabled` | `true` | a timeline rule skipped with a reason naming `tracking.tool_calls off` |
| `tracking.gate_outcomes.enabled` | `true` | `slow_gate_run` or `gate_rerun_unchanged_key` skipped with a reason naming `tracking.gate_outcomes off` |

Every proposed value turns a recording on. The table holds no gate, threshold, review or approval key, and no `false` value. The row shape is closed: a `tracking.<name>.enabled` key with the value `true`. A row outside that shape is refused when the module loads. M_fd9a03 widens the shape by one case in its own FR: STE-723 admits an `optimizations` knob from its `OPTIMIZATION_KNOBS` with the value `reuse`, and adds the one reuse row. Any other row needs its own FR.

### propose

`bun run retro_proposal.ts propose <projectRoot> <report-file>` is read-only. It reads the report through `parseRetroReport` (STE-719), the home through `settingsWriteSource`, and each row's current value through its own section read: `loadProjectSection(projectRoot, "tracking")` for the three `tracking` rows (v3.0.0 validates per section, so a malformed unrelated section does not hide a proposal). It prints nothing and exits 0 when no row applies, when every applicable key is already on, when the settings source is not `settings`, or when a section read it needs refuses. Otherwise it prints one `set <key>: <value>` line per row, one `because <rule id> <disposition>: <reason>` line per row, then `digest=sha256:<hex>`. When the `tracking.tool_calls.enabled` row is printed and `git check-ignore` does not report `.claude/settings.local.json` ignored, it also prints `add .gitignore: .claude/settings.local.json` before the digest. The digest covers the settings file bytes, the `.gitignore` bytes and the printed lines.

### apply

`bun run retro_proposal.ts apply <projectRoot> <report-file> <digest>` recomputes the proposal. A digest that no longer matches refuses in NFR-10 shape and writes nothing.

The approval is checked in code, not in prose (supervisor ruling 2026-11-04, for operator review). A model can call `apply` with a digest it read, so a digest alone proves nothing. Before any write, `apply` reads this session's transcript at `<defaultConfigDir()>/projects/<cwdToSlug(projectRoot)>/<CLAUDE_CODE_SESSION_ID>.jsonl`, with `defaultConfigDir` and `cwdToSlug` imported from `find_current_session.ts`, the shipped module; it depends on no M_fd9a03 module. It reads records through `firstCopies` (`templates/hooks/_lib/session.ts`) and needs all three of these, in order:

1. A real propose. A Bash `tool_use` that `runsRetroProposal(command, "propose")` accepts: one plain `bun [run] <absolute path> propose ...` whose path realpaths to this module, read by the `bunInvocation` grammar `announcesGateReceipt` uses. So an `echo`, a `cd ... &&` chain or a same-named file elsewhere does not count. Its `tool_result` must hold the line `digest=<the given digest>`.
2. A real answer. After that result, an `AskUserQuestion` `tool_use` whose question text holds the same digest line, and whose `tool_result` selects the option labelled exactly `Apply the shown change`. The verdict is the shipped `perQuestionConsent(questions, label, names, answer)` of `join_consent_ownership.ts`, the one per-question consent rule the tracker-write hook and the live grader already share, called with `label` `Apply the shown change` and `names` true for a question holding `digest=<the given digest>`. Only its answer lookup is new: an exported `askAnswerTo(record, block, question)` in `retro_proposal.ts` with the two arms of `answerTo` in `templates/hooks/_lib/hooks/pre-tracker-write-gate.ts`, read in that order: the record's `toolUseResult.answers[question]`, else the harness sentence `"<question>"="<answer>"` in the `tool_result` text. It carries a `Twin:` comment naming that hook function, which is not edited. An `is_error` result, a result naming another question, or a typed answer other than the exact label is no approval; the `Adopt` typed-answer arm of `perQuestionConsent` cannot fire, since the label is not `Adopt <KEY>`.
3. This call. The `apply` command runs after that answer.

A missing transcript, an unset session id, a missing step, a step out of order, another digest or another label refuses in NFR-10 shape and writes nothing. This is stronger than the `/upgrade` rail, whose approval lives in skill prose. That matters here, because `apply` is a second model-callable writer of `NEW_KEYS` keys, beside the closed `set` verb of STE-710.

On a verified approval it runs in this order:

1. Check. For the `tracking.tool_calls.enabled` row, call `checkRegisterPreconditions(root, { settingOn: true })` (STE-716), so the check sees the setting as the next step will leave it. A not-ignored refusal is cleared only by a printed `add .gitignore:` line. Any other refusal stops `apply` in NFR-10 shape before any write.
2. Write each row's key through `writeProjectSettings` (STE-710). The writer validates the whole merged file before it writes, so a malformed section anywhere in the file refuses `apply` here, before any byte is written, and the rollback below has nothing to restore. The writer rewrites CLAUDE.md only when the binding stub's render changes; no proposable key enters the stub, so `apply` never writes CLAUDE.md, the `## Project Settings` pointer line included.
3. Append the printed `.gitignore` line, when one was printed, to `<projectRoot>/.gitignore`, creating the file if absent. This is the only `.gitignore` edit, and it is part of the diff the operator approved.
4. For the `tracking.tool_calls.enabled` row, call `register`. If it refuses or throws, restore the settings file, `.gitignore` and `.claude/settings.local.json` to their prior bytes, deleting any of them that did not exist before, and refuse.

`apply` writes nothing else and never commits.

### The gate

`skills/retro/SKILL.md` runs `propose` after printing the rule table. When it prints, the skill asks its own `AskUserQuestion`. The question text repeats the printed `digest=` line, and its two options are `Apply the shown change` and `Leave settings unchanged`, the default. The question follows the `requires_explicit_approval` rail of `docs/upgrade-reference.md`: the auto-approve marker never answers it. A driven run, or a run without an interactive operator, prints `settings proposal not applied — run /dev-process-toolkit:retro to review it` and never calls `apply`. Only an explicit approval calls `apply`.

`retro.ts` never imports this module, and the report schema is unchanged.

## Technical Design

The proposal is derived from the saved report, never from a second evaluation, so it can only cite what the report already says.

The table is closed and holds only turn-on values for recording keys, plus the one reuse knob. A proposal therefore cannot reach a gate.

The digest binds the approval to the bytes the operator saw, the ignore line included. A settings change in between makes the apply refuse rather than write something unseen.

Capture registration rides the same approval, because the key alone records nothing. The approval is read back from the transcript, so a model holding the digest cannot apply on its own.
