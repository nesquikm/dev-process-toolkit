# The Epic close checks that every listed child belongs to the Epic

## Summary

Closing a shipped milestone's Epic runs four checks first.
The last check reads the Epic's children and needs every one to be done.
A child row that names no parent at all still passes that check today.
So any list of finished tickets can close an Epic it has nothing to do with.
This fix refuses a row unless it names this Epic as its parent, and pins three smaller gaps beside it.

## Requirement

### Steps to reproduce

1. Build two sibling repositories that share a Jira project, with an archived plan for the Epic-keyed milestone `M_GK_85`, a shipped stamp and a matching CHANGELOG heading.
2. Save a children listing whose rows are done but carry no `fields.parent` (also: `parent: null`, `parent: {}`, `parent: "GK-99"`).
3. Run `bun run adapters/_shared/src/epic_close.ts <projectRoot> GK-85 --children <listing>`.

### Expected

The front door refuses, naming each row whose parent is missing or not `GK-85`, and writes no receipt.

### Actual

It exits 0 and writes an `epic-close` receipt. Only a row whose `fields.parent.key` is a string naming another Epic is refused.

## Acceptance Criteria

- AC-STE-701.1: Regression: `tests/m_9261c7-STE-701-epic-close-parent.test.ts › a child row with no parent proves nothing` fails before the fix and passes after it.
- AC-STE-701.2: Check (d) of `epic_close.ts` accepts a row only when `fields.parent.key` is a string equal to the Epic key, compared without case. A row whose parent is missing, `null`, an object without a string `key`, or a bare string is refused in the NFR-10 shape, naming the row key and that its parent is missing, and no receipt is written.
- AC-STE-701.3: The refusal for a row that names another Epic is unchanged, and a listing whose rows all name the Epic still writes the receipt.
- AC-STE-701.4: `skills/ship-milestone/SKILL.md` post-ship step 3 names the children query: JQL `parent = <P>-<N>` with `parent` among the requested fields.
- AC-STE-701.5: `isStatusOnlyTransition` in `join_consent_ownership.ts` returns true only when `issueIdOrKey` is a string and `transition` is present, with no key outside the allowed set. Unit cases: `{cloudId}` and `{cloudId, issueIdOrKey}` return false; `{cloudId, issueIdOrKey, transition}` returns true.
- AC-STE-701.6: One test drives `pre-tracker-write-gate` and `shared_tracker_live_grader.ts` on the same session, with the `epic-close` receipt rooted in the session's other bundle root, and asserts both give the same verdict on the Epic transition.

- AC-STE-701.8: Removing the parent requirement, or either new conjunct of `isStatusOnlyTransition`, turns at least one named test red.
- AC-STE-701.9: `bun test` from `plugins/dev-process-toolkit` reports 0 failures, and its skip identities equal the trunk baseline by name.

## Technical Design

### Root cause

Check (d) collects foreign rows only when `fields.parent.key` is a string that differs from the Epic key. A row with no readable parent falls through as neither foreign nor proven, so it counts as a done child.

The fix inverts the test: a row is proven only when its parent key equals the Epic key; every other row is refused, with missing and foreign parents named apart. The status-only predicate gains its two presence conjuncts. The parity test reuses the STE-699 two-root fixture.

## Testing

The verifier's four row shapes become table cases through the shipped front door, beside the existing foreign-parent and own-children legs. Unit cases for the predicate, one hook-and-grader parity case, and mutation controls.

Origin: verified M_a5dc12 follow-ups. The predicate gap was found not exploitable and the two roots do not diverge today; both are pinned so they stay that way.
