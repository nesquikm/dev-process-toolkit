# /ship-milestone reads the codename instead of asking

## Summary

The release ceremony stops prompting for a codename.
It takes the override flag when one is given, and otherwise the codename the plan already records.
Only for a plan written before the key existed does it compose one from the milestone goal and feature titles.
The release approval shows the codename and where it came from, but never asks about it.

## Requirement

- **Precedence.** Flag, then plan key, then composed — every source passes the shared validator.
- **No prompt.** The "Enter milestone codename" prompt and its re-prompt loop are removed.
- **Bounded compose.** A composed value that fails validation is recomposed at most once, then the run refuses; no placeholder is ever written.
- **Visible, not asked.** The approval preview names the codename and its source.
- **Writer refuses.** The release writer refuses an invalid `--codename` before touching any file.
- **Recorded.** A composed codename is written into the plan with the release.

## Acceptance Criteria

- AC-STE-658.1: `skills/ship-milestone/SKILL.md` step 3 is titled "Resolve codename" and states the precedence `--codename` > plan `codename:` (read via the `milestone_codename.ts` front door) > composed from the plan Goal and FR titles; the string `Enter milestone codename` appears nowhere under `plugins/dev-process-toolkit/skills/`.
- AC-STE-658.2: Step 3 states that a plan whose `codename:` reads valid ships with that value and no question, and that `--codename` overrides it.
- AC-STE-658.3: Step 3 states that, for a plan with no key, the composed value is checked through the front door, recomposed at most once on failure, and then refused in the NFR-10 shape — never prompted for and never written as a placeholder.
- AC-STE-658.4: The step-6 release approval preview includes a `Codename: <value> (source: flag|plan|composed)` line, and the approval's options contain no codename edit.
- AC-STE-658.5: `release_config.ts` validates `--codename` through `validateCodename`; for each of the four rule violations it prints the NFR-10 envelope, exits 1, and leaves every release file byte-identical.
- AC-STE-658.6: When the codename was composed, the release commit sets the plan's `codename:` to that value, alongside its `shipped_in:` stamp.
- AC-STE-658.7: The argument hint and the flags line describe `--codename` as an override of the plan's codename (no longer "skip prompt"), and `tests/ship-milestone-shape.test.ts` and `tests/m141-ste-545-release-writer-door.test.ts` pin the new wording instead of the retired prompt.

## Technical Design

Rewrite step 3 of the skill around the front door from the codename FR. `release_config.ts` calls `validateCodename` where it parses `--codename`, before any write, refusing through its existing NFR-10 path. The plan stamp that writes `shipped_in:` gains the `codename:` write for the composed source only; a plan or flag source leaves the key untouched. The preview line reuses the step-6 preview block.

## Testing

`release_config.test.ts` gains the four refusal legs with a byte-identity check on every release file. The two shape tests swap the prompt pin for the precedence wording, with a control that the old prompt string is absent. A stamp test covers composed versus plan sources.

## Notes

Depends on STE-657 for the validator and reader. The `--summary` prompt is out of scope: it is not a name.
