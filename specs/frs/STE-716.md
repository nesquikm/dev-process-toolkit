# An opt-in capture hook records each Bash and Skill call as a privacy-safe row

## Summary

The session log cannot say what the working tree looked like when a call ran.
This adds an opt-in hook that writes one small row for each Bash or Skill call.
Rows carry a call class, a toolkit skill name, content hashes and counts.
They never carry command text, file paths, the working directory or branch names.
Only a user's approved opt-in registers the hook, so a default install runs nothing new.
No gate reads its rows.

## Requirement

Timestamps and error flags come from the transcript (STE-717). A live hook is justified only for what the transcript cannot hold: the tree state at call time, the staged diff size at a commit, and rows that outlive transcript cleanup. This FR adds that hook and nothing more. Where it says "per D<n>", it implements the branch the STE-714 decision table names. If D6 answers no, this FR stops before /implement and goes back to the operator.

### Setting

`specs/settings.yaml`, read through the M_94e6f7 settings loader:

```yaml
tracking:
  tool_calls: { enabled: false }   # enabled: true | false; absent means false
```

`loadProjectSettings` (`project_settings.ts`, M_94e6f7) gains `tool_calls` (closed key set `{enabled}`, the same shape as `token_stats`) in the closed key set of `tracking`; an `enabled` value outside `true`/`false` throws `SettingsShapeError`. A legacy-only or settings-less tree reads `false`, since no legacy home carries the key; the CLAUDE.md binding stub that M_94e6f7 generates holds no `tracking` key either. `/setup` writes no `tool_calls` key, and no migration does. `docs/settings-reference.md` documents the key, its type, its default and "no legacy home". The hook treats every read error as off.

### Registration (supervisor ruling 2026-11-04, for operator review)

Operator rule, 2026-11-04: no behaviour change by default. So `hooks/hooks.json` gains no entry and stays byte-identical, and a default install starts no new hook process. The hook is registered only when a user turns capture on through an approved settings change, and the registration follows the setting.

Where it lives: `<projectRoot>/.claude/settings.local.json`, Claude Code's per-user project settings file, which is never committed. `${CLAUDE_PLUGIN_ROOT}` does not expand outside a plugin's own `hooks/hooks.json` (`docs/hooks-reference.md` § Override pattern). So the entry names the plugin by absolute path, and that path names the user's home, so it may never reach a committed file.

The entry: under `hooks.PreToolUse` and `hooks.PostToolUse`, one group per event with the D4 matcher shape, each holding one command entry with `"timeout": 2` (seconds). Its command is the render below, byte for byte:

```
[ -f "$CLAUDE_PROJECT_DIR/specs/settings.yaml" ] && grep -q 'tool_calls' "$CLAUDE_PROJECT_DIR/specs/settings.yaml" && grep -qF '"<pluginRoot>"' '<installedPlugins>' && grep -qF '"version": "<version>"' '<pluginRoot>/.claude-plugin/plugin.json' && [ -x '<pluginRoot>/templates/hooks/process/tool-call-capture.sh' ] && CLAUDE_PLUGIN_ROOT='<pluginRoot>' exec '<pluginRoot>/templates/hooks/process/tool-call-capture.sh'; exit 0
```

`<pluginRoot>` is the real path of the running plugin root at registration, `<version>` is the version its `.claude-plugin/plugin.json` declares then, and `<installedPlugins>` is the absolute path of Claude Code's installed-plugins record, `<config dir>/plugins/installed_plugins.json`. The command is `renderCaptureHookCommand({ pluginRoot, version, installedPlugins })`.

Stale paths. Claude Code keeps an orphaned plugin version directory for up to 14 days after an update, so a path check alone would keep running the old version's capture code. The guard therefore pins the version: it runs only while `<pluginRoot>` is an install path that record lists and that root's manifest still names `<version>`. After an update the old root leaves the record, the guard fails, and the entry exits 0 silently with no Bun start. `status` then reports `stale`, and probe #69 lists the re-registration as pending. The record is Claude Code's own file; if its format changes, the guard fails closed the same way, and capture stops rather than run unpinned code. The guard also exits 0 silently when the settings file lacks the key. An entry is a capture entry when its command contains `templates/hooks/process/tool-call-capture.sh` (`isCaptureHookCommand`).

New module `adapters/_shared/src/capture_registration.ts`, with a front door of three verbs:

- `status <root>` is read-only. It prints `setting: on|off` and `registration: none|current|stale`. Stale means an entry exists but its command differs from the render for the running plugin root and version, or the setting is off.
- `register <root>` refuses in NFR-10 shape, exit 1, writing nothing, when the setting is off, when `.claude/settings.local.json` is tracked by git, when `git check-ignore` does not report it ignored, or when it exists but holds no JSON object. The not-ignored refusal's remedy names the exact line to add, `.claude/settings.local.json`, and the file to add it to, `<projectRoot>/.gitignore`. Claude Code adds a global ignore rule only when it writes that file itself, and `DPT_GITIGNORE_BODY` does not list it, so a fresh repository may lack the rule. Otherwise it adds or replaces the capture entries. Every other key and entry stays deep-equal and in its original order. A second run leaves the file byte-identical.
- `unregister <root>` removes only capture entries, plus the matcher groups their removal leaves empty. It writes nothing when no capture entry exists.

Neither write verb touches the `env` key or `.claude/settings.json`.

The module also exports `checkRegisterPreconditions(root, { settingOn })`, pure and read-only, returning the refusals `register` would raise with the setting taken as `settingOn` instead of read. `register` calls it with the setting it reads. STE-728 calls it with `settingOn: true` before its first write, so its check sees the state after its own settings write.

Who registers, always behind an explicit approval:

1. `retro_proposal.ts apply` (STE-728) calls `register` in the same approved act that turns `tracking.tool_calls.enabled` on, after the ordered precondition check that FR defines.
2. A migration entry `capture-registration` in `migrations/entries/capture_registration.ts`, `introduced_in: "3.1.0"`, `kind: "script"`, `requires_explicit_approval: true`, registered after `settings-file`. Its pure detect applies when the setting is on and the registration is `none` or `stale` (apply registers), or when the setting is off and a capture entry exists (apply unregisters). The setting is read from the working-tree `specs/settings.yaml`, the bytes the shell guard reads. A key removed or set false locally, committed or not, reads off: the entry is already inert, and apply removes only the user's own entry. Neither arm ever edits, restores or commits the settings file. `/upgrade` previews it and asks its own approval; the auto-approve marker never applies it.

Removal: no toolkit command turns the key off. When a user deletes the key, the shell guard makes the entry inert at once, with no Bun start. Probe #69 then lists `capture-registration` as pending, and `/upgrade` removes the entry on approval. On a default tree, with no key and no entry, the migration never applies, so probe #69 shows nothing new. Claude Code's settings watcher picks up a registration or removal, at the latest at the next session start; `docs/hooks-reference.md` says so.

### Per repository switch, per user registration (supervisor ruling 2026-11-04, for operator review)

The switch is per repository: `tracking.tool_calls` lives in the committed settings file, so turning it on reaches every clone through git. Registration is per user: each user's own `.claude/settings.local.json`, written only behind that user's own approval. A teammate who pulls an enabled setting and never approved gets exactly one warn-only pending `capture-registration` row from probe #69, and nothing else. No hook runs for them, no file changes, and nothing prompts outside `/upgrade`. This is the one allowed difference the M_7bc805 defaults gate lists for capture.

### Fast path

The wrapper is `exec bun run "${CLAUDE_PLUGIN_ROOT}/templates/hooks/_lib/hooks/tool-call-capture.ts"`, like `session-token-ledger.sh`. The entry module statically imports only Node built-ins and `../session.ts` (`parseHookPayload`). It finds the checkout by walking up from `payload.cwd` to the nearest directory holding a `.git` entry, with no child process. When that directory has no `specs/settings.yaml`, it exits 0 at once. Otherwise it loads `project_settings.ts` by dynamic `import()`, reads the flag, and exits 0 when off. `dpt_paths.ts`, `commit_target_repo.ts`, `pr_target_repo.ts`, `gate_receipt.ts` and `gate_reuse_key.ts` are loaded by dynamic `import()` only after the flag reads true. A flag-off run spawns no child process.

### Row — schema `tool-call/v1`, one JSON line per hook event

Path: `toolCallLedgerPath(root, sessionId)` = `<root>/.dpt/ledger/tool-calls/<sessionId>.jsonl`, a new composer in `dpt_paths.ts` that calls `assertPathSafeSessionId`. Under `ledger/`, so `DPT_GITIGNORE_BODY` (`setup/dpt_gitignore.ts`) needs no new rule.

Closed key set:

| Key | Value |
|---|---|
| `schema` | `"tool-call/v1"` |
| `event` | `"pre"` or `"post"` |
| `tool_use_id` | the payload's `tool_use_id`, or `null` |
| `tool` | `"Bash"` or `"Skill"` |
| `class` | Bash: `commit` (`resolveCommitTargetFromPayload(payload).isCommit`), `pr-create` (`resolvePrTargetFromPayload(payload).isPr`), `gate-receipt` (`announcesGateReceipt` or `runsGateOutcome`, both from `gate_receipt.ts`), else `other`. Skill: `skill` |
| `skill` | Skill calls only: the skill name when it starts with `dev-process-toolkit:`, else `"other"`; `null` for Bash |
| `ts` | the hook's own ISO wall-clock |
| `tree` | `worktreeDigest` of the session checkout, only on `pre` of a `commit` Bash call and on both events of a Skill call; else `null` |
| `diff` | `{ files, insertions, deletions }` summed from `git diff --cached --numstat` in the commit's resolved target checkout, only on `pre` of a `commit` call; `null` when unresolvable or otherwise |
| `scope` | `"main"`, or `"fork"` when D1 found a distinguishing field and it marks the call |
| `exit_code` | present only when D2 found one: the PostToolUse Bash exit code |

The session id lives in the file name only. No raw `tool_input`, `tool_response`, `description`, `cwd`, path or branch is written.

### Behaviour

Every run exits 0 with empty stdout and stderr: flag off, malformed stdin, no checkout, unsafe session id, a git failure or an unwritable ledger all write nothing and stay silent. Each row is one `appendFileSync` of one line.

## Technical Design

The plugin registers nothing. A user's approved opt-in writes one entry per event into their own project-local settings, so the default install and every teammate who never opts in run no hook.

The registered command guards in shell first. A project without the key, or an old plugin version, costs one shell and no Bun.

Inside the hook the flag check comes first, then heavy imports. Classification reuses the commit and pull request front doors the gates use. Git work runs only on commit and Skill calls. Rows append to a per-session file. Failure is silent, and the timeline reader counts the gaps.

Registration drift is a migration, so /upgrade's explicit approval governs both adding and removing the entry.
