# Build the falsifiability harness and one-way derivation binding for SMOKE_LEGS

## Summary

The module that names which conformance legs exist is supposed to be the authority for the leg set. It is not. Adding a fake fourth leg to it and running the whole gate left every one of 6605 tests green — not one noticed. The reason is that the enum is exported and imported by nothing at all; its only consumers are two call sites inside its own file.

That means the binding this milestone wants to strengthen does not exist yet. It has to be built from nothing, and the first thing built has to be the proof that it can fail. Otherwise the milestone ships assertions that look like coverage and are not.

The direction of derivation is the whole safety property. The TypeScript enum is the authority and the skill prose is the thing being checked. A test that works out what to expect by reading the same document it then inspects can never fail, and would sit green forever looking like protection.

This work gates everything downstream. If the mutation cannot be made to produce a failure, the approach has collapsed and the milestone stops here rather than proceeding.

## Requirement

Before a third leg is added anywhere, establish a binding between the leg-set enum and the two project-local driver skills that assert against it, and prove that binding is falsifiable.

The measured baseline: widening `SMOKE_LEGS` in `adapters/_shared/src/smoke_fixture_groups.ts` from `["linear","jira"]` to a three-member array containing a synthetic leg produced `6605 pass / 15 skip / 0 fail` — byte-identical to the clean baseline. `grep -rln "SMOKE_LEGS\|SmokeLeg" tests/ adapters/` returns only the defining module.

Exactly one assertion in the suite was even reachable by that mutation, and it tolerated it: `tests/m117-ste-425-falsifiable-coverage.test.ts:867` asserts `toMatch(/--leg must be one of linear \| jira/)` against a string built by `SMOKE_LEGS.join(" | ")`. The regex is unanchored, so `linear | jira | zzprobe` still matched. Every other two-leg pin in the suite stayed green legitimately — it asserts against skill prose or its own literals and was never connected to the enum.

## Acceptance Criteria

- AC-STE-445.1: A permanent mutation test widens `SMOKE_LEGS` with a synthetic leg absent from the canonical set and asserts that at least one derivation assertion FAILS. The mutation test itself fails when the mutation produces zero failures. {#AC-STE-445.1}
- AC-STE-445.2: The `--leg` error-string assertion in `tests/m117-ste-425-falsifiable-coverage.test.ts` is an exact-set match rather than a prefix substring: it fails when `SMOKE_LEGS` gains a member the assertion does not name. {#AC-STE-445.2}
- AC-STE-445.3: Rendering a leg that is registered in `SMOKE_LEGS` but absent from every group's roster does NOT silently report all groups `not-applicable`; a test pins the observed behavior. {#AC-STE-445.3}
- AC-STE-445.4: No derivation test reads a skill file to compute its own expected value. A meta-test asserts that each derivation test's expectation originates in TypeScript, not in the asserted prose. {#AC-STE-445.4}
- AC-STE-445.5: The milestone plan at `specs/plan/M121.md` records this FR's outcome as exactly one of two literal tokens — `fr1_derivation_falsifiable` or `fr1_derivation_collapsed` — written when this FR completes. When `fr1_derivation_collapsed` is recorded, `git log` shows zero commits referencing STE-446. An auditor reading only the repository can determine which occurred without relying on any narration. {#AC-STE-445.5}

## Technical Design

The mutation test (AC.1) cannot mutate the real source file in-place during a run — that would race the rest of the suite and leave the tree dirty on failure. Two viable shapes, to be settled at implementation: parameterize the derivation helpers over an injected leg list so the test can pass a synthetic set directly, or drive the mutation as a subprocess against a temporary copy of the module. The injected-list shape is preferred because it also makes AC.4 mechanically checkable — a helper that accepts the authority as an argument cannot be reading it from the prose.

AC.2 is a narrow edit: anchor the regex, or better, build the expected string from `SMOKE_LEGS` in the test so it tracks the enum by construction.

AC.3 covers a consequence no test observes today. With a synthetic leg *recognized* by the enum, `appliesToLeg` stops taking its everything-applies fallback and returns `spec.legs.includes(<synthetic>)`, which is `false` for all eight groups — so the render reports every group `not-applicable`, a completely vacuous leg reporting no gaps. The correct behavior needs deciding as part of this FR, not assumed.

AC.5's two tokens must be written by the implementation, not by a summary message. The plan file is the artifact of record.

## Implementation notes

**AC.3 changes shipped runtime behavior, and the new path is unreachable in production until STE-446.** `groupsCoveringLeg` plus a second CLI boundary guard mean a leg registered in `SMOKE_LEGS` but rostered by no fixture group now exits 2 with a diagnostic, where it previously exited 0 rendering all eight groups `not-applicable` — a vacuous pass. This is a behavior change to a surface that ships to every plugin consumer (`adapters/_shared/src/smoke_fixture_groups.ts`), not a test-only edit, and it is recorded as such in the changelog.

The new exit path **cannot be triggered through the shipped CLI today**: while `SMOKE_LEGS` is `["linear","jira"]`, every registered leg is rostered by at least one group, so no input reaches it. That is by design and it is resolved by STE-446, which widens the enum. An auditor who goes looking for a production trigger will not find one — that is expected, not evidence the AC is untested.

It **is** exercised now, through the mutation harness: widening the enum in a temp copy reaches the guard, and the observed result is exit code 2, empty stdout, and the diagnostic `leg "zzsynthetic" is registered in SMOKE_LEGS but no fixture group rosters it — every group would render not-applicable and the run would report a vacuous pass.` That is where the coverage lives.

**AC.4's registry-equality assertion was re-aimed, not dropped.** As originally written it compared `DERIVATION_TARGETS` against the executed `checks` and asserted equality — a drift detector. That assertion could not fail: the implementation makes both `.map()` projections of a single `DERIVATION_SPECS` array, so their id sets are identical for any contents including empty (measured: with the array emptied, the assertion stayed green; and provable by inspection, since `A = arr.map(f)` and `B = arr.map(g)` always agree on membership).

The honest description is not that the test went vacuous but that **its subject ceased to exist** — single-source construction makes drift unrepresentable rather than merely detected, which is strictly stronger than detecting it. Re-splitting into two hand-maintained arrays so a test could fail would have reintroduced the exact hazard the construction eliminates, and was rejected on that basis.

The assertion now targets the property that still holds and still can fail: that there is exactly **one** source. It has two arms, and the audit corrected an overclaim in an earlier revision of this note.

The first arm anchors on the **type**, not the name: exactly one `readonly DerivationSpec[]` declaration may exist. An earlier revision anchored on `^const DERIVATION_SPECS\b` and this note claimed a second declaration would break it — **that claim was false and is retracted**. `\b` cannot fire before `_`, so a differently-named `const DERIVATION_SPECS_TWO` slipped past it entirely, and the only thing the name-anchored arm caught was a redeclaration of the same identifier, which TypeScript already rejects without help. The original probe was mis-designed: it appended both a renamed array *and* a same-identifier redeclaration, then generalised from the half that needs no test.

Both arms are now verified falsifiable against the regressions that matter: appending a differently-named `readonly DerivationSpec[]` array fails arm 1 (`Expected: 1, Received: 2`), and replacing either consumer with a hand-maintained array literal fails arm 2.

**AC.3's guard is CLI-boundary-only — this is a real scope limit, not an oversight to discover later.** `groupsCoveringLeg` is consulted at exactly one site, inside the `import.meta.main` CLI block. The library functions — `reconcileFixtureGroups`, the summary renderer, the aggregate — still resolve a registered-but-unrostered leg to eight `not-applicable` records and report a pass. No library caller exists today (the only consumers are the CLI itself and two test files), so this is forward-looking rather than a live defect. It stops being forward-looking when STE-446 widens the enum, and that FR should decide whether to move the guard into the render path or accept the boundary-only scope deliberately.

**Two low-severity harness caveats, recorded rather than fixed.** Direction (i) of the mutation report cannot by itself distinguish "the hardcoded expectation correctly rejected the widened set" from "the mutated copy failed to execute at all" — any spawn or compile failure also yields stderr that fails the expectation. The mitigation exists (a separate test asserts exit code 2 and the synthetic leg's presence in stderr) but lives in a different test, so deleting that one test would silently un-protect the halt gate. Folding an exit-code precondition into the report record would make the harness self-sufficient. Separately, AC.5's git-log arm is unreachable on the falsifiable branch — it returns after re-asserting the token, so the `git log --grep=STE-446` invocation has never executed in the suite; run manually it exits 0 with zero matches, so the command shape is right, but nothing in the suite proves that.

**AC.4's one-way check has disclosed structural limits.** It is a textual scan, not dataflow analysis. It detects: an expectation literal deleted from or moved out of its declared file; an expectation-source file pointed at a markdown/prose path; and a skill-path read appearing in an expectation-*defining* module. It does **not** detect an expectation reached indirectly — laundered through a helper in a third module, assembled from path fragments, or read by a spawned process. Reading a skill file in order to *assert against* it remains legal by design; only computing an expected value from it is forbidden. The narrower guarantee is stated here so a later reader does not over-trust the check.

**The mutation harness registers one derivation target today** (`leg-error-exact-set`), which satisfies AC.1's "at least one derivation assertion". STE-446's five prose surfaces each need registering into `DERIVATION_SPECS` as they land, and that FR's own AC requires the harness to turn one of them red. The wiring cost is named here so the follow-on FR is not surprised by it.

**Duplication deliberately left in place.** `CANONICAL_LEG_ERROR_PATTERN` versus `expectationLiteral`, `THIS_MODULE_PATH` versus the module's real location, and `groupsCoveringLeg` versus `appliesToLeg` all look like DRY targets and are not. Each is a deliberate second statement whose collapse would restore a tautology. The `expectationLiteral` pin was checked against the M120 header-comment trap and is genuinely non-self-satisfying: doubled escapes in the string literal mean the only matching text in the file is the regex literal itself. One genuine duplication remains out of scope — `runGroupsCli` in `tests/m117-ste-425-falsifiable-coverage.test.ts` overlaps the exported `runCanonicalLegCli`; it is duplication, not a defect.
