# Every /deliver surface states FR scope, not only the reference

## Summary

The last milestone repaired a defect whose cause was a contract living only in a document the skill itself marks as not required reading, and then reproduced that same defect four requirements later. The routing rules for this milestone are the next candidate to land in that same optional file. Stating them on the operative surface is therefore part of the work, not a documentation chore that follows it.

## Requirement

The FR-scoped chain and the auto-extend rule are stated on the surface a live run actually reads, and the two surfaces are asserted to agree.

## Acceptance Criteria

- AC-STE-502.1: `skills/deliver/SKILL.md` states the FR-scoped chain and the auto-extend rule on the operative surface.
- AC-STE-502.2: Cross-surface agreement between the skill and `docs/deliver-reference.md` is asserted directly, not by checking each side's content separately.
- AC-STE-502.3: The argument-classification section no longer says an FR identity resolves through its milestone frontmatter to the same routing, because it no longer does.
- AC-STE-502.4: `docs/workflow-overview.md` reflects FR scope.
- AC-STE-502.5: A test goes RED if the rule is moved off the operative surface back into the reference alone.

## Technical Design

M129 recorded this as a first-class process finding: *"We repaired a defect class in FR 1 and reproduced it in FR 5."* STE-492 existed because a contract lived only in `docs/deliver-reference.md`, a file `skills/deliver/SKILL.md` marks *"not required reading"* immediately after saying *"The sections below are sufficient to operate"*. Four FRs later, STE-495 landed every target-repo routing rule into that same reference and nothing into the skill.

The finding's own conclusion is the design input here: *"the optional-reference surface is load-bearing by default. 'Not required reading' is not a description of that file, it is an instruction the next author will follow — including the next author who has just finished repairing the damage it caused."* This milestone is that next author, and this FR is the pre-commitment.

AC.2 is the mechanism, not AC.1. Asserting the skill carries the rule catches its absence; asserting the two surfaces agree catches the harder case where both carry a rule and the rules differ. M129 shipped AC-STE-492.2 on exactly that reasoning, and the same shape applies.

AC.3 is a deletion, and it is separated from AC.1 because adding the new rule while leaving the old sentence standing produces a skill that states both scopes. The shipped sentence — an FR identity "resolves through its `milestone:` frontmatter to the same routing" — is a true description of the defect and a false description of the fix.

AC.5 pins the placement rather than the prose, so a future trim that moves the rule back into the reference fails rather than passing quietly.

## Testing

Literal assertions that the operative skill file carries the FR-scoped chain and the auto-extend condition. A cross-surface agreement assertion comparing the two files' claims directly. A negative assertion that the superseded sentence is gone. Mutation check for AC.5: moving the rule out of the skill and into the reference alone must go RED — this is the clause that fails if the milestone repeats M129's mistake, so it is the one that must be verified by mutation rather than by inspection. `bun test` full root.

## Notes

This FR is not documentation cleanup. It is the guard against a defect this repository has now committed twice, in consecutive milestones, in the same file.

Line-cap pressure is not a defence and should not be accepted as one in review: when M129 reproduced the defect, `skills/deliver/SKILL.md` was 119 lines of a 358-line cap.
