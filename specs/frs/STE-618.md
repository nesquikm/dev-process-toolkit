# The programme's release waits for a passing live proof

## Summary

A live proof is only worth something if the release cannot go out without it.
The final milestone's plan now records where each tracker's live evidence is kept, and the test suite grades that evidence again with the same program the live run used.
While the milestone is unreleased, evidence taken against older code does not count.
A missing, failing, stale or altered proof turns the suite red, and the release ceremony already refuses a red suite.

## Requirement

The operator's proof bar for the shared-tracker programme is a passing live two-repository run on BOTH trackers, graded before release. A bar written only in a plan is followed by whoever reads the plan; this one must be executed. It must also not cost a new gate probe (21 test files pin the numbered probe count at ac1f3cb) or a new `/ship-milestone` refusal (a consumer-visible ceremony change for a maintainer-only rule).

It therefore rides on two refusals `/ship-milestone` already executes. Refusal #3 runs the project's test command and refuses on any failure. Refusal #1 refuses while any FR in the plan is still active, and this FR cannot close while its own suite is red.

**What gets built.**

1. **The record.** This milestone's plan carries a `### Live proof` table with one row per tracker (`jira`, `linear`): the committed bundle path under `plugins/dev-process-toolkit/tests/fixtures/shared-tracker-live/`, the run date, the run nonce, the tracker's spaces in a `Spaces` column (the Jira project keys, for example `DST, DST2`, or the Linear team key), and the bundle's content hash as the grader's `grade` printed it after writing `verdict.json` into the bundle directory (SHA-256 over exactly `bundle.json` and `verdict.json`; any other file in the directory is not part of the bundle). A row whose cells read `pending` is a named state, not an absence.
2. **The gate module.** `adapters/_shared/src/live_proof_gate.ts` exports `gradeLiveProof({ repoRoot, planPath })`, which returns per tracker `{ outcome, reason }` plus an overall verdict. It has a command-line front door, `bun run adapters/_shared/src/live_proof_gate.ts <repoRoot> <planPath>`, which prints one line per tracker and exits 0 only when both pass, refusing otherwise in the three-line NFR-10 shape. The plan is found at `specs/plan/<M>.md` or, after archival, at `specs/plan/archive/<M>.md`.
3. **Re-grade, never trust.** Each bundle is graded by the grade function of `shared_tracker_live_grader.ts` (STE-617). The outcome recorded inside the bundle is compared with the re-grade, never read as the answer. The bundle also records the registry scenario ids that applied to its tracker when it ran. In pre-release mode that set must equal the current registry's, so a scenario added after the run cannot ship unproven. In post-release mode the re-grade covers the recorded set, so a scenario a later milestone adds does not retroactively red a shipped proof. The recorded outcome and the re-grade must agree in BOTH directions (a recorded fail or abort that re-grades pass reds `recorded-verdict-disagrees` too), and a tracker passes only when both read pass. The bundle's recorded tracker must equal its row's (`tracker-mismatch` otherwise), so one run can never prove both trackers. The grader suite's synthetic-bundle builders stamp every bundle they make as synthetic, and the live `extract` never does; the gate refuses a synthetic bundle, and a Jira bundle whose item keys do not carry the plan row's project keys, as `not-live`, so a test fixture copied into the live path cannot stand in for a run. The Jira bundle must also record S8 (repoint) with outcome `pass`: a bundle whose S8 is the `repoint-space-not-given` skip, or absent, reds as `jira-repoint-not-proven`, so the programme cannot ship without the operator's second throwaway space having been used.
4. **Freshness.** While the plan's `shipped_in` is null (pre-release mode), each bundle's recorded behaviour digest must equal `behaviourDigest` of the working tree (git-tracked files only, as STE-617 defines it), and a mismatch names every file added, removed or changed since the run. The digest hashes `.claude-plugin/plugin.json` with its `version` value blanked, so the release commit's version bump cannot stale a fresh proof, while any other change to shipped behaviour does. Once `shipped_in` is stamped (post-release mode) freshness is no longer asserted, because later milestones must be free to change the code. Post-release mode also requires the stamped version to have a CHANGELOG release heading and to be strictly newer than the plugin version every bundle recorded at its run, so neither a hand-written stamp nor a stamp of an already-released older version can switch freshness off. The suite names which mode it ran in.
5. **Two suites, landed in order.** A synthetic suite, named by the house convention, grades synthetic plans and bundles for every named outcome; it lands with the gate module, before the live runs. A real-plan suite grades this milestone's plan and its two committed bundles. It lands in the same commit as the second leg's bundle and the filled table, after the live runs; the first leg's bundle is committed alone before the second leg, because the second leg's pre-flight refuses an untracked tree. Both sit in the default `bun test` set. The order is forced. The gate module sits inside the behaviour digest, so it must exist before the live runs. A real-plan leg landed before the runs would read `pending` and turn every intervening commit red. Test files sit outside the digest, so adding the real-plan suite afterwards cannot stale the proof.

## Technical Design

The gate is a thin reader over the live grader: it finds the plan, parses the table, and calls the grader's grade and digest functions, so the proof and its freshness are judged by one definition each. Blocking reuses refusals the release ceremony already runs, so no probe id, capability key or skill text changes. The pre-release and post-release split is keyed on the plan's own stamp, which the release commit writes, so the gate is strict up to the release and silent on freshness afterwards. The real-plan suite lands after the runs, because test files sit outside the digest.

## Testing

Synthetic plans and bundles cover every named outcome and both modes; the stale-proof case edits a scratch copy of the plugin tree, and the relocation case runs the digest from a second worktree. Before the live runs, the front door over the real plan exits 1 naming `pending`. That is the gate working, and the suite stays green because the real-plan suite does not exist yet. The real-plan suite lands with the bundles, and the plan's task list orders the live runs before this FR can close.

## Notes

This FR cannot close by code alone: its real-plan clause needs the operator to run the live smoke by keystrokes on both trackers. A code change after the run stales the proof and needs a fresh run, by design.

## Findings

**The gate is inside the proof it computes.** `live_proof_gate.ts` is a git-tracked file under the plugin root, so it is one of the files `behaviourDigest` hashes: a change to the gate after the live run stales the proof exactly as a change to any guard would. The same holds for the live grader and, since STE-617 moved it, the tool inventory the grader classifies tools by.

**The orchestrator's brief carried a defect a live run would have paid for.** The first design, written into this FR's deviations and into the implementer's brief, had `extract` print the bundle hash. `grade` then writes `verdict.json` into the same directory, so every hash copied from `extract` would have failed to match the gate's recomputation: every live proof would have read `bundle-altered`, and the first live run would have spent a tracker budget to discover a flaw in the brief. A hardening agent caught it before the freeze. An orchestrator's brief is not a trusted input either; it gets the same scrutiny as the code it asks for.

**An abort must still be recorded.** Once `grade` privacy-refuses a verdict like a bundle, a missing-bundle abort whose detail named the directory's absolute path (under `/Users/<name>`) would have been refused, so the abort's reason would never have been saved. The detail now names only the bundle directory's own name and the error code; a test grades an abort under a home-shaped path.

**A fork has its orchestrator's git authority and no instruction not to use it.** Two implementer forks in this FR ran `git stash push` on the gate file while working (one more did so during M_85e846). Each was harmless by circumstance, not by design: once because the file was untracked, once because the stash found nothing it treated as stashable; both times the stash list and the working tree were checked afterwards and nothing was lost. With a dozen dirty files, or an intent-added file at the wrong moment, the same command would take work that nothing reports as missing. Every later fork brief in this milestone forbids `git stash`, `git checkout --`, `git reset` and `git clean`, and tells the fork to report and stop if it believes it needs a clean tree. The harness itself forbids none of these; that belongs with the follow-on milestone's structural findings.
