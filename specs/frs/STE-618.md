# The programme's release waits for a passing live proof

## Summary

A live proof is only worth something if the release cannot go out without it.
The final milestone's plan now records where each tracker's live evidence is kept, and the test suite grades that evidence again with the same program the live run used.
While the milestone is unreleased, evidence taken against older code does not count.
A missing, failing, stale or altered proof turns the suite red, and the release ceremony already refuses a red suite.

## Requirement

The operator's proof bar for the shared-tracker programme is a passing live two-repository run on BOTH trackers, graded before release. A bar written only in a plan is followed by whoever reads the plan; this one must be executed. It must also not cost a new gate probe (21 test files pin the numbered probe count at ac1f3cb) or a new `/ship-milestone` refusal (a consumer-visible ceremony change for a maintainer-only rule).

It therefore rides on two refusals `/ship-milestone` already executes. Refusal #3 runs the project's test command and refuses on any failure. Refusal #1 refuses while any FR in the plan is still active, and this FR cannot close while its own suite is red.

**What gets built.**

1. **The record.** This milestone's plan carries a `### Live proof` table with one row per tracker (`jira`, `linear`): the committed bundle path under `plugins/dev-process-toolkit/tests/fixtures/shared-tracker-live/`, the run date, the run nonce, and the bundle's content hash as the grader's `extract` printed it (SHA-256 over the bundle's sorted files). A row whose cells read `pending` is a named state, not an absence.
2. **The gate module.** `adapters/_shared/src/live_proof_gate.ts` exports `gradeLiveProof({ repoRoot, planPath })`, which returns per tracker `{ outcome, reason }` plus an overall verdict. It has a command-line front door, `bun run adapters/_shared/src/live_proof_gate.ts <repoRoot> <planPath>`, which prints one line per tracker and exits 0 only when both pass, refusing otherwise in the three-line NFR-10 shape. The plan is found at `specs/plan/<M>.md` or, after archival, at `specs/plan/archive/<M>.md`.
3. **Re-grade, never trust.** Each bundle is graded by the grade function of `shared_tracker_live_grader.ts` (STE-617). The outcome recorded inside the bundle is compared with the re-grade, never read as the answer. The bundle also records the registry scenario ids that applied to its tracker when it ran. In pre-release mode that set must equal the current registry's, so a scenario added after the run cannot ship unproven. In post-release mode the re-grade covers the recorded set, so a scenario a later milestone adds does not retroactively red a shipped proof. The grader suite's synthetic-bundle builders stamp every bundle they make as synthetic, and the live `extract` never does; the gate refuses a synthetic bundle, and a Jira bundle whose item keys do not carry the plan row's project keys, as `not-live`, so a test fixture copied into the live path cannot stand in for a run. The Jira bundle must also record S8 (repoint) with outcome `pass`: a bundle whose S8 is the `repoint-space-not-given` skip, or absent, reds as `jira-repoint-not-proven`, so the programme cannot ship without the operator's second throwaway space having been used.
4. **Freshness.** While the plan's `shipped_in` is null (pre-release mode), each bundle's recorded behaviour digest must equal `behaviourDigest` of the working tree (git-tracked files only, as STE-617 defines it), and a mismatch names every file added, removed or changed since the run. The digest hashes `.claude-plugin/plugin.json` with its `version` value blanked, so the release commit's version bump cannot stale a fresh proof, while any other change to shipped behaviour does. Once `shipped_in` is stamped (post-release mode) freshness is no longer asserted, because later milestones must be free to change the code. Post-release mode also requires the stamped version to have a CHANGELOG release heading, so a hand-written stamp cannot switch freshness off. The suite names which mode it ran in.
5. **Two suites, landed in order.** A synthetic suite, named by the house convention, grades synthetic plans and bundles for every named outcome; it lands with the gate module, before the live runs. A real-plan suite grades this milestone's plan and its two committed bundles. It lands in the same commit as the bundles and the filled table, after the live runs. Both sit in the default `bun test` set. The order is forced. The gate module sits inside the behaviour digest, so it must exist before the live runs. A real-plan leg landed before the runs would read `pending` and turn every intervening commit red. Test files sit outside the digest, so adding the real-plan suite afterwards cannot stale the proof.

## Acceptance Criteria

- AC-STE-618.1: The plan read at either path carries a `### Live proof` table with exactly one row for `jira` and one for `linear`, each naming a bundle path under `plugins/dev-process-toolkit/tests/fixtures/shared-tracker-live/`, a date matching `\b20\d{2}-\d{2}-\d{2}\b`, the run nonce the bundle records and a 64-hex bundle hash; the section passes the plan narrative cap.
- AC-STE-618.2: `gradeLiveProof` returns `pass` for a tracker only when that tracker's bundle re-grades `pass` through the live grader's grade function; the front door exits 0 when both trackers pass and exits 1 otherwise, with one line per tracker on stdout and the refusal on stderr.
- AC-STE-618.3: Tampering and drift are named. A bundle whose recorded outcome is `pass` while its re-grade is not reds as `recorded-verdict-disagrees`. A bundle whose recorded nonce differs from the plan row's reds as `nonce-mismatch`. A bundle whose content hash differs from the plan row's (one byte changed in one committed record) reds as `bundle-altered`, naming the bundle. In pre-release mode, a bundle whose recorded scenario id set differs from the registry's current applicable set reds as `registry-changed`, naming the ids added and removed. In post-release mode the same bundle is graded on its recorded set and stays green. A bundle carrying the synthetic stamp, or a Jira bundle holding an item key outside the plan row's spaces, reds as `not-live`; the unstamped live bundle with matching keys is its permit twin.
- AC-STE-618.4: The Jira repoint is proven. A Jira bundle whose S8 is recorded as the `repoint-space-not-given` skip, and one that carries no S8 record, each red as `jira-repoint-not-proven` even when every other scenario passes and the recorded verdict is `pass`; the same bundle with S8 passing is its permit twin and grades `pass`. A Linear bundle is never asked for this.
- AC-STE-618.5: Freshness. In pre-release mode, a bundle whose behaviour digest differs from the working tree's reds as `stale-proof`, naming each added, removed and changed path. Editing one tracked file under `adapters/` in a scratch copy turns a passing gate red naming exactly that file. Editing only the `version` value in `.claude-plugin/plugin.json`, or adding an untracked or ignored file, leaves it green; editing any other `plugin.json` field turns it red. A second worktree of the same commit computes the same digest, so the gate passes there too. A root that is not a git checkout reds as `digest-unavailable`, never as a pass. Post-release mode, with `shipped_in` stamped on a synthetic plan, does not assert freshness, and both modes print their name. Post-release mode is entered only when the repository CHANGELOG carries a release heading for the stamped version; a stamp without one reds `stamp-without-release`, so a hand-written stamp cannot switch freshness off.
- AC-STE-618.6: Every failure is named and none is skipped: no section reds `no-live-proof-section`; a tracker without a row reds `missing-tracker:<tracker>`; a row reading `pending` reds `pending`; an absent or unreadable bundle path reds `bundle-unreadable` naming the path; an unparseable bundle reds `bundle-malformed`; a bundle holding zero scenario records reds `bundle-empty`; a plan found at neither path reds `plan-not-found` naming both; a plan found at both paths reds `plan-ambiguous` naming both, never picks one. Each is asserted on a synthetic input, and neither suite contains a skip, `test.if`, or early return.
- AC-STE-618.7: `behaviourDigest` has exactly one definition, in the live grader module, and the gate imports it; a meta-test finds one definition across `adapters/_shared/src/` and fails on a copied second one.
- AC-STE-618.8: The release is blocked through the existing refusals. In a scratch copy of the repository with either real bundle removed, `bun test` over the real-plan suite exits non-zero naming it; with both present and passing it exits 0. The commit that adds the real-plan suite changes no file inside the behaviour digest, which is checked by comparing the digest before and after that commit. The synthetic suite also carries the closing guard: once this FR's file sits under `specs/frs/archive/`, or either plan row reads other than `pending`, the real-plan suite file must exist, else it reds `real-plan-suite-missing`, so the FR cannot be archived around the proof. `skills/ship-milestone/SKILL.md` and `skills/gate-check/SKILL.md` are byte-identical to this milestone's kickoff.
- AC-STE-618.9: When the release ceremony's test-gate refusal (#3, which runs before the step-7 `shipped_in` stamp) runs for this milestone, the gate over the real plan passes for both trackers in pre-release mode. The plan's milestone-level acceptance table carries the front-door command with expected exit 0.
- AC-STE-618.10: Every clause asserting new behaviour fails on a sibling gate that lacks only the property it asserts. The siblings are: one that trusts the recorded outcome; one that skips freshness; one that hashes ignored files; one that skips the bundle hash; one that grades on the recorded id set in pre-release mode; one that reads a missing tracker or a `pending` row as a pass; one that accepts an unmatched stamp; one that accepts a synthetic bundle; one that accepts a Jira bundle whose repoint scenario was skipped. Each is measured red on its sibling and green on the shipped gate, and the direction is recorded in this FR's Falsifiability section. A module-absent failure is not counted as evidence. Controls and the post-release relaxation are exempt by construction.

## Technical Design

The gate is a thin reader over the live grader: it finds the plan, parses the table, and calls the grader's grade and digest functions, so the proof and its freshness are judged by one definition each. Blocking reuses refusals the release ceremony already runs, so no probe id, capability key or skill text changes. The pre-release and post-release split is keyed on the plan's own stamp, which the release commit writes, so the gate is strict up to the release and silent on freshness afterwards. The real-plan suite lands after the runs, because test files sit outside the digest.

## Testing

Synthetic plans and bundles cover every named outcome and both modes; the stale-proof case edits a scratch copy of the plugin tree, and the relocation case runs the digest from a second worktree. Before the live runs, the front door over the real plan exits 1 naming `pending`. That is the gate working, and the suite stays green because the real-plan suite does not exist yet. The real-plan suite lands with the bundles, and the plan's task list orders the live runs before this FR can close.

## Notes

This FR cannot close by code alone: its real-plan clause needs the operator to run the live smoke by keystrokes on both trackers. A code change after the run stales the proof and needs a fresh run, by design.
