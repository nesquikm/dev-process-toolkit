# The Verification block declares how to run the project

## Summary

The verification block names a check skill and a mode, and nothing else. It cannot say whether the project can be brought up at all, or how, or what its end-to-end suite is. Every consumer that wants to know has to guess, and guessing is why the check is optional today.

## Requirement

The block declares how to run the project and how to run its end-to-end suite, with an explicit way to say the project cannot be run.

## Acceptance Criteria

- AC-STE-503.1: `## Verification` accepts `run_cmd` and `e2e_cmd`; the closed key set becomes exactly four.
- AC-STE-503.2: `run_cmd: none` is the explicit declaration that the project cannot be run, and is a valid value rather than an absent key.
- AC-STE-503.3: `readVerificationConfig` returns the new keys; both absent keeps today's behaviour exactly.
- AC-STE-503.4: A key outside the four is still a config error.
- AC-STE-503.5: An existing two-key block parses byte-identically to today.

## Technical Design

The shipped contract in `docs/verification-skills.md` states the key set is closed at exactly two keys — `verify_skill` and `verify_mode` — and that any other key inside the section is a config error. Widening a deliberately closed set is the whole of this FR, and it is separated from the behaviour change in STE-505 so the config surface can land and be reviewed on its own terms.

The distinction between `run_cmd: none` and an absent `run_cmd` is load-bearing for STE-504's probe and is why AC.2 is its own criterion. Absent means the question was never answered; `none` means it was answered in the negative. A probe that cannot tell those apart either nags every library or silently excuses every unrun app.

AC.3's "both absent keeps today's behaviour exactly" is the compatibility clause every downstream consumer relies on. `/implement` Phase 4b" reads this config on every run, and a project that has not migrated must not change behaviour when the toolkit updates.

AC.4 preserves the closed-set discipline at its new width. The set is closed at four, not opened.

## Testing

Parse coverage for each of the four keys, for `run_cmd: none`, for the absent-key defaults, and for an unknown key producing a config error. AC.5 asserted against a real two-key block with the result compared to the shipped parse output rather than to a restatement of it. Round-trip coverage that `none` survives parse and re-render distinguishably from absence. `bun test` full root.

## Notes

Widening a closed key set touches `readVerificationConfig`, the config-error probe, the `/setup` writer, the `/upgrade` migration, the authoring guide, and every worked example. The blast radius is the reason this is its own FR rather than a preamble to STE-505.
