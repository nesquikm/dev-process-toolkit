# Two repositories on one tracker double, with every guard shown able to fail

## Summary

The shared-tracker guards from the earlier milestones are each tested alone, and one once passed only against a stub ignoring its query.
This adds one offline suite that builds two real repositories bound to one pretend Jira space and one pretend Linear project.
It drives the real decision commands and write hook end to end, for coexisting and spanning milestones on both trackers.
A mutation matrix breaks each guard in turn and requires a named scenario to go red.

## Requirement

The programme's safety claim is a property of two repositories acting on one container. Every guard M_947c79, M_685ff6 and M_85e846 ship is graded by its own suite, one guard at a time, and this repository has already shipped a guard whose only test passed because its stub ignored the query it was handed (at ac1f3cb, the foreign-repo-tag stop: `tests/m_840a06-ste-579-idempotency-probe-narrows.test.ts:142-155` returns a fixed result whatever `search` receives; M_947c79 repairs that one recorder). This FR does not re-close that finding; it generalises its lesson to every guard of the programme at once. One suite must hold the whole programme to account, offline and deterministic, before any live run is spent.

**The doubles must be no kinder than the real trackers.** Three measured properties of the real tools make a kind stub lie, and each becomes a double rule: (1) a filter conjunct that a stub ignores returns a superset the real tracker never would (RS-12); (2) text search is a superset, not an equality — Jira's `summary ~` is a phrase search and Linear's `query` searches title and description — so a front door that reads a text-search page as exact matches is wrong on the real tracker; (3) listings page — Jira search answers at most 100 rows with a `nextPageToken`, Linear `list_issues` defaults to 50 rows with a `cursor` and hides archived issues unless `includeArchived` is true — so a stub that answers everything in one page hides every not-last-page branch. A fourth property belongs to the harness, not the tracker: Claude Code blocks a PreToolUse call only when the hook exits 2 (or exits 0 with a deny decision on stdout); any other non-zero exit is advisory and the tool call proceeds (`docs/hooks-reference.md`, "Exit-code contract"). A fixture that treated every non-zero exit as a block would pass a hook that refuses with exit 1, which lets every write through live.

**What gets built.**

1. **Tracker doubles** — `tests/_tracker_doubles.ts` (leading underscore: a helper, never collected). A Jira double that stores issues and evaluates every conjunct of every JQL string it receives, and a Linear double that applies every filter parameter of `list_issues`, `list_milestones` and the `save_*` writes. Each double records every call, read and write, so a zero-write claim is a count, not an absence. Either double can land a create and then answer it with a transport error, which is how the network-error retry path is driven. The grammar the Jira double understands is exactly what the programme's front doors emit (`project =`, `parent =`, `labels =`, `labels in (...)`, `issuetype =`, `summary ~ "\"<phrase>\""`, `statusCategory`, `AND`, `ORDER BY`); anything else throws `UnsupportedQueryError` naming the conjunct. `summary ~` is evaluated as case-insensitive phrase containment, so it returns every stored summary that contains the phrase, never only the equal one. Pages hold at most the requested `maxResults` (capped at 100) with a `nextPageToken` while rows remain. The Linear double rejects an unknown parameter the way the real tool does (its input schema is closed, `additionalProperties: false`, checked against the parameter names recorded beside the tool inventory fixture of STE-607), models `query` as a ranking over a superset and never as an exact filter, pages `list_issues` at `limit` (default 50) with a `cursor`, hides archived issues unless `includeArchived` is true, and serves `list_milestones` newest-first in the real 50-row window. Every double's page size is settable per scenario, so a scenario can force a multi-page answer.
2. **The two-repository fixture** — `tests/_shared_tracker_fixture.ts` exports `makeSharedTrackerFixture({ tracker, shape })`, built ON `makeSpanFixture` from `tests/_span_fixture.ts` rather than beside it. It turns both roots into git repositories with one commit, writes each root's tracker declaration (`repo_tag`, `default_labels` carrying that tag, `min_dpt_version`) and the stop paragraph for old clients by running the M_947c79 declaration front door as a subprocess, shares one double between the two roots, can add a `git worktree` of either root (the relocated case) and a branch of either root whose CLAUDE.md predates the declaration, and removes roots and worktrees in `cleanup()`. Because `makeSpanFixture` leaves teardown to its caller, the helper also exports `withSharedTrackerFixture(opts, body)`, which runs `body` inside `try` and calls `cleanup()` in `finally`; every scenario uses it. The declaration front door is whichever command M_947c79 ships for writing the tracker sub-section (drafted as `adapters/_shared/src/setup/tracker_binding_write.ts`).
3. **The scenario registry** — `adapters/_shared/src/shared_tracker_scenarios.ts` exports the closed list of scenario ids, the trackers each applies to, a one-line property per id, and the Linear issue budget the live smoke may spend. The budget is unchanged by S15 to S18, which create no tracker issue: S15 is offline-only, because its fixture needs seeded tickets carrying a numeric label, and S16 to S18 make no tracker call at all. This suite and the live smoke (STE-617) read the same list, so the offline and live scenario sets cannot drift.
4. **The end-to-end suite** — one new suite named by the house convention for this milestone and FR. Its scenarios live in a helper, `tests/_shared_tracker_runner.ts`, exporting `runScenario(id, tracker, { pluginRoot })`, so the same scenario can be pointed at the tree under test or at a mutated copy. Every tracker decision is made by spawning the M_947c79 / M_685ff6 front door command from `pluginRoot` as a subprocess, in the order the skill prose gives, with the double's answers fed in. Every tracker write passes through a model of the harness before it reaches a double: the hook is `<pluginRoot>/templates/hooks/process/pre-tracker-write-gate.sh`, run through `bash` with `CLAUDE_PLUGIN_ROOT` set and a PreToolUse payload (`tool_name`, `tool_input`, `session_id`, `cwd`, `transcript_path`). The runner applies the harness rules exactly. It invokes the hook only when the matcher `<pluginRoot>/hooks/hooks.json` registers for it matches the tool name. B's writes go out under the second server name (`claude_ai_Atlassian` / `claude_ai_Linear`), so a matcher that knows one server lets B's writes through unhooked. The write is blocked when the wrapper exits 2, or exits 0 with a deny decision on stdout. It reaches the double on every other outcome, advisory exits included. The suite never imports a guard function where the live path runs a subprocess.
5. **The mutation matrix** — a second new suite. Each row copies the plugin tree (tests excluded, `node_modules` linked) to a temporary directory, applies ONE mutation with `mutateInRegion` from `tests/_sited-mutation.ts`, and calls `runScenario` for the ids the row names with `pluginRoot` set to the copy. Rows, by guard: (a) the FR-create decision drops the repo-tag conjunct; (b) the milestone decision reports `act=create` whatever the listing held (the mint commands cannot print anything but `created`, so the decision door is the site); (c) the mint binds a coincidental title match without an explicit join; (d) the tracker-write hook exits 0 before reading receipts; (e) the hook reads receipts from the payload's `cwd` instead of the target repository; (f) the version-floor comparison is removed; (g) the orphan listing drops its tag scope; (h) the untagged-ticket detector treats a missing tag as present; (i) `readWorkspaceBinding` drops `repoTag`; (j) the hook matcher names one MCP server only; (l) the commit and PR hooks accept evidence from the session's own repository for a write into its sibling; (m) the sibling ship gate reads a busy sibling as idle; (n) the repoint front door skips its old-container active-plan check; (o) the hook accepts a receipt from another session; (p) the hook skips comparing the tool input with what the receipt decided; (q) the declaration reader treats an unreadable CLAUDE.md as undeclared; (r) the hook's refusal exits 1 instead of 2; (s) the hook passes a create that names no project, so its target among the declared repositories cannot be resolved; (t) a front door takes the not-last page of a listing as complete (the FR-create door on both trackers; the milestone decision on Jira only); (u) the detector counts only its own repository's tag as a tag, so it flags the sibling's tickets; (v) the sibling ship gate reads ANY active FR in the sibling as busy, whatever milestone it is bound to; (w) the hook refuses a create made under a join receipt (the join path); (x) the hook counts an import or adopt receipt whose consent question was declined; (y) the attach-target front door skips its provenance check, so a new plan binds a sibling's Epic with no milestone decision; (z) the ownership decision drops its project comparison; (aa) the detector drops the `numeric-milestone-shared` warning; (ab) the typed-`M<N>` door answers `verdict=free` in tracker mode; (ac) probe #73's `mode: linear` arm is skipped; (ad) the recogniser reads `git merge`, `cherry-pick`, `revert`, `am` and `commit-tree` as non-commits; (ae) the recogniser classifies an alias word without resolving it; (af) the /tdd hook's Reminders exit 0 again; (ag) the recogniser reads `git merge --ff-only` as a commit; (ah) the Linear arm dates a plan by its archive commit, so a pre-epoch archived plan fails; (ai) the FR-create door takes a not-last page of its listing as complete (Jira). Rows (u) to (w), (ag) and (ah) mutate toward over-refusal, so each guard is graded against what it exists to permit as well as what it forbids. The doubles are test helpers outside the copied tree, so "a double ignores its query" is an in-suite negative control (AC.19), not a matrix row; the letter (k) is retired rather than reused.

**Scenarios** (ids live in the registry; each runs on Jira and Linear unless the registry says otherwise; "coexist" means each repository in its own milestone, "span" means one milestone both repositories joined):

- **S1 coexist, same title** — A and B each create an FR whose titles are byte-identical, and again with dash, NBSP and whitespace variants.
- **S2 span, same title** — the same, both FRs inside the one joined milestone: the container conjunct no longer separates them, so only the tag does.
- **S3 mint and join** — A mints; B joins A's milestone by key through the M_685ff6 mint decision, naming A as its sibling; B also asks to create a milestone whose title coincides with A's, without a join key.
- **S4 orphan listing** — each repository's reconcile listing, with the sibling's tickets and an untagged ticket present in the container.
- **S5 sibling-busy ship** — `sibling_release.ts` in A while B holds an active FR bound to the token the join produced: in B's main checkout, only on a second worktree of B, and only on an unmerged branch of B; then with B unreadable, absent, or holding a malformed plan; then with B idle, and with B busy only on a different milestone.
- **S6 version floor** — a hook running from a plugin copy whose `.claude-plugin/plugin.json` version is below the target's `min_dpt_version`, at it, and above it.
- **S7 receipt integrity** — writes with no receipt, another session's receipt, a malformed receipt, an unreadable receipt directory, and a tool input that differs from what the receipt decided.
- **S8 repoint** — B, first bound to its own container with one legacy ticket, moves into the shared container through the M_685ff6 repoint front door.
- **S9 cross-repository session** — a session rooted in A makes a write decided for B; and a write whose target repository the hook cannot resolve from its payload.
- **S10 old client** — a ticket written straight to the double with no tag and no hook, standing in for a pre-floor client or a human.
- **S11 relocated checkout** — the decided-for repository is a worktree of B at another path; and a worktree of B on a branch whose CLAUDE.md predates the declaration, which by contract is an undeclared repository.
- **S12 hooks by repository** — commit and PR commands issued from a session rooted in A that write into B (M_85e846's pre-commit and pre-PR wrappers).
- **S13 claim and import ownership** — B is handed A's tagged ticket key (as an argument and as a branch name), an untagged ticket, and a ticket from another project: STE-606's decision, then the claim transition and the import sync through the hook, with the adopt and import questions answered yes, answered no, and never asked.
- **S14 zero-write join and span** — B writes a new plan naming A's milestone container with no milestone decision, then after a decided join by key; the span is declared through STE-610's writer; A's release runs with B's plan not naming A back, and with a child ticket carrying neither tag.
- **S15 numeric-label collision** (Jira; offline-only) — tickets seeded straight into the double carry the legacy label `milestone-M8`, one tagged for A and one for B, as NEX-211 and NEX-297 do; then only A's tickets carry it.
- **S16 new numeric milestone** — in each root, the typed-`M<N>` door is run for `M999`. A hand-written `specs/plan/M999.md` is committed after `LINEAR_TRACKER_KEY_EPOCH`, and probe #73 is run. Beside it sits an old numeric plan `M8`, introduced before the epoch, that archives and ships.
- **S17 commit-writing subcommands and aliases** — from a session rooted in A: `git -C <B> merge --no-ff`, `cherry-pick`, `revert`, `am` and `commit-tree`, an alias `ci` → `commit` and a `!` alias configured in B, and `git -C <B> pull`, through the real commit wrappers.
- **S18 visible /tdd Reminders** — commits whose target cannot be resolved, a commit into a checkout with no stack marker, and a commit where `git` cannot run in the target, through the real /tdd wrapper.

## Technical Design

The helper extends the span fixture instead of forking it, adding git initialisation and a declaration written by the real front door. The doubles are small interpreters: each evaluates the exact query the front door emits, pages its answer and treats text search as a superset, so a dropped conjunct or a skipped page changes the answer instead of vanishing. Scenarios run subprocesses in prose order and block a write exactly when the harness would: exit 2 or a deny decision. The matrix points the same runner at a copied tree carrying one sited mutation. The registry is shared with the live smoke.

## Testing

Three helper modules (`tests/_tracker_doubles.ts`, `tests/_shared_tracker_fixture.ts`, `tests/_shared_tracker_runner.ts`), the tool inventory fixture STE-607 ships, extended in place with the parameter names of every tool a double implements (no second snapshot), and two suites: the end-to-end scenario suite and the mutation-matrix suite, both named by the house milestone-and-FR convention. The doubles carry their own self-test block (AC.2) inside the scenario suite. That inventory is re-captured at kickoff if either server has grown a tool; the live smoke re-checks it against live traffic. Mutation rows re-run only their named scenarios, so the matrix costs a fraction of the scenario suite per row. Run from `plugins/dev-process-toolkit` with `bun test`; both suites are in the default set.

## Finding: a guard whose refusal induces the act it exists to prevent

Measured on the first live Jira leg, 2026-09-23, and new to this programme. Every defect class this milestone had named so far was a guard failing to fire, firing on the wrong subject, or being structurally unable to fire. This one fires correctly and causes the harm.

The S8 child, rooted in B, ran the repoint command with `--peer <A>`. Row 3 refused: `--peer <A> declares jira_issue_type (none), not Task`. The refusal named a real disagreement and a file, and named no action the child could legally take — this repository could not "agree" with an absent declaration, because row 3 refuses an undeclared repository too. So the child edited `<A>/CLAUDE.md` with a `perl -0pi` loop over both roots: a cross-repository write, performed to satisfy a check whose whole subject is whether the two repositories agree. Nothing graded it. The tracker-write hook gates tracker writes, the commit and PR predicates grade git, and no predicate looked at file writes.

Three conditions had to hold at once, and all three are closed here rather than one:

1. **The peer was undeclared.** The bootstrap wrote both bindings through a writer that had no `jira_issue_type` key, so neither root declared one. The writer now has `--issue-type`, the pre-flight measures the type from the shared space's own create metadata (never a hand-typed "Task", whose spelling the repoint check compares byte for byte), and the bootstrap declares it on both sides and refuses before writing anything if it is unset. Both roots also get the `.mcp.json` row 5 reads.
2. **The refusal offered no legal path.** Every peer-naming reason is now built by one helper that names what the peer declares, an action this operator can take alone, and the one action always available — dropping the flag — plus that the peer's CLAUDE.md belongs to that repository's operator. A source pin keeps the eight sites from drifting apart again, since a hand-written ninth is how this class returns.
3. **Nothing graded the act.** The live grader has a `sibling-file-write` predicate: file-writing tool calls whose target is under the other root, and shell commands whose write verb targets it. It is target-aware, because an earlier "names the other root anywhere" rule flagged `cat`, `git -C … status` and every tool run named against the sibling — the root tokens are spelled `<A>`/`<B>`, so even a redirect arm matched their own `>`. Its one named limit is the in-place arm (`perl -i`, `sed -i`), which fires on the whole command because the live shape's target was a loop variable: a command editing its own root while merely naming the other is flagged, and that is reported rather than silently resolved.

The generalisation, for the next guard: a refusal is part of the system's behaviour, not commentary on it. A guard that leaves its subject no legal path has not prevented the act; it has chosen which way the act will be performed.

## Audit round 1 of the live-leg repair: what was found, and the pattern

The peer's audit of the repair commit found two HIGHs, both introduced BY that commit and both in the same new predicate, and three MEDIUMs that were mirrors of its own three fixes. All are repaired; the pattern is recorded because its frequency is now the point.

**The two HIGHs, both in `siblingFileWrites`.** It skipped every call whose `tool_result.is_error` was true. For a file-writing TOOL that is correct — the tool reports the write, so its error is evidence of absence. For BASH it is a fail-open: a command that writes and then exits non-zero has already done the harm, and the founding case is exactly that shape, a `perl -0pi` loop over both roots that fails the moment one iteration does. The guard built to catch that command would not have caught that command. It also disagreed with the rest of its own module, which grades Bash by `exitCode`. The second: `shellWriteInto` resolved only literal root-prefixed targets, so `cd <sibling> && <relative write>` evaded it — while step 23's own prompt is `cd <B> && gh pr create`, so the run primes every child on the evading shape. Segments are now walked in order with `cd` followed.

**The third of the cluster, the false-positive direction.** Steps 23 and 24 tell an A-rooted child to create B's own gate evidence, which writes under B's receipt ledger. That escaped the check only because `bun` is not a write verb — an accident, not a permission. A child that reached for `mkdir -p` while obeying the prompt would have failed the leg on by-design behaviour, and a guard that fails correct behaviour is one nobody trusts. There is now an explicit permit, scoped by BOTH scenario and path, with two refusal twins: the same write from a scenario whose prompt does not order it, and an S12 session writing anything else in the sibling.

**The mirror, now eleven instances.** Three fixes in one commit, three unfixed twins: F1's Epic correction reached the expected arm and not the worst case (`worstCaseExtraIssues` counts LINEAR issues, so Jira needed the same re-costing — S6's create is an FR in a new milestone and costs two, making the worst case 16); F5's name check reached the two stubs the bootstrap writes and not `--old-client`, the one client shape it does not write; and F7's redactions reached the strings the projection composes and not the ones it FORWARDS — a Node error message, a tracker answer's items, an unreadable-answer reason — each of which would have made `privacyViolations` refuse the whole bundle at Phase 6, which is the throw-away-the-leg mode F7 existed to remove. At this frequency the mirror is not a recurring accident: it is how this codebase fails, and the question to ask of every fix is which sibling path has the same shape and was not touched.

**The flake, root-caused rather than re-run.** `create-front-door-shared` failed with `code = -1` and an empty stderr in the audit fork's first `bun test` at HEAD (17089/1). `-1` is this harness's rendering of `exitCode === null`, which is what Bun reports when a child is KILLED BY A SIGNAL — and Bun's default per-test timeout is 5 seconds, which a `bun run` spawn can exceed under the load of the full 653-file gate. It is the same load-dependent 5 s timeout this milestone already root-caused once. The signal is now named in the stderr the assertions carry, so the next occurrence diagnoses itself, and the spawn-heavy suites carry a 60 s per-test budget. Raising that budget is not weakening the assertion: a module that never returns still fails, 60 s later.

**Both frequencies, because one of them alone is misleading.** In 17 saved full-suite runs spanning 2026-09-20 23:09 to 2026-09-23 14:24 and every commit from the pre-freeze tree to 1c6af11, run in a detached worktree on an otherwise quiet machine, `create-front-door-shared` fails in **zero**. In the audit fork, running alongside its own probes, it failed in **one of two**. 0/17 and 1/2 are not in conflict: they are what a per-test budget exceeded UNDER LOAD looks like, so the flake is load-sensitive and not commit-sensitive. Recorded together because the next person to meet it will otherwise conclude from a clean run that it is fixed. The 17 runs also show three environment-specific `AC-STE-594` failures every time, and nothing else.

## A pattern, not three accidents: syntax evaluated where text was meant

Three times in this milestone a value was read as SYNTAX by the layer it passed through, each time silently, each time in a different language. A `$'` inside a shell canary was read by JavaScript's string-replacement rules as "everything after the match", and broke about twenty unrelated mutation tests. A `\b` written into a regex through a Python heredoc arrived as a literal backspace. A backticked `` `scripts/` `` in an inline `git commit -m` message was run by zsh as command substitution, and the commit SUCCEEDED with the token deleted from its own body. Earlier milestones contributed the same shape: a perl `\|` read as alternation, and a bare `declare(...)` call erased by Bun.

What makes it a pattern rather than a run of bad luck is the failure mode, which is identical every time: the layer accepts the input, does something plausible with it, and reports success. Nothing refuses. The damage is only visible later, in a test that had nothing to do with the change, or in a commit message a reader trusts.

The remedy is not vigilance about backticks, because the NEXT instance will not look like the last three — it will be some other character that one of the four or five languages in this repository's toolchain treats as live. It is to stop passing text through an evaluating layer at all where a non-evaluating one exists: a commit message through `-F <file>` rather than `-m`, a script through a file rather than stdin, a regex built from a constant rather than interpolated through a heredoc. Where no such route exists, the value gets a control that would catch its corruption. That second half is the operative one: all three of this milestone's instances were found by a control READING THE ARTIFACT BACK, and none by inspection. AN EXIT CODE IS NOT A CONTROL — the zsh case reported success while deleting a token from the very message it was writing — which is the zero-hit-grep rule one level down: a command that answers nothing, or answers zero, has told you about itself and not about its subject.
