# Make SMOKE_LEGS the sole leg-set authority with five derivation surfaces

## Summary

The leg set is currently written down in at least three independent places that nothing keeps in sync: the exported enum, a second hardcoded copy immediately below it, and the literal text of two driver skills. Changing any one of them leaves the others untouched and the suite silent.

This work makes the enum the single authority and binds five prose surfaces to it, so that adding or dropping a leg turns tests red until the prose catches up. The second hardcoded copy is deleted outright — it is the direct reason the fixture-group rosters did not move when the enum was mutated during the design measurement.

The failure mode being closed here is silent drift, which is distinct from the operator-facing hazard handled by the next FR. Keeping them apart means each gets its own red signal instead of one large change where a partial regression hides.

One existing pin has to be replaced rather than widened. It asserts a fixed count of spawn blocks and locates each by a hardcoded tracker name, which is a slicing technique rather than the contract it appears to protect.

## Requirement

`SMOKE_LEGS` becomes the sole source of truth for which conformance legs exist, and the two project-local driver skills derive their leg-shaped assertions from it rather than restating them.

Five surfaces must derive:

1. The Phase A spawn-fence brace groups in `.claude/skills/conformance-loop/SKILL.md`
2. Pre-flight #6's basename allow-list in `.claude/skills/smoke-test/SKILL.md`
3. The `green` probe's per-leg findings-file list
4. The closing-summary table columns
5. The pidfile globs

Derivation is one-way per STE-445: the enum is authority, the prose is asserted.

## Technical Design

The five surfaces differ in how mechanically they can be derived. The pidfile globs and the findings-file list are template-shaped and already close to leg-agnostic. The spawn fence and the summary columns are literal-shaped and need the most work.

For the spawn fence, the replacement assertion is: for each leg in `SMOKE_LEGS`, exactly one brace group exists whose `--tracker` token is that leg and whose verdict-artifact path contains that same leg. That is strictly stronger than the current pair of assertions and is what the STE-423 contract actually says — its own test already asserts scoping through path templates and the generic tracker-segment regex, so a templated form satisfies it. The `toBe(2)` count and the hardcoded lookup are a slicing technique, not the contract.

Pre-flight #6's allow-list is the one surface where the shipped shell snippet contains a literal `case` list. Deriving it means either generating the case arms from the enum at test time and byte-comparing, or restating the allow-list in a form the test can reconstruct. The former is preferred.

## Implementation notes

**Roster-guard scope (AC.6) — decided, not inherited:** `roster_guard_left_at_cli_boundary` because widening the guard into the library render path would not make it reachable either, since that path reads the same `SMOKE_LEGS`-derived roster, and making it testable would require adding injectable-roster API surface purely to construct a state that can no longer occur.

The question this AC forces is whether the STE-445 registered-but-unrostered guard should move from the `import.meta.main` CLI into `reconcileFixtureGroups` / the render + aggregate functions. It should not, and the reason is that AC.6's premise stopped holding the moment AC.1 landed.

AC.1 made the group rosters derive from the enum — `const ALL_LEGS: readonly SmokeLeg[] = SMOKE_LEGS`, replacing the second hardcoded `BOTH_LEGS` copy. Measured after that change: `groupsCoveringLeg("none")` returns `[1, 3, 4, 5, 6, 7, 8]`. The state the guard fires on — a leg REGISTERED in `SMOKE_LEGS` but rostered by NO group — is now unrepresentable through the real roster, because widening the enum widens the rosters with it, so a registered leg is always rostered. The guard is consequently unreachable by any input to the shipped CLI.

Leaving it at the CLI boundary rather than widening it into the library render path, because:

- Widening it would not make it reachable either — the render path reads the same derived roster.
- Making it testable would require adding injectable-roster API surface purely to construct a state that can no longer occur. That is manufacturing reachability to justify a test.
- The guard is cheap and fail-closed, so it stays as a backstop against a future re-introduction of a partial literal roster.

The same construction retires one STE-445 assertion. `tests/m121-ste-445-derivation-falsifiability.test.ts` § `AC-STE-445.3` previously drove the guard through the mutated CLI with `--leg <synthetic>`; measured after AC.1, that invocation now yields `Fixture groups: PASS — 7 passed … 1 n/a` at rc 0, because the mutated enum carries the mutated roster with it. That test is re-aimed at the property that now holds and can still fail — every leg registered in `SMOKE_LEGS` is rostered by at least one fixture group — which is exactly what re-introducing a partial literal roster would break.

**AC.5 is PARTIAL against its literal wording, and the shortfall is architectural.** AC.5 says "the STE-445 mutation harness, run against the post-change tree, turns at least one of the five derivation tests RED." It does not. Running `runLegDerivationMutation()` against the finished tree reports exactly one target — `leg-error-exact-set`, inherited from STE-445 — and `failuresUnderMutation` contains only that.

The five prose surfaces are **not** registered in `DERIVATION_SPECS`, and cannot be. STE-445's AC.4 meta-test textually forbids a skill-path read inside an expectation-defining module, so the harness is structurally barred from reading the two driver skills. `leg_prose_surfaces.ts` takes document *text* (`proseLegs(docs)`) precisely so the caller supplies it. Registering the surfaces would require the harness to read files and would break the predecessor's contract.

What the five surfaces have instead is their own executed comparison in the AC.5 block, and it is genuinely falsifiable — but only after a repair. As first written, direction (i) compared each surface's prose against `[...EXPECTED_LEGS, SYNTHETIC_LEG]` and asserted none covered the widened set. That could not fail: the synthetic leg is absent from prose by construction, so the survivor list was always empty **including for a surface whose `proseLegs` returned nothing at all**. Measured: stripping `none` from the green-probe prose turned direction (ii) RED while direction (i) stayed GREEN — it passed for an unbound surface.

Direction (i) was re-aimed at the complement of direction (ii): no surface may enumerate a leg the enum does not register. The pair now asserts set equality and each half fails on its own drift direction — (ii) on prose short a registered leg (the widened-enum case), (i) on a stale leg left behind after a removal, which nothing previously covered. Verified falsifiable: injecting a phantom leg into the conformance-loop prose turned direction (i) RED across three surfaces.

So the honest reading: the five surfaces ARE bound to the enum and that binding IS falsifiable, but the binding is enforced by the AC.5 test block rather than by the STE-445 harness registry. An auditor looking for the five in `failuresUnderMutation` will not find them, and that is by construction rather than by omission.

**Falsifiability witness for direction (i) is a PERMANENT TEST, not a manual probe.** The original verification — injecting a phantom leg into the real conformance-loop skill on disk, observing RED, restoring — was a one-off and would not have counted as coverage. It is now a standing test that feeds the surfaces a SYNTHETIC document carrying an unregistered leg and asserts they report it. Synthetic text rather than a mutated file, so it needs no backup/restore and cannot leave the tree dirty if an assertion throws mid-test.

Building it surfaced something the manual probe had obscured: appending the phantom at end-of-document is NOT detected. The extractors are region-scoped rather than whole-file greps, so the witness has to anchor on an existing per-leg line inside the parsed fence. That scoping is correct behaviour — a whole-file grep would match leg tokens in unrelated prose — and the witness now carries a non-vacuity assertion that its anchor still resolves, so a prose edit cannot silently reduce the injection to a no-op.

**Correction tally for this FR, recorded verbatim because it is evidence for the milestone's central claim.** Three assertions were reported green and were not sound; every one surfaced only by EXECUTING the thing rather than reading its report:

1. **STE-445 singularity probe (my error).** I claimed a second `DERIVATION_SPECS` declaration broke the re-aimed assertion. My probe appended both a renamed array and a same-identifier redeclaration, and only the latter broke it — a case TypeScript already rejects. The audit measured that `\b` cannot fire before `_`, so a differently-named array slipped past. Re-anchored on the type.
2. **Re-aim arm insufficiency (my error, fork caught it).** My proposed "every registered leg is rostered by ≥1 group" does not fail when a SINGLE group is re-pointed at a literal — the other seven still roster the leg. The fork measured this and added a second arm.
3. **Direction (i) vacuity (fork reported AC.5 green; the harness run disagreed).** The assertion could not fail: the synthetic leg is absent from prose by construction, so the survivor list was always empty INCLUDING for a surface returning nothing. Found by executing it against a deliberately unbound surface — reading it would not have revealed it, because it looks correct.

Two of the three were mine. The pattern is that a green report and a green run are different claims, and only the second is evidence.

## Audit findings — fixed, and deliberately not fixed

The end-of-FR audit found a **fourth** vacuous assertion and a false claim in shipped prose. Both are recorded because they are evidence about this milestone's own thesis, not just defects.

**Fixed — shipped-prose overclaim (the worst of them).** The conformance-loop skill's new STE-446 paragraph listed the machine-enforced enumerations and included the per-leg **log** paths. Log paths are NOT bound — the pidfile matcher is `.pid`-only. Measured: stripping every per-leg `.log` reference reds zero surfaces. A false coverage claim, in shipped prose, inside the FR whose purpose is that unverifiable claims rot. Replaced with a table naming all eight per-leg enumerations and marking the three that are NOT bound (log paths; the `RC_FILE_*` family, covered behaviourally instead by the rc-gate test driving `SMOKE_LEGS`; the Phase 0 operator-contract `--tracker` list). A reader can now tell which enumerations a widened enum catches and which need hand-updating.

**Fixed — fourth vacuous assertion.** AC.2's per-surface DISCRIMINATOR paired `prose.length > 0` with `expect(prose).not.toContain(SYNTHETIC_LEG)`. The second could not fail: `zzsynthetic` appears in neither driver document, so no extractor — genuine or hardcoded — can return it. Its comment described a widened-set comparison from a revision that no longer existed there. It was the AC.5 direction-(i) defect surviving inside AC.2's own non-vacuity check. Replaced with the empty-documents discriminator, which actually distinguishes reading prose from echoing a constant.

**Fixed — AC.2's one-way pin did not forbid the circularity it claimed to.** It banned `node:fs`, `readFileSync`, `SKILL.md` and `.claude/skills`, but not importing the authority set — even though the module's header claims it "never states the expected side and never imports it". The sibling pin on `leg_derivation_mutation.ts` already carried that clause; its absence here was an oversight. Now scoped to IMPORTS specifically: a blanket ban on the identifier would forbid the header from NAMING the enum it explains it never imports, which is the documentation-accuracy cost AC.1's whole-file pin already paid once. (Noted honestly: the first attempt at this fix WAS the blanket ban, and it fired on those two comments — the same trap, reproduced while repairing a different finding.)

**Fixed — AC.4 diffed against HEAD instead of the merge-base.** `git diff --quiet HEAD` reads as "unmodified" only while the work is uncommitted; once committed it degrades to "working tree clean vs HEAD", which is true for a modification made IN that commit — exactly what the AC forbids. Symmetric false-positive too: any later unrelated uncommitted edit to that file would turn it red. Now diffed against `merge-base HEAD main`, with a non-vacuity check that the base resolved.

**AC.7's history arm was DELETED, not shipped.** Cross-commit atomicity is **not enforced**. The arm walked every revision of the module on this branch asserting none registered a leg while still reading the second copy. It was removed on two independent grounds, either of which disqualifies it:

1. It goes **permanently vacuous post-merge**. The range is `merge-base(HEAD, main)..HEAD`; on main that collapses to `HEAD..HEAD` and the walk passes over an empty set for the rest of the repository's life. M121 exists to eliminate assertions that cannot fail — shipping one inside its own implementation would be self-refuting.
2. Its predicate was an **identifier proxy**, requiring the old alias to be present. A split that first renames the alias while keeping the enum two-member, then widens in a later commit, leaves a broken intermediate the walk cannot see.

A vacuous test is worse than no test: no test is an honest absence, a vacuous one is a false presence that reads as coverage. Documentation does not stop a future maintainer reading a green suite and concluding atomicity is covered — so the arm is gone and the absence is stated in-source, in this FR, and in `specs/notes/follow-ups.md`.

**AC.7's working-tree invariant arm is retained** and is the sound half: falsifiable on every run, and it catches the end state the AC cares about. What it does NOT catch is a split across commits.

**A mechanism that might actually work**, recorded as follow-up scope rather than attempted here: walk the **milestone's** commit set (shas touching `specs/plan/M121.md`, or a recorded kickoff..ship range) rather than a range that collapses against its own merge target, and key the predicate on **roster coverage** — every declared leg rostered by at least one group in that revision — rather than on the presence of any particular identifier.

**Superseded, retained for the record — the three defects as originally found.**
1. Its git-history walk currently examines **zero relevant revisions**: on this branch the range yields exactly one sha (the STE-445 harness commit), whose enum is still two-member, so the broken-intermediate predicate is false by construction. The STE-446 change is uncommitted, so the atomicity claim the walk exists to verify **has not been exercised**.
2. It goes **permanently vacuous post-merge**: on main, `merge-base(HEAD, main) == HEAD`, so the range collapses to `HEAD..HEAD` and the walk passes over an empty set forever.
3. Its predicate is an **identifier proxy**, not a coverage check: it requires the old identifier to be present. A split that first renames the literal while keeping it two-member, then widens the enum later, leaves a broken intermediate the walk cannot see. The AC's own wording — "rosters ceasing to READ the hardcoded literal" — implies a roster-coverage predicate, which would be exact.

AC.7's working-tree invariant arm is sound and does hold. The history arm is the weak half.

**NOT fixed — advisory.** AC.4's hazard guard hardcodes `new Set(["linear","jira"])`, a third copy of STE-423's `TRACKER_SEGMENT` alternation, which will drift silently in both directions if that alternation changes. AC.3's removal check is an exact-string `not.toContain`, so it would pass against a reformatting of the same literal (the positive replacement assertions are sound, so this is cosmetic). AC.6 was implemented as a bun test rather than a registered `/gate-check` probe though the AC says "a probe" — the substantive check exists, is section-scoped correctly, and is falsifiable, so this is wording rather than coverage; registering a real probe would flip the probe count across roughly seven pinned test files.


**Recurrence, not anecdote: whole-file textual pins keep colliding with the prose that explains them.** M120 shipped a defect green because a header comment SATISFIED a source pin. This FR hit the inverse twice: AC.1's `not.toMatch(/SMOKE_LEGS\s*\.\s*join/)` was tripped by `leg_derivation_mutation.ts`'s own header quoting the mechanism it documents, and my first attempt at AC.2's import pin — a blanket `not.toContain("SMOKE_LEGS")` — fired on two comments explaining that the module never imports it. Two independent instances, opposite signs, make this a pattern in this codebase rather than a one-off. The lesson each time was the same: narrow the pin to the actual hazard (an import, a call expression) rather than banning an identifier everywhere, because the broad form taxes documentation accuracy and the prose loses.
