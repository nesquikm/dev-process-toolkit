# A gate that ships unannounced reds the run that ships it

## Summary

Documenting two of three would reproduce the omission being fixed, and this repository has five recorded milestones that reproduced their own defect. A correction is one edit; the class needs a reader. Derive the blocking gates from the hook entry points themselves, then grade every announcing surface against that derived set, so a fourth gate reds the run that adds it rather than the run that trips it.

## Requirement

The set of blocking gates is derived from the hook entry points themselves, and every announcing surface is graded against that derived set rather than against a hand-maintained list of names.

## Acceptance Criteria

- AC-STE-573.1: A reader enumerates the bundled hook entry points under `templates/hooks/_lib/hooks/` and selects the blocking ones by structure — an entry point that calls `requireSkillToolUse` and exits blocking on the miss — never by a hard-coded list of hook names. It resolves exactly the gates that ship today, and the number it resolves is asserted against what the entry points carry rather than against a literal.
- AC-STE-573.2: For every derived gate the reader asserts `docs/hooks-reference.md` documents it, naming both the hook and the Skill it requires.
- AC-STE-573.3: For every derived gate the reader asserts `docs/honored-contracts.md` carries an entry naming it.
- AC-STE-573.4: For every derived gate the reader asserts `templates/CLAUDE.md.template` announces it.
- AC-STE-573.5: The reader asserts `docs/hooks-reference.md` is linked from at least one surface other than itself, and it counts only surfaces a reader actually reaches — the manual citing its own filename does not satisfy the clause.
- AC-STE-573.6: Falsifiability, and this is the load-bearing clause. The reader is mutation-tested against a synthetic fourth blocking entry point that no surface mentions, and against removing one existing gate's mention from each graded surface in turn. Every mutation is first measured clean against the landed tree, through the throwing `mutate` helper. A reader built on a hard-coded list would survive the fourth-gate mutation, which is exactly what this clause exists to catch.
- AC-STE-573.7: The reader adds no `/gate-check` probe and no ordered adapter module. The probe count and the down-only module-reachability pin are asserted unmoved by this FR.

## Technical Design

The reader ships as a test file at `plugins/dev-process-toolkit/tests/m_a41431-ste-573-blocking-gate-announcement.test.ts` and nowhere else. A new probe would cost the probe-count pin in three places, and a new ordered adapter module without a runnable front door raises a pin that only moves down. Neither buys anything `bun test` does not already give.

Derivation, not enumeration, is the point. The blocking set is read off each entry point's own text — the required-Skill call and the blocking exit — so a fourth hook in the same shape joins the set without anyone updating the reader.

The mutations write to a temporary copy of the region under test and restore it, so a failed assertion cannot leave the repository edited.

## Testing

AC.6's fourth-gate mutation is the one clause that separates a real reader from a list. It is run first and measured clean before the mutation is applied, because a check that also passes on the unmodified tree proves nothing about either.

## Notes

The five prior occurrences are M129, M132, M133, M135 and M_645517; in the last of those a newly written checker false-positived on its own tree, which is why this reader is run against the landed tree before the milestone ships.
