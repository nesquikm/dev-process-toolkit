# A create never reuses a closed ticket, and the Epic carries the labels

## Summary

Before a create, a check looks for a ticket that a timed-out create already made.
It also matched an old ticket that was already done, and offered it for reuse.
A done ticket is finished work, not a lost create.
The fix ignores closed tickets in that check.
The milestone Epic also missed the project's default labels.
So cleanup that searches by label left the Epic open.

## Requirement

`create_idempotency_probe.ts decide` never returns `reused` for a closed candidate, and a minted Jira milestone Epic carries every `default_labels` entry.

## Acceptance Criteria

- AC-STE-787.1: `query` asks for the status field (Jira `status`, Linear `statusType`), and `decide` treats a candidate whose status is closed (Jira category `done`; Linear `completed` or `canceled`) as no match, so a page holding only a closed same-title ticket yields `create`.
- AC-STE-787.2: A candidate that lacks the status field makes `decide` refuse as unreadable, never reuse.
- AC-STE-787.3: An open same-title candidate is still reused, exactly as before.
- AC-STE-787.4: After `mintMilestoneEpic` creates an Epic, it adds each `default_labels` entry beside the `milestone-<id>` label; a failed label write does not fail the mint, and `labelled` reports it.
- AC-STE-787.5: `bun test` from `plugins/dev-process-toolkit` reports 0 failures, and its skip identities equal the trunk baseline by name.

## Technical Design

Add the status field to the printed search for both trackers, parse it in the page readers, and filter closed candidates before the title compare. The mint helper takes the binding's default labels and writes them with the same label operation it already uses, once, outside the retry.

## Testing

Decide tests per tracker with closed, open and status-less candidates. A mint test with a fake provider records every label written.
