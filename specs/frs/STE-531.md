# The skip-baseline order is proven to fire, not merely reachable

## Summary

A check already exists that walks the shipped surfaces, finds every place one of them tells a reader to run a module, and grades whether that module can be run. It classifies both of the skip-baseline orders as ordered, and both as reachable. Measured this session, at the pinned count, reporting fine.

Both of them were, at that moment, unable to fire in this project at all. One is inside a paragraph conditioned on a key this repository does not set; the other is placed after a branch creation that an already-acceptable branch never performs. The module they name is genuinely runnable, which is what the check asks and what it correctly answered.

So the certificate is true and the conclusion drawn from it is false. Reachable means the module can be run. It does not mean the order will ever be given. Nothing distinguishes those two today, and the difference is the entire subject of this milestone.

This closes the gap for this order, by executing it rather than reading it, and writes down what the existing certificate does and does not cover so the next reader is not misled the same way.

## Requirement

Whether the skip-baseline order fires in this project is decided by executing the ordering path against the project's own configuration, and the limit of the existing reachability certificate is recorded on the surface that documents it.

## Acceptance Criteria

- AC-STE-531.1: The measured gap is recorded as a fact with its measurement. Running `runModuleReachabilityProbe` against this repository at 9b420ec returns `ok: true`, `orderedUnreachable: 142` at the pinned value, 343 records total, and among them exactly two naming the skip-baseline module — `skills/implement/SKILL.md:45` and `docs/implement-reference.md:77` — each classified `ordered` with `reachable: true`. The FR states these numbers as measured, not as a target.
- AC-STE-531.2: A check decides whether the skip-baseline order FIRES in a given project by executing the ordering path against that project's own `CLAUDE.md` and asserting a baseline record results. Behaviour, not vocabulary: no phrase list, no proximity window, and no enumeration of conditional wordings decides it. A detector built from an enumeration inherits the enumeration's blind spot, which is how the surface M135's own detector missed was missed.
- AC-STE-531.3: The check is falsifiable in both directions. Re-introducing the `branch_template:` conditional to EITHER ordering surface turns it red, asserted once per surface so a one-surface regression cannot hide behind its neighbour. A fixture whose configuration sets the key and one whose configuration omits it BOTH produce a capture, so the check is not merely detecting the key's absence.
- AC-STE-531.4: `ORDERED_UNREACHABLE_PIN` is re-measured after this milestone's surface edits and moved in the same commit if the classification changed, following the remedy the check itself prints. The pin is never raised to admit a new unrunnable order. If the count is unchanged, that is asserted rather than assumed — an edit to two ordered references that leaves the count identical is a claim, not a default.
- AC-STE-531.5: The distinction in AC.1 is written onto the shipped surface that documents the reachability rule: reachable answers whether the module can be run, and does not answer whether the order that names it will ever be given. The next reader of a green reachability row is told what it certifies.
- AC-STE-531.6: The check is non-vacuous: a positive result requires reading the capture record back off disk in the fixture project. A result derived from the entry point's exit status would be satisfied by a writer that succeeds and writes nothing, which is the precise shape this milestone exists to close.
- AC-STE-531.7: The check does not silently pass on a fixture it failed to set up. A fixture whose git repository, trunk ref, or configuration file is missing surfaces as a failure naming what was absent, never as a skipped or vacuous assertion. Twelve tests in this repository already skip on absent fixtures and read as green; this must not become the thirteenth.

## Technical Design

This is an executable test rather than a new gate probe, and that is a deliberate scope decision. A new probe would be the eighty-second, and registering one moves counts pinned across roughly two dozen test sites for no gain in falsifiability here — the assertion is equally binding as part of the suite, which is itself the gate.

The check works by construction rather than by inspection. It builds a throwaway project carrying a configuration file, runs the shipped ordering path, and looks for the record. Nothing about the wording of the order enters into the verdict, which is what makes it survive a rewording that keeps the defect.

The two-direction falsification in AC.3 matters more than the positive case. A check that only asserts the capture happens would pass just as well against a version where the conditional had never been removed, if the fixture happened to satisfy the condition. Asserting that restoring the conditional reddens it is what proves the check is reading the thing it claims to read.

The generalisation to all orders is deliberately NOT attempted. Whether an arbitrary ordered reference fires depends on conditions this check would have to model, and a partial model that reports confidently is worse than the current honest silence. What is recorded instead is the limit of the existing certificate.

## Testing

The fixture project is created fresh per test and its git repository is initialised with a real commit and a real trunk ref, because the ordering path resolves a merge base and a fixture without one would exercise a different branch than production takes.

The falsification cases restore the conditional wording to a COPY of each shipped surface rather than to the shipped file itself, so a failing run cannot leave the repository holding the defect it was testing for.

The absent-fixture assertion in AC.7 is exercised by deliberately omitting each of the three setup elements in turn and asserting a named failure each time, rather than by trusting that setup always succeeds.

## Notes

The reachability check is not wrong and is not being changed beyond its pin. It answers the question it was written to answer, and M133's own design correction records why the stricter rule it replaced was rejected. What is added here is a second question, asked only of the one order this milestone repairs.
