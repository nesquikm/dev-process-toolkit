# A second repo joins a milestone instead of minting a rival

## Summary

Two repos working one milestone need to arrive at the same milestone object. Nothing currently tells the second one to look before it creates, so it mints a rival with a near-identical name and the two halves drift apart with no listing surface that shows both. The allocation guard gains an instruction to derive the identity from the key that already exists, and to refuse rather than mint when it cannot look first.

## Requirement

When a milestone container already exists for the work, the allocation guard must order derivation from its key rather than a fresh mint, and must order a refusal when the provider cannot enumerate what already exists.

## Technical Design

Line 177 is a single 9,675-character line carrying the whole allocation guard, so appending is line-neutral by construction. The asymmetry the clause closes is in the repository:

```
adapters/_shared/src/attach_project_milestone.ts:676-678  bind path REFUSES without listEpics/setParent
adapters/_shared/src/mint_milestone_epic.ts:88-90         "listEpics is optional; without it a mint simply has no find leg"
```

The path that creates on a board with no delete tool is the one that degrades silently. STE-521 is the precedent: an Epic-keyed milestone binds by key, never by summary, and minting to satisfy an unresolvable token is refused. Live evidence that names are unsafe to join on: measured live, five of this project's seven tracker-first milestones carry the renamed form and two carry the bare title the mint writes, so a name match misses straight across the rename.
