# /deliver enters a resumed milestone at the phase its state allows

## Summary

Work arrives mid-pipeline routinely: specs written in an earlier session, or written by someone else, reviewed and merged; a milestone half-implemented and abandoned; a milestone fully built that needs only the ship ceremony. The orchestrator can be entered only at its first phase, so none of those states can be asked for.

The most common resume state is the worst one. A freshly merged spec-only pull request lands with its requirements flagged for technical review, and the implement skill hard-refuses a whole milestone in that state — so naive entry at the ceremony phase is guaranteed to bounce, and the operator discovers the spec-writing passes they needed only by reading the refusal. Every input the routing needs is already computed by an existing helper or probe.

## Requirement

A resumed milestone is classified from what is on disk, entered at the phase that state allows, and the classification is shown to the operator before anything is spawned.

## Acceptance Criteria

- AC-STE-498.1: A resumed milestone is classified into the states that change the entry point: FRs awaiting technical review, ready to implement, partly implemented, ship-ready, already shipped, and parked.
- AC-STE-498.2: The classifier reads only files already on disk and mutates nothing — no spec write, no tracker write.
- AC-STE-498.3: Classification reuses the existing helpers and probes (`plan_task_state`, `active_plan_ship_ready`, `plan_ship_coherence`, `needs_technical_review_consistency`) rather than re-deriving their logic.
- AC-STE-498.4: **(amended 2026-08-17 — see § Deviations)** A milestone with FRs awaiting technical review runs those `/spec-write` passes where the milestone's target repo requires: **inline in the invoking session** when the milestone targets the invoking repo, and **inside the target repo's worker** when it declares a `target_repo:` at another toolkit repo, where the operator answers in that visible session directly. In both branches the Socratic contract is preserved identically — `/deliver` never answers on the operator's behalf, never paraphrases, never pre-fills, and never batches the questions, wherever the skill runs.
- AC-STE-498.5: A ship-ready milestone enters at `/ship-milestone`, skipping `/implement`.
- AC-STE-498.6: A shipped or parked milestone refuses cleanly, with the parked reason surfaced when there is one.
- AC-STE-498.7: The classified state and the exact chain the orchestrator intends to run are rendered to the operator, who confirms, edits, or aborts before any worker is spawned and before any tracker claim is made.
- AC-STE-498.8: Aborting at that gate leaves no side effects.
- AC-STE-498.9: Resume runs one milestone per invocation; the serial worker topology is unchanged.

## Technical Design

Every classifier input already exists and was verified present: `adapters/_shared/src/plan_task_state.ts`, `adapters/_shared/src/active_plan_ship_ready.ts` (probe 75, which also ships a runnable CLI entry), `adapters/_shared/src/plan_ship_coherence.ts` (probe 63), and `adapters/_shared/src/needs_technical_review_consistency.ts` (probe 40). AC.3 therefore constrains this FR to assembly rather than new machinery — re-deriving any of that logic would create a second source of truth for a classification the gate already computes.

The ship-ready row pays twice: probe 75 exists solely to tell the operator a milestone is ship-ready, and today acting on it means reading a gate report and hand-running the ceremony.

AC.4 inherits a hard constraint from the orchestrator's existing contract, but the constraint is narrower than this FR first stated it. `/spec-write` is Socratic and `/deliver` forbids **proxying** Socratic questions — answering on the operator's behalf, paraphrasing, pre-filling, or batching them. That prohibition governs **who answers and how the question is conveyed**, not where the skill executes. The reference doc's where-based line is a *cost* argument — "running it in a spawned worker inserts a relay hop into every question" — and that cost is zero for a **visible** worker the operator types into directly: no relay hop, therefore no proxy.

So the placement follows the target repo. For a milestone targeting the invoking repo the passes run inline, exactly as the normal spec-writing phase does. For a milestone declaring a `target_repo:` at another toolkit repo they run inside that repo's worker, because that is the only place its tracker and specs bind correctly — and the operator answers there, in the visible session, with `/deliver` still answering nothing.

AC.7 makes the classifier's verdict auditable before any side effect, so a misclassification costs a keystroke rather than a worker session and a tracker claim. AC.8 pairs with it — the abort must be genuinely free.

Explicitly out of scope, per the source request: multi-milestone resume, any change to the three ceremony skills (all three are already individually resumable), and deciding which FRs need re-specing beyond the existing flag.

## Deviations

**AC.4 was amended on 2026-08-17, after this FR had already gone green.** An operator decision, taken on evidence, and recorded here because an AC changed after the fact is the first thing a reviewer must be shown rather than something they discover.

**Both readings, named.**

- **As originally written:** *"runs those `/spec-write` passes inline in the invoking session, **never in a spawned worker**, so the Socratic contract is preserved."* Unconditional.
- **As amended:** placement follows the milestone's target repo — inline for the invoking repo, inside the target repo's worker for a declared cross-repo toolkit target, with the Socratic guarantee stated identically in both branches.

**Why it had to change.** The original wording collided head-on with `AC-STE-495.3`, shipped earlier in this same milestone, which requires a milestone targeting another toolkit repo to run its spec-writing **inside that milestone's worker** so tracker and specs bind to the target tree. A resumed milestone that declares such a target *and* carries review-flagged FRs satisfies both preconditions, and nothing ordered them. Worse, AC.4's own rationale — that any `/spec-write` in a worker is the forbidden proxy — read as an indictment of AC-STE-495.3's shipped route.

**The ground for choosing this direction rather than the other.** The prohibition `/deliver` actually carries is *"answering on the operator's behalf, paraphrasing, or pre-filling answers"*, plus batching. That is about **who answers**. The only where-based statement in the toolkit is a cost argument about an inserted relay hop, and a visible worker session inserts none — the operator types into it directly. `never in a spawned worker` was therefore over-broad, not a load-bearing invariant. Forcing the other resolution — cross-repo resumes inline — would have broken the tracker/specs binding that `AC-STE-495.3` exists to establish, which is a real capability loss to preserve a phrase that was protecting nothing extra.

**Second face, fixed by the same decision.** `resumeChain` had no target-repo awareness and always emitted the full `/implement → /ship-milestone → /pr` tail, so a resumed milestone whose target repo has no toolkit received a chain naming two ceremony stages that cannot exist there. It now takes the resolved route and emits the reduced chain (`/work`, `/pr`) for that case, and places `/spec-write` in the worker for the cross-repo case.

**Provenance.** The conflict was found by the STE-498 refactor pass after both FRs were green; the implementing session declined to resolve it, since adopting the reconciliation would have closed an AC by reinterpretation. It was escalated with all options and the evidence, and the operator chose the amendment. The interim shipped behaviour — surface the conflict and ask — has been replaced by the resolved routing, and the pin that protected the interim clause has been re-pointed at the scoped rule so a future trim still goes RED.
