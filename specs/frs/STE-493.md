# Approval gates carry a class, and a standing authorization covers only one of them

## Summary

The deliver orchestrator relays every worker gate to the operator, tracker-write prompts included, and separately forbids both the auto-approve marker and any fabricated approval. Those rules are individually right and jointly make a common operator instruction impossible to express: drive the mechanics yourself, but never merge without me.

A live run spent the operator's attention re-asking a milestone number they had already chosen minutes earlier and a branch name with exactly one correct answer, while the genuinely irreversible actions sat in the same undifferentiated queue. The operator stopped the run to say so. Three distinct kinds of gate are collapsed into one: what gets built, how it lands, and what cannot be undone.

## Requirement

Every gate the orchestrator relays carries one of three classes; an operator may delegate the mechanical class for the rest of a run by saying so, and no statement, however general it sounds, can ever delegate the irreversible class.

## Acceptance Criteria

- AC-STE-493.1: Gates are classified into exactly three classes — content, mechanical, and irreversible or outward-facing — and each class names who decides.
- AC-STE-493.2: Relay-every-gate remains the shipped default: a run in which the operator says nothing behaves exactly as it does today.
- AC-STE-493.3: An operator statement delegating the mechanical class is restated back once before it takes effect, so its scope is on the record.
- AC-STE-493.4: A recorded delegation is carried into every subsequently spawned worker's kickoff text, never as a mid-run message to an already-running worker.
- AC-STE-493.5: A delegation never covers merge, push to trunk, deploy, publish, or any outward-facing action — including when the operator's words are general, such as "drive it yourself" or "stop asking me"; those require a fresh instruction naming the action.
- AC-STE-493.6: The irreversible-class exclusion is enforced by a shared module and a gate-check probe rather than by prose alone, and every guard in it is mutation-verified.
- AC-STE-493.7: The delegation mechanism is distinct from the `<dpt:auto-approve>v1</dpt:auto-approve>` marker; `/deliver` still never injects that marker into any worker prompt or kickoff text.
- AC-STE-493.8: The FR records why this does not weaken STE-313: that AC governs headless runs, `/deliver` refuses non-tty stdin unconditionally, and the delegation can exist only where a live operator typed the words.

## Technical Design

`skills/deliver/SKILL.md` line 55 relays every gate including "any tracker-write prompts", and lines 59-60 carry the two prohibitions. No gate-class vocabulary exists anywhere in the toolkit — a sweep for "mechanical gate", "standing authorization", "gate class", and "gate taxonomy" across skills, docs, and adapters returns only unrelated uses of "irreversible".

The precedent to extend, not reinvent, is `requireCommittableBranch`, which already default-applies the branch gate under `isAutoMode` (AC-STE-228.7). The toolkit therefore already concedes that some gates are mechanical enough to default-apply when authorized; today the only authorization channel is the headless marker, which `/deliver` is forbidden to inject. This FR adds a second channel for the interactive case, which is why AC.7 requires the new mechanism to be distinct from the marker.

The STE-313 collision is real and must be argued rather than assumed. STE-313 AC.5 names "standing instruction" prose, system-reminder text, autonomous-mode, and pre-baked command-args as explicitly unacceptable auto-apply triggers, with the byte-checkable marker as the sole evaluation path. That AC governs headless runs, where nobody typed anything and prose can be forged by an injected reminder. `/deliver` hard-refuses under non-tty with no carve-out, so the two domains are disjoint: a standing authorization that can only exist in an interactive session, where a live human demonstrably typed the words, lives where STE-313 has no jurisdiction.

Tier assignment: the irreversible-class exclusion is Tier 1 (module plus probe plus mutation-verified tests) because a silent drift there causes an unrecoverable action. Gate classification itself is Tier 2 (prose with targeted literal probes).

## Testing

Module-level tests for the classifier and for the standing-authorization scope, with the irreversible-class exclusion mutation-verified in both directions: a general-sounding delegation must not reach the irreversible class, and a specific instruction naming the action must. Gate-check probe registration with its own coverage. Byte-checkable literal probes for the three-class vocabulary and the kickoff-carry rule. `bun test` full root.

## Notes

Origin: 2026-08-17 field report, Findings 1 and 2, which the report lists separately. They are one change: the gates originate in `/implement`, `/ship-milestone`, and `/pr`, so `/deliver` can only choose whether to relay, and its own no-fabricated-approval rule forbids answering. Reclassifying gates without a delegation mechanism would be inert.

Default posture was an explicit operator decision on 2026-08-17: relay by default, delegation only on an explicit operator statement. The alternative — delegating the mechanical class out of the box — would have silently changed shipped behaviour for every user and contradicted CLAUDE.md core principle 4 ("Human approval before commit"), which would then have needed rewording. Relay-by-default keeps that principle intact.

The taxonomy is deliberately not hardcoded per class-membership: this repo's operator delegates merges to the agent after independent verification, while the operator in the reported run reserved them. A fix that baked in either posture would break the other.

**Why the first pass missed 8 of them — the reusable lesson.** The initial sweep list was built by grepping **literal strings** (`toBe(77)`, `"77 numbered"`). Several pins are **regex forms** that no literal grep finds: `toMatch(/\b77\b\s+numbered/)`, `/layers 77 probes/`, `Array.from({ length: 77 }, …)`. Worse, `m109-ste-394-docs-pins.test.ts` carries **meta-assertions that pin the regex *source text* of three other test files** (`expect(body).toContain("\\b77\\b.*numbered")`), so those had to move in lockstep or they would have kept pinning the retired form. A future count sweep in this repo will hit both shapes again: enumerate by running the failing gate, never by grepping one spelling.

**One decoy correctly left alone:** `tests/m121-ste-461-lock-commit-conformance.test.ts:482`'s `expect(subject.length).toBe(77)` is a commit-subject **character** length, not a probe count. A sweep that "fixed" it would have been a perfect pin moved onto the wrong subject.

**Both new registry rows became carriers of the probes they register.** Probe #78 failed on row #78 at first write, because the row said "merge, push to trunk, deploy, publish" while the *derived* required phrases are `merge a pull request`, `deploy to an environment`, `publish a package or release`, `send an outward-facing message`. The probes catching their own registration prose is the strongest non-vacuity evidence either could produce.

**A genuine safety hole, audit-found and closed.** `IRREVERSIBLE_GUARDS.push_to_trunk` originally required `trunk|main|master` to appear after the verb, so `push to origin`, `push the tag` and `force-push the branch` were **not** caught — a standing authorization would have silently covered them. It was the only guard whose misses fell on the *unsafe* side; every sibling is verb-only and fails closed-broad. Widened to verb-only, with the rationale recorded in place. Verified no `mechanical` gate in `GATE_REGISTRY` names a push, so the widening cannot reclassify one.

**Recurring defect class — the wrong-subject pin, twice in one milestone.** Logged as a pattern rather than two incidents, because it recurred inside a single milestone with different surfaces each time:

1. **STE-492** — the group-14 capture predicate hand-rolled `/^M\d+$/`, so a genuine Jira- or tracker-less-leg capture would have been graded `ok: false`. The pin was perfect and pointed at the wrong grammar.
2. **STE-493** — the first pin for the push-guard widening asserted `delegationCovers()` against an ad-hoc **unregistered** gate object. `delegationCovers` returns `false` for any unregistered gate, benign or not, so those five legs would have passed with the push guard **deleted entirely**.

Both were caught the same way, and it is the method worth keeping: **mutation-test the fix and predict the kill count first.** Instance 2 surfaced because the mutation killed 1 test where ~6 were expected, and the gap was chased instead of the green being banked. A mutation that kills fewer tests than predicted is evidence about the *pin*, not reassurance about the code. Re-pointed at `isIrreversibleGate` / `classifyGate` — the guard-driven entry points that actually read the text — after which the mutation kills 6, and `push the release commit to trunk` correctly *survives* it because it matches both the narrow and broad forms, which is the isolation half.

**Combined REFACTOR pass, disclosed.** STE-493 and STE-494 were refactored in one pass rather than two. Their probe modules landed in a single registration sweep and share a carrier/derived-phrase idiom, so a per-FR pass would structurally miss the duplication *between* them. It found it: `carrier_phrase_probe.ts` now owns the mechanism both had re-derived (213+224 lines → 133+146+177), each probe keeping its own `PROBE_ID`, anchor, and derived phrase source. Probe independence was re-verified post-hoist with two fixtures — a `#79`-only carrier yields zero `#78` violations and vice versa. The refactorer separately *declined* to unify `IRREVERSIBLE_GUARDS` with `LOOSENING_GUARDS`: their matchers have different arities, and for Tier-1 rules independence is the property — a defect in one guard list must not be able to propagate to the other.
