# A feature request's milestone container is found before its ticket is created

## Summary

Adding a feature request to a milestone whose container is outside the bound tracker project creates the ticket, then fails to attach it, leaving an orphan the tracker tools cannot delete.
The container is now resolved before any create, by the code the attach itself runs.
A ticket already bound to its container is left alone rather than refused, and a refusal names the project the container is in.

## Requirement

Measured at HEAD ac1f3cb (findings MI-4 with the skeptics' correction, ENUM-4, RP-3):

- `/spec-write` calls `Provider.sync` (the create) and only afterwards `attachProjectMilestone` (`skills/spec-write/SKILL.md:107-111`). When the milestone's container is absent from the bound project (the repoint-mid-milestone case: plan `M_GB_40`, repository now bound to `GF`), the attach throws `MilestoneEpicNotFoundError` after the ticket already exists in `GF`. The result is a parentless ticket, a loud `milestone_attach_failed`, and an FR file that is not rolled back.
- `attachProjectMilestone`'s epic arm enumerates the configured project's Epics before it reads the ticket (`attach_project_milestone.ts:717-746`). So `/implement` step 0.e refuses a legacy FR that is correctly parented to an Epic in the old project.
- The refusal for a token whose Epic lives in another project reads exactly like a missing Epic. The operator cannot tell a stranded binding from a typo.

Required behaviour:

1. The attach's find leg is factored into one exported resolver that both the attach and a new front door call.
2. `/spec-write` resolves the target before the draft gate and before any create. In a shared repository, the tracker-write hook refuses an FR create that lacks a resolved-target receipt.
3. The attach reads the ticket first and makes no call beyond that read when the binding is already present.
4. A cross-project miss names both projects.
5. In a shared repository, a new plan may bind only a container this session's milestone decision chose, so a join that writes nothing to the container still cannot pass unapproved.

Old clients keep today's order. This FR's release version joins the floor the plan tells shared repositories to declare.

## Acceptance Criteria

- AC-STE-611.1: `resolveAttachTarget(provider, project, milestoneName)` is exported from `adapters/_shared/src/attach_project_milestone.ts`. It returns the binding surface (`parent` with the Epic key, `label`, `object` with the milestone identifier, or `object-create` for a grandfathered numeric Linear name with no match), or it throws the permanent refusals `attachProjectMilestone` throws today, unchanged in class and text except as AC.5 says. `attachProjectMilestone` obtains its target only through this function. An agreement suite drives both over one fixture table (Epic-keyed, numeric, pre-key title, Linear identifier, Linear numeric name; hit and miss each), and a mutation that gives the attach its own divergent find leg turns that suite red.
- AC-STE-611.2: Front door. `bun run adapters/_shared/src/attach_project_milestone.ts <projectRoot> <mode> <project> <planFile> <listingFile>` exits 0 printing `surface=` and, when the surface has one, `key=` or `id=`, and writes one receipt of kind `attach-target` through the receipt store of STE-602 under `<projectRoot>`, printing its `dpt-receipt:` line, also when run from another repository's checkout (relocated leg). A numeric Jira token resolves to `surface=label` and prints `listing=not read`. A permanent refusal exits 1 with the refusal on stderr, empty stdout and no receipt. So do an unreadable plan file, an unreadable or malformed listing, an unrecognised listing shape, a Jira page that is not the last page, and incomplete argv. The test spawns the command as a subprocess.
- AC-STE-611.3: Resolve before create. `skills/spec-write/SKILL.md` orders the front door before the step 4 draft gate and before `Provider.sync`, and names the resolved container in the gate preview. A refusal ends the run with zero tracker writes and no FR file. The prose is edited in place: 358 split-lines, the line 111 prefix unchanged, zero new STE tokens. The executed half: in a target repository that declares `repo_tag`, `pre-tracker-write-gate` (the hook of STE-607) refuses an FR create unless an `attach-target` receipt from this session in the target repository resolved a surface in the same project; when the create payload names a parent, as the payload of STE-604 does, that parent must equal the key the receipt resolved. An FR create here means an Atlassian issue create whose type is not Epic, or a Linear issue save without an `id`. `attach_project_milestone.ts` is appended to that hook's `RECEIPT_ANNOUNCING_MODULES`. The rule is added to that hook's `create` class, beside its `create`-receipt rule, and has a permit leg (exit 0), a forbid leg (exit 2, NFR-10 naming the front door), an unreadable-receipt leg (treated as absent) and an other-session leg (does not satisfy), each driven through `templates/hooks/process/pre-tracker-write-gate.sh` with a recorded payload on stdin. In a repository with no `repo_tag`, both payloads exit 0 with empty output.
- AC-STE-611.4: Bound first. `attachProjectMilestone` reads the ticket before any enumeration. When `milestoneBindingPresent` already holds for the declared binding, it returns without calling `listEpics` or `listMilestones` and writes nothing. A legacy FR whose parent is `GB-40`, attached for `M_GB_40` with the configured project `GF`, returns this no-op; on HEAD it throws `MilestoneEpicNotFoundError`. Control: the same FR with no parent under `GF` still refuses. Existing suites that pin the old list-then-read call order are amended in the same commit, each listed in the implementation notes.
- AC-STE-611.5: A cross-project miss names the project. When an Epic-keyed token does not start with the forward-sanitized configured project (`M_<project>_`), the `MilestoneEpicNotFoundError` names the configured project and the token. Its remedy says the Epic lives in another project: set the parent by hand in the tracker, or archive the FR before a repoint. It never says to create an Epic. A same-project miss keeps today's text byte-for-byte (control). Linear tokens carry no project, so this leg is not applicable there and the suite asserts that it is skipped, not passed.
- AC-STE-611.6: The stranding scenario. A fixture repository declares `repo_tag`, is bound to `GF` and holds the active plan `M_GB_40`. For a new FR in that plan, the front door exits 1 naming `GB` and writes no receipt, and the hook then refuses the FR-create payload for that repository, so no ticket can be created. On HEAD neither piece exists and the create is unguarded; because both are new, this leg is graded red against a faithful pre-change-semantics sibling (create first, attach after), as STE-597 did for its own new module. Control: bound to `GB`, the target resolves to `GB-40`, the receipt is written and the hook permits the create. Join-path permit leg: in a shared project, a plan whose Epic another repository minted resolves to that Epic, and the create proceeds.
- AC-STE-611.7: Provenance, closing the zero-write join. In a repository that declares `repo_tag`, when the plan file passed to the front door is absent from the target repository's `HEAD` commit (a plan this session is writing), the front door exits 1 with an NFR-10 refusal and writes no receipt unless a `milestone-decision` receipt of STE-608 from this session in the same repository decided that container: a join whose key is the resolved key, or a create whose title equals the resolved container's listed title. The refusal names the resolved key and says the milestone was bound without a decision. Legs: a new plan naming a sibling's Epic with no decision receipt (the live silent join) refuses, and is graded red against the pre-change-semantics sibling; the same plan after a decided join by key passes; after a decided create of that title passes; a plan already committed at `HEAD` passes with no decision receipt (continuing work across sessions); a receipt from another session does not satisfy; an unreadable or malformed receipt counts as absent; a target that is not a git repository refuses, because `HEAD` cannot be read. In a repository without `repo_tag` this check does not run and the output is unchanged.
- AC-STE-611.8: Every clause asserting new behaviour is falsifiable: it fails on the pre-change bytes, passes on the post-change bytes, and the direction is recorded per clause. Controls, negative guards and no-regression pins are exempt by construction.

## Technical Design

The resolver is the attach's own find leg, lifted out and exported, so the pre-create check and the attach cannot disagree. The module is already reachable through the mint modules, so its front door moves no reachability pin. Reading the ticket first reuses `milestoneBindingPresent`, the predicate the archival assertion already trusts. The cross-project remedy uses forward sanitization only, because a token cannot be turned back into a key.

## Testing

Drive the resolver and the attach against recording providers: bound legacy ticket, missing parent in each project, numeric label, Linear identifier and numeric name. Spawn the front door with a missing listing, a malformed listing and a not-last page. Run the hook's shell entry point on FR-create payloads with a receipt, without one, with an unreadable one and with another session's. The stranding fixture checks the call log. The provenance legs use a git-initialised fixture whose plan is committed in one leg and uncommitted in the others, with decision receipts written through the receipt store.

## Notes

- A grandfathered numeric Linear name with no match still auto-creates in an unshared project. In a shared one, the milestone-create hook rule of STE-608 refuses that save.
- An older client can still leave a parentless ticket; probe #26 already reports an active FR whose ticket lacks its milestone.
