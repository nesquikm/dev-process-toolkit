# An unrecognised layout is a loud signal, not a silent pass

## Summary

When the guard recognises nothing in a staged set it reports the commit as carrying nothing to guard and exits successfully — the same outcome as a commit that truly has nothing to guard.

So a guard that did not apply is indistinguishable from one that passed, and a clean exit reads as a check that ran.

That is how the defect survived: on an unsupported stack it never said so. Widening what it recognises cannot close that.

## Requirement

A staged set the hook cannot classify against any known stack produces a distinct, visible outcome naming the reason, separate from the outcome for a set that carries nothing to guard. The distinction survives in the exit path and in what the operator reads, so silence is never the answer to an unanswerable question.

## Acceptance Criteria

- AC-STE-548.1: A staged set on a project whose stack the toolkit cannot identify produces an outcome distinct from the one produced by a staged set that carries nothing to guard. The two are compared directly on fixtures differing only in recognisability.
- AC-STE-548.2: That outcome names its reason in the text the operator reads — which project, and that no stack was identified — rather than resolving to a bare status.
- AC-STE-548.3: A project whose stack IS identified but whose staged set genuinely carries no source-and-test pair keeps today's quiet outcome. The new signal reports inability to look, never absence of anything to see.
- AC-STE-548.4: The signal is not a refusal. A commit is not blocked because the toolkit does not know the stack; blocking on the toolkit's own ignorance would punish the operator for it.
- AC-STE-548.5: Falsifiability — collapsing the new outcome back onto the pre-existing quiet one turns a fixture green that this criterion requires to be distinguishable, asserted by a mutation.
- AC-STE-548.6: The three outcomes are exhaustive and mutually exclusive over the classifier's inputs: nothing to guard, requires the run, cannot tell. A staged set resolves to exactly one, asserted rather than assumed.

## Technical Design

`StagedClassification` gains a fourth member for the unidentifiable case, distinct from `no-fr`. `classifyStagedPaths` returns it when the shared marker detection resolves no stack, which is the one condition today's code silently folds into `no-fr`.

The hook's exit path treats it as advisory: exit 0 with a named line, not a refusal. AC.4 is the reason — the operator did nothing wrong, and a guard that blocks on its own ignorance gets disabled, which costs more than the miss it was preventing.

The line follows the house NFR-10 shape for its reason and remedy so it reads like every other signal the toolkit emits, and so an operator can act on it by naming their stack rather than by guessing.

## Testing

`tests/pre-commit-tdd-orchestrator.test.ts`.

- AC.1 — two fixtures differing only in whether a stack marker is present, asserting different classifications. The pair is the assertion; either alone proves nothing about the distinction.
- AC.2 — assert the emitted text contains the project and the reason, matched on the real output rather than on a format string, so a renamed field fails here rather than silently later.
- AC.3 — a recognised stack with a staged set carrying no source-and-test pair still yields `no-fr`, with a positive control in the same test showing the same fixture yields `tdd-required` once a test file is added. Without the control this leg passes on a classifier that returns `no-fr` for everything.
- AC.4 — assert the exit status is 0 on the unidentifiable path, and that the commit is not refused. A test that only reads the text would miss a refusal introduced later.
- AC.5 — mutation: map the new member back onto `no-fr` and assert AC.1's pair stops differing.
- AC.6 — enumerate the classifier over a fixture matrix and assert every input lands in exactly one of the three, so a fourth silent path cannot be added without failing here.
