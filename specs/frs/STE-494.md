# Merge policy can be tightened conversationally, never loosened

## Summary

The run's merge policy is readable only from the project's CLAUDE.md, so an operator who says "don't merge anything" mid-run has said something the orchestrator cannot act on. Reaching the safest setting requires editing configuration before the run starts, which is precisely when the operator does not yet know they will want it.

The shipped default is the one that asks, which under a flat relay adds another prompt per milestone. The opposite direction must stay closed: the automatic setting is never inferred by any path, and a conversational channel that could reach it would quietly undo that guarantee.

## Requirement

An operator can tighten the run's merge policy by saying so, the tightening holds for the rest of the run, and no conversational path can ever reach the automatic setting.

## Acceptance Criteria

- AC-STE-494.1: An operator statement restricting merging applies for the remainder of the run without editing CLAUDE.md.
- AC-STE-494.2: The override is restated back once, so its scope is on the record.
- AC-STE-494.3: The legal transitions are exactly the tightening ones: `offer` to `never`, `auto` to `offer`, and `auto` to `never` are accepted; every loosening transition is refused.
- AC-STE-494.4: No conversational statement can enable `auto` — the only enabling act remains the operator writing `merge_policy: auto` into the orchestration config themselves.
- AC-STE-494.5: The ratchet is enforced by a shared module whose refusal carries the NFR-10 canonical shape, and every loosening guard in it is mutation-verified.
- AC-STE-494.6: The conversational override never persists to CLAUDE.md; persisting it stays a separate, explicit operator request.
- AC-STE-494.7: The FR records why this does not contradict STE-463 AC.3 or STE-464 AC.7 — a tightening transition cannot produce `auto`, so "auto is never inferred" holds byte-intact.

## Technical Design

`MERGE_POLICIES` in `adapters/_shared/src/orchestration_config.ts` is a closed three-value set read only from the `## Orchestration` block of CLAUDE.md, with defaults `{ defaultEffort: "ultracode", mergePolicy: "offer" }`. The module's header comment states that values are matched literally with no inference, and `docs/deliver-reference.md` states that the only enabling act for `auto` is the operator writing the config line.

The restriction-only ratchet is what makes a conversational override compatible with that guarantee rather than a contradiction of it. Tightening transitions form a partial order toward `never`; since no tightening transition has `auto` as its target, no conversational path can reach `auto`, and the "never inferred" property is preserved by construction rather than by a runtime check that could drift.

This is Tier 1 in the milestone's hybrid verification split — a module plus probe plus mutation-verified guards — because a loosening that slipped through would cause an unrecoverable action (an unwanted merge). The spec-research seed flagged the naive form of this feature as directly contradicting STE-463 AC.3; the ratchet is the reconciliation and AC.7 requires it to be argued in writing rather than assumed.

### Why this contradicts neither prior AC

AC.7 names two shipped ACs, and each needs its own argument. The first draft of this section argued only the first, which is a spec defect found during implementation; both are now stated.

**STE-463 AC.3 — "`auto` is never inferred."** That AC governs how `merge_policy` is *read*: `MERGE_POLICIES` is a closed set matched literally, with no case coercion, no quote stripping, and no inference. The ratchet does not touch the reader. It sits downstream of it, transforming an already-parsed value into a tighter already-parsed value. Its legal transitions are exactly `offer → never`, `auto → offer`, `auto → never`, and **no tightening transition has `auto` as its target**, so the set of values a conversational path can produce is `{offer, never}` — a set `auto` is not in. The guarantee is preserved *by construction* rather than by a runtime check that could drift, which is the stronger form: even with every loosening guard dropped, `applyOverride` refuses an `auto` target unconditionally and ahead of the guards, so no mutation of the guard list can make `auto` reachable.

**STE-464 AC.7 — "`auto` is strictly opt-in; the only enabling act is the operator writing `merge_policy: auto` into the orchestration config."** This is the *enabling* claim rather than the *inference* claim, and the ratchet leaves it byte-intact for the same structural reason plus one more: the override is **non-persistent**. AC.6 requires that it never writes to CLAUDE.md, so a run's spoken tightening cannot become a later run's configured state. The config file therefore remains the sole surface on which `auto` can ever be enabled, and it remains writable only by the operator. A conversational channel that could reach `auto` would have violated this AC even while satisfying STE-463 AC.3 — the two are genuinely separate obligations, which is why arguing only the first would have left the change correctly rejectable by a reviewer.

The direction of the ratchet is what makes both arguments hold at once: it is a partial order toward `never`, and `auto` is its maximal element. Restriction-only means the one value both prior ACs protect is precisely the one value no transition can output.

## Deviations

**AC.7 was unsatisfiable as originally written — a spec defect, not a reinterpretation.** The AC requires the argument against *both* STE-463 AC.3 and STE-464 AC.7, but the FR body as drafted argued only the first. The two are separate obligations and need separate arguments: STE-463 AC.3 is the **inference** claim (how `merge_policy` is *read* — closed set, literal match, no coercion), while STE-464 AC.7 is the **enabling** claim (what can turn `auto` *on*), and it is AC.6's non-persistence that protects the second. A reviewer who checked AC.7 against the drafted body would have correctly found it unmet. The `### Why this contradicts neither prior AC` section was added during implementation to argue both. Recorded as a defect in the drafted spec rather than smoothed over.

## Follow-up — `resolveStatement` precedence, declined deliberately

`resolveStatement` tests `NEVER_PATTERNS` before `OFFER_PATTERNS`, so a statement matching both resolves to the tighter value. The known cost: **"don't merge without asking me" is an explicit request *to be asked*, and it resolves to `never` — meaning the operator is never asked.** That is a misread of intent, and only AC.2's restate-once catches it.

This was **not** changed in M129, deliberately. Reversing the precedence wholesale risks the opposite error — a statement meaning `never` resolving to the looser `offer` — which is the unrecoverable direction for a Tier-1 rule: erring tight costs one keystroke, erring loose merges something. Changing precedence logic on a safety rule mid-implementation is how the safe version gets lost.

**A resolution exists that loosens nothing**, sketched here so the next person does not have to rediscover the tension: match the *more specific* ask-request shape — "without asking", "ask me first", "ask me before" — **ahead of both** `NEVER_PATTERNS` and `OFFER_PATTERNS`. An explicit request to be asked then resolves to `offer`, while every ambiguous statement still falls through to the tight default unchanged. This is additive precedence on a narrower pattern, not a reordering of the existing two, so no statement that resolves to `never` today can become `offer` under it. Needs its own FR, its own corpus entry, and the same drop-one mutation treatment the existing guards carry.
