# The inventory of unrunnable orders is generated, never written down

## Summary

The delivery orchestrator is one instance of a class. Across the toolkit, skills name shared modules and tell the reader to run them, and most of those modules cannot be run. Counting them by hand produces a list that is stale the day it lands and acceptance criteria nobody can check.

So the list is produced by a check that walks the shipped surfaces and classifies every reference it finds: ordered, where the surface tells the reader to run that module; descriptive, where it merely names it; or harness, where the module is executed by the test run rather than by a skill. Reachability is decided mechanically. The criterion that matters pins the count of orders that are both given and unrunnable, so the next one reddens the run that introduces it.

The check's classifier is phrase-based, which makes it the part most likely to be wrong while looking right. It gets its own fixtures and its own mutation pass.

## Requirement

A gate check generates the inventory of module references across the shipped surfaces, classifies each one, and pins the count that is both ordered and unreachable.

## Acceptance Criteria

- AC-STE-517.1: A new gate check walks the shipped markdown surfaces and emits one classified record per module reference: the surface, the line, the module, its class, and whether it is reachable. Nothing in the record is hand-authored.
- AC-STE-517.2: The walk covers both shipped trees — the skills tree and the docs tree — reusing the existing shared walk rather than a second one. Restricting to skills alone is rejected: references that are ordered and unreachable live in the docs tree too, and a check that cannot see them is not measuring the class.
- AC-STE-517.3: Classification is one of exactly three values, and the ordered test is scoped to the reference's own line. A phrase elsewhere in the file does not make a reference ordered.
- AC-STE-517.4: Reachability is mechanical: a module is reachable when it carries a command-line entry point, or when something that carries one imports it, directly or transitively. Anything else is unreachable.
- AC-STE-517.5: AC.4 is validated against both boundary cases rather than asserted. Modules that carry an entry point and have no non-test importer are reachable — the nine this FR was written against are asserted as a subset of the measured set, not as its total. A module that carries no entry point and that nothing with one imports, directly or transitively, is unreachable.
- AC-STE-517.6: The count of references that are both ordered and unreachable is pinned to the value the check itself reports at implementation time, and the pin is derived from a run rather than typed from any prior document.
- AC-STE-517.7: The orchestrator's own ordered-and-unreachable count is zero once this milestone lands, asserted directly, and it was non-zero before.
- AC-STE-517.8: The classifier has its own fixture set covering each of the three classes and both reachability outcomes.
- AC-STE-517.9: AC.8 is mutation-verified: a fixture deliberately misclassified turns the check red. A classifier that cannot fail on a wrong fixture is graded as no classifier at all.
- AC-STE-517.10: The check reports non-vacuously in both directions — a surface with no module references yields no records, and a seeded surface yields exactly its records.
- AC-STE-517.11: The check never crashes the gate run: a malformed or unreadable surface surfaces as a verdict, not a throw.
- AC-STE-517.12: The check's severity does not fail the gate for pre-existing references it merely catalogues; only the pinned count fails.

## Technical Design

The mechanism already exists. The shared carrier-phrase engine walks the skills and docs trees and scans files for phrases, hoisted out of two probes that had each written it once. This reuses that walk. What it does not reuse is the file-scoped phrase test, and that departure is deliberate: the question here is whether the surface says to run this reference, which is a per-reference question. A file-scoped test would classify every reference in any file containing one such phrase as ordered, which collapses the distinction the three classes exist to draw. Line-scoped also avoids a proximity window reaching into adjacent pre-existing text, the wrong-subject shape recorded here twice.

The reachability rule corrects the approved design. The design defined it as an entry point AND at least one non-test consumer. Measured, that rule calls nine shipped modules unreachable that are perfectly runnable command-line front doors, one of them the front door an existing gate check invokes — and it would call this milestone's new front door unreachable on the day it ships, so the fix would fail its own test. The transitive rule preserves what the second clause was for: the resume classifier carries no entry point and nothing with one imports it, so it stays exposed, which is the reason the clause was written.

The inventory total is deliberately not pinned. The design carried one, and it does not reproduce — measured now, the skills tree alone holds more distinct references than the design attributed to the whole toolkit, and the design's per-skill breakdown has already drifted from disk. That is the argument for generating rather than writing down, made by the design's own number.

## Testing

Fixtures cover each class and each reachability outcome as small synthetic surfaces, so the classifier is tested in isolation from the shipped trees.

The mutation pass is what the criteria are worth. A fixture whose class is deliberately wrong must turn the check red; if it does not, the check is asserting the shape of its output and nothing about its correctness.

Both boundary cases in AC.5 are asserted as named cases, since they are the two the rule was corrected to get right.

Non-vacuity runs both directions, so an empty result is shown to mean nothing found rather than nothing looked at.

## Notes

Scope is the class, not the instance. The orchestrator's own ordered-and-unreachable references are the ones this milestone repairs; the rest are catalogued and left, and the pin is what stops the number growing quietly.

## Implementation notes

AC.5's original text named the resume classifier as the unreachable boundary case, on the measurement that nothing carrying an entry point imported it. That stopped being true inside this milestone: STE-513 gave the decision front door an entry point and a value import of the classifier, so under AC.4's transitive rule the classifier is now reachable. The requirement is unchanged — validate the rule against a reachable and an unreachable case — but the example had to move, and the tests assert the negative boundary on a module measured unreachable today while pinning the classifier's real status as a named drift test so the contradiction stays visible rather than being quietly dropped.

The positive boundary moved for the same reason. The count of entry-point-carrying modules with no non-test importer measures higher than the nine this FR named — the original list omitted two that predate the milestone, and this milestone added another front door of its own. The nine are asserted as a subset; pinning a total would have made the criterion fail on a correct tree.

Two further numbers in this FR's own text were hand-carried and did not survive measurement, which is the failure mode the FR exists to abolish. AC.7 claimed the orchestrator's pre-milestone ordered-and-unreachable count was five; run the shipped classifier against the milestone's base commit and it measures one. AC.2 claimed four such references in the docs tree; the shipped check measures fifteen. Both figures came from an ad-hoc script written before the classifier existed, using a different phrase list and a different reachability rule, and neither is a quantity the shipped check would ever have reported. Both clauses now state the direction rather than a figure, because the only number this FR is entitled to assert is one its own check produced.

The zero AC.7 asserts is module-granular, not order-granular, and that distinction is worth keeping in view. An order naming a module is counted carriable once anything with an entry point reaches that module. One order on the orchestrator's surface names a configuration field that nothing in the tree exposes, so the module is reachable while that particular instruction still is not. Closing that gap means grading the member an order names, not just the module, and that is a wider check than this one.
