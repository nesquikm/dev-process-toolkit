# A milestone declares the repo it targets, and /deliver routes on it

## Summary

The design and spec-writing phases run inline in the invoking session, which binds spec-writing to that session's tracker and its specs tree. A milestone belonging to a different repo would therefore file its requirement against the wrong tracker project and write it into the wrong repo.

A repo with no toolkit installed has no ceremony to run at all, so the implement, ship, and pull-request chain is meaningless there. A live run spanning three repos — two with the toolkit on different tracker projects, one with none — worked around both cases by hand, because the pipeline has no vocabulary for either.

## Requirement

A milestone can name the repo it targets, and the orchestrator routes each milestone to the phase topology that repo can actually support.

## Acceptance Criteria

- AC-STE-495.1: A milestone plan can declare a target repo; a milestone that declares none means the invoking session's repo, and every existing single-repo plan behaves exactly as it does today.
- AC-STE-495.2: A milestone targeting the invoking repo keeps the design and spec-writing phases inline, unchanged.
- AC-STE-495.3: A milestone targeting another repo that has the toolkit runs its spec-writing inside that milestone's worker, as the first step of that worker's chain, so tracker and specs bind to the target repo.
- AC-STE-495.4: A milestone targeting a repo with no toolkit runs a reduced chain — do the work, open a PR — with no ceremony stages.
- AC-STE-495.5: A reduced chain is not held to the full ceremony's hand-off contract; the orchestrator does not halt it for stages that do not exist there.
- AC-STE-495.6: The serial one-worker-per-milestone invariant is unchanged; multi-repo routing introduces no concurrency.
- AC-STE-495.7: A declared target repo that cannot be located refuses in the NFR-10 canonical shape rather than silently falling back to the invoking repo.

## Technical Design

`/spec-write` resolves everything relative to the invoking session's working directory: `buildResolverConfig(claudeMdPath, adaptersDir)`, the specs directory, and `specs/tracker-config.yaml`. The fix for the cross-tracker case is therefore topological rather than parametric — running `/spec-write` inside the target repo's worker rebinds tracker and specs naturally, with no alternate-root plumbing to thread. That makes AC.3 substantially cheaper than the field report implies.

AC.5 is the interaction with the fence contract in this milestone's hand-off FR: a reduced chain must not be measured against a contract written for the full ceremony, or the toolkit-less path would halt on stages it was never meant to run.

The spec-research seed found no FR precedent for multi-repo or target-repo routing anywhere in the active or archived spec set — this is greenfield, which is why AC.1 fixes the default (absent declaration means the invoking repo) so no existing plan changes behaviour.

Tier 2 in the milestone's verification split: prose routing rules with targeted literal probes, since a misroute is recoverable at the confirmation surface rather than unrecoverable.

## Testing

Routing coverage for all three cases: invoking repo, cross-tracker toolkit repo, and toolkit-less repo. Assertion that an absent target-repo declaration is byte-identical to today's behaviour on an existing plan. NFR-10 refusal coverage for an unlocatable target repo, including that no fallback occurs. Serial-topology invariant asserted unchanged. `bun test` full root.

## Notes

Origin: 2026-08-17 field report, Finding 3. The report treats one case as primary; the operator decided on 2026-08-17 to cover both, because the half-fix would leave a documentation repo still needing hand-driving.

The report frames the cross-tracker case as needing new plumbing. It does not: because `/spec-write` binds to its own working directory, moving the call into the target repo's worker is sufficient. Recording this because the cost estimate in the report is higher than the actual one.

## Deviations

**AC.3 and AC.4 shipped their routing to the OPTIONAL surface only, and the audit was right to rate them Partial.** Every routing rule was implemented and mutation-verified in `adapters/_shared/src/target_repo.ts`, but the only prose carrying it was `docs/deliver-reference.md` — the file `skills/deliver/SKILL.md:15` marks *"not required reading"*. The operative skill had zero occurrences of `target_repo` and still stated the unconditional inline-phases clause and the unconditional single chain. This is STE-492's defect, committed four FRs after STE-492 repaired it, with no cap pressure to excuse it (119 of 358 lines). Fixed: the three routes, the toolkit-presence rule, the NFR-10 refusal, and `routeMilestone` as the decision function now live in `skills/deliver/SKILL.md` § Phases 1–2. Recorded as a first-class process finding in `specs/plan/M129.md` § Findings about the process, not the code.

**Two of four prose pins were satisfied by PRE-EXISTING text — a new shape of the wrong-subject pin, and the fourth instance in this milestone.**

The pins used `nearby(anchor, needle, window)`: true when both strings occur within `window` characters. The anchor was `target_repo`, a token that genuinely appears nowhere in either surface at HEAD — so the pins read as new-text-only. They were not. The new `## Target repo` section was inserted directly beneath `docs/deliver-reference.md`'s **pre-existing Phase table**, whose rows already read *"Inline, invoking session"* and *"One fresh spawned visible worker per milestone, strictly serial"*, verbatim in HEAD. The 900-character window reached back into that table, so the *needle* half matched shipped text. The audit proved it by stubbing the whole new section — token kept, every routing claim stripped — and two of four pins still passed.

**The generalisable rule:** a two-anchor proximity pin only guarantees the **anchor** is new. The needle half is free to match anything inside the window, so a pin whose new section is inserted adjacent to topically similar shipped text is satisfiable by that shipped text. **Slice to the new section; do not widen the window.** Fixed here with a `routingProse()` helper that evaluates those pins against only the sections mentioning the key. Re-running the audit's exact stub mutation now kills **six** tests where it killed two.

**The test file's own header made this harder to find, and that is part of the finding.** It asserted *"EVERY PROSE PIN IS ANCHORED ON A TOKEN THAT DOES NOT EXIST TODAY"* — true of the anchor, false of the pin. A header documenting the property the author *intended* rather than the one they *achieved* is worse than no header, because it stops the next reader from checking. The header even recorded testing the unanchored variant without noticing the anchored variant inherits the same window.

**A cross-FR contradiction, the third of its shape in this milestone.** `deliver_stage_capture` validated the fence's `stage:` scalar against the full-ceremony triple only, while this FR's routing adds `work` (reduced chain) and `spec-write` (cross-repo). A healthy reduced-chain worker emitting `stage: work` was graded `ok: false` by the predicate that grades it — fixture group 14 would have failed a correct run, while AC.5 says that chain's fence is fully conformant. Fixed by making `DELIVER_STAGE_IDS` the single vocabulary, with `StageId` derived from it (that direction, because `target_repo` already imports `DELIVER_STAGE_SECTIONS` and the reverse would be circular). Mutation-verified: narrowing back kills 2, and the isolation leg (`deploy` / `merge` / `release` still rejected) survives, so the widening is not a blanket accept. All three instances are catalogued together in the plan's process-findings section.
