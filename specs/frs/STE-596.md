# Design references reach the project's verification step

## Summary

A project can paste a mockup into its specs today and nothing ever opens it. The images are stored, cited, and checked for existence, but the step that runs a project's own verification skill hands it nothing about them. This milestone closes the last hop, so the verification step receives the design references bound to the feature being built, each with the caption its author wrote.

## Requirement

Phase 4b" resolves and runs a project's check skill without telling it anything about the spec it is checking. The storage half of the design-reference capability shipped in M91, which named the consuming half as a later milestone. M93 claimed that lineage, but its acceptance criteria are entirely about the verification hook itself — discovery precedence, run placement, failure classification, the blocking and advisory split — and not one of them mentions a design reference.

Close the gap: render the in-scope FR's design references into the resolved check skill's invocation through one shared renderer. The consumer is an arbitrary project-local skill file, a prompt rather than a program, so the payload must be useful with no contract on the consumer's side while staying canonical enough for a probe to grade.

## Acceptance Criteria

- AC-STE-596.1: Phase 4b" passes the in-scope FR's design references to the resolved check skill as part of its invocation, each row carrying the repo-root-relative path and the authored caption. An FR citing zero references is vacuous — the check skill is invoked byte-identically to today.
- AC-STE-596.2: The block is produced by exactly one shared renderer, which is the sole definition of its shape. No caller re-renders it, and any grader reads the same function the producer does.
- AC-STE-596.3: Rows come from `scanDesignReferences` filtered by the FR's own spec path (`DesignReferenceRow.file`). No second parser for the design-references section exists on the consumer side.
- AC-STE-596.4: `DesignReferenceRow` carries the caption, and a test asserts the whole row object with a single `toEqual`, so an added or renamed field cannot pass unnoticed.
- AC-STE-596.5: A cited image that does not resolve on disk is rendered as unresolved-and-skipped and never fails Phase 4b". Probe #61 already fails the gate for that condition at error severity.
- AC-STE-596.6: The `manual` verification path renders the same block in its reminder. The capability is not restricted to projects whose check skill auto-runs.
- AC-STE-596.7: Exactly one capability token fires per run, distinguishing "references passed" from "FR cites none", registered in `closing_summary_capability_keys` and in the `/spec-write` section 7 static map.
- AC-STE-596.8: The archived lineage claim in `specs/frs/archive/STE-347.md` is corrected in place to state what M93 shipped, what this FR ships, and that the app-driving visual comparison M91 specified remains the project-authored check skill's own job. The Phase 4b" argument-surface owner, STE-505, is amended to match.

## Technical Design

Widen the shared row to carry the caption its sibling row type already parses, then filter rows by the FR's own spec path. One renderer owns the block's shape; Phase 4b" injects it into the resolved check skill's invocation and into the manual-mode reminder alike. Unresolved paths render as skipped rather than raising, because the gate already fails them at error severity. The capability token registers in the canonical key set beside the existing verification family.

## Testing

Assert the whole row with one `toEqual`, because field-by-field assertions stay green against an added field. Pair a positive control beside every absence leg: a zero-count assertion passes on a permanently broken caller unless the same double records a non-zero count on a sibling fixture. Cover the vacuous path where an FR cites nothing, the unresolved-image path, and the manual-mode render. Extend the three existing design-reference suites rather than duplicating them.
