# Implement and deliver offer the pending upgrade at close-out

## Summary

Pending toolkit upgrades surface today mainly as a note in the full gate report.
This change offers to run the upgrade at the end of a standalone implement run.
It also adds an offer point at the end of a delivery run, which later offers reuse.
Both offers appear only when the upgrade check finds pending steps.
Neither offer appears in a run driven by an orchestrator.

## Requirement

### The offer source

A new module `adapters/_shared/src/upgrade_offer.ts`, shaped like `video_offer.ts`: `upgradeOfferLines(projectRoot)` awaits `runUpgradeStalenessProbe(projectRoot)` from `upgrade_staleness.ts` and returns its `rows` followed by `UPGRADE_OFFER_QUESTION` (`Apply the pending toolkit upgrades now? [y/N]`), or `[]` when `rows` is empty or `isToolkitManaged(projectRoot)` is false. The second guard matters because on an unmanaged tree probe #69 still returns the legacy-monolith row, whose hint routes to `/setup`, and `/upgrade` Step 0 refuses that tree. The CLI `bun run "${CLAUDE_PLUGIN_ROOT}/adapters/_shared/src/upgrade_offer.ts" <projectRoot>` prints the lines or nothing and exits 0. The module never walks the registry itself. A decline prints `UPGRADE_STALENESS_REMEDY`, imported, not retyped. Acceptance invokes `/dev-process-toolkit:upgrade`, which keeps its own preview and approval.

### /implement

Inside step 15, after Close sub-steps (b) and (c) settle, and before the ship-ready close offer on an FR-form run or the Phase 5 prompt on a milestone-form run, a standalone `/implement` runs the CLI and, when it prints, asks the question once. When the offer is made, the carried-forward `GATE PASSED WITH NOTES` block in the Phase 4 report keeps probe #69's rows and drops its remedy line, so the upgrade is named once. The prose lives in `docs/implement-reference.md` § Upgrade offer, behind a one-line pointer.

### /deliver

`skills/deliver/SKILL.md` gains a section `## Close-out — offers after the last milestone`, after `## Post-PR — merge-policy routing`. It runs once per run, after the last milestone's post-PR routing settles under any merge policy, in the checkout `/deliver` runs in. Its first offer runs the same CLI itself, because worker fences carry no notes. The section is the single place later close-out offers register; each one asks its own question, in registry order.

### Registry

`CONTINUATION_OFFERS` in `continuation_offer.ts` gains `implement_upgrade_offer` (skill `implement`) and `deliver_close_upgrade_offer` (skill `deliver`), each with every `ContinuationOffer` field (`file`, `asks` included), anchor `UPGRADE_OFFER_QUESTION`, `runsWhenAccepted: ["/upgrade"]` and `runsWhenDriven: []`. The count pin `CONTINUATION_OFFERS.length` in `tests/m143-ste-551-continuation-offers.test.ts` moves from 8 to 10, and its distinct-skill pin moves from 5 to 6, since `deliver` owns no offer today. M_d1b4b7 adds two more entries and leaves the distinct-skill pin at 6. Each span carries `DRIVEN_OMISSION_CLAUSE`, so probe #85 grades both.

## Technical Design

The offer reads probe #69's output and adds only a question. That keeps one source for what is stale and one remedy string.

Both close-outs register in the existing offer registry, so the driven-run rule and probe #85 apply without new machinery.

The delivery section is built as a list of offers in order. The retrospective milestone adds its entry there rather than a second section.

## Testing

Offer lines over stale, current and unmanaged trees, a source scan, registry and probe #85 rows, modelled runs, and span scans of both skills.
