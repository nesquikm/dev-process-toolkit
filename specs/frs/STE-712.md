# Implement and deliver offer the pending upgrade at close-out

## Summary

Pending toolkit upgrades surface today mainly as a note in the full gate report.
This change lets a project opt in to an upgrade offer at close-out.
With the setting on, a standalone implement run and a delivery run each offer the pending upgrade.
With it off, which is the default, both close-outs read exactly as they do today.
No offer appears in a run driven by an orchestrator.

## Requirement

Operator rule, 2026-11-04: toolkit behaviour does not change by default. So the offer is opt-in, and its default close-out is byte-identical to v2.101.x.

### The switch

`specs/settings.yaml` gains `close_out.upgrade_offer`, closed key set `{enabled}`, the same shape as `tracking.token_stats`. It is read through `loadProjectSection(projectRoot, "close_out")` (STE-706). An absent key or section, `enabled: false`, a legacy tree, a tree with no settings file and any loader refusal all mean off. No legacy home carries the key, and neither `/setup` nor the `settings-file` migration writes it. It enters the AC-STE-706.12 table as a `new` row naming this FR, and `docs/settings-reference.md` documents it.

No call is added while the switch is off (operator rule; review 4, R4-1 and R4-6). The switch is announced on output an existing call already prints. `gate_capture.ts`, which `/implement` already runs at step 14 on every run, before step 15, prints one extra last line, `upgrade_offer: on`, only when the switch is on. `deliver_decision.ts` prints one extra last line, `upgrade_offer: on`, after its eight fields, only when the switch is on. With the switch off, both outputs are byte-identical to the switch-absent output. `/implement` runs the offer CLI only when its `gate_capture.ts` call printed that line, and `/deliver`'s close-out runs it only when its decision record carried it. So a project with the switch off makes no extra call at close-out.

### The offer source

A new module `adapters/_shared/src/upgrade_offer.ts`, shaped like `video_offer.ts`. `upgradeOfferLines(projectRoot)` reads the switch first and returns `[]` when it is off, before running any probe. With the switch on, it awaits `runUpgradeStalenessProbe(projectRoot)` from `upgrade_staleness.ts` and returns its `rows` followed by `UPGRADE_OFFER_QUESTION` (`Apply the pending toolkit upgrades now? [y/N]`). It returns `[]` when `rows` is empty or `isToolkitManaged(projectRoot)` is false. The second guard matters because on an unmanaged tree probe #69 still returns the legacy-monolith row, whose hint routes to `/setup`, and `/upgrade` Step 0 refuses that tree. The CLI `bun run "${CLAUDE_PLUGIN_ROOT}/adapters/_shared/src/upgrade_offer.ts" <projectRoot>` prints the lines or nothing and exits 0. The module never walks the registry itself. A decline prints `UPGRADE_STALENESS_REMEDY`, imported, not retyped. Acceptance invokes `/dev-process-toolkit:upgrade`, which keeps its own preview and approval.

### /implement

Inside step 15, after Close sub-steps (b) and (c) settle, and before the ship-ready close offer on an FR-form run or the Phase 5 prompt on a milestone-form run, a standalone `/implement` runs the CLI and, when it prints, asks the question once. When the offer is made, the carried-forward `GATE PASSED WITH NOTES` block in the Phase 4 report keeps probe #69's rows and drops its remedy line, so the upgrade is named once. When the CLI prints nothing, no question is asked and the Phase 4 block keeps its remedy line, as in v2.101.4. The prose lives in `docs/implement-reference.md` § Upgrade offer, behind a one-line pointer.

### /deliver

`skills/deliver/SKILL.md` gains a section `## Close-out — offers after the last milestone`, after `## Post-PR — merge-policy routing`. It runs once per run, after the last milestone's post-PR routing settles under any merge policy, in the checkout `/deliver` runs in. Its first offer runs the same CLI itself, because worker fences carry no notes. When no offer prints, the section prints nothing. The section is the single place later close-out offers register; each one asks its own question, in registry order.

### Registry

`CONTINUATION_OFFERS` in `continuation_offer.ts` gains `implement_upgrade_offer` (skill `implement`) and `deliver_close_upgrade_offer` (skill `deliver`), each with every `ContinuationOffer` field (`file`, `asks` included), anchor `UPGRADE_OFFER_QUESTION`, `runsWhenAccepted: ["/upgrade"]` and `runsWhenDriven: []`. The count pin `CONTINUATION_OFFERS.length` in `tests/m143-ste-551-continuation-offers.test.ts` moves from 8 to 10, and its distinct-skill pin moves from 5 to 6, since `deliver` owns no offer today. M_d1b4b7 adds two more entries and leaves the distinct-skill pin at 6. Each span carries `DRIVEN_OMISSION_CLAUSE`, so probe #85 grades both.

## Technical Design

The switch is read before anything else, so an off project pays one settings read and runs no probe.

With the switch on, the offer reads probe #69's output and adds only a question. That keeps one source for what is stale and one remedy string.

Both close-outs register in the existing offer registry, so the driven-run rule and probe #85 apply without new machinery.

The delivery section is built as a list of offers in order. The retrospective milestone adds its entry there rather than a second section.
