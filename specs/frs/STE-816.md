# A settings change is reverted only against its receipt

## Summary

A retrospective can now propose undoing a settings change it applied earlier.
The proposal is made only when a change receipt exists and the file still holds the value that change wrote.
A hand edit since then refuses, because the operator's own edit wins.
An undo brings back a missing key as missing, never as a default.
It uses the same approval as any other change and never starts a trial.

## Requirement

`retro_proposal.ts` proposes and applies a revert of one settings key only against a STE-815 change receipt whose written value is still in the file, through the existing one-approval-one-apply flow.

## Acceptance Criteria

- AC-STE-816.1: `bun run retro_proposal.ts propose-revert <projectRoot> <key>` reads the newest `retro-change` receipt in the tree, across every session, that has a change for `<key>`. When the key's current value equals that change's `to`, it prints `revert <key>: <to> -> <from>` and a final `digest=<hex>` line, with `from` as recorded, `"absent"` included.
- AC-STE-816.2: With no such receipt it refuses in the NFR-10 shape (no apply receipt for the key) and prints no digest line. When the current value differs from the receipt's `to`, it refuses in the NFR-10 shape naming the key, the receipt and both values (the file was edited by hand since the change), and prints no digest line.
- AC-STE-816.3: `apply-revert <projectRoot> <key> <digest>` (a revert has no report file to hand `apply`; amended after review, 2026-11-17), applying a revert digest approved through the existing flow (a question repeating every printed line, answered `Apply the shown change`, one approval admitting one apply) sets the key back to `from`. When `from` is `"absent"` it removes the key, and removes each parent mapping the removal leaves empty, through a new `opts.remove` list of dotted keys on `writeProjectSettings`. It never writes a default value.
- AC-STE-816.4: A successful revert writes its own `retro-change` receipt with `changes: [{ key, from: <to>, to: <from> }]` and `revert_of: <applied_at of the reverted receipt>`, under the STE-815 lock, hash check and write order. It writes no `trial_id` and opens nothing else.
- AC-STE-816.5: A revert of `tracking.tool_calls.enabled` changes the settings key only and leaves the capture registration in `.claude/settings.local.json` as it is. The capture then reads its switch as off.
- AC-STE-816.6: `docs/retro-reference.md` describes the revert verb, its two refusals and the absent rule.
- AC-STE-816.7: `bun test` from `plugins/dev-process-toolkit` reports 0 failures, and its skip identities equal the trunk baseline by name.

## Technical Design

Add `proposeRevertLines(root, key)` beside `proposeLines`. Receipts are read across sessions through the receipts directory walk in `tracker_receipts.ts`. The digest covers the lines and the settings bytes, as `proposalDigest` does today. `apply-revert` shares `apply`'s approval and consumption code and builds a `remove` list for absent values. `writeProjectSettings` gains `opts.remove`, which deletes the leaves before the in-place edit and drops parents left empty.

## Testing

Revert tests: a change then a revert (receipt chain, value back), an absent-from revert removing the key and its emptied parent, a hand edit refusal, a no-receipt refusal, a consumed approval, and a revert of a revert.

## Notes

Operator rule: never change settings without asking, reverts included. A later trial engine will propose reverts through this verb and never write by itself.
