# An unmeasurable skip baseline names the command that measures it

## Summary

When no baseline exists, the report says the guard is unmeasured and ends by telling the reader to capture a baseline at the branch point. It names no command. There is no command to name, because the only thing that would have captured one is skipped on every run here.

That sentence has already produced a wrong number. Somebody reached the refusal at the end of an implementation run, with the current count on the screen in front of them, and wrote that count down as the baseline. It was the post-work count. It shipped, and it shipped green, because nothing consulted it afterwards. The trap worked exactly as designed on someone who had not measured the trunk, and the instruction gave them nothing else to do.

A refusal that cannot be acted on is a refusal that gets satisfied by whatever is nearest. So every outcome that is not a measured pass carries a command the reader can paste, the new cross-checkout refusal gets its own sentence rather than borrowing the old one, and the command is asserted by running it rather than by matching it.

## Requirement

The verdict vocabulary distinguishes an absent baseline from an incomparable one, neither borrows the wording of a pass, and each carries a copy-pasteable command that produces the missing measurement.

## Acceptance Criteria

- AC-STE-530.1: `SKIP_OUTCOMES` gains `incomparable` and becomes four-valued. `isCleanPass` returns true for `pass` alone, asserted against all four members rather than against the new one — a predicate widened by accident is the failure this guards.
- AC-STE-530.2: Every non-pass rendering carries a copy-pasteable command line, not a prose instruction. Measured today: `renderSkipVerdict`'s unmeasured branch ends with the words "capture a baseline at the branch point" and contains no command at all.
- AC-STE-530.3: `unmeasured` and `incomparable` render as DISTINCT sentences with distinct remedies, and neither is assembled from `measuredAgainstBaseline`. The asymmetry rule AC-STE-509.3 established for the third outcome extends to the fourth: a refusal built from the same parts as a pass is a relabelled pass.
- AC-STE-530.4: The step-14 consumer treats `incomparable` as a refusal ground with its OWN reason line, distinct from the unmeasured one. Measured today: `deliver_stage_evidence.ts` carries exactly two reason branches for the gate section, `unmeasured` and `fail`, so a fourth outcome added without this would fall through and render a passing block.
- AC-STE-530.5: The remedy is asserted EXECUTABLE rather than present. The test extracts the command from the rendered line, runs it in a fixture project, and asserts a baseline record exists on disk afterwards. A remedy that names a command with a wrong flag, a wrong path, or a flag that does not exist reads identically to a correct one under a substring match, and this repository has shipped exactly that.
- AC-STE-530.6: AC.5 is mutation-verified: replacing the remedy's command with prose turns it red, and the mutation is asserted to have applied by naming the clause it changed. A mutation that silently failed to apply is indistinguishable from a pin that works.
- AC-STE-530.7: The two shipped measured outcomes are regression-pinned byte-wise. The `pass` and `fail` lines keep their exact current wording and their exact current arithmetic. A four-valued enum must not silently reword the outcomes that already worked, and the rendering functions are the surface most likely to be rewritten wholesale while extending them.
- AC-STE-530.8: The refusal text names WHICH condition failed, and the two conditions do not share one line. An incomparable verdict caused by a foreign checkout and one caused by a named baseline meeting an unnamed run have different remedies — re-measure here, versus re-run the gate so it names its skips — and a shared remedy would be wrong on one of them. This is the shape M135 recorded, where one shared remedy was correct on one cause and dangerous on three.

## Technical Design

The outcome enum grows rather than being replaced by a richer result object, because the enum is already read by name in the consumer and by the fence parser, and a shape change there is a wider blast radius than this FR is worth.

Each remedy is composed from the same entry point the capture order names, so the command in the refusal and the command in the skill are the same string produced by the same function. Two spellings of a command are two things that can drift, and the drifted one appears exactly where somebody is already stuck.

The executable assertion runs the command in a temporary project rather than in this repository, so the test neither depends on nor mutates the real store.

The byte-wise regression pin on the two measured lines is written against the current literals, captured from the shipped module rather than retyped, so the pin cannot record a typo as the contract.

## Testing

The executable-remedy test extracts the command from the rendered string with no manual editing between extraction and execution. Reconstructing the command in the test would test the test author's reading of the line rather than the line.

The four-way `isCleanPass` assertion enumerates every member of the outcome list rather than asserting the two interesting ones, so a fifth outcome added later fails to compile or fails the test rather than being silently admitted as clean.

The consumer test drives the real renderer with an incomparable verdict and asserts the block is refused, rather than asserting the reason string in isolation — a reason that is produced but never reaches the refusal set is the fail-open half of this.

## Notes

The wrong number this FR is written against is still on disk at the time of writing, and STE-527 removes it. The two are separable: this FR is about what the reader is told when there is nothing to compare against, and it would remain necessary even if no wrong record had ever been written.
