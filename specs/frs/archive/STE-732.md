# The test capture reads Vitest, Cargo and Playwright counts, and refuses another runner's output

## Summary

A project using Vitest gets bun's test command and a wrong red gate.
The declared-command list cannot help, because no parser reads Vitest, Cargo or Playwright output.
The pytest parser even takes Vitest's file count as the test count.
Three new parsers fix this, and Cargo projects get a default command.
A Vitest project is told to declare its command instead of getting bun's.
The bun and pytest parsers now refuse output that clearly comes from another runner.

## Requirement

The capture front doors and the delivery evidence renderer read Vitest, Cargo and Playwright counts exactly; a Vitest project never gets the bun command; and a parser given another runner's output refuses instead of reporting a wrong count.

## Acceptance Criteria

- AC-STE-732.1: `vitest`, `cargo` and `playwright` join the `Stack` type in `test_count_parser.ts` and `TEST_COMMAND_STACKS` in `project_settings.ts`; `verification.test_commands` accepts them and `docs/settings-reference.md` lists them.
- AC-STE-732.2: The `vitest` parser reads the `Tests` summary line (passed, failed, skipped, todo) and never the `Test Files` line. The `cargo` parser sums every `test result:` line (passed, failed, ignored). The `playwright` parser reads the final passed, failed, flaky and skipped lines, counting flaky as passed. Each parser returns exact counts on recorded runner output, and refuses when its own summary line is absent.
- AC-STE-732.3: `deriveRunCounts` returns exact pass, fail and skip for each new stack's recorded output.
- AC-STE-732.4: The `bun` and `pytest` parsers refuse, naming the detected runner, when the output carries a Vitest `Test Files` summary or a Cargo `test result:` line; their counts on every existing recorded fixture are unchanged.
- AC-STE-732.5: In `stack_layout.ts`, a root `Cargo.toml` maps to `{ stack: "cargo", command: ["cargo", "test"] }`. A root `package.json` that lists `vitest` in `dependencies` or `devDependencies` gets no table gate: both capture front doors refuse in the NFR-10 shape, and the remedy names `verification.test_commands` with stack `vitest`. A `package.json` without `vitest` keeps today's bun entry.
- AC-STE-732.6: Fixtures prove it: fake `vitest`, `cargo` and `playwright` scripts on a private `PATH` print recorded output, run as declared commands, and sum correctly; a Vitest output declared as `pytest` refuses.
- AC-STE-732.7: Removing any new parser's summary-line requirement, the mislabel refusal, or the Vitest table refusal turns at least one named test red.
- AC-STE-732.8: Projects whose stacks are bun, pytest or flutter, and that declare no new stack, behave exactly as at v3.3.0; existing capture and parser suites stay green except for named amendments.

## Technical Design

The parsers stay table-driven in `test_count_parser.ts`, one function per stack, each anchored on its own summary line. Mislabel detection is a small list of other runners' signature lines, checked only by the bun and pytest parsers. Vitest gets no default command because the package manager varies.

## Testing

Recorded runner outputs as fixtures, fake runners on a private `PATH` through the shipped front doors, and mutation rows per rule.

## Notes

Extends STE-730's declared commands, which stay as shipped. Origin: a field report from a Vitest repository with a Rust service.

- Worker ruling (for operator review): the Vitest, Cargo and Playwright parsers strip colour codes; the bun/pytest mislabel guard fires only on another runner's full summary, so a run that merely prints such a line keeps its v3.3.0 counts; Vitest's unhandled `Errors` line fails the run (Phase 3 review).
