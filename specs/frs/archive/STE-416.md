# STE-416: Linear AC push emits task-list checkboxes for the AC-toggle round-trip {#STE-416}

## Summary

When the toolkit creates a Linear issue for a new feature request, it writes each acceptance criterion into the issue description as a plain bullet rather than a markdown task-list checkbox. Linear renders a native, togglable checkbox only when the source line carries checkbox syntax, so the plain-bullet form gives the acceptance-criteria completion-state round-trip nothing to operate on: the read step finds no box to report and the write step finds no box to flip. This request makes the Linear push path emit each acceptance criterion as an unchecked checkbox on create, restoring the pull-then-toggle round-trip that a prior milestone left half-built when it hardened only the read side. The Jira path keeps its plain-bullet section, which is correct there and stays untouched.

## Requirement

When `/spec-write` (and the canonical chain) create a Linear FR ticket, the acceptance criteria are written into the issue description as plain markdown bullets (`- AC-<id>.<n>: …`) under the `## Acceptance Criteria` heading. The Linear push path (`formatLinearDescription` in `adapters/linear/src/format_description.ts`) only wraps AC-ID prefixes in inline-code fences to defeat Linear's auto-linker; it does **not** convert plain bullets into markdown task-list checkboxes. `normalize` (`adapters/linear/src/normalize.ts`) canonicalizes *existing* checkbox state but passes non-checkbox lines through unchanged — it never synthesizes a checkbox from a plain bullet. Because no checkbox is emitted on create, the adapter's documented `pull_acs` / `push_ac_toggle` round-trip (`adapters/linear.md` § Operations) is inoperative for Linear-created tickets: `pull_acs` has no `[ ]` / `[x]` state to read and `push_ac_toggle` has no box to flip.

STE-190 (M52) hardened the pull side to tolerate checkbox bullets but explicitly scoped the push side out; this FR closes that gap. The Linear push path must emit each acceptance criterion as an unchecked task-list checkbox (`- [ ] AC-<id>.<n>: …`) on create, while preserving any existing checked/unchecked state on re-push (idempotent — a toggled `- [x]` is never reset to `- [ ]`). The scope is **Linear-only**: the Jira path (`jira_ac_field: description`) stores ACs as a plain bullet list under `## Acceptance Criteria`, parsed and rewritten as a section — plain bullets are correct there and must not change.

## Acceptance Criteria

- AC-STE-416.1: On the Linear push path, each acceptance-criterion line inside the `## Acceptance Criteria` section is emitted as an unchecked markdown task-list checkbox (`- [ ] AC-<id>.<n>: …`) before the description is pushed to Linear; a unit test asserts the transformed body renders every AC line as checkbox syntax (not a plain `- AC-…` bullet), that an already-checked AC line is preserved as `- [x]` (idempotent — no state reset on re-apply), and that bullets outside the AC section are left untouched. {#AC-STE-416.1}
- AC-STE-416.2: The AC completion-state round-trip is operative on the Linear checkbox form — a unit test seeds an unchecked-checkbox AC body, flips one specific criterion's box to checked, re-reads the section through the canonical normalizer, and asserts the re-read body shows exactly that criterion as `- [x]` and every other AC as `- [ ]` (the `- [ ]` ⇄ `- [x]` flip is the mechanism the `pull_acs` / `push_ac_toggle` capabilities drive against Linear). {#AC-STE-416.2}
- AC-STE-416.3: The Jira AC representation is unchanged — plain bullets under `## Acceptance Criteria`, no checkbox conversion. A test asserts the Jira push path leaves an equivalent plain-bullet AC section byte-identical (the Linear checkbox transform is not applied to the Jira path), guarding against cross-adapter checkbox leakage. {#AC-STE-416.3}

## Technical Design

**Push-side checkbox transform (Linear-scoped).** Add a transform that, within the `## Acceptance Criteria` section only, converts a plain bullet (`- <text>` / `* <text>`) into an unchecked checkbox (`- [ ] <text>`), and leaves an existing checkbox's state intact (`- [x]` stays checked, `- [ ]` stays unchecked). Reuse the section-boundary detection already in `normalize` (find `## Acceptance Criteria`, stop at the next heading). Two implementation shapes are acceptable — the AC + gate decide:

- (a) extend `normalize` so a non-checkbox AC bullet is synthesized into an unchecked checkbox instead of passed through (the branch at `normalize.ts` lines 60–63), or
- (b) add a dedicated `checkboxifyLinearACs(body)` helper in `format_description.ts` applied on the push/create composition alongside `formatLinearDescription`.

Prefer (b) to keep `normalize`'s pull-side semantics unchanged and make the push-side intent explicit.

**Wiring.** Apply the transform on the Linear create/upsert description composition (the body that feeds `mcp__linear__save_issue` on create — `upsert_ticket_metadata`). It commutes with `formatLinearDescription`: the checkbox marker is the line prefix, the backtick-wrap touches the AC-ID token, so either order yields the same bytes. The read side (`pull_acs`) and toggle (`push_ac_toggle`) already parse checkbox state via `normalize` — no read-side change beyond confirming the round-trip.

**Idempotency.** Applying the transform twice, or to an already-checkbox body, yields identical output and never resets checked state — required so a re-push after a `push_ac_toggle` preserves the operator's toggle.

**Jira untouched.** The Jira adapter's description composition does not call the Linear checkbox transform; its `## Acceptance Criteria` section stays plain bullets (STE-190's pull-side tolerance already covers Jira's ADF `[x]` read-back separately).

## Testing

- **Unit (Linear checkbox emission):** feed a plain-bullet AC body through the transform; assert each AC line becomes `- [ ]`, an already-`- [x]` line is preserved, non-AC-section bullets are untouched, and re-applying is idempotent. New cases in `adapters/linear/src/` (sibling to `format_description.test.ts` / `normalize.test.ts`).
- **Unit (round-trip):** seed an unchecked body, flip one AC to `- [x]`, re-read via `normalize`, assert only that AC reads checked and the rest unchecked.
- **Unit (Jira guard):** run the Jira push-path composition on an equivalent plain-bullet AC body; assert the AC section is byte-identical (no checkbox conversion).
- Full `bun test` from `plugins/dev-process-toolkit` green; existing `format_description.test.ts` / `normalize.test.ts` unchanged.

## Implementation notes

**Spec deviation 1 — `underspecified` (state-loss bug, found at REFACTOR).** The FR's Technical Design sketched a narrow "already a checkbox" predicate, but `normalize`'s pull-side predicate accepts slack internal bracket whitespace. So `- [x ] …` — a form `normalize` happily canonicalizes on pull — missed the push-side predicate, fell through to the plain-bullet branch, and was emitted as `- [ ] [x ] …`: a nested box with the operator's **checked state destroyed**. That directly violates AC.1's "an already-checked AC line is preserved as `- [x]`". Fixed by mirroring `normalize`'s predicate exactly.

**Spec deviation 2 — `underspecified` (GFM validity, found at AUDIT).** The transform originally *skipped* an existing box rather than *canonicalizing* it, so a slack box reached Linear verbatim. Per GFM a task-list marker requires exactly one character between the brackets, so `- [x ]` / `- [  ]` render as literal text with **no togglable box** — AC.1's "emitted as an unchecked markdown task-list checkbox" was unsatisfied for that input (AUDIT classified AC.1 Partial). Changed skip → canonicalize; AC.1 closed to Done. Side benefit: `normalize(push(x))` is now a true fixpoint.

**Spec deviation 3 — `underspecified` (CRLF, found at Phase 3 code review).** `checkboxifyLinearACs` split on `\n` with no CRLF normalization, unlike `normalize`'s explicit Step 1. Both line regexes end in `(.*)$` with no `m` flag, and JS `$` without `m` matches only the true end of string while `.` never matches `\r` — so **no AC bullet in a CRLF-sourced body could convert**. The failure was maximally quiet: the AC-section heading and boundary regexes run on `.trim()`ed lines, so the section was still located correctly and only the per-bullet conversion no-opped. Contract now pinned in two arms: CRLF→LF on the transform path (matching `normalize`); the original body returned byte-identically on the no-AC-section early return.

**AC.3 framing.** There is no Jira description-composition TS function (`adapters/jira/src/` holds only `discover_field.ts` and `list_milestones.ts`); the Jira push path is LLM-emulated prose. Per the FR's own AC.2 note about MCP-emulated capabilities, AC.3 is satisfied against the pure-helper surface — identity on the Jira body plus a discriminating negative and static leakage guards — rather than by fabricating a Jira composition function.

## Advisory notes

- A lone `\r` (old-Mac line ending, not part of `\r\n`) still defeats the line regexes. Inherited scope identical to `normalize.ts`'s `\r\n`-only Step 1, degrades to a benign no-op, and fixing it only on the push side would create the reverse push/pull asymmetry. Follow-up for both sides together, not this FR.
- No shared AC-section boundary helper was extracted between `normalize.ts` and `format_description.ts`. `normalize.ts` is behaviour-pinned and the two intentionally diverge on the no-AC-section case (`""` vs byte-identical body). A pure `findACSectionBounds` could still be extracted without touching `normalize`'s behaviour — a real but minor missed opportunity, recorded rather than taken.
- AC.2's round-trip seeds an already-canonical body, so `normalize` is a fixpoint there and AC.2 alone would not catch a `normalize` regression. By design per `normalize.ts`'s convergence docstring, and covered by `normalize.test.ts`; a server-mangled seed would harden it.
