# The mismatch remedy names an operation that exists

## Summary

Three surfaces tell an operator whose milestone binding does not match to run a command with a flag that has never existed. The skill it names accepts no such flag and its argument hint lists a different set entirely. An operator following the instruction gets nothing, at the moment they have already been told something is wrong.

The same sentence names the wrong tracker. It says to rename the Linear milestone, and it is emitted while diagnosing a Jira Epic as readily as a Linear one, because the string is fixed while the binding it explains is not. A remedy that is confidently specific about the wrong system is worse than a vague one — it sends the operator somewhere real, to look for something that is not there.

The existing test half-pins the string: it accepts either the flag or the bare word rename. A fix that drops the flag but keeps the word passes without changing anything an operator can act on, so the pin is strengthened to fail on the flag and pass only on a replacement.

What replaces it is per-binding and names operations that exist: edit the plan heading, or rename through the tracker's own call, chosen by which binding is being diagnosed.

## Requirement

Every milestone-mismatch remedy names an operation the operator can actually run, on the tracker actually being diagnosed.

## Acceptance Criteria

- AC-STE-525.1: No surface under the skills or adapters trees orders `/spec-write --rename-milestone`. Asserted as a scan whose searched roots are named in the assertion message.
- AC-STE-525.2: AC.1's scan is proven to be looking at something: the same scan, run in the same test for a token known to be present in those roots, returns a non-zero count. A scan pointed at the wrong directory reports zero exactly like a clean tree does.
- AC-STE-525.3: The replacement remedy is binding-aware. The `object` remedy may name Linear; the `epic` and `label` remedies name Jira surfaces and never say Linear. Asserted per binding, as three separate cases.
- AC-STE-525.4: Every operation named by a replacement remedy exists: a named file path resolves on disk and a named tracker call appears in that adapter's documented op list. Asserted mechanically, so a remedy cannot be replaced by a differently-worded impossible one.
- AC-STE-525.5: The existing assertion is strengthened from a pattern that accepts either the flag or the bare word `rename` to one that FAILS on the flag string. Mutation-verified in both directions: restoring the flag turns it red, and the replacement text keeps it green.
- AC-STE-525.6: All three surfaces are updated and parity is asserted — `skills/gate-check/SKILL.md`'s probe row, and both remedy sites in `adapters/_shared/src/tracker_project_milestone_attached.ts`, including the module header comment. Deleting the change from any ONE of the three turns the assertion red.
- AC-STE-525.7: The mismatch remedy still tells the operator the other direction: if the tracker side is correct, edit the plan-file heading to match. That half of the current text is accurate and is preserved rather than replaced.
- AC-STE-525.8: The `epic` binding's mismatch remedy reflects what this milestone changed: under Epic-keyed binding the Epic is resolved by key, so a name mismatch is no longer a binding failure, and the remedy for a genuinely missing binding points at the absent Epic key rather than at a rename.

## Technical Design

The remedy builder already branches on binding for the manual-attach half of its message and does not branch for the rename half, which is how one Linear-specific sentence ended up on every path. Extending the existing branch to cover the mismatch remedy is the whole code change; there is no new structure.

AC.8 is the substantive part rather than a wording pass. Once STE-521 lands, a name mismatch under the Epic binding cannot cause a binding failure at all — the Epic is found by key and the summary is not consulted — so a remedy telling that operator to reconcile names describes a mechanism the milestone just removed. The Epic-binding mismatch case narrows to the one thing that can still be wrong: no Epic in the project carries the key the token encodes.

The scan in AC.1 is written as an assertion over named roots because of how this class of defect survived. The flag string is present in tests as a matcher and in a recorded pre-change constant that a milestone-scoped prose test keeps deliberately, so a naive repository-wide scan for the string cannot go to zero and would have to be weakened until it proved nothing. Scoping to the surfaces that ORDER the operation is what makes the zero meaningful.

The positive control in AC.2 follows this repository's standing rule that a zero-hit search is a claim about the search. The specific failure it guards against has fired here before: the trees being scanned live under the plugin directory rather than the repository root, and a scan rooted one level too high returns zero while a warning it never reads goes to standard error.

## Testing

The three surfaces are asserted individually and then together, so the parity claim in AC.6 has something to be parity between. Mutation verification is performed per surface rather than once for the group, since a group assertion satisfied by any one member is the shape that lets two of three drift.

AC.4's existence check is what separates this FR from a rewording. The remedies name a file path and tracker calls; the test resolves the path and looks the call names up in the adapter's own documented ops, rather than trusting that a plausible-sounding name is real.

AC.5's mutation in both directions matters more than usual because the existing pattern is a disjunction. A one-directional check that merely confirms the new text passes would also pass on the old text.
