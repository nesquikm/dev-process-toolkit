# Gate evidence counts only in the repository it was produced for

## Summary

The blocking guards accept evidence from anywhere in the session, so a gate run for one repository lets a commit into another one through.
A skill call that was denied or failed also counts, as if the skill had run.
Each gate skill now leaves a small receipt inside the repository it ran for, and the guards look for it in the repository the commit actually targets.
A red-before proof now names its repository as well.

## Requirement

All three blocking hooks ask one question: does some transcript line carry both the `"name":"Skill"` and `"skill":"<skill>"` substrings (`templates/hooks/_lib/session.ts:149-166`)? The question has no repository in it, a fact the gate-check hook states in its own header (`templates/hooks/_lib/hooks/pre-commit-gate-check.ts:14-18`). STE-597 made the /tdd hook classify the staged set of the target repository, but that hook then asks the same session-wide question (`pre-commit-tdd-orchestrator.ts:374-380`). Measured on the installed 2.86.0 hooks (skeptic repro `verify-hooks/drive.ts`, session rooted in FE, B staging an FR file, a source file and a test):

- **HS-1.** The rows `git -C B commit`, `cd B && git commit` and `(cd B; git commit)` are refused with no evidence. Each is allowed once the transcript holds a gate-check or /tdd Skill line recorded while the session worked on FE.
- **NF-3.** A real gate-check Skill line followed by an `is_error: true` result also allows every recognised shape. A denied or failed invocation counts.
- **NF-2.** A plain-text `dpt-red-before-proof: tests/test_app.py specs/frs/GF-99.md` written while working on FE satisfies the /tdd hook for B's commit of the same relative paths (`session.ts:286-309`).
- **Live occurrence.** FE session `3ca0ab95` ran /spec-review for FE (1-based line 988), then opened BE's PR #62 from the same session (line 1016).

The transcript's `cwd` cannot carry the repository: 63 of 75 Glacy sessions carry Claude Code's "Shell cwd was reset" notice, and none recorded a cwd outside its start root. So the repository has to be recorded by the skill run itself.

**Decision: the evidence rule.** A blocking hook demands skill S (`gate-check`, `tdd`, `spec-review`) for an action whose target the shared recogniser resolved. The target is a checkout R, or a set of checkouts, or it is unresolved. The session's own checkout is the checkout root of the payload's `cwd`.

1. **The transcript leg.** The transcript holds a Skill `tool_use` for S whose paired `tool_result` (matched by `tool_use_id`) does not carry `is_error: true`. A `tool_use` with no paired result stays eligible. The receipt leg catches a skill that has not run yet, such as a Skill call issued in parallel with the commit. Lines that fail `JSON.parse` are skipped, never thrown on. A text mention of the needles is never evidence (existing control).
2. **The receipt leg.** This applies when R is toolkit-managed, as decided by `isToolkitManaged` from `adapters/_shared/src/toolkit_managed.ts`, the single implementation and never a re-implementation. It is demanded IN ADDITION to the transcript leg, never instead of it. R's receipt store (from M_947c79) must hold, in this session's directory, a valid gate receipt for S. Valid means: `kind` is `gate`; `subject` is S; `sessionId` equals the payload's `session_id`; and the realpath of `root` equals the realpath of R. Each other state refuses by name: no gate receipt for S; malformed or unreadable receipt files, which the store's reader skips and counts; a gate receipt for another skill; or a foreign one, whose `root` names another checkout, as a copied or relocated receipt does. A payload lacking `session_id` refuses by name too. A linked worktree is its own checkout: a receipt written for the main checkout does not satisfy a commit in its linked worktree, and the reverse holds too.
   **Vouching.** A receipt is a file any Bash call can write, so the store alone proves nothing about which checkout the skill ran for. A receipt for S counts only when a non-error Skill `tool_use` for S vouches for it. Each such call opens a window, running to the next Skill `tool_use` for S or to the end of the transcript. Within one window, only the FIRST root ANNOUNCED in that window is vouched for. So one skill run vouches for one checkout. A receipt announced before any Skill call for S, or a second root minted in the same window by hand, is not evidence. It refuses naming the root and the window. A Skill line with no parseable `timestamp` opens no window.

   **Amended in review, because the rule as first written was forgeable — measured, not argued.** It said a window ran from its `timestamp` and was claimed by the first receipt WRITTEN in it, ordered by the envelope's `createdAt`. Both are fields inside a file that, as this paragraph says, any Bash call can write. Driving the shipped hook: a hand-written receipt naming a checkout no gate had ever run against, stamped one millisecond earlier than the genuine one, took the window and its commit was PERMITTED — HS-1 reopened by the rule meant to close it. So a receipt now counts only when the transcript carries its own `dpt-receipt: <path> sha256:<digest>` announcement, printed by the front door into the result of the Bash call that ran it, and the file still hashes to that digest; and a window's claim is decided by the announcement's position in the transcript, which no file content can forge. This is the binding M_947c79's tracker-write gate already uses, applied to this receipt. A file rewritten after its announcement stops counting, and a receipt nobody announced never counted.
3. **Unmanaged R** (no toolkit-managed CLAUDE.md, such as a scratch fixture or an unrelated repository). The transcript leg alone applies, which is today's rule minus NF-3, and success stays silent. No gate skill can run in such a checkout, and demanding a receipt there would be unsatisfiable, the failure STE-598 exists to prevent.
4. **Several resolved checkouts** in one command (`git -C A commit && git -C B commit`). Evidence must hold in every one of them, and the refusal names each checkout that lacks it. `CommitTarget` gains an additive `repoRoots: string[]` field: `[repoRoot]` when there is one checkout, every distinct root when there are several.
5. **Unresolved target.** This covers an unexpandable word, an unplaced wrapper, or `--git-dir`. The gate-check and spec-review hooks evaluate the rule against the session's own checkout AND every root in the target's `candidateRoots` (from STE-601), so an unplaced wrapper around a literal foreign target (`sudo git -C <BE> commit`) gets no easier treatment than the bare command. When that fails, they refuse. When it holds, they exit 1 with a `Reminder:` naming the unresolved word. Exit 1 is deliberate: the exit-code contract in `docs/hooks-reference.md` says a PreToolUse exit 0 surfaces no stderr, while any exit other than 0 and 2 shows stderr to the operator and lets the command run. An exit-0 Reminder would therefore be a silent allow. If the session's own directory lies in no checkout, the transcript leg applies and the exit-1 Reminder still prints. This amends one STE-597 control, named here: `tests/hook-modules-pre-commit-gate-check.test.ts`, "CONTROL — the SAME unresolvable command exits 0 when the /gate-check Skill tool_use IS present", now asserts exit 1 with a `Reminder:` naming `$REPO`, where it previously asserted exit 0 with empty stderr. The replay measures how often this leg fires.
   The /tdd hook's own advisory legs already exit 1, visibly, from STE-601 on.
6. **The red-before proof** (the second /tdd door). A claim of the form `dpt-red-before-proof: repo=<absolute checkout root> <paths>` covers paths only in the checkout whose realpath equals `repo=`. A claim without `repo=` covers paths only when the target is the session's own checkout. A `repo=` value that is relative, unexpanded or inside no checkout covers nothing. The marker constant is unchanged. The refusal's remedy prints the exact form with the target's root. The guard's own refusal record must never satisfy the door (the STE-598 bound, re-pinned against the new remedy text, which keeps the literal `<paths>` placeholder after the marker).

**Decision: the receipt.** It is written by a new front door, `adapters/_shared/src/gate_receipt.ts`, through the receipt store M_947c79 ships in STE-602. That store provides `receiptsDir(projectRoot, sessionId)` in `dpt_paths.ts`, `writeReceipt` and `readSessionReceipts` in `tracker_receipts.ts`, the `dpt-receipt: ` announcement, and the location `.dpt/ledger/receipts/<session>/`, which the existing `ledger/` rule of `.dpt/.gitignore` already ignores. This FR adds no second composer, writer, reader or ignore rule. The front door ships an `import.meta.main` CLI: `bun run "${CLAUDE_PLUGIN_ROOT}/adapters/_shared/src/gate_receipt.ts" <gate-check|tdd|spec-review> <any path inside the checkout>`. The session id comes from `CLAUDE_CODE_SESSION_ID`, the store's single source. **Recorded dependency:** gate evidence in a managed checkout exists only while Claude Code exports that variable to Bash tool subprocesses. It is measured at spec time as exported on Claude Code 2.1.276, equal to the running transcript's session id, and a subagent's Bash call sees the parent session's id; AC.14 and M_2306b6 re-prove it live. When it is absent or empty, the front door refuses with the named class `session-id-unavailable`: the verdict line names `CLAUDE_CODE_SESSION_ID` and says gate evidence depends on it, and the remedy says to run the skill in a Claude Code session that exports it. The skill stops on that refusal and reports it, so the later hook refusal is never the first the operator hears of it. The receipt uses the store's envelope with `kind: "gate"`, `subject` set to the full `dev-process-toolkit:<name>`, `root` set to the realpath of the checkout, `decision: "ran"`, `adapter` and `container` null, and `evidence: { head }` (the sha, or null on an unborn branch). A re-run in the same session writes a fresh receipt, and the reader takes the newest valid one. The front door refuses, with exit 1, an NFR-10 block on stderr, empty stdout and no file written, on: an unknown skill name; a path inside no checkout; `CLAUDE_CODE_SESSION_ID` absent or empty; a session id that is not a single path-safe token (`/`, `..` and whitespace are refused); and an unwritable store. On success it prints the store's `dpt-receipt: <absolute path>` line.

**Decision: who writes it.** Each gate skill orders the front door as its first executed step, for the checkout it is about to act on:

- `skills/gate-check/SKILL.md` edits its line 8 in place, one line for one line, because the file measures 356 of its 358 split-lines. The edited line also decides which checkout the gate runs for: the checkout named by an optional path argument, or the session's working directory when none is given; every gate command then runs with that checkout as its working directory, and the front door is called for that same checkout. The frontmatter `argument-hint` line gains the optional path in place. Without this, a gate run from an FE-rooted session could only ever grade FE, and the HS-1 remedy would be unreachable from that session.
- `skills/tdd/SKILL.md` orders it in step 1, for the FR file's checkout, with no new heading.
- `skills/spec-review/SKILL.md` orders it in step 1, for the checkout in scope. Its `allowed-tools` gains `Bash(bun run:*)`, and the audit fork and the `spec-reviewer` agent stay byte-identical and read-only.

Whether the step ran is graded by executed code, not by the prose: without the receipt, the hook refuses.

**Decision: the remedy.** A receipt-leg refusal names the checkout and gives the exact command to run for it: `/dev-process-toolkit:gate-check <checkout root>` for the gate-check hook, `/dev-process-toolkit:tdd` run on the FR in `<checkout root>` for the /tdd hook, and `/dev-process-toolkit:spec-review` run in `<checkout root>` for the PR hook. It adds that a session started before this release must be restarted. It never prints the front-door command line: a remedy that hands the agent the minting command invites a receipt with no gate behind it, which the vouching rule would then refuse anyway.

**Scope, confirmed by the operator.** Repository-scoped gate evidence applies in EVERY toolkit-managed checkout, shared or not, whether or not it declares `repo_tag`. This is a behaviour change from this milestone's release: from then on, a commit or PR in any managed checkout needs its receipt, and the CHANGELOG entry says so. HS-1 was reproduced with separate tracker containers, and the live cross-repo PR happened while GF and GB were separate Jira projects. The helpers keep their names. `requireSkillToolUse` and `requireTddEvidence` gain an optional target argument, so `tests/_blocking_gates.ts` keeps deriving the three blocking gates. `session.ts` keeps exactly one `readFileSync`, the transcript, because receipts are read inside `gate_receipt.ts`. No guard entry point gains a filesystem read. Both pins in `tests/hook-session-lib.test.ts` stay green unedited.

## Acceptance Criteria

- AC-STE-614.1: The transcript leg (NF-3). For each of the three blocking hooks, a transcript holding a Skill `tool_use` for its skill whose paired `tool_result` carries `is_error: true`, and no other such `tool_use`, is not evidence: the hook exits 2 with a `Refusing:` that says the call ended in an error or denial. The permit siblings differ in one field. The same transcript with `is_error` absent or false is evidence. A `tool_use` with no paired result is evidence for this leg. One denied plus one successful call is evidence. A transcript containing an unparseable line is decided by its other lines and never throws. A JSON-escaped text mention of the needles is not evidence. The plain-miss refusal text ("required <skill> Skill tool_use not found in current session.") is byte-identical to HEAD.

## Technical Design

`gate_receipt.ts` owns the gate receipt's validity verdict, including the realpath comparison, and writes and reads only through M_947c79's store. `session.ts` imports its verdict function, so the transcript keeps one reader and the guard entry points stay free of filesystem reads. `requireSkillToolUse` and `requireTddEvidence` take an optional target record (resolved roots, candidate roots, unresolved word, session checkout). A call without one keeps today's session-wide rule minus error results, which leaves the advisory brainstorm hook's shape untouched. Vouching windows are computed from the same parsed lines. The `tool_use` and `tool_result` pairing reuses the one M_947c79's tracker-write hook reads, so both gates share one pairing rule. The commit hooks pass the `CommitTarget`, and STE-615 passes the PR target.
