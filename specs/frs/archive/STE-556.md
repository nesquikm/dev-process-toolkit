# The guards read what the writers write, and the docs stop overclaiming

## Summary

Four checks or claims narrower than the thing they describe.

The root-hygiene probe is codename-blind: the latest-release line names a codename, and only its version is compared.

Two documents promise a bug class cannot happen, and give as their example the surface where it does.

The version bumper reports the total FR count as the additive count, so a mixed milestone gets a false rationale.

The guard grading the release surfaces knows numeric milestone ids only, which blocks this milestone.

## Requirement

Every guard on the release path compares the fields the writers write, over the full grammar of the identities this project mints. Documents describing the ceremony say what is true of it, including where it is incomplete.

## Acceptance Criteria

- AC-STE-556.1: Probe #9b captures the codename from the `Latest shipped release:` line and compares it against the CHANGELOG entry for the version that line declares. A mutated codename produces a drift naming the field; the unmutated line produces none. Both halves asserted — the mutation alone would pass on a probe that reds unconditionally.
- AC-STE-556.2: The codename comparison is vacuous where the surface does not exist: a `Latest shipped release:` line carrying no codename, and a CHANGELOG with no entry for the declared version, each produce no codename drift. Consumer projects that never adopted a codenamed banner stay green, asserted per case rather than as one combined fixture.
- AC-STE-556.3: The CHANGELOG is read through the same reader `release_surface_agreement` already uses to answer "what codename shipped as this version". A second parser here would be the drift this criterion exists to catch, so the assertion is on the import, not only on the answer.
- AC-STE-556.4: Probe #9b's in-flight milestone check reads the shared union grammar, so `In-flight milestone: M_<key>` resolves. Asserted both ways: an `M_<key>` naming a live plan is green, and one naming no plan reds with the same `in-flight-missing-plan` kind its numeric sibling produces. Measured at HEAD: the private `\bM(\d+)\b` matched nothing on an `M_<key>` line, so the check silently passed on a claim it never read.
- AC-STE-556.5: The two absolute "cannot happen" claims are replaced by statements true of the shipped ceremony. A tripwire asserts the absolute wording is absent from both files, so the sentence cannot return by a later copy-paste.
- AC-STE-556.6: `inferBump`'s minor rationale reports the number of ADDITIVE FRs. `[Added, Fixed, Fixed, Removed]` reports 1. An all-additive milestone's rationale is byte-identical to today's. The patch branch's label is untouched, asserted rather than assumed.
- AC-STE-556.7: `docs/ship-milestone-reference.md`'s description of that rationale matches what the module now emits. A doc left describing the old sentence is the same class of defect as the sentence itself.
- AC-STE-556.8: `release_surface_agreement.ts` recognises the full `M<N>` | `M_<key>` union wherever it recognises a milestone: the README banner's parenthetical, the plan frontmatter's `milestone:` key, and the plan-filename fallback. Asserted over a fixture reproducing this milestone's own post-release tree — README naming `M_dc2ecb`, CHANGELOG carrying the release, plan stamped `shipped_in:` — which returns zero violations. Measured at HEAD on that same fixture: one `latest_line` violation and a `findMilestonesForRelease` of `[]`.
- AC-STE-556.9: The canonical-milestone ordering is total over the union. `Number(token.slice(1))` is `NaN` for every `M_<key>`, and a comparator returning `NaN` orders nothing, so the ordering is re-expressed through the shared token parser: numeric ids descending by number, then epic-keyed ids descending by key. Asserted on a mixed list, and asserted to be a stable total order rather than merely "correct for one input".
- AC-STE-556.10: `release_surface_agreement.ts` is registered in the STE-335 AC-7 consumer audit. It was absent from that list, which is why three private copies survived a check written to prevent exactly them.
- AC-STE-556.11: Falsifiability — AC.1, AC.4, AC.6 and AC.8 are mutation-tested by reverting the single change that satisfies each and asserting that criterion's leg reds while its siblings stay green. AC.5's tripwire is verified by re-introducing the absolute wording into a fixture copy and asserting it fires.

## Technical Design

The freshness check gains an optional changelog path and a codename-mismatch drift kind. The codename is read from the same line the version is read from, by widening the existing matcher with a second named group. The expected value comes from the reader that already owns "what codename shipped as version X".

In the surface-agreement guard, three private numeric milestone literals are replaced by the shared union source and the sort by the shared token parser. The module is added to the consumer list of the audit that exists to stop private copies returning.

The version bumper counts the FRs whose category is not fix-class, and uses that only in the minor label.

## Testing

The probe legs run the real `findVersionFreshnessDrift` over fixture trees on disk. The mutation legs edit the fixture, never the module under test, so what is graded is the probe's reading of a changed world rather than a changed probe.

The union-grammar legs build the fixture from this milestone's own post-release shape, because that is the tree the guard must accept before this milestone can ship at all.

## Notes

The consumer audit is an enumerated list, not a sweep: it asserts that each named file mentions the shared module, which is why an unregistered module kept three private copies and a registered one kept a copy beside its import. Turning it into a derived sweep is a wider change, left as a follow-up.
