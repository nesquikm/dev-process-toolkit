# /deliver routes an FR identity at FR scope, not milestone scope

## Summary

When the operator names a single FR, the orchestrator reads that FR's milestone frontmatter, discards the FR, and delivers the entire milestone. The identity is a lookup key and nothing more. An operator who asked for one task gets every task in its milestone built, version-bumped and released. Nothing in the run says the scope widened.

## Requirement

An argument naming an FR delivers that FR. The milestone it belongs to is resolved and carried, but it does not become the unit of work.

## Acceptance Criteria

- AC-STE-499.1: `DeliverRouting` carries the resolved FR identity and a scope discriminator separating an FR-scoped run from a milestone-scoped one.
- AC-STE-499.2: An FR identity resolves to FR scope; a milestone identity resolves to milestone scope; a prose argument still enters the design phase.
- AC-STE-499.3: The FR's milestone is still resolved and carried on the routing, because later chain stages need it.
- AC-STE-499.4: Every refusal already on the FR path fires on unchanged terms — FR file absent, `milestone:` absent or malformed, non-tty stdin.
- AC-STE-499.5: A milestone-identity run is byte-identical to today, asserted rather than assumed.

## Technical Design

`resolveDeliverArgument` in `adapters/_shared/src/deliver_argument.ts` already classifies `fr_identity` distinctly from `milestone_identity`, so the grammar half of this work shipped with STE-497. What it does with that classification is the defect: the `fr_identity` branch reads the FR body, parses `milestone:` out of its frontmatter, assigns it to the local `milestone`, and from that point the two kinds are indistinguishable to every downstream consumer. `DeliverRouting.kind` preserves the distinction on the returned value, but no consumer reads it.

AC.1 is therefore a consumer change more than a producer one: `DeliverRouting` gains an explicit scope field so `classifyResume` (STE-500) and `resumeChain` (STE-501) can branch without re-deriving intent from `kind`. Re-deriving is the split-source-of-truth pattern M129 recorded three separate times in one milestone; a second answer to a question that already has one home is exactly what this field exists to prevent.

AC.3 matters because FR scope does not mean the milestone is irrelevant — the extended chain in STE-501 needs it for `/spec-archive M<N>` and `/ship-milestone M<N>`, and the confirm gate needs it to state how many active FRs remain. Dropping it would trade one defect for another.

AC.4 is a no-regression clause. The two FR-path refusals (`fr=not-found`, malformed `milestone:`) and the unconditional non-tty refusal all fire before any routing decision, and widening what the routing does downstream must not move them.

AC.5 exists because this FR changes a shared code path. The milestone-identity path is the one every shipped `/deliver` invocation uses, and an assertion that it is unchanged is cheaper than discovering it is not.

## Testing

Routing coverage per argument kind: FR identity returns FR scope with the milestone carried; milestone identity returns milestone scope; prose enters the design phase. The milestone-scope path asserted against its current shipped output rather than against a restatement of it. Refusal coverage for FR-not-found, absent `milestone:`, malformed `milestone:`, and non-tty stdin on every argument form. Mutation check: collapsing FR scope back into milestone scope must go RED — a test that only asserts the milestone is carried would pass under the shipped defect and is worth nothing here. `bun test` full root.

## Notes

Origin: operator request, 2026-08-24, in the `/brainstorm` session that produced M130–M132.

The defect is a live one rather than an unimplemented feature. `/deliver STE-500` today builds four FRs, bumps a version and opens a release PR, and the only signal the operator gets is the confirm gate rendering a milestone chain they did not ask for.

This FR is deliberately separable from STE-500 and STE-501. Even with no FR-scoped chain at all, carrying the scope rather than discarding it is the change that makes the widening visible.

## Implementation notes

- `DELIVER_SCOPES` is derived per-kind rather than deduped, so a future fourth argument kind mapping to an existing scope would grow a duplicate entry and redden the vocabulary pin even though the vocabulary is unchanged. Do not consume it as a set.
