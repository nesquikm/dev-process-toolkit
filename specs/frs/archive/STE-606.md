# Implement confirms a ticket is this repository's before importing or claiming it

## Summary

Given a ticket id, the implement flow could import a ticket from another project or repository and rewrite it before asking the operator anything, then claim it even while it sat in review or was cancelled.
Ownership is now decided by a command before any write: a ticket from another project or another repository is refused, and an unlabelled one needs an explicit yes.
The confirmation now comes before the import and before the claim.

## Requirement

Measured at HEAD `ac1f3cb`:

- `skills/implement/SKILL.md` step 0.b′ (line 46) imports on a local miss, and `importFromTracker` ends in `provider.sync` — an outward rewrite of the ticket's description. The mandatory "Operating on ticket <ID>: <title> — proceed?" confirmation runs at 0.f (line 54), after 0.c's claim. `docs/ticket-binding.md` says `/implement` confirms before any side effect; the skill does the opposite. `/spec-write` § 0a's miss path (line 39) imports the same way.
- The resolver accepts any upper-case id (`^[A-Z]+-\d+$`), so `GF-86` resolves as a Linear id, and nothing compares the fetched ticket's project with the binding. The branch-name tier likewise takes any ticket-shaped id on the branch.
- The claim runbook (`docs/implement-tracker-mode.md` § Claim runbook) routes "Otherwise (Backlog, Unstarted, Cancelled, etc.)" to a claim, which covers a sibling's In Review ticket: it moves it back to In Progress and reassigns it. The assignee check cannot tell repositories apart — one account is assignee on both FE's GF-86 and BE's GB-41.
- `isClaimable` in `adapters/_shared/src/tracker_provider.ts:183-185` accepts done, completed and cancelled, so `claimLock` reopens and reassigns a Done ticket (repro: `claimed`, transition plus assignee writes); the runbook sends Done to already-released. `TrackerProvider` has no production caller, so the divergence is latent — until anything constructs one.

### 1. The ownership decision

A new `adapters/_shared/src/ticket_ownership.ts`:

- `decideTicketOwnership({ projectRoot, ticket, binding })` over one fetched ticket (Jira `getJiraIssue` fields `summary, labels, issuetype, status, project, creator, description`; Linear `get_issue`), using the classifier of STE-605 and the FR bindings that are TRACKED in `projectRoot`'s git index: `readLocalFRBindings` applied only to the files `git ls-files` lists under `specs/frs/` and `specs/frs/archive/`, so the binding is read from each file's `tracker:` frontmatter, never inferred from its name. Tracked matters: an import writes its FR file before it syncs, so a file merely present on disk proves nothing. Verdicts:
  - `owned` — a tracked FR file here binds the key, whatever the ticket's project (bindings left behind by a repoint stay this repository's); or, when shared, the ticket carries this repository's tag;
  - `foreign-project` — not tracked-bound, and the ticket's Jira project, or Linear project or team, differs from the binding: refused in every mode;
  - `container` — refused in every mode;
  - `foreign-repo` — shared, not tracked-bound, classified `sibling`: refused; the remedy names running from the owning repository, or a person relabelling the ticket in the tracker;
  - `unowned` — shared, not tracked-bound, classified `unowned` (no label beyond this repository's own default and milestone labels, back-link or not): allowed only after an explicit adopt question;
  - undeclared and the project matches: `owned`, today's path.
- Front door: `bun run adapters/_shared/src/ticket_ownership.ts decide <projectRoot> <ticket.json>` prints the verdict as one JSON line. `confirm <projectRoot> <key> <ticket.json> [--adopt]` re-decides and, in a shared repository, writes a `binding` receipt once the mandatory confirmation was answered yes, printing `dpt-receipt: <path>`. For an `unowned` verdict `decide` prints the adopt question's option labels, `Adopt <KEY>` and `Skip <KEY>`, and `confirm` also requires `--adopt`; the write gate separately requires that question in the transcript, answered with `Adopt <KEY>` — a flag the model can pass is not consent, the recorded answer is. `confirm` refuses every refused verdict and writes nothing.
- `claimRoute(status, assignee, currentUser)` — the one routing function behind the runbook and `TrackerProvider.claimLock`: in progress with another assignee → `taken-elsewhere`; in progress with me → `already-ours`; done or completed → `already-released`, zero writes; anything else → claim. `isClaimable` drops done and completed; `LockResult.kind` gains `already-released`, which `LocalProvider` never returns. Routing for this repository's own tickets is otherwise unchanged; tickets that are not ours never reach it.

### 3. Who enforces the order

In a shared repository the write gate (STE-607) refuses the import's sync and the claim's transition on any key that is neither tracked-bound nor named by a receipt, so the order holds even when the prose is skipped. In an undeclared repository the order is prose, and the `foreign-project` refusal is the executed part.

## Technical Design

Ownership is decided once, from the fetched ticket and the repository's own git index, by the classifier the orphan listing uses. A binding tracked in git always wins, which keeps legacy bindings working after a repoint and stops a just-written import file from vouching for itself. The confirmation moves ahead of the import because the import's last act is a write. Claim routing becomes one function, so the documented routing and the typed provider cannot drift again.

## Implementation notes

- **Pin moves** (named, and none other):
  - In `adapters/_shared/src/tracker_provider.test.ts`, no pre-existing case asserted that done or completed was claimable, so nothing moved. The moves are therefore NEW cases, each labelled `MOVED:` and saying what they were: `claimRoute` for done and completed, and `claimLock` for done and completed with zero driver writes. A backlog control keeps the transition and the assignee write.
- **Test defect fixed by the orchestrator.** The new AC-STE-606.10 leg asserted `expect(ORDERED_UNREACHABLE_PIN).toBe(122)`. The STE-557 guard forbids any test pinning the live count to a literal. The leg now asserts three things: no ledger entry names this FR; the head is at or below STE-605's entry; and the head is what the awaited probe measures.
- **Stage C / AUDIT fixes:**
  - The ownership decision reads each tracked FR file's COMMITTED bytes (`git show :<path>`), not the working tree. Parsing the disk copy of a git-listed file let a tracked FR edited on disk vouch for a key it never committed (H1).
  - The tracker-id reading is one exported `trackerIdsOf(content)` in `reconcile_tracker_local.ts`, shared by the working-tree walk and this reader. `readLocalFRBindings` keeps its pre-change signature.
  - A Linear ticket with no `team`, under a binding that names one, is now `foreign-project`. It used to skip the comparison silently (H2).
  - `docs/implement-tracker-mode.md` § Claim runbook step 0 now also orders `confirm`, the `binding` receipt the write gate needs, after the operator's yes.
- **Pass 2 review fixes:**
  - **One batch read.** Committed blobs are now read with ONE `git cat-file --batch` instead of one `git show` per FR file. An archive holds hundreds of FRs, and the decision runs on every `decide` and every `confirm`.
  - **Named failures.** A blob that cannot be read is fail-safe, so it never vouches. It is also named in the decision's `git` field, where before it was silently skipped.
  - **Containers skip git.** A container is refused before git is read at all.
  - **Strict headers (H3).** The batch reader slices by BYTES. H3 first survived, because a misaligned read landed mid-object-id, and the header regex then accepted a partial hex id and quietly re-synchronised. The header must now be a full 40- or 64-hex object id, and H3 was re-measured red.
  - **No control characters.** The tracked-path filter excludes names with control characters. A name carrying a newline would desync the LF-framed batch requests; that failed safe, to a named `gitError`, but falsely refused every FR read after it.
- **Test-harness flake fixed.** `tests/_orphan_pages.ts`'s `snapshotTree` walked `.git`, and git's background maintenance after a commit creates and deletes `.git/objects/maintenance.lock` mid-walk. That was a measured ENOENT flake, one run in five, in AC-STE-606.3 "writes nothing". The walk now skips `.git`, since every claim it grades is about the working tree. The STE-606 fixture's `gitInit` also sets `gc.auto 0` and `maintenance.auto false`. The three affected suites then ran 10 of 10 green.
- **Probe #74:** `ticket_ownership.ts` reads CLAUDE.md through `readWorkspaceBinding`, so it gains a recorded `CLAUDEMD_GUARD_EXEMPT` entry. Its applicability is the declared tracker `mode:`, the same reason the other shared-declaration readers carry.
- **Beyond the routing table as written:** `claimRoute` returns a fifth route, `not-claimable`, for a status outside the canonical set. `claimLock` surfaces it as `taken-elsewhere`, the refusal it returned before. The FR says "anything else → claim"; for every canonical `TicketStatus`, anything else is claimable (backlog, unstarted and cancelled route to `claim`, tested), so the fifth route is reachable only by a non-canonical status. It is kept as a refusal rather than a silent claim.

  - `docs/resolver-entry.md` § 0a and `docs/ticket-binding.md` § Ownership decision restate the same sequence.
  - AC-STE-606.3's join path was first graded through a test-side re-enactment of the documented order. After the pre-PR /spec-review, it is graded on production code: the resolver front door, the exported `ticketImportOwnership` (import.ts), and the real hook fed the real `confirm` output. The skill's own order is still graded structurally by AC-STE-606.5.
