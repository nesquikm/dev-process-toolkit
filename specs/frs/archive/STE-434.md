# STE-434: Conformance probe: CLAUDE.md-derived probes route through the shared predicate {#STE-434}

## Summary

The probe 18 defect was not a typo. It was one probe re-deriving the managed-tree question by hand and getting it wrong, in a codebase where five other places already answer it and three of them disagree on the regular expression.

Once a shared predicate exists, nothing stops the next probe from ignoring it. This adds the structural fuse: a conformance probe that finds every adapter module whose applicability derives from CLAUDE.md and asserts it consults the shared predicate, or is named in an exemption list with a stated reason.

The toolkit pins several cross-surface contracts this way already. This applies the same pattern to the guard that just failed.

## Requirement

A `/gate-check` conformance probe MUST assert that every module under `adapters/_shared/src/` whose applicability derives from `CLAUDE.md` routes through the shared toolkit-managed predicate, or is explicitly exempted with a recorded reason.

Established during design, against v2.57.1 at `edd8eaf`:

- **The drift is real and already happened.** Fifteen modules read `CLAUDE.md`; the predicate is open-coded in five places with three divergent `## Docs` regexes, and probe #18 drifted to guarding on nothing without any check catching it.
- **This is the toolkit's established pattern.** Probes #38, #42, #54 and #55 pin cross-surface contracts structurally rather than by convention; #54 in particular is allowlist-driven, which is the shape reused here.
- **The cost is bounded and known.** Eight sites: `README.md:14` (regex-pinned by `public_surface_count_drift.ts:210`), `README.md:109`, the three count assertions and comment at `tests/gate-check-public-surface-count-drift.test.ts:396-400`, the new `skills/gate-check/SKILL.md` entry, the probe-authoring contract list in the same file, the new probe module, its new test file, and `CHANGELOG.md`. This repo's `CLAUDE.md` carries no probe-count token, so it needs no edit.

  **CORRECTION, recorded at implementation (M118).** The eight-site inventory above undercounts, and the single-test guard rail in § Technical Design is falsified. Registering entry 74 flips hard-coded probe-count pins in **seven** pre-existing test files, not one — verified empirically by simulating the added entry and re-evaluating each pin: `tests/gate-check-public-surface-count-drift.test.ts`, `tests/gate-check-upgrade-staleness.test.ts`, `tests/gate-check-spec-write-next-line-doc.test.ts`, `tests/m108-ste-393-docs-pins.test.ts`, `tests/m109-ste-394-docs-pins.test.ts`, `tests/m115-ste-417-docs-pins.test.ts`, `tests/m116-ste-424-short-ulid-collision.test.ts`. The last of these carries a comment putting the true figure at *"~26 pinned count sites across README.md, skills/gate-check/SKILL.md and five test files"* — so the real profile was already documented in-repo when this FR was written. `tests/m109-ste-394-docs-pins.test.ts` additionally holds **meta-meta** pins asserting that three of the other files literally contain the `73`-form strings, so updating those files requires updating it too. Direct precedent: commit `392dd3e` (M115, registering probe #73) made the identical mechanical edit across the same family of files, `tests/gate-check-upgrade-staleness.test.ts` included. Every edit is digits-and-titles only: no assertion was added, deleted, or loosened, and probe-*number* references to #73 were left at 73.
- **Bump consequence.** This FR is the only one in M118 outside the fix class, so `inferBump` yields a minor bump rather than a patch. Release target v2.58.0 is set accordingly.

## Technical Design

**Allowlist-driven scan, mirroring probe #54.** The probe globs `adapters/_shared/src/*.ts`, selects modules that join a `CLAUDE.md` path, and checks each for an import from `./toolkit_managed`. Modules that legitimately do not need the predicate are named in `CLAUDEMD_GUARD_EXEMPT` with a reason, so an exemption is a recorded decision rather than an omission.

**Why membership, not signal equality.** The probe asserts that a module *consults the shared module* — not that it accepts the same signal set. Those are different requirements, and conflating them would break the codebase: probes #19 and #22 deliberately accept only the setup marker, and widening them turns this repo's own gate red (see STE-432). The per-probe acceptance policy is a design decision that must stay visible at the call site; what this probe forbids is answering the question somewhere else entirely.

**Ordering.** AC-STE-434.3 is satisfiable only after STE-432 lands, so this FR is last in the milestone. Landing it first would produce a probe that fails on its own repo.

**Count maintenance.** Observed probe count is derived from the largest `/^(\d+)\.\s/` prefix in the gate-check SKILL (`public_surface_count_drift.ts:97-110`), so registering entry 74 updates the observed side automatically. Only the two documented README values and the meta-test's pinned regexes need explicit edits — the same maintenance profile STE-386 recorded when it added a probe.

**Guard rails — the pre-existing tests this FR may change:** ~~`tests/gate-check-public-surface-count-drift.test.ts:396-400` only~~ — **superseded at implementation**, see the CORRECTION in § Requirement. The real set is the seven probe-count-pinning test files enumerated there, and the permitted edit in each is strictly mechanical: the count digits and the titles/comments quoting them. No assertion may be added, deleted, or loosened, and probe-*number* references to #73 stay at 73. Every other existing test must pass unmodified. In particular this FR must not need to edit any probe module other than by adding the new one — if it does, STE-432 left a site unrouted. *(Verified at implementation: it did not. The only adapter modules touched in M118 are STE-432's four, STE-433's one, and the two new files.)*

## Notes

This FR is the designated drop-candidate for the milestone. Dropping it leaves M118 a pure fix-class set, which `inferBump` renders as a patch release rather than the minor currently targeted. The operator accepted the minor bump and the eight-site cost deliberately, on the grounds that the fuse is the point: without it, the next probe to read `CLAUDE.md` can re-derive managed-ness by hand exactly as probe #18 did.

The blanket alternative — a gate-check-level rail making every probe vacuous on an unmanaged tree — was considered and rejected. It needs an escape hatch by construction, because probe #69's legacy-monolith sniff is a deliberate exception; a rail with an exception is a per-probe decision wearing a uniform. It would also live as SKILL prose, which is LLM-evaluated, and replacing one silent drift surface with a larger one contradicts the deterministic-gates-over-judgment principle. This probe is the narrow, byte-checkable version of the same intent.

## Implementation notes

- **Compliance is import-presence, not use.** The probe accepts any in-scope module that imports `./toolkit_managed`. A module that imports `isToolkitManaged` and *still* open-codes its applicability from `CLAUDE.md` passes the guard — probe #18's exact original failure mode. Spec-conformant (AC-STE-434.2 and the Technical Design both say "imports") and latent rather than live: all three import-routed modules genuinely call it. Flagged because the Requirement's prose says "routes through", which is strictly stronger than what is enforced.
- The unreadable-module branch fires **before** the selection check, so a module that is unreadable but never touches `CLAUDE.md` still yields a violation — an over-approximation the selection rule does not sanction. Fail-closed by design and documented, but covered by zero tests.
- The guard's own exclusion from its scan rests on a textual accident: its selector regex literal escapes the paren, so the module's source never forms the shape it searches for. Documented in the module, including the instruction to keep the literal join shape out of its comments; no dormant exemption key was added, since an exemption that exempts nothing is a false record. Not structurally guaranteed.
- AC-STE-434.6 names README lines 14 and 109; the tests anchor on content uniqueness via `onlyLine()` rather than the line index (following the correction the public-surface suite already made). Both tokens do sit at exactly 14 and 109 today, but a future line shift would not be caught by the line-number half of the claim.
- The FR's "eight sites" cost inventory and its single-test guard rail were **falsified at implementation** — see the CORRECTION recorded in § Requirement. The real cost is seven pre-existing test files; a comment already in `m116-ste-424` put the figure at "~26 pinned count sites". Each new probe-count-pinning suite added by a milestone compounds this tax; a shared count-pin helper would retire it.
