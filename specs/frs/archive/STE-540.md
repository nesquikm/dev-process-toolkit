# Bind Linear issues to milestones by key rather than by name

## Summary

Matching a milestone by name works only while the name is the identity. Once the identity comes from the tracker's own identifier, the milestone keeps whatever human title someone typed, and the two can never be equal again.

So the reader computes the same derivation the writer did, rather than comparing strings.

Name matching also binds to the first of two milestones sharing a name. Key matching removes that as a class.

## Requirement

An identity derived from a Linear milestone identifier binds and verifies by deriving each candidate milestone's identity forward and comparing it to the requested one. A grandfathered sequential identity keeps the name-matching path unchanged. An identity with no matching milestone is refused and never causes one to be created.

## Acceptance Criteria

- AC-STE-540.1: A milestone token derived from a Linear identifier binds through a match-by-key leg — each candidate's identifier is sanitized forward and compared to the token — with no name string-comparison on that path.
- AC-STE-540.2: The post-write verify asserts that the bound milestone's identifier derives back to the requested token; a mismatch raises `MilestoneAttachmentError` in the NFR-10 canonical shape with a Linear-specific remedy naming the identifier.
- AC-STE-540.3: A grandfathered numeric `M<N>` token keeps the shipped match-by-name path byte-for-byte, asserted against the current expectation rather than a rewritten one.
- AC-STE-540.4: `adapters/linear.md` is corrected: its claim that the milestone parameter is a name and not an ID contradicts the tool schema, which documents it as a name or an ID. A name-resolution fallback is exercised by a test whose provider double rejects an identifier.
- AC-STE-540.5: A token with no matching milestone is refused; the attach never creates one, since a fresh create would allocate an identifier that can never sanitize back to the token.

## Technical Design

No new module. In `adapters/_shared/src/attach_project_milestone.ts` the object branch gains the STE-523 kind route: `parseMilestoneToken(leadingMilestoneToken(name))`. `numeric` falls into today's list/create/attach-by-name code untouched; `epic` takes a by-id arm using STE-539's uuid derivation — never `milestoneIdFromEpicKey`, which is the `mode: jira` dispatch — so minter, writer and reader share one expression. `MilestoneOps.listMilestones` widens to `{name, id?}[]`; `TicketMilestoneView.projectMilestone` AND `milestoneBindingPresent`'s separate inline param (line 779) each gain `id?` — one is not the other. On this arm a miss refuses rather than auto-creating. An id-rejecting tracker retries once with `found.name` inside `write`. Add `MilestoneObjectNotFoundError extends MilestonePermanentRefusalError` outside `retryTransient`; `"milestone-id"` joins the binding union at `MilestoneAttachmentError` and `writeAndVerify`.
