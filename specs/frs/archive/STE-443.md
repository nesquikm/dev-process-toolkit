# Add a jira-keyed provenance arm to probe #73

## Summary

Probe seventy-three is bidirectional but asymmetric. Under the tracker-less mode a freshly created sequential plan is an error, decided by git provenance against an epoch. Under any tracker mode the only rule is that no plan may carry an identity key, so a sequential plan in a Jira project is fully gate-clean.

That is why two consumer projects accumulated five such plans in the two weeks after the Epic-first path shipped, with a clean gate on every run and no signal to anyone.

The asymmetry has a cause worth naming. The tracker branch keys on a boolean meaning simply not tracker-less, and that boolean lumps together two modes with opposite expectations: sequential numbering is correct for one of them by explicit prior decision, and wrong for the other. Widening the boolean would turn this repository's own gate red.

This FR adds a third branch keyed on the Jira mode specifically, reusing the provenance classifier the tracker-less arm already uses and hardened this week.

## Requirement

Under `mode: jira`, a sequential milestone plan whose git provenance shows it arrived at or after this release must fail the gate. One that arrived before must stay silent, requiring no action from any existing consumer project. `mode: linear` and `mode: none` must be byte-unchanged.

The arm cannot fire on this repository, which runs `mode: linear`. There is therefore no dogfood available, and fixture tests are the only evidence the arm works at all.

## Acceptance Criteria

- AC-STE-443.1: `classifyPlanProvenance` accepts an optional epoch argument; when omitted it uses `MINT_EPOCH` exactly as today. Every existing `mode: none` call site and every existing test passes unmodified. {#AC-STE-443.1}
- AC-STE-443.2: `JIRA_EPIC_EPOCH` is an exported module constant equal to `2026-08-05T00:00:00Z` — v2.60.0's ship date, documented as the release that made sequential Jira plans legacy, in the shape `MINT_EPOCH` already uses. {#AC-STE-443.2}
- AC-STE-443.3: The walk branches on `mode === "jira"` specifically, never on the `isTracker` boolean. Under `mode: linear` the only plan rule remains id-absence, since sequential numbering is Linear's specified behaviour. {#AC-STE-443.3}
- AC-STE-443.4: Under `mode: jira`, a non-minted sequential `M<N>` plan classified `fresh` against `JIRA_EPIC_EPOCH` produces an error-severity violation; `legacy` produces nothing; `undecidable` produces a warning-severity advisory whose remedy names `kind: legacy`; `exempt` produces nothing. Messages follow the NFR-10 canonical shape already used by this probe. {#AC-STE-443.4}
- AC-STE-443.5: The pre-existing tracker-mode rule — no plan may carry an `id:` line — still fires under `mode: jira`. The new arm adds a check; it never replaces one. {#AC-STE-443.5}
- AC-STE-443.6: Exemption reuses `EXEMPT_PLAN_KINDS` (`scaffolding`, `legacy`), read through the same frontmatter path so CRLF- and BOM-prefixed plans are recognised. No second exemption key is introduced. {#AC-STE-443.6}
- AC-STE-443.7: A fixture reproduces the reported incident: a `mode: jira` project with one sequential plan introduced 2026-08-04 and one introduced 2026-08-05. The first stays silent, the second fails. {#AC-STE-443.7}
- AC-STE-443.8: For identical fixtures, `mode: linear` and `mode: none` produce byte-identical violation lists before and after this change, asserted by test rather than by inspection. {#AC-STE-443.8}
- AC-STE-443.9: Every test added by this FR is mutation-verified — each must fail when run against the pre-change module and pass against the post-change module, and the verification is recorded in the commit message. A test that passes against both proves nothing, and no dogfood exists to catch that here. {#AC-STE-443.9}
- AC-STE-443.10: `bun test` from `plugins/dev-process-toolkit` is green with zero failures. No new gate probe is registered and the documented probe count stays 74. {#AC-STE-443.10}

## Technical Design

The classifier already answers the only hard question — when did this plan arrive — and answers it robustly after this week's hardening: keyed on the milestone token's two canonical paths, so it survives archival, reopen cycles, and content-changing archive commits, and it treats a monorepo package as datable rather than grandfathering it silently. None of that logic needs to change. What it needs is to stop hardcoding which epoch it compares against.

An optional parameter defaulting to the existing constant is the smallest change that achieves this. Every current caller omits it and gets today's behaviour by construction, which is what makes the `mode: none` regression risk near zero.

The branch keys on the mode string rather than the boolean, and that choice is the whole point of the FR. Sequential numbering under Linear is specified behaviour, frozen by an earlier decision when only Jira was flipped to Epic-first. A branch keyed on the boolean would police Linear identically and fail this repository on its own hundred-plus archived plans. The distinction must live in the code, not in a comment.

The epoch differs from the tracker-less one deliberately. Reusing that constant would date the boundary two weeks earlier and flag five plans in two consumer projects that cannot be edited — a forced migration arriving through the side door. The epoch is set to this release's ship date so every plan extant today is grandfathered and only future ones are policed.

Ordering within the walk matters: the existing id-absence check runs for every tracker mode, and the new sequential check runs additionally for Jira. Expressing the arm as an extra condition rather than a replacement keeps the two invariants independent, so a plan can violate both and report both.

## Testing

The incident fixture is a real temporary git repository with commits authored either side of the epoch, not a mock — the same shape as the tracker-less arm's fixture, which proved its worth by catching a defect no synthetic case would have.

The cross-mode invariant in AC-STE-443.8 is asserted directly: the same plan fixtures are run under all three modes and the linear and tracker-less outputs are compared against recorded pre-change values. Asserting only the new Jira behaviour would leave the widening risk untested, and that risk — a boolean that quietly polices Linear — is the one that would break this repository.

AC-STE-443.9 is a process requirement with a concrete procedure: stash the module, run the new tests against the previous implementation, confirm each fails, restore, confirm each passes. It exists because the arm is unfirable here, so a green suite is not evidence. The tracker-less work this week produced a regression test that passed against both implementations and was silently vacuous until mutation-tested; that is the failure this AC prevents.

The advisory path is exercised by severing the introducing commit, matching the existing technique.

## Notes

This is the second half of a defect the tracker-less side closed days ago. That side got a provenance-keyed arm and a repair migration; the Jira side got neither, and the asymmetry was invisible because both halves of probe seventy-three are in one module and each looked complete on its own.

The repair half is deliberately absent here. The consumer projects cannot be edited, so there is nothing to repair from this side, and the plans already written stay exactly as they are.

Making the Epic-first path actually execute is explicitly out of scope. Nothing currently runs it — the module that would perform the attach has no command-line entry point, so its branches are unreachable in a real invocation, and the operation names its epic branch requires appear in no skill, document, or adapter surface. That is a design question deserving its own milestone; this FR only makes the drift loud.

## Implementation notes

- AC-STE-443.8 and AC-STE-443.9 are mutually unsatisfiable as literally written — an invariance test asserting `mode: linear` is unchanged passes against the pre-change module *by construction*, which is precisely what invariance means. Resolved as two-pronged mutation verification: behavioural tests against the pre-change tree, invariance tests against targeted semantic mutants. AC.9's wording should be amended in a follow-up to say "each test fails against the pre-change module OR against a named mutant of the guard it pins".
- The FR's § Testing prescribes "stash the module" for the mutation pass. That is insufficient: a module-only revert leaves the SKILL-row test (AC-STE-443.10) green, silently counting it as mutation-verified. The pass run here reverted every touched file to HEAD instead.
- Mutation verification caught two defects a green suite hid. The AC-3 source pin greped the whole module for `mode === "jira"` and was satisfied by the module's own header comment — it survived the boolean-widening mutant, the exact regression it existed to catch. And the `undecidable` advisory asserted no epoch, so handing the shared row-builder `MINT_EPOCH` instead of `JIRA_EPIC_EPOCH` left the entire suite green. Both are now pinned.
- `JIRA_EPIC_EPOCH` is midnight UTC on the ship date, so the module's original claim to grandfather every extant plan "BY CONSTRUCTION" was false for the hours between 00:00Z and the actual release. AC-STE-443.2 pins the constant, so the prose was corrected to state the residual window rather than the epoch moved.
- Residual, not fixed: `rowsOf` in the test projects 5 of a violation's 7 fields, so AC-STE-443.8's "byte-identical" is asserted over `{file, line, expected, actual, severity}` and would not catch a prose-only change to `note`/`message` in the linear or mode-none arms. Covered indirectly by the m119 suite.
