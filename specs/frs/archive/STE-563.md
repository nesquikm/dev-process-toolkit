# The AC toggle survives a milestone-keyed branch

## Summary

The default branch template renders a milestone token, not a ticket id, so a Linear project on the defaults produces a branch carrying no ticket. Tier-1 resolution misses, Tier-2 asks a human, and a headless run has none — so the criteria push is withheld.

Measured 2026-09-05: a green gate, a Done ticket, four criteria that never toggled.

Template and resolver disagree by construction; repairing either alone is a half-fix.

## Requirement

The active ticket resolves without depending on the branch name carrying it, deterministically and with no interactive step, on a branch the shipped default template rendered. The template's output and the resolver's accepted input are asserted to agree FROM BOTH SIDES, so a future change to either one reds rather than silently re-opening the gap.

## Acceptance Criteria

- AC-STE-563.1: `adapters/_shared/src/branch_ticket_resolution.ts` exports `milestoneBranchSegment(branch)`, which returns the milestone segment a milestone-keyed branch carries — `feat/m19-x` yields `m19`, `feat/m_f040b5-x` yields `m_f040b5` — and `null` for a branch carrying none. The match is word-bounded in the same discipline `matchesMilestone` already uses, so `m19` is not found in `m191` and `m_proj_500` is not found in `m_proj_5001`. Pure, no I/O.
- AC-STE-563.2: The comparison happens in the RENDERING domain, never by reconstructing a milestone id from a branch. `milestoneBranchToken`'s epic arm lowercases the key and rewrites `-` as `_`, so `M_PROJ-500` and `M_proj_500` both render `m_proj_500` and the branch cannot say which it came from. `milestoneMatchesBranch(milestoneId, branch)` therefore renders the CANDIDATE through the same `canonicalBranchTemplate` + `milestoneBranchToken` path the branch was built with and compares the results. Asserted with a case-and-separator-varying pair that a reconstructing implementation would get wrong.
- AC-STE-563.3: `resolveTicketForBranch(projectRoot, branch, { idPattern })` returns a discriminated resolution: `{ tier: "branch-id", ticketId }` when the branch itself carries a ticket id matching the adapter's `id_pattern` (Tier 1, unchanged and still first); `{ tier: "milestone-fr", ticketId, milestone, frPath }` when the branch is milestone-keyed and EXACTLY ONE FR under `specs/frs/` (active, then `archive/`) binds to that milestone and carries a tracker id; `{ tier: "interactive", reason }` otherwise. The reason names what was found — no milestone segment, no matching FR, or the ids of every candidate when more than one matched.
- AC-STE-563.4: More than one candidate NEVER resolves. Two FRs bound to the same milestone yield `interactive` naming both tracker ids, not the first, not the newest, not the one whose slug is closest to the branch. That is the guess `docs/ticket-binding.md` forbids, and a milestone branch with several FRs on it is the ordinary case rather than an edge one.
- AC-STE-563.5: The new tier is documented in `docs/ticket-binding.md` as Tier 1b, between the branch regex and the interactive prompt, stating that it is deterministic, that it reads only local files, that it refuses on ambiguity, and that the mandatory confirmation prompt is unchanged — resolution is not consent. `docs/gate-check-tracker-mode.md`'s pre-flight step 1 names it, so the surface that withheld the toggle says how it now resolves.
- AC-STE-563.6: TEMPLATE-TO-RESOLVER agreement. For every milestone-id producer in the union grammar — `milestoneIdFromEpicKey`, `milestoneIdFromUlid`, `milestoneIdFromLinearMilestone`, and a bare sequential `M<N>` — rendering `buildBranchProposal` with `canonicalBranchTemplate`'s selection for that id produces a branch on which `milestoneMatchesBranch(<that id>, branch)` is true. Driven from the PRODUCERS, not from a list of example branches, so a new producer that renders unresolvably reds this leg.
- AC-STE-563.7: RESOLVER-TO-TEMPLATE agreement, the other direction and not implied by AC.6. Every branch `milestoneBranchSegment` accepts is a branch `buildBranchProposal` can render: the accepted segment is fed back through the renderer and must reproduce itself. A resolver that accepted shapes the template never emits would pass AC.6 while binding tickets on branches nobody can produce, which is the same class of wrong-subject agreement as pinning a rendering.
- AC-STE-563.8: The measured case is closed end to end, over a fixture tree on disk: a project whose branch is `feat/m_b11423-greet-helper` and whose single FR carries `milestone: M_b11423` and `tracker: { linear: STE-559 }` resolves `STE-559` at tier `milestone-fr` with no prompt. A ticket-keyed branch (`feat/ste-559-greet-helper`) still resolves at tier `branch-id` — the pre-existing path is unchanged, asserted rather than assumed.
- AC-STE-563.9: The module carries an `import.meta.main` front door, so the surfaces that order it name something a reader can run. Asserted behaviourally by executing it and reading its exit status, not by grepping for the guard.
- AC-STE-563.10: Falsifiability — AC.2, AC.4, AC.6 and AC.7 are mutation-tested. Replacing the rendering-domain comparison with a reconstructing one reds AC.2; returning the first candidate instead of refusing reds AC.4; dropping any one producer's arm reds AC.6; widening the accepted segment grammar beyond what the template renders reds AC.7. Each mutation is asserted to red ITS OWN leg and to leave its siblings green.

## Technical Design

One new pure module beside the branch renderer, importing that renderer rather than restating any part of it — the agreement this FR asserts is only meaningful if both sides read one implementation.

The FR walk reads frontmatter through the shared normalizer, so a CRLF or BOM-mangled file is read rather than silently skipped, and looks at active FRs before archived ones in the house order.

Resolution returns a value. It does not prompt, transition, or write: the mandatory confirmation prompt stays where it is and stays mandatory. This changes what the skill knows, never what it may do without asking.

## Testing

Fixture trees built on disk under a temporary root, so the FR walk is exercised against real files rather than a mocked reader.

The two agreement legs are driven from the producers and from the accepted grammar respectively, and each is mutation-tested: a leg that cannot red is a leg that says nothing about the subject, which is the finding the sibling FR in this milestone is about.

## Notes

Whether the same disagreement exists on the Jira path is UNMEASURED. Jira mints milestone identity by a different route, and the run deliberately did not infer the Jira result from the Linear one. AC.6 covers the Epic-key producer at the unit level, which is evidence about rendering rather than about a live run; a targeted Jira leg would settle it.
