# Derive the TDD hook's path predicates from the detected stack

## Summary

The guard requiring a test-driven run recognises one project layout: one source directory, a test directory the reference does not name, and three extensions from one language.

Measured by executing the shipped classifier, Dart, Python, Go and Kotlin commits carrying a source and its test all classify as carrying nothing to guard.

A longer extension list is the same defect spelled differently. The stack is already detected from marker files, and the rules should follow that.

## Requirement

The hook's source and test predicates are derived from the stack the toolkit already detects from marker files, rather than from a private list of directory names and extensions. Every stack the toolkit bootstraps is recognised. The documented trigger and the implemented trigger describe the same thing, in whichever direction resolves the contradiction between them.

## Acceptance Criteria

- AC-STE-547.1: A staged set of a source file and its test classifies as requiring the run on every stack the toolkit ships an example configuration for — measured at minimum for Dart, Python and Kotlin, each asserted separately rather than as a group.
- AC-STE-547.2: The stack is resolved through the shared marker-based detection the toolkit already uses, not a second copy of that knowledge inside the hook. A test asserts the hook and the gate detector agree on the stack for one fixture per recognised marker.
- AC-STE-547.3: `docs/hooks-reference.md`'s documented trigger and the implemented predicates name the same directories. The contradiction is resolved in one direction and asserted from both sides, so neither can drift alone.
- AC-STE-547.4: The currently-recognised TypeScript layout is unchanged. The existing expectations run unmodified — a rewritten assertion would conceal exactly the regression this criterion excludes.
- AC-STE-547.5: A suffix outside the recognised set for a recognised stack still classifies as requiring the run when the stack's own convention matches it, so the rule is the stack's convention rather than an extension list.
- AC-STE-547.6: Each new stack's recognition is falsifiable: removing that stack's rule turns its fixture from requiring the run back to carrying nothing, asserted by a mutation rather than by inspection.

## Technical Design

The hook's private `SRC_RE`, `TESTS_DIR_RE` and `TEST_SUFFIX_RE` in `templates/hooks/_lib/hooks/pre-commit-tdd-orchestrator.ts` are replaced by a per-stack rule set keyed on the marker-based detection behind `detectGate` (`adapters/_shared/src/capture_skip_baseline.ts`, `STACK_MARKERS`). The hook resolves the project's stack once, then applies that stack's source and test conventions.

Reuse rather than extend-in-place: the marker table currently answers "which runner", and this adds "which layout" to the same subject. One table, two questions, so a stack added later gains both at once. A private copy inside the hook is what produced this defect.

`classifyStagedPaths` keeps its call signature and its existing verdicts; only the predicates behind it change. Four facts measured on this tree before implementation change what that costs, and the plan records them.

## Testing

`tests/pre-commit-tdd-orchestrator.test.ts` gains a per-stack table plus mutation legs.

- AC.1 — one case per stack, each asserting `tdd-required` for a source-plus-test pair in that stack's real layout. Asserted individually, not by iterating a list into one expectation, so a stack that regresses names itself in the failure.
- AC.2 — a fixture per recognised marker asserting the hook's resolved stack equals `detectGate`'s. Include a project carrying two markers to pin the precedence, since the shared table is ordered most-specific-first and that ordering becomes load-bearing here.
- AC.3 — read the documented trigger sentence and the implemented rule and assert they name the same directories. A one-sided assertion lets the other drift, which is the state this AC exists to end.
- AC.4 — the file's existing TypeScript expectations are byte-unchanged; assert the count of prior assertions is unchanged rather than trusting review.
- AC.6 — per stack, remove that stack's rule and assert its fixture falls back to `no-fr`, then restore and assert it recovers. A recognition rule with no mutation proof is a rule nobody has shown can fail. **The mutation empties that stack's LAYOUT and leaves its marker entry standing** — deleting the entry outright makes the project unidentifiable, which is a different question and, once STE-548 lands, a different answer.

## Notes

The reporter's second scenario is right for a reason worth keeping: a TypeScript project using the documented test directory does fire, but via the suffix rule, not the directory rule. So the documented directory rule has never been load-bearing, and reconciling the two surfaces cannot be done by simply believing the document.
