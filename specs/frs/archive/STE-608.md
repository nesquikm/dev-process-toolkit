# A milestone mint names the act it performs and never joins silently

## Summary

In a tracker project two repositories share, creating a milestone can quietly bind to another repository's look-alike milestone, even a closed one, right after the operator approved a create.
One executed decision now reads the container listing before anything is written and names its act in the approval question.
The write that follows refuses to perform any other act.
Joining by key works on both trackers, and a new milestone is always keyed by the tracker.

## Requirement

Measured at HEAD ac1f3cb (findings MI-1, RS-2, ENUM-6, LJ-3, LIN-1, MI-2, MI-3, RS-3, LJ-1, plus two skeptic findings):

- The find leg of both mints runs on every call. Exactly one row whose title normalizes equal is bound, with or without `{ join: true }`; there is no status filter, so a Done Epic is joined; and the result `{ epicKey, milestoneId, labelled }` / `{ milestoneUuid, milestoneId }` has no field that tells a join from a create (`mint_milestone_epic.ts:144-149`, `mint_milestone_linear.ts:158-163`).
- `{ join: true }` changes only the zero-match case, so a join carries no evidence of intent.
- The one call `/spec-write` mandates, `resolveMilestoneIdentity`, cannot express a join on Linear (its Linear branch calls `mintMilestoneLinear` with no options) and has no front door, so the live session cannot run it at all; every live mint is the LLM following prose.
- `milestoneAllocationGateSpec` runs the Linear mint INSIDE the computation of the gate's default, so the milestone is created before the gate that approves it is asked. The Jira gate default is the id derived from an Epic that already exists.
- The approved act is not the performed act: the live draft gate read "y creates the Jira Epic", then the find leg ran and could have joined. The title question never shows the container's existing titles.
- The live session wrote the Epic label as a SET (`fields.labels=["milestone-M_GB_44"]`), not the read-merge `adapters/jira.md` prescribes; on a joined Epic that carries other labels this clobbers them.
- `skills/spec-write/SKILL.md:177` says "The join is by key and never by name" beside a join call that matches by normalized title only, and line 179 still says Linear's gate default "is the sequential `M<N>`", stale since tracker-first Linear milestones.
- A retyped near-miss title (tab, trailing period, hyphen for space, a canonical-renamed Epic) mints a twin in default mode and refuses in join mode; the only reliable join is by key, which nothing mandated route exposes.
- A hand-typed numeric milestone survives in tracker mode. The explicit-`M<N>` door, `bun run adapters/_shared/src/next_free_milestone_number.ts <specsDir> <M-token>`, answers `verdict=free` for an unclaimed number whatever the mode, so a new `M<N>` plan can still be started in a Jira or Linear repository. In a shared container two repositories' numeric labels then merge into one bucket: live in NEX, `milestone-M8` sits on NEX-211 (FE) and NEX-297 (BE), and both repositories hold an active M13 (LJ-1).

Required behaviour:

1. One pure decision, `decideMilestoneMint`, owned by `adapters/_shared/src/milestone_token.ts` beside the one title normalizer, decides create or join from the container listing the session enumerated, before any write. Both mints and the gate spec call it; nothing else re-derives the decision.
2. A join is either by KEY (the operator names the existing Epic key or Linear milestone token) or by TITLE (a find-leg hit). A title join in a repository whose binding is shared (the `shared` flag STE-602 adds to `readWorkspaceBinding`) has no safe default and must be answered explicitly.
3. Closed containers are never joined by title, and a key join onto a closed container refuses.
4. The approval question is the decision's own sentence, and the write that follows refuses to perform an act other than the one approved.
5. The Jira label write is computed as a read-merge by executed code, and the tracker-write hook refuses a label write that drops a label the decision observed.
6. Old clients: a client below the declared version floor has none of this code and still joins by title silently; its protection is the version floor and the stop paragraph of STE-603 and the untagged-ticket listing of STE-605. An Epic an older client minted without its label is joined like any other row, and the computed label line adds the missing label. This FR's release version is the floor the plan tells operators to declare once it ships.
7. In every tracker-mode repository, shared or not, a NEW milestone is always tracker-keyed (`M_<KEY>` from an Epic, `M_<6-hex>` from a Linear milestone), and FRs keep their tracker-id names. The explicit-`M<N>` door refuses a typed number when the CLAUDE.md beside `<specsDir>` binds `mode: jira` or `mode: linear`, with the remedy to mint through the tracker by running the decision front door. Old numeric milestones are never renamed or migrated: their plans, labels and tracker containers keep archiving and shipping as they do today. `mode: none` keeps today's door. The door's row in `docs/workflow-overview.md` states the tracker-mode refusal.
8. A plan file written by hand bypasses that door, so probe #73 (`plan_identity_mode_conditional.ts`) gains a `mode: linear` arm mirroring its `mode: jira` one. Today Linear runs no provenance rule at all. A new constant, `LINEAR_TRACKER_KEY_EPOCH`, is this milestone's release date. A sequential `M<N>` plan that git introduces at or after it is an error whose remedy is to mint through the decision front door. The date comes from the existing `classifyPlanProvenance` machinery, whose oldest add across the active and archive paths survives archival. Earlier plans are grandfathered and never renamed, `kind: legacy` clears a misdated one, and an undecidable date is the shared warning advisory.

## Acceptance Criteria

- AC-STE-608.1: `decideMilestoneMint(input)` is exported from `adapters/_shared/src/milestone_token.ts`, performs no I/O and receives no provider. Its input is the mode, the project, the enumerated rows and exactly ONE of a human title or a join key; supplying both, or neither, throws an NFR-10 three-line refusal. It returns `{ act: "create" }` or `{ act: "join", via: "key" | "title", key, name }`, or throws an NFR-10 refusal. Its parameter type has no provider or path field, and `mintMilestoneEpic`, `mintMilestoneLinear` and `milestoneAllocationGateSpec` each call it: a mutation that makes any one of them skip it turns that caller's decision test red.
- AC-STE-608.2: Join by KEY never compares a title. Jira: a join key equal to a listed Epic key joins that Epic, and `milestoneId` is `milestoneIdFromEpicKey(key)`. Linear: a join key that is either a milestone UUID or an `M_<6-hex>` token joins the one row whose identifier derives to that token through `milestoneIdFromLinearMilestone`. A row whose title shares no word with anything typed still joins (the canonical-renamed Epic of MI-3). A join key naming no listed row refuses, names the project and the key, and never falls through to create. Two listed Linear rows deriving the same `M_<6-hex>` token refuse as ambiguous, naming both identifiers. Through the mandated call: `resolveMilestoneIdentity` accepts the listed rows and a join key on both modes and returns the joined `milestoneId` with `outcome: "joined"`, making zero create calls; on HEAD its input has no join field and its Linear branch mints (red on HEAD).
- AC-STE-608.3: Closed containers. A Jira row whose status category is done is excluded from the TITLE comparison: a title matching only closed rows decides `create`, and the decision names every excluded key. A join KEY naming a closed row refuses, and the remedy says to reopen it in the tracker first. A Jira row carrying no status field makes the whole decision refuse, because the listing cannot tell open from closed. Linear rows carry no status: the front door prints the closed rule as not applicable for Linear, never as passed.
- AC-STE-608.4: Title leg. Zero open matches decides `create`; one decides `join` via title; two or more refuse with the existing ambiguous refusal naming every candidate. The receipt records the decision (`act`, `via`, `key`, the title or join key) and, in `evidence`, the listing it was computed from: the listing file's SHA-256 and the listed row keys in order, so a grader can match it to a recorded tracker answer. The receipt lands under `<projectRoot>` even when the command runs from another repository's checkout (a relocated leg asserts the receipt lands under `<projectRoot>` and nothing lands under the working directory). ## Technical Design

The decision is pure and lives beside the title normalizer, which both mints and the dispatcher already import, so one home serves all callers and no import cycle forms. The live session enumerates through MCP and hands the raw response to the front door, the precedent `discover_field.ts` set. The front door prints the decision and writes a receipt. The hook, which until now only reminded on container writes, compares each one against that receipt, turning a prose order into a refusal. The mints take the approved decision and refuse a different act. Retries keep their find leg, so timeout idempotency survives.

## Testing

A new suite drives `decideMilestoneMint` over Jira and Linear listings: key join, renamed Epic, closed-only match, statusless row, ambiguous, empty, not-last page. It spawns the front door. It drives both mints with `expect` on first-attempt and retry paths, and the gate spec with a create counter. Hook legs run the hook's shell entry point on recorded payloads, with receipts present, absent, unreadable and from another session. The two amended prose suites stay green.
