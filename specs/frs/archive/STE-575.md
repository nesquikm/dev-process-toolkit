# /pr transitions the ticket forward only

## Summary

The post-create step moves the bound ticket into the review lane every time, without reading where the ticket already is. On a project whose review lane sits behind its done lane, that drags a finished ticket backwards, and the next gate run reads it as genuine drift.

Read the status first, and skip the move once the ticket has reached the done role. Say so in words: a silent skip is a failure this repository has condemned before.

## Requirement

The post-create tracker transition is decided from the ticket's observed status rather than issued unconditionally, and every skip is reported in plain words rather than passed over in silence.

## Acceptance Criteria

- AC-STE-575.1: A pure helper `prTransitionDecision(observedStatus, config)` returns `{ action, reason }` where `action` is `"transition"` or `"skip"`. It performs no input and no output, so it is decidable in a test without a tracker.
- AC-STE-575.2: When `statusToRole(config, observedStatus)` is `"done"`, the helper returns `action: "skip"`. This is the forward-only clause.
- AC-STE-575.3: When the project's configured `in_review` status is byte-identical to its `in_progress` status — no review lane exists — the helper returns `action: "skip"`. Issuing a transition to a lane the project does not have is a write with no destination.
- AC-STE-575.4: In every other case, including an unknown status, a non-key status, and an absent config, the helper returns `action: "transition"`. Today's behaviour is preserved wherever the two skip clauses do not fire.
- AC-STE-575.5: Every skip carries a non-empty `reason` naming the observed status and why it was not moved, and `/pr` reports that reason. A skip with an empty reason fails this clause.
- AC-STE-575.6: Falsifiable end-to-end arm, against a synthetic config that declares a real review lane distinct from both in-progress and done, with the ticket observed in the done status. After the helper's decision, routing the resulting status through `routeWithTolerance` against the `done` role yields `pass`. Before the change the same arm yields `fail-genuine-drift`, because the unconditional transition leaves the ticket in the review lane.
- AC-STE-575.7: Companion arm on the same synthetic config: `activeTicketDriftPasses` is true for the post-decision status and false for the status today's unconditional transition would leave behind.
- AC-STE-575.8: Mutation arm. Forcing the helper to return `action: "transition"` reds AC-STE-575.6 and AC-STE-575.7, proving both can fail.
- AC-STE-575.9: The four regions that describe the post-create sequence are amended together: the skill's tracker-mode bullet, the post-create step list in `docs/pr-tracker-mode.md`, the draft-rationale paragraph in that same file, and the workflow diagram edge in `docs/workflow-overview.md`. A test asserts each of the four independently carries the forward-only condition in one paragraph, so amending three and leaving one fails.
- AC-STE-575.10: The MCP call budget is unchanged at two. The observed status is already read before any write, so the decision costs no additional call.

## Technical Design

The helper lives beside `statusToRole` in the existing tracker-config module rather than in a new one. Reachability probe #81 grades ordered module references in shipped markdown, not adapter modules, so an added function raises nothing — and no prose this FR writes orders a reader to run the module, which is what would.

The synthetic config matters more than it looks. The repository's own tracker config collapses the review lane onto in-progress, so building the load-bearing arm on it would satisfy the no-review-lane clause and prove nothing about the forward-only one. The arm therefore declares its own three-lane config.

## Testing

The two skip clauses are tested separately, because a single fixture that trips both cannot show which one fired.

The guard can over-fire when a project legitimately reopens a done ticket for a follow-up pull request. That is why the skip is reported rather than silent: the operator sees the decision and can move the ticket by hand. Silence would make an over-fire indistinguishable from correct behaviour.

## Notes

The producer and consumer surfaces have drifted apart here before — a skill amended while its reference document kept the old unconditional wording. The three-surface clause exists because that shape has shipped in this repository more than once.

## Implementation notes

- `prTransitionDecision` has no runtime call site, and that is the architecture rather than an oversight: `/pr` is a skill an agent reads, not a TypeScript program, so the shipped executable for this rule is the prose in the four amended surfaces and the helper is its single testable statement. The two agree today and nothing grades that agreement — a real divergence risk, recorded here rather than closed, because closing it means giving `/pr` a runtime, which is a larger change than this FR.
- The prose surfaces do not state what happens when a project has no `specs/tracker-config.yaml`. The helper transitions in that case, preserving today's behaviour, but a future wirer passing a null config would not learn that from the docs.
- The audit found two ungraded surfaces still describing the transition as unconditional — the artifact-flow table in `docs/workflow-overview.md` and the adapter-author conformance checklist in `docs/tracker-adapters.md`. Both were corrected in this FR's commit. They are the producer/consumer asymmetry this FR's own Notes predicted, caught inside the milestone rather than after it.
