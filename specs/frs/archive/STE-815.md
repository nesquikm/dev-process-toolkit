# A settings change leaves a receipt, and one writer changes the file at a time

## Summary

An approved settings change records only that the approval was used, and it does so before the write.
Now a second receipt names each key with its old and new value, written only after the change succeeded.
A failed change writes no such receipt.
The settings writer takes a lock and refuses when the file changed since it was read.
A test pins which modules may call the writer.

## Requirement

A successful `/retro` apply leaves a change receipt recording what it changed, and the project settings writer serialises writers and refuses a write over bytes it did not read.

## Acceptance Criteria

- AC-STE-815.1: After every step of a `retro_proposal.ts apply` succeeds (settings write, `.gitignore` append, capture registration), apply writes a second receipt of kind `retro-change` whose evidence is `{ digest, applied_at, changes }`. `changes` is a list of `{ key, from, to }`, one per written key. `from` is the prior value, or `"absent"` when the key was not set. No `trial_id` key is written.
- AC-STE-815.2: When any apply step fails and the prior bytes are restored, no `retro-change` receipt is written. The `retro-apply` consumption receipt is written exactly as today.
- AC-STE-815.3: `writeProjectSettings` accepts `opts.expectSha256`. When it is given and the sha256 of the file's current bytes differs, the writer refuses with a `SettingsShapeError` in the NFR-10 shape naming both hashes, and writes nothing. Apply passes the hash of the bytes it read when it recomputed the proposal.
- AC-STE-815.4: `writeProjectSettings` holds an exclusive lock file at `specs/settings.yaml.lock` (created with `O_EXCL`) for its whole read-modify-write. A lock younger than 30 seconds held by another writer makes it refuse in the NFR-10 shape and write nothing. An older lock is replaced. The lock file is removed on every exit path, a refusal included.
- AC-STE-815.5: An importer-allowlist test lists every non-test `.ts` module under `plugins/dev-process-toolkit` (outside `node_modules` and `tests/`) that imports `project_settings_writer`. The list must equal the pinned set; a new importer fails the test with a message naming the module.
- AC-STE-815.6: `docs/retro-reference.md` describes the change receipt, its write order, and the lock and hash refusals.
- AC-STE-815.7: `bun test` from `plugins/dev-process-toolkit` reports 0 failures, and its skip identities equal the trunk baseline by name.

## Technical Design

In `retro_proposal.ts`, apply records each key's prior value through `currentValue` before the write, and calls `writeReceipt` for `retro-change` after the register step, outside the restore block. In `project_settings_writer.ts`, a small `withSettingsLock(path, fn)` wraps the existing body, and the hash check runs on the bytes read inside the lock. The allowlist test walks the tree with a regex on import specifiers.

## Testing

Apply tests with a stubbed transcript approval: a success (both receipts, change values), a register failure (no change receipt) and a stale-hash refusal. Writer tests cover a held fresh lock, a stale lock, lock removal after a throw, and the hash mismatch.

## Notes

The change receipt is the record a revert (STE-816) and a later trial must check against.

## Implementation notes

- two writers racing to replace the same stale lock is not exercised by a test — the rename-aside and inode check make it safe by construction; timing cannot be forced
- if the retro-change receipt cannot be written after a successful apply, a later revert has no receipt to check against — the refusal says the change is applied and lists it for a hand record
