# Every spawned smoke session carries a recorded id, and a passed leg cleans up after itself

## Summary

The loop and the smoke test start their child sessions without naming them, so afterwards nothing says which sessions a run owned.
From now on each child is started with an id its parent mints and writes to a run ledger that survives a reboot.
When the loop finishes, every leg whose verdict passed has its recorded sessions removed, while a failed or aborted leg keeps all of its evidence for triage.

## Requirement

Every `claude -p` spawn in `.claude/skills/conformance-loop/SKILL.md` (5 sites) and `.claude/skills/smoke-test/SKILL.md` (9 sites) passes `--session-id <uuid>`, minted by the spawning shell, and records `{run, leg, session_id, parent, spawned_at}` in a per-run ledger under `.dpt/` before it spawns. The loop's Termination runs the STE-593 cleanup in delete mode for each selected leg whose verdict artifact says `pass`, scoped to that leg's recorded sessions; a `fail`, `abort` or missing-verdict leg is kept whole and named in the closing summary with the manual command that clears it later.

## Acceptance Criteria

- AC-STE-594.1: Every `claude -p` spawn line in both skills carries `--session-id`, preceded by a ledger append for the same id; an enumerating meta-test counts spawn literals and paired appends in both files and fails on any spawn without one.
- AC-STE-594.2: The run ledger's path is composed only in `dpt_paths.ts`, sits in a git-ignored `.dpt/` subtree, and survives a `/tmp` wipe; the `.dpt` path-drift tests stay green.
- AC-STE-594.3: A grandchild spawned by `/smoke-test` records the run id and leg it inherits from its parent's environment, so one leg's scope covers its children and grandchildren.
- AC-STE-594.4: At Termination, a selected leg whose verdict artifact reads `pass` (the artifact, never the exit code) has its recorded sessions removed through the STE-593 delete mode and the survivor check passes; a `fail`, `abort`, missing or unreadable verdict deletes nothing of that leg, and the closing summary names the leg and its manual cleanup command; an unselected leg is untouched.
- AC-STE-594.5: Termination cleanup of a leg waits until none of its recorded pids answers `kill -0`, after orphan adoption, and never runs while one does.
- AC-STE-594.6: Every leg's findings file and approval record survive Termination cleanup.
- AC-STE-594.7: The actual Termination fence, extracted from the skill and run with `claude`, `bun` and the cleanup stubbed, gives opposite outcomes for a `pass` and a `fail` artifact, one case per leg derived from `SMOKE_LEGS`.
- AC-STE-594.8: A tandem fixture proves a passed leg's cleanup leaves a failed partner leg's sessions, pidfiles and processes untouched.
- AC-STE-594.9: Runtime, verified at the next live run (ships `[~]` until then): a live `/conformance-loop` run records every child and grandchild, and each passed leg leaves zero files for its recorded sessions in the stores keyed by session id (transcripts and their subdirs, `session-env`, telemetry, MCP logs) and zero token-ledger rows for them; shell snapshots, id-less orphans and emptied project dirs are left to manual mode (narrowed 2026-09-15 after the pre-PR review; see F21).

## Technical Design

Each spawn mints a uuid in shell and passes it as `--session-id`; cmux's wrapper skips its own id when one is passed (wrapper source, lines 884–888). A small TS writer appends ledger rows atomically, so shells never compose JSON. The loop exports the run id and leg to its children, which pass them to grandchildren. Termination gains one fence after the green probe: read each selected leg's verdict with the smoke verdict reader, then call the STE-593 front door scoped to that leg. Brace groups keep `{` and `} &` at column 0 so `leg_prose_surfaces` still parses them.

## Testing

Enumerating meta-test over both skills; a fence-execution harness with stubbed `claude`, `bun` and cleanup against pass, fail, abort and missing verdicts; ledger-writer tests for atomic append and three concurrent legs; the tandem fixture.

## Notes

Recording precedes spawning, so a fence that loops still records every launch it makes. Six tests pin the loop's skill and `leg_prose_surfaces` parses its spawn fence, so expect pinned-surface churn.
