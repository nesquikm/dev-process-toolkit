# Test waits and product child processes are bounded

## Summary

Some test helpers wait in a loop that blocks the whole test process.
While they wait, the test runner cannot stop them, even past their time limit.
Three product commands also start a child process and wait for it with no limit.
This change makes the waits pause without blocking and gives each child process a time limit.
It also records what to capture if the test run ever hangs again.

## Requirement

The `_ste594_harness.ts` waits (`waitForKind`, `waitDead`, `spawnLive`) and the two waits in the m_4df444-ste-595 test loop on `Bun.sleepSync`. Bun cannot pre-empt synchronous code, so a wait that overruns is reported only after it returns, and `spawnLive` forks `ps` every 20 ms with no timeout on any of those calls. Three product spawn sites have no bound either: the ownership check in the `spawn_receipt.ts` front door, typedoc in `signature_extractor.ts`, and the `bash -c` assertion in `falsifiability_harness.ts`. M_0cac80 also recommended a capture recipe for the next occurrence.

## Acceptance Criteria

- AC-STE-686.1: `tests/_ste594_harness.ts` and `tests/m_4df444-ste-595-phase-a-fence-run.test.ts` contain no `Bun.sleepSync`; their waits pause with `await Bun.sleep`, and every caller awaits them.
- AC-STE-686.2: Every `ps` spawn in `tests/_ste594_harness.ts` passes a `timeout` of at most 2000 ms.
- AC-STE-686.3: A wait whose condition never holds returns within its budget plus 500 ms, and a test that overruns its own timeout while waiting is stopped by bun at that timeout.
- AC-STE-686.4: The `spawn_receipt.ts` front door runs its ownership check with a 10000 ms `timeout` and `killSignal: "SIGKILL"`; a check that outlives it ends in the `ownership-unresolved` refusal naming the timeout, with nothing on stdout.
- AC-STE-686.5: `runTypedoc` in `signature_extractor.ts` passes `timeout: 60_000`, matching its dart and griffe siblings; a typedoc that outlives it returns `ok: false` with a reason naming the timeout.
- AC-STE-686.6: `runAssertion` in `falsifiability_harness.ts` passes a 60000 ms `timeout`, and an assertion that outlives it is reported as a command that did not complete, never as a count.
- AC-STE-686.7: `docs/implement-reference.md` carries the wedge capture recipe: run `ps -axo pid,ppid,pcpu,etime,command | grep bun` while the gate is stalled, and read a spinning test (one bun pid at high CPU) apart from a nested pile-up (a parent chain of bun test processes).
- AC-STE-686.8: The `gate_capture.ts` front door prints the identity (`file > test name`) of every failing test from the run it measured, read from that run's own junit report before the report is removed, so a red gate run can be diagnosed from its own capture without a re-run.
- AC-STE-686.9: The gate run bound in `gate_identity_run.ts` defaults to 40 minutes. A run that outlives it is sent SIGTERM, then SIGKILL after a short grace period, so a child that ignores SIGTERM still ends. The `gate_capture.ts` front door then reports the run as killed on the bound, naming the bound, not only as an unreadable report.
- AC-STE-686.10: Removing each new timeout, the SIGKILL escalation, or a naming step reddens at least one test.
- AC-STE-686.11: `bun test` from `plugins/dev-process-toolkit` reports 0 failures, and its skip identities equal the trunk baseline by name.

## Technical Design

The harness waits become async functions with the same arguments and budgets, and their callers become async tests. The product timeouts reuse values that already exist next to each site: 60 s for the typedoc siblings, and 10 s for the session probe that `owned.py` itself uses. Hung children are simulated with a stub command that sleeps longer than the bound. Tests shrink each bound through a seam whose default is the specified value: `DPT_OWNED_CHECK_TIMEOUT_MS`, `typedocTimeoutMs`, and `runAssertion`'s `timeoutMs`. Each kill is SIGKILL; the gate runner escalates to it after SIGTERM. A red run whose report cannot be read says so.

## Testing

Each bound gets a stub that never finishes and an assertion on elapsed time and outcome. The harness change is covered by its existing STE-594 and STE-595 suites, which stay green.

## Implementation notes

- AC-STE-686.10 battery, 2026-10-21: 7 controls green, 7 mutants red (owned-check timeout, its SIGKILL, typedoc timeout, assertion timeout, gate SIGKILL escalation, gate group kill on the `/bin/sh -c` arm, supervisor backstop timeout); hand checks reddened AC .2 on each harness `ps` timeout and AC .8 on the naming line.
- AC-STE-686.9 was added by operator ruling after gate run 3 spun at ~100% CPU for an hour with one unreaped zombie child; the 20-minute bound fired SIGTERM, which the spinning runtime never handled.
- The gate now runs under a supervisor in its own process group: SIGTERM at 40 minutes, SIGKILL 5 s later. A `/bin/sh -c` tree ignoring TERM was killed in 1318 ms with no survivors.
- AC-STE-686.9 bun-stack path (supervisor ruling, after gate run 5): a test drives `gate_identity_run.ts`'s `/bin/sh -c` arm with a TERM-ignoring stub `bun` and grandchild, and asserts both pids are dead and the bound is named. Mutant 6 signals the child pid instead of its group and reddens it: the grandchild survives.
- AC-STE-686.10 backstop (operator ruling A, after /spec-review marked it partial): a wedged supervisor, set up through the test-only `DPT_GATE_SUPERVISOR_WEDGE_FILE` seam, is cut by the caller's backstop (`DPT_GATE_SUPERVISOR_BACKSTOP_MS` shrinks it). The caller then SIGKILLs the gate group the supervisor recorded, so no orphan survives. Mutant 7 drops the backstop timeout and reddens the test.
- The AC .4 behavioural tests grade on an `armed` / `done` marker, not wall time, after a SIGTERM-trap race survived one loaded run.
- The failing-test names (AC .8) diagnosed gate runs 1, 2 and 4 directly from their own captures.

- dart pub get, dart run and griffe dump carry a 60 s timeout but no SIGKILL and no exitedDueToTimeout reason — pre-existing siblings outside this FR; candidate follow-up
- The bounded-waits ceilings are wall-clock (budget plus 500 ms) — they are AC .3's own literal budget and held across four loaded full runs
- After a backstop kill, a gate that holds the supervisor's stdout or stderr pipe open could still delay the caller's return — the test gate sends its stdio to /dev/null, so this is untested
