# A hook refuses shared-container tracker writes that skipped the deciding commands

## Summary

The deciding commands protect a shared container only if every write goes through them, and the model can skip a command.
A new guard runs before each tracker write the model attempts.
Where a repository declares a shared container, it refuses a write that no deciding command approved in the session, and every write from a toolkit older than the declared minimum.
Repositories that declare nothing see no change: the guard stays silent.

## Requirement

Measured at HEAD `ac1f3cb`: every create, import and claim decision on the live path is markdown the model follows; `hooks/hooks.json` registers PreToolUse hooks for `Bash` only (three commit and PR gates), so no hook ever sees an MCP tool call; and the teammate-machine evidence shows clients writing into shared spaces under rules nobody here can observe. The commands of STE-604, STE-605 and STE-606 are safe only if skipping them is refused.

### 1. Wiring

- `templates/hooks/process/pre-tracker-write-gate.sh` execs `bun run "${CLAUDE_PLUGIN_ROOT}/templates/hooks/_lib/hooks/pre-tracker-write-gate.ts"`, like its siblings.
- `hooks/hooks.json` gains a PreToolUse group whose matcher is generated from ONE list, `TRACKER_WRITE_TOOLS` in the hook module, as `^mcp__.+__(<names>)$`, so any server name matches (`atlassian`, `claude_ai_Atlassian`, `linear`, `claude_ai_Linear`, …). The list: Atlassian `createJiraIssue`, `editJiraIssue`, `transitionJiraIssue`, `addCommentToJiraIssue`, `addWorklogToJiraIssue`, `createIssueLink`; Linear `save_issue`, `save_milestone`, `save_comment`, `delete_comment`, `create_attachment`, `create_attachment_from_upload`, `delete_attachment`, `share_issue`, `unshare_issue`, `save_project`, and the label and project-level writes `create_issue_label`, `save_issue_label`, `retire_issue_label`, `restore_issue_label`, `save_project_label`, `retire_project_label`, `restore_project_label`, `save_status_update`, `delete_status_update`, `save_document`. Timeout `5000`, as its siblings. *(Amended by the round-2 pre-PR /spec-review: Claude Code reads a hook's `timeout` in SECONDS, so `5000` is 5,000 s, not 5,000 ms, and a timed-out PreToolUse command hook does not block the call. The budget this FR grades is the hook's own runtime, AC-STE-607.9. For the same reason an exception inside the hook refuses (exit 2): any other exit is non-blocking.)*
- The list is closed against an inventory, not against memory. A checked-in fixture holds every tool name both servers expose (captured from a live tool listing of each server, the capture date and count recorded beside it). Each inventory name sits in exactly one of `TRACKER_WRITE_TOOLS`, `TRACKER_READ_TOOLS` or `UNGATED_WRITE_TOOLS` (Confluence, Compass, Linear diff, release and notification writes, each with a one-line reason). A name in none of them fails the suite, so a server that grows a write tool is caught when the inventory is refreshed.

### 2. Classification

Each call is `create` (a `createJiraIssue` whose type is not Epic; a `save_issue` without `id`), `container` (a `createJiraIssue` of type Epic, `save_milestone`, `save_project`, and every label, status-update and document write — a renamed or retired label can strip a sibling's ownership tag from every ticket at once), or `ticket` (every other call). A ticket call's subject keys come from `issueIdOrKey`, both keys of a link, `id`, or the commented issue. Parent is read from either the `parent` argument or `additional_fields.parent`.

### 3. Target resolution

Receipts are read from the TARGET repository, never assumed to be the session's directory.

- Candidates: the git top level of `payload.cwd`, plus every root announced in this session's transcript by a `dpt-receipt: <absolute path> sha256:<digest>` line, read through `readTranscriptLines` — the one transcript reader of the guard family.
- An announcement counts only inside the non-error tool_result of a `Bash` tool_use whose command RUNS a module listed in `RECEIPT_ANNOUNCING_MODULES`, one exported constant of the hook module: the command is one plain `bun [run] <path> <subcommand> …` invocation, with no chaining, pipe, redirection, comment or substitution, the path is this plugin's own copy of the module (`${CLAUDE_PLUGIN_ROOT}` or `$CLAUDE_PLUGIN_ROOT`, bare or inside double quotes — `${CLAUDE_PLUGIN_ROOT}/…`, `"${CLAUDE_PLUGIN_ROOT}/…"`, `"${CLAUDE_PLUGIN_ROOT}"/…` — resolves to the hook's own root; an absolute path is compared as is; a relative path is refused), and the subcommand is the module's receipt-writing one: `create_idempotency_probe.ts decide`, `container_ownership.ts consent`, `ticket_ownership.ts confirm` (`RECEIPT_WRITING_SUBCOMMANDS`). A result carrying more than one announcement line announces none. No deciding module prints tracker- or model-supplied text at the start of a `dpt-receipt:` line: page and argument text is flattened onto one line (`printable`), and `normalize` refuses a title that starts with the prefix. A title a plain command cannot quote (a backtick, `$` or `\`) is passed with `--title-file <path>`. Every refusal names this plain-invocation rule with the exact accepted shape, and names the latest deciding command the gate ignored for its shape. *(Amended by the round-2 pre-PR /spec-review: any subcommand of an announcing module counted, so `create_idempotency_probe.ts normalize '<announcement>'` echoed a self-written receipt into an accepted result, and `container_ownership.ts list` printed a page key holding one; the hooks.json quoting style was rejected; and the refusal never said why a real `decide` was ignored.)* It counts only for a path under `receiptsDir(<root>, <this session>)`, and only while the file still hashes to the digest the command announced. *(Amended by the pre-PR /spec-review: the first version matched the module's NAME anywhere in the command text, so `echo "dpt-receipt: …"  # ticket_ownership.ts` announced a receipt the model wrote itself.)* This milestone lists the three deciding modules (`create_idempotency_probe.ts`, `container_ownership.ts`, `ticket_ownership.ts`); a later milestone that adds a deciding command appends its module there and nowhere else, and a module that writes receipts the gate must not trust (a gate-evidence receipt) is never listed. A receipt file written any other way — the Write tool, an `echo` of the announcement, assistant text quoting it — authorises nothing: the model can skip a command, so it must not be able to stand in for one. The grammar grades the command TEXT, not the environment it runs in: a `bunfig.toml` `preload` (in the working directory or the global config) or a `bun` shim earlier on a writable `PATH` directory can make an accepted command print a forged announcement. That environment-tampering class is a recorded residual (Implementation notes), not a guarantee. *(Amended by the round-3 pre-PR /spec-review.)*
- The call's container: Jira `projectKey`, or the project prefix of each subject key; Linear `project` and `team` on a create, the team prefix of an identifier otherwise.
- Declared targets: candidates whose reader (STE-602) says `shared` and whose binding matches the container, compared case-insensitively (`gf` is `GF`, `ste` is `STE`; the trackers match keys without regard to case). *(Amended by the round-2 pre-PR /spec-review: an exact-case compare let a case variant pass as undeclared.)* When several declared candidates bind the call's container (a cross-repository session), a `create` targets the one whose `repo_tag` the payload's labels carry, and none or more than one is refused as unresolvable; a `ticket` call targets the candidate that owns its subject (§4), and is refused when none does. Receipts are read only from the chosen target. On Linear an identifier's team prefix cannot tell the team's projects apart, so a ticket write in a declared team is gated even when the ticket sits in another project of that team: an over-refusal that is loud and names the ticket, never a silent pass.

No declared target → exit 0 with no stdout and no stderr: byte-identical to today, when no hook ran at all.

### 4. What is refused

Each refusal exits 2 with the NFR-10 block from `emitNFR10("Refusing", …)` (hook `pre-tracker-write-gate`), naming the tool, the subject or container, the target root, and the command that would have authorised the write.

- The running version, read from the hook's own plugin manifest, is below any declared target's floor.
- A declared target's declaration is malformed — the reader's own text.
- The container or the subject cannot be resolved (a numeric issue id, a project UUID, a comment id alone) while any candidate is declared. On a create this includes a Linear team or project named by UUID or slug and a numeric Jira project id; a plainly named container no candidate declares stays silent.
- A `create` with no `create` receipt in the target, for this session, whose payload matches the call on project, normalized title, labels containing the tag (and the numeric milestone label when one is set), and container (parent or milestone).
- A `create` whose matching receipt is spent. A `create` receipt authorises exactly ONE create tool_use after its announcement, whatever that call's result. Receipts are allocated to create tool_uses in transcript order, pending ones included, so two creates in one assistant turn never share a receipt. A create that timed out may still have made the ticket, and a tracker search can lag its index, so after a create tool_use of an earlier turn whose result is an error that does not prove the call never ran (a timeout, a server error, an interrupt — not a hook or permission denial, a user rejection, an input-validation error, or a definite tracker rejection: a 4xx status other than 408 with no timeout, 5xx or interrupt wording, which proves nothing was written), or that has no result, NO create receipt — fresh or not — authorises another create of the same ticket (normalized title, project, container). When retry-3 still misses, the refusal names the concrete next step: ask the operator (AskUserQuestion) to search the tracker by hand, then either `ticket_ownership.ts confirm` the ticket they find or have them create it by hand. *(Amended by the round-3 review: a 400 validation rejection locked the corrected create out for the rest of the session, and "a person decides" named no action.)* The retry runs `decide --attempt retry-<N>`, which searches for it: a `reused` decision's receipt authorises writes to that ticket, and in a shared repository a retry never yields a create receipt (retry-3 misses stop for a person, STE-604). This is the double-create the GF-90/GF-91 pair shows, refused in code. *(Amended by the pre-PR /spec-review: the first text promised a fresh retry receipt STE-604 cannot write, and parallel creates shared one receipt. Amended again by the round-2 review: an honest re-run of `decide --attempt fast` after a timed-out create could miss the ticket through index lag and mint a fresh create receipt — the GF-90/GF-91 double create with nobody lying.)*
- A `ticket` call on a subject the target does not own. Owned means one of: bound by an FR file tracked in the target's git index; created in this session (a create tool_use of this session whose paired tool_result carries the key and is not an error); or named by a receipt of kind `reuse`, `binding` or `import`. An `import` receipt, and a `binding` receipt for an adopted ticket, count only when the transcript also carries — before that receipt's announcement — an ANSWERED consent: an `AskUserQuestion` tool_use naming the key whose paired, non-error tool_result selects the affirmative option label the deciding command printed (`Import <KEY>` or `Adopt <KEY>`), or an operator-authored answers block that `resolveInterviewAnswer` resolves for `tracker_orphan_import` to a value naming the key. A question that was asked and declined, answered with another option or free text, denied, or errored is not consent. A `createIssueLink` needs at least one owned side.

### 5. Container writes are named, not gated, in this milestone

A `container` call in a declared target exits 1 with a stderr `Reminder:` naming its kind (milestone, project, label, status update, document) and saying it is gated from M_685ff6: a named skip, never a silent pass. Exit 1, not 0, because the exit-code contract in `docs/hooks-reference.md` surfaces no stderr on exit 0, so an exit-0 Reminder would be a silent allow; exit 1 shows the operator the text and lets the call run. M_685ff6 must turn every one of these kinds into a decision or a refusal, and its rule (f) does: every Linear label, status-update and document write in a declared target is refused, except a `create_issue_label` whose name equals the target's own `repo_tag`, and a label retire, restore or rename is always refused, since it can strip a sibling's tag from its tickets. An Epic's own label write is a `ticket` call and passes because the session created that Epic. A mint that JOINS an Epic another repository created is refused its label write here — the mint already treats a failed label write as non-fatal — and M_685ff6 decides joins.

### 6. Unreadable inputs

- Unparseable stdin → exit 0, the family's fail-open for calls made outside a session.
- Unreadable transcript → no announced roots and no session-created keys; any resulting refusal names the unreadable transcript.
- A receipt file that fails to parse is ignored and counted in the refusal text.
- The cwd's CLAUDE.md present but unreadable → exit 2 naming the file. Unreadable is not undeclared: the reader refuses the same file, and a permissions glitch must not turn a declared repository's gate off.
- The hook's own `.claude-plugin/plugin.json` absent, unreadable or carrying a non-semver version, while any candidate is declared → exit 2 naming the manifest: the running version is never assumed.

### 7. Surfaces and pins

- The gate is announced where operators look: `docs/hooks-reference.md`, `docs/honored-contracts.md`, `docs/workflow-overview.md`, `README.md` (the hooks tree, line 180) and the repository's `CLAUDE.md` structure line, plus `templates/CLAUDE.md.template`, which announces gates in every bootstrapped project.
- `tests/bundled-hooks-shape.test.ts` pins move — PreToolUse 3 → 4 entries, the matcher no longer uniformly `Bash`, the total 4 → 5 — each move named.
- `tests/_blocking_gates.ts` derives gates from Skill-demand calls; this gate demands receipts. Either the derivation gains a second demand family (`skill: null`) and the STE-577 roll-ups follow it, or the suite records why this gate is a separate kind. The choice is recorded; silence is not an option.

## Technical Design

The hook trusts no receipt the model could have written itself. It reads the declaration and receipts from disk in the target repository, but only receipts a deciding command it can see RAN announced, still carrying the bytes announced. It reads created keys and consent from the session transcript, and ownership from the git index. It classifies the call before reading anything else, and exits silently when no candidate repository declares the call's container, so the undeclared path does no work that could change its output. Milestone writes are classified but only reminded, because the command that decides them lands in the next milestone. The model-supplied tracker JSON the deciding commands classify is a recorded residual trust (Implementation notes).

## Notes

Clients that predate this hook cannot be refused by it; the stop paragraph and the floor are the only levers there. A wrong refusal costs one re-run of a deciding command; a wrong pass costs a write nobody can delete.

**Runtime (AC-STE-607.9).** Measured on 2026-09-18:
- **The five unreadable-input refusals:** 48–58 ms each, the fastest of three spawns.
- **5,000 lines / 200 receipts:** 82 ms.
- **The largest real session transcript on this machine** (108 MB, 2,081 lines): 107–130 ms for a refused create and a refused ticket write, with the transpiler cache on or off.
- **300 sequential spawns:** p50 33 ms, p99 70 ms, max 76 ms.

**Why five tests timed out at 5,000 ms in a full-suite run.** The undeclared matrix (AC-STE-607.1) launched all 78 hook processes at once. Measured during a concurrent full-suite run, they sat in state `U` (uninterruptible wait) for up to 29 s. Any test running beside that window exceeded bun's 5,000 ms per-test default. The five "unreadable inputs" tests are the file's last tests without an explicit timeout, and they build git fixtures in their bodies.

The fix is in the suite:
- `mapBounded` caps the file at `HOOK_SPAWN_LIMIT` = 6 concurrent hook processes, and the pin asserts both a peak of at most 6 and a peak above 1;
- those five tests take the 30 s timeout their siblings carry, because their wall time is fixture setup;
- the new runtime clause grades the hook's own time.

This also accounts for the auditor's 1-in-296 flake, which ran in the same window.

**Budget.** Claude Code's hook `timeout` is in seconds: the documentation says `timeout` is "Seconds before canceling" and that "a timed-out `command` … hook doesn't block the tool call". So `5000` gives 5,000 s, and a timeout would fail open. Any exit other than 2 also fails open, so an exception inside the gate now refuses (`exitCodeFor`).

**Not done, on purpose.** A per-run nonce written into both the receipt and its announcement adds nothing here: the model writes both sides of a forgery, so it can write a matching nonce as easily as a matching digest. The protection is structural — which program printed the line — and that is what this round enforces.

- **The AUDIT's HIGH, fixed before commit: a live-harness bug the fixtures could not see.** Claude Code writes a `tool_use` to the transcript BEFORE its PreToolUse hook runs; this was measured on this session's own transcript, where the Bash `tool_use` at one line precedes its hook attachment several lines later. The first implementation counted every create `tool_use` after an announcement as spending the receipt, so the gated create spent its OWN receipt, and every legitimate create in a shared repository would have been refused as "spent".
  - The test transcripts never contained the pending `tool_use`, so all of AC-STE-607.3 passed.

- **Residual: the Bun environment, recorded (round-3 pre-PR /spec-review).** The accepted-command grammar reads the Bash command's text. What `bun` then runs depends on the environment: a `bunfig.toml` `preload` in the working directory or the user's global Bun config, or a `bun` shim on a writable `PATH` directory ahead of the real one, can run model-written code before the deciding module and print a forged `dpt-receipt:` line into an accepted result. Closing this needs the hook to pin Bun's config (for example `--config` pointing at the plugin's own, and an absolute `bun`), which is a named follow-up: pin Bun's config and binary for the deciding commands. Like the trust residual below, it requires the model to tamper with its environment, not merely to skip a step.
- **Residual trust, recorded (pre-PR /spec-review).** The first Technical Design text said "the hook trusts nothing the model says", which overstated it. The deciding commands classify JSON the model saved from a tracker read: the search page `decide` grades, and the ticket or page `confirm` / `consent` classify. The hook does not check that those bytes came from a real tracker read. A model that fabricates a ticket file carrying this repository's tag gets an `owned` binding receipt, and one that feeds `decide` an empty page gets a `create` receipt. *(Round 2: a `create` receipt minted by `--attempt fast` after a timed-out create of the same ticket no longer authorises the create — honest index lag reached that double create too — unless the timed-out call is absent from the transcript the hook reads.)* The same holds for a shell in which `CLAUDE_PLUGIN_ROOT` was re-exported to another tree. These require the model to lie about tracker data, not merely to skip a step. Closing them needs the hook to cross-check the saved bytes against a tracker-read tool_result, which is recorded as a follow-up rather than claimed here.
