# The branch token is the whole milestone token

## Summary

The branch substitution takes one value and the prose describing it says another. Three surfaces define it as the milestone digits. The function performing it wants bare digits for a numeric milestone and the whole token for an Epic-keyed one, and passes anything else through untouched.

For a numeric milestone the two readings agree, which is why this has gone unnoticed. For an Epic-keyed one they diverge silently: handing over the digits yields a branch named after a milestone number that has nothing to do with this milestone, and the acceptance check then rejects that branch for the very scope that produced it. The operator is refused a branch the instructions told them to make.

The number it lands on is not harmless either. It is a real milestone number in this scheme, so the branch collides with whatever milestone eventually takes it.

Nothing in the code needs changing — the render and the acceptance check already handle the whole token correctly and symmetrically. What is wrong is only what a reader is told, and the reader here is a language model following prose. So the prose is corrected, and the behaviour is pinned on both sides at the same time, because a prose fix with no executable witness is indistinguishable from no fix at all.

## Requirement

The prose defining the branch substitution states what the code requires — bare digits for a numeric milestone, the full Epic-keyed token for an Epic-keyed one — and the behaviour is pinned on both sides.

## Acceptance Criteria

- AC-STE-526.1: Every prose surface defining the `{N}` substitution states both cases: bare digits for a numeric milestone, and the FULL `M_<epic-key>` token for an Epic-keyed one. A surface saying only "digits" is a violation.
- AC-STE-526.2: The surfaces are updated together and parity is asserted — `docs/patterns.md`, `docs/implement-reference.md` (both statements), `skills/implement/SKILL.md` (both statements), and `docs/setup-tracker-mode.md`. Deleting the change from any ONE turns the assertion red. **The last of those was missed by this FR's own measurement and added during implementation.** It defines the substitution as a milestone "number" with a numeric-only example rather than saying "digits", so it fell outside both the enumeration written here and the detector built from it — a surface can be wrong in this exact way while using none of the words the scan looks for. Finding it is AC.3 earning its place: the moment it is fixed, a hand-carried list that had not been extended goes red.
- AC-STE-526.3: The enumeration in AC.2 is not trusted as a fixed list: the same test scans the docs and skills trees for surfaces that define the substitution and asserts the found set equals the enumerated one. A hand-carried list drifts the moment a surface is added, and this repository has shipped exactly that drift before.
- AC-STE-526.4: The correct rendering is pinned: `buildBranchProposal` with milestone `M_GF_78` renders a branch carrying `m_gf_78`, and `isCurrentBranchAcceptable` accepts that branch for a scope whose milestone is `M_GF_78`.
- AC-STE-526.5: The incorrect rendering is pinned as REJECTED: the digits-derived branch `feat/m78-waiting-states` is asserted NOT acceptable for a scope whose milestone is `M_GF_78`. Both sides are asserted, because a one-sided pin proves the correct form works without proving the form the prose currently produces fails.
- AC-STE-526.6: The numeric case is asserted unchanged in the same test: milestone `19` renders `m19` and is accepted for a numeric scope. The two readings agree here, and this pin is what keeps a fix for the Epic case from disturbing the case that was always right.
- AC-STE-526.7: The acceptance check's handling of the full token is pinned as a REGRESSION guard, and the criterion records that it already passes today. The correction is entirely in prose; a criterion that implied otherwise would misrepresent the change and mask which half is actually at risk.
- AC-STE-526.8: The word-boundary discipline holds for Epic-keyed branches: a scope of `M_GF_78` does not accept a branch carrying `m_gf_781`. Asserted alongside AC.4, since a matcher relaxed to make the full token work is the obvious wrong fix.
- AC-STE-526.9: The corrected prose must not introduce a SECOND wrong reading, and this one did before its audit caught it. Every fixed statement first led with "the whole `milestone:` frontmatter token" — false for the numeric half, and measured: `canonicalBranchTemplate({ milestone: "M135" })` selects the TICKET template, the milestone form renders `fix/mM135-...`, and `M135` is rejected as a scope. Only a trailing parenthetical rescued each sentence, and the reader this FR exists for is a language model keying on the leading noun phrase. The value is the milestone's BRANCH token — its digits when numeric, its full `M_<epic-key>` token when Epic-keyed — and it is never the frontmatter token for a numeric milestone. Stated that way on every surface.
- AC-STE-526.10: The substitution's OTHER half is defined too. `docs/implement-reference.md`'s milestone-run RunScope line defined `number` from an `M<N>` argument as `"<N>"` — numeric-only, contradicting AC.4's own pin, one line above an enumerated surface, and invisible to AC.3's detector because it writes `<N>` rather than `{N}` and says neither "digits" nor `M_<epic-key>`. Corrected, and its numeric trap named: passing `M19` where `19` is wanted selects the ticket-keyed template. AC.3's detector is DELIBERATELY not widened to catch it — that was tried and measured, and admitting `<N>` pulls in ten unrelated surfaces, so the scan's limits are recorded in the test instead of papered over with carve-outs. The scan is a floor, not a proof, and says so.

## Technical Design

There is no production code change in this FR, and saying so plainly is part of its content. The render function already maps an epic token to its sanitizer form, and the acceptance matcher already builds the same needle from the same parse, so the two agree with each other and with the branch naming convention. What diverges is the instructions given to whoever supplies the value.

That makes the pins the deliverable. A prose-only FR whose tests only read prose can be satisfied by an edit that says the right words while the reader keeps doing the wrong thing, so the criteria assert the rendered branch and the acceptance verdict on both the correct and the incorrect input. The rejected case is the one that carries the information: it is what the current prose actually produces.

AC.3 exists because the enumeration is the fragile part. This FR names five statements across three files, measured; a sixth surface added later would silently fall outside a hand-written list while every existing assertion stayed green. Deriving the set and comparing it to the enumeration converts a maintenance hazard into a test failure.

AC.7's honesty clause follows from the same measurement. The acceptance matcher was extended for epic tokens when the union grammar landed, so the behavioural half is already correct; framing this FR as fixing it would claim credit for work already done and, worse, would hide that the only thing standing between the prose and a broken branch is a reader noticing the contradiction.

## Testing

The behavioural assertions run against the shipped render and acceptance functions with no wrapper, since the whole question is what those functions do with a value the prose tells someone to supply.

The rejected case in AC.5 is written with the branch name spelled out literally rather than computed from the digits, so the test states the exact string the current instructions produce. Computing it would let a change in the derivation quietly change what is being rejected.

The surface scan in AC.3 names its roots in the assertion message and carries a positive control, per this repository's rule that a zero-hit or empty-set search is a claim about the search before it is a claim about the tree.
