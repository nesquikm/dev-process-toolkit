# A headless implement run keeps going after its gate

## Summary

The implement skill runs the gate check in the middle of its own work.
The gate check ends with its own closing report.
In headless runs, that report sometimes became the end of the whole run.
The work stayed staged, the lock stayed claimed, and nothing was committed.
The fix tells the gate check it is driven, so it skips its closing block.
The implement skill also states that the gate report never ends its turn.

## Requirement

`/implement` invokes `/gate-check` with the driven-run marker, and its skill text says a gate report never ends the `/implement` turn.

## Acceptance Criteria

- AC-STE-788.1: `skills/implement/SKILL.md` step 11 tells the run to invoke `/dev-process-toolkit:gate-check` with the driven-run marker `<dpt:driven>v1</dpt:driven>` in its arguments.
- AC-STE-788.2: The same step states that the gate-check report never ends this skill's turn: on a pass, the run continues to Phase 3, then Phase 4, in the same turn.
- AC-STE-788.3: A test reads the shipped skill text and fails if either sentence is dropped, and the skill stays within its line cap.
- AC-STE-788.4: `bun test` from `plugins/dev-process-toolkit` reports 0 failures, and its skip identities equal the trunk baseline by name.

## Technical Design

Prose only, appended to the existing step 11 line so the line count stays under the cap. The marker constant is the one `driven_run_signal.ts` exports, and the test reads it from there instead of restating it.

## Testing

A doc-conformance test over the skill text that imports the marker constant.

## Notes

Conformance run 2026-11-14, linear and none legs, fixture 3a. The fault was not deterministic, so the test pins the instruction, not the model.
