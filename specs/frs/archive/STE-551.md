# A continuation offer is not made when the answer was already given

## Summary

Four skills end by offering to run the step that comes next, or printing it as a recommendation to a human.

Under an orchestrator that step was named in the kickoff before the skill started, so the offer asks a question already answered.

One is worse than a repeat: where the chain already includes the close ceremony, offering to run it makes it run twice.

The offers are right when a person is choosing. Deleting them would remove real gates.

## Requirement

A skill that ends by offering or recommending the next step omits that offer when an orchestrator has already fixed the step, and makes it exactly as today otherwise. No step is ever performed twice because an offer and a chain both claimed it.

## Acceptance Criteria

- AC-STE-551.1: Under the driven signal, `/brainstorm`'s hand-off ends without emitting its "or I can start now" offer AND without starting the next phase itself. The RUN proceeds to that phase, because the orchestrator already names `/spec-write` as its own Phase 2 and runs it exactly once; a hand-off that started it here would run it twice, which is the defect AC.4 forbids. Standalone, the offer is emitted verbatim as today. (Corrected 2026-09-05: the original wording said the hand-off "proceeds to the next phase", which reads as an order to perform the very step the chain owns.)
- AC-STE-551.2: Under the driven signal, `/spec-write`'s closing `Next:` recommendation is omitted, because the next actor is a spawned worker rather than a human who could act on it. Standalone it is emitted, and its existing variant rule is unchanged.
- AC-STE-551.3: Under the driven signal, `/implement`'s Phase 5 chain prompt and `/ship-milestone`'s ceremony-PR prompt are not asked, because the worker's kickoff already names the chain that contains them.
- AC-STE-551.4: The close ceremony executes exactly once across a run where both the ship-ready offer and the orchestrator's own chain name it. Asserted by counting executions across the whole run, not by reading either surface.
- AC-STE-551.5: `/spec-archive`'s trailing `Next:` line is omitted when the same session already holds the step it names.
- AC-STE-551.6: `/ship-milestone`'s "not automated" notice is not printed in a run that automated it, since a false statement about the run is worse than a redundant one.
- AC-STE-551.7: Every standalone path is byte-identical. The existing expectations for all five skills run unmodified, asserted as an unchanged count.
- AC-STE-551.8: Falsifiability — restoring any one offer on the driven path reintroduces exactly one operator turn, asserted per offer rather than in aggregate, so a single surviving offer cannot hide behind the others.

## Technical Design

Each offer gains a driven branch keyed on STE-549's signal; the standalone branch is untouched. The sites are `skills/brainstorm/SKILL.md:102`, `skills/spec-write/SKILL.md:290`, `skills/implement/SKILL.md:305` and `:314`, `skills/implement/SKILL.md:301`, `skills/ship-milestone/SKILL.md:251` (the prompt itself; `:246` is its section heading) and `:240`, and `skills/spec-archive/SKILL.md:74`.

`skills/implement/SKILL.md` measures 358 lines against a 358-line cap, so its edits are net-zero or shorter. The existing idiom to copy is `/implement`'s own Phase 5 guard, which already suppresses a double offer against itself — the same shape now applied against the orchestrator's chain rather than against a sibling phase.

The double-run in AC.4 is the one correctness defect here; the rest cost turns. It is guarded at the offer, not at the ceremony, because the ceremony cannot know why it was invoked.

## Testing

New `tests/m143-ste-551-continuation-offers.test.ts`.

- AC.1 / AC.2 / AC.3 / AC.5 / AC.6 — one paired leg per surface: driven omits, standalone emits, same fixture. Asserted per surface and never as a group, so a surface that regresses names itself.
- AC.4 — the load-bearing leg. Run the FR-scoped last-active chain and count invocations of the close ceremony across the whole run, asserting exactly one. Include a pre-fix control asserting the unguarded arrangement yields two, or the leg cannot show it fixed anything.
- AC.7 — assert the pre-existing expectation count in all five suites is unchanged.
- AC.8 — mutation per offer: restore that one offer on the driven path and assert the run gains exactly one operator turn, with the other offers still suppressed.

## Notes

The offers were never wrong; they were unconditional. That is why deletion is the wrong fix and a branch is the right one — a standalone `/brainstorm` genuinely should ask before writing specs, and an operator who ran it alone would rightly object to it proceeding on its own.
