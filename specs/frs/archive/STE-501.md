# The FR chain auto-extends to the ship ceremony only when the FR closes its milestone

## Summary

Delivering the last open task of a milestone and then stopping at the pull request leaves the milestone ship-ready but unshipped, which the operator must notice and act on themselves. Delivering any other task and continuing into the ship ceremony would release a milestone that is not finished. The chain therefore has to be chosen, and the operator has to see which one was chosen and why before anything runs.

## Requirement

An FR-scoped chain stops at the pull request, except when building that FR closes its milestone, in which case it extends through archival and the ship ceremony.

## Acceptance Criteria

- AC-STE-501.1: The FR-scoped chain is `/implement <FR-id>` then `/pr` when other active FRs remain bound to the milestone.
- AC-STE-501.2: When the FR is the last active one, the chain extends to `/implement <FR-id>`, `/spec-archive M<N>`, `/ship-milestone M<N>`, `/pr`.
- AC-STE-501.3: `/spec-archive` is an explicit chain step, because a single-FR `/implement` run leaves `status: active` and archives nothing.
- AC-STE-501.4: The confirm gate renders the chosen chain, the count of active FRs that would remain, and which of the two chains was selected and why.
- AC-STE-501.5: On `edit`, the operator's chain is what runs.
- AC-STE-501.6: Aborting at the gate leaves no side effects — nothing spawned, nothing claimed, not one byte changed.
- AC-STE-501.7: An FR flagged `needs_technical_review` gets one `/spec-write <FR-id>` pass at the head of its chain, scoped to that FR.

## Technical Design

`resumeChain` in `adapters/_shared/src/resume_classifier.ts` builds the step list from the classified state and the resolved route. The FR-scoped branch reads STE-500's last-active-FR flag and emits one of two step lists. Both are ordinary `ResumeChainStep` sequences, so the shipped placement rules (inline versus worker) and the reduced-chain route for a toolkit-less target apply unchanged.

AC.3 is the non-obvious step and it is written into the AC rather than left to the implementer, because the shipped `/implement` contract states it plainly: *"Single-FR runs (`/implement <FR-id>`) intentionally leave `status: active`; bulk archive a completed milestone via `/spec-archive M<N>` before running `/ship-milestone`."* A chain that goes straight from a single-FR implement to the ship ceremony would try to ship a milestone whose FRs are all still active, and `active_plan_ship_ready` would correctly refuse it. The archive step is what makes the extended chain coherent.

AC.4 is the operator-facing half and it is why this milestone is worth shipping at all. The shipped confirm gate already renders the classified state and the intended chain before any worker is spawned; the addition is the remaining-FR count and the reason for the branch, so the operator is deciding rather than ratifying. A gate that renders the extended chain without saying "this is the last active FR" gives the operator no way to catch a miscount.

AC.7 places the spec-write pass at the head of the chain rather than treating it as a separate state, mirroring the shipped `needs_technical_review` milestone route. Scope is the single FR, so the pass is one invocation, not a sweep.

## Testing

Chain coverage for both branches from on-disk fixtures: siblings-remaining emits the two-step chain, last-active emits the four-step chain with the archive step present and ordered before the ship step. Boundary asserted in both directions. Confirm-gate rendering asserted to carry the remaining count and the branch reason — a render that shows only the step list passes a naive assertion and is the vacuity to avoid. AC.6 asserted by mutation: nothing spawned, no tracker claim, no tree change on the abort path. AC.7 asserted for a flagged FR on both chain branches. `bun test` full root.

## Notes

The chain is chosen by code and confirmed by the operator. Neither half alone is sufficient — the code cannot ask, and the operator cannot be expected to recount active FRs by hand.

**Backfilled during implementation:** `ResumeTrackerSink` gains an optional `claimFr(fr)`. An FR-scoped run claims at FR granularity when the sink offers that channel and falls back to the shipped `claimMilestone` when it does not, so a tracker that can only claim milestones keeps working while one that can claim an FR no longer has to claim the whole milestone for one task. Optional rather than required, because making it required would break every shipped sink for a field only the FR path reads.

Deliberately not in scope: merging. Post-PR routing stays on the shipped merge policy, and an FR-scoped run reaches it on exactly the same terms as a milestone-scoped one.

## Implementation notes

- `runResume` dispatches to the FR branch BEFORE the shipped/parked refusals, so an active FR bound to a shipped or parked milestone classifies and spawns instead of refusing. No AC covers it and gate probe #27 already reddens that tree state, so it is recorded rather than fixed here.
- On the siblings-remaining chain `/pr` targets the MILESTONE, not the FR — consistent with the shipped milestone chain, and the FR text specifies no target, but `/pr M<N>` after building one of four FRs reads as a milestone PR.
- The auto-extend branch may be unreachable in a purely FR-by-FR flow: `/implement <FR-id>` deliberately leaves `status: active` and the siblings-remaining chain adds no `/spec-archive`, so previously delivered siblings stay in `activeFrIds` and `lastActiveFr` never flips unless the operator archives by hand. Implemented exactly as specified; the gap is in the design, and it is the milestone's most load-bearing follow-up.
