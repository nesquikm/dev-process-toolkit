# STE-425: Make smoke fixtures falsifiable and account for unreached coverage {#STE-425}

## Summary

Three coverage-integrity gaps travel together because each one lets a run look better covered than it actually is.

One regression fixture stages a historical failure by removing a permission entry and expects the resulting denial to be caught. On both legs nothing was denied, because the operator's user-level settings put children under a classifier rather than under the tracked allow-list. The fixture therefore passes identically whether its detector works or not, which is worse than having no fixture at all.

A whole fixture group was never reached on one leg. It was independently runnable and not blocked by anything — it simply ran out of wall-clock. That has to be reported as a gap rather than quietly absorbed.

And the run leaves seven untracked transcript files in the toolkit repository. They are deliberate replay evidence, but the pre-flight refuses on a dirty tree, so the next run refuses until somebody deals with them by hand.

## Requirement

A regression fixture MUST be able to fail. An unreached fixture group MUST be reported as unreached rather than counted as a pass. A completed run MUST leave the toolkit tree in a state where the next run's pre-flight passes.

Observed 2026-07-27:

- **Fixture 8b is vacuous.** With `Bash(claude:*)` removed from the test project's allow-list (verified absent), the nested spawn still returned its expected token with `permission_denials: []` on both legs. Root cause confirmed independently: `~/.claude-st/settings.json` carries `permissions.defaultMode: auto`, so the classifier governs, not the tracked allow-list. Pre-flight #10 consequently refuses whole runs over a pattern that is not the operative gate in this environment.
- **Fixture group 2 not reached** on the Linear leg (STE-214 probe scanner, 3 sub-fixtures). Not blocked by the keystone finding — the leg recorded it explicitly as a gap.
- **Seven untracked fixtures** remain under `plugins/dev-process-toolkit/tests/fixtures/socratic-first-turn/`, and `/smoke-test` pre-flight #4 refuses on a dirty toolkit tree.

## Acceptance Criteria

- AC-STE-425.1: Fixture 8b either asserts against the mechanism that actually gates child spawns in the presence of an auto default permission mode, or is retired — and if retained, a mutation check proves it fails when its detector is disabled.
- AC-STE-425.2: The run summary distinguishes three fixture-group outcomes — passed, failed, and not-reached — and a group that did not execute is never rendered as a pass.
- AC-STE-425.3: The smoke SKILL states the disposal rule for Phase 8 transcript fixtures, and following it leaves the toolkit tree clean enough for the next run's pre-flight #4.
- AC-STE-425.4: A pre-flight or closing check surfaces any untracked artifact the run itself created, so the operator learns about it at the end of the run rather than at the start of the next one.

## Technical Design

The 8b question is the substantive one. Under an auto default permission mode the tracked allow-list is not the enforcement point, so the fixture as designed cannot distinguish a working detector from an absent denial. Two honest options: re-found the negative case on whatever does gate the spawn in that configuration, or retire the fixture and document that the allow-list is not the operative gate here. Either is acceptable; silently keeping a can't-fail fixture is not.

The not-reached accounting is a reporting change in the phase summary plus a per-group execution record, so the aggregate cannot infer a pass from silence.

Fixture disposal is a one-line policy decision — commit them, git-ignore them, or write them outside the repo — that the skill currently does not make.

## Testing

- A mutation check per AC-STE-425.1: disable the detector and assert the fixture fails.
- Summary-rendering unit cases covering all three outcomes per AC-STE-425.2.
- A dirty-tree simulation asserting pre-flight #4 passes after the documented disposal step.

## Notes

The 8b vacuity reproduces findings already recorded on 2026-07-19 and 2026-07-20; this is its third appearance, which is itself an argument for retiring rather than patching it.
