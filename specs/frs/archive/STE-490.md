# RC collection must read the verdict artifact, not the raw exit code

## Summary

A capture-only run that finds anything reconciles to a non-zero exit code, because the code was deliberately made to carry the verdict. The collection gate then reads any non-zero code as a crashed subprocess and stops the whole iteration before it can aggregate — so in capture-only mode the loop cannot produce its own report whenever the runs find something, which is essentially always. Two correct decisions, made at different times, collide. This run had to be graded by hand around the gate, and the same lesson was already recorded once before without being fixed.

## Requirement

The RC-collection gate distinguishes a declared-findings verdict from a genuine subprocess failure by reading the verdict artifact independently of the exit code — the rule STE-420 already established when the exit code was made to carry a verdict at all. A missing or unreadable artifact remains a failure; no findings and no evidence must never reconcile to the same answer.

## Acceptance Criteria

- AC-STE-490.1: A leg whose verdict artifact declares findings (`{"outcome":"fail","trigger":"declared"}`) does not abort the iteration; aggregation proceeds and the loop emits its own deliverable.
- AC-STE-490.2: A leg that genuinely crashed still aborts the iteration with a diagnostic naming the failure — the gate is narrowed, not removed.
- AC-STE-490.3: A missing, empty, or non-integer rc-file remains a failure; the existing fail-closed hardening for those three shapes is preserved byte-for-byte.
- AC-STE-490.4: § RC collection's prose no longer states "abort on any non-zero keeps its exact shape" as the design intent, and records the collision it resolves.
- AC-STE-490.5: The gate's bash fences are extracted and executed against both a declared-findings artifact and a crash artifact, producing opposite outcomes (STE-452 harness method).
- AC-STE-490.6: Notes record that this lesson was logged on 2026-08-01 and recurred unfixed — the recurrence is part of the record, not smoothed over.

## Technical Design

`adapters/_shared/src/smoke_verdict.ts:259` defines `RC_VERDICT_NON_PASS = 64`, and the reconciler returns it for any non-pass verdict. A capture-only run that declares findings — the normal, expected outcome — therefore exits 64. § RC collection then applies "abort on any non-zero" and would emit a diagnostic naming a subprocess failure for three legs that all ran to completion, aborting before aggregation.

Grepping for `64`, `RC_VERDICT`, and `declared` across both driver SKILLs returns only prose: there is no carve-out anywhere, and the section states the abort-on-any-non-zero shape as deliberate. So this is a design collision between STE-420's truthful-rc and the pre-existing gate, not a typo — which is why the fix belongs at the gate's decision rule rather than at the reconciler.

STE-420's own precedent supplies the shape: gate on the artifact independently of rc, treat a missing artifact as a failure, and make every "MUST exit non-zero" clause either true by the wrapper or restated to name the artifact. AC-STE-490.3 explicitly preserves the existing hardening, because that hardening exists to catch the empty-file and diagnostic-write shapes the rc-file redirect can produce.

## Testing

Fences extracted from § RC collection and executed against a declared-findings artifact (expect proceed), a crash artifact (expect abort), and the three malformed shapes (expect abort). A one-byte rewording of the gate must return nothing, per the STE-456 AC.7 method. `bun test` full root.

## Implementation notes

- The RC fence's outer three-way guard (`[ "${RC_LINEAR}" -ne 0 ] || …`) is semantically dead — every `RC_*` is pre-defaulted to 0 and normalized before it, and the per-leg loop's own `[ "${LEG_RC}" -ne 0 ] || continue` already skips clean legs; replacing the guard with `if true` changed zero of four fence outcomes. It survives as a short-circuit and as the only line satisfying `tests/conformance-loop-aggregator.test.ts:71`'s 80-character proximity pin. It does not weaken any AC here — the real decision path is independently killed by two other mutations — but that pin would now stay green with the whole classification loop deleted, which is a perfect pin on a subject that has moved. Recorded in `specs/notes/follow-ups.md`; re-pointing it is a shipped-test change and wants its own FR.
- The fence hardcodes the literal `64` and the leg list `linear jira none`, both second copies of values the modules own (`RC_VERDICT_NON_PASS`, `SMOKE_LEGS`). Both are defence-in-depth rather than the decision: `classifyLegRc` independently rejects every non-64 code (removing the shell guard still aborts at 65 and 137), and the `EXAMINED_LEGS`/`SELECTED_COUNT` accounting guard above aborts on any selected token outside the three, so a fourth registered leg can never reach the loop silently.
- AC.4's offender filter is word-level, not clause-level: it exempts any line matching `/64|declared|classif/i`, and on the pre-change tree the second flat statement already escaped it on the unrelated phrase "both legs declared failure in prose" — so one candidate survived the filter, not two. The test is still genuinely RED before the fix (the § opener survives), so the AC is closed; the test comment that overstated this was corrected in place.
- `tests/m116-ste-420-verdict-artifact.test.ts`'s `phaseAIterationAborts` helper was documented as "the Phase A gate exactly as the SKILL documents it … abort the iteration on any non-zero". That became false the moment this FR landed. Its docblock was corrected so the file no longer ships a model of a gate the gate has diverged from; the helper itself still describes `reconcileLegRc` truthfully and all six call sites reconcile through an armed trigger or a bad artifact, never through `declared`, so each still aborts under both rules.
