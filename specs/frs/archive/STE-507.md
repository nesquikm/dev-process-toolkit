# /setup and /upgrade seed the runnability contract

## Summary

A gate that fails a repo until someone hand-edits a config block is a gate people route around. The two surfaces that already write this block at bootstrap and at upgrade time should write the new keys too, so an existing project meets the contract by running a migration rather than by reading a probe message and guessing what it wants.

## Requirement

Bootstrap and upgrade both populate the new keys.

## Acceptance Criteria

- AC-STE-507.1: `/setup` offers `run_cmd` when it scaffolds or adopts a check skill, seeded from the detected stack.
- AC-STE-507.2: `/setup` writes `run_cmd: none` when detection reports the project is not runnable, so the probe is satisfied at bootstrap without a follow-up edit.
- AC-STE-507.3: `/upgrade` carries a migration-registry entry that adds the keys to an existing block.
- AC-STE-507.4: The migration previews every change and applies nothing without approval.
- AC-STE-507.5: A project already carrying the keys is a no-op.

## Technical Design

`/setup` already offers a stack-aware check-skill scaffold and writes `verify_skill` into the `## Verification` block on accept. The `run_cmd` offer rides that existing step rather than adding a new one, and it is seeded from the same stack detection the scaffold already performs — a web project's dev server, a Flutter project's run command, a Python service's entry point.

AC.2 is the quiet half and it is the one most likely to be dropped. A project where detection does not fire still needs `run_cmd: none` written, because a bootstrap that leaves the key absent hands the author a probe failure on their first gate run for a question `/setup` could have answered. Writing `none` at bootstrap is what makes the contract cost nothing for projects that cannot be run.

AC.3 uses the shipped `/upgrade` migration registry, which walks version-ordered entries, previews every change, and applies them in one approved commit. AC.4 restates the preview-and-approve contract rather than assuming it, since a migration that edits a config block without showing the diff would be a new behaviour for that surface.

AC.5 keeps re-entry idempotent, matching `/setup`'s existing re-entry discipline.

The migration is deliberately narrower than "adds the keys", in two ways worth recording here rather than only in the entry's own source. The entry writes `run_cmd` only and never `e2e_cmd`, because nothing in the closed source set the detector consults inspects an end-to-end suite, so `e2e_cmd: none` would be a guess about a question the detector never asked. The entry also declines the runnable half of the population — a project whose run instructions the detector actually found is left alone — because a migration must not invent a run command it cannot verify. The second reason is sharper: a wrong `run_cmd` under the sibling FR's `blocking` default would gate every commit on a command that does not work, so the safe move is to write nothing and leave that tree to probe #80 (`runnability_declared`), which fails it, names the source that fired, and offers `none` in its remedy.

## Testing

`/setup` coverage for the scaffold-accept path writing `run_cmd`, and for the not-runnable path writing `none`. Assertion that neither path leaves the key absent. `/upgrade` migration coverage: an existing two-key block gains the new keys, the preview lists every change, nothing applies without approval, and a block already carrying the keys is a no-op. `bun test` full root.

## Notes

AC.2 is the clause to defend in review. A silent skip here reads identically to a correct run and leaves every non-runnable project failing a probe it should never have seen.

## Implementation notes

- The entry writes `run_cmd` ONLY and never `e2e_cmd`, and it declines the RUNNABLE half of the population entirely. Both narrowings are recorded in the Technical Design with their reasons. AC.3's wording ("adds the keys", plural) is therefore delivered in part: nothing in the closed source set inspects an end-to-end suite, so `e2e_cmd: none` would be a guess.
- A pre-M131 project where detection FIRES and `run_cmd` is absent gets nothing from this entry. `/upgrade` now points that operator at gate probe #80 rather than leaving `Nothing to do.` as the last word while their gate is about to red.
- `introduced_in: "2.70.0"` couples to the plan's release target. If the ship lands at a different version, `/ship-milestone`'s `assertMigrationDeclared` pre-flight refuses LOUDLY — a known, non-silent failure.
- FOLLOW-UP, out of this FR's scope: `/implement` Phase 4b″'s adopt path writes `verify_skill` into the same block and seeds no `run_cmd`, so a project acquiring its block through adoption still lands with the key absent — the state this FR exists to prevent.
- AC.2 is delivered on the § 8c ACCEPT path only. That step is opt-in and a no-op on decline, so a bootstrap that declines the check-skill scaffold still lands with `run_cmd` absent — the exact state this AC exists to prevent. The migration entry's own header already names § 8c decliners as part of its target population, so the gap is known to the code; it is recorded here because the FR, not a module comment, is the durable record. Closing it means either seeding `run_cmd` outside § 8c or making the seed survive a declined scaffold.
- The `/setup` surfaces originally keyed the `none` write on the detected STACK rather than on `detectRunnability`. A repo whose stack matched nothing recognisable could carry a `## Running` heading and still be handed `run_cmd: none` — a false declaration that permanently silences probe #80, which is the reflex-silence this milestone's detector FR is written against. Caught by the pre-PR spec review and re-keyed on the detector by name, on both the skill and the reference.
