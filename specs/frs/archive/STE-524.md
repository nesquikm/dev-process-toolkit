# The archival gate re-checks the predicate it opened with

## Summary

The archival gate opens by asking a predicate whether the binding is present. If the answer is no it attaches once and then returns success — not because it asked again, but because the attach did not throw. The predicate that decided the binding was missing is never consulted a second time, so the gate can and does stamp an affirmative verdict on the exact state its own opening question calls false.

An attach that does not throw is a weaker claim than it looks. The attach verifies its own write by reading back the field it just wrote, which is self-consistent and tells you nothing about whether that field is the one the predicate reads. Two shipped paths make the gap concrete: a binding that lands on the wrong Epic, and a degrade that writes a label while the predicate is watching the parent. In both the attach is honest and the gate is wrong.

This is the last moment anyone looks. The gate probe that would otherwise catch a bad binding skips archived work by design, and archiving is the transition that makes the work archived, so nothing revisits it afterwards. A gate positioned at a boundary with no downstream reader has to fail closed, because a false pass there is permanent.

The fix is small and its size is the point: re-read the ticket after the attach and return the affirmative verdict only when the same predicate, with the same arguments, now says yes.

## Requirement

`assertMilestoneBindingAtArchive` returns `asserted` only when its own present/missing predicate is true on a fresh read after the attach — never on the mere fact that the attach did not throw.

## Acceptance Criteria

- AC-STE-524.1: After a non-throwing attach, the gate re-fetches the ticket and evaluates `milestoneBindingPresent` with the same canonical name and binding it used for the pre-check. `asserted` is returned only when that call is true; otherwise the gate returns `refused` carrying the refusal token.
- AC-STE-524.2: The duplicate-Epic state is reproduced and asserted REFUSED: the ticket's parent is a foreign Epic key whose sanitized token differs from the milestone token, and no Epic in the project sanitizes to the milestone token. The gate returns `outcome: "refused"`, and the foreign parent is never rewritten. **This is a state-based REGRESSION pin, not a live reproduction, and the difference is recorded rather than glossed.** As first written this criterion said it fails on the current implementation — true when the FR was authored, false by the time it was built: STE-521 and STE-522, earlier in this same milestone, removed mint-on-miss, so the attach now throws and the gate's pre-existing generic catch already converts that to a refusal. This FR's own Technical Design anticipated exactly that, so the original AC text contradicted the design paragraph beside it. The pin stays because the STATE must keep refusing however the mechanism that produced it changes; the live reproduction of the fail-open is AC.3's, which is why AC.3 is the one that must be red.
- AC-STE-524.3: The degrade path is reproduced and asserted REFUSED as a SECOND, independent route to the same fail-open: with the Epic-availability probe returning false, the attach writes the milestone label and returns cleanly while the epic-kind predicate reads the parent. The gate returns `refused`. This route survives STE-521 and STE-523, so a fix that only closes one of the two cannot pass both criteria.
- AC-STE-524.4: The happy paths are asserted in the same test file and must stay green: a binding already present returns `asserted`, and a binding missing then successfully attached returns `asserted`. A gate that refused everything would satisfy AC.2 and AC.3 on its own.
- AC-STE-524.5: The refusal detail distinguishes "the attach landed and the binding is still absent" from "the attach threw", in different wording per case. The current single message tells an operator that one attach attempt did not land, which is a false statement in the case this FR adds and sends them to the wrong diagnosis.
- AC-STE-524.6: The extra read costs exactly one additional `getIssue` and only on the miss-then-attach leg. The already-present path's `getIssue` count is asserted UNCHANGED from today's. Pinned as a call count, because a re-check bolted on unconditionally would double every archival batch's tracker traffic.
- AC-STE-524.7: The vacuous paths are unchanged and asserted: tracker-less mode, an adapter without the capability, an FR with no tracker binding or no milestone, and a missing or heading-less plan file each still return `vacuous` with zero tracker calls.
- AC-STE-524.8: The gate's own surface records WHY it must fail closed: the gate probe that verifies this binding skips non-active FRs, archiving is what makes an FR non-active, and the archival boundary is therefore the last read of that binding. Stated on the module so the next reader cannot restore the fail-open as a simplification.
- AC-STE-524.9: The gate still never throws. Every added path converts to a refusal, so one FR's failure never aborts a milestone-group archival batch. Asserted with a re-read that throws, on both the object route and the degraded-epic route. The original wording also named "the predicate throwing" as a path to cover; measurement shows that is not constructible — `milestoneBindingPresent` catches internally on every branch, and STE-523's read-side guard closed the last way it could raise. Naming an uncoverable path in an AC invites a test that fakes it, so the claim is narrowed to what can actually be exercised.
- AC-STE-524.10: The gate's "never throws" contract holds from its FIRST line, not merely from the fetch onward. It derives the expected label through `milestoneLabel(canonical)` before the predicate is ever reached, and that derivation throws on a name carrying no milestone token — so a token-less name would escape as an exception from a helper whose whole contract is that it returns a verdict, aborting a milestone-group archival batch instead of skipping one FR. That derivation is guarded and converts to a refusal naming the unusable name. **The guard covers every binding that NEEDS the token, not just the one that derives a label.** Scoped to `label` alone it left a live misdirection the FR's own audit found: under `epic`, a token-less name skips this route, the attach matches an Epic by NAME and sets a parent, the re-check still reads false, and the operator is handed the landed-but-absent remedy — told to set a parent that is already correct — while the real fault is the milestone name. `object` is the only binding that genuinely needs no token, and it is the only one exempt. As with the sibling guard in STE-523, the honest strength of this claim is stated: every production caller derives the name from the plan-heading parser, whose grammar cannot emit a token-less name, so this is hardening at the contract boundary rather than the repair of a live crash — and it is worth doing precisely because the surrounding comment already promises the helper NEVER throws, a promise the first line did not keep.
- AC-STE-524.11: Each refusal route carries a remedy that fits ITS cause, not one shared line. The gate refuses on six distinct routes and a single remedy misdirects three of them, two dangerously: when the ticket FETCH failed, nothing is known to be missing and the binding may be perfectly fine, so advising a manual attach invites a duplicate write; when the post-attach RE-READ failed, the attach probably landed, and the same risk applies. The third misfit is the sharpest: on the degrade route the attach wrote a milestone LABEL while the epic predicate reads `parent`, and the shared remedy sends the operator to a backfill that rewrites the label already present and never touches the parent — telling them to repeat the thing that did not work. Advising an action that risks a duplicate write is the defect class this milestone exists to close, so a remedy is not decoration here. Every route's remedy is asserted individually, and the set is asserted EXHAUSTIVELY: a route added later without its own remedy fails the pin rather than silently inheriting a wrong one, which is how the shared line came to cover six causes in the first place. **Exhaustiveness is over refusal SITES, not over route ids.** Counting ids is defeatable and was defeated: widening an existing branch's condition, or extracting one refusal into a helper called from two places, adds a new CAUSE with no new id literal, so an id-based pin stays green while the new cause inherits a remedy written for a different fault. The count of refusal sites in the module must equal the registry's size.
- AC-STE-524.12: A PERMANENT attach refusal does not inherit the transient remedy. Three refusal classes introduced by sibling FRs earlier in this milestone — an Epic-keyed token whose Epic is absent, a title-shaped name whose Epic was never minted, and a name whose leading token parses to neither kind — all reach this gate as ordinary throws and fall to the attach-call-failed route, whose remedy tells the operator to clear an outage or expired credentials and retry. Retrying fixes none of them. They are routed to a remedy that says so and defers to the refusal's own instruction, which is already threaded into the headline. This is the defeat AC.11's own rationale predicted, arriving from OUTSIDE the module: a new CAUSE with no new id literal, invisible to a site count that only sees this file. It is also why AC.2's assertion is strengthened here to pin the ROUTE and not merely that the outcome was a refusal — asserting `refused` alone passes over a refusal that says the wrong thing, which is the whole subject of AC.11.

## Technical Design

The change replaces the unconditional `return asserted(...)` after the attach with a fresh `getIssue` and a `milestoneBindingPresent` call, mirroring the pre-check exactly. Reusing the same predicate and the same arguments is what makes the gate's verdict mean the same thing as its question; a bespoke post-attach check would be a second surface that could drift, which is the failure this milestone is about.

The two reproductions in AC.2 and AC.3 are chosen because they fail for different reasons. The first is the duplicate-Epic state, whose mechanism STE-521 removes — after that FR the attach refuses rather than producing it, and the gate's refusal path then fires through the caught `MilestoneAttachmentError`. The second is the degrade path, which STE-521 and STE-523 both leave intact: the availability probe returns false, the label attach succeeds honestly, and the epic-kind reader looks at the parent. It will still be reachable after this milestone ships, which is exactly what makes it the durable pin.

That second route also marks a boundary this FR deliberately does not cross. The degrade writes a label the epic-kind reader will not accept, which is arguably a reader gap rather than a gate gap, and closing it on the reader side would be a third writer/reader convergence change. This FR takes the position that the gate refusing is CORRECT there: the operator asked for Epic binding, got label binding, and should be told at the boundary rather than have the predicate widened to accept a surface the milestone's own design rejected.

The cost pin in AC.6 shapes the implementation. The re-read belongs after the attach only, not as a general post-condition, because the already-present path has already read the ticket and its binding was true on that read.

## Testing

Every fixture is built as a state, not as a stubbed verdict. The gate is driven with a provider double whose ticket view is whatever the attach actually left behind, so the pre-check, the attach, and the re-check all read the same evolving object. A double that returned a canned answer to the second read would pass this FR's criteria while proving nothing about the ordering.

AC.4 is the anti-vacuity pin and is not optional. The whole implementation surface of this FR is one branch that turns an unconditional affirmative into a conditional one; the degenerate implementation returns `refused` always, and only the happy-path assertions distinguish it.

The call-count assertions read the double's recorded op counts rather than inferring from timing or from the returned value.
