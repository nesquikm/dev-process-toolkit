# A ticket or container created in this session is never created again

## Summary

A create that already made its ticket left the door open for a second one: a fresh receipt announced after the success authorised an identical create.
Once a create in this session returns a key, or a success naming none, no receipt authorises another create of that ticket or container.
The refusal names the key and the route that writes to it, the mismatch refusal stops naming spent receipts, and read-only commands stop counting as deciding ones.

## Requirement

Once a create in this session has returned a key, or has returned a success that names no key, no receipt or decision authorises another create of the same ticket or container, however fresh it is. The refusal names the key and the route that writes to it, and never offers a fast re-decide. The mismatch refusal grades only unspent receipts. The "not a plain invocation" diagnostic counts only commands that actually run a deciding module under bun.

Covers A1 (F4-b, including an unkeyed success; medium) and A3 (C-N2; low). Amends the STE-607 §4 create rule. Builds on the previous FR's transcript wait and (line, position) ordinal.

## Technical Design

The lost-create scan generalises into one prior-create scan that gives every earlier create of the session a state: lost, settled (a non-error result naming a key), or unkeyed (a non-error result naming none, treated as lost). Creates that never ran stay excluded. The ticket-create gate and the container-create gate each refuse a settled same-ticket create before any receipt is consulted, naming the returned key. The mismatch branch grades only unspent receipts and otherwise falls through to the no-receipt refusal. The deciding-command recogniser splits a command into segments and counts only a segment that runs bun on the module.

## Notes

## Implementation notes

- the container-side unkeyed state (an Epic or save_milestone success naming no key) has no dedicated leg; AC-STE-642.7 covers ticket creates — the same priorCreates state serves both gates and the ticket leg proves it
- the settled refusal is exercised with Jira keys only; no Linear save_issue settled leg — createdKeyOf is shared across adapters and already tested per adapter
- rejectedDecidingCommand's NAME=<module> pattern misses a module path containing spaces, and counts a quoted 'bun run <module> decide' inside an echo — diagnostic note only; the accepted-invocation set is unchanged and spec-conformant

## Design detail

- **priorCreates.** Generalise lostCreates (~:846-874) into `priorCreates(parsed, adapter, gatedId, kind)`, ordered by the ordinal. States: `lost` as today; `settled` via createdKeyOf (~:1279), or createdMilestoneIdOf (~:1325) for a Linear save_milestone; `unkeyed`, treated as lost with why = "its result names no created key". neverRan creates stay excluded.
- **gateCreate.** After the stale check and before the lost check (~:941-950), a `settled` create with sameTicket refuses with "…returned `<KEY>` — no create receipt, fresh or not, authorises a second create of that ticket". Labels are outside sameTicket. Remedy: "write to `<KEY>` (this session created it, so it is owned); for a genuinely second ticket, decide a distinct title, or have the operator create it by hand".
- **gateMilestoneCreate (~:1576-1606).** The same check over MILESTONE_CREATES. Remedy: "use `<KEY>`; a second `<Epic|project milestone>` titled "`<title>`" would duplicate it".
- **Keep the fallbacks.** The spent refusals (~:969-974, ~:1607-1612) stay; row p's anchor sits above them.
- **Mismatch branch (~:975-981).** Grade the last element of `seen.filter((r) => !r.spent)`. When none is unspent, fall through to the no-receipt refusal (~:982-985) and add "this session's `<n>` create receipt(s) are all spent, each by the create it authorised". Row p's anchor `  const matching = seen.filter((r) => createMismatch(call.adapter, shape, r.shape, tag) === null);` stays byte-identical.
- **rejectedDecidingCommand (~:393-398).** Split the command on `;`, `&&`, `||`, `|` and newlines. It counts only when (i) a segment contains a `bun` word followed later in the same segment by the module path and its receipt subcommand (any argument for a module with no subcommand), or (ii) a segment assigns `NAME=<…module>` and a later segment contains `bun` followed by `$NAME`, `"$NAME"` or `${NAME}`.
- **Anchors.** Write the new code as separate statements. Do not copy matrix anchors e (`    if (a.root !== target.root || !a.intact) continue;`), p, or s (`if (shape.project === "" && shape.team === "") {`).
