# STE-415: /spec-write emits em-dash canonical milestone names to match probe #26 {#STE-415}

## Summary

The milestone name a Linear consumer creates and the name gate-check probe 26 expects can disagree on one character — colon versus em-dash — and that single-character gap turns an otherwise-clean fresh chain red. The plan-heading parser already normalizes both separators to the em-dash canonical form, but the spec-write skill still emits colon-form headings and tells the operator only to use the canonical name with the anchor stripped, so an emulated consumer reading the heading by eye creates the milestone with the colon name. This milestone closes the emit side: spec-write emits em-dash milestone headings by default, states outright that the created milestone name must be the em-dash canonical form, and pins the create side and the probe side to the one shared normalizer so they cannot drift again. The parser stays tolerant of the colon form, so existing projects keep canonicalizing correctly.

## Requirement

STE-335 (M87) unified milestone-heading parsing into one normalizer, `parsePlanHeading` in `adapters/_shared/src/plan_heading.ts`, which accepts both `## M<N>: <title>` and `# M<N> — <title>` and always returns the canonical em-dash form `M<N> — <title>`. STE-335 deliberately fixed the drift in the parser and left `/spec-write` and `templates/spec-templates/plan.md.template` emitting the colon form, reasoning that the parser normalizes everything downstream. That holds when the milestone name is derived by the helper (`planFileHeadingToMilestoneName` → `parsePlanHeading`), but breaks in the LLM-emulated consumer path: an emulated `/spec-write` reads the colon-form plan heading and, following the milestone-attachment prose "the canonical milestone name (anchor stripped)", creates the Linear milestone with the colon name `M2: Greeting core` instead of routing through the normalizer. Gate-check probe #26 (`tracker_project_milestone_attached`) byte-compares the created `projectMilestone.name` against `parsePlanHeading`'s em-dash output for the same heading, so the colon-vs-em-dash gap fails an otherwise-clean chain (2026-07-23 conformance run, Linear leg: 71/72, probe #26 the sole red). This FR extends STE-335 to the emit side: stop emitting the colon form, make the em-dash requirement explicit at milestone-create time, and pin the create-side derivation to the same normalizer probe #26 consumes. The parser stays tolerant of the colon form so legacy plan files keep canonicalizing correctly.

## Technical Design

**`skills/spec-write/SKILL.md` § 0b Milestone attachment.** Amend "derive the canonical milestone name (anchor stripped)" to state the derived name MUST be the em-dash-normalized canonical form `M<N> — <Title>` (never the colon form `M<N>: <Title>`), obtained by routing the plan heading through `planFileHeadingToMilestoneName` → `parsePlanHeading` (`adapters/_shared/src/plan_heading.ts`) — the single source of truth probe #26 also consumes. This is the LLM-facing contract that stops an emulated consumer from eyeballing the colon heading at `save_milestone` / `save_issue` time.

**`skills/spec-write/SKILL.md` § Stable anchor IDs (~line 154).** Rewrite the exemplar `## M{N}: ...` to `## M{N} — ...` (em-dash), keeping the `{#M{N}}` anchor.

**`templates/spec-templates/plan.md.template` (~line 47).** Rewrite `## M<N>: [Foundation / Scaffolding] {#M<N>}` to `## M<N> — [Foundation / Scaffolding] {#M<N>}`.

**`adapters/_shared/src/plan_file_single_milestone.ts` (line 27).** Widen `MILESTONE_HEADING_RE = /^## M\d+:/gm` to match both separators, e.g. `/^## M\d+ *(—|:)/gm`, so em-dash plan files (the new emit form) are still counted for the multi-milestone advisory. Update the probe's reason wording (line 73) and the gate-check SKILL probe #32 description from "`## M<N>:` headings" to a separator-neutral phrasing.

**Tests.** `tests/plan-template-shape.test.ts` (AC-STE-197.1, `/^## M[^:\s]+:/gm`) → em-dash regex. `tests/gate-check-plan-file-single-milestone.test.ts` reason-string assertion updated if the reason wording changes; add an em-dash multi-milestone fixture proving the widened regex counts it.

**Verified-safe (no change needed).** `adapters/_shared/src/plan_only_archival.ts` scans task-checkbox lines via a heading-agnostic `TASK_LINE_RE` (`/^\s*-\s*\[...\]\s/`), so the em-dash heading does not affect archival checkbox detection; its `## M<N>:` mentions are comments only (optionally refreshed for accuracy). `parsePlanHeading` already accepts both separators, so probe #26's verify side and the attach helper need no code change — only the emit side and probe #32 change.

## Notes

- Prose + template + probe FR (like STE-412): the runtime behavior in a consumer project is LLM-executed prose, so the deterministic enforcement is the meta-tests + the widened probe #32 regex + the shared-normalizer unit test; the real toolkit code path (`planFileHeadingToMilestoneName` → `parsePlanHeading`) already produced em-dash and needs no change.
- Reconciliation with STE-335 (M87 "Unified"): STE-335 chose parser-side normalization and intentionally left the emit side colon-form on the assumption the parser normalizes everything downstream. That assumption breaks only in the LLM-emulated create path, where the milestone name is derived by eye rather than by the helper. This FR extends STE-335 to the emit side rather than reverting it — the parser stays the tolerant single normalizer; the template and SKILL simply stop emitting the form that only round-trips correctly through the helper.
- Scope: Linear plan-heading → milestone-name path only. The Jira Epic-first path already emits em-dash (2026-07-24 conformance run, Jira leg: `M_DST_52 — Greeting helper`). Not re-reproduced on 2026-07-24 (the Linear leg fire-and-exited before the chain — STE-414); the root cause in the SKILL prose is inspectable and unchanged on this branch.
- Probe #32 is warning-only; widening its regex is not strictly required to pass any gate, but omitting it would let a multi-milestone em-dash plan file escape the advisory — a latent gap this change would introduce, hence folded into AC.2.

## Implementation notes

**Spec deviation — `underspecified` (backfilled + tested, resolved in-run).** AC.2 flipped the milestone-heading EMIT side to em-dash but the FR enumerated no read-side consumers. Flipping emit left five colon-only readers stale, two of them **functional**: `skills/setup/SKILL.md` (the doctor anchor check greps `specs/plan/M*.md` for `## M{N}:`, so it went silently vacuous on every plan scaffolded from the new template) and `docs/patterns.md` (the prescribed missing-anchor grep `^##\s+M[0-9]+:`). Three were documentation-only: the `docs/patterns.md` anchor-conventions table row (which named the plan template as its own source of truth while contradicting it), its worked example, and the "current format" docstrings in `attach_project_milestone.ts` / `tracker_project_milestone_attached.ts`. One flagged item was **refuted**: `skills/spec-archive/SKILL.md` + `plan_only_archival.ts` describe a `## M<N>:`-scoped block scan, but `isPlanOnlyEligible` is heading-agnostic (`TASK_LINE_RE` over every line), so that framing was descriptive fiction — reworded, not re-scoped. Resolution: all sites made separator-neutral or accurate, pinned by `tests/m113-ste-415-read-side-separator-neutrality.test.ts`. Rationale for treating this as in-scope rather than deferring: the milestone exists to eliminate emit-vs-read separator divergence, and shipping it would have created two fresh instances of exactly that.

**Scoped out deliberately.** `docs/patterns.md`'s `M[0-9]+` leaf predates the `M_<epic-key>` union grammar. That is a pre-existing gap, not one this FR introduces; only the SEPARATOR was widened, and no assertion forces the union-grammar change.

## Advisory notes

- `plan_file_single_milestone.ts` uses ` *` before the separator where `plan_heading.ts` uses `[ \t]*` — a tab-separated heading parses but is not counted by the advisory probe. Left alone: widening an advisory probe past its ACs is implementation, not refactor.
- No shared separator constant was extracted between `plan_file_single_milestone.ts` and `plan_heading.ts`. `plan_heading.ts` is off limits under AC.4, and AC.4's last test asserts its literal `(?:—|:)` source text, so a shared constant is blocked by the test contract itself.
