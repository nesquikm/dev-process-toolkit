# A declared-runnable project must actually be driven

## Summary

The check skill runs today only if one is declared or adopted, and a failing check is reported without blocking anything. In a headless run both the adopt offer and the scaffold offer decline themselves, and the run finishes reporting that no verification was configured. Every one of those paths ends with the pipeline saying done about an app nobody started.

## Requirement

When the project declares it can be run, the drive happens and a failure is red.

## Acceptance Criteria

- AC-STE-505.1: When `run_cmd` is set and is not `none`, Phase 4b" runs the resolved check skill — mandatory, not offered.
- AC-STE-505.2: `verify_mode` defaults to `blocking` when `run_cmd` is set and not `none`, and stays `advisory` otherwise.
- AC-STE-505.3: A failing drive under that default blocks the step-15 commit approval.
- AC-STE-505.4: The non-interactive decline-default does not apply when `run_cmd` is set — a headless run that cannot drive fails rather than emitting the none-declared token.
- AC-STE-505.5: `run_cmd: none` keeps every existing path byte-identical, asserted rather than assumed.
- AC-STE-505.6: The mandatory paths emit capability tokens distinct from the five existing outcome tokens.
- AC-STE-505.7: The FR records, in writing, the supersession argument against the shipped decision that made this check advisory on purpose — a reviewer who does not see the argument will correctly reject the change.

## Technical Design

Three shipped paths each end with a green report about an app that was never started, and all three are closed here. First, `verify_mode: advisory` is the documented default and it "reports a failing check in the step-14 report but the step-15 approval still proceeds". Second, the discovery precedence ends at an offer, and declining it proceeds "with a no verification configured note". Third, under non-interactive stdin both the adopt-offer and the scaffold-offer carry a safe decline-default and "never block".

Each of those was correct when verification was opt-in enrichment. None survives the premise that a declared-runnable project must be driven — which is why the gate is `run_cmd`, not a blanket flip. A project that declares `none`, or declares nothing, keeps all three paths exactly as they are (AC.5).

AC.4 is deliberately narrow. The shipped rule that "an autonomous `/implement` must never stall waiting on a verification offer" is preserved: the headless run does not stall, it fails. Stalling and failing are different outcomes and only the first is forbidden.

### Supersession argument (AC.7)

STE-347 (M93) chose advisory deliberately. Its requirement states the new phase "discovers + runs it after gate-check GREEN, surfaces the result advisorily, and — on failure — analyzes and *proposes* a remediation route". The authoring guide was explicit about the intent; as it read before this milestone rewrote it: "This is the safe default: verification informs, it does not gate." That sentence is quoted here as the pre-change text — `docs/verification-skills.md` no longer carries it, so a reader grepping the current guide will not find it and should not expect to.

That decision is not being overturned as a mistake; its precondition has changed. STE-347's advisory default protects projects that have no check skill, an unfinished stub, or a check needing a device or credentials — for those, a blocking default would gate commits on a check that cannot pass, which is why the guide recommends starting advisory and promoting once stable.

The `run_cmd` key STE-503 adds is a signal STE-347 had no access to: an author stating that this project can be brought up by this command. Every project STE-347's default protects still declares `none` or declares nothing, and keeps advisory. The flip reaches only projects whose author has said, in the config, that the app runs. `verify_mode: advisory` also remains explicitly settable, so the promote-when-stable workflow the guide teaches is unchanged — what changes is which end of it a declared-runnable project starts at.

### Recorded decision — a written `manual` mode with a declared `run_cmd` (AC.7)

AC.1 states the drive is "mandatory, not offered" and names no exception; the implementation ships one, so it is recorded here rather than left to be discovered in the resolver's source. The exception: a project that has explicitly written `verify_mode: manual` keeps the no-auto-run reminder path even when `run_cmd` declares a real command — the mandatory-drive rule does not apply to it. The reasoning is precedence. `resolveVerifyMode` returns a declared `verify_mode` before it ever inspects `run_cmd`, so an explicitly written mode always wins over the `run_cmd`-keyed default; that key decides only what an *absent* mode resolves to, and AC.2 scopes the flip to exactly that. `manual` also exists precisely for checks needing a device, credentials, or a human in the loop that an autonomous run cannot supply — forcing a drive there would gate commits on a check that structurally cannot pass unattended, which is the failure mode STE-347's advisory default was protecting against in the first place. An exception a reviewer can see is defensible; an unrecorded one is not.

## Testing

Phase 4b" coverage across the matrix of `run_cmd` set / `none` / absent against `verify_mode` set / absent, asserting which paths are mandatory and which default to blocking. Failing-drive coverage asserting the step-15 gate is closed under the new default and open under an explicit advisory. Non-tty coverage asserting failure rather than stall, and asserting the none-declared token is not emitted when `run_cmd` is set. AC.5 asserted against the shipped outputs for the `none` and absent paths. Capability-token coverage for the new tokens. `bun test` full root.

## Notes

This is the FR a reviewer is most likely to reject on sight, because it reverses a shipped, deliberate, well-argued default. The supersession argument above is part of the deliverable, not commentary on it — M129 shipped two ACs of exactly this shape for the same reason.

The change is gated on an author's explicit declaration, so no project's behaviour changes until someone writes `run_cmd` into its config.

## Implementation notes

- `verify_mode: manual` together with a declared `run_cmd` resolves to `manual` — an explicitly written mode always beats the run_cmd-keyed default. AC.1 states the drive is "mandatory, not offered" with no exception, so this is a narrowing of that AC; the reasoning is recorded in this FR's `### Recorded decision`, because an unrecorded decision is one a reviewer is right to reject.
- One preservation pin (an explicit `advisory` still lets the step-15 approval proceed) passes against the PRE-change prose too. It is sound as an AC.5 byte-identity guard and is NOT evidence for AC.3, whose discriminating leg requires the `run_cmd` literal.
- The supersession argument quotes the guide sentence "This is the safe default: verification informs, it does not gate." This milestone rewrote that sentence out of the guide; the FR now marks the quote as the pre-change text, so a reader grepping the current guide is not misled.
- The non-tty paragraph shipped WITHOUT the `manual` carve-out that the mandatory-drive paragraph carried, so a headless run on a project declaring both a real `run_cmd` and an explicit `verify_mode: manual` read as a failure emitting `verify_drive_unavailable` — contradicting this FR's own Recorded decision and the shipped rule that `manual` never auto-runs. The correct token there is `verify_skill_manual_reminder`. Caught by the pre-PR spec review; the carve-out now sits on both paragraphs. This is the third time in one milestone that a rule landed on one surface and not its sibling, which is the failure mode worth designing against rather than re-fixing.
