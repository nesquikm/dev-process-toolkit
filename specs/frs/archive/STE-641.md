# The tracker-write gate grades a transcript that holds its own call

## Summary

The tracker-write hook decides from the session transcript, but Claude Code writes a turn's call lines there only after the first call's hook has returned.
The hook judged a history missing the very call it graded, refusing writes it should permit and permitting a duplicate it should refuse.
It now waits for a later call's line, grades a lone call as the last of its turn instead of refusing it, and orders same-turn creates as the transcript lays them out.

## Requirement

When a tracker write binds a declared shared target, `pre-tracker-write-gate` grades every verdict that depends on history over a transcript read that contains the gated call's own `tool_use` line. (Re-cut: a lone or first call's read cannot hold its own line — § Re-cut — and is graded with the call placed last.) That covers settled, lost and spent creates, milestone governance, the latest join, and ticket provenance.

- If the first read lacks the line, the hook re-reads for up to 2000 ms.
- If the line never appears, the read is graded with the gated call placed after every recorded line, as for a payload with no tool_use_id; nothing is refused for the lag (re-cut, review B1).
- A ticket-write refusal in that case notes that the read did not hold the call and never says "this session did not create it".
- Creates ordered before the gated call are ordered by (line, position). The one-line-per-`tool_use` layout Claude Code writes and the legacy one-line layout then give the same verdict, and a pending same-turn duplicate is refused as a parallel duplicate when its sibling's line is in the read.

Covers A2 (FE-1, S3 and the racy lost-create verdict; medium) and A6 (T-1; low). Amends the `createsBefore` premise at STE-607.md:223, which held that Claude Code writes a `tool_use` to the transcript BEFORE its PreToolUse hook runs; measurement refuted it.

Measured basis: on Claude Code 2.1.283, a message's `tool_use` lines reach disk together when the message list next changes — for the first call of a message, after that call's own tool has run and its result is recorded — and seconds after their own `timestamp` (see § Measurement and § Re-cut below; the design draft's 103-105 ms figure was not reproduced, and the first cut's reading of the data as a bounded lag was wrong).

Operator ruling R5 applies: a payload carrying `agent_id` is graded as at HEAD, with no wait, until the subagent's `transcript_path` is measured.

## Acceptance Criteria

- AC-STE-641.1: When the gated tool_use id is absent from the first read and appears within 2000 ms, the verdict equals the verdict on the complete transcript: the FE-1 edit of a key this session created exits 0, and the S3 duplicate create exits 2.
- AC-STE-641.2: When the id is still absent after 2000 ms, a ticket create, a container create or a joined-labels edit into a declared container is graded with the gated call placed after every recorded line — the verdict a payload with no tool_use_id gets — and is never refused for the lag (amended at the re-cut, review B1: the line of a lone or first call is written only after its hook returns).
- AC-STE-641.3: A ticket write graded without its own line and refused on ownership notes that the read did not hold the call, and its stderr contains neither "this session did not create it" nor "retry the same call".
- AC-STE-641.4: A call bound by no declared target (an undeclared repository, or another project's container) exits 0 with empty stdout and stderr, performs no re-read, and finishes in under 1000 ms.
- AC-STE-641.5: A payload with no tool_use_id, a payload carrying `agent_id`, or an unreadable transcript is graded exactly as at HEAD, with no wait.
- AC-STE-641.6: `awaitGatedLine` returns the first read that holds the id. When the id never appears, it returns `stale: true` after at most ceil(2000/25)+1 reads. It never sleeps when the first read holds the id or is null.
- AC-STE-641.7: When Claude Code writes the gated call's own tool_use line relative to its PreToolUse hook is measured on the Claude Code version in use (at least 20 samples) and recorded in this FR before merge, and no verdict depends on that line landing within GATED_LINE_WAIT_MS (amended twice: 2026-09-29 by operator ruling, then at the re-cut after review B1 falsified the bounded-lag reading).
- AC-STE-641.8: `pendingToolUses` writes one transcript line per tool_use, the lines share one message.id, and `pendingToolUsesOneLine` keeps the legacy layout.
- AC-STE-641.9: With two pending identical creates and two matching receipts, the second is refused (exit 2) in both layouts.
- AC-STE-641.10: Two pending creates with different titles, each with its own receipt, are both permitted (exit 0) in both layouts.
- AC-STE-641.11: Of two pending Epic creates, the second is refused when the titles are the same, and both are permitted when the titles differ, in both layouts.
- AC-STE-641.12: The refusal for a pending same-turn sibling names it as a parallel call and does not offer `decide --attempt retry-<N>`.

## Technical Design

A pure, exported wait function re-reads the transcript every 25 ms, up to 2000 ms, until the gated call's line appears, and reports stale when it never does. The hook calls it only after the undeclared early return and the floor check, only for a call that binds a declared target, only when the payload carries a tool use id and no agent id, and only when the first read is non-null and lacks that id. The final read re-derives announcements and declarations. Create ordering uses a running line-and-position ordinal, so both transcript layouts grade alike. The hook timeout unit is seconds, so the wait cannot time it out.

## Implementation notes

- awaitGatedLine budgets requested sleep time, not elapsed time, so slow sleeps or reads can overrun 2000 ms — the hook's timeout is 5000 SECONDS, so the wait cannot time the hook out; a clock bound would add nothing the AC asks for
- no perf sample covers the stale (80-read) wait path on a 5,000-line transcript — the path is bounded by construction (ceil(2000/25)+1 reads, cheap includes() pre-filter)
- a create or container call naming no project, and a ticket call with no key, bind a declared target and so wait 2 s before a refusal that does not depend on history — latency only; the verdict is unchanged and fail-closed

## Design detail

- **The wait function.** Export a pure `awaitGatedLine(read, id, waitMs, sleep) → {lines, stale}` with `GATED_LINE_WAIT_MS = 2000`, re-reading every 25 ms through `Bun.sleepSync`. The hooks.json timeout is 5000 and its unit is seconds.
- **Where run() calls it (~:1839-1865).** After `if (declared.length === 0) return 0` and after checkFloors. Only when all hold: (i) the first read is non-null; (ii) `payload.tool_use_id` is a string; (iii) no tool_use block in the read carries it; (iv) `declared.some((d) => bindsCall(call, d))`; (v) the payload has no `agent_id`. On the final read, re-run scanAnnouncements, readDeclarations and the declared filter; the file is append-only, so once the gated line is in the read every earlier line is too.
- **Stale refusals — SUPERSEDED at the re-cut (review B1): no gate refuses for the lag; a stale read is graded with the call placed last.** Originally: gateCreate after target resolution; gateMilestoneCreate at the top; gateJoinedLabels before its permit. Gate order in gateCreate: stale → settled (the next FR) → lost → receipts. Remedy: "retry the same call unchanged; do not re-run a deciding command for it".
- **gateTicket (~:1463-1466).** [Superseded at the re-cut: nothing is prepended; the lag is noted as a fact, never as a retry.] Keep the verdict and the prefix "the ticket is not owned by the declared target". Replace "this session did not create it" with "no create of it is visible in this session's transcript". Prepend "retry the same call once first — the transcript read lags this call (its tool_use <id> is not in it yet)" when stale.
- **lostCreates (~:846-874).** Order creates by a running (line, position) ordinal, as createsBefore does. A no-result create ordered before the gated call then counts in both layouts. When it shares the gated call's message.id, word the refusal as a parallel duplicate, without the retry-search remedy.
- **Comments.** Rewrite the createsBefore and lostCreates comments with the measurement.
- **Anchors and exclusions.** Compute the wait above the guard-matrix row d anchor `  const note = unreadableInputsNote(payload, transcript, scan);` without copying that line. No PostToolUse ledger: a model-writable ledger used to permit is a forgery path, and it would move `tests/bundled-hooks-shape.test.ts:145` and `docs/hooks-reference.md:18`.

## Measurement: tool_use flush lag (AC-STE-641.7)

Measured 2026-09-28 on Claude Code 2.1.283 (this repository's M_101065 implementation session), with a 5 ms poller tailing the session transcript and recording each `tool_use` line's arrival wall-clock time. Two instruments were run, because the first answered a different question than the hook asks.

- **Instrument 1 — arrival behind the line's own `timestamp` (the AC's literal wording), 26 samples:** min 1451 ms, median 2255 ms, p90 3271 ms, max 3355 ms; a second run of 25 samples spanned 1414–3789 ms. This exceeds `GATED_LINE_WAIT_MS` (2000). It does not measure what the hook waits on: an assistant line's `timestamp` is stamped when the message STARTS streaming, and every parallel `tool_use` in that message streams after it, so this lag grows with the message and says nothing about the hook's read. The draft's "103-105 ms after their timestamp" figure is not reproduced by either instrument.
- **Instrument 2 — arrival relative to the tool's own start (what the hook's read sees), 25 samples in five parallel batches of five:** each call printed its own start time in epoch ms; PreToolUse runs before the tool body, so the tool start is an upper bound on the hook's read. Per batch the first two calls' lines landed AFTER their tool started (+138..+149 ms and +26..+34 ms); the other three landed before it (−75..−322 ms). Maximum observed lag behind the tool start: 149 ms, identical in shape across all five batches.

**Verdict — SUPERSEDED by § Re-cut below; this reading was wrong.** The lag the wait exists for is at most ~150 ms plus the PreToolUse hooks' own run time, far below `GATED_LINE_WAIT_MS` = 2000, so the bound holds. The AC's literal reference point (the line's `timestamp`) is the wrong one and fails as worded; this was recorded as an ambiguous spec deviation, and on 2026-09-29 the operator ruled to amend the AC to the reading "lag behind the gated call's execution start", which the AC now states. A related consequence for STE-644 (corrected in round 2 of the review): the gated line's `timestamp` marks its message's START, so measuring re-list freshness from it would WIDEN the window for a later call of a batch; STE-644 therefore measures freshness against the grading time.

## Re-cut: the flush premise was false (review B1, 2026-09-29)

The first cut assumed the gated call's own `tool_use` line reaches the transcript within a bounded time while its PreToolUse hook waits. That premise is FALSE for a lone call and for the first call of a message: Claude Code 2.1.283 writes a message's `tool_use` lines when the message list next changes, which is normally the first tool's result, after that call's hook has returned. Evidence from this implementation session's own transcript (lines 867-875) against the § Measurement poller: `s1` ran at 53.607, its result was recorded at 53.638, and the whole batch's `tool_use` lines reached disk together at 53.754. Instrument 2 above measured arrival relative to the tool's start and read the "+149 ms" as a lag the hook could wait out; it is in fact arrival after the tool had finished. The shipped first cut therefore refused every lone shared ticket create, container create and joined-labels edit (HEAD permitted them). The unit and spawned tests were green only because their helper wrote the gated line before the hook's first read.

**Amended design.** The bounded wait stays, because a later call of a batch can find its line. When the wait runs out, the read is graded with the call placed after every recorded line, the verdict HEAD gave and the one a payload with no `tool_use_id` gets. The three stale refusals are removed. `gateTicket` notes the lag as a fact instead of a retry. STE-644's freshness falls back to grading time when the gated line is absent. **Residual (named in the v2.91.0 release notes):** two calls of one message whose lines are not yet on disk are graded without each other, so a same-turn duplicate is refused as a parallel duplicate only when its sibling's line has landed.
