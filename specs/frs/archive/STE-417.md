# STE-417: Mint opaque ULID-derived milestone ids in tracker-less mode {#STE-417}

## Summary

In a project with no tracker, milestone numbers are chosen by scanning what the local checkout happens to see — active plans, archived plans, the changelog, and whichever git refs are present. Two developers working on separate branches that have not yet been pushed will both scan the same visible history, both land on the same next number, and discover the clash only when the branches meet.

This milestone stops allocating that number in tracker-less mode and mints an opaque identifier instead, derived from the same locally minted unique id that tracker-less feature records already use, with collision **detection within one working tree** rather than prevention by construction: the mint re-tries when a plan file for the derived id already exists (active or archived), and the gate detects a duplicate derived token spanning both trees. Two working trees that cannot see each other can still mint the same token, and will only find out when they meet. Milestones that already carry a sequential number keep working exactly as they do today — no migration, no rewriting of shipped release history.

The tracker-backed modes are untouched. One already derives milestone identity from the tracker-assigned key; the other keeps the scan it has today.

## Requirement

STE-377 (M101) introduced key-derived, collision-free milestone identity for the Jira path and **deliberately declined to extend it to tracker-less mode**, recording in its Notes that with no key available the mode keeps `max+1`, and that "the race is a multi-dev *tracker* problem". That reasoning holds only if tracker-less projects are single-developer. They are not necessarily, and `Provider.mintId()` already supplies exactly the unique, offline-safe key STE-377 assumed was unavailable — it is the same minter that has produced tracker-less FR identity since STE-134 (M37), scoped to `mode: none` and offline-safe by invariant.

STE-338 (M89) added the fifth cross-branch scan leg (`scanBranchMilestones`) for precisely this race and describes itself as **detection, not prevention**: it enumerates `M<N>.md` plan files across local heads and already-present remote-tracking refs, with no fetch by default. That narrows the window to "milestones allocated on refs this checkout cannot see" — unpushed branches, fresh clones, parallel worktrees — and cannot close it. Atomic tracker-side reservation was considered and rejected in a 2026-05-26 design session (recorded in STE-329 Notes) as a network dependency for zero gain, which leaves minting as the only remaining route to closure.

This FR therefore **reverses STE-377's tracker-less carve-out** on the grounds that its stated premise — no key to claim from — is false, and closes the race by construction rather than by widening detection further. The scope is `mode: none` only: Linear keeps its client-picked `M<N>` plus the five-way scan, and Jira keeps Epic-first derivation. The union milestone-token grammar STE-376 centralized already accepts the new shape, so no grammar change is required — only a new producer for the existing opaque branch.

## Technical Design

**`adapters/_shared/src/milestone_token.ts` — new producer, no grammar change.** `EPIC_KEY_SOURCE = [A-Za-z0-9][A-Za-z0-9_-]*` already admits a 6-char Crockford base32 tail, so `M_VDTAF4` parses today under the shipped union grammar. Add `milestoneIdFromUlid(ulid: string): string` beside `milestoneIdFromEpicKey`, returning `M_${ulid.slice(23, 29)}`. Validate the input against `ULID_REGEX` (`adapters/_shared/src/ulid.ts`) and the output against `isMilestoneToken`, throwing on either failure — never a silent bad id, mirroring `milestoneIdFromEpicKey`'s contract. The `slice(23, 29)` offsets are shared verbatim with `acPrefix` (`adapters/_shared/src/ac_prefix.ts`); the tail rather than the head of the random segment is used for the reason documented there — the minter is monotonic, so same-millisecond mints share leading random chars.

**Discriminant left alone (deliberate).** A minted milestone id parses as `{kind: "epic"}`. This is semantically loose in a repo with no tracker and no Epics, but renaming the union branch would require a consumer sweep across `branch_proposal.ts` (`epicBranchKey`), `compareMilestoneTokens`, and their tests for no behavioral gain. Keeping `"epic"` means `branch_proposal`'s `m_<key>` branch template and the numeric-then-opaque ordering work untouched. A third `{kind: "ulid"}` was ruled out as unsound: the parser is mode-agnostic and both producers emit literally `M_<key>`, so no token-local test can distinguish them without a fragile charset or length heuristic.

**`skills/spec-write/SKILL.md` § plan.md milestone-allocation guard.** Today the guard has two branches: the five-way scan (Linear + `mode: none`) and the Jira Epic-first bypass. Add a third for `mode: none`, structurally identical to the Jira branch but with a local producer: mint, derive, write `specs/plan/M_<short-ULID>.md`, bind FRs, bypass `nextFreeMilestoneNumber`. The sentence "Linear and `mode: none` keep the sequential five-way scan unchanged" narrows to Linear only. The milestone-allocation `requireOrRefuse` gate routes **all three** branches at the same gate site, differing only in what it recommends as `defaultValue`: the scanned `M<N>` on Linear, the Epic-derived `M_<epic-key>` on Jira, and the locally minted `M_<short-ULID>` here. An earlier draft of this section claimed the gate "stays on the Linear path" and that Jira has no allocation decision to route — that misreads the shipped guard, which has routed Jira through the same gate since Epic-first landed. Leaving the minted path off the gate would give `mode: none` + non-tty + no marker no defined outcome, which is the exact silent-no-op shape the gate exists to prevent.

**`mintUniqueId` reuse for the collision guard.** `adapters/_shared/src/ulid.ts` already exports `mintUniqueId({ exists })` with a 3-attempt retry, so the milestone guard needs no new scan module (unlike the FR side's `scanShortUlidCollision`, which post-dates it). The predicate is a synchronous `existsSync` pair over the active and archived plan directories — `mintUniqueId` requires a synchronous predicate by contract.

**Plan-frontmatter `id:`.** New surface: `id:` exists only on FR files today. Mode-conditional exactly like the FR bimodal invariant — present in `mode: none`, absent in tracker mode. The probe follows AC-STE-321.5's bidirectional shape (probe #13 `identity_mode_conditional`), extended to walk `specs/plan/**`.

**Verified-safe (no change needed).** A repo-wide grep confirms no numeric-only plan-filename filter survives in `adapters/`: STE-376's sweep routed every walker through `PLAN_FILENAME_RE` / `parseMilestoneToken`. Fourteen shared consumers already ride the union matcher. The three remaining `NUMERIC_MILESTONE_*` consumers are correct as-is — `next_free_milestone_number.ts` and `branch_milestone_scan.ts` allocate and scan *numbers* by design and become vacuous on the minted path (AC-STE-376.3 already specifies opaque ids never bump the counter), and `migrations/monolith_split.ts` is a legacy migration path to re-confirm at implementation time. `/ship-milestone` already declares `M_<epic-key>` an accepted milestone token everywhere it says `M<N>`, including the CHANGELOG ref convention, so the release path needs no change.

## Notes

- **Reversal, not gap-fill.** STE-377 considered tracker-less minting and declined it in writing. This FR overturns that specific call because `Provider.mintId()` supplies the key STE-377 assumed absent, and because the single-developer premise behind "the race is a multi-dev tracker problem" is not guaranteed. Recorded explicitly so a future reader does not mistake this for an oversight being corrected.
- **The `fr_` prefix rides along.** The minted value is stored in plan frontmatter verbatim, prefix included, so a plan's `id:` reads `fr_01K…` despite not being an FR. Stripping it would require a parallel regex and a second slice constant, and would desynchronize the `slice(23, 29)` offsets shared with `acPrefix`. Byte-compatibility was chosen over cosmetics; if the prefix is ever generalized, both call sites move together.
- **The ordinal is given up deliberately.** In `mode: none` there is no longer any answer to "which milestone is next" — no sequence, no ship-time renumbering, no display ordinal. Chronology is carried by the release version and codename in the CHANGELOG. A ship-time stamped ordinal was considered and rejected: it re-creates the dual-identity shape that produced M101's enumeration bug.
- **Scope boundary.** Linear remains client-picked `M<N>` and therefore remains theoretically racy, narrowed but not closed by the STE-338 branch leg plus tracker enumeration. Extending key-derived identity to Linear (deriving from the native milestone object's server-assigned id, mirroring Jira's Epic-first) is a coherent follow-up and was explicitly deferred out of this milestone.
- **Coexistence is already specified.** AC-STE-376.3 pins that opaque ids are accepted, excluded from `max+1`, and never integer-parsed, so a mixed `specs/plan/` tree needs no new machinery — only the re-scoped regression assertions in AC.5.
- **Collision-fixture caveat (`DPT_TEST_ULID_SEED`).** Under the seeded test path (`adapters/_shared/src/ulid.ts:98-100`) the tail is produced by a monotonic **in-process counter** (`encodeTestCounter`), so consecutive mints inside one test file yield different tails and the counter's value depends on the test's position in the file. AC.4's forced-collision fixture therefore cannot pre-create a fixed literal filename — it must pre-create the file for the tail the *first* mint will actually produce, and should pin that derivation explicitly in the test setup rather than hard-coding a string. Recorded here so it is a known constraint at implementation time, not a debugging surprise.

## Implementation notes

- AC.1's second throw branch is provably unreachable — any input passing `ULID_REGEX` yields a 6-char Crockford slice that `isMilestoneToken` always accepts, so all malformed fixtures fail at the first guard. Kept for defensive symmetry with `milestoneIdFromEpicKey`; the § Testing line asking for a "throw when the derived id would be malformed" case is unmeetable without mocking and should not be read as covered.
- AC.5's "the allocator is not called on the minted path" proof is an inference, not a spy: it asserts `mintMilestoneId` returns synchronously and that its module imports neither `next_free_milestone_number` nor `branch_milestone_scan`. That pins the module, not the `/spec-write` flow — the flow-level guarantee rests on the prose meta-test over the SKILL paragraph.
