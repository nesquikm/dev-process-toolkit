# A user can switch the tracker write gate off for themselves

## Summary

The tracker write gate guards shared trackers so one repo cannot write another team's tickets.
Some users need to work without it, and today the only way out disables the whole plugin.
This adds a per-user option that turns the gate off for that user alone.
The team default stays on, and the gate is never silent when it is off.
It says so on every write it lets through, and the gate check reports the setting.

## Requirement

GitHub issue #118 asks for a per-user switch for `pre-tracker-write-gate` through the plugin's `userConfig`. Claude Code cannot disable one hook of a plugin, only the whole plugin or every hook, so the switch must live in the plugin. The value is stored per user under `pluginConfigs`, so a team that leaves it alone keeps enforcing.

## Acceptance Criteria

- AC-STE-693.1: Before any gate code changes, a live run on the installed Claude Code (version recorded) with the option declared and set through `/plugin configure` records in this FR's Notes: the exact environment variable the hook receives and its value, and whether a value under project-scope `pluginConfigs` (a committed `.claude/settings.json`) also reaches the hook. Later ACs use the measured variable name.
- AC-STE-693.2: `.claude-plugin/plugin.json` declares `userConfig.tracker_write_gate` with the values `enforce` and `off`, default `enforce`, and a description naming what `off` does. A test reads the manifest and asserts all three.
- AC-STE-693.3: With the variable set to `off`, the hook exits 0 for every write the existing refusal fixtures refuse, and prints exactly one stderr line containing `tracker write gate off for this user`, the tool name, and every ticket key it did not check. Where no candidate repository declares a shared container, the hook stays silent whatever the setting, exactly as AC-STE-607.1 requires: every stderr line this FR adds speaks only when a declared shared target binds the call.
- AC-STE-693.4: With the variable absent, empty or `enforce`, the hook's exit code and stderr are byte-identical to today across the same fixtures. Any other value is treated as `enforce` and adds one stderr line naming the value it ignored.
- AC-STE-693.5: Nothing the model can write turns the gate off: a transcript carrying the literal option name and `off`, an assistant echo of the variable, or a repo file naming it leaves every decision unchanged (the STE-607 forgery rule). That includes a `.claude/settings.json` or `.claude/settings.local.json` under the hook's git top level whose `env` block names the variable, a route measured to deliver it to the hook: the hook then treats `off` as `enforce` and adds one stderr line naming that file. Amended 2026-10-23 (post-release fix on PR #122): Claude Code loads project settings from the session's launch directory, which hooks receive as `CLAUDE_PROJECT_DIR`, so the scan also runs from `CLAUDE_PROJECT_DIR` up to its git top level (the directory itself outside a repository); when both it and the cwd's git top level resolve and differ, both are scanned and either file naming the variable enforces. An unset or empty `CLAUDE_PROJECT_DIR` leaves the cwd scan unchanged, and the AC.6 row scans the same roots.
- AC-STE-693.6: `/gate-check` reports the effective setting in one row, `enforce` or `off (per-user)`. If AC.1 measured that a project-scope value reaches the hook, the row also warns when a committed project settings file sets the option to `off`. AC.1 measured that project `pluginConfigs` does not, but a project settings `env` block does, so the row warns when `.claude/settings.json` or `.claude/settings.local.json` sets the variable in its `env` block.
- AC-STE-693.7: The hooks reference documents the option: values, default, how to set it with `/plugin configure`, the stderr line, and the scope rule AC.1 measured.
- AC-STE-693.8: Mutation battery: removing the `off` branch, removing the stderr line, or treating an unknown value as `off` each reddens a named test.
- AC-STE-693.9: Gate: `bun test` from `plugins/dev-process-toolkit` reports 0 fail with skip identities equal to the baseline, and `/gate-check` is clean.

## Technical Design

Read the variable once at hook entry, before the ownership checks, through one exported helper the hook and the gate-check row share. `off` short-circuits after the hook has identified the write and its keys, so the stderr line can name them; it never reads the transcript to decide. Unknown values fail closed to enforce. The new probe row follows the registry's count-pin procedure.

## Testing

Drive the hook as a subprocess with the variable set per case over the existing refusal fixtures; compare enforce runs byte-for-byte against a pre-change capture. Forgery cases plant the option in the transcript and repo files.

## Notes

Project and local `pluginConfigs` never reach it; a project settings `env` block does. Runs and transcript: `specs/notes/ste-693-userconfig-measurement.md`.

## Implementation notes

- declaredTargetBinds re-reads and re-scans the transcript and re-runs git rev-parse only to decide whether a stderr line speaks — an efficiency cost on the off and unknown-value paths only; the enforce path is unchanged and decisions are correct, so it is a refactor candidate, not a defect
- hooks.json declares timeout 5000 for this hook, which Claude Code reads as seconds — informational; the line predates this milestone and nothing here depends on a 5 s bound
- gate-check SKILL.md row #89 does not say the row names an unrecognised value — the AC-STE-618.8 byte freeze admits edits on lines 120, 128 and 154 only; the row's wording, an unknown value is enforce, is still true
- one STE-693 test still pins the hook's variable-absent stderr to 976e6b8e plus PERMITTED_WORDING_DELTAS — a deliberate freeze: the next legitimate change to the hook's refusal wording must add a named delta, as STE-694 did
