# The stage report is a fenced status block with a hard line budget

## Summary

Every stage ends by narrating what it did in paragraphs, and nothing anywhere constrains how long that narration runs. The operator scans several screens for two numbers. This defines one fenced status block with a fixed section order and a hard line budget covering the whole report, plus a validator that grades a rendered report against it. The block is the report, not a summary appended to one.

## Requirement

A shared validator defines and grades the status block: fixed section order, a hard line cap over the whole stage report, an explicit empty-section fallback, and counts that must be backed by captured output.

## Acceptance Criteria

- AC-STE-532.1: A module in the shared adapters tree exports a validator taking a rendered stage report and returning `{ ok, reasons }`. On a clean report `ok` is true and `reasons` is empty; every rejection names its own reason rather than returning a bare false.
- AC-STE-532.2: The block declares a fixed section order, and a report whose sections are reordered or whose required section is missing fails, naming the offending section. The order is stated in exactly one place and read from there.
- AC-STE-532.3: The line cap spans the WHOLE stage report — prose lead-in plus fence — not the fence alone. A report with a compliant fence and forty lines of narration above it FAILS, and the test asserts that specific shape, because a cap that measures only the fence leaves the surface it was written to shorten unconstrained.
- AC-STE-532.4: A section with nothing to report keeps its heading and carries the literal `- (none found)`. A dropped section is a violation, not an empty one. Scalar sections cannot carry the list-item fallback and are excluded from that rule.
- AC-STE-532.5: A numeric count with no captured output behind it fails, in the same `{ ok: false, reasons }` verdict shape as a structural violation, so invented numbers take the existing recovery path and earn no second budget of their own.
- AC-STE-532.6: The validator delegates to the shipped fence-parsing primitives in `adapters/_shared/src/markdown_fences.ts` rather than re-implementing them. A second parser free to disagree with the first about the same bytes is the two-renderers defect this repository has already recorded; the test asserts the delegation, not merely the result.
- AC-STE-532.7: Mutation-verified, and each mutation is asserted to have applied. Removing the fence turns AC-STE-532.1's assertion red; swapping two sections turns AC-STE-532.2's red; deleting the prose lead-in from the measured span turns AC-STE-532.3's red. The test names the clause each mutation changed.

## Technical Design

The validator lives beside the shipped stage-capture grader in `adapters/_shared/src/` and reuses its fence primitives; it does not fork them. The report-wide line span in AC-STE-532.3 is the one genuinely new measurement — `verifyDeliverStageCapture` measures inside the fence because its subject is a hand-off between machines, whereas this subject is what a human reads on screen.

Section order and the cap number are module constants exported for the authoring surfaces to read, so the prose and the scanner cannot disagree. STE-536 consumes those exports.

## Testing

AC-STE-532.3 is tested with a report that is compliant inside the fence and non-compliant overall, because the discriminating case is the disagreement between the two spans, not either verdict alone.

Counts-without-capture reuses the shipped grader's fixtures rather than new ones, so a drift in that contract surfaces here too.

## Notes

The block replaces narration rather than summarising it. That decision is STE-533's to implement; this FR only defines and grades the shape.
