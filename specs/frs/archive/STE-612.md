# Re-pointing a repository at another tracker project is checked by code, not a checklist

## Summary

Moving a repository's tracker binding into a project another repository already uses rests on seven preconditions that nothing checks. The rewrite of the binding can also silently drop the keys that mark the project as shared.
One command checks every precondition and refuses while any branch or worktree holds active old-project work.
It rewrites only the project line, then names the branches that still carry the old binding and says why the old project must never be archived.

## Requirement

Measured at HEAD ac1f3cb against the two real repositories the contract was written from (findings RP-1, RP-9, RP-12, RP-PROC, MI-4, and the skeptics' notes on key preservation and the old project):

- `/setup --resume-tracker-binding` routes to `docs/setup-reference.md` § 0c, whose seven preconditions are prose. No shipped code checks any of them, and the suite that ships with them pins wording only. Measured today, rows 2, 3, 5 and 6 fail for `glacy-app-be`, and nothing would stop the flip.
- Row 7 is FR-level only. A repository with an active plan whose container lives in the old project (`M_GB_40`, Epic `GB-40`) passes it. After the flip that plan is stranded: attach lists the new project and refuses, and a new FR creates a parentless ticket first (the create-first half is closed by STE-611).
- Step 7b "writes the sub-section with `project:`" and has no contract preserving the other keys. A flip run after `repo_tag`, `default_labels`, `min_dpt_version` or `jira_issue_type` were declared may drop them. STE-603 ships the key-preserving writer; this command is the only repoint caller of it, and calls it only after every row passes.
- The binding lives in each branch's CLAUDE.md, so every unmerged branch and worktree keeps creating tickets in the old project until it rebases.
- Legacy FRs stay bound to old-project tickets by key, and probes #8 and #26 and the archival assertion read them there. Archiving or deleting the old project breaks those reads.
- The MEASURED facts in rows 3 and 6 are wrong for this repository pair: the label overlap is 17 tokens, not the range the row states.

Required behaviour: one command, `repoint_tracker_binding.ts`, decides every row from the tracker listings the session passes in. It writes the binding only when no row refuses, preserves every other byte of CLAUDE.md, and reports what a checklist cannot enforce. Each row prints `PASS`, `REFUSE` or `NOT-APPLICABLE` with a reason, and a row whose input is absent, unreadable or malformed prints `REFUSE`, never `PASS`.

Rows, in the order § 0c lists them, plus row 8. A target counts as shared when this repository declares `repo_tag`, when `--containers` or (Jira) `--labels` lists at least one row, or when at least one `--peer` is named; rows 2 and 3 apply only to a shared target and otherwise print `NOT-APPLICABLE` with that reason, so a plain move into an empty project is not forced to declare a tag. The line names which empty listings made the target unshared, and the receipt records it.

Not every run of the flag is a repoint. When the sub-section's `project:` is absent or is the `<deferred>` placeholder step 7b writes before authentication, the run is a resume; when the new project equals the bound one, it is a declaration (STE-603). Neither runs the rows: the command prints `resume` or `declare` and hands straight to the writer, so those two routes behave as M_947c79 ships them.

Old clients run § 0c as prose and can still flip unchecked. A newer client's gate catches the result through the probe #25 leg below.

1. The new project appears in the project listing (`--projects`).
2. Probe #25, as STE-603 extends it (declaration read without refusal, stop paragraph byte-equal, running version at or above the floor), reports zero violations for this repository, run in-process on its tree. Each `--peer` must also report zero, bind the new project and declare a distinct tag. With no peer, the command prints `peers=0 (not checked)`.
3. Jira: `jira_issue_type` is declared and appears in `--issue-types` for the new project, and every peer declares the same value. Linear: not applicable.
4. `specs/tracker-config.yaml` exists and its statuses include every status in `--statuses`. The file's statuses are snapshotted into the receipt.
5. `mcp_server` names an entry in `.mcp.json`, and each peer's entry points at the same server URL. A spelling difference is reported, never refused.
6. No active numeric `M<N>` plan collides with the new project: Jira, its `milestone-M<N>` label in `--labels`; Linear, a milestone of the same canonical name. Overlaps involving only archived plans pass and are counted as legacy history.
7. No active plan's container is missing from `--containers` for the new project, no active FR is bound to such a plan, and (Jira) no active FR's key prefix differs from the new project's key. **Amended (M_685ff6 pre-PR review, round 1):** row 7 read the working tree only, so work active on an unmerged branch passed and was merely reported by row 8. It now reads the git state — every worktree, local branch and remote-tracking ref, without fetching — and a plan or FR active there (live somewhere, archived nowhere) refuses; row 8 still reports the bindings merely present on stale branches.
8. Report only: the local branches and worktrees whose CLAUDE.md still binds the old project, and the count of archived FRs still bound to old-project tickets by key.

## Acceptance Criteria

- AC-STE-612.1: Front door. `bun run adapters/_shared/src/repoint_tracker_binding.ts <projectRoot> <mode> <newProject> --projects <file> --containers <file> [--issue-types <file>] [--statuses <file>] [--labels <file>] [--peer <path>]…` prints one line per row, `<n> PASS|REFUSE|NOT-APPLICABLE <reason>`, for rows 1 to 7 in order. It exits 1 when any row refuses and then writes nothing: CLAUDE.md is byte-identical and no receipt exists. For each row, an absent, unreadable or malformed input file makes that row `REFUSE` (asserted per row). `mode: none`, or no `## Task Tracking` section, refuses before any row, as § 0c already requires. Resume and declare legs: a sub-section with `project: <deferred>`, and one whose project equals `<newProject>` with no `repo_tag`, each run zero rows and reach the writer (exit 0), where on the rows path the second would refuse at row 2. The test spawns the command as a subprocess.
- AC-STE-612.2: Rows 1 to 3, each with a pass leg and a refuse leg. The new project is absent from the listing ⇒ row 1 refuses. No `repo_tag`, a malformed declaration, a missing or stale stop paragraph, or a floor newer than the running plugin ⇒ row 2 refuses, carrying probe #25's own violation text. A peer bound to another project, or declaring the same tag ⇒ row 2 refuses. No peer ⇒ row 2 prints `peers=0 (not checked)` and does not refuse on that account. Jira with no `jira_issue_type`, or one the project does not offer ⇒ row 3 refuses. Linear ⇒ row 3 prints `NOT-APPLICABLE`. Empty `--containers` and `--labels` listings, no peer and no `repo_tag` ⇒ rows 2 and 3 print `NOT-APPLICABLE` naming those empty listings (the plain-move permit leg); the same repository with one listed container, or one listed label, or a declared `repo_tag` ⇒ both rows apply.
- AC-STE-612.3: Rows 4 to 6, each with a pass leg and a refuse leg. A tracker config lacking one of the new project's statuses, or absent ⇒ row 4 refuses and names the missing statuses. Peers whose `.mcp.json` entries point at different URLs ⇒ row 5 refuses; the same URL under two spellings ⇒ row 5 passes and names both spellings. An active numeric plan whose label, or Linear name, exists in the new project ⇒ row 6 refuses. The 17-token archived-only overlap measured for this pair passes as `overlap=17 archived tokens`, with the count computed and not typed.
- AC-STE-612.4: Row 7 is the old-container rule. A fixture bound to `GB`, repointing to `GF` while `M_GB_40` is active with two active FRs, refuses and names the plan and both FR ids. After that plan and its FRs are archived, the same run passes (permit leg). Linear: an active plan whose `M_<6-hex>` token resolves to no milestone in `--containers` refuses, and one that resolves passes. An active Jira FR keyed `GB-*` refuses a repoint to `GF`. This module is absent at HEAD, so each leg is graded red against a faithful pre-change-semantics sibling in which the flip proceeds with no check, as STE-597 did for its own new module.
- AC-STE-612.5: The write changes one line, through one writer. When no row refuses, the command calls `writeTrackerSubsection` of STE-603 with the new project (and, for Linear with `--team`, the new team) and edits CLAUDE.md no other way; a mutation that makes the command write the file itself is caught by a test asserting the writer was the only caller. A byte diff of CLAUDE.md on the repoint path shows exactly the project (and team) line changed and, when a tag is declared, the stop paragraph re-rendered by `renderSharedTrackerSentinel` for the new project, since that paragraph names the project and probe #25 compares it byte-for-byte; `repo_tag`, `default_labels`, `min_dpt_version`, `jira_issue_type` and every other line are preserved. Probe #25 run on the written tree reports zero violations. The command writes one receipt of kind `repoint`, recording the old project, the new project and the row-4 status snapshot, through the receipt store of STE-602, and prints its `dpt-receipt:` line.
- AC-STE-612.6: Post-flip verification. `bun run adapters/_shared/src/repoint_tracker_binding.ts <projectRoot> --verify` exits 0 when `specs/tracker-config.yaml` still carries every status in the receipt's snapshot. When step 7f dropped some, it exits 1 and names each dropped status. When there is no repoint receipt, it refuses, because it cannot verify what was not recorded. `docs/setup-reference.md` § 0c orders `--verify` as the last step of the flag, after step 7f.
- AC-STE-612.7: Row 8, the report. On success the output names every local branch and every worktree whose CLAUDE.md still binds the old project; zero is printed as `0 branches`, never omitted. It then prints one line with the count of archived FRs whose tracker keys carry the old project's prefix, stating that the old project must not be archived or deleted because those bindings are read by key. For Linear the line counts archived plans instead. A fixture with one stale branch and one worktree names both, and the same fixture with them removed prints `0 branches`.
- AC-STE-612.8: The gate catches a flip that skipped the command. ## Technical Design

A new module owns the rows, the repoint receipt and the verification. Its front door takes MCP listings as files, the `discover_field.ts` pattern. The binding write is delegated to the key-preserving sub-section writer the declaration FR ships, so CLAUDE.md has one writer. The probe #25 leg reuses the same forward sanitization as the attach refusal, so the token and project agree by one expression.

## Testing

Fixture repositories are built with `makeSpanFixture` and its `claudeMd` helper from the measured Glacy shapes: a GB-bound repository with an active `M_GB_40`, a tracker config, `.mcp.json` entries under two spellings, and a stale branch and worktree. For each row, test a pass leg, a refuse leg and an unreadable-input leg. Byte-diff the write. Cover verification with a clobbered and an intact config. Run probe #25 on consistent and hand-flipped trees.

## Notes

- Per-contributor create access and the tracker's board filters and automation cannot be checked with the operator's credentials, so they remain manual.
- Peers are checked on their current working tree only, not on their other branches.

## Implementation notes

- `adapters/_shared/src/repoint_tracker_binding.ts` is the repoint command. It decides rows 1 to 7 from pre-fetched listings and the tree; it never makes a live tracker call. The one write goes through `writeTrackerSubsection`, followed by one `repoint` receipt announced by `announceReceipt`. After that come `--verify` and the row 8 report. Every printed line is collapsed with `oneLine`.
- Probe #25 and row 7 share `epicTokenPrefix`, `epicTokenOutside`, `foreignJiraKeyProject`, `activeJiraKeyOf` and `mdFiles`, exported from `task_tracking_workspace_binding_present.ts`, so the two cannot disagree. Row 8's legacy count uses `jiraKeyOf`, the same key without the status filter.
- Probe #25 reports the key-prefix leg under a plain `skipped` field when the mode is not Jira. A leg that did not run is listed, never counted as passed. The 603.6 pre-change test compares `.violations` (amended by AC-STE-612.8).
- Reachability: the command imports `tracker_config.ts`, so `skills/gate-check/SKILL.md:139` is no longer an ordered reference to an unreachable module. The awaited probe, diffed record by record against 1332279, measured 121 -> 120; three `setup-reference.md` records moved two lines and are the same records. The new ledger head records the move. STE-608's 608.12 leg now finds its own entry by subject, and 558.7's `LATER_MOVES` gains STE-612.
- Phase 3 findings fixed with RED-first legs:
  - the audit's vacuous `^0 branches` guard;
  - probe #25 grading archived-status FRs;
  - probe #25 and row 7 grading every tracker's key;
  - a newline in an FR filename forging a front-door line;
  - row 8 counting non-Jira keys;
  - row 7 reporting a heading defect as a `--containers` miss.
- `--verify` reads the session's own receipts, so § 0c now says to run all three steps in one session.

- **The git-state reader is batched (pre-PR review, round 2).** One `git ls-tree` per ref cost about 5 ms per ref: 504 ms for this repository's 100 refs, and the audit extrapolated 7.9 s for 2,000 branches. The reader now runs three git processes whatever the ref count. `cat-file --batch-check` resolves each ref's four spec trees. `cat-file --batch` reads each distinct tree once, and then each distinct live blob once. Measured on the same 100 refs: 62-68 ms, with the result byte-identical to the per-ref reader.
