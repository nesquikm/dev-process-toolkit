# The blocking-gate count is derived, not typed

## Summary

Two sibling suites decide their every-gate roll-ups by comparing a hand-typed array against the literal three. One of them sits under a comment claiming the list was measured from the hook registry, which it was not. A fourth blocking gate lands and both suites stay green.

That is exactly the failure the milestone that wrote them was built to prevent, reproduced inside its own tests. A reader that derives the set already ships beside them and is not consulted.

## Requirement

Both sibling suites grade their hand-kept gate list against the set derived from the hook entry points, so a blocking gate that neither suite covers reds the run that adds it.

## Acceptance Criteria

- AC-STE-577.1: Each of the two suites imports `deriveBlockingGates` and computes the derived set once from the plugin root. Neither suite's roll-up predicate compares against the literal `3` any longer; each compares against the derived set's length.
- AC-STE-577.2: Each suite carries an agreement test asserting its hand-kept list and the derived set name the same gates and the same demanded skills, compared as sorted collections rather than positionally. Its failure message names the hook entry-point directory, so a red run points at the file to open.
- AC-STE-577.3: The agreement test is the first test in each file, so a fourth gate reds at the top of the output rather than buried among collateral failures.
- AC-STE-577.4: Each agreement test is guarded by an assertion that the derived set is non-empty. An unreadable or missing hook tree yields an empty set, and an agreement check against nothing would pass vacuously.
- AC-STE-577.5: The hand-kept arrays are not replaced by the derived set, and their element order is unchanged. Two entries are bound by index to specific skill files while the derived set is name-sorted, so a substitution would silently regrade the wrong file and stay green — reproducing this FR's own subject. A test asserts the two index-bound entries still name the skills they name today.
- AC-STE-577.6: Falsifiability, both directions, measured clean on the unmutated tree first. Adding a real fourth blocking gate to a scratch copy — entry point, shell shim and registry entry, all three, since the derived reader inspects entry-point sources and never opens the registry — reds both suites. Removing one existing gate's entry point reds both suites too.
- AC-STE-577.7: The mutation arm is proved to be a mutation. Before the change, the same fourth-gate mutation leaves both suites green; that green is measured and recorded, because a mutation that never applied is indistinguishable from one the code survives.
- AC-STE-577.8: The false comment claiming the list was measured from the hook registry is deleted or corrected.
- AC-STE-577.9: This FR adds no gate-check probe and no ordered adapter module. The probe count and the down-only module-reachability pin are asserted unmoved.

## Technical Design

Roughly a dozen lines per suite: one import, one derived constant, two roll-up predicates re-pointed at its length, and one agreement test.

The derived reader throws rather than returning an empty set when a hook entry point cannot be read. Adopting it moves that import-time failure from one file to four, counting this FR's own suite. Intended — loud beats silent — and recorded so it is a decision rather than a surprise on the day it fires.

The scope this closes is entry points that carry the blocking shape. A gate registered in the hook registry with no matching entry point stays invisible to the derived reader, and this FR must not be described as closing that.

## Testing

The fourth-gate mutation needs all three pieces because the derived reader reads entry-point sources only. A registry-only mutation changes nothing the reader can see, and a suite that stayed green under it would read as evidence that the finding was false.

Comparing sorted name collections rather than lengths is what makes the removal direction red as well: a bare count comparison is satisfied by any swap that keeps the total.

## Notes

The suite carrying the false comment is the artefact its sibling was written to retire. Converting it makes one sibling depend on the other's subject, which is why the derived set grades the list here instead of replacing it.

## Implementation notes

- The audit re-measured the pre-change counterfactual rather than trusting the record: both sibling suites are 76 pass / 0 fail on a staged copy carrying a real fourth blocking gate, and 76 / 0 again with an entry point removed. After the change the same fourth-gate mutation is 72 / 6, with the agreement test red first in both files. The mutation was confirmed to have applied — the derived reader returned four gates including the synthetic one — so this is a mutation the old code survived, not one that never ran.
- The suite grades the two siblings at SOURCE level, not by behaviour: it reads each body for the import, the single derivation call, the first-test position and the non-empty guard. That is why the agreement test is duplicated in both files rather than hoisted into a shared helper — the duplication is the specified deliverable, and hoisting it would red four ACs.
- Narrower than its wording: the AC.1 source pin matches `<array>.length === <digits>` only, so a reversed `3 === HOOKS.length` or a `!== 3` would slip past it. Not a live defect — both roll-ups are derived, confirmed by grep — but the pin is narrower than the clause it enforces.
- Under a substitution mutation the 572 suite reds one of its own tests by coincidence of the two skill files' contents. That single red is not a designed guard; AC.5's pin is the only thing that names the regrade, and nobody should later read the coincidental red as sufficient protection.
