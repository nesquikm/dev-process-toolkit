# Every spawned worker carries a name, on both paths

## Summary

Naming a worker is not something the spawning skill does on its own. The name is supplied by whoever calls it, the bridge argument is opt-in, and the orchestrator supplies neither today. So a change that only reaches the confirm gate would name workers on the resume path and leave every fresh-idea run spawning workers with no name and no bridge at all.

That asymmetry — a rule landing on one path and not its sibling — is a shape this repository has been bitten by repeatedly, and it is why this criterion is written as a pin rather than a sentence. Both paths hand the spawning skill a name. The gate is the surface where the operator can change it, and that surface exists only on the resume path; a fresh-idea run is named without being editable, which is a different thing from being unnamed.

When the spawning skill is too old to understand the argument, the run proceeds. The worker launches unbridged and unnamed, one advisory row says so, and nothing halts. That departs from a precedent in this codebase, deliberately, and the departure is recorded rather than left for a reader to reconcile.

## Requirement

Both delivery paths hand the spawning skill a worker name, and a spawning skill that cannot use it degrades to today's behaviour without halting the run.

## Acceptance Criteria

- AC-STE-520.1: Phase 3's spawn step hands the spawning skill the worker name on the resume path, taken from the confirmed record's `remote_control` field rather than re-derived at the spawn.
- AC-STE-520.2: Phase 3's spawn step hands the spawning skill the worker name on the fresh-idea path, derived by the same function from the milestone Phase 2 produced. A fresh-idea run never spawns an unnamed worker.
- AC-STE-520.3: AC.2 is pinned as a falsifiable assertion against the shipped surface, and its deletion turns the assertion red. A sentence asserting the fresh path is covered, with nothing reading that surface, would pass while the path silently stayed uncovered.
- AC-STE-520.4: The bridge argument is opt-in. When the orchestrator supplies no name, the launch line the spawning skill builds is byte-identical to today's.
- AC-STE-520.5: A record whose `remote_control` field reads `none` spawns a worker with no bridge, and the run proceeds.
- AC-STE-520.6: When the spawning skill does not understand the argument, the worker launches unbridged and unnamed, the run proceeds, and exactly one advisory row reports it. This is never a halt.
- AC-STE-520.7: The operative surface records the departure in these terms: the existing halt for a missing spawning skill protects a safety property, because a visible session is the pipeline's contract and an invisible background agent is an explicit non-substitute; remote-control naming is legibility, and an unnamed unbridged worker still completes the whole ceremony in a visible session. Fail closed there, degrade cleanly here.
- AC-STE-520.8: Neither plugin declares a version floor on the other. The orchestrator is useful against a spawning skill without the argument, and the argument is useful to callers that are not this orchestrator.
- AC-STE-520.9: When the bridged launch hard-exits BEFORE the session starts — the account's organization disables remote control, or the subscription does not cover it — the spawn is retried exactly once without the bridge argument, the run proceeds, and one advisory row names that condition. A name the operator confirmed at the gate can never strand the pipeline.
- AC-STE-520.10: AC.9's condition and AC.6's are reported distinguishably. An argument the spawning skill does not understand and an argument it passes to a CLI that refuses it are different failures with different remedies, and collapsing them into one advisory sends the operator to the wrong fix.
- AC-STE-520.11: When the worker name cannot be derived — the identity leaves no room for a repository segment, or the repository basename sanitizes to something the grammar rejects — the decision record renders `remote_control: none`, the run PROCEEDS TO THE GATE, and exactly one advisory row reports it. The record never refuses for this reason. The advisory names WHICH RULE was broken — the length cap, a leading character outside the grammar, or nothing left after sanitizing — and the three do NOT share a remedy: the cap is an identity fault answered by shortening the identity, while the other two are basename faults answered by renaming the repository. An operator cannot fix what they cannot diagnose, and pointing all three at a rename would send two of them to the wrong file.
- AC-STE-520.12: AC.11 is pinned on BOTH sides: a derivable name renders in full, and an underivable one yields `none`, the advisory, and a run that continues. A one-sided pin would pass forever on this repository, whose own basename is legal — a test that cannot fail.
- AC-STE-520.13: The fallback is NARROW. Only the underivable-name refusal is caught; any other error from that call site propagates unchanged. Mutation-verified: a different error thrown from the same site must still surface, so the catch cannot widen into the fail-open shape this milestone exists to prevent.
- AC-STE-520.14: Sibling-surface parity for the clauses AC.2, AC.6, AC.7, AC.9 and AC.11 place: each is asserted present on `skills/deliver/SKILL.md` and consistent with `docs/deliver-reference.md`, mutation-verified in both directions.

## Technical Design

The two paths differ in where the identity comes from, not in how the name is built. The resume path has a confirmed record and takes the name from it, which is what makes an operator edit at the gate actually reach the spawn — re-deriving at the spawn would discard the edit. The fresh-idea path has no record, because the gate that produces one classifies an identity the operator typed and a fresh run typed prose instead; there the identity is the milestone Phase 2 has just minted, and the same derivation runs on it.

Degrading cleanly rather than halting is the deliberate departure. The existing halt fires when `agent-toolkit:spawn-agent` is absent altogether, and it protects the pipeline's contract that work happens in a session the operator can watch and take over. Nothing about a milestone's correctness depends on the worker's name, so the same reasoning does not reach here, and applying it by analogy would turn a legibility feature into a reason a delivery run cannot start. Stating both halves at the surface is what stops the next reader from cargo-culting the halt.

The hard-exit is the one failure mode that can break a spawn outright, and it is why the argument is opt-in at the launch line rather than unconditional: passing it on an account whose organization disables remote control makes the CLI exit before the session starts. Opt-in keeps that away from operators who never ask for a bridge, but it does not protect the operator who confirms a name at the gate and turns out to be ineligible — so the retry in AC.9 covers exactly that case, once, without the argument. Reporting it apart from AC.6 matters because the remedies differ: one is an out-of-date spawning skill, the other an account entitlement, and an operator sent to upgrade a plugin over an organization policy will not get anywhere.

An underivable name is the third condition in this family, and it is the one this FR did not originally carry. STE-519 made the derivation load-bearing inside the decision record, so a repository whose basename the grammar rejects — a leading digit, a leading underscore — began refusing the whole record before the gate the operator would have used to drop the bridge. A naming problem halting the run hardest is the exact inversion of this milestone's posture, so it degrades like the other two rather than refusing. The catch stays narrow on purpose: widening it to swallow any error from that call site would be the fail-open shape, arriving one AC after the guard that was tightened to close it.

The advisory row is the orchestrator's own surface. The `closing_summary_capability_keys` probe that enforces literal-token directives globs `skills/{spec-write,gate-check,smoke-test}/SKILL.md` only, so this row does not enter that canonical set; it is pinned by reading the orchestrator surface directly instead.

## Testing

The two hand-offs are asserted separately, against the shipped surface, with the fresh-path clause mutation-verified — deleting it turns the assertion red. Asserting them together would let one satisfy both.

The opt-in property is asserted where it is actually decidable here. Nothing in this repository composes a launch line — the orchestrator delegates every spawn mechanic to the other plugin — so what this side can pin is the STATED contract: the surface says that supplying no name leaves the launch line byte-identical to today's. The behavioural half belongs to the repository that builds the line, and is pinned there. The degrade path is asserted to produce an advisory and to leave the run proceeding, and asserted NOT to produce a halt, since a test that only checks for the advisory would pass on an implementation that emitted one and halted anyway.

## Notes

The measurement behind this FR: `skills/deliver/SKILL.md:141` hands the spawning skill only the kickoff task text and the milestone identity; `agent-toolkit:spawn-agent` takes its name from its caller; and the bridge argument is opt-in by design. The supervisor's initial model held that naming was universal and only editability varied; that model was checked against the tree and refuted, and the scope was widened from the recommended resume-only option as a result. The reversal is recorded here rather than presented as the first answer.
