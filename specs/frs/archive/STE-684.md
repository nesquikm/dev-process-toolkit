# Bug type check runs before a new milestone Epic exists

## Summary

A bug filed in Jira must use an issue type that can sit under the milestone Epic.
The check for that type asks for the Epic key.
On a run that creates a new milestone, that Epic exists only after it is created.
The check must run before any tracker write, so it cannot have the key yet.
This fix makes the key optional and runs the check before the Epic is created.

## Requirement

### Steps to reproduce

1. In a Jira project, run spec-write with the bug flag for an FR that needs a new milestone.
2. Reach the bug type check, which the skill orders before any tracker write; the milestone Epic is not minted yet.
3. Run `bun run plugins/dev-process-toolkit/adapters/_shared/src/bug_tracker_type.ts jira <listing.json> Bug` with no Epic key, because none exists.

### Expected

The check grades the issue type and prints it, or refuses with no tracker write.

### Actual

The front door prints its usage line and exits 2. The only way through is to mint the Epic first, a tracker write before the check.

## Acceptance Criteria

- AC-STE-684.1: Regression: `tests/m_0cac80-ste-684-bug-type-before-epic.test.ts › the jira front door grades a type with no epic key` fails before the fix and passes after it.
- AC-STE-684.2: `checkBugTrackerType({ mode: "jira", issueType, listing })` with no `epicKey` runs every Jira check; its parent refusal names "the new milestone Epic" and its Context line carries `epic=(new)`; with a key, every output is byte-identical to today.
- AC-STE-684.3: The front door accepts `jira <listing.json> <issueType> [<epicKey>]`.
- AC-STE-684.4: `skills/spec-write/SKILL.md` and `docs/resolver-entry.md` order the `--bug` check before the milestone Epic mint on a new-milestone run, passing the key only when the milestone already exists; `skills/spec-write/SKILL.md` stays under its line cap.
- AC-STE-684.5: Making the key required again reddens at least one test.
- AC-STE-684.6: `bun test` from `plugins/dev-process-toolkit` reports 0 failures, and its skip identities equal the trunk baseline by name.

## Technical Design

### Root cause

The front door in `bug_tracker_type.ts` exits on a Jira call with no `epicKey`, and the skill prose places the check "before the draft gate", which on a new-milestone run comes after the Epic mint. The level-0, non-subtask rule does not depend on which Epic, so the key only labels the message.

## Testing

Front door and in-process cases with and without a key, for an absent type, a subtask type and a good type.

## Notes

A low finding from the M_7384cf review that was left unfixed.

An empty `epicKey` counts as no key: the message names the new milestone Epic and the Context line carries `epic=(new)`, never a bare `epic=`.

## Implementation notes

- AC-STE-684.5 mutation battery, 2026-10-21: making the key required again reddened 4 tests and labelling the new Epic with an empty key reddened 5, all in `tests/m_0cac80-ste-684-bug-type-before-epic.test.ts`.
- `skills/spec-write/SKILL.md` stays at 357 lines under its 358-line cap; both doc edits extend existing lines.

- SKILL.md shows `[<epicKey>]` on the combined `<jira|linear>` form, and the front door ignores a fourth argument on Linear without a warning — harmless; resolver-entry.md splits the two forms
