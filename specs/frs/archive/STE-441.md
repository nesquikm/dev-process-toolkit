# Re-key probe #73 grandfathering from filename shape to git-introduction provenance

## Summary

Probe seventy-three scopes its tracker-less requirement to the output range of the minting helper and grandfathers everything outside that range. The carve-out is sound for the purpose it was written for, which is letting existing tracker-less projects upgrade without a forced migration. The gap is that it is keyed on filename shape alone.

Nothing in the current check distinguishes a plan that predates minted identities from one created moments ago on a path where minting is mandatory. A freshly mis-named milestone is byte-identical to a legitimately legacy one, so it passes green permanently. The invariant is unenforceable for exactly the new milestones the probe exists to protect, which is what the reported incident demonstrates.

This FR replaces the shape heuristic with a provenance signal, and turns the cases where evidence is inconclusive into a visible advisory the operator can clear rather than a silent pass.

## Requirement

The probe must distinguish a newly created mis-named tracker-less plan from a genuinely legacy one, fail the gate on the former, stay silent on the latter, and surface an advisory rather than a silent pass when the evidence is inconclusive. Genuinely legacy plans must continue to require no consumer action, preserving the upgrade-safety property the current carve-out provides.

## Technical Design

The provenance query is a single `git log --diff-filter=A -1 --format=%aI -- <path>` invocation per candidate plan, run through `execFileSync` with the project root as cwd. This mirrors how probe twenty-two and probe thirty already shell out, so no new dependency posture is introduced. Only sequential plans under `mode: none` are queried, which bounds the cost to the small set the carve-out currently covers.

The untracked case is the one worth calling out, because it is both unambiguous and the most valuable. A plan file that git does not track cannot predate anything; it was written by the current session. Classifying it `fresh` means the probe catches a mis-named plan at the moment the producer writes it, before it is ever committed, which is the earliest possible signal and the cheapest possible repair.

Per-violation severity is a change to this module's public shape. The module currently exports a single `PLAN_IDENTITY_MODE_CONDITIONAL_SEVERITY` constant that the gate reads for the whole report. Advisory rows require the severity to travel with the violation instead. The precedent is `MilestoneGateRoutedViolation`, which already carries a per-violation `severity` field, so the gate-side consumer shape is established.

The exemption reads `kind`, extending the vocabulary `/setup` already writes rather than introducing a second key. Both existing readers of that field compare against the literal `scaffolding` — `plan_only_archival.ts` for plan-only archival eligibility and `tracker_local_reconciliation_drift.ts` for orphan suppression — so a new value is inert to them by construction and neither needs to change.

Vacuity on non-git projects is deliberate and matches the two sibling probes. A consumer without git has no provenance to read, and failing them would be the forced migration this design exists to avoid.

## Testing

The fixture in AC-STE-441.7 is the centrepiece and is built as a real temporary git repository, not a mock. Two plans are committed with controlled author dates straddling `MINT_EPOCH`, which is the only way to exercise the classification honestly. A third case covers the untracked plan, and a fourth removes the git directory entirely to assert vacuity.

The `undecidable` path is produced by committing a plan and then severing the introducing commit's loose object, so `git log --diff-filter=A` cannot reach it.

**Corrected during implementation (`contradicts`, rationale only — the ACs are unaffected).** This was specified as "the shallow-clone condition without needing a clone." It is not. Verified empirically against git 2.55: in a shallow clone `git log --diff-filter=A -1 --format=%aI -- <path>` returns the *boundary* commit's date rather than failing, so a genuinely legacy plan in a shallow clone classifies **`fresh`** and fails the gate — the exact outcome § Notes claims the advisory prevents. The severed-object fixture is a real `undecidable` producer; a shallow clone is not. `kind: legacy` remains the operator's remedy for both, so the shipped behavior is safe, but the advisory does **not** shield shallow-clone CI the way the original prose asserted. Also note the discriminator this forces: staged-but-never-committed and severed-history are indistinguishable to `ls-files` + `git log`; only `git cat-file -e HEAD:<path>` separates `fresh` from `undecidable`.

AC-STE-441.8 is verified by running the suite. Any test still asserting that a sequential tracker-less plan passes unconditionally will fail, and that failure is the signal to retire it rather than a regression to repair.

The bidirectional and duplicate-token assertions in AC-STE-441.9 are existing tests and must remain green unmodified. If they need changing, the change has gone wider than intended.

## Notes

This FR does not remove the grandfathering. It re-keys it from a signal that cannot distinguish the two cases to one that can. Genuinely legacy plans in existing tracker-less consumer projects stay green with no action required, which was the property the original carve-out was protecting and remains a hard constraint here.

The advisory disposition is a deliberate softening at exactly one point: a git repository that cannot answer the provenance query — the introducing commit's object is severed or pruned, or git itself refused (missing binary, corrupt index). Failing there would turn the gate red on plans the operator has no way to date. Passing silently would restore the blind spot this FR exists to close. The advisory is the only disposition that is neither, and `kind: legacy` gives the operator a way to clear it permanently.

**Rewritten during implementation.** This paragraph originally argued the advisory from a shallow-clone rationale, which § Testing above retracts as factually wrong — a shallow clone answers the query with its boundary commit rather than failing, so it classifies `fresh` and goes red; it never reaches the advisory. The advisory's real constituency is the severed/pruned/broken-git case. Shallow-clone CI in a tracker-less consumer with legacy sequential plans still needs `kind: legacy`, and probe #73's shipped entry now says so explicitly rather than claiming a protection that does not exist.

One consequence worth recording because it nearly shipped as a forced migration: the introducing-commit query must be **rename-aware**. `git log --diff-filter=A` scoped to a single path stops at a rename, and `/spec-archive` and `/implement` Phase 4 archive every plan they close with `git mv` — so the un-followed query re-dated each archived legacy plan to its archive commit, classified it `fresh`, and failed it. The implementation takes the earlier of the plain and `--follow` answers, so a rename can only make a plan look older, never newer.

Adding no new probe is a real saving. Registering one would move the documented count from 74 to 75 across roughly seven test files including meta-pins that assert other test files contain those literals. Editing probe #73 in place avoids that entirely.

## Implementation notes

- The FR's original § Testing and § Notes both argued from a shallow-clone rationale that is factually wrong — a shallow clone answers the provenance query with its boundary commit rather than failing, so a legacy plan there classifies `fresh` and goes RED; it never reaches the advisory. Both sections were corrected in place, and probe #73's shipped entry now states the real behavior with `kind: legacy` as the remedy. Shallow-clone CI in a tracker-less consumer with legacy sequential plans still needs that declaration.
- The provenance query had to be made rename-aware or this FR would have shipped as a forced migration: `/spec-archive` and `/implement` Phase 4 archive by `git mv`, and an un-followed `git log --diff-filter=A` re-dated every archived legacy plan to its archive commit. `git log --follow` is NOT the fix — it resolves renames by content similarity and template-shaped plan files clear the default threshold, so it laundered a genuinely fresh plan to `legacy`. Renames are hopped explicitly, one commit's diff at a time.
- Cost: up to four `execFileSync` spawns per sequential plan per gate run. Acceptable for the small carve-out set today, but the upgrading tracker-less project this exists to serve is exactly the one likely to hold many `M<N>` plans — a single batched `git log --name-only` pass would collapse it if that ever bites.
- A project root nested inside a git repository (a monorepo package with no `.git` of its own) classifies every plan `legacy` silently. This matches the two sibling probes that shell out to git, so it is consistent rather than novel, but it is a permanent blind spot; `git rev-parse --show-toplevel` would close it.
