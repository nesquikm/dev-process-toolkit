# A retro priority order in the settings file

## Summary

The trend ranks its numbers by what the project cares about most.
A new setting holds that order as three words: waste, tokens and time.
The loader accepts only those three words, each exactly once.
An upgrade step writes the default order into a moved settings file.
Setup writes the default order too, so a new project starts current.

## Requirement

`retro.priority` holds an order of waste, tokens and time, each used exactly once; it reads as waste, tokens, time when absent, and `/upgrade` writes that default.

## Acceptance Criteria

- AC-STE-775.1: `retro.priority` must list `waste`, `tokens` and `time`, each exactly once, in any order. Any other value throws `SettingsShapeError` naming `retro.priority`. The key joins the `retro` closed set and `docs/settings-reference.md`.
- AC-STE-775.2: `project_settings.ts get retro` answers `priority: [waste, tokens, time]` when the key is absent.
- AC-STE-775.3: Migration entry `retro-priority-default` adds `priority: [waste, tokens, time]` under `retro` in a moved `specs/settings.yaml` that lacks it. The preview shows the change before it is applied, and a second run changes nothing. On a tree that has not moved, the step is skipped and names the reason.
- AC-STE-775.4: Both writers that create a new `specs/settings.yaml` — `/setup` and the `settings-file` move — write `retro: { priority: [waste, tokens, time] }` into it, so a freshly created settings file is current and the `retro-priority-default` step does not apply to it. One `/upgrade` of a legacy tree therefore leaves nothing pending, and a second run changes nothing. Each writer's output differs from v3.5.0 only by that `retro` section. (Amended 2026-11-13 by operator ruling: the original "writes no retro section" left every fresh tree with a pending upgrade; the move is covered for the same reason.)
- AC-STE-775.5: Removing the closed-set check or the migration's already-present guard turns at least one named test red.
- AC-STE-775.6: `bun test` from `plugins/dev-process-toolkit` reports 0 failures, and its skip identities equal the trunk baseline by name.

## Technical Design

The `retro` section's closed key set gains `priority`, validated as a permutation of the constant `RETRO_METRICS`. The default lives beside that constant, so the loader, the migration and the trend read one value. The migration is a registry entry under `adapters/_shared/src/migrations/entries/` that writes through `writeProjectSettings`, so CRLF and comments survive.

## Testing

Loader tests over every permutation and each refused shape; the migration walked twice over a moved tree, once over an unmoved tree and once over a tree that already has the key; a `/setup` output check that the only new section is the retro default.

## Notes

The order is read by the trend in this milestone and by the proposals in milestone B.

## Implementation notes

- retro_priority_default.ts apply: a writeProjectSettings throw (e.g. `retro: 5`) escapes instead of becoming a Refusing: summary — round-2 low severity; fails loudly, and the loader already refuses that shape
- retro_priority_default.ts: the already-present guard counts `priority: null` as present, so such a file is never repaired — the loader refuses the file with SettingsShapeError naming retro.priority, so it is not silent
