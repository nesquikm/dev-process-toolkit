# Setup declares a shared container and leaves a stop paragraph older clients obey

## Summary

A repository joins a shared tracker container through setup, which records its ownership label and the minimum toolkit version, and writes a short plain-language stop paragraph into the project instructions.
Older toolkit versions cannot run the new guards, but every session reads those instructions, so the paragraph tells them to leave the tickets alone.
The gate check fails when the declaration, the paragraph or the running version disagree.
Re-pointing a repository keeps its declaration.

## Requirement

Measured at HEAD `ac1f3cb`:

- No code writes `repo_tag`. `docs/setup-reference.md` step 7b.6 writes the tracker sub-section "with `project:`", and § 0c routes `/setup --resume-tracker-binding` through the same prose write, with no contract that the other keys of the sub-section survive. An LLM that rewrites the block after `repo_tag`, `default_labels` or `jira_issue_type` were added may drop them silently.
- The rules that apply in a shared container are those of the OLDEST client writing into it. Measured: nothing in the toolkit writes a plugin version pin or checks a minimum version (0 hits); `glacy-app-fe` enables the plugin with no version and `glacy-app-be` does not enable it at all. Every Epic a teammate's client minted after v2.82.0 (GF-89, GF-92, GF-94) lacks the label v2.82.0 writes, so older clients are writing today. Clients below v2.81.0 read `/spec-write` § 0.5 as "tracker-only orphans auto-import" — in a shared container, every sibling ticket, and the import ends in an outward sync.
- Every session loads CLAUDE.md whatever its plugin version, so a paragraph there is the one instruction an older client is guaranteed to read.
- `specs/requirements.md:246` still lists "cross-repo … ticket binding — one repo, one tracker project" as out of scope.

**Readiness preconditions (documented, not new machinery).** A shared container counts as ready only when (1) every participating repository declares `repo_tag`, shown by probe #25 green in each one, and (2) every sharing repository raises `min_dpt_version` after each programme release. Protection is one-sided until (1) holds: an undeclared writer is not refused, and is surfaced only by the untagged tickets STE-605 reports. Floors are per repository, so (2) is a step each repository takes. `docs/setup-reference.md` states both where the shared question is asked.

### 1. The writer

A new `adapters/_shared/src/setup/tracker_binding_write.ts` exports `writeTrackerSubsection(claudeMdPath, adapter, { project, team?, shared? })` — `shared` is `{ repoTag }`, `"unshare"`, or absent — and `renderSharedTrackerSentinel({ adapter, project, repoTag, minDptVersion })`. Its front door is `bun run adapters/_shared/src/setup/tracker_binding_write.ts <projectRoot> <jira|linear> --project <p> [--team <t>] [--shared <tag> | --unshare]`, which prints a unified diff of what it wrote and exits 1 with the file unchanged on any refusal.

- It owns exactly: `project`, `team`, `repo_tag`, `min_dpt_version`, the tag's entry in `default_labels`, and the stop paragraph. Every other line of the sub-section — `jira_issue_type`, other labels, unknown free-form keys, blank lines — is preserved byte-for-byte and in order.
- Declaring writes `repo_tag`, appends the tag to `default_labels` (creating the key when absent, never duplicating an entry), writes `min_dpt_version` as the running version read by STE-602, and inserts the paragraph once, as the last block of the sub-section.
- Re-running with the same inputs and the same running version is a byte-identical no-op. A declare re-run from a newer running version raises the floor to it and re-renders the paragraph: this is how a sharing repository raises its floor after a release. The writer never lowers an existing floor.
- A project change (a repoint) keeps the declaration and RE-RENDERS the paragraph for the new project, because the paragraph names the project and probe #25 compares it byte-for-byte; a kept stale paragraph would red probe #25 on the written tree.
- `--unshare` removes `repo_tag`, `min_dpt_version` and the paragraph, leaves `default_labels` as found, and says so on stdout.
- The written file is read back through `readWorkspaceBinding`; a read-back refusal restores the original bytes and refuses with the reader's text.
- Sequencing trap: the floor written is the running version, and the reader refuses a floor below `FIRST_GATED_DPT_VERSION`. Until the release commit lands, this repository's own manifest (2.86.0) is below that constant, so a declaration made from the development tree refuses at read-back. That refusal is correct, and is asserted: every declaring fixture carries a manifest at or above the constant, and one fixture at 2.86.0 refuses with the floor class.
- It refuses, leaving the file byte-identical: no `## Task Tracking` section; `mode: none`; an unreadable file; an invalid tag.

### 2. The stop paragraph

A blockquote inside the tracker sub-section whose first line is the fixed marker `> **Shared tracker container — stop before any tracker write.**`. Only `renderSharedTrackerSentinel` produces it, deterministically. It must:

- name the container kind and the project, the repository's tag and the floor;
- tell any client whose dev-process-toolkit plugin is older than the floor, or that cannot tell its version, not to create, edit, transition, comment on, link or import any ticket in this container, and to ask the operator to upgrade instead;
- tell people who file tickets by hand to add the tag to tickets that belong to this repository, and say that every other repository writing into this container must declare its own tag, because an untagged writer is not refused, only reported;
- say that newer clients enforce the same rule in code.

No line of it matches the reader's key pattern, and it adds no line at the top level of `## Task Tracking`, where any non-`key:` line is a canonical-keys violation.

### 3. The setup flow

- `docs/setup-reference.md` step 7b.6 gains the shared question, asked with `AskUserQuestion` after the project is chosen: "Does any other repository create tickets in this same project?", proposing the repository directory's basename, kebab-cased, as the tag. `--shared-tracker=<tag>` pre-bakes the answer. Under a non-tty stdin with no flag the answer is "not shared" — today's behaviour — recorded as the audit row `step:7b (shared_tracker) value:"none" reason:"default applied"`. The step orders the writer with `bun run`.
- § 0c routes every write of `--resume-tracker-binding` through the same writer, so a repoint preserves every key it does not own and re-renders the paragraph, and asks the shared question when no declaration exists. A same-container run of the flag is how an existing repository declares. The routing sentence leaves room for M_685ff6's repoint command, which checks its rows first and bypasses them for a resume (`project:` absent or `<deferred>`) or a same-project declaration, reaching this writer either way. Repoint precondition #2 becomes "probe #25 is green in every participating repository".
- `skills/setup/SKILL.md` needs no edit — its step 7b already points at the reference section. If an edit proves necessary it is in place: the file stays at 358 split-lines and 17 STE tokens.

### 4. Gate probe #25

`runTaskTrackingWorkspaceBindingPresentProbe` (`adapters/_shared/src/task_tracking_workspace_binding_present.ts`) gains three legs, applied only when the sub-section declares a tag:

- (a) a reader refusal is a violation carrying the reader's own text;
- (b) the paragraph absent, present twice, or not byte-equal to `renderSharedTrackerSentinel` for the declared tag and floor is a violation — so a raised floor without a re-rendered paragraph is red;
- (c) the running version below the floor is a violation naming both versions.

A paragraph present with no declaration is also a violation (a stale paragraph after a hand edit). With no declaration and no paragraph, the probe's output is byte-identical to today's. The module gains an `import.meta.main` front door, and `skills/gate-check/SKILL.md` row 25 (line 80) is rewritten in place to run it and name the three legs; the file stays at 356 split-lines and 87 STE tokens.

### 5. The product's own contract

`specs/requirements.md:246` is rewritten to say shared tracker containers are supported under this declaration. Line 259 (`specs/` stays per-repository) is unchanged.

## Technical Design

The writer is a line editor over the one sub-section it owns: it splits lines into owned and foreign, edits only owned ones, and re-reads the result through the declaration reader before the bytes land. The paragraph is rendered, never typed, so the probe can compare bytes and a raised floor forces a re-render. Probe 25 keeps its decision path for undeclared files and adds three legs behind the declaration. The paragraph lives inside the tracker sub-section because top-level prose under Task Tracking is itself a gate failure.

## Notes

The paragraph is the only lever on a client that predates the gate, and it is plain language because only the model reads it. Declaring is opt-in: a non-tty setup defaults to not shared, which is today's behaviour. Untagged tickets from undeclared writers are surfaced by STE-605.
