# The repoint has a real instrument and written preconditions

## Summary

Five separate surfaces tell an operator to re-point a tracker binding with a flag that the setup skill has no branch for, and the alternative they name refuses the job twice over. Anyone following the instructions arrives nowhere. The flag gets a dispatch branch, the surfaces stop contradicting it, and the preconditions for re-pointing a project are written down where there is room for them.

## Requirement

The resume-tracker-binding flag must dispatch to a real contract, every shipped surface naming it must describe that same instrument, and the conditions under which a repoint is safe must be documented and checkable.

## Acceptance Criteria

- AC-STE-581.1: `skills/setup/SKILL.md` routes `--resume-tracker-binding` to the workspace-binding resume contract regardless of `## Task Tracking` presence, and stops offering `--migrate` for that job. `grep -c "resume-tracker-binding"` on that file goes from 1 at HEAD to at least 2, and the file measures exactly 358 split-lines — the edit is an in-place one-line rewrite, not an added section.
- AC-STE-581.2: Every shipped site naming the flag describes the same instrument, and none offers `--migrate` as an equivalent. There are five such sites, not the three the approved draft named. What is invariant is the FILE SET, not the raw line count: the enumerating grep, scoped to the plugin directory and excluding tests, still names exactly those FOUR files and no fifth — the five sites span four files, because `skills/spec-write/SKILL.md` holds two of them — with `docs/setup-reference.md`, `adapters/_shared/src/tracker_config_proposal.ts` and `skills/spec-write/SKILL.md` frozen at one, one and two occurrences. Only `skills/setup/SKILL.md`'s count moves, because AC.1 requires it to — so the total is `5 + (setupCount - 1)`, never a hard 5. Each site is asserted separately rather than through one roll-up: a fix landing on three of five is precisely the failure this FR exists to prevent.
- AC-STE-581.3: `docs/setup-reference.md` carries the full contract — probe, write, skip every other step, and refuse rather than partially write when the tracker MCP is unreachable — plus a "Repoint preconditions" section with at least seven numbered rows. The rows name at least: no active FRs mid-flight, one reconciled tracker site and MCP server, the repo tag declared in every participating repo and present in the forwarded default labels, a surveyed milestone-label collision, and a status vocabulary that is hand-written as the union of both containers BEFORE the flip and re-checked AFTER it — because the flag's own step 7f run rewrites that file from the newly-bound container alone.
- AC-STE-581.4: The flag's name survives in both `skills/setup/SKILL.md` and `docs/setup-reference.md`. The existing cross-reference suite requires it, and deleting the flag is the naive way to "fix a contradiction"; this FR makes it real instead. The sibling assertions are unbroken: `--docs` stays absent, `--template` and `--migrate` stay present.
- AC-STE-581.5: The docs state exactly which steps the flag runs and which it does not — step 7b's workspace-binding probe and write and, in tracker mode, step 7f's tracker-config write, every other step skipped — and correct the false equivalence: `--migrate` refuses when the mode does not change and skips steps 1 through 8, which is where step 7f lives, so it cannot perform a repoint. `grep -c "Materially equivalent"` on the reference doc returns 0, paired with `step 7f` appearing at least once. The remedy string in `adapters/_shared/src/tracker_config_proposal.ts` keeps its literal `Remedy:` prefix, which is the only thing asserted on it.
- AC-STE-581.6: The repoint path obeys the first-action non-tty rule: under a non-interactive stdin the first tool call is an ask or a refusal, routed through the existing single-call arbiter at the `setup-socratic` gate site. No fourth gate site is introduced; the set is closed. Step 7f's five-outcome capability contract is unchanged and a repoint run that REACHES step 7f emits exactly one of its literal tokens. The qualifier is load-bearing: § 0c's own no-binding branch refuses before step 7f and emits none of the five.
- AC-STE-581.7: The docs state that the flag DOES re-run step 7f, and state that step 7f fetches statuses from the ACTIVE binding — after a repoint, the new container alone. They therefore state plainly that running the flag can CLOBBER a hand-written union vocabulary, and that the operator must re-check after the flip that the written statuses still cover the legacy container's, hand-merging the union when they do not. The reason is named, not asserted as a collision: archived FRs stay bound to the old container's tickets under the no-migration constraint, and the archive-side ticket-state probe reads their statuses through this same file, so a vocabulary written from the new container alone can strand every legacy binding as an unknown status. Whether the names actually collide is empirical per repo pair, so the docs order a check rather than assert an answer.

The remedy at `tracker_config_proposal.ts:211` fires from the MCP-unavailable branch, a FAILED 7f, and names this flag — so the flag must re-run 7f. Measured GB-versus-GF delta:

## Testing

Assert each of the five sites separately rather than through one roll-up, because a fix landing on three of five is the failure this FR exists to prevent. Pair the "Materially equivalent" absence assertion with a presence assertion on the corrected text. Assert the precondition rows by name, not by count alone — seven rows of the wrong content pass a count. Assert both split-line pins before and after, and re-run the module-reachability probe with `await`: the precondition list names no module path in an ordering sentence, and the config-proposal module has no front door.

## Notes

The precondition list records the milestone-label collision survey rather than solving it; that belongs to a later milestone. Naming it here is what keeps it from being assumed closed. The approved draft said the flag does not re-run the tracker-config write; the measured repoint requires it, so step 7f is in scope.

## Implementation notes

- Spec defect, caught by the test-writer and fixed before implementation: AC.1 and AC.2 were mutually unsatisfiable as first written. AC.1 orders the flag count in the setup skill from 1 to at least 2, which necessarily takes the tree-wide enumeration past 5, while AC.2 said it still returns exactly 5. AC.2 was rewritten around what is actually invariant — a closed FILE SET with three files frozen at fixed counts — and both sides are recorded in the plan.
- Deliberate reversal of the approved draft, recorded rather than applied silently: the draft said the flag does NOT re-run the tracker-config write. The remedy at `tracker_config_proposal.ts:211` fires from a FAILED step 7f and names this flag, so the flag must be able to re-run 7f or the remedy names an instrument that cannot recover the failure.
- Fixed in-flight: a sentence decided the status-collision question in the negative two sentences before stating it cannot be known in advance; a forecast that two named repos are about to share a project appeared in generic shipped docs, when this project own survey argued against that merge; three unmeasured universals over every probe were scoped to what was actually measured; the invisible-key and MCP-unreachable failures were lumped into one refusal clause; and the contract said nothing about a project with no binding to re-point, which section 0 routes here unconditionally.
- Advisory, open: for three of the five sites, describes-the-same-instrument is enforced as the line not naming the mode-switch flag plus a subject anchor. A future rewording that drifts the described instrument without naming that flag would pass.
