# STE-429: Give Phase 8 a scaffold-free workspace per in-scope skill {#STE-429}

## Summary

The first-turn phase runs after the canonical chain, against the same project that chain has already fully configured. That position makes a pass structurally unreachable for two of the four skills it tests.

On one leg both the setup and brainstorm children returned vacuous: they never asked, never structurally refused, and never scaffolded. The setup skill simply ran to completion and reported status, because there was nothing left for it to configure and therefore nothing to ask about. Its tool sequence contained no question and no in-scope write, and the tree stayed clean.

So the contract's signal is weaker than its pass-or-fail framing suggests. A skill that cannot reach the asking state in the position the driver runs it will never render a pass there, however correct its behavior — and a reader of the summary cannot tell that apart from a skill that was tested and behaved well.

## Requirement

Each in-scope Phase 8 skill MUST be exercised in a workspace state where entering the Socratic loop is actually reachable, so that a pass and a violation are distinguishable outcomes for every skill in the rotation.

Observed 2026-07-27 on the Jira leg:

- `/spec-write` returned `ok-refused askIndex=15` (rc=0) — a genuine pass, and evidence the STE-404 fence renders correctly under `-p`.
- `/setup` and `/brainstorm` both returned `vacuous askIndex=-1` (rc=3). The `/setup` child's tool sequence was `Skill, Bash×7, ToolSearch, mcp__atlassian__*` — no `AskUserQuestion`, no in-scope `Write`, tree clean.

Partially reproduces the 2026-07-20 "vacuous ×4" finding, with the notable improvement that `/spec-write` now renders a structured pass rather than a prose-only refusal.

Note this is distinct from the setup first-turn violation tracked in M116: on the Linear leg, against a *differently*-scaffolded project, the same skill produced a genuine violation. The two observations are consistent — what the skill does depends on what is left to do — which is precisely why the phase needs a controlled starting state.

## Acceptance Criteria

- AC-STE-429.1: Each in-scope Phase 8 skill runs against a workspace state in which its Socratic entry is reachable, rather than against the already-scaffolded chain output.
- AC-STE-429.2: For every in-scope skill, both a pass and a violation are achievable outcomes — a fixture demonstrates each skill can render `ok-asked` or `ok-refused` under correct behavior.
- AC-STE-429.3: A `vacuous` outcome is reported as an inconclusive result naming the skill, never folded into an aggregate pass.
- AC-STE-429.4: The phase's workspace preparation does not disturb the canonical chain's own test project or its captures.

## Technical Design

The straightforward shape is a scratch workspace per in-scope skill, prepared to the state that skill expects to act on — empty for setup, minimally scaffolded for the others — rather than reusing the chain's output directory.

That costs setup time per skill but buys a meaningful verdict, and the phase already spawns one child per skill so the marginal cost is a directory rather than a session.

AC-STE-429.4 matters because the phase currently runs inside the same test project the chain used; moving it out must not invalidate the chain captures the completeness check reads.

## Testing

- Per-skill fixtures per AC-STE-429.2 demonstrating a reachable pass.
- A rendering case per AC-STE-429.3 asserting an inconclusive result is named, not aggregated.
- An isolation assertion per AC-STE-429.4 that the chain's captures are untouched.

## Notes

Interacts with STE-419 rather than duplicating it. This FR is about the phase's ability to produce a meaningful verdict; STE-419 is about the setup skill's actual first-turn behavior. Both are needed: fixing the workspace without fixing the skill would turn a vacuous result into a violation, which is more honest but still failing.
