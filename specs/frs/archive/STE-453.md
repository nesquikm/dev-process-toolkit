# Narrow --dry-run prose to what ships and generalize the report shape to N legs

## Summary

The conformance driver documents a dry-run mode that returns canned per-leg findings by reading from a fixture directory. That directory does not exist anywhere in the repository, and the test named as its coverage never imports any code, never spawns anything, and asserts among other things that the skill mentions the test file's own name.

So the flag is a claim rather than a mechanism. The previous FR builds a real harness for the termination probes specifically; this one narrows the surrounding prose to describe exactly that and nothing more.

The honesty requirement is the substance here, not a tidying pass. Whatever remains uncovered after the harness lands — the aggregation pass, the cross-leg dedup, the report shape — must be named as prose-only in the skill body and in its rules, rather than left implied to be tested. An overstated claim of coverage is worse than an acknowledged gap, because it stops anyone from looking.

The report shape also carries a pairwise assumption in its own right, describing coverage as a two-element tracker list and its dedup as a walk from one named tracker to another.

## Requirement

Narrow the dry-run documentation to describe exactly what ships, name every remaining prose-only surface as such, and generalize the aggregated report past its two-leg assumption.

The measured state: the fixture directory the skill describes is absent from the repository, and `plugins/dev-process-toolkit/tests/conformance-loop-dry-run.test.ts` is 81 lines carrying no executable coverage of the mechanism it is named for.

## Acceptance Criteria

- AC-STE-453.1: The `--dry-run` prose in the conformance-loop skill describes only what ships. No claim of a fixture directory broader than what exists on disk survives anywhere in the skill. {#AC-STE-453.1}
- AC-STE-453.2: The aggregation pass, the cross-leg dedup and the report shape are explicitly named as prose-only — model judgment rather than algorithms — in both the skill body and its `## Rules` section. {#AC-STE-453.2}
- AC-STE-453.3: `tests/conformance-loop-dry-run.test.ts` no longer asserts that the skill cites the test file's own name, and carries the STE-452 executed-fence assertions instead. {#AC-STE-453.3}
- AC-STE-453.4: The aggregated report emits an N-way `legs:` list in place of the pairwise `tracker-coverage:` field. {#AC-STE-453.4}
- AC-STE-453.5: The dedup prose describes a registry-order walk scanning all later legs rather than a walk from one named tracker to another, and is explicitly labeled model judgment. {#AC-STE-453.5}
- AC-STE-453.6: **The `max-iterations` termination probe fails CLOSED on an unusable cap.** An absent, empty or non-numeric `MAX_ITERATIONS` is a FAILURE, never a permissive zero: the probe emits a named refusal and aborts **before the iteration proceeds**, rather than reaching `[ … -ge … ]` as a `test(1)` usage error whose non-zero status merely skips the branch. The guard uses the `case "${VAR}" in ''|*[!0-9]*)` shape this document already carries at the rc-collection gate and at the `green` probe's `HIGH_*` check — the established in-file pattern, not a new one. **A valid integer cap must be unaffected**, asserted by executing the fence across the boundary cases so a fail-open is not traded for a run that cannot start. {#AC-STE-453.6}

## Technical Design

AC.3 removes a self-referential assertion. A test asserting that the skill mentions the test's own filename is circular in the same way this milestone's other findings are circular: it cannot fail for any reason connected to the behavior it purports to cover.

AC.4 is a rename with a shape change, and the closing-summary columns derive from the leg set per STE-446, so the report's leg list should derive the same way rather than being restated.

AC.5 keeps the dedup as model judgment deliberately. Making it an algorithm is out of scope for this milestone; what is in scope is that the prose no longer implies otherwise and no longer hardcodes two named trackers into its description of the walk.

## Testing

Assertions on the narrowed prose, plus the rewritten dry-run test carrying the executed-fence coverage from STE-452.

The check that AC.1 and AC.2 actually landed is that a reader can no longer find a coverage claim in the skill that is not backed by an executing test. That is checkable by enumerating the skill's coverage claims and pairing each with its test.

Full gate green from the plugin root.

**AC.6 was not in the FR as authored.** The sweep required by AC.1/AC.2 found the `max-iterations` probe failing OPEN on a non-integer cap — `rc 0`, `STATUS` unset, the loop continues — and the implementing session recorded it as out of scope, on the correct ground that no AC authorized a behavioural change to a shipped fence.

So the failure mode of a malformed `--max-iterations` is an unbounded loop that keeps committing code — a materially worse consequence than any other finding in this milestone, including the ones that were fixed. Recording it in `follow-ups.md` while shipping a release whose headline is the elimination of fail-open surfaces would have been indefensible.

The AC is added here rather than the fix being smuggled in under AC.3, on the same mechanism this milestone used twice before — AC-STE-446.6, and the AC added to STE-452 by a separate docs commit. **An unauthorized fix and an unfixed defect are both worse than an authorized fix.** The AC addition ships as its own `docs(specs)` commit, ahead of the implementation.

## Implementation notes

### The final-FR sweep — what it found

The FR's § Testing prescribes the check: enumerate the skill's coverage claims and pair each with its test. Done over all 999 lines and every `conformance-loop-*.test.ts`. **Ten claims are backed by nothing, one EXECUTED claim is overstated, and four assertions are satisfied by prose saying the opposite of what they check.** AC.1 and AC.2 reach five; the rest are recorded at `specs/notes/follow-ups.md` § 0k, each with the RED-producing input that does *not* work.

The single worst row: **the `max-iterations` probe failed open.** Executed — `MAX_ITERATIONS=""` or `abc` with `ITER=3` gave `[: integer expression expected`, `STATUS` unset, **rc 0, loop continues**. That is the loop's only spending control, and it was the last surviving instance in this driver of the class STE-452 AC.5 removed from the `green` probe.

**Recorded as out of scope, then FIXED under AC-STE-453.6 after the operator widened the scope** (see § Scope amendment). The deferral was correct on process and wrong on consequence: under `--auto-fix` an unbounded loop spawns children that commit. The test written to keep the deferral honest — asserting the diagnostic was *emitted*, so a future fix would redden it — did exactly its job one turn later, against the session that wrote it.

### The measured state was worse than the FR described

The FR says `--dry-run` reads from a fixture directory that does not exist. Measured: the flag has **no operative behaviour at all**. It appears in exactly four places — the `argument-hint`, its bullet, the unknown-flag remedy and one `## Rules` bullet — and **no branch, fence or conditional anywhere in the document reads it**. So there was no narrower true description to fall back to; the honest prose had to say the flag is inert.

Retiring it was measured and rejected: 12 red predicates across 9 tests in 2 files, all enforcing shipped AC-STE-224.2. The flag stays, its semantics go. The unsatisfiable pair is recorded in `specs/plan/M121.md` § Recorded conflict — AC-STE-224.2 vs AC-STE-453.1.

### The trap in AC.1, which is the reason zero assertions were carried forward

**The honest prose is written in exactly the vocabulary the old pins searched for.** `/--dry-run[\s\S]{0,500}mock/i` and `/--dry-run[\s\S]{0,500}(canned|fixture|without invoking real)/i` are both satisfied by a sentence saying *"there is no mock, no canned findings and no fixture directory"*. Keeping either would have produced a green assertion whose subject had been deleted — the defect this milestone exists to remove, reached by doing the right thing to the documentation. Every one of the old file's ten assertions has this property or is circular; none survived.

### AC.4 was unfalsifiable as written, and a rename alone would have left it that way

Measured before changing anything: **rewriting the entire 34-line report template reddened ZERO assertions.** The three `tracker-coverage:` regexes are written `tracker-coverage:\s*\[`, which cannot cross the `**` in the template's `**tracker-coverage:**`; they resolved only to the dedup prose. So the field the AC names was pinned by nothing, and renaming it would have relocated an unbacked claim rather than removed one.

The new field is bound to the enum by `reportShapeLegs(loopDoc)`, exported **beside** `LEG_PROSE_SURFACES` and deliberately not registered in it — `m121-ste-446-leg-set-authority.test.ts` pins that registry at exactly five entries, and bumping it is the relaxation this milestone forbids. It takes document text, never a path (AC-STE-445.4).

### AC.6 — the fail-closed guard, and the probe bug that nearly hid it

The guard is the house shape, applied where the document already carried it twice:

```bash
case "${MAX_ITERATIONS:-}" in ''|*[!0-9]*)
  echo "/conformance-loop: --max-iterations is '…' — not a plain integer, so the loop's only spending control is unusable and it refuses to iterate rather than run uncapped. Aborting."
  exit 1
  ;;
esac
```

It **refuses** rather than normalizing, because unlike `RC_*` there is no safe value to substitute for a cap the operator meant to set.

**Executed, before and after, across every input pair.** Valid caps are unaffected: `ITER=1 MAX=3` → unset; `3/3`, `4/3`, `1/1` → `max-iterations`; all rc 0, identical to the pre-guard measurements. Invalid caps now refuse at rc 1 with the value named: empty, `abc`, and `"3 "` (trailing whitespace — genuinely not a plain integer, and the rc gate treats it the same way).

**Four mutations, all RED, each discriminating:**

| # | Mutation | Result |
|---|---|---|
| M24 | the guard is deleted (the shipped fail-open, restored) | **RED** — 5, incl. the witness |
| M25 | the empty-string arm is dropped, non-digit class kept | **RED** — 2, exactly the empty-cap case |
| M26 | the guard rejects everything, valid caps included | **RED** — 6, **caught by the regression floor** |
| M27 | the refusal prints but does not `exit` | **RED** — 3 |

M26 is the one worth keeping: it is the obvious way to overshoot this fix, and the regression floor exists precisely to catch trading a fail-open for a run that cannot start.

**A tooling finding that nearly produced three false results.** The first run of M25/M26/M27 reported **GREEN**, which reads as "the new AC.6 tests are vacuous". They were not — the *probes* were. Each used a first-occurrence `replace(find, repl, 1)` on anchors (`in ''|*[!0-9]*)`, `exit 1`) that **occur earlier in the document**, in the rc gate and the `green` probe, so all three mutated a different guard entirely while the byte-change check passed. Re-anchored to the fence region, the same three return 2, 6 and 3 RED. **§ 0b's "assert the mutation applied" is insufficient — it must be asserted to apply at the intended site**, and a codebase whose guards deliberately share one house shape makes first-occurrence anchors a trap by construction. Recorded at § 0k(m).
