# STE-420: Make driver abort verdicts machine-checkable when the exit code cannot carry them {#STE-420}

## Summary

Both drivers state that an abort must exit non-zero, and that a false green must never be reported in the exit code. That contract cannot be satisfied as written. The driver is a model running inside a command-line process, and a model has no way to set that process's exit status; the process returns zero for any session that finishes without a harness error, whatever verdict the model reached.

On the 2026-07-27 run both legs aborted and both exited zero. One of them printed its abort banner and stated in its own summary that it was exiting non-zero, while the file recording its actual exit status reads zero. The driver believed a thing about itself that was not true, and nothing in the pipeline contradicted it.

The consequence is that the parent's fail-fast check is dead code. It passed on a run where both legs aborted, and the truncation was caught only by a separate completeness check that happens to exist. Any consumer that trusts the exit status reads a false green.

## Requirement

The abort contract MUST rest on a signal the driver can actually emit. A parent MUST NOT be able to read a green result from a leg that aborted.

Observed 2026-07-27, verified directly rather than inferred:

- Jira leg final message begins `SMOKE-ABORT: incomplete grandchild chain (/implement + /spec-review never ran)` and its summary line reads `VERDICT: FAIL (rc=1)`. Its rc-file contains `0`.
- Linear leg declares `SMOKE-TEST FAIL` with 4 high findings. Its rc-file contains `0`.
- `/conformance-loop` Phase A's documented gate is `if RC != 0 … Aborting` — it did not fire.

Note the contract text is currently emphatic about this exact point (*"a loud banner is not sufficient, because rc is one of several corroborating signals the parent reads"*), which makes the gap a specification defect rather than an oversight: the prose demands something the runtime cannot provide.

Either the drivers stop claiming the exit code carries the verdict and the parent gates on a byte-checkable verdict artifact, or the spawn wrapper derives a real exit code from that artifact. This FR does not pre-commit to which.

## Acceptance Criteria

- AC-STE-420.1: A leg that aborts writes a machine-readable verdict artifact at a documented per-tracker path recording at minimum the outcome (`pass` / `fail` / `abort`) and the abort trigger.
- AC-STE-420.2: `/conformance-loop` Phase A treats a leg as failed when that artifact reports a non-pass outcome, **independently of** the collected exit code; a fixture with rc=0 plus an abort artifact aborts the iteration.
- AC-STE-420.3: A leg that completes its canonical chain cleanly writes a `pass` verdict artifact, and the same gate lets it through — the gate is non-vacuous in both directions.
- AC-STE-420.4: A missing verdict artifact after leg exit is treated as a failure, not as a pass, so a leg that dies before writing one cannot read as green.
- AC-STE-420.5: Every SKILL.md clause asserting that the abort "MUST exit non-zero" is either made true by the spawn wrapper or restated to name the artifact as the authoritative signal — no clause is left asserting an unsatisfiable guarantee.

## Technical Design

The spawn wrapper already brackets each leg in a brace group that captures the exit status to an rc-file. That same wrapper is the natural place to reconcile: after the leg exits, read the verdict artifact and, if it reports non-pass, write a non-zero value to the rc-file instead of the process status. That preserves every existing consumer of the rc-file — including the documented Phase A gate — while making the value mean what the contract says it means.

The artifact should be per-tracker scoped from the start, per STE-423, so a tandem partner cannot read or overwrite it.

The `/smoke-test` final-message self-check is the emit site: it already computes both abort triggers (incomplete chain, live pidfile) and is specified to run before any final message.

## Testing

- Unit coverage for the verdict-artifact reader: pass, fail, abort, malformed, and absent.
- A Phase A fixture pair proving non-vacuity: rc=0 with an abort artifact must fail the gate; rc=0 with a pass artifact must clear it.
- A regression fixture reproducing the 2026-07-27 shape — abort banner in the final message, rc-file containing zero — asserting the iteration aborts.

## Notes

This finding appears in neither per-tracker findings file. It was raised at the loop level during aggregation, when the Jira leg's self-reported exit status was checked against the rc-file it actually produced and the two disagreed. Recorded here because a driver's self-report is not evidence — the same lesson the capability-key finding teaches in STE-421.

## Implementation notes

- AC-STE-420.5 was satisfied additively: every "MUST exit non-zero" sentence is byte-unchanged and made true by rc reconciliation, because six meta-tests pin those sentences and one fails when more than one sentence in a clause matches an anchor role.
- The FR's Technical Design claim that the final-message self-check "already computes both abort triggers" was inaccurate — it computed only the live-pidfile trigger; the emitter now consumes chain-integrity findings as well.
