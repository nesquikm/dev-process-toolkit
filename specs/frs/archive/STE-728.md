# A retrospective can propose a settings change the operator must approve

## Summary

A retrospective often skips a rule because the project has not turned on the data it needs.
Today the operator must work out which setting to change by hand.
This lets the retrospective propose that one change, with the evidence that motivated it.
The change is applied only after an explicit yes from the operator.
It can only turn on a setting from a fixed list, so it never weakens a gate.

## Requirement

Operator rule, 2026-11-04: the toolkit's default behaviour does not change, and every optimization is a settings change the user approves after `/retro`. This FR is that approval path. It is the only path by which `/retro` changes a file other than its report.

### The proposable set

A new module `adapters/_shared/src/retro_proposal.ts` exports `PROPOSABLE_SETTINGS`, a closed table. Each row names one key, the one value it may propose, and the rule outcome that justifies it:

| Key | Proposed value | Proposed when |
|---|---|---|
| `tracking.token_stats.enabled` | `true` | `cost_per_changed_line` skipped, or the scope resolved to no session, with a reason naming `tracking.token_stats off` |
| `tracking.tool_calls.enabled` | `true` | a timeline rule skipped with a reason naming `tracking.tool_calls off` |
| `tracking.gate_outcomes.enabled` | `true` | `slow_gate_run` or `gate_rerun_unchanged_key` skipped with a reason naming `tracking.gate_outcomes off` |

Every proposed value turns a recording on. The table holds no gate, threshold, review or approval key, and no `false` value. The row shape is closed: a `tracking.<name>.enabled` key with the value `true`. A row outside that shape is refused when the module loads. M_fd9a03 widens the shape by one case in its own FR: STE-723 admits an `optimizations` knob from its `OPTIMIZATION_KNOBS` with the value `reuse`, and adds the one reuse row. Any other row needs its own FR.

### propose

`bun run retro_proposal.ts propose <projectRoot> <report-file>` is read-only. It reads the report through `parseRetroReport` (STE-719), the home through `settingsWriteSource`, and each row's current value through its own section read: `loadProjectSection(projectRoot, "tracking")` for the three `tracking` rows (v3.0.0 validates per section, so a malformed unrelated section does not hide a proposal). It prints nothing and exits 0 when no row applies, when every applicable key is already on, when the settings source is not `settings`, or when a section read it needs refuses. Otherwise it prints one `set <key>: <value>` line per row, one `because <rule id> <disposition>: <reason>` line per row, then `digest=sha256:<hex>`. When the `tracking.tool_calls.enabled` row is printed and `git check-ignore` does not report `.claude/settings.local.json` ignored, it also prints `add .gitignore: .claude/settings.local.json` before the digest. The digest covers `realpath(projectRoot)`, the settings file bytes, the `.gitignore` bytes and the printed lines. The root is in the digest because two worktrees of one repository on one branch hold byte-identical settings and `.gitignore` files: without it, an approval given for worktree A would admit `apply <worktree B> ...` (review 8, R8-2a). `apply` computes its digest over the realpath of its own root argument, so a digest printed for another tree never matches.

### apply

`bun run retro_proposal.ts apply <projectRoot> <report-file> <digest>` recomputes the proposal. A digest that no longer matches refuses in NFR-10 shape and writes nothing.

The approval is checked in code, not in prose (supervisor ruling 2026-11-04, for operator review). A model can call `apply` with a digest it read, so a digest alone proves nothing. Before any write, `apply` reads this session's transcript, located by `sessionTranscriptPath(CLAUDE_CODE_SESSION_ID, process.cwd())`, a new export of `find_current_session.ts`, the shipped module beside `defaultConfigDir` and `cwdToSlug`; it depends on no M_fd9a03 module. Claude Code names the transcript folder after the session's launch directory, not after the checkout root, so `cwdToSlug(projectRoot)` misses a session launched in a subdirectory or in another worktree of the same repository. `sessionTranscriptPath(sessionId, cwd, configDir = defaultConfigDir())` therefore looks for the file `<sessionId>.jsonl` under `<configDir>/projects/`: first in `cwdToSlug(cwd)`, then in the slug of each ancestor of `cwd`, nearest first, which covers a Bash call whose working directory sits below the launch directory; then, when none holds it, in every project folder, taking the file only when exactly one folder holds it. It returns `null` when no folder or more than one holds it, and when `sessionId` does not match `^[A-Za-z0-9-]{1,64}$`, so a crafted id cannot leave the projects folder. The file name is the session id itself, so whichever folder holds it holds this session's transcript. M_fd9a03's reuse front door (STE-724) locates its transcript through the same export. It reads records through `firstCopies` (`templates/hooks/_lib/session.ts`) and needs all three of these, in order:

1. A real propose. A Bash `tool_use` that `runsRetroProposal(command, "propose")` accepts: one plain `bun [run] <absolute path> propose ...` whose path realpaths to this module, read by the `bunInvocation` grammar `announcesGateReceipt` uses. So an `echo`, a `cd ... &&` chain or a same-named file elsewhere does not count. Its `tool_result` must hold the line `digest=<the given digest>`.
2. A real answer. After that result, an `AskUserQuestion` `tool_use` whose question text holds the same digest line and every other line the matched propose result printed (each `set ...`, `because ...` and `add .gitignore: ...` line, verbatim, each on a line of its own in the question text), and whose `tool_result` selects the option labelled exactly `Apply the shown change`. The verdict is the shipped `perQuestionConsent(questions, label, names, answer)` of `join_consent_ownership.ts`, the one per-question consent rule the tracker-write hook and the live grader already share, called with `label` `Apply the shown change` and `names` true only for a question holding `digest=<the given digest>` and every printed line of that propose result. The lines are read from the propose `tool_result` text, never recomputed, and `apply` also checks that its recomputed proposal prints the same lines. A question that names the digest but leaves out or rewrites one printed line is no approval, so the question cannot describe a different change from the one the digest covers (review 8, R8-2b). Only its answer lookup is new: an exported `askAnswerTo(record, block, question)` in `retro_proposal.ts` with the two arms of `answerTo` in `templates/hooks/_lib/hooks/pre-tracker-write-gate.ts`, read in that order: the record's `toolUseResult.answers[question]`, else the harness sentence `"<question>"="<answer>"` in the `tool_result` text. It carries a `Twin:` comment naming that hook function, which is not edited. An `is_error` result, a result naming another question, or a typed answer other than the exact label is no approval; the `Adopt` typed-answer arm of `perQuestionConsent` cannot fire, since the label is not `Adopt <KEY>`.
3. Not yet used. The approval is consumed, and `apply` refuses, when any of these holds:
   - Receipt. This session's receipt store (`readSessionReceipts(realpath(projectRoot), CLAUDE_CODE_SESSION_ID)`, `tracker_receipts.ts`) holds a `kind: "retro-apply"` receipt whose `evidence.answer` is the `uuid` of the approving answer record. `apply` writes that receipt itself, through `writeReceipt`, after the approval verifies and before its first write (below), so consumption holds whatever command form ran the earlier `apply`.
   - Recorded call. Any Bash `tool_use` whose command text contains `retro_proposal` and the digest's hex has a `tool_result` recorded after that answer. This match is deliberately broad, unlike step 1: a `cd <root> && bun run <abs>/retro_proposal.ts apply ...` chain, an `echo` prefix or any other form counts. Step 1 is positive evidence, where a loose match would admit a forgery; this is negative evidence, where a loose match costs at most one re-ask.
   - Consumption line. Any `tool_result` recorded after that answer holds the line `retro-apply: consumed digest=<the given digest>`, which `apply` prints, fixed, right after it writes its receipt (spec review 9, m9-1). This arm reads the call's output, not its command text, so it holds where the recorded-call arm goes blind: an `apply` whose digest came from a shell variable or a file, or that ran through a symlinked path. The receipt arm in turn holds where a transcript arm cannot see, and the two transcript arms hold where the receipt arm goes blind: after `git clean -fdx` deleted `.dpt/`, or in a `--fork-session` whose new session id reads another receipt store. Reading `retro-apply` receipts across sessions by answer uuid is not done here; it is a possible later hardening.

   One approval admits one `apply`, whatever that call's outcome; a retry needs a new question. Deleting the receipt is the same tamper class as forging the transcript, and the recorded-call match still holds after it (review 8, R8-1).

The running `apply` call itself is not looked for (review 7, R7-2). Claude Code writes a lone call's `tool_use` line, and the first call's line of a message, only after that call's tool has run and its result is recorded (archived STE-641, § Re-cut, measured on Claude Code 2.1.283), so a check requiring that line refused every live approval. The STE-641 re-cut rule, which grades an absent own line as placed after every recorded line, needs the gated call's `tool_use_id`; a hook payload carries it, and a Bash child process does not, so `apply` cannot tell its own line from another `apply`'s. The step is dropped rather than re-cut, and nothing it guarded is lost:

- Order. The process runs now, so every recorded line precedes it. The order the approval needs reduces to steps 1 and 2: the propose result, then the answer.
- Forgery. Writing an `apply` line proves nothing, so dropping the check admits nothing new; the approval still needs a real propose and a real answer. The residual is the one the tracker-write hook shares: a model that writes the session transcript itself can forge both.
- Reuse. The digest covers the settings file bytes, and a successful `apply` changes them, so the same digest can never match again on that tree. Step 3 covers the remaining case, a tree restored to the approved bytes: the earlier `apply`'s consumption receipt, or its recorded result in any command form, consumes the approval. A Bash line with no recorded result is either this call or a sibling of its own message still running; it does not consume the approval through the recorded-call arm, though a sibling that has already written its receipt does.
- Residual, named: two `apply` calls in one assistant message that both read the receipt store before either writes its receipt both pass step 3. Each writes only the approved, digest-matched change to the approved root, so the operator's approval still bounds every byte written.
- Residual, named (spec review 9, m9-1): in that same race, one call's rollback can undo its sibling's write. If the second call's `register` refuses after the first call's writes landed, it restores the bytes it read before its own writes, which may be the pre-approval bytes, so the first call's approved change is undone. The tree is left at bytes the operator saw before the proposal, never at bytes they did not approve.

A missing transcript (`sessionTranscriptPath` returning `null`), an unset session id, a missing step, a step out of order, another digest, another root, a question missing a printed line, a consumed approval or another label refuses in NFR-10 shape and writes nothing. This is stronger than the `/upgrade` rail, whose approval lives in skill prose. That matters here, because `apply` is a second model-callable writer of `NEW_KEYS` keys, beside the closed `set` verb of STE-710.

On a verified approval it first consumes the approval: it writes the one `retro-apply` receipt through `writeReceipt(realpath(projectRoot), { kind: "retro-apply", adapter: null, container: null, subject: "dev-process-toolkit:retro", decision: "apply", evidence: { answer, digest } })`, where `answer` is the approving answer record's `uuid`. A refused receipt write refuses `apply` in NFR-10 shape before any other write. The receipt is never rolled back: a refused `apply` still consumes its approval (review 7). It lives under `.dpt/ledger/receipts/<session id>/`, which the `ledger/` rule of `.dpt/.gitignore` keeps ignored; `writeReceipt` creates `.dpt/.gitignore` when absent. No hook or gate reads a `retro-apply` receipt: `gateReceiptEvidence` grades only the `gate` kind.

It then runs in this order:

1. Check. For the `tracking.tool_calls.enabled` row, call `checkRegisterPreconditions(root, { settingOn: true })` (STE-716), so the check sees the setting as the next step will leave it. A not-ignored refusal is cleared only by a printed `add .gitignore:` line. Any other refusal stops `apply` in NFR-10 shape before any write.
2. Write each row's key through `writeProjectSettings` (STE-710). The writer validates the whole merged file before it writes, so a malformed section anywhere in the file refuses `apply` here, before any byte is written, and the rollback below has nothing to restore. The writer rewrites CLAUDE.md only when the binding stub's render changes; no proposable key enters the stub, so `apply` never writes CLAUDE.md, the `## Project Settings` pointer line included.
3. Append the printed `.gitignore` line, when one was printed, to `<projectRoot>/.gitignore`, creating the file if absent. This is the only `.gitignore` edit, and it is part of the diff the operator approved.
4. For the `tracking.tool_calls.enabled` row, call `register`. If it refuses or throws, restore the settings file, `.gitignore` and `.claude/settings.local.json` to their prior bytes, deleting any of them that did not exist before, and refuse.

Apart from that consumption receipt, `apply` writes nothing else and never commits.

### The gate

`skills/retro/SKILL.md` runs `propose` after printing the rule table. When it prints, the skill asks its own `AskUserQuestion`. The question text repeats every line `propose` printed, each on its own line: every `set ...`, `because ...` and `add .gitignore: ...` line, then the `digest=` line. `apply` refuses a question that leaves one out. Its two options are `Apply the shown change` and `Leave settings unchanged`, the default. The question follows the `requires_explicit_approval` rail of `docs/upgrade-reference.md`: the auto-approve marker never answers it. A driven run, or a run without an interactive operator, prints `settings proposal not applied — run /dev-process-toolkit:retro to review it` and never calls `apply`. Only an explicit approval calls `apply`. The skill says what follows a refused `apply`, in this sentence: `A refused apply consumes the approval: fix the cause, then re-run propose and ask again.`

`retro.ts` never imports this module, and the report schema is unchanged.

## Technical Design

The proposal is derived from the saved report, never from a second evaluation, so it can only cite what the report already says.

The table is closed and holds only turn-on values for recording keys, plus the one reuse knob. A proposal therefore cannot reach a gate.

The digest binds the approval to the tree and the bytes the operator saw, the ignore line included. A settings change in between makes the apply refuse rather than write something unseen.

Capture registration rides the same approval, because the key alone records nothing. The approval is read back from the transcript, so a model needs a real answer, unless it forges the transcript.
