# STE-430: Widen transient-failure retry and clear recurring gate noise {#STE-430}

## Summary

Three smaller defects share a theme: a healthy run is harder to read, and harder to complete, than it should be.

The retry-with-rollback path covers only one upstream failure signature and explicitly excludes every other error as needing operator inspection. On a headless leg there is no operator, so the strict reading aborts an otherwise-healthy run over a transient network blip. That is what happened here: the first setup attempt died mid-response having written nothing at all, and the driver had to choose between aborting the run and taking a documented deviation.

A commit issued in one particular shell form was denied even though the matching command pattern is present in the allow-list. The child recovered by re-issuing it differently and the commit landed, so the effect is cosmetic — but it costs turns and would strand a skill with no fallback.

And on any freshly bootstrapped project the gate emits a drift warning because the scaffolding milestone has no matching tracker milestone. That milestone has no ticket by design, so every new project starts life with a warning that means nothing.

## Requirement

A transient upstream failure with a provably clean tree MUST be recoverable on a headless leg, and a healthy freshly-bootstrapped project MUST produce no spurious gate warnings.

Observed 2026-07-27:

- **Retry budget.** `/setup` attempt 1 ran 76→32 turns then exited `is_error: true, terminal_reason: "api_error"` with the signature `API Error: Connection closed mid-response`, producing nothing: no `CLAUDE.md`, no `specs/` scaffold, no branch, no commit, `git status --porcelain` empty. STE-195's retry covers only `API Error: Stream idle timeout` and explicitly excludes other errors. The driver verified the tree was byte-identical to the pre-spawn commit, spent one retry, and attempt 2 completed normally. The surviving `dpt-smoke-linear-setup.attempt1.log` (649,627 bytes) corroborates.
- **Heredoc commit denial.** The `/setup` child's result carried one `permission_denials[]` entry for `git commit -q -F - <<'EOF' … EOF`. Command head is `git`, so it is correctly not a nested-spawn regression and the detector ignored it. The pattern matcher appears not to match the heredoc/stdin form.
- **Scaffolding-milestone drift.** `/gate-check` emitted warning-tier `#49 tracker_local_reconciliation_drift` with capability key `milestone_local_orphan`, because `specs/plan/M1.md` has no matching tracker milestone. M1 is `kind: scaffolding` and has no ticket by design. Gate still passes.

## Acceptance Criteria

- AC-STE-430.1: The retry path covers a connection-drop class failure whose post-hoc tree state is provably clean, so a headless leg recovers instead of aborting; the retry budget stays bounded at one.
- AC-STE-430.2: A failure whose tree state is **not** provably clean still does not auto-retry — the widening is gated on the clean-tree check, not on the error class alone.
- AC-STE-430.3: A commit issued in the heredoc/stdin form is permitted under the same allow-list entry that permits its non-heredoc equivalent, or the driver stops emitting that form.
- AC-STE-430.4: Probe #49 does not emit `milestone_local_orphan` for a milestone whose plan declares the scaffolding kind, and a freshly bootstrapped project produces a clean gate with no spurious drift row.
- AC-STE-430.5: The retry audit row records both attempts with their outcomes, so a widened retry remains visible in the run's audit trail rather than silently absorbed.

## Technical Design

AC-STE-430.2 is the load-bearing constraint. The reason STE-195 restricted itself to one signature is that a rollback is only safe when the failed attempt's side effects are known; widening on error class alone would reintroduce that risk. Gating on a verified-clean tree preserves the original reasoning while covering the observed case — which is exactly the check the driver performed by hand this run.

The scaffolding carve-out is a condition on the reconciler: read the plan's kind and skip the orphan comparison when it declares scaffolding.

The heredoc denial needs a diagnosis step before a fix — determine whether the matcher sees a different command string than expected, or whether the form itself is classified separately.

## Testing

- Retry-path cases per AC-STE-430.1 and the negative case per AC-STE-430.2 (dirty tree ⇒ no auto-retry).
- An audit-row assertion per AC-STE-430.5 covering both attempts.
- A permission case per AC-STE-430.3 covering both commit forms.
- A gate case per AC-STE-430.4 over a freshly bootstrapped project asserting the row is absent.

## Notes

Groups three low-and-medium items that all degrade run legibility. They are unrelated in mechanism, so the implementation may split them if that produces cleaner commits — the grouping is for tracking, not for a single change.

The retry deviation taken during the run was documented rather than silent, which is the behavior to preserve: whatever widening lands should still leave an audit trail.

**AC-STE-430.3 — the observed defect was under-described, and the fix's reach is narrower than this FR implies (recorded at implementation).** Three corrections to the Observed bullet above, established from bytes during implementation and preserved in `tests/fixtures/permission-denials/setup-heredoc-commit-denial-2026-07-27.json`:

1. The command carried no `-q`; the recorded form is `git commit -F - <<'EOF'`. Head is `git`, as stated.
2. "The pattern matcher appears not to match the heredoc/stdin form" is not the mechanism. Under this repo's matcher model, a rule with no `:*` suffix is an **exact** rule matching only the literal string — so `Bash(git *)` matched *nothing*, and neither commit form was ever authorized. The prefix form `Bash(git:*)` covers both. The asymmetry between the two shapes is the whole defect, and it is larger than a heredoc edge case.
3. The escape hatch "or the driver stops emitting that form" is unsatisfiable: no driver and no skill in this repo emits `git commit -F -`. The form was the child model's own choice, so only the allow-list branch was available.

Two limits on the fix, both deliberate. The edit that closes the *observed* denial is the smoke scaffold's shift to the prefix form (landed under STE-426's shape work and pinned here). The edit made under this AC — `templates/settings.json` — has **no runtime consumer**: `/setup` derives a project's allow-list from `templates/permissions.json` via `canonicalAllowList`, and that file deliberately ships exact rules per an earlier self-modification finding, which under the same matcher model grant nothing. Every `/setup`-bootstrapped consumer project therefore still permits neither commit form. That is a real defect, covered by no AC in this milestone, and it is the follow-up this FR should spawn.

And note the interaction with STE-425's narrowing: wherever the inherited default permission mode is `auto`, the classifier — not the allow-list — decides each call, so a corrected entry is a corrected *policy artifact* rather than a guaranteed runtime fence. Both statements are true and they bound each other.
