# Probe #63 does not resolve ship stamps against a CHANGELOG the project never declared

## Summary

The ship check looks up each archived plan's release in the changelog.
Some projects keep no changelog, and their release files say so.
For them every archived plan failed, and nothing could fix it.
Now the lookup is skipped when no changelog is declared, and one note counts the skipped plans.
The stamp's own format is still checked.

## Requirement

When the project's declared release files hold no changelog-kind entry, probe #63 does not resolve shipped_in stamps against CHANGELOG headings and reports the skipped count as a note; every other leg behaves as today.

## Acceptance Criteria

- AC-STE-874.1: When the release files the project declares (`release.files` in `specs/settings.yaml`, or the legacy CLAUDE.md `## Release Files` block) are readable and hold no entry of kind `changelog`, probe #63 reports no violation for a well-formed `shipped_in: v<X.Y.Z>` stamp that has no matching CHANGELOG heading.
- AC-STE-874.2: In that case the report carries exactly one notes row naming how many stamps were not resolved and why: no changelog release file is declared. With zero such stamps, no row is shown.
- AC-STE-874.3: Regression: a fixture whose release files list only a non-changelog file and whose archived plan carries a stamp with no CHANGELOG heading passes. A paired fixture that declares a changelog-kind file and has the same missing heading still fails with `corrupt_stamp`.
- AC-STE-874.4: Unchanged: a malformed stamp still fails, as do unshipped debt and the `unreleased` stamp without `changelog_unversioned`. Parked plans, the release-surface agreement leg and the sibling leg are unchanged. Missing or unreadable release files keep today's behaviour.
- AC-STE-874.5: Every other reader of stamp-versus-CHANGELOG coherence that uses this probe's verdict, such as the resume classifier, agrees with the probe on the fixture in AC-STE-874.3.
- AC-STE-874.6: `bun test` from `plugins/dev-process-toolkit` reports 0 failures, and its skip identities equal the trunk baseline by name.

## Technical Design

Root cause: `runPlanShipCoherenceProbe` reads CHANGELOG headings and checks every stamp against them, never asking whether the project declares a changelog. The fix reads the declared release files through the existing release-config reader once per call. A readable list with no changelog kind skips the heading lookup and counts the stamp. A missing or unreadable list keeps the lookup. The note shares the probe's existing notes array.

## Testing

Fixture trees with settings-file and legacy release files, each with and without a changelog-kind entry, plus a malformed stamp and an unreadable release-files block.

## Notes

From a v3.11.0 consumer report. The consumer worked around it by rebuilding a CHANGELOG from archived plans.

## Implementation notes

- live_proof_gate.ts changelogHasRelease resolves a shipped_in stamp against CHANGELOG.md on its own and never asks whether a changelog is declared — it does not use probe #63's verdict, so it sits outside AC-STE-874.5; it grades this repository's own live-proof plans only
- The malformed-stamp remedy and the epic_close fallback remedy still tell a project with no declared changelog to match a CHANGELOG.md heading — wording only; the verdicts are right and the FR pins which commands fail, not their remedy text
- The gate-check skill's probe #63 entry does not mention the no-changelog condition or its notes row — four suites freeze that file line by line; admitting the edit is its own change and is listed as a follow-up
- An existing fixture in m141-ste-546-surface-agreement.test.ts now declares a changelog release file — it wrote a CHANGELOG.md while declaring json and regex only, which this FR now reads as no changelog declared; the test still drives the missing-heading path
