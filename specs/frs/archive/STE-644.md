# A container create needs a fresh, complete re-list of its project

## Summary

Two repositories sharing one tracker project could both create the same milestone container, because a decision from a stale listing stayed valid after the other repository created it.
Version 2.90.0 shipped that race as a named known defect and promised this fix next.
A container create is now permitted only after a recent, complete, correctly scoped re-list of the project, and a same-titled open container in it refuses the create by its key.

## Requirement

A container create is permitted only when the transcript records, after the permitting decision, a harness-recorded re-list of the project's containers that meets all four of these:

- **Canonical scope:** Jira `project = <P> AND issuetype = Epic`, or Linear `list_milestones` for the create's project.
- **Complete:** one page chain from an unpaged request to a proven-last page.
- **Field-complete:** every row carries the fields the check reads.
- **Fresh:** its last result is within 120 s of the gated call.

A same-titled open container in that listing refuses the create by its key. A Linear answer of exactly 50 rows never proves absence; only the previous FR's "Create `<title>`" consent permits that case. The hook still makes no tracker call; it grades what the harness recorded.

Covers A5 (medium). Retires KNOWN DEFECT D-4 of STE-616 ("a milestone create decided from a stale listing makes a duplicate container"), which the v2.90.0 release notes promised as the first FR of the next milestone. Per operator ruling R4, the D-4 bullet in `specs/frs/archive/STE-616.md` gains one clause, "Fixed in `STE-644` (v2.91.0)", and the shipped 2.90.0 CHANGELOG entry is not edited. Per ruling R3, there is no live-proof release gate; one Jira smoke leg runs after the merge as a non-gating check.

**Documented residuals, not closed:** a sibling's create landing inside the 120 s window; Jira search-index lag; and the operator's permission prompt, which Claude Code shows after PreToolUse permits, so approval time is outside any hook bound.

## Acceptance Criteria

- AC-STE-644.1: A container create exits 2 when its permitting create decision has no later, complete, canonical-scope container listing chain recorded in the transcript.
- AC-STE-644.2: A listing whose last result line is more than 120 s older than the gated tool_use line does not qualify (exit 2).
- AC-STE-644.3: A Jira listing whose JQL is not `project = <P> AND issuetype = Epic` (modulo whitespace, case, quoting and ORDER BY), or whose rows lack summary or status, does not qualify (exit 2).
- AC-STE-644.4: A listing chain that does not start from an unpaged request and end on a proven-last page does not qualify (exit 2).
- AC-STE-644.5: A qualifying listing holding an open container whose normalized title equals the create's title refuses the create (exit 2) and names that container's key.
- AC-STE-644.6: A qualifying listing with no such open container permits the create (exit 0).
- AC-STE-644.7: In the D-4 scenario with B re-listing after A's mint, on both Jira and Linear, the refusal names A's key, the double ends with exactly one container of that title, and B adds zero writes.
- AC-STE-644.8: A Linear listing of exactly 50 milestones never qualifies as proof of absence.

## Technical Design

The container-create gate gains one more condition, checked after the settled-create and consent checks once the permit is otherwise met. It looks for non-error Epic-search or milestone-list results whose first request follows the permitting decision, checks their scope against the canonical query, reads the page chain through the shared tracker-answer readers, requires the fields it reads on every row, and requires the chain's last result to be within 120 seconds of the gated call. A same-titled open container refuses by key; no qualifying re-list refuses with a re-list remedy. The live grader mirrors the requirement.

## Design detail

- **Where.** gateMilestoneCreate, after the settled check and the consent check, once the permit is otherwise met (~:1605-1606).
- **(i) Tool.** Non-error results of `mcp__*__searchJiraIssuesUsingJql` or `mcp__*__list_milestones` whose first request is announced after the permitting decision's line.
- **(ii) Scope.** Jira: `input.jql` normalises (collapse whitespace; keywords and field names case-insensitive; project optionally quoted; optional trailing ORDER BY) to the canonical JQL of `adapters/jira.md` (~:511, ~:676). A narrowed JQL (summary, status, key, created, labels, OR or NOT) does not qualify. Linear: `input.project` names the create's project (sameName).
- **(iii) Chain.** Read pages through `adapters/_shared/src/tracker_answer.ts`'s exported readers: readTrackerPage, chained the way readTrackerListing chains them (~:120-158). The first request carries no token, cursor or startAt; each later token equals the previous page's next; the final page is proven last. A single last page alone never proves absence. Exactly LINEAR_MILESTONE_WINDOW (50) rows never proves absence on Linear.
- **(iv) Fields.** Every Jira row carries `fields.summary` and `fields.status.statusCategory`, and its key carries the create's project prefix. Every Linear row carries a name. A row missing them disqualifies the listing; it is not skipped.
- **(v) Freshness.** `LISTING_FRESH_MS = 120_000` between the chain's last result line timestamp and the gated tool_use line timestamp, which the transcript-wait FR guarantees is present. A missing timestamp counts as not fresh.
- **Refusals.** An open same-title row (Jira statusCategory not done, or any Linear row, matched through normalizeMilestoneTitle in `milestone_token.ts` ~:197) names its key, remedy "join it: decide with --join-key `<KEY>` --sibling `<path>`; nothing is created". No qualifying re-list, remedy "list project `<P>`'s containers again after the decision with `project = <P> AND issuetype = Epic` (every page, with summary and status), and send the create within 120 s of that read".
- **Grader.** Mirror the re-list requirement in the milestone-create acceptance of `shared_tracker_live_grader.ts` (~:2383-2390).

## Implementation deviations

- **Underspecified — which recorded runs the grader holds to the re-list.** The committed live-proof bundles under `plugins/dev-process-toolkit/tests/fixtures/shared-tracker-live/` were recorded under hooks that never asked for a re-list, and the STE-618 suite re-grades them; mirroring the rule unconditionally would have flipped their verdicts. The grader therefore applies the re-list requirement only when the bundle's own recorded behaviour digest shows a hook source other than the committed pre-STE-644 ones (`hookDemandsRelist`, keyed on the recorded SHA-256 of `pre-tracker-write-gate.ts`); a bundle recording no hook source is held to it. Verified: all 13 committed bundles grade identically under the d7ae018 grader and the new one (5 pass, 8 fail), and removing the recorded hook hash flips every passing one.
- **Grader limits, recorded rather than closed.** A bundle stores projected rows and no next-page cursor, so the grader cannot check token continuity or row completeness (the hook does both); it uses the last page's call time for its result time, and judges an open Jira row by status name where the hook reads `statusCategory`.
- **A consented forbidden decision admits a full Linear window.** The hook accepts a 50-row `list_milestones` answer as a qualifying re-list only when the permitting decision was forbidden and its ``Create `<title>` `` consent was answered (the case STE-643 authorises); a same-title milestone in that window still refuses.
