# STE-418: Restore headless drivability of /spec-write under claude -p {#STE-418}

## Summary

The canonical smoke chain stops at its second step because the spec-writing skill cannot finish in a non-interactive session. The tool it needs to ask a clarifying question is not registered there, and the Socratic interview entry is unconditional with no safe default, so the skill correctly refuses rather than guessing.

The refusal itself is right. What is wrong is that nothing else is offered: there is now no sanctioned way for an autonomous driver to get through the interview at all. Because the two skills that follow both take a feature identifier that can never be allocated, three of the six canonical steps become unreachable and every fixture group downstream of them is blocked.

This is the keystone of the 2026-07-27 conformance run. Until it is closed, every future headless smoke or conformance run fails in exactly the same place, and the toolkit loses the end-to-end signal those runs exist to produce.

The fix must not reopen the bypass that was deliberately closed earlier this year. Pre-baked prose and autonomous-mode reminders must remain non-triggers; what is needed is a narrow, byte-checkable sanctioned path, not a softer fence.

## Requirement

`/spec-write` MUST be completable end-to-end in a non-tty `claude -p` child spawned by `/smoke-test`, without weakening the STE-270 / STE-404 Socratic Loop Contract for any caller that does not carry the sanctioned marker.

Observed 2026-07-27 at v2.56.0 on **both** legs: `/spec-write` exited `subtype: success` after ~13 turns having done nothing — `specs/frs/` empty, tree clean, still on trunk, and zero tracker writes (confirmed via `mcp__linear__list_issues` on the smoke project and a JQL over the Jira run window). The child emitted the canonical `RequiresInputRefusedError` with capability key `requires_input_refused`, reporting that `AskUserQuestion` is absent from the session tool set. Both legs verified that absence with an independent minimal probe rather than trusting the child's self-report.

This is a **regression in headless drivability**, not a newly-introduced refusal: the 2026-07-24 M101 validation drove `/setup` + `/spec-write` grandchildren under `-p` successfully at v2.55.0.

The scope of this FR is the sanctioned path plus its fences. It does **not** change the interactive tty flow, and it does **not** relax the first-turn contract for unmarked callers.

## Technical Design

The decision surface already exists and is deterministic: `check_marker_runtime.ts` byte-greps the invoking prompt body and prints `PRESENT` / `ABSENT`, and `requireOrRefuse(...)` routes the three-branch outcome. What is missing is a documented answer source for the interview questions themselves when the marker is present and no human is reachable.

Two candidate shapes, to be settled during implementation:

1. **Marker-scoped pre-baked answer block.** The driver supplies interview answers in a structured, byte-identifiable block inside the same prompt body that carries the marker. The skill consumes answers only from that block, only when the marker is present. Unmarked prose is never an answer source, which preserves the STE-404 fence by construction.
2. **Sanctioned non-interactive interview transport.** The interview is emitted in a machine-readable form the driver can answer in one round trip.

Shape 1 is the smaller change and composes with the existing marker gate; shape 2 is more faithful to the Socratic intent. The FR does not pre-commit — the AC set constrains behavior, not mechanism.

Note the interaction with STE-419: `/setup` currently resolves the same interview from pre-baked prose with no marker at all. Whatever mechanism lands here should be the one `/setup` is moved onto, so the two skills stop disagreeing about what an absent ask tool means.
