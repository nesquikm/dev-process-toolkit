# An opt-in capture hook records each Bash and Skill call as a privacy-safe row

## Summary

The session log cannot say what the working tree looked like when a call ran.
This adds an opt-in hook that writes one small row for each Bash or Skill call.
Rows carry a call class, a toolkit skill name, content hashes and counts.
They never carry command text, file paths, the working directory or branch names.
Only a user's approved opt-in registers the hook, so a default install runs nothing new.
No gate reads its rows.

## Requirement

Timestamps and error flags come from the transcript (STE-717). A live hook is justified only for what the transcript cannot hold: the tree state at call time, the staged diff size at a commit, and rows that outlive transcript cleanup. This FR adds that hook and nothing more. Where it says "per D<n>", it implements the branch the STE-714 decision table names. If D6 answers no, this FR stops before /implement and goes back to the operator.

### Setting

`specs/settings.yaml`, read through the M_94e6f7 settings loader:

```yaml
tracking:
  tool_calls: { enabled: false }   # enabled: true | false; absent means false
```

`loadProjectSettings` (`project_settings.ts`, M_94e6f7) gains `tool_calls` (closed key set `{enabled}`, the same shape as `token_stats`) in the closed key set of `tracking`; an `enabled` value outside `true`/`false` throws `SettingsShapeError`. A legacy-only or settings-less tree reads `false`, since no legacy home carries the key; the CLAUDE.md binding stub that M_94e6f7 generates holds no `tracking` key either. `/setup` writes no `tool_calls` key, and no migration does. `docs/settings-reference.md` documents the key, its type, its default and "no legacy home". The hook treats every read error as off.

Loader wiring, in the shape STE-715 gives `tracking.gate_outcomes`: `settingsKeyOrder("tracking")` gains `tool_calls` after `gate_outcomes`, `settingsKeyOrder("tracking.tool_calls")` returns `["enabled"]`, `NEW_KEYS` gains `"tracking.tool_calls"`, `defaults()` and the legacy `tracking` view gain `tool_calls: { enabled: false }`, and the `tracking` validator adds `checkEnabledMap(tr, "tracking", "tool_calls")`. The AC-STE-706.12 test's `MAPPING` gains `"tracking.tool_calls": { kind: "new", fr: "STE-716", note: "no legacy home" }` and `LEAF_BLOCKS` gains the path. Every read goes through `loadProjectSection(root, "tracking")`, wrapped by a `toolCallsSwitchOn(projectRoot)` export that reads any refusal as off.

The `tracking` defaults merge of STE-715 (AC-STE-715.21) fills `tool_calls` too: an absent `tool_calls` in a parsed `tracking` map reads `{ enabled: false }`, after `gate_outcomes` in `settingsKeyOrder("tracking")` order, and every v3.0.0 key reads as on v3.0.0. The AC-STE-706.1 literal at `tests/m_94e6f7-ste-706-settings-loader.test.ts:362` moves again, to `toEqual({ ...BASE.tracking, gate_outcomes: { enabled: false }, tool_calls: { enabled: false } })`, its comment gaining `; Amended by AC-STE-716.24 (M_7bc805): tool_calls too.`

Interaction with the v3.0.0 loader rules (supervisor note for the rebase onto 6c62b32c):

- Per-section validation. The key shares `tracking` with `token_stats`, so a malformed `tool_calls` value refuses every `tracking` read, the token ledger's switch included, as a malformed `token_stats` does on v3.0.0. Only a user who wrote the key reaches that state. The hook, the migration's detect and `status` read such a refusal as off. A malformed key in any other section never reaches them, since `loadProjectSection` validates only `tracking`.
- The migrated-tree rule. On a tree whose CLAUDE.md `## Project Settings` section holds the pointer line (`isMigratedTree`), the loader is strict: a settings file that cannot be read, lacks `min_dpt_version` or sits beside a keyed legacy home refuses, and capture reads off. On any other tree, a `specs/settings.yaml` with no column-0 `min_dpt_version:` is the project's own file (`isForeignSettingsFile`), and the loader ignores it. The shell guard's `grep -qs 'tool_calls'` and the hook's first `specs/settings.yaml` check are byte prefilters only. A foreign file that happens to hold `tool_calls` passes them, and the loader still reads capture off. The migration's detect reads the setting through the same loader, never by grep, so a foreign or refused file never registers capture.
- No FR of this milestone writes CLAUDE.md. The `## Project Settings` pointer line and the binding stub stay as `/setup` and `/upgrade` wrote them.

### Registration (supervisor ruling 2026-11-04, for operator review)

Operator rule, 2026-11-04: no behaviour change by default. So `hooks/hooks.json` gains no entry and stays byte-identical, and a default install starts no new hook process. The hook is registered only when a user turns capture on through an approved settings change, and the registration follows the setting.

Where it lives: `<projectRoot>/.claude/settings.local.json`, Claude Code's per-user project settings file, which is never committed. `${CLAUDE_PLUGIN_ROOT}` does not expand outside a plugin's own `hooks/hooks.json` (`docs/hooks-reference.md` § Override pattern). So the entry names the plugin by absolute path, and that path names the user's home, so it may never reach a committed file.

The entry: under `hooks.PreToolUse` and `hooks.PostToolUse`, one group per event with the D4 matcher shape, each holding one command entry with `"timeout": 2` (seconds). Its command is the render below, byte for byte:

```
[ -f "$CLAUDE_PROJECT_DIR/specs/settings.yaml" ] && grep -qs 'tool_calls' "$CLAUDE_PROJECT_DIR/specs/settings.yaml" && grep -qsF '"<pluginRoot>"' '<installedPlugins>' && grep -qsF '"version": "<version>"' '<pluginRoot>/.claude-plugin/plugin.json' && [ -x '<pluginRoot>/templates/hooks/process/tool-call-capture.sh' ] && CLAUDE_PLUGIN_ROOT='<pluginRoot>' exec '<pluginRoot>/templates/hooks/process/tool-call-capture.sh' '<installedPlugins>'; exit 0
```

`<pluginRoot>` is the real path of the running plugin root at registration, `<version>` is the version its `.claude-plugin/plugin.json` declares then, and `<installedPlugins>` is the absolute path of Claude Code's installed-plugins record, `<config dir>/plugins/installed_plugins.json`. The command is `renderCaptureHookCommand({ pluginRoot, version, installedPlugins })`.

Stale paths. Claude Code keeps an orphaned plugin version directory for up to 14 days after an update, so a path check alone would keep running the old version's capture code. The shell guard is a cheap prefilter: it runs Bun only while `<pluginRoot>` appears anywhere in that record and that root's manifest still names `<version>`. That alone proves little. The record lists one entry per scope, so after this project updates, another project may still pin the old root, and the grep still passes.

So the hook itself pins the root, before any dynamic import. It reads the record from its first argument with Node built-ins and takes the `dev-process-toolkit@` entry whose `projectPath` is the checkout's real path, else the entry with `scope: "user"`. It goes on only when that entry's `installPath`, as a real path, equals its own plugin root, resolved from the entry module's location. Otherwise it exits 0 silently and writes nothing. So after an update, the old code stops at the first event, even while another project lists the old root. `status` then reports `stale` or `guard: fail`, and probe #69 lists the re-registration as pending when the command is stale. The record is Claude Code's own file; if its format changes, or it cannot be read, both checks fail closed, and capture stops rather than run unpinned code. The guard also exits 0 silently when the settings file lacks the key. An entry is a capture entry when its command contains `templates/hooks/process/tool-call-capture.sh` (`isCaptureHookCommand`).

New module `adapters/_shared/src/capture_registration.ts`, with a front door of three verbs:

- `status <root>` is read-only. It prints `setting: on|off`, `registration: none|current|stale` and `guard: pass|fail`. Stale means an entry exists but its command differs from the render for the running plugin root and version, or the setting is off. `guard` evaluates both checks for the running plugin root: the shell guard's, and the hook's record-entry check for this checkout. So a current registration that would never write a row shows `guard: fail` rather than looking healthy.
- `register <root>` refuses in NFR-10 shape, exit 1, writing nothing, when the setting is off, when `.claude/settings.local.json` is tracked by git, when `git check-ignore` does not report it ignored, or when it exists but holds no JSON object. The not-ignored refusal's remedy names the exact line to add, `.claude/settings.local.json`, and the file to add it to, `<projectRoot>/.gitignore`. Claude Code adds a global ignore rule only when it writes that file itself, and `DPT_GITIGNORE_BODY` does not list it, so a fresh repository may lack the rule. Otherwise it adds or replaces the capture entries. Every other key and entry stays deep-equal and in its original order. A second run leaves the file byte-identical.
- `unregister <root>` removes only capture entries, plus the matcher groups their removal leaves empty. It writes nothing when no capture entry exists.

Neither write verb touches the `env` key or `.claude/settings.json`.

The module also exports `checkRegisterPreconditions(root, { settingOn })`, pure and read-only, returning the refusals `register` would raise with the setting taken as `settingOn` instead of read. `register` calls it with the setting it reads. STE-728 calls it with `settingOn: true` before its first write, so its check sees the state after its own settings write.

Who registers, always behind an explicit approval:

1. `retro_proposal.ts apply` (STE-728) calls `register` in the same approved act that turns `tracking.tool_calls.enabled` on, after the ordered precondition check that FR defines.
2. A migration entry `capture-registration` in `migrations/entries/capture_registration.ts`, `introduced_in: "3.1.0"`, `kind: "script"`, `requires_explicit_approval: true`, registered after `settings-file`. Its pure detect applies when the setting is on and the registration is `none` or `stale` (apply registers), or when the setting is off and a capture entry exists (apply unregisters). The setting is read from the working-tree `specs/settings.yaml`, the bytes the shell guard reads. A key removed or set false locally, committed or not, reads off: the entry is already inert, and apply removes only the user's own entry. Neither arm ever edits, restores or commits the settings file. `/upgrade` previews it and asks its own approval; the auto-approve marker never applies it.

Removal: no toolkit command turns the key off. When a user deletes the key, the shell guard makes the entry inert at once, with no Bun start. Probe #69 then lists `capture-registration` as pending, and `/upgrade` removes the entry on approval. On a default tree, with no key and no entry, the migration never applies, so probe #69 shows nothing new. Claude Code's settings watcher picks up a registration or removal, at the latest at the next session start; `docs/hooks-reference.md` says so.

### Per repository switch, per user registration (supervisor ruling 2026-11-04, for operator review)

The switch is per repository: `tracking.tool_calls` lives in the committed settings file, so turning it on reaches every clone through git. Registration is per user: each user's own `.claude/settings.local.json`, written only behind that user's own approval. A teammate who pulls an enabled setting and never approved gets exactly one warn-only pending `capture-registration` row from probe #69, and nothing else. That row also moves their `/gate-check` verdict line from GATE PASSED to GATE PASSED WITH NOTES, as any warn-only row does. No hook runs for them, no file changes, and nothing prompts outside `/upgrade`. The STE-717 fold also stays off for them, since it needs a current registration. This row and its verdict effect are the one allowed difference the M_7bc805 defaults gate lists for capture.

### Fast path

The wrapper is `exec bun run "${CLAUDE_PLUGIN_ROOT}/templates/hooks/_lib/hooks/tool-call-capture.ts" "$@"`, like `session-token-ledger.sh`. The entry module statically imports only Node built-ins and `../session.ts` (`parseHookPayload`, and `findCheckoutRoot`, a new export). `findCheckoutRoot(payload.cwd)` walks up to the nearest directory holding a `.git` entry, with no child process. It splits and joins the path with string operations and probes with `existsSync` from the file's existing `node:fs` import: `session.ts` keeps its one import, which `tests/m_85e846-review-hs1-announcement-provenance.test.ts:572` pins (one `node:fs` specifier, one `ImportKeyword`), so it imports neither `node:path` nor any other module (review 7, m7-1). When that directory has no `specs/settings.yaml`, it exits 0 at once. Next it runs the record-entry check above, and exits 0 when that fails. Only then does it load `project_settings.ts` by dynamic `import()`, read the flag, and exit 0 when off. `dpt_paths.ts`, `commit_target_repo.ts`, `pr_target_repo.ts`, `gate_receipt.ts` and `gate_reuse_key.ts` are loaded by dynamic `import()` only after the flag reads true. A flag-off run spawns no child process.

### Row — schema `tool-call/v1`, one JSON line per hook event

Path: `toolCallLedgerPath(root, sessionId)` = `<root>/.dpt/ledger/tool-calls/<sessionId>.jsonl`, a new composer in `dpt_paths.ts` that calls the module-private `assertPathSafeSessionId` inside it, as the shipped session composers do. `docs/layout-reference.md` names it in its "is composed by" composer list, which `tests/m132-cross-fr-hardening.test.ts:816` requires to name every `dpt_paths.ts` export (review 7, R7-1e). Under `ledger/`, so `DPT_GITIGNORE_BODY` (`setup/dpt_gitignore.ts`) needs no new rule.

Closed key set:

| Key | Value |
|---|---|
| `schema` | `"tool-call/v1"` |
| `event` | `"pre"` or `"post"` |
| `tool_use_id` | the payload's `tool_use_id`, or `null` |
| `tool` | `"Bash"` or `"Skill"` |
| `class` | Bash: `commit` (`resolveCommitTargetFromPayload(payload).isCommit`), `pr-create` (`resolvePrTargetFromPayload(payload).isPr`), `gate-receipt` (`announcesGateReceipt` or `runsGateOutcome`, both from `gate_receipt.ts`), else `other`. Skill: `skill` |
| `skill` | Skill calls only: the skill name when it starts with `dev-process-toolkit:`, else `"other"`; `null` for Bash |
| `ts` | the hook's own ISO wall-clock |
| `tree` | `worktreeDigest` of the session checkout, only on `pre` of a `commit` Bash call and on both events of a Skill call; else `null` |
| `diff` | `{ files, insertions, deletions }` summed from `git diff --cached --numstat` in the commit's resolved target checkout, only on `pre` of a `commit` call; `null` when unresolvable or otherwise |
| `scope` | `"main"`, or `"fork"` when D1 found a distinguishing field and it marks the call |
| `exit_code` | present only when D2 found one: the PostToolUse Bash exit code |

The session id lives in the file name only. No raw `tool_input`, `tool_response`, `description`, `cwd`, path or branch is written.

### Behaviour

Every run exits 0 with empty stdout and stderr: flag off, malformed stdin, no checkout, unsafe session id, a git failure or an unwritable ledger all write nothing and stay silent. Each row is one `appendFileSync` of one line.

## Technical Design

The plugin registers nothing. A user's approved opt-in writes one entry per event into their own project-local settings, so the default install and every teammate who never opts in run no hook.

The registered command guards in shell first, so a project without the key costs one shell and no Bun. The hook then checks this project's record entry, then the flag, then loads heavy imports. Classification reuses the gates' commit and pull request front doors. Git work runs only on commit and Skill calls. Failure is silent, and the timeline reader counts the gaps.

Registration drift is a migration, so /upgrade's explicit approval governs both adding and removing the entry.
