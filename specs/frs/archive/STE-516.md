# A stage cannot report a spawn it did not perform

## Summary

The pipeline emits a chain in which some steps are marked to run in a spawned worker, and nothing anywhere checks that a spawn happened. On the run that prompted this work, every ceremony step ran in the orchestrating session, the report looked exactly like a healthy one, and the discrepancy was invisible.

A stage now carries a receipt naming the worker it spawned, and the receipt names a handle it did not compose. The handle is resolved through the spawning tool's own ownership check, which answers whether the live session behind a ledger row is the one this run started. That check is run before the report is emitted, and anything other than a clean resolution is a named halt rather than a report.

The check is fail-closed on purpose. The failure being prevented is a report that looks correct, so a check that quietly passes when it cannot run reproduces exactly the defect it was added to catch.

## Requirement

A stage that emits worker-placement steps carries a receipt for a spawn proven to belong to this run, or it halts.

## Acceptance Criteria

- AC-STE-516.1: The hand-off block's `summary` section carries a receipt line with a fixed prefix and a fixed field order, naming the spawned worker's handle.
- AC-STE-516.2: The handle is the one the spawning tool returned and the ownership check resolved. A handle composed, reconstructed or inferred by the reporting stage is not acceptable and is asserted against by a fixture carrying a well-formed but composed handle, which is rejected.
- AC-STE-516.3: The hand-off verifier grades the `summary` section for the first time: a stage whose chain contained worker-placement steps and whose summary carries no receipt is graded not-ok, with a reason naming the missing receipt.
- AC-STE-516.4: Before the block is emitted, the handle is resolved through the spawning tool's ownership check. Exit zero is the only outcome that permits emission.
- AC-STE-516.5: Every non-zero outcome is a named halt, not a warning and not a skip. No exit code falls through to emission. The two the design named get their own remedies — no ledger row, and no ownership sidecar — and every other non-zero outcome halts with the exit code quoted in the message.
- AC-STE-516.6: The one legitimate configuration that cannot run the check — the spawning tool installed with no terminal host to spawn into — is a named halt carrying its own remedy, never a guarded pass. Pre-flight probes for the tool, never for the host, so this case cannot be detected earlier.
- AC-STE-516.7: A chain containing no worker-placement steps requires no receipt and is graded exactly as today, asserted byte-identically rather than assumed.
- AC-STE-516.8: The receipt costs one line and the block stays inside its shipped line cap, asserted against the cap read from its exported constant rather than a retyped number.
- AC-STE-516.9: The three shipped hand-off fixtures carry the receipt and still grade as they did — the well-formed one accepted, both mutations rejected — so the fixture group is green in the same milestone that makes the receipt required.
- AC-STE-516.10: Guards are mutation-verified: a removed receipt, a composed handle, and each non-zero ownership outcome in turn each produce a distinct failure, and none of them produces a pass.

## Technical Design

The receipt rides the `summary` section rather than becoming a ninth section. Three things make that structurally free. Section detection matches keys anchored at the start of a line, so an indented list item is invisible to it. The order check filters to known keys, so extra content is tolerated. And `summary` has no content check at all today — which means adding the receipt makes the verifier grade that section for the first time, strengthening the contract rather than straining it.

A ninth section would reopen a fixed section order this repository repaired one milestone ago, for a field that fits in a line.

AC.2 is the criterion that carries the weight. A handle the stage composed is narrated evidence, which is precisely what the evidence sections exist to eliminate. The ownership check is what makes the receipt unforgeable by an inline run: an inlined chain has no ledger row, so the check exits with no row and the run halts instead of reporting.

Fail-closed is stated as a criterion because the alternative is seductive. Every guard that cannot run has a plausible reason to pass anyway, and every one of them turns into a silent skip. The recorded lesson here is that a silent skip is worse than a loud failure, and two guards shipped fail-open one milestone ago.

The ownership contract carries more outcomes than the design enumerated. Beyond a clean resolve, a missing ledger row and a missing ownership sidecar, it also reports nothing live for the row, a live session that is not ours, and an ambiguous match — the last two documented as hard stops by the tool itself. Naming only three and letting the rest fall through would be the fail-open shape this FR exists to close, so every non-zero outcome halts.

The ledger path and the worker name are taken from what the spawning tool reported. This FR authors no spawn mechanics of its own and derives no ledger path, which would duplicate a host-dependent contract that the shipped criteria already forbid re-implementing.

## Testing

The verifier gets fixtures for a receipt present, a receipt absent with worker-placement steps in the chain, a composed handle, and a chain with no worker-placement steps at all.

The ownership check is exercised through an injected runner so each documented exit code can be driven deterministically without a live session. Every non-zero code gets a case, and each asserts a halt with its own message rather than a shared one, so a single catch-all cannot satisfy them collectively.

The three shipped fixtures are updated and re-run through the existing verifier, including both mutations, so the group's discriminating power is preserved rather than merely its green.

## Notes

The shipped fixtures are hand-authored models, and their provenance file records that no spawned worker has ever emitted one. This FR does not close that gap. It does make the receipt the thing a genuine capture would have to carry, which narrows what a future real capture has to prove.
