# STE-460: Repair the lock-evidence guards so the claim-subject repair is detectable and its driver edit is budgeted

## Summary

Two guards this milestone shipped cannot detect the change the next one is about to make. The fence negative was written to prove that a reworded commit subject stops matching, and it does prove that for a single reworded byte — but it stays green when the pattern loses its leading anchor or its trailing space, which are the two widenings a subject repair actually performs.

The window budget has the same shape of problem from the other side. The headroom figure everyone edits against is a comment rather than an assertion, the assertion beside it only checks that headroom is greater than zero, and the two checks meant to bound growth fire in ranges that do not overlap, so a band of growth passes both.

This lands the repairs before the change they must catch, so that change is proven while the defect it fixes is still live rather than after. Nothing here alters shipped behaviour — every criterion below repairs one of this milestone's own assertions.

## Requirement

The claim-subject repair tracked by STE-461 edits two executed fences and one budgeted prose window. Both surfaces are guarded today, and neither guard can detect the specific edit that FR will make. Landing that FR first would mean changing a shipped commit-message format behind assertions that stay green either way — the exact failure mode this milestone exists to have found.

This FR repairs the guards so the subsequent repair is provable. It is a hard prerequisite of STE-461, not adjacent tidying: the ordering follows the precedent AC-STE-456.7 and AC-STE-456.8 set inside this milestone, which is to land the detection before the fix so the detection is proven while the defect is still live.

## Acceptance Criteria

- AC-STE-460.1: The fence negative reddens when the `--grep` pattern loses its `^` anchor. RED-producing input: restore the current one-byte-rewording negative unchanged — measured GREEN today against exactly this widening.
- AC-STE-460.2: The fence negative reddens when the `--grep` pattern loses its trailing space. RED-producing input: as above — measured GREEN today.
- AC-STE-460.3: Both strengthened negatives stay GREEN for every healthy fence form currently shipped, so the strengthening does not overshoot into a false RED. RED-producing input: any healthy fence form that the new negative rejects.
- AC-STE-460.4: The AC-STE-448.9 window headroom is asserted as a **number** equal to the recorded figure, not as `headroom > 0`. RED-producing input: rot the recorded figure to `1` — currently GREEN, because the live assertion only requires positivity.
- AC-STE-460.5: Prose growth of **94** characters and of **95** characters both turn the suite RED. RED-producing input: restore either assertion alone. Measured today: at 94 the headroom assertion reddens; at 95 it goes GREEN again and only `budgetViolations` fires. The two assertions bite in disjoint regimes, so neither alone bounds growth.
- AC-STE-460.6: `AC9_WINDOW` resolves from exactly one definition. RED-producing input: leave either hardcoded `2400` literal in place. Measured today: the cap is defined in three places — one exported constant plus two hardcoded literals in a consumer that does not import it.
- AC-STE-460.7: `expect(furthest).toBeLessThanOrEqual(AC9_WINDOW)` is either removed or made falsifiable, and the `endsAt > AC9_WINDOW` disjunct is resolved as dead code. RED-producing input: keep the assertion as written. `win` is `doc.slice(start, start + AC9_WINDOW)`, so `indexOf` can only return complete in-window matches — `endsAt <= AC9_WINDOW` holds by construction, and an overrun makes `furthest` **decrease** rather than exceed the cap.
- AC-STE-460.8: The second, tighter guarded window — the 61-character row title asserted inside `row.slice(0, 200)`, measured headroom 124 — is **budgeted** by the same mechanism as the 2400-char window, not merely asserted. RED-producing input: grow that row past its headroom and observe the budget stay silent.
- AC-STE-460.9: The pin array's documentation matches the array. RED-producing input: any surviving instance of the three measured discrepancies — the doc comment claims document order twice while the array is not in document order; the comment block is duplicated with a stale copy describing a five-element list; and the same pin set is counted as six in the array, as three (while asserting four) in one test comment, and as five in the follow-ups note.
- AC-STE-460.10: The plan's blast-radius surface count is **derived from the table**, not restated beside it. The assertion reads the count from the **prose sentence** and the row count from the **table**, compares them, and the two sides come from **different expressions** — never one expression feeding both, which is the circularity that makes an assertion incapable of failing. RED-producing input: **add a row to the blast-radius table without touching the prose sentence** — the assertion must redden. Today `expect(plan!).toContain("receives the seven surfaces above")` and `expect(rows.length).toBe(7)` are two hardcoded constants restating one fact; the pair has gone stale **four times**, once per milestone growth, which makes it a mechanism that produces wrongness rather than a number that has been wrong. The three per-surface coverage assertions beside it are correct and stay byte-unchanged.

- AC-STE-460.11: The claim-fence index set is **derived from the fences**, not hardcoded. `CLAIM_FENCE_INDICES = [1, 2]` is a literal — measured complete today (fixture group 10 carries exactly three fences, and exactly indices 1 and 2 carry a claim `--grep`) — but **nothing asserts that the claim-fence set IS {1, 2}**, so a fourth claim fence would be silently unguarded. That is the same failure this FR repairs everywhere else, left in this FR's own instrument. The derivation uses **two independent predicates** — a precise one matching the claim-subject grep, and a broad one matching any `--grep` — and **throws** when they diverge or when the precise set is empty. A single predicate is rejected in both available forms, measured: broad alone over-matches a future unrelated grep fence into a **false RED**; precise alone **silently shrinks** if a later FR renames the claim subject, which is this AC's own defect one level up wearing a better disguise. RED-producing inputs, both to be executed: **(a)** add a fourth `--grep`-carrying claim fence — the derived form must cover it and the hardcoded `[1, 2]` must not; **(b)** add a fence the broad predicate sees and the precise one does not — the divergence throw must **fire**, which is what proves the two predicates are independent rather than one expression wearing two names. If no disagreement can be constructed, the predicates are not independent, the throw can never fire, and the derivation is ceremony — in which case this AC is withdrawn and the hazard recorded instead.

## Technical Design

Three surfaces change, all under `plugins/dev-process-toolkit/tests/`:

1. **`_ac9-row-guard.ts`** — becomes the single definition site for `AC9_WINDOW` (AC.6) and gains the second window's cap alongside it (AC.8). The duplicated/stale doc comment block is collapsed to one block that states the array's real ordering (AC.9).
2. **`m121-ste-456-two-sided-lock-evidence.test.ts`** — the fence negative gains two additional mutations beyond the existing one-byte rewording: anchor-drop and trailing-space-drop (AC.1, AC.2), each asserted to return nothing, with a positive arm asserting healthy forms still match (AC.3). The headroom assertion becomes an equality against the recorded figure (AC.4), the growth battery is extended to cover both 94 and 95 (AC.5), and the unfalsifiable `furthest` assertion is resolved (AC.7).
3. The consumer that hardcodes `2400` twice imports the constant instead (AC.6).
4. **`m121-ste-457-mode-none-claim-instruction.test.ts`** — the blast-radius pin's two hardcoded constants become one derived comparison (AC.10). The count is read from the **prose sentence** by one expression and the row count from the **table** by a different expression, then compared; a single expression feeding both sides would be circular and could not fail. The three per-surface coverage assertions in the same test are correct and stay byte-unchanged.

**Why AC.10's subject is the mechanism, not the number.** The pair has gone stale four times — once per milestone growth — because a prose count and a table are two independently-worded statements of one fact. That is the dominant defect shape in this repository: the same as a leg enum imported by nothing, and the same as a producer and a verifier restating one rule in different words (which STE-461 repairs at AC-STE-461.10). Correcting the constants again would reproduce the mechanism; deriving retires it.

**Ordering constraint.** This FR must be committed before STE-461 touches either fence. The two FRs are independently gatable: this one changes no shipped file, so a failure here is attributable to guard repair alone.

**Overshoot check.** AC.3 exists because a negative strengthened past the real defect converts a healthy run into a false RED — the other half of the vacuity this milestone hunts. Every strengthened negative is run against the current healthy fence forms and asserted to pass.

## Testing

Gate: `bun test` from `plugins/dev-process-toolkit`.

Each criterion carries a named RED-producing input above; each is applied and the resulting failure recorded. Per the mutation-siting rule recorded in the milestone's follow-ups, every mutation is applied to a **sliced region** rather than by first-occurrence replacement, and each is asserted to have changed bytes **at its intended site** — the guards in these files deliberately share one house shape, so a first-occurrence anchor is a trap by construction.

Restores use absolute paths on both sides and are checksum-verified.

Known flake to distinguish from a real RED: `AC-STE-456.6` failed once in seventeen consecutive full-gate runs and could not be reproduced. A single unreproducible failure in that test is not evidence of a defect introduced here.

## Notes

Every defect listed above was found by **executing** mutations against the full gate, not by reading the assertions. Four of them look like ordinary pins.

The two fence-negative gaps were measured directly: dropping the `^` anchor and dropping the trailing space each leave **both** existing tests green. STE-461 removes exactly that trailing space, which is why this FR is a prerequisite rather than a cleanup.

## Implementation notes

**Gate: 7127 pass / 15 skip / 0 fail** at completion (baseline 7078/15/0). Three commits: the authorizing spec commit, the guard repairs, and AC.11's derived index set.

**AC.11 was added mid-FR** by its own `docs(specs)` commit ahead of the change, after the implementer's own prediction that `CLAIM_FENCE_INDICES = [1, 2]` was complete-when-measured and asserted by nothing. Two independent predicates with a divergence throw, because each single form fails in an opposite direction: broad over-matches a future unrelated grep fence into a false RED; precise silently shrinks if a later FR renames the claim subject. Proven on the real document — a 4th claim fence gives `derived=[1,2,3]` where the retired literal gave `[1,2]`, and a release-grep fence makes the predicates disagree and the throw fire naming both sets.

**AC.6's guard was RE-AIMED, not weakened.** It pinned the literal `AC9_WINDOW` where its AC states a property, which blocked consolidating onto the strictly stronger `ac9Window()` (which also calls `assertAnchorUnique`). Checked in the load-bearing direction first — the only thing the literal added was blocking an obfuscated re-derivation the digit scan cannot see, and the accessor blocks that equally because it re-derives nothing. Then proved a real second definition is still caught.

**Four deletions left the gate byte-identically green** when the AUDIT ran, including one on AC.10's own named subject: three bans whose positive twin was `toContain("<IDENTIFIER>")`, satisfied by the `import` line. Repaired by pinning whole assertion expressions.

**Advisory notes.** The reject arms of the fence negatives depend on their paired accept arm for liveness — the pairing is a convention, not an assertion. AC.9's order property is asserted but consumed by nothing (every consumer is order-independent), so it guards a property only human prose depends on. Two raw-substring bans are brittle toward false RED (`200` matches `2000`; `2400` matches `24000`) — deliberate, loud rather than quiet.
