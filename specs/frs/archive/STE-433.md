# STE-433: Gate probe #37's fence scan on the info string {#STE-433}

## Summary

Probe 37 warns when a directory-tree block in the cross-cutting specs names a path that no longer exists on disk. It decides what counts as a tree block by flipping a flag on every triple-backtick line, without ever reading the info string that follows it.

So a Dart, shell, or YAML code block is scanned as though it were a directory tree. On the first real consumer project to exercise the probe, every note it produced was a false positive: package imports and app-relative asset paths that were never tree leaves at all. The module header, the violation text, and the gate-check prose all describe the narrower scope the code does not implement.

Every directory tree this repo authors already opens with a bare fence, so restricting the scan to fences that mark a tree costs no coverage and changes no existing fixture.

## Requirement

Probe #37 `cross_cutting_spec_stale_file_refs` MUST scan only fences whose info string marks a directory tree, so that language-tagged code fences stop producing false positives.

Verified against v2.57.1 at `edd8eaf`:

- **The defect.** `adapters/_shared/src/cross_cutting_spec_stale_file_refs.ts:77-81` — `if (/^\s*```/.test(line)) { inFence = !inFence; continue; }`. The info string is never read.
- **Contract mismatch.** The module header at `:5`, the violation text at `:104` ("directory-tree leaf references missing path"), and `skills/gate-check/SKILL.md:116` all state a directory-tree scope the implementation does not honour.
- **False-positive class 1 — package imports.** `PATH_TOKEN_RE` at `:36` is `(?<![\w/.-])…`; `:` is absent from that class, so a Dart import inside a tagged fence yields a token starting after the colon, which of course does not resolve from the repo root.
- **False-positive class 2 — app-relative literals.** `join(projectRoot, token)` at `:102` resolves every token against the repo root, so a runtime asset path misses its real location under an asset directory.
- **False-positive class 3 — shell path arguments.** Not named in the field report; found during verification. A shell fence containing a two-path copy command produced two additional violations.
- **Reproduced.** A synthetic spec containing one Dart fence and one shell fence produced **4** violations; the same probe returns **0** on this repo today.
- **No coverage is lost.** All 29 bare fences plus 6 YAML, 6 TypeScript and 3 markdown fences were walked in `specs/technical-spec.md`: every tree-glyph line sits inside a **bare** fence. `specs/testing-spec.md` has no fences. `templates/CLAUDE.md.template` and `templates/spec-templates/testing-spec.md.template` are bare-fenced too.

## Acceptance Criteria

- AC-STE-433.1: The scan is restricted to fences whose info string is empty, `text`, or `tree`; the accept-list is an exported constant in the module.
- AC-STE-433.2: A `dart`-tagged fence containing a `package:`-prefixed import statement yields zero violations.
- AC-STE-433.3: A `dart`-tagged fence containing an app-relative asset path string literal yields zero violations.
- AC-STE-433.4: An `sh`-tagged fence containing a shell command with two path arguments yields zero violations.
- AC-STE-433.5: A bare fence whose leaf names a path that does not resolve on disk still yields exactly one violation with `severity: "warning"`.
- AC-STE-433.6: A `text`-tagged fence and a `tree`-tagged fence each behave identically to a bare fence.
- AC-STE-433.7: A tagged fence still closes correctly — a `dart` fence, followed by prose naming a non-existent path, followed by a bare tree fence whose leaf does not resolve, yields exactly one violation.
- AC-STE-433.8: `runCrossCuttingSpecStaleFileRefsProbe` returns zero violations on this repo's root.
- AC-STE-433.9: `skills/gate-check/SKILL.md` entry #37 and the module header both name the accept-list and state that language-tagged fences are out of scope.

## Technical Design

**Track the open fence's info string, not a boolean.** Replace `inFence: boolean` with `fenceInfo: string | null`. A fence line either opens — capture and normalize the info string, stripping any trailing carriage return — or closes, resetting to `null`. Scan only while `fenceInfo` is in the accept-list.

AC-STE-433.7 exists because the obvious shortcut is wrong: filtering out tagged *lines* rather than tracking the open fence desynchronizes the toggle, and a tagged fence's closing marker would then be read as an opening one, leaking the following prose into scan scope. That is a strictly worse failure than the one being fixed, and it is invisible unless a fixture spans a tagged fence and a bare fence in the same file.

**Accept-list, not a migration.** Bare stays canonical because it is what every tree in this repo already uses; `text` and `tree` are accepted so downstream authors who tag for their renderer are not punished. No spec file and no template needs editing.

**Why not the narrower fix.** Excluding tokens preceded by `package:` or `dart:` addresses only the import shape and leaves every other language's syntax to be discovered one incident at a time. It is strictly weaker than the info-string gate and is subsumed by it.

**Why not retire the probe.** It is warn-only, cheap, and it is the only read-side check for tree leaves that go stale through a manual delete or a `git rm`. The false-positive rate that prompted this FR is entirely attributable to scope, not to the underlying matcher.

Prior art cuts both ways and is worth naming: STE-386 deliberately chose a coarse superset over fence parsing for the summary-altitude probe. That is not this case — probe #37 already parses fences, and this FR makes an existing parse correct rather than introducing parsing where none existed.

**Guard rails — tests that MUST NOT change:** all seven existing fixtures in `tests/gate-check-cross-cutting-spec-stale-file-refs.test.ts`. Each was checked and each uses a bare fence, so the info-string gate leaves every one of them passing unmodified. If any existing fixture needs editing to make this FR green, the implementation has over-reached.

**Deferred residual — recorded so it stays findable.** A tree rooted at a subdirectory prints its leaves relative to *that* root, and the probe still resolves them against the repo root. Resolving against a fence-declared root is deliberately out of scope: inferring the root is ambiguous (a first line of `src/` may be root or leaf), the module already concedes the sibling case for bare basenames at `:93-101`, and the probe is warn-only. Shipping the info-string gate without it strictly reduces false positives and adds none. Document the residual in the module header next to the existing bare-basename concession.

## Notes

The field report listed two false-positive classes. Verification found a third — shell-command path arguments — which the info-string gate closes along with the other two. That is the argument for fixing scope rather than special-casing syntaxes: the classes are open-ended, and enumerating them means rediscovering this defect once per language.

This FR is independent of STE-432 and STE-434 and may land in any position within the milestone. It shares only the defect *class* with them: a probe whose stated contract is narrower than its implementation.

## Implementation notes

- **The write-side twin was not fixed, and it is destructive.** `adapters/_shared/src/scan_cross_cutting_spec_refs.ts` still does `if (/^\s*```/.test(line)) { inFence = !inFence; }` with no info-string gate, and `/implement` Phase 4b′ (`skills/implement/SKILL.md`) instructs *"For every `treeLeaf` hit, delete that line … via the Edit tool"*. A deleted file whose basename appears inside one of `specs/technical-spec.md`'s 6 TypeScript or 6 YAML fences would therefore have that **code line silently deleted**. Same defect class as this FR, on the destructive side. Out of STE-433's stated scope (the FR names only probe #37) — **recommend a follow-up FR**.
- `scan_cross_cutting_spec_refs.ts`'s header claims it is used "by the `/gate-check` cross-cutting-spec-stale-file-refs probe as a defense-in-depth read-side check". That is false — probe #37 carries its own scanner and imports only `node:fs` / `node:path`. Pre-existing, but the two fence semantics now diverge, so the false pairing is more misleading than before.
- Module-header residual note reads "alongside the bare-basename concession above"; that concession is an inline comment *below* the header, at the scan loop. Dangling reference, cosmetic.
- `.claude/skills/smoke-test/SKILL.md` fixture 3c stages a stale leaf in `specs/technical-spec.md` without specifying the fence kind. Under the accept-list, staging it in a language-tagged fence makes the probe correctly no-op and would score a healthy probe as FAIL. The fence-kind constraint (bare / `text` / `tree`) should be spelled out there.
- `normalizeFenceInfo`'s `/\r$/` strip is unreachable (the capture class is `[^\r\n]*` and `trim()` would strip CR anyway). Kept because the FR's Technical Design mandates it and it guards a future widening of the capture class.
