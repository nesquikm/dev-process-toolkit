# Close-out offers a retrospective only when a rule tripped

## Summary

Today nothing tells an operator that a retrospective would find something.
This adds one question at the end of an implement run and at the end of a delivery run.
The question appears only when the project turns the offer on and at least one rule tripped.
A delivery run asks it once, never once per milestone and again inside each worker.
Declining prints the command to run later.

## Requirement

### The offer front door

New module `adapters/_shared/src/retro_offer.ts`, front door `bun run retro_offer.ts <projectRoot> <scope>` with the `if (import.meta.main)` guard, in the `video_offer.ts` shape.

### The offer rides an existing call

Operator ruling at the v3.0.0 rebase: with every switch off, a default close-out issues no extra tool call. The retro switch is read inside the two calls v3.0.0 already makes for its own close-out switch, exactly as `upgrade_offer: on` is printed (STE-712, `upgradeOfferSwitchOn`):

- `gate_capture.ts` (the `/implement` step 14 run) and `deliver_decision.ts` (the `/deliver` decision command) each read `retroSwitchOn(projectRoot)` (STE-719) beside `upgradeOfferSwitchOn`. When it is on, each prints one extra line, exactly `retro: on`. A loader refusal reads off.
- The switch lines trail the record in a fixed order: `retro: on`, then `upgrade_offer: on`. With only the retro switch on, `retro: on` is the last line. With both on, `upgrade_offer: on` stays the last line, so the shipped STE-712 contract ("printed `upgrade_offer: on` as its last line"), its skill sentences and the AC-STE-712.14 test literals hold byte for byte, and `retro: on` is the line before it. These one or two lines are the call's trailing switch lines.
- With the retro switch off, each call's stdout is byte-identical to v3.0.0 on every input, with the upgrade switch on or off.
- The archived AC-STE-712.14 prose says that with the upgrade switch off each call prints "exactly its v2.101.5 lines" and "exactly its eight fields". With `retro.enabled` on and the upgrade switch off, that no longer holds, so `specs/frs/archive/STE-712.md` AC-STE-712.14 gains, appended at the end of its line and no other byte changed, the clause `` *(Amended by AC-STE-722.14 (v3.2.0): with `retro.enabled` on, each call also prints `retro: on`, placed before `upgrade_offer: on` so that line stays last; with the retro switch off, the byte-equality above holds as written.)* ``. The test literals of `tests/m_94e6f7-ste-712-upgrade-offer.test.ts` carry no retro key in their fixtures and do not move.
- `upgrade_offer.ts` is not touched: it reads no retro key and its stdout stays byte-identical to v3.0.0.
- The skills run `retro_offer.ts` only when the call's trailing switch lines hold `retro: on`. With the offer off no such line exists, so no retro call is made.
- Every sentence of `skills/implement/SKILL.md`, `skills/deliver/SKILL.md` and `docs/implement-reference.md` that names `retro_offer.ts` also names `retro: on`.

The front door itself:

- Reads `retro.enabled` first, before any scope or ledger read, as a second guard; a loader refusal counts as off.
- Prints nothing and exits 0 when `retro.enabled` is off, the scope resolves to no session, or no rule trips. `retro.enabled` gates this offer and nothing else; `/retro` itself always runs (STE-719, operator ruling R4).
- Otherwise prints `scope=<scope>` and then one line per tripped rule: `rule=<id> <value> <unit> > <threshold>`.
- It calls `resolveRetroScope` and `evaluateRetroRules` (STE-719), never a second derivation. An FR or milestone scope needs `tracking.token_stats` on (STE-719); with it off the offer stays silent and `/retro` names that reason.
- It is read-only and writes no report file; only `/retro` writes one.

## Technical Design

The offer reuses four shipped pieces. The `video_offer.ts` shape gives empty stdout for no prompt. The registry and probe #85 give driven omission. The M_94e6f7 close-out section gives `/deliver` a place to ask, and the M_94e6f7 switch line gives both skills a zero-cost signal. Because workers run `/implement` driven, only the orchestrator asks, so one run yields one question. The threshold lives only in the rule engine, so the offer and the report can never disagree about what tripped.
