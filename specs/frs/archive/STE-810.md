# A toolkit run records the settings it started under

## Summary

Each time a toolkit skill starts, the toolkit writes one row with the settings it started under.
The row holds a hash and the proposable settings only, plus the plugin version and the capture registration state.
A later report can then say which settings a run had, or say that it does not know.
The row is written when any tracking switch is on, not only token stats.
A tree with every switch off writes nothing.

## Requirement

Every start of a `dev-process-toolkit:` skill writes one run-start row carrying a privacy-limited settings snapshot and its hash, taken at the start of the run, so later readers can join a run to the settings it ran under.

## Acceptance Criteria

- AC-STE-810.1: A new module `adapters/_shared/src/run_start.ts` appends one JSON line with schema `dpt-run-start/1` to `.dpt/ledger/run-starts.jsonl`, a path composed only in `dpt_paths.ts` as `runStartLedgerPath(root)`. The row has exactly the keys `schema`, `session_id`, `skill`, `fr`, `started_at`, `settings_hash`, `settings`, `plugin_version` and `registration`.
- AC-STE-810.2: `settings` maps every `PROPOSABLE_SETTINGS` key, and no other key, to its current value or to the literal `"absent"` when the key is not set. A test plants a non-proposable settings key holding a unique string and proves that string appears nowhere in the ledger file.
- AC-STE-810.3: `settings_hash` is the sha256 hex of the canonical JSON (keys sorted at every level) of `{ settings, plugin_version, registration }`. Changing any one of the three changes the hash. Reordering the settings file with equal values does not. `plugin_version` is the `version` in the running plugin's `.claude-plugin/plugin.json`, or `"unknown"` when unreadable. `registration` is `captureStatus(root).registration`.
- AC-STE-810.4: A new hook entrypoint, registered in `hooks/hooks.json` on PreToolUse with matcher `Skill` and on UserPromptSubmit, records a start when the invoked skill is `dev-process-toolkit:<name>` (the prompt form: a prompt whose first token is `/dev-process-toolkit:<name>`). `fr` is the first argument token equal to the stem of a file in `specs/frs/` or `specs/frs/archive/`, else `null`. Any other skill, or a prompt that is not such a command, records nothing.
- AC-STE-810.5: A row is written only when the checkout root has a toolkit settings file (`specs/settings.yaml`) and at least one `tracking.<name>.enabled` in it is `true`. A legacy tree whose settings still live in CLAUDE.md records nothing until `/dev-process-toolkit:upgrade` moves them. A tree with `token_stats` off and `gate_outcomes` on records. A tree with every switch off records nothing, and its hook run loads no module beyond Node built-ins.
- AC-STE-810.6: The hook is fail-open: on any error it writes nothing, prints nothing on stdout, and exits 0, so it never blocks a tool call or a prompt.
- AC-STE-810.7: `bun run adapters/_shared/src/run_start.ts <projectRoot> <skill> [<fr>]` records a start for the session named by `CLAUDE_CODE_SESSION_ID` (under the same gate as AC-STE-810.5) and prints `settings_hash=<hex>`, or `skipped: no tracking switch is on`. With no session id it refuses in the NFR-10 shape and writes nothing.
- AC-STE-810.8: `docs/retro-reference.md` describes the run-start ledger, its keys, the any-switch gate and the proposable-keys-only privacy rule.
- AC-STE-810.9: `bun test` from `plugins/dev-process-toolkit` reports 0 failures, and its skip identities equal the trunk baseline by name.

## Technical Design

`run_start.ts` exports `snapshotSettings(root)`, `recordRunStart(root, { session, skill, fr, at })` and `readRunStarts(root, session?)`. The hook script `templates/hooks/process/run-start-snapshot.sh` execs `_lib/hooks/run-start-snapshot.ts`, which takes a built-ins-only fast path (skill prefix, a settings file containing `enabled: true`) before any dynamic import, as the STE-717 fold does. Setting values are read raw from `specs/settings.yaml` (`settingsSectionValue`), because the loader fills defaults and a snapshot must tell an absent key from a default. The append is a single `appendFileSync` of one line.

## Testing

Unit tests on the snapshot (privacy plant, hash stability and sensitivity, absent values) and on the hook entrypoint driven with synthetic stdin payloads for Skill, UserPromptSubmit and foreign skills, each switch combination, and an unreadable settings file. Existing hooks.json shape tests are amended for the new entries.

## Notes

The snapshot is taken at run start, not at SessionEnd or Stop, because a setting can change mid-session. Rows written before this release have no snapshot; STE-813 reads them as settings unknown.

## Implementation notes

- the run-start hook swallows every error silently — AC-STE-810.6 requires the hook to fail open
- a repeated Skill call can write a second start row for the same run — readers take the earliest row, so a duplicate changes no join
- the hook runs under the 5000 ms hook timeout — measured p50 well under 300 ms (PR body)
