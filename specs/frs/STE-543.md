# Gate probe grading recorded external-link verdicts

## Summary

Every probe here reads files and nothing else, and two say so in shipped prose.

A probe making its own requests would overturn that in a direction the gate cannot defend: it would fail differently depending on where it ran, and a machine with no egress would look like one facing dead links.

So it grades the verdict the author recorded, failing on a dead link something depends on and declining to fail on what it cannot be sure of.

## Requirement

The probe walks both reference sections across the spec tree, active and archived, and grades each recorded verdict. A dead link classified as required fails the gate. A dead informational link, a stale record, and a missing record on an informational link are reported without failing. A required link with no record at all fails, because the check never ran.

## Acceptance Criteria

- AC-STE-543.1: The probe walks `## Design References` and `## External References` across the spec glob, active and archived alike, and grades each row's recorded verdict using only file reads — no network and no git, so the purity claims in probes #68 and #69 need no edit.
- AC-STE-543.2: A recorded-dead link classified as required is GATE FAILED; a recorded-dead informational link is GATE PASSED WITH NOTES.
- AC-STE-543.3: A required link carrying no record at all is GATE FAILED, because the check never ran; an informational link carrying no record is NOTES.
- AC-STE-543.4: A record older than the exported staleness threshold is NOTES and never GATE FAILED.
- AC-STE-543.5: Every violation renders in the NFR-10 canonical shape naming the spec file, the one-indexed line, and the offending URL.
- AC-STE-543.6: The check is falsifiable: removing the verdict comparison turns a fixture carrying a recorded-dead required link green, asserted by a mutation test.
- AC-STE-543.7: The probe passes vacuously on a project where neither reference section exists, which is the state of this repository at the time the probe ships.
- AC-STE-543.8: The probe-count bump lands at every pinned surface — the two README occurrences, the gate-check skill file, and each test file carrying the previous count — edited by subject and never by digit: the assertion naming `stage_block_adoption`'s own probe number must still read 82 afterwards, and a sweep that rewrites it is a regression this AC forbids. Any count assertion that cannot fail is repaired before the bump, so the new count is enforced rather than merely written.

## Technical Design

New `adapters/_shared/src/external_link_verdicts.ts` exporting `PROBE_ID`, `runExternalLinkVerdictsProbe(projectRoot, now = new Date(), rules = VERDICT_RULES)`, plus an `if (import.meta.main)` front door — `skills/gate-check/SKILL.md:245` makes a registration whose module lacks one turn probe #81 red; that line's own "probe #82" literal moves to #83. Section names, the row parser and `EXTERNAL_LINK_TTL_DAYS` import from STE-542's `external_link_record.ts`: one parser, never a reader-side copy. Headings come from `walkSections` (`markdown_section_walk.ts:173`); the spec glob lifts out of `scan_design_references.ts`'s private `listSpecFiles` (line 77) so active and `archive/` stay one list. `scan_design_references.ts:51` still drops URLs — unchanged. Report is `{violations, notes, vacuous}`: `notes` per `best_practices_manifest_hygiene.ts:37`, `vacuous` and the violation shape per `runnability_declared.ts:73`. Staleness grades before classification, so a stale dead+required row is NOTES. Registers as probe #83.

## Testing

**AC.1 — both sections, active and archive.** Fixture tree carries `specs/requirements.md`, `specs/frs/STE-543.md`, `specs/frs/archive/STE-100.md` and `specs/plan/M140.md`, each with one `## Design References` row and one `## External References` row. Assert a PER-SECTION row count per file, not a total: a total of eight is reachable by walking one section twice. Isolating half: the same URL under `## Notes` and under an h3 `### External References` yields zero rows, so the section match is doing the work. Purity legs, both with positive controls because both are absence claims: (a) run the probe with `globalThis.fetch` replaced by a counting double and assert `calls === 0`, and in the same test invoke the double once directly and assert `calls === 1` — a call count on a double that was never wired reads clean; (b) read the module source and assert it names none of `node:child_process`, `node:https`, `node:http`, `node:net` or a git helper — the fetch double covers only the `fetch` path, so a socket module would otherwise pass both legs — with the control that the identical search DOES find `node:child_process` in `adapters/_shared/src/falsifiability_harness.ts:22`, proving the search can hit. Finally assert probes #68/#69 need no edit by pinning their existing `no git, no network` purity substrings at `skills/gate-check/SKILL.md:155` and `:156` — unchanged bytes, asserted rather than assumed.

**AC.2 — recorded dead.** Two fixtures differing in exactly one token (the classification). Required: `violations.length === 1`, `severity === "error"`, zero notes rows for that link. Informational: `violations` empty, exactly one notes row naming the URL. Guard the isolation itself — diff the two fixture strings and assert exactly one line differs, so the verdict flip cannot be caused by some other edit.

**AC.3 — no record at all.** Required link with no record: one violation whose `reason` names the missing record and whose `message` says the check never ran (distinct text from AC.2's dead-link reason — assert the two reasons are not equal, or a single generic message would satisfy both legs). Informational with no record: zero violations, one notes row. Same one-token isolation as AC.2.

**AC.4 — TTL.** `now` is injected, never read from the wall clock: a wall-clock test passes today and rots silently. Boundary pair on the same dead+required fixture — `checked_at` exactly `EXTERNAL_LINK_TTL_DAYS` old still yields the violation; one day older yields zero violations and one staleness notes row. Because that row's recorded verdict is dead AND required, the leg proves staleness OUTRANKS classification rather than merely coinciding with an already-clean row.

**AC.5 — NFR-10 shape.** `note` matches `/^specs\/[^:]+:\d+ — /`; `message` carries `Remedy:` and `Context:` sub-lines and contains the offending URL verbatim, following probe #61 (`skills/gate-check/SKILL.md:148`). The violation record is `RunnabilityDeclaredViolation`-shaped (`runnability_declared.ts:73` — `{file, line, severity, reason, note, message}`); the report's `notes: string[]` follows `best_practices_manifest_hygiene.ts:37`, since `RunnabilityDeclaredReport` carries no `notes` field. Isolating half: a fixture with two dead required links in different files yields two violations with different `file:line` pairs and different URLs — one message reused for both passes a single-row assertion.

**AC.6 — falsifiability.** The rule table is a parameter, mirroring `runUpgradeStalenessProbe(projectRoot, registry)` (`upgrade_staleness.ts:137`, registry defaulted second). Build `mutant = VERDICT_RULES.filter(r => r.id !== "dead-required")` and assert `mutant.length === VERDICT_RULES.length - 1` FIRST — counts, not presence: a filter that matched nothing leaves the suite green and reads as a pass. Then the recorded-dead-required fixture yields one violation under `VERDICT_RULES` and zero under `mutant`.

**AC.7 — vacuity.** A spec tree with neither section returns `{violations: [], notes: [], vacuous: true}`; absent `specs/` likewise, with no throw. Positive control in the same test: adding one `## External References` row to that same tree flips `vacuous` to false and returns at least one row, so vacuous is a measured state and not a scan that silently found nothing.

## Notes

No network by design: a fetching probe fails differently per machine, and probes #68/#69 restate that purity in shipped prose. Staleness downgrades rather than escalates — a stale record is evidence about the past, not a verdict now. A second reader-side parser was rejected; producer/consumer asymmetry has shipped here three times. README's pins sit at lines 14 and 109.
