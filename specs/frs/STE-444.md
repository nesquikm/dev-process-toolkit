# Correct the contradictory Jira milestone-binding prose

## Summary

The spec-writing skill carries two instructions about Jira milestone binding that cannot both be followed. One section describes creating the milestone epic first and deriving the milestone identity from its tracker-assigned key. Another section — the one on the path a run actually takes when it creates a feature ticket — says Jira read-merge-writes a milestone label. A model reading the file in order meets the second at the moment it acts, and what the consumer projects contain matches the second exactly.

Separately, the gate-check skill's row for this probe carries two false statements on a single line. It claims a binding value is wired in production from the active adapter's schema frontmatter, when nothing anywhere parses that key and the resolver reads it from a provider object instead. And it names only two of the three binding kinds the code handles, omitting the epic branch entirely.

In this toolkit the prose is what a model executes, so documentation contradicting the code is a defect rather than a nitpick.

## Requirement

No surface may describe Jira milestone binding as label-only where the epic path applies, and no surface may assert a wiring that does not exist. Every claim about which binding kinds are handled must match the code, and the corrections must be pinned so they cannot silently regress.

## Acceptance Criteria

- AC-STE-444.1: `skills/spec-write/SKILL.md` line 111 no longer states unconditionally that Jira read-merge-writes the milestone label. It defers to the binding kind, so it no longer contradicts the Epic-first description in the same file. {#AC-STE-444.1}
- AC-STE-444.2: `skills/gate-check/SKILL.md` line 81 no longer claims the binding value is wired in production from the active adapter's Schema M frontmatter. No parser for that key exists, and the resolver reads the value from a provider object. {#AC-STE-444.2}
- AC-STE-444.3: The same line enumerates all three binding kinds the code handles — object, label, and epic — rather than the two it names today. {#AC-STE-444.3}
- AC-STE-444.4: A grep-shape meta-test pins all three corrections: the absence of the unconditional label claim, the absence of the false wiring claim, and the presence of the epic kind in the enumeration. Each assertion fails against the pre-change files. {#AC-STE-444.4}
- AC-STE-444.5: `skills/spec-write/SKILL.md` stays within its 358-line cap measured as `split("\n").length` and introduces no new `STE-<N>` token; `skills/gate-check/SKILL.md` stays within its 354-line cap. {#AC-STE-444.5}
- AC-STE-444.6: `bun test` from `plugins/dev-process-toolkit` is green with zero failures. {#AC-STE-444.6}

## Technical Design

Both files sit at or near their line caps and the skills tree has no headroom on its ticket-token ceiling, so every correction must trade bytes rather than add them. This is a rewrite-in-place exercise, not an expansion, and the line-cap assertions in AC-STE-444.5 are the guard that keeps it honest.

The spec-write correction is the load-bearing one. Its sentence sits on the FR-creation path, which is where a model is when it decides what to do, so it wins any contest with a description elsewhere in the file. Making it defer to the binding kind rather than assert one removes the contradiction without duplicating the Epic-first recipe into a second place, which would create a third surface to keep in sync.

The gate-check line carries two independent defects that happen to share a sentence, and they need separate fixes: one removes a claim about where a value comes from, the other adds a missing member to an enumeration. Treating them as one edit risks fixing the visible half and leaving the other.

The meta-test is deliberately grep-shaped rather than semantic. The repository's precedent for pinning prose is literal substring matching, and it is the only form that fails loudly when a future copy edit reintroduces the claim. AC-STE-444.4's requirement that each assertion fail against the pre-change files is what separates a real pin from one that would pass against any text.

## Testing

The meta-test asserts three things about the shipped files: the unconditional label claim is gone, the false wiring claim is gone, and the epic kind is present in the enumeration. Each is verified to fail against the files as they stand before this change — a pin that passes both before and after is not a pin.

Line-cap and token-ceiling assertions follow the existing shapes in this repository and are extended rather than newly written.

No runtime behaviour changes in this FR, so there is nothing to exercise beyond the file contents themselves.

## Notes

The false wiring claim is the more dangerous of the two, because it describes a mechanism an implementer would reasonably build against. Someone reading it would look for a frontmatter parser, find none, and either write one that no code path consumes or conclude the documentation is stale and stop trusting it. Both outcomes are worse than silence.

The contradiction between the two spec-write sections is the direct cause of the milestone drift its sibling FR detects. Fixing the prose does not make the epic path execute — nothing does today — but it stops the file from instructing two different behaviours depending on where a reader enters it.
