# A token claim survives the next session-end capture

## Summary

When an FR is archived, the token stats for its sessions are claimed for that FR in the ledger.
Those sessions are still running, and each time one stops, the capture hook rewrites its rows.
The rewrite drops every claim, so the release rollup later finds no rows for the FR.
This fix keeps each claim when a session's rows are written again.

## Requirement

### Steps to reproduce

1. Write a token ledger holding rows for a live session `syn-session-1` on a feature branch: one implement row and one tdd row.
2. Claim the FR's rows with `claimRowsForFR` for `STE-900`, which persists `claimed_by` on both rows.
3. Run `writeSessionRows` for `syn-session-1` with freshly derived rows, as the Stop hook does.

### Expected

Both rows still carry `claimed_by: STE-900`, with their token counts updated.

### Actual

Both rows lose `claimed_by`. The session's rows are dropped and the fresh ones are appended without any claim.

## Acceptance Criteria

- AC-STE-698.1: Regression: `tests/m_46b121-STE-698-claim-survives-capture.test.ts › a claim made mid-session survives the next session-row write` fails before the fix and passes after it.
- AC-STE-698.2: `writeSessionRows` carries each existing row's `claimed_by` value onto the fresh row of the same session with the same skill and model, including a demotion to the design bucket.
- AC-STE-698.3: A fresh row with no earlier row of the same skill and model carries no claim, and a fresh row never takes a claim from another session's row.
- AC-STE-698.4: Rows of other sessions stay byte-identical across the write.
- AC-STE-698.5: After a claim and a later capture write, the milestone rollup renders a bucket for the claimed FR.
- AC-STE-698.6: Removing the carry-forward reddens the regression test, and keying it by skill alone reddens a test with two models under one skill.
- AC-STE-698.7: `bun test` from `plugins/dev-process-toolkit` reports 0 failures, and its skip identities equal the trunk baseline by name.

## Technical Design

### Root cause

The capture hook re-derives a whole session from the transcript on every Stop and SessionEnd fire. `writeSessionRows` drops the session's rows and appends the fresh ones, so a `claimed_by` mark that `claimRowsForFR` wrote while the session was live is lost.

The fix reads the dropped rows' claims into a map keyed by skill and model, and copies each claim onto the matching fresh row before the write.

## Testing

Unit tests over temporary ledgers with synthetic session ids, plus one rollup render after a claim and a capture write.

## Notes

Origin: a maintainer follow-up from shipping v2.101.1, where the archive rendered rows for its FR but the ledger held no claims afterwards. Rows whose claims were already lost stay unclaimed, and writing these specs saw the brainstorm bridge offer them to new FRs; they were declined by hand.
